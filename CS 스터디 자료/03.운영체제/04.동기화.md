# 04. 프로세스 동기화 (Synchronization)

> **학습 목표**
> - 경쟁 상태와 임계 영역의 의미를 예시로 설명할 수 있다.
> - 임계 영역 문제 해결의 3가지 조건을 말할 수 있다.
> - 뮤텍스, 세마포어, 모니터의 차이를 설명할 수 있다.
> - Java의 synchronized, volatile, Atomic을 구분해 사용할 수 있다.

---

## 1. 경쟁 상태 (Race Condition)

**여러 프로세스/스레드가 공유 자원에 동시에 접근할 때, 실행 순서에 따라 결과가 달라지는** 상황입니다.

### 예시: count++
`count++`는 한 줄이지만 CPU에서는 3단계입니다.
```
1. LOAD  count → 레지스터     (읽기)
2. ADD   레지스터 + 1          (계산)
3. STORE 레지스터 → count     (쓰기)
```

두 스레드가 동시에 실행하면:
```
count = 0
스레드 A: LOAD (0)
스레드 B: LOAD (0)          ← A가 쓰기 전에 B가 읽음
스레드 A: ADD → 1, STORE → count = 1
스레드 B: ADD → 1, STORE → count = 1    ← 2가 되어야 하는데 1!
```

```java
class Counter {
    int count = 0;
    void increment() { count++; }   // 스레드 안전하지 않음
}
// 스레드 2개가 각각 100만 번 호출 → 결과가 200만보다 작게 나옴
```

## 2. 임계 영역 (Critical Section)

**공유 자원에 접근하는 코드 영역**입니다. 한 번에 하나의 스레드만 실행해야 합니다.

```
do {
    [진입 영역]   ← 들어가도 되는지 확인 (락 획득)
    [임계 영역]   ← 공유 자원 접근
    [퇴출 영역]   ← 나간다고 알림 (락 해제)
    [나머지 영역]
} while (true);
```

### 해결 조건 3가지
| 조건 | 의미 |
|---|---|
| **상호 배제** (Mutual Exclusion) | 한 스레드가 임계 영역에 있으면 다른 스레드는 들어갈 수 없다 |
| **진행** (Progress) | 임계 영역이 비어 있으면, 들어가려는 스레드가 들어갈 수 있어야 한다 |
| **한정 대기** (Bounded Waiting) | 무한정 기다리면 안 된다 (기아 방지) |

## 3. 동기화 도구

### 3-1. 하드웨어 지원: 원자적 명령어
- **Test-and-Set**, **Compare-and-Swap (CAS)**: 읽기·비교·쓰기를 **끊기지 않는 하나의 명령어**로 실행
- 모든 락의 기반이 됩니다.

```
CAS(메모리주소, 기대값, 새값):
  if (*주소 == 기대값) { *주소 = 새값; return true; }
  return false;
  → 이 전체가 원자적으로 실행됨
```

### 3-2. 뮤텍스 (Mutex, Mutual Exclusion Lock)
- **락을 가진 하나의 스레드만** 임계 영역에 들어갈 수 있습니다.
- `lock()` → 임계 영역 → `unlock()`
- **락을 획득한 스레드만 해제할 수 있습니다.** (소유권 개념)

### 3-3. 스핀락 (Spinlock)
- 락을 얻을 때까지 **반복문을 돌며 계속 확인**(바쁜 대기, busy waiting)
- 컨텍스트 스위칭이 없어 **락이 금방 풀리는 경우** 효율적 (멀티코어)
- 오래 기다리면 CPU 낭비

### 3-4. 세마포어 (Semaphore)
**정수 변수 S**와 두 원자적 연산으로 이루어집니다.
```
wait(S)  / P(S):  S--; if (S < 0) 대기 큐에서 잠듦
signal(S)/ V(S):  S++; if (S <= 0) 대기 중인 스레드 하나 깨움
```

| 종류 | S 범위 | 용도 |
|---|---|---|
| **이진 세마포어** | 0 또는 1 | 뮤텍스처럼 상호 배제 |
| **카운팅 세마포어** | 0 ~ N | **N개의 자원**에 동시 접근 허용 (DB 커넥션 풀 10개) |

- 세마포어는 **소유권이 없어** 다른 스레드가 signal 할 수 있습니다. → 스레드 간 **순서 제어(신호)** 에도 사용

### 뮤텍스 vs 세마포어
| 항목 | 뮤텍스 | 세마포어 |
|---|---|---|
| 동시 접근 수 | 1개 | N개 |
| 소유권 | **있음** (잠근 스레드만 해제) | 없음 |
| 용도 | 상호 배제 | 상호 배제 + 자원 개수 관리 + 순서 제어 |

### 3-5. 모니터 (Monitor)
세마포어는 `wait/signal` 순서를 잘못 쓰면 데드락이나 상호 배제 실패가 생깁니다. 모니터는 **언어 차원에서 상호 배제를 자동으로 보장**하는 고수준 동기화 도구입니다.

- 모니터 안의 메서드는 **한 번에 하나의 스레드만** 실행
- 조건 변수(condition variable)로 `wait()` / `notify()` 제공
- **Java의 `synchronized` + `wait()/notify()`** 가 모니터입니다.

## 4. 고전적 동기화 문제

### 생산자-소비자 (Bounded Buffer)
- 생산자는 버퍼가 **꽉 차면** 대기, 소비자는 버퍼가 **비면** 대기
- 세마포어 3개: `mutex`(버퍼 접근), `empty`(빈 칸 수), `full`(찬 칸 수)
- Java: `BlockingQueue`가 이 문제를 해결해 줌

### 읽기-쓰기 (Readers-Writers)
- 읽기는 **여럿이 동시에** 가능, 쓰기는 **혼자만**
- Java: `ReentrantReadWriteLock`

### 식사하는 철학자 (Dining Philosophers)
- 원형 테이블에 철학자 5명, 젓가락 5개. 모두 왼쪽 젓가락을 동시에 집으면 **데드락**
- 해결: 홀수 번은 왼쪽 먼저, 짝수 번은 오른쪽 먼저 / 동시에 4명만 앉게 제한
- (→ `05.데드락.md`)

## 5. Java 동기화

```java
// 1) synchronized: 모니터 락
class Counter {
    private int count = 0;
    public synchronized void increment() { count++; }
    public synchronized int get() { return count; }
}

// 2) ReentrantLock: 타임아웃, 공정성, tryLock 등 세밀한 제어
Lock lock = new ReentrantLock();
lock.lock();
try {
    count++;
} finally {
    lock.unlock();          // 반드시 finally에서 해제
}

// 3) Atomic: CAS 기반, 락 없이 원자적 연산 (단일 변수에 효율적)
AtomicInteger atomic = new AtomicInteger();
atomic.incrementAndGet();

// 4) Semaphore: 동시 접근 수 제한
Semaphore sem = new Semaphore(3);
sem.acquire();
try { /* 최대 3개 스레드만 */ } finally { sem.release(); }
```

### volatile
```java
private volatile boolean running = true;
```
- 변수를 CPU 캐시가 아닌 **메인 메모리에서 읽고 쓰도록** 보장 → **가시성(visibility)** 해결
- **원자성은 보장하지 않습니다.** `volatile int count; count++;` 는 여전히 경쟁 상태
- 용도: 한 스레드만 쓰고 여러 스레드가 읽는 플래그

| 도구 | 가시성 | 원자성 | 비고 |
|---|---|---|---|
| volatile | O | X | 플래그용 |
| synchronized | O | O | 블로킹 |
| Atomic* | O | O (단일 변수) | 논블로킹 CAS |

## 6. 면접 질문

1. **경쟁 상태란? 예를 들어 설명해 주세요.**
   → 여러 스레드가 공유 자원에 동시에 접근해 실행 순서에 따라 결과가 달라지는 상황입니다. `count++`가 읽기·계산·쓰기 세 단계라 중간에 끼어들면 값이 유실됩니다.
2. **뮤텍스와 세마포어의 차이는?**
   → 뮤텍스는 하나의 스레드만 접근하며 락을 건 스레드만 해제할 수 있고, 세마포어는 카운터로 N개의 접근을 허용하며 소유권이 없습니다.
3. **volatile만으로 count++를 안전하게 만들 수 있나요?**
   → 아닙니다. volatile은 가시성만 보장하고 원자성은 보장하지 않아 synchronized나 AtomicInteger가 필요합니다.
4. **스핀락은 언제 유리한가요?**
   → 멀티코어 환경에서 락 보유 시간이 매우 짧아, 잠들고 깨는 컨텍스트 스위칭 비용보다 잠깐 도는 비용이 더 쌀 때입니다.

## 핵심 정리
- 경쟁 상태 → 임계 영역 보호 (상호 배제·진행·한정 대기)
- 뮤텍스(1개, 소유권) / 세마포어(N개, 소유권 X) / 모니터(언어 수준, Java synchronized)
- volatile = 가시성만, 원자성은 synchronized/Atomic
