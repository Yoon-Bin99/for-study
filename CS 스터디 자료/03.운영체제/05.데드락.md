# 05. 데드락 (Deadlock, 교착 상태)

> **학습 목표**
> - 데드락의 정의와 발생 조건 4가지를 말할 수 있다.
> - 예방, 회피(은행원 알고리즘), 탐지·회복, 무시 전략을 비교할 수 있다.
> - Java 코드에서 데드락이 생기는 상황과 해결법을 설명할 수 있다.

---

## 1. 개념

**둘 이상의 프로세스가 서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상태**입니다.

```
     자원 A를 가짐              자원 B를 가짐
  [프로세스 1] ──B를 요청──> (자원 B)
       ↑                        │
    (자원 A) <──A를 요청── [프로세스 2]

  P1은 B를 기다리고, P2는 A를 기다림 → 둘 다 영원히 대기
```

비유: 좁은 다리 양쪽에서 차가 동시에 진입해 서로 비켜 주기만 기다리는 상황

---

## 2. 발생 조건 4가지 (모두 만족해야 발생)

| 조건 | 의미 |
|---|---|
| **상호 배제** (Mutual Exclusion) | 자원을 한 번에 하나의 프로세스만 사용 |
| **점유 대기** (Hold and Wait) | 자원을 가진 채로 다른 자원을 기다림 |
| **비선점** (No Preemption) | 다른 프로세스의 자원을 강제로 뺏을 수 없음 |
| **순환 대기** (Circular Wait) | P1 → P2 → ... → Pn → P1 처럼 대기가 원형으로 이어짐 |

> **하나라도 깨면 데드락은 발생하지 않습니다.** 이것이 "예방" 전략의 핵심입니다.

---

## 3. 자원 할당 그래프 (Resource Allocation Graph)

```
P → R : 프로세스가 자원을 요청
R → P : 자원이 프로세스에 할당됨

  P1 → R1 → P2 → R2 → P1     ← 사이클 존재
```

- 각 자원의 인스턴스가 **하나씩**이면: 사이클 = 데드락
- 인스턴스가 **여러 개**면: 사이클이 있어도 데드락이 **아닐 수 있음**

---

## 4. 데드락 처리 방법

### 4-1. 예방 (Prevention): 4가지 조건 중 하나를 원천 차단

| 깨는 조건 | 방법 | 문제점 |
|---|---|---|
| 상호 배제 | 자원을 공유 가능하게 | 프린터 같은 자원은 불가능 |
| 점유 대기 | 시작할 때 **필요한 자원을 한꺼번에** 요청 | 자원 낭비, 기아 |
| 비선점 | 자원을 못 얻으면 **가진 것을 모두 반납** | 작업 손실 |
| **순환 대기** | 자원에 **번호를 매기고 오름차순으로만** 요청 | 가장 현실적 |

### 4-2. 회피 (Avoidance): 위험해 보이면 할당하지 않음

자원을 할당하기 전에 **할당 후에도 시스템이 안전 상태(Safe State)인지** 검사합니다.

- **안전 상태**: 모든 프로세스가 끝까지 실행될 수 있는 순서(**안전 순서열**)가 존재하는 상태
- 불안전 상태가 곧 데드락은 아니지만, 데드락이 생길 **가능성**이 있음

#### 은행원 알고리즘 (Banker's Algorithm)
은행이 대출해 줄 때 "모든 고객이 최대 대출액을 요청해도 갚을 수 있는 순서가 있는가?"를 확인하는 것과 같습니다.

```
사용 가능 자원: 3

        최대 필요  현재 할당  추가 필요(Need)
P0         10         5          5
P1          4         2          2
P2          9         2          7

1) P1의 Need 2 ≤ 가용 3 → P1 실행 완료 → 가용 3 + 2 = 5
2) P0의 Need 5 ≤ 가용 5 → P0 완료 → 가용 5 + 5 = 10
3) P2의 Need 7 ≤ 가용 10 → P2 완료
안전 순서열 <P1, P0, P2> 존재 → 안전 상태
```

- 단점: 프로세스가 **최대 필요량을 미리 알려야** 하고, 매 요청마다 검사 오버헤드 → 실제 범용 OS에서는 거의 안 씀

### 4-3. 탐지 및 회복 (Detection & Recovery)

데드락을 허용하되, 주기적으로 **탐지(자원 할당 그래프의 사이클 검사)** 하고 발생하면 회복합니다.

회복 방법:
- **프로세스 종료**: 데드락에 걸린 프로세스를 모두 종료하거나, 하나씩 종료하며 확인
- **자원 선점**: 프로세스의 자원을 뺏어 다른 프로세스에 줌 (롤백 필요, 같은 프로세스만 계속 희생되는 기아 주의)

> **DB가 이 방식을 씁니다.** MySQL InnoDB는 락 대기 그래프에서 사이클을 탐지하면 비용이 적은 트랜잭션 하나를 롤백합니다.

### 4-4. 무시 (Ostrich Algorithm, 타조 알고리즘)
데드락이 드물게 발생하므로 **아무것도 하지 않고**, 생기면 사용자가 재시작합니다. 예방·회피 비용이 더 크기 때문입니다.

> **Windows, Linux 등 대부분의 범용 OS가 이 방식**입니다. 데드락 방지는 응용 프로그램 개발자의 몫입니다.

## 5. 데드락 vs 기아 vs 라이브락

| 구분 | 상태 | 비유 |
|---|---|---|
| 데드락 | 서로 기다리며 **모두 멈춤** | 다리 위에서 마주친 두 차 |
| 기아 (Starvation) | 특정 프로세스만 **계속 밀림** | 끼어들기 때문에 영원히 못 들어가는 차 |
| 라이브락 (Livelock) | 계속 움직이지만 **진행이 없음** | 복도에서 서로 같은 방향으로 계속 비켜 주는 두 사람 |

## 6. Java에서의 데드락

```java
Object lockA = new Object();
Object lockB = new Object();

// 스레드 1
synchronized (lockA) {
    Thread.sleep(100);
    synchronized (lockB) { /* ... */ }    // B를 기다림
}

// 스레드 2
synchronized (lockB) {
    Thread.sleep(100);
    synchronized (lockA) { /* ... */ }    // A를 기다림 → 데드락
}
```

### 해결 방법
1. **락 순서 통일** (순환 대기 제거): 모든 스레드가 A → B 순서로만 획득
2. **tryLock + 타임아웃** (점유 대기 제거)
```java
if (lockA.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lockB.tryLock(1, TimeUnit.SECONDS)) {
            try { /* 작업 */ } finally { lockB.unlock(); }
        }
    } finally { lockA.unlock(); }
}
```
3. 락 범위 최소화, 중첩 락 피하기

> **실무 팁**: 계좌 이체처럼 두 계좌를 동시에 잠글 때, **계좌 ID가 작은 쪽을 먼저** 잠그면 데드락을 예방할 수 있습니다. DB에서도 여러 행을 업데이트할 때 **항상 같은 순서(PK 오름차순)** 로 업데이트하면 데드락이 줄어듭니다.

### 데드락 확인
```bash
jstack <pid>      # "Found one Java-level deadlock" 출력
```

## 7. 면접 질문

1. **데드락 발생 조건 4가지는?**
   → 상호 배제, 점유 대기, 비선점, 순환 대기입니다. 네 가지가 모두 성립해야 발생합니다.
2. **데드락을 예방하는 가장 현실적인 방법은?**
   → 자원에 순서를 매기고 정해진 순서대로만 획득해 순환 대기를 없애는 것입니다.
3. **은행원 알고리즘이란?**
   → 자원을 할당하기 전에 할당 후에도 안전 순서열이 존재하는지 검사해 안전할 때만 할당하는 회피 기법입니다.
4. **대부분의 OS가 데드락을 무시하는 이유는?**
   → 발생 빈도에 비해 예방·회피·탐지 비용이 크기 때문입니다.

---

## 핵심 정리
- 4조건: 상호 배제 + 점유 대기 + 비선점 + 순환 대기 (모두 만족 시 발생)
- 예방(조건 제거) / 회피(은행원) / 탐지·회복(DB) / 무시(범용 OS)
- 실무 해결: 락 획득 순서 통일, tryLock 타임아웃
