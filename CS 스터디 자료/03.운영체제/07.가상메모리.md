# 07. 가상 메모리 (Virtual Memory)

> **학습 목표**
> - 가상 메모리와 요구 페이징의 개념을 설명할 수 있다.
> - 페이지 폴트 처리 과정을 순서대로 말할 수 있다.
> - 페이지 교체 알고리즘(FIFO, OPT, LRU, LFU, Clock)을 직접 계산할 수 있다.
> - 스래싱의 원인과 해결책을 설명할 수 있다.

---

## 1. 가상 메모리란?

**프로세스 전체를 메모리에 올리지 않고 필요한 부분만 올려서**, 실제 물리 메모리보다 큰 프로그램을 실행할 수 있게 하는 기법입니다.

```
프로세스가 보는 가상 주소 공간 (예: 64비트 → 매우 큼)
+---------+
| Page 0  | ──> 물리 메모리 프레임 3
| Page 1  | ──> 디스크 (스왑 영역)   ← 아직 안 올라옴
| Page 2  | ──> 물리 메모리 프레임 8
| Page 3  | ──> 디스크
+---------+
```

### 장점
- 물리 메모리보다 **큰 프로그램 실행** 가능
- 각 프로세스가 사용하는 실제 메모리가 줄어 **더 많은 프로세스를 동시에** 실행
- 프로세스마다 독립된 주소 공간 → **보호**
- 공유 라이브러리를 여러 프로세스가 **공유**, fork 시 Copy-on-Write

---

## 2. 요구 페이징 (Demand Paging)

**페이지가 실제로 필요할 때(접근할 때) 비로소 메모리에 올리는** 방식입니다.

페이지 테이블의 **유효-무효 비트(valid-invalid bit)** 로 페이지가 메모리에 있는지 표시합니다.
```
| 페이지 | 프레임 | valid |
|   0    |   3    |   1   |  ← 메모리에 있음
|   1    |   -    |   0   |  ← 디스크에 있음 (접근 시 페이지 폴트)
```

---

## 3. 페이지 폴트 (Page Fault) 처리 과정

**접근하려는 페이지가 메모리에 없을 때** 발생하는 인터럽트(트랩)입니다.

```
1. CPU가 페이지 접근 → 페이지 테이블의 valid 비트 = 0
2. MMU가 페이지 폴트 트랩 발생 → 커널 모드로 전환
3. OS가 유효한 접근인지 확인 (아니면 Segmentation Fault)
4. 빈 프레임을 찾음 (없으면 페이지 교체 알고리즘으로 희생 페이지 선택,
   수정된(dirty) 페이지면 디스크에 기록)
5. 디스크에서 해당 페이지를 프레임으로 읽어 옴 (이 동안 프로세스는 Waiting)
6. 페이지 테이블 갱신 (프레임 번호, valid = 1)
7. 중단된 명령어를 다시 실행
```

> 디스크 접근은 메모리보다 **수만~수십만 배 느립니다.** 페이지 폴트가 조금만 늘어도 성능이 크게 떨어지므로, 교체 알고리즘이 중요합니다.

---

## 4. 페이지 교체 알고리즘

빈 프레임이 없을 때 **어떤 페이지를 내보낼지(victim)** 결정합니다. 목표는 **페이지 폴트 최소화**입니다.

예시: 프레임 3개, 참조열 `7 0 1 2 0 3 0 4 2 3`

### 4-1. FIFO (First-In First-Out)
**가장 먼저 들어온 페이지**를 내보냅니다.

```
참조:  7  0  1  2  0  3  0  4  2  3
F1     7  7  7  2  2  2  2  4  4  4
F2        0  0  0  0  3  3  3  2  2
F3           1  1  1  1  0  0  0  3
폴트   F  F  F  F     F  F  F  F  F    → 9번
```

- 구현이 쉬움
- 자주 쓰는 페이지도 오래됐다는 이유로 내보낼 수 있음
- **벨라디의 모순 (Belady's Anomaly)**: 프레임 수를 늘렸는데 오히려 페이지 폴트가 늘어나는 현상이 FIFO에서 발생할 수 있음

### 4-2. OPT (Optimal, 최적)
**앞으로 가장 오랫동안 사용되지 않을 페이지**를 내보냅니다.

```
참조:  7  0  1  2  0  3  0  4  2  3
F1     7  7  7  2  2  2  2  2  2  2
F2        0  0  0  0  0  0  4  4  4
F3           1  1  1  3  3  3  3  3
폴트   F  F  F  F     F     F          → 6번
```

- 페이지 폴트가 **이론상 최소**
- **미래를 알아야 해서 구현 불가능** → 다른 알고리즘의 성능 비교 기준으로 사용

### 4-3. LRU (Least Recently Used)
**가장 오랫동안 사용되지 않은(가장 옛날에 쓴) 페이지**를 내보냅니다. "최근에 안 쓴 건 앞으로도 안 쓸 것" (시간 지역성)

```
참조:  7  0  1  2  0  3  0  4  2  3
F1     7  7  7  2  2  2  2  4  4  4
F2        0  0  0  0  0  0  0  0  3
F3           1  1  1  3  3  3  2  2
폴트   F  F  F  F     F     F  F  F    → 8번
```
(2 참조 시 7이 가장 오래 안 쓰임 → 7 교체, 3 참조 시 1 교체, 4 참조 시 2 교체 ...)

- OPT에 가까운 성능, **실제로 가장 많이 쓰이는 개념**
- 구현: 타임스탬프 or **이중 연결리스트 + 해시맵** (사용하면 맨 앞으로, 교체는 맨 뒤)
- 하드웨어로 정확히 구현하기는 비용이 커서 OS는 **근사 알고리즘(Clock)** 을 씀

### 4-4. LFU (Least Frequently Used)
**사용 횟수가 가장 적은 페이지**를 내보냅니다.
- 초반에 많이 쓰고 이후 안 쓰는 페이지가 계속 남는 문제

### 4-5. Clock (Second Chance, LRU 근사)
- 각 페이지에 **참조 비트(reference bit)** 를 두고, 원형 큐를 시계 바늘처럼 돕니다.
- 바늘이 가리킨 페이지의 참조 비트가
  - **1이면** → 0으로 바꾸고 한 번 더 기회를 줌, 다음으로 이동
  - **0이면** → 교체
- 하드웨어가 참조 비트만 세팅하면 되므로 구현 비용이 낮음 → **실제 OS에서 사용**

### 비교
| 알고리즘 | 기준 | 특징 |
|---|---|---|
| FIFO | 들어온 순서 | 단순, 벨라디 모순 |
| OPT | 미래 사용 | 최적, 구현 불가 |
| **LRU** | 최근 사용 시점 | OPT에 근접, 구현 비용 |
| LFU | 사용 빈도 | 과거 빈도에 갇힘 |
| Clock | 참조 비트 | LRU 근사, 실제 OS |

> **백엔드와 연결**: Redis의 `maxmemory-policy allkeys-lru`, Java `LinkedHashMap(accessOrder=true)` 기반 LRU 캐시도 같은 원리입니다.

```java
// LinkedHashMap으로 LRU 캐시
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LRUCache(int capacity) {
        super(capacity, 0.75f, true);   // accessOrder = true: 접근 순서로 정렬
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;       // 넘치면 가장 오래된 것 제거
    }
}
```

## 5. 스래싱 (Thrashing)

**프로세스가 실제 작업보다 페이지 교체(페이지 폴트 처리)에 더 많은 시간을 쓰는** 상태입니다.

```
CPU 이용률
   ↑         ___
   |       /     \
   |     /         \     ← 스래싱 시작
   |   /             \
   | /                 \___
   +------------------------→ 동시 실행 프로세스 수 (멀티프로그래밍 정도)
```

### 발생 과정
1. 프로세스가 많아짐 → 프로세스당 프레임 부족
2. 페이지 폴트 급증 → 프로세스들이 I/O 대기
3. OS는 CPU 이용률이 낮으니 **프로세스를 더 투입**
4. 프레임이 더 부족해짐 → 악순환

### 해결
| 방법 | 설명 |
|---|---|
| **워킹 셋 (Working Set) 모델** | 프로세스가 일정 시간 동안 자주 참조하는 페이지 집합(워킹 셋)만큼 프레임을 보장. 부족하면 프로세스 일부를 스왑 아웃 |
| **페이지 폴트 빈도 (PFF)** | 페이지 폴트율이 상한보다 높으면 프레임을 더 주고, 하한보다 낮으면 회수 |
| 멀티프로그래밍 정도 낮추기 | 실행 중인 프로세스 수 줄이기 |
| 물리 메모리 증설 | 근본적인 해결 |

## 6. 지역성 (Locality)

가상 메모리와 캐시가 잘 동작하는 근본 이유입니다.

| 종류 | 의미 | 예 |
|---|---|---|
| **시간 지역성** | 최근 접근한 데이터를 곧 다시 접근 | 반복문 변수, 카운터 |
| **공간 지역성** | 접근한 데이터 주변을 곧 접근 | 배열 순차 접근 |

## 7. 면접 질문

1. **가상 메모리란?**
   → 프로세스에 실제 물리 메모리와 무관한 독립된 주소 공간을 제공하고, 필요한 페이지만 물리 메모리에 올려 물리 메모리보다 큰 프로그램을 실행할 수 있게 하는 기법입니다.
2. **페이지 폴트가 발생하면 어떤 일이 일어나나요?**
   → 트랩이 발생해 OS가 디스크에서 해당 페이지를 빈 프레임(없으면 교체)으로 읽어 오고, 페이지 테이블을 갱신한 뒤 명령어를 재실행합니다.
3. **LRU를 구현하는 방법은?**
   → 해시맵과 이중 연결리스트로 접근 시 노드를 맨 앞으로 옮기고, 교체 시 맨 뒤를 제거하면 O(1)에 구현할 수 있습니다.
4. **스래싱이란? 해결 방법은?**
   → 페이지 폴트가 과도해 CPU가 실제 작업보다 페이지 교체에 시간을 쓰는 상태로, 워킹 셋이나 PFF로 프레임을 적절히 할당하거나 실행 프로세스 수를 줄여 해결합니다.

---

## 핵심 정리
- 가상 메모리 = 필요한 페이지만 메모리에 (요구 페이징)
- 페이지 폴트 → 디스크에서 로드 → 테이블 갱신 → 재실행
- 교체: FIFO(벨라디) / OPT(이론 최적) / LRU(실전 기준) / Clock(OS 근사)
- 스래싱 → 워킹 셋, PFF
