# 08. 파일 시스템과 입출력 (File System & I/O)

> **학습 목표**
> - 파일 시스템의 역할과 파일 할당 방식(연속, 연결, 색인)을 비교할 수 있다.
> - inode의 구조와 하드 링크·심볼릭 링크의 차이를 설명할 수 있다.
> - 블로킹/논블로킹, 동기/비동기 I/O와 DMA를 설명할 수 있다.

---

## 1. 파일 시스템이란?

**디스크(저장장치)에 파일을 어떻게 저장하고 찾을지 관리하는** OS의 구성 요소입니다.

- 파일: 이름이 붙은 관련 데이터의 묶음 (OS 입장에서는 바이트의 나열)
- 디렉토리: 파일 이름과 파일 정보(메타데이터)를 연결하는 특수한 파일
- 디스크는 **블록(보통 4KB)** 단위로 읽고 씁니다.

| 파일 시스템 | 사용처 |
|---|---|
| ext4 | Linux 기본 |
| NTFS | Windows |
| APFS | macOS |
| FAT32 / exFAT | USB 메모리 (호환성) |

---

## 2. 파일 할당 방식

파일 데이터를 디스크의 어떤 블록에 배치할까?

### 2-1. 연속 할당 (Contiguous)
```
파일 A: 블록 3, 4, 5, 6 (시작 블록 3, 길이 4)
```
- 순차·직접 접근 모두 빠름
- **외부 단편화**, 파일 크기 늘리기 어려움

### 2-2. 연결 할당 (Linked)
```
파일 A: 블록 9 → 16 → 1 → 10 → 25 → null
각 블록 끝에 다음 블록 번호 저장
```
- 외부 단편화 없음, 크기 늘리기 쉬움
- **직접 접근이 느림**(처음부터 따라가야 함), 포인터 하나 손상되면 뒤가 모두 유실
- **FAT (File Allocation Table)**: 포인터들을 별도 테이블에 모아 메모리에 캐싱 → 직접 접근 개선

### 2-3. 색인 할당 (Indexed)
```
파일 A의 색인 블록: [9, 16, 1, 10, 25]
```
- 파일마다 **블록 번호 목록(색인 블록)** 을 따로 둠
- 직접 접근 빠름, 외부 단편화 없음
- 작은 파일도 색인 블록 하나를 써야 함 → **Unix inode 방식**

## 3. inode (Unix/Linux)

**파일의 메타데이터와 데이터 블록 위치를 저장하는 구조체**입니다. 파일 하나당 inode 하나.

```
inode
+------------------------+
| 파일 종류, 권한 (rwx)     |
| 소유자, 그룹             |
| 크기, 시간(생성/수정/접근) |
| 링크 수                 |
+------------------------+
| 직접 블록 포인터 × 12     | → 데이터 블록 (작은 파일은 여기서 끝)
| 단일 간접 포인터          | → [포인터 블록] → 데이터 블록들
| 이중 간접 포인터          | → [포인터 블록] → [포인터 블록] → 데이터
| 삼중 간접 포인터          | → ... (매우 큰 파일)
+------------------------+
```

- **파일 이름은 inode에 없습니다.** 디렉토리가 `(이름, inode 번호)` 쌍을 저장합니다.
- 작은 파일은 직접 포인터로 빠르게, 큰 파일은 간접 포인터로 확장

### 하드 링크 vs 심볼릭 링크
```bash
ln original.txt hard.txt       # 하드 링크
ln -s original.txt soft.txt    # 심볼릭 링크
```

| 항목 | 하드 링크 | 심볼릭(소프트) 링크 |
|---|---|---|
| 가리키는 것 | **같은 inode** | 원본 파일의 **경로** |
| 원본 삭제 시 | 데이터 유지 (링크 수가 0이 될 때 삭제) | **깨진 링크** |
| 다른 파일 시스템 | 불가 | 가능 |
| 디렉토리 | 불가 | 가능 |
| 비유 | 같은 사람의 다른 이름 | 바탕화면 바로가기 |

## 4. 저널링 (Journaling)

파일을 쓰는 도중 전원이 꺼지면 메타데이터와 데이터가 불일치할 수 있습니다. 저널링 파일 시스템은 **변경 내용을 먼저 로그(저널)에 기록하고, 그다음 실제로 반영**합니다. 장애 후에는 로그를 보고 복구합니다. (ext4, NTFS)

## 5. 입출력 (I/O)

### 5-1. I/O 방식
| 방식 | 설명 |
|---|---|
| 프로그램 I/O (폴링) | CPU가 장치 상태를 계속 확인 → CPU 낭비 |
| 인터럽트 I/O | 장치가 끝나면 인터럽트로 알림 → 데이터 이동은 여전히 CPU가 함 |
| **DMA** (Direct Memory Access) | **DMA 컨트롤러가 CPU 대신 장치 ↔ 메모리 데이터를 직접 전송**, 끝나면 인터럽트 한 번 |

> DMA 덕분에 대용량 디스크/네트워크 전송 중에도 CPU는 다른 일을 할 수 있습니다.

### 5-2. 버퍼링과 캐싱
- **버퍼**: 속도가 다른 장치 사이에서 데이터를 임시 저장 (키보드 입력 버퍼)
- **페이지 캐시 (버퍼 캐시)**: 디스크 블록을 메모리에 캐싱해 다음 읽기를 빠르게. Linux는 남는 메모리를 페이지 캐시로 적극 사용

### 5-3. 블로킹 / 논블로킹, 동기 / 비동기

| 구분 | 기준 | 의미 |
|---|---|---|
| **블로킹** | 제어권 | 호출한 함수가 끝날 때까지 **제어권을 돌려주지 않음** (호출자는 대기) |
| **논블로킹** | 제어권 | **즉시 제어권을 돌려줌** (준비 안 됐으면 "아직"이라고 반환) |
| **동기** | 결과 확인 | 호출자가 **직접** 작업 완료를 확인 |
| **비동기** | 결과 확인 | 작업이 끝나면 **콜백/이벤트로 알려 줌** |

```
블로킹 + 동기    : 일반 read(). 데이터 올 때까지 멈춤 (Java InputStream)
논블로킹 + 동기  : 계속 "다 됐어?" 물어봄 (폴링)
논블로킹 + 비동기 : 요청만 하고 다른 일, 끝나면 콜백 (Node.js, CompletableFuture)
블로킹 + 비동기  : 드묾 (비동기 호출 후 결과를 블로킹으로 기다리는 실수 등)
```

### 5-4. I/O 멀티플렉싱
**하나의 스레드로 여러 소켓(파일 디스크립터)을 감시**하다가, 준비된 것만 처리합니다.

| 방식 | 특징 |
|---|---|
| select | 감시 대상 수 제한(1024), 매번 전체 검사 O(n) |
| poll | 수 제한 없음, 여전히 O(n) |
| **epoll** (Linux) / kqueue (BSD) | 준비된 이벤트만 반환 → 대규모 연결에 효율적 |

> **Nginx, Netty, Node.js, Spring WebFlux, Redis**가 epoll 기반 이벤트 루프로 적은 스레드로 많은 연결을 처리합니다. 반면 전통적인 Tomcat(BIO)은 연결당 스레드를 씁니다.

## 6. 면접 질문

1. **inode란?**
   → 파일의 권한·소유자·크기·시간 등 메타데이터와 데이터 블록 위치를 저장하는 구조체이며, 파일 이름은 디렉토리 엔트리에 저장됩니다.
2. **하드 링크와 심볼릭 링크의 차이는?**
   → 하드 링크는 같은 inode를 가리켜 원본을 지워도 데이터가 남고, 심볼릭 링크는 경로를 가리켜 원본이 지워지면 깨집니다.
3. **블로킹과 논블로킹, 동기와 비동기의 차이는?**
   → 블로킹/논블로킹은 호출한 함수가 제어권을 바로 돌려주는지, 동기/비동기는 작업 완료를 호출자가 직접 확인하는지 콜백으로 통보받는지의 차이입니다.
4. **DMA란?**
   → CPU를 거치지 않고 장치와 메모리 사이에서 데이터를 직접 전송하는 방식으로, CPU 부담을 줄입니다.

## 핵심 정리
- 파일 할당: 연속(빠름, 단편화) / 연결(FAT) / 색인(inode)
- inode = 메타데이터 + 블록 포인터, 이름은 디렉토리에
- 블로킹/논블로킹 = 제어권, 동기/비동기 = 완료 확인 방식
- epoll 기반 이벤트 루프 → Nginx, Netty, Redis
