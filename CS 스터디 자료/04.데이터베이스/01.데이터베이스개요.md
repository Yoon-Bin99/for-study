# 01. 데이터베이스 개요

> **학습 목표**
> - 파일 시스템 대비 DBMS의 장점을 설명할 수 있다.
> - 3단계 스키마 구조와 데이터 독립성을 설명할 수 있다.
> - 관계형 모델 용어와 키(Key)의 종류를 구분할 수 있다.
> - ER 모델과 관계(1:1, 1:N, N:M)를 표현할 수 있다.

---

## 1. 왜 DBMS가 필요한가?

파일로 데이터를 관리하면 생기는 문제:
| 문제 | 예 |
|---|---|
| 데이터 중복 | 학생 정보가 수강 파일, 성적 파일에 각각 저장 |
| 불일치 | 한 파일에서만 전화번호를 바꿈 |
| 동시 접근 문제 | 두 사람이 동시에 같은 파일 수정 |
| 보안·권한 관리 어려움 | 파일 단위로만 권한 설정 |
| 장애 복구 어려움 | 쓰는 도중 장애 시 파일 손상 |

**DBMS (Database Management System)** 는 이를 해결하는 소프트웨어입니다. (MySQL, PostgreSQL, Oracle, MongoDB)

| DBMS가 제공하는 것 | 설명 |
|---|---|
| 중복 최소화, 무결성 | 제약 조건으로 잘못된 데이터 차단 |
| 동시성 제어 | 여러 사용자가 동시에 안전하게 사용 |
| 회복 | 장애 후 일관된 상태로 복구 |
| 보안 | 사용자·테이블·컬럼 단위 권한 |
| 데이터 독립성 | 저장 구조가 바뀌어도 응용 프로그램 수정 X |

## 2. 3단계 스키마 구조 (ANSI/SPARC)

**스키마**: 데이터베이스의 구조와 제약 조건을 정의한 것

```
  사용자1   사용자2   사용자3
     ↓        ↓        ↓
+--------------------------------+
|  외부 스키마 (External / View)    |  사용자별로 보는 관점 (뷰)
+--------------------------------+
         ↕ 논리적 데이터 독립성
+--------------------------------+
|  개념 스키마 (Conceptual)         |  전체 DB의 논리 구조 (테이블, 관계, 제약)
+--------------------------------+
         ↕ 물리적 데이터 독립성
+--------------------------------+
|  내부 스키마 (Internal)           |  실제 저장 방식 (인덱스, 파일 구조)
+--------------------------------+
```

- **논리적 데이터 독립성**: 개념 스키마(테이블 구조)가 바뀌어도 외부 스키마(응용 프로그램)는 영향 X
- **물리적 데이터 독립성**: 내부 스키마(인덱스 추가, 저장 장치 변경)가 바뀌어도 개념 스키마는 영향 X

## 4. 관계형 모델 용어

```
                학생 (릴레이션 = 테이블)
     +---------+--------+------+-----------+
     | 학번     | 이름    | 학년  | 학과        |  ← 속성(Attribute) = 열(Column)
     +---------+--------+------+-----------+
     | 2021001 | 김철수  |  3   | 컴퓨터공학   |  ← 튜플(Tuple) = 행(Row)
     | 2022015 | 이영희  |  2   | 전자공학     |
     +---------+--------+------+-----------+
```

| 관계형 용어 | 일반 용어 | 의미 |
|---|---|---|
| 릴레이션 | 테이블 | 데이터 집합 |
| 튜플 | 행, 레코드 | 하나의 데이터 |
| 속성 | 열, 컬럼 | 데이터의 특성 |
| 도메인 | - | 속성이 가질 수 있는 값의 범위 (학년: 1~4) |
| **차수 (Degree)** | - | **속성(열)의 수** → 위 예시는 4 |
| **카디널리티 (Cardinality)** | - | **튜플(행)의 수** → 위 예시는 2 |

### 릴레이션의 특징
- 튜플은 **중복되지 않음** (그래서 키가 존재)
- 튜플 사이에 **순서가 없음**
- 속성 사이에 순서가 없음
- 속성 값은 **원자값** (더 쪼갤 수 없는 값, 1정규형)

## 5. 키 (Key)

| 키 | 정의 | 예 (학생 테이블) |
|---|---|---|
| **슈퍼키** (Super Key) | 튜플을 **유일하게 식별**할 수 있는 속성 집합 (유일성 O) | {학번}, {학번, 이름}, {주민번호, 학과} |
| **후보키** (Candidate Key) | 슈퍼키 중 **최소성**까지 만족 (속성을 하나라도 빼면 식별 불가) | {학번}, {주민번호} |
| **기본키** (Primary Key) | 후보키 중 **대표로 선택한 키**. NULL 불가, 중복 불가 | {학번} |
| **대체키** (Alternate Key) | 기본키로 선택되지 않은 후보키 | {주민번호} |
| **외래키** (Foreign Key) | **다른 테이블의 기본키를 참조**하는 속성 | 수강 테이블의 학번 |

```
슈퍼키 ⊇ 후보키 ⊇ 기본키
         후보키 = 기본키 + 대체키
```

### 자연키 vs 대리키
- **자연키**: 비즈니스 의미가 있는 값 (주민번호, 이메일)
- **대리키 (Surrogate Key)**: 의미 없는 인공 식별자 (AUTO_INCREMENT id, UUID)

> 실무에서는 **대리키를 기본키로 쓰는 것을 권장**합니다. 자연키는 비즈니스 규칙이 바뀌면(이메일 변경) 변할 수 있고, 외래키로 참조하는 모든 테이블을 바꿔야 하기 때문입니다.

## 6. 무결성 제약 조건

| 제약 | 의미 | SQL |
|---|---|---|
| **개체 무결성** | 기본키는 NULL이거나 중복될 수 없다 | `PRIMARY KEY` |
| **참조 무결성** | 외래키 값은 참조하는 테이블의 기본키에 존재하거나 NULL이어야 한다 | `FOREIGN KEY ... REFERENCES` |
| 도메인 무결성 | 속성 값은 정의된 도메인에 속해야 한다 | `CHECK`, 데이터 타입 |
| 고유 무결성 | 지정한 속성은 중복 불가 | `UNIQUE` |
| NULL 무결성 | 지정한 속성은 NULL 불가 | `NOT NULL` |

### 참조 무결성 옵션 (부모 행 삭제 시)
| 옵션 | 동작 |
|---|---|
| RESTRICT / NO ACTION | 자식이 있으면 삭제 거부 |
| CASCADE | 자식도 함께 삭제 |
| SET NULL | 자식의 외래키를 NULL로 |
| SET DEFAULT | 기본값으로 |

## 7. ER 모델 (Entity-Relationship)

데이터베이스 설계 단계에서 **개체(Entity), 속성(Attribute), 관계(Relationship)** 로 현실 세계를 표현합니다.

### 관계의 종류 (카디널리티)
| 관계 | 예 | 테이블 설계 |
|---|---|---|
| **1:1** | 회원 - 회원상세 | 한쪽에 외래키 (+ UNIQUE) |
| **1:N** | 회원 - 주문 | **N쪽(주문)에 외래키** |
| **N:M** | 학생 - 강의 | **중간 테이블(수강)** 을 만들어 1:N 두 개로 분리 |

```
N:M 해소
[학생] 1 ──< N [수강] N >── 1 [강의]
                 학번(FK)
                 강의번호(FK)
                 성적
```

> JPA에서도 `@ManyToMany`보다 **중간 엔티티를 직접 만들어 `@OneToMany` + `@ManyToOne`** 으로 푸는 것을 권장합니다. 중간 테이블에 수강일·성적 같은 컬럼이 추가되는 경우가 많기 때문입니다.

### 설계 단계
```
요구사항 분석 → 개념적 설계 (ERD) → 논리적 설계 (테이블, 정규화) → 물리적 설계 (인덱스, 파티션)
```

## 8. 면접 질문

1. **DBMS를 사용하는 이유는?**
   → 데이터 중복과 불일치를 줄이고, 무결성·동시성 제어·장애 회복·보안·데이터 독립성을 제공하기 때문입니다.
2. **슈퍼키, 후보키, 기본키의 차이는?**
   → 슈퍼키는 유일성만, 후보키는 유일성과 최소성을 만족하며, 기본키는 후보키 중 대표로 선택한 키입니다.
3. **N:M 관계는 어떻게 설계하나요?**
   → 두 테이블의 기본키를 외래키로 갖는 중간 테이블을 만들어 1:N 관계 두 개로 분리합니다.
4. **대리키를 기본키로 쓰는 이유는?**
   → 비즈니스 규칙 변경에 영향을 받지 않고, 짧고 단순해 인덱스·조인 효율이 좋기 때문입니다.

---

## 핵심 정리
- DBMS = 중복·불일치 해결 + 동시성·회복·보안·독립성
- 3단계 스키마: 외부 - 개념 - 내부 (논리적/물리적 독립성)
- 키: 슈퍼키(유일성) ⊇ 후보키(+최소성) ⊇ 기본키
- N:M은 중간 테이블로 분리
