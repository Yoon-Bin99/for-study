# 04. 인덱스 (Index)

> **학습 목표**
> - 인덱스가 조회를 빠르게 하는 원리와 비용을 설명할 수 있다.
> - B-Tree와 B+Tree의 구조와 DB가 B+Tree를 쓰는 이유를 설명할 수 있다.
> - 클러스터드/논클러스터드 인덱스, 복합 인덱스, 커버링 인덱스를 설명할 수 있다.
> - 인덱스가 동작하지 않는 쿼리를 알아볼 수 있다.

---

## 1. 인덱스란?

**원하는 데이터를 빨리 찾기 위해 컬럼 값과 행의 위치를 정렬해 저장한 별도의 자료구조**입니다. 책 뒤의 "찾아보기"와 같습니다.

```sql
SELECT * FROM member WHERE email = 'a@b.com';
```
- 인덱스 없음: **Full Table Scan** → 100만 행을 전부 확인 O(n)
- 인덱스 있음: **Index Scan** → 트리를 타고 내려가 바로 찾음 O(log n)

```sql
CREATE INDEX idx_member_email ON member(email);
```

---

## 2. 인덱스의 비용

| 장점 | 단점 |
|---|---|
| SELECT의 WHERE, JOIN, ORDER BY, GROUP BY 성능 향상 | **INSERT, UPDATE, DELETE가 느려짐** (인덱스도 함께 갱신) |
| | **추가 저장 공간** (보통 테이블의 10% 내외) |
| | 잘못 만들면 오히려 성능 저하 |

> 인덱스는 "읽기를 빠르게, 쓰기를 느리게" 만드는 트레이드오프입니다. 무조건 많이 만들면 안 됩니다.

---

## 3. 인덱스 자료구조

### 왜 해시 테이블이 아닌가?
- 해시는 `=` 검색은 O(1)이지만 **범위 검색(`>`, `BETWEEN`, `LIKE 'abc%'`)과 정렬이 불가능**합니다.
- (MySQL MEMORY 엔진 등 일부에서는 해시 인덱스도 지원)

### 왜 이진 탐색 트리(BST, 레드블랙)가 아닌가?
- 노드 하나에 키 하나 → 100만 건이면 높이가 약 20
- 디스크에서 노드 하나 읽을 때마다 I/O 발생 → **20번의 디스크 I/O**
- 디스크는 **블록(페이지) 단위**로 읽으므로, 한 번에 많은 키를 읽는 것이 유리

### B-Tree
- 한 노드에 **여러 개의 키와 자식 포인터**(수백 개)를 저장하는 균형 트리
- 노드 크기를 디스크 페이지 크기(InnoDB 기본 16KB)에 맞춤 → **트리 높이가 매우 낮음** (3~4단계로 수천만 건)
- 모든 리프가 같은 깊이 (균형)

### B+Tree (대부분의 RDBMS가 사용)
```
                     [ 30 | 60 ]                    ← 루트 (키만, 데이터 X)
                   /      |      \
          [10|20]      [40|50]      [70|80]          ← 브랜치 (키만)
          /  |  \       / | \        / | \
리프:   [5,10]→[15,20]→[25,30]→[35,40]→ ... →[75,80]→[85,90]
          ↑ 실제 데이터(또는 PK/행 주소)는 리프에만, 리프끼리 연결리스트
```

| 항목 | B-Tree | B+Tree |
|---|---|---|
| 데이터 위치 | 모든 노드 | **리프 노드에만** |
| 내부 노드 | 키 + 데이터 | **키만** → 한 노드에 더 많은 키 → 높이 더 낮음 |
| 리프 연결 | X | **연결리스트로 연결** |
| 범위 검색 | 트리를 오르내려야 함 | **리프만 순서대로 따라가면 됨** |
| 검색 시간 | 운이 좋으면 내부에서 끝남 | 항상 리프까지 (일정함) |

> **DB가 B+Tree를 쓰는 이유**: 내부 노드에 키만 있어 팬아웃(자식 수)이 크고 높이가 낮아 디스크 I/O가 적고, 리프가 연결되어 있어 **범위 검색과 정렬에 유리**하기 때문입니다.

## 4. 클러스터드 vs 논클러스터드 인덱스

### 클러스터드 인덱스 (Clustered Index)
- **테이블 데이터 자체가 인덱스 키 순서대로 정렬되어 저장**됩니다.
- 테이블당 **하나만** 존재 (데이터를 두 가지 순서로 저장할 수 없으므로)
- MySQL InnoDB: **기본키가 클러스터드 인덱스**. 리프 노드에 **행 전체 데이터**가 있음
- 범위 검색이 매우 빠름

### 논클러스터드 인덱스 (Secondary Index, 보조 인덱스)
- 데이터와 별도로 인덱스 구조를 만듦
- 여러 개 생성 가능
- InnoDB: 리프 노드에 **인덱스 키 + 기본키 값** 저장

```
SELECT * FROM member WHERE email = 'a@b.com';

1. 보조 인덱스(email)에서 'a@b.com' 검색 → PK = 42 획득
2. 클러스터드 인덱스(PK)에서 42 검색 → 행 전체 데이터 획득
   (이 두 번째 단계를 "테이블 랜덤 액세스" 또는 "북마크 룩업"이라 함)
```

> InnoDB에서 **PK가 너무 크면**(UUID 문자열 등) 모든 보조 인덱스의 크기도 커집니다. 또한 랜덤한 PK는 삽입 시 페이지 분할을 자주 일으킵니다. 그래서 `AUTO_INCREMENT BIGINT`나 순차적인 UUID(v7)를 권장합니다.

## 5. 복합 인덱스 (Composite Index)

여러 컬럼을 묶어 만든 인덱스입니다. **컬럼 순서가 매우 중요**합니다.

```sql
CREATE INDEX idx_name_age ON member(last_name, age);
```

```
정렬 상태: (김, 20) (김, 25) (김, 30) (이, 22) (이, 28) (박, 19) ...
           ↑ last_name으로 먼저 정렬, 같으면 age로 정렬
```

| 쿼리 | 인덱스 사용 |
|---|---|
| `WHERE last_name = '김'` | O |
| `WHERE last_name = '김' AND age = 25` | O |
| `WHERE age = 25` | **X** (첫 컬럼 없이는 정렬이 의미 없음) |
| `WHERE last_name = '김' AND age > 20` | O |

→ **최좌측 접두사 규칙 (Leftmost Prefix Rule)**: 복합 인덱스는 **왼쪽 컬럼부터 순서대로** 조건이 있어야 사용됩니다.

### 컬럼 순서 정하는 기준
1. **`=` 조건 컬럼을 앞에**, 범위 조건(`>`, `BETWEEN`) 컬럼을 뒤에 (범위 조건 뒤의 컬럼은 인덱스 효율이 떨어짐)
2. 자주 함께 조회되는 순서
3. **카디널리티(값의 종류 수)가 높은** 컬럼을 앞에 두는 것이 일반적으로 유리 (성별보다 이메일)

---

## 6. 커버링 인덱스 (Covering Index)

**쿼리에 필요한 모든 컬럼이 인덱스에 포함**되어 있어, 테이블(클러스터드 인덱스)에 접근하지 않고 인덱스만으로 결과를 반환하는 경우입니다.

```sql
-- idx_name_age (last_name, age)
SELECT last_name, age FROM member WHERE last_name = '김';
-- 필요한 컬럼이 모두 인덱스에 있음 → 테이블 접근 X → 빠름
-- EXPLAIN의 Extra: "Using index"
```

## 7. 인덱스가 동작하지 않는 경우

| 경우 | 예 | 해결 |
|---|---|---|
| 인덱스 컬럼을 **가공** | `WHERE YEAR(created_at) = 2026` | `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| 인덱스 컬럼에 **연산** | `WHERE price * 1.1 > 1000` | `WHERE price > 1000 / 1.1` |
| **앞에 %** 있는 LIKE | `WHERE name LIKE '%철수'` | 전문 검색(Full-text), 검색 엔진 |
| **타입 불일치** (묵시적 형변환) | 문자열 컬럼에 `WHERE phone = 01012345678` | 타입 맞추기 `'01012345678'` |
| 복합 인덱스 첫 컬럼 누락 | 위 5절 참고 | 컬럼 순서 조정 |
| `OR` 조건 (일부 컬럼에만 인덱스) | `WHERE a = 1 OR b = 2` | UNION, 각각 인덱스 |
| `!=`, `NOT IN` | 대부분 범위가 너무 넓음 | - |
| 옵티마이저가 Full Scan이 낫다고 판단 | 조회 결과가 전체의 상당 부분 (보통 20~25% 이상) | 정상 동작 |

---

## 8. 인덱스를 만들면 좋은 컬럼

- WHERE, JOIN ON, ORDER BY, GROUP BY에 **자주 쓰이는** 컬럼
- **카디널리티가 높은** 컬럼 (값이 다양 → 선택도가 좋음). 성별(M/F)은 비효율적
- 외래키 컬럼 (JOIN 성능)
- **수정이 잦지 않은** 컬럼

---

## 9. 실행 계획 확인 (MySQL)

```sql
EXPLAIN SELECT * FROM member WHERE email = 'a@b.com';
```

| type 값 | 의미 (위로 갈수록 좋음) |
|---|---|
| const | PK/UNIQUE로 1건 조회 |
| eq_ref | JOIN에서 PK/UNIQUE로 1건씩 |
| ref | 일반 인덱스로 동등 조건 |
| range | 인덱스 범위 검색 |
| index | 인덱스 전체 스캔 |
| **ALL** | **테이블 전체 스캔** (개선 대상) |

## 10. 면접 질문

1. **인덱스를 쓰면 조회가 빨라지는 이유는?**
   → 컬럼 값을 정렬된 B+Tree로 관리해 전체 스캔 O(n) 대신 O(log n)으로 찾을 수 있기 때문입니다.
2. **DB 인덱스에 B+Tree를 쓰는 이유는?**
   → 노드에 많은 키를 담아 높이가 낮아 디스크 I/O가 적고, 리프 노드가 연결되어 범위 검색에 유리합니다. 해시는 범위 검색이 불가능합니다.
3. **인덱스를 많이 만들면 안 되는 이유는?**
   → 쓰기 작업마다 인덱스를 갱신해야 해서 INSERT/UPDATE/DELETE가 느려지고 저장 공간도 늘어납니다.
4. **클러스터드 인덱스와 논클러스터드 인덱스의 차이는?**
   → 클러스터드는 데이터 자체가 키 순서로 정렬 저장되어 테이블당 하나이고, 논클러스터드는 별도 구조로 키와 데이터 위치(InnoDB는 PK)를 저장하며 여러 개 만들 수 있습니다.
5. **복합 인덱스 (a, b)에서 WHERE b = 1이 인덱스를 못 타는 이유는?**
   → 인덱스가 a 기준으로 먼저 정렬되어 있어 b만으로는 정렬 순서를 활용할 수 없기 때문입니다.

---

## 핵심 정리
- 인덱스 = 정렬된 별도 구조, 읽기 ↑ 쓰기 ↓
- B+Tree: 키는 내부, 데이터는 리프, 리프 연결 → 낮은 높이 + 범위 검색
- InnoDB: PK = 클러스터드, 보조 인덱스는 PK를 가리킴
- 복합 인덱스: 최좌측 접두사, `=` 컬럼 먼저
- 컬럼 가공·앞 %·형변환 → 인덱스 무력화
