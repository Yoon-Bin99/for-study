# 05. 트랜잭션 (Transaction)

> **학습 목표**
> - 트랜잭션과 ACID 각 속성의 의미를 예시로 설명할 수 있다.
> - 트랜잭션 상태 전이를 설명할 수 있다.
> - 동시성 이상 현상(Dirty Read, Non-Repeatable Read, Phantom Read)을 구분할 수 있다.
> - 격리 수준 4단계와 각 수준에서 발생하는 문제를 정리할 수 있다.
> - Spring `@Transactional`의 전파 속성과 주의점을 설명할 수 있다.

---

## 1. 트랜잭션이란?

**더 이상 쪼갤 수 없는 논리적 작업 단위**입니다. 모두 성공하거나, 모두 실패해야 합니다.

### 예시: 계좌 이체
```sql
START TRANSACTION;
UPDATE account SET balance = balance - 10000 WHERE id = 'A';   -- A 출금
UPDATE account SET balance = balance + 10000 WHERE id = 'B';   -- B 입금
COMMIT;
```
출금만 되고 입금 전에 장애가 나면 돈이 사라집니다. 둘을 **하나의 트랜잭션**으로 묶어 **둘 다 반영(COMMIT)되거나 둘 다 취소(ROLLBACK)** 되게 합니다.

---

## 2. ACID

| 속성 | 의미 | 계좌 이체 예 | 보장 방법 |
|---|---|---|---|
| **원자성** (Atomicity) | 모두 실행되거나 전혀 실행되지 않음 (All or Nothing) | 출금과 입금이 함께 성공 or 함께 취소 | **Undo 로그**, 롤백 |
| **일관성** (Consistency) | 트랜잭션 전후로 DB가 **무결성 제약을 만족** | 이체 전후 두 계좌 합이 같음, 잔액은 음수 불가 | 제약 조건, 애플리케이션 로직 |
| **격리성** (Isolation) | 동시에 실행되는 트랜잭션이 **서로 간섭하지 않음** | 이체 중간 상태를 다른 트랜잭션이 보지 못함 | **락, MVCC**, 격리 수준 |
| **지속성** (Durability) | COMMIT된 결과는 **장애가 나도 유지** | 이체 완료 후 서버가 꺼져도 반영되어 있음 | **Redo 로그 (WAL)**, 백업 |

## 3. 트랜잭션 상태

```
                ┌──────────> [부분 완료] ──COMMIT──> [완료 Committed]
                │            (마지막 연산 실행)
  [활동 Active] ─┤                 │ 반영 실패
                │                 ↓
                └──오류 발생──> [실패 Failed] ──ROLLBACK──> [철회 Aborted]
```

| 상태 | 의미 |
|---|---|
| 활동 (Active) | 실행 중 |
| 부분 완료 (Partially Committed) | 마지막 연산까지 실행했지만 아직 COMMIT 전 |
| 완료 (Committed) | COMMIT 성공, 영구 반영 |
| 실패 (Failed) | 오류로 중단 |
| 철회 (Aborted) | ROLLBACK 완료, 시작 전 상태로 복구 |

## 4. 동시성 이상 현상

여러 트랜잭션이 동시에 실행될 때 생기는 문제입니다.

### 4-1. Dirty Read (오손 읽기)
**COMMIT되지 않은** 다른 트랜잭션의 변경을 읽음
```
T1: UPDATE 잔액 = 0  (아직 COMMIT 안 함)
T2: SELECT 잔액 → 0 을 읽음
T1: ROLLBACK         → 실제 잔액은 원래 값인데 T2는 0을 기준으로 처리
```

### 4-2. Non-Repeatable Read (반복 불가능 읽기)
같은 트랜잭션에서 **같은 행을 두 번 읽었는데 값이 다름**
```
T1: SELECT 잔액 → 10000
T2: UPDATE 잔액 = 5000; COMMIT
T1: SELECT 잔액 → 5000   ← 같은 쿼리인데 결과가 다름
```

### 4-3. Phantom Read (유령 읽기)
같은 조건으로 두 번 조회했는데 **없던 행이 생기거나 사라짐**
```
T1: SELECT COUNT(*) FROM 주문 WHERE 금액 > 1000 → 5건
T2: INSERT 주문 (금액 2000); COMMIT
T1: SELECT COUNT(*) FROM 주문 WHERE 금액 > 1000 → 6건   ← 유령 행 등장
```

> Non-Repeatable Read는 **기존 행의 수정**, Phantom Read는 **행의 추가·삭제** 때문에 생깁니다.

### 4-4. Lost Update (갱신 손실)
```
T1: 재고 읽기 → 10
T2: 재고 읽기 → 10
T1: 재고 = 10 - 1 = 9 저장
T2: 재고 = 10 - 1 = 9 저장    ← 두 개 팔았는데 재고는 9
```
→ `SELECT ... FOR UPDATE`(비관적 락)나 버전 컬럼(낙관적 락)으로 해결 (→ `06.동시성제어와회복.md`)

## 5. 격리 수준 (Isolation Level)

격리를 높일수록 안전하지만 **동시 처리 성능이 떨어집니다.**

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| **READ UNCOMMITTED** | 발생 | 발생 | 발생 |
| **READ COMMITTED** | - | 발생 | 발생 |
| **REPEATABLE READ** | - | - | 발생 (InnoDB는 대부분 방지) |
| **SERIALIZABLE** | - | - | - |

### READ UNCOMMITTED
- COMMIT 안 된 데이터도 읽음
- 거의 사용하지 않음

### READ COMMITTED
- **COMMIT된 데이터만** 읽음
- **Oracle, PostgreSQL, SQL Server의 기본값**
- 조회할 때마다 최신 커밋 스냅샷을 봄 → Non-Repeatable Read 발생

### REPEATABLE READ
- 트랜잭션이 **처음 읽은 시점의 스냅샷**을 끝까지 봄 (MVCC)
- **MySQL InnoDB의 기본값**
- InnoDB는 일반 SELECT는 스냅샷 읽기로, `SELECT ... FOR UPDATE` 같은 잠금 읽기는 **넥스트 키 락(갭 락)** 으로 Phantom Read를 대부분 막습니다.

### SERIALIZABLE
- 트랜잭션을 **순차 실행한 것과 같은 결과** 보장
- InnoDB는 모든 SELECT를 공유 락으로 읽음 → 동시성이 크게 떨어짐

```sql
-- MySQL
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 6. Spring @Transactional

```java
@Service
@RequiredArgsConstructor
public class TransferService {
    private final AccountRepository accountRepository;

    @Transactional
    public void transfer(Long fromId, Long toId, long amount) {
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to = accountRepository.findById(toId).orElseThrow();
        from.withdraw(amount);
        to.deposit(amount);
    }   // 정상 종료 → COMMIT, RuntimeException → ROLLBACK
}
```

### 주의할 점
| 주의점 | 설명 |
|---|---|
| **Checked Exception은 기본적으로 롤백 X** | `RuntimeException`, `Error`만 롤백. 필요하면 `@Transactional(rollbackFor = Exception.class)` |
| **같은 클래스 내부 호출은 적용 X** | `@Transactional`은 **프록시** 기반이라 `this.method()` 호출은 프록시를 거치지 않음 |
| `private` 메서드에는 적용 X | 프록시가 오버라이드할 수 없음 |
| `readOnly = true` | 조회 전용 → JPA 변경 감지(dirty checking) 생략, 읽기 전용 DB로 라우팅 가능 |

### 전파 속성 (Propagation)
이미 트랜잭션이 있는 상태에서 다른 `@Transactional` 메서드를 호출하면 어떻게 할까?

| 속성 | 기존 트랜잭션 있음 | 없음 |
|---|---|---|
| **REQUIRED** (기본) | 참여 | 새로 생성 |
| **REQUIRES_NEW** | 기존을 잠시 보류하고 **새로 생성** | 새로 생성 |
| SUPPORTS | 참여 | 트랜잭션 없이 실행 |
| MANDATORY | 참여 | 예외 |
| NOT_SUPPORTED | 보류하고 없이 실행 | 없이 실행 |
| NEVER | 예외 | 없이 실행 |
| NESTED | 중첩 트랜잭션 (세이브포인트) | 새로 생성 |

> **REQUIRES_NEW 예**: 주문이 실패해 롤백되더라도 **실패 로그는 남겨야** 할 때 로그 저장 메서드를 REQUIRES_NEW로 분리합니다.

> **REQUIRED 함정**: 내부 메서드에서 예외가 발생해 롤백 마크가 찍히면, 외부에서 그 예외를 catch 해도 커밋 시점에 `UnexpectedRollbackException`이 발생합니다.

## 7. 면접 질문

1. **ACID를 설명해 주세요.**
   → 원자성은 전부 성공 또는 전부 실패, 일관성은 전후로 제약 조건 만족, 격리성은 동시 트랜잭션 간 간섭 없음, 지속성은 커밋된 결과의 영구 보존입니다.
2. **격리 수준별로 발생하는 문제는?**
   → READ UNCOMMITTED는 Dirty Read, READ COMMITTED는 Non-Repeatable Read, REPEATABLE READ는 Phantom Read가 발생할 수 있고, SERIALIZABLE은 모두 방지합니다.
3. **MySQL의 기본 격리 수준과 Phantom Read 처리는?**
   → REPEATABLE READ이며, MVCC 스냅샷 읽기와 잠금 읽기 시 넥스트 키 락으로 대부분의 Phantom Read를 방지합니다.
4. **@Transactional이 동작하지 않는 경우는?**
   → 같은 클래스 내부 호출, private 메서드, Checked Exception 발생 시(기본 설정)입니다.

## 핵심 정리
- 트랜잭션 = All or Nothing 작업 단위
- ACID: 원자성(Undo) / 일관성(제약) / 격리성(락·MVCC) / 지속성(Redo)
- 이상 현상: Dirty → Non-Repeatable(수정) → Phantom(추가·삭제)
- 격리 수준: RU < RC(Oracle·PG 기본) < RR(MySQL 기본) < SERIALIZABLE
- Spring: 프록시 기반, RuntimeException만 롤백, 전파 속성 REQUIRED/REQUIRES_NEW
