# 06. 동시성 제어와 회복 (Concurrency Control & Recovery)

> **학습 목표**

> - 낙관적 락과 비관적 락을 비교하고 JPA로 구현할 수 있다.

# Part 1. 동시성 제어

## 1. 직렬 가능성 (Serializability)

여러 트랜잭션을 **동시에 실행한 결과가, 어떤 순서로 하나씩 실행한 결과와 같으면** 직렬 가능하다고 합니다. 동시성 제어의 목표는 성능을 유지하면서 직렬 가능성을 보장하는 것입니다.

---

## 2. 락 (Lock)

### 락 종류
| 락 | 다른 이름 | 용도 | SQL |
|---|---|---|---|
| **공유 락 (S Lock)** | 읽기 락 | 읽는 동안 다른 사람의 **쓰기 차단** | `SELECT ... FOR SHARE` |
| **배타 락 (X Lock)** | 쓰기 락 | 쓰는 동안 다른 사람의 **읽기·쓰기 모두 차단** | `SELECT ... FOR UPDATE`, UPDATE, DELETE |

### 호환성
| 요청 \ 보유 | S | X |
|---|---|---|
| **S** | O (같이 읽기 가능) | X |
| **X** | X | X |

> InnoDB에서 **일반 SELECT는 락을 걸지 않습니다(MVCC 스냅샷 읽기).** 그래서 배타 락이 걸린 행도 일반 SELECT로는 읽을 수 있습니다.

### 락 단위 (Granularity)
| 단위 | 동시성 | 관리 비용 |
|---|---|---|
| 데이터베이스 | 낮음 | 낮음 |
| 테이블 | ↓ | ↓ |
| 페이지 | ↓ | ↓ |
| **행 (Row)** | **높음** | **높음** |

InnoDB는 **행 단위 락**을 쓰며, 실제로는 **인덱스 레코드에 락**을 겁니다. → 인덱스가 없는 컬럼으로 `UPDATE ... WHERE`하면 **스캔한 모든 행에 락**이 걸려 사실상 테이블 락처럼 동작할 수 있습니다.

### InnoDB의 락 종류
- **레코드 락**: 인덱스 레코드 하나
- **갭 락 (Gap Lock)**: 레코드 사이의 **빈 공간**을 잠가 새 행 삽입 차단
- **넥스트 키 락**: 레코드 락 + 그 앞의 갭 락 → REPEATABLE READ에서 Phantom 방지

---

## 3. 2단계 락킹 (2PL, Two-Phase Locking)

트랜잭션이 락을 획득·해제하는 과정을 두 단계로 나눕니다.

```
락 개수
  ↑      ___________
  |     /           \
  |    /             \
  |   /               \
  +--/-----------------\----> 시간
   확장 단계 | 축소 단계
   (획득만)    (해제만)
```

1. **확장 단계 (Growing)**: 락을 **획득만** 하고 해제하지 않음
2. **축소 단계 (Shrinking)**: 락을 **해제만** 하고 새로 획득하지 않음

- 2PL을 지키면 **직렬 가능성이 보장**됩니다.
- 단점: **데드락이 발생할 수 있음**
- **Strict 2PL**: 배타 락을 **COMMIT/ROLLBACK 할 때까지 유지** → 연쇄 롤백 방지 (대부분 DBMS 방식)

---

## 4. MVCC (Multi-Version Concurrency Control)

**데이터의 여러 버전을 유지해서, 읽기와 쓰기가 서로를 막지 않게** 하는 기법입니다.

```
T1(트랜잭션 ID 100): UPDATE 잔액 = 5000 (아직 COMMIT 안 함)

     테이블(최신)            Undo 로그(이전 버전)
   | 잔액 5000, trx=100 | → | 잔액 10000, trx=90 |

T2(ID 101): SELECT 잔액
  → 최신 행은 아직 커밋 안 된 trx 100이 수정함 → 내가 볼 수 없음
  → Undo 로그를 따라가 커밋된 이전 버전 10000을 읽음 (락 대기 없음!)
```

- 각 트랜잭션은 시작 시점(또는 쿼리 시점)의 **스냅샷(Read View)** 을 봅니다.
  - READ COMMITTED: **쿼리마다** 새 스냅샷
  - REPEATABLE READ: **트랜잭션의 첫 조회 시점** 스냅샷 유지
- **읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않음** → 높은 동시성
- 쓰기끼리는 여전히 락으로 충돌을 제어
- MySQL InnoDB, PostgreSQL, Oracle이 사용

> 트랜잭션을 오래 열어 두면 오래된 Undo 버전을 지울 수 없어 Undo 공간이 커지고 성능이 떨어집니다. **트랜잭션은 짧게** 유지하세요.

## 5. 낙관적 락 vs 비관적 락 (애플리케이션 관점)

### 비관적 락 (Pessimistic Lock)
"충돌이 **자주 날 것**이다" → **먼저 락을 건다**

```sql
SELECT * FROM product WHERE id = 1 FOR UPDATE;   -- 다른 트랜잭션은 대기
UPDATE product SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

```java
// JPA
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Optional<Product> findByIdForUpdate(@Param("id") Long id);
```

### 낙관적 락 (Optimistic Lock)
"충돌이 **거의 안 날 것**이다" → 락 없이 진행하고 **커밋할 때 버전을 확인**

```sql
-- 읽을 때: version = 3
UPDATE product SET stock = 9, version = 4
WHERE id = 1 AND version = 3;
-- 영향받은 행이 0이면 → 누군가 먼저 수정함 → 재시도 or 실패 처리
```

```java
@Entity
public class Product {
    @Id Long id;
    int stock;
    @Version Long version;   // JPA가 자동으로 버전 체크
}
// 충돌 시 ObjectOptimisticLockingFailureException 발생 → 재시도 로직 필요
```

### 비교
| 항목 | 비관적 락 | 낙관적 락 |
|---|---|---|
| 방식 | DB 락 (`FOR UPDATE`) | 버전 컬럼 비교 |
| 충돌 시 | 대기 | 예외 → 재시도 |
| 적합한 경우 | **충돌이 잦음** (인기 상품 재고, 좌석 예매) | **충돌이 드묾** (게시글 수정, 프로필 수정) |
| 단점 | 대기 시간, 데드락 위험 | 충돌 잦으면 재시도 폭증 |

> **분산 환경(서버 여러 대)** 에서는 Redis 기반 분산 락(Redisson)을 쓰기도 합니다. 단순 재고 차감은 `UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock > 0` 처럼 **원자적 UPDATE** 한 줄로도 해결됩니다.

# Part 2. 회복 (Recovery)

## 6. 장애 유형
| 유형 | 예 |
|---|---|
| 트랜잭션 장애 | 논리 오류, 데드락으로 인한 강제 롤백 |
| 시스템 장애 | 전원 차단, OS 크래시 → **메모리 내용 손실** |
| 미디어 장애 | 디스크 손상 → 백업 필요 |

## 7. DB는 왜 바로 디스크에 쓰지 않을까?

디스크 랜덤 쓰기는 느립니다. 그래서 DB는 변경을 **메모리(버퍼 풀)** 에 먼저 반영하고, 나중에 모아서 디스크에 씁니다. 그러면 메모리에만 있던 커밋 데이터가 장애로 사라질 수 있습니다. → **로그**로 해결합니다.

## 8. 로그 기반 회복

### Undo 로그
- 변경 **이전 값** 기록
- **롤백**할 때, 그리고 장애 후 **커밋 안 된 트랜잭션을 되돌릴 때** 사용 → **원자성**
- MVCC의 이전 버전 제공에도 사용

### Redo 로그
- 변경 **이후 값** 기록
- 장애 후 **커밋됐지만 디스크에 반영 안 된 변경을 다시 적용** → **지속성**

### WAL (Write-Ahead Logging)
**데이터 페이지를 디스크에 쓰기 전에, 해당 로그를 먼저 디스크에 기록**한다는 원칙입니다.
- COMMIT 시 **로그만 순차적으로** 디스크에 쓰면(빠름) 지속성이 보장됩니다.
- 실제 데이터 페이지는 나중에 천천히 디스크에 반영해도 됩니다.

```
COMMIT 시점
 1. Redo 로그를 디스크에 flush   ← 순차 쓰기, 빠름
 2. "커밋 완료" 응답
 3. (나중에) 버퍼 풀의 변경 페이지를 디스크에 기록
```

## 9. 체크포인트 (Checkpoint)

장애 후 로그를 **처음부터 전부** 다시 실행하면 너무 오래 걸립니다. 주기적으로 **메모리의 변경 페이지를 디스크에 반영하고 그 시점을 기록**해 두면, 회복 시 **마지막 체크포인트 이후의 로그만** 처리하면 됩니다.

```
---[체크포인트]----T1 시작---T1 커밋---T2 시작---💥장애
                   └── Redo (커밋됨, 다시 적용)
                                    └── Undo (커밋 안 됨, 되돌림)
```

## 10. 회복 기법 요약
| 기법 | 설명 |
|---|---|
| 지연 갱신 (Deferred Update) | 커밋 전까지 디스크에 반영 X → 장애 시 Redo만 필요 |
| 즉시 갱신 (Immediate Update) | 커밋 전에도 디스크 반영 가능 → Undo + Redo 필요 |
| 그림자 페이징 (Shadow Paging) | 변경 시 페이지 복사본에 쓰고, 커밋 시 페이지 테이블 교체 (로그 불필요) |

> MySQL InnoDB는 **Redo 로그(ib_logfile / redo log) + Undo 로그 + Doublewrite 버퍼**로 회복합니다. 복제와 시점 복구에는 별도의 **Binary Log**를 씁니다.

## 11. 면접 질문

1. **공유 락과 배타 락의 차이는?**
   → 공유 락은 읽기용으로 서로 같이 걸 수 있지만 배타 락과는 공존할 수 없고, 배타 락은 쓰기용으로 어떤 락과도 공존할 수 없습니다.
2. **MVCC란?**
   → 데이터의 여러 버전을 Undo 로그로 유지해 각 트랜잭션이 자신의 스냅샷을 읽게 함으로써, 읽기와 쓰기가 서로를 막지 않게 하는 동시성 제어 방식입니다.
3. **낙관적 락과 비관적 락은 언제 쓰나요?**
   → 충돌이 잦으면 미리 락을 거는 비관적 락, 충돌이 드물면 버전으로 커밋 시점에 검사하는 낙관적 락을 씁니다.
4. **WAL이란?**
   → 데이터를 디스크에 쓰기 전에 로그를 먼저 디스크에 기록하는 원칙으로, 커밋 시 로그만 순차적으로 기록해 빠르면서도 지속성을 보장합니다.
5. **Redo와 Undo의 차이는?**
   → Redo는 커밋된 변경을 재적용해 지속성을, Undo는 커밋되지 않은 변경을 되돌려 원자성을 보장합니다.

## 핵심 정리
- S 락끼리만 호환, X 락은 모두 배타 / InnoDB는 인덱스 레코드에 행 락
- 2PL: 확장 → 축소, 직렬성 보장, 데드락 가능
- MVCC: Undo로 이전 버전 → 읽기·쓰기 비차단
- 비관적(FOR UPDATE) vs 낙관적(@Version)
- 회복: Undo(원자성) + Redo(지속성) + WAL + 체크포인트
