## 1. NoSQL이란?

**Not Only SQL**. 관계형 모델(고정 스키마 테이블 + JOIN)이 아닌 방식으로 데이터를 저장하는 데이터베이스입니다.

### 등장 배경
- 웹 서비스 데이터가 폭증 → 한 대의 서버로 감당 불가
- RDBMS는 **수평 확장(서버 추가)** 이 어려움 (JOIN, 트랜잭션이 여러 서버에 걸치면 복잡)
- 스키마가 자주 바뀌는 비정형 데이터 (로그, SNS 게시물, IoT)

---

## 2. RDBMS vs NoSQL

| 항목 | RDBMS | NoSQL |
|---|---|---|
| 데이터 모델 | 테이블 (행·열) | 키-값, 문서, 컬럼, 그래프 |
| 스키마 | **고정** (먼저 정의) | **유연** (스키마리스) |
| 관계 | JOIN | 보통 JOIN 없음 → **중복 저장(비정규화)** |
| 트랜잭션 | **ACID** 강함 | **BASE**, 제품마다 다름 (MongoDB는 다중 문서 트랜잭션 지원) |
| 확장 | **수직 확장** (Scale-up, 더 좋은 서버) 위주 | **수평 확장** (Scale-out, 서버 추가) 용이 |
| 쿼리 | 표준 SQL | 제품별 API/쿼리 언어 |
| 적합한 곳 | 금융, 주문, 결제 등 **정합성 중요** | 대용량, 빠른 읽기·쓰기, 유연한 구조 |

> 둘 중 하나만 고르는 것이 아니라, **용도에 따라 함께 쓰는 것(Polyglot Persistence)** 이 일반적입니다. 예: 주문은 MySQL, 세션·캐시는 Redis, 검색은 Elasticsearch.

## 3. NoSQL 유형

### 3-1. 키-값 (Key-Value)
```
"session:abc123" → {"userId": 42, "role": "USER"}
"product:1:stock" → 100
```
- 가장 단순, **매우 빠름** (해시 테이블 구조)
- 값 내부로 검색하기 어려움
- **Redis**, Amazon DynamoDB, Memcached
- 사용처: **캐시, 세션 저장소**, 실시간 순위, 장바구니

### 3-2. 문서 (Document)
```json
{
  "_id": "u1",
  "name": "김철수",
  "address": { "city": "대전", "zip": "34100" },
  "orders": [
    { "item": "책", "price": 15000 },
    { "item": "펜", "price": 2000 }
  ]
}
```
- JSON/BSON 형태의 문서 저장, **문서마다 구조가 달라도 됨**
- 내부 필드로 검색·인덱싱 가능
- 관련 데이터를 **한 문서에 내장(embed)** → JOIN 불필요
- **MongoDB**, CouchDB
- 사용처: 콘텐츠 관리, 상품 카탈로그(상품마다 속성이 다름), 사용자 프로필

### 3-3. 컬럼 패밀리 (Wide Column)
```
Row Key: user1
  ├─ profile: {name: 김철수, age: 25}
  └─ activity: {2026-11-01: login, 2026-11-02: purchase, ...}  ← 컬럼이 계속 늘어날 수 있음
```
- 행마다 다른 컬럼을 가질 수 있고, 컬럼이 수백만 개까지 가능
- **쓰기 성능이 매우 뛰어남**, 대규모 분산
- **Apache Cassandra**, HBase
- 사용처: 로그, 시계열 데이터, 채팅 메시지 기록

### 3-4. 그래프 (Graph)
```
(김철수)-[:친구]->(이영희)-[:좋아요]->(게시글1)
```
- **노드와 관계(엣지)** 를 저장, 관계 탐색에 특화
- RDBMS에서 여러 단계 JOIN이 필요한 쿼리를 빠르게 처리
- **Neo4j** (Cypher 쿼리), Amazon Neptune
- 사용처: SNS 친구 추천, 추천 시스템, 사기 탐지, **지식 그래프·온톨로지**

```cypher
// 친구의 친구 찾기
MATCH (me:Person {name: '김철수'})-[:FRIEND]->()-[:FRIEND]->(fof)
WHERE fof <> me
RETURN DISTINCT fof.name
```

## 4. CAP 정리 (CAP Theorem)

분산 시스템은 다음 세 가지를 **동시에 모두 만족할 수 없다**는 정리입니다.

| 속성 | 의미 |
|---|---|
| **C** (Consistency, 일관성) | 모든 노드가 **같은 시점에 같은 데이터**를 보여 줌 |
| **A** (Availability, 가용성) | 일부 노드가 죽어도 **모든 요청에 응답** |
| **P** (Partition Tolerance, 분할 내성) | 노드 간 **네트워크가 끊겨도** 시스템이 동작 |

```
           C
          / \
        CP   CA
        /     \
       P ─ AP ─ A
```

- 분산 시스템에서 **네트워크 장애(P)는 피할 수 없으므로**, 실제로는 **장애 시 C와 A 중 무엇을 포기할지**의 선택입니다.

| 선택 | 의미 | 예 |
|---|---|---|
| **CP** | 분할 시 일관성을 위해 일부 요청을 거부 | MongoDB(기본 설정), HBase, ZooKeeper |
| **AP** | 분할 시 응답은 하지만 오래된 데이터일 수 있음 | Cassandra, DynamoDB(기본), CouchDB |
| CA | 분할이 없는 단일 노드 | 단일 서버 RDBMS |

> CAP은 장애 상황만 다룹니다. 정상 상황까지 고려한 **PACELC** 정리: 분할(P) 시에는 A와 C 중 선택, 정상(Else) 시에는 지연 시간(L)과 일관성(C) 중 선택.

## 5. BASE

RDBMS의 ACID에 대응하는, 가용성을 우선하는 NoSQL의 특성입니다.

| 속성 | 의미 |
|---|---|
| **B**asically **A**vailable | 기본적으로 항상 응답 |
| **S**oft state | 외부 입력이 없어도 상태가 변할 수 있음 (복제 진행 중) |
| **E**ventually consistent | **결국에는** 모든 노드가 같은 값이 됨 (**최종적 일관성**) |

예: SNS 좋아요 수가 사용자마다 잠깐 다르게 보여도, 몇 초 뒤에는 같아짐

## 6. Redis 자세히

백엔드에서 가장 많이 쓰는 NoSQL입니다.

### 특징
- **인메모리** 키-값 저장소 → 매우 빠름 (μs 단위)
- **싱글 스레드**로 명령 처리 (I/O 멀티플렉싱) → 명령 하나하나가 원자적
  - Redis 6부터 네트워크 I/O는 멀티스레드 옵션 지원, 명령 실행은 여전히 단일 스레드
  - 그래서 `KEYS *` 같은 O(n) 명령은 **전체를 멈추게** 할 수 있음 → `SCAN` 사용
- 다양한 자료구조 지원
- 영속성 옵션: **RDB**(주기적 스냅샷), **AOF**(모든 쓰기 명령 로그)

| 자료구조 | 사용 예 |
|---|---|
| String | 캐시, 카운터 (`INCR`), 분산 락 (`SET key val NX EX 10`) |
| List | 메시지 큐, 최근 본 상품 |
| Set | 중복 없는 집합 (좋아요 누른 사용자) |
| **Sorted Set** | **실시간 랭킹** (점수 기준 정렬) |
| Hash | 객체 저장 (사용자 정보 필드별) |

### 캐시 전략
| 전략 | 방식 |
|---|---|
| **Cache-Aside (Look-Aside)** | 앱이 캐시 조회 → 없으면(miss) DB 조회 후 캐시에 저장. **가장 일반적** |
| Write-Through | 쓸 때 캐시와 DB에 동시에 기록 → 일관성 좋음, 쓰기 느림 |
| Write-Back (Write-Behind) | 캐시에만 쓰고 나중에 DB에 일괄 반영 → 빠름, 유실 위험 |

```java
// Spring Cache-Aside
@Cacheable(value = "product", key = "#id")
public ProductDto getProduct(Long id) {
    return productRepository.findById(id).map(ProductDto::from).orElseThrow();
}

@CacheEvict(value = "product", key = "#id")
public void updateProduct(Long id, UpdateRequest req) { ... }
```

### 캐시 문제
| 문제 | 설명 | 해결 |
|---|---|---|
| **캐시 스탬피드** (Thundering Herd) | 인기 키가 만료되는 순간 수많은 요청이 동시에 DB로 | 락으로 한 요청만 갱신, 만료 전 미리 갱신, TTL에 랜덤 값 추가 |
| 캐시 관통 (Penetration) | 존재하지 않는 키 요청이 계속 DB로 | 빈 값도 짧게 캐싱, 블룸 필터 |
| 데이터 불일치 | DB는 바뀌었는데 캐시는 옛날 값 | 수정 시 캐시 삭제(evict), 적절한 TTL |

## 7. 면접 질문

1. **RDBMS와 NoSQL의 차이와 선택 기준은?**
   → RDBMS는 고정 스키마와 ACID로 정합성이 중요한 데이터에, NoSQL은 유연한 스키마와 수평 확장으로 대용량·빠른 처리·비정형 데이터에 적합합니다.
2. **CAP 정리란?**
   → 분산 시스템은 일관성, 가용성, 분할 내성을 동시에 만족할 수 없다는 정리로, 네트워크 분할은 피할 수 없어 실제로는 C와 A 중 하나를 선택합니다.
3. **Redis가 싱글 스레드인데 빠른 이유는?**
   → 데이터가 메모리에 있고, 이벤트 루프 기반 I/O 멀티플렉싱으로 컨텍스트 스위칭과 락 경쟁 없이 명령을 처리하기 때문입니다.
4. **Cache-Aside 전략이란?**
   → 애플리케이션이 먼저 캐시를 조회하고, 없으면 DB에서 읽어 캐시에 저장하는 방식입니다.

## 핵심 정리
- NoSQL 4유형: 키-값(Redis) / 문서(MongoDB) / 컬럼(Cassandra) / 그래프(Neo4j)
- CAP: P는 필수 → CP vs AP
- BASE: 최종적 일관성
- Redis: 인메모리 + 싱글 스레드 + 다양한 자료구조, Cache-Aside가 기본
