# 08. DB 확장: 레플리케이션, 파티셔닝, 샤딩

> **학습 목표**
> - 수직 확장과 수평 확장의 차이를 설명할 수 있다.
> - 레플리케이션의 구조와 복제 지연 문제를 설명할 수 있다.
> - 파티셔닝과 샤딩의 차이, 샤딩 전략을 비교할 수 있다.
> - 커넥션 풀이 필요한 이유를 설명할 수 있다.

---

## 1. 확장 방식

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **수직 확장** (Scale-Up) | 서버 사양을 높임 (CPU, RAM, SSD) | 구조 변경 없음 | 비용 급증, **한계가 있음**, 단일 장애점 |
| **수평 확장** (Scale-Out) | 서버 대수를 늘림 | 이론상 무한 확장, 장애 분산 | 데이터 분산·일관성 관리 복잡 |

DB 수평 확장 방법:
- 읽기가 많다 → **레플리케이션**
- 데이터가 너무 많다 → **파티셔닝 / 샤딩**

---

## 2. 레플리케이션 (Replication)

**같은 데이터를 여러 DB 서버에 복제**하는 것입니다.

```
              쓰기(INSERT/UPDATE/DELETE)
  [Application] ─────────────> [Primary (Master)]
        │                           │ 변경 로그(binlog) 전송
        │ 읽기(SELECT)               ├──────────> [Replica 1 (Slave)]
        └─────────────────────────> ├──────────> [Replica 2]
                                    └──────────> [Replica 3]
```

- **Primary**: 쓰기 담당
- **Replica**: Primary의 변경을 복제받아 **읽기 담당**
- 웹 서비스는 보통 **읽기가 쓰기보다 훨씬 많아서**(8:2 이상) 읽기를 분산하면 효과가 큼

### 장점
- **읽기 성능 향상** (부하 분산)
- **고가용성**: Primary가 죽으면 Replica를 Primary로 승격 (Failover)
- 백업, 분석 쿼리를 Replica에서 실행 → 운영 DB 부하 없음

### 복제 방식
| 방식 | 설명 | 특징 |
|---|---|---|
| **비동기** (Asynchronous) | Primary는 커밋 후 바로 응답, 복제는 나중에 | 빠름, **장애 시 데이터 유실 가능** (MySQL 기본) |
| 동기 (Synchronous) | 모든 Replica 반영 후 응답 | 안전, 느림 |
| **반동기** (Semi-sync) | 최소 하나의 Replica가 **받았다는 확인** 후 응답 | 절충안 |

### 복제 지연 (Replication Lag) 문제
```
1. 사용자가 글 작성 → Primary에 INSERT
2. 바로 목록 조회 → Replica에서 SELECT
3. 아직 복제 안 됨 → 방금 쓴 글이 안 보임!
```
해결:
- **쓰기 직후 읽기는 Primary에서** (Read-Your-Writes)
- 중요한 조회는 Primary로 라우팅

```java
// Spring: readOnly 트랜잭션을 Replica로 라우팅 (AbstractRoutingDataSource 활용)
@Transactional(readOnly = true)    // → Replica
public List<Post> findPosts() { ... }

@Transactional                     // → Primary
public void writePost(...) { ... }
```

## 3. 파티셔닝 (Partitioning)

**하나의 큰 테이블을 여러 조각으로 나누는 것**입니다. 보통 **같은 DB 서버 안에서** 나눕니다.

### 수직 파티셔닝 (Vertical)
**컬럼 기준**으로 나눔
```
member (id, name, email, profile_image, introduction)
→ member (id, name, email)
→ member_detail (id, profile_image, introduction)   ← 큰 컬럼, 자주 안 쓰는 컬럼 분리
```

### 수평 파티셔닝 (Horizontal)
**행 기준**으로 나눔
```
order_log
→ 2024년 파티션
→ 2025년 파티션
→ 2026년 파티션     ← WHERE created_at >= '2026-01-01' 이면 이 파티션만 스캔
```

```sql
-- MySQL 범위 파티셔닝
CREATE TABLE order_log (
    id BIGINT, created_at DATE, ...
    PRIMARY KEY (id, created_at)
)
PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN (2027)
);
```

- 조회 범위가 줄어들고(**파티션 프루닝**), 오래된 파티션은 통째로 삭제 가능

## 4. 샤딩 (Sharding)

**수평 파티셔닝을 여러 DB 서버에 분산**하는 것입니다. 각 서버(조각)를 **샤드**라고 합니다.

```
                [Application / Router]
               /          |           \
   [Shard 1: user 1~100만] [Shard 2: 100만~200만] [Shard 3: 200만~300만]
```

### 샤딩 전략
| 전략 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **범위 기반** (Range) | id 1~100만 → 샤드1 | 구현 쉬움, 범위 조회 유리 | **데이터 쏠림(핫스팟)** — 최신 데이터가 한 샤드에 몰림 |
| **해시 기반** (Hash) | `hash(user_id) % N` | 고르게 분산 | **샤드 추가 시 대부분 재배치**, 범위 조회 불리 |
| **디렉토리 기반** | 조회 테이블로 매핑 | 유연 | 조회 테이블이 병목/단일 장애점 |
| **일관된 해싱** (Consistent Hashing) | 해시 링에 샤드 배치 | 샤드 추가 시 **일부만 재배치** | 구현 복잡 |

### 일관된 해싱
```
          0
     S3 /   \ S1
       |     |       키는 시계 방향으로 가장 가까운 샤드에 저장
     S2 \   / 
          ...
샤드 S4를 S1과 S2 사이에 추가 → S1~S4 구간의 키만 S4로 이동 (전체의 일부)
```
- `% N` 방식은 N이 바뀌면 거의 모든 키의 위치가 바뀌지만, 일관된 해싱은 약 1/N만 이동합니다.
- Cassandra, DynamoDB, Redis Cluster(해시 슬롯 방식) 등에서 유사한 개념을 사용

### 샤딩의 어려움
- **샤드 간 JOIN 불가** → 애플리케이션에서 합치거나 비정규화
- **샤드 간 트랜잭션** 어려움 → 분산 트랜잭션(2PC), Saga 패턴
- **샤드 키 선택**이 매우 중요 (자주 같이 조회되는 데이터가 같은 샤드에)
- 전역 고유 ID 생성 필요 (AUTO_INCREMENT를 샤드별로 쓰면 중복) → Snowflake ID, UUID
- 재샤딩(리밸런싱) 비용

> 샤딩은 복잡도가 매우 크므로 **인덱스 튜닝 → 캐시 → 레플리케이션 → 파티셔닝 → 샤딩** 순서로 검토합니다.

## 5. 커넥션 풀 (Connection Pool)

DB 연결을 만드는 것은 비쌉니다 (TCP 3-way handshake, 인증, 세션 생성). 요청마다 연결을 새로 만들면 느립니다.

**커넥션 풀**: 미리 일정 개수의 연결을 만들어 두고 **빌려 쓰고 반납**합니다.

```
[요청] → 풀에서 커넥션 대여 → 쿼리 실행 → 반납
         (모두 사용 중이면 대기 → 타임아웃 시 예외)
```

- Spring Boot 기본: **HikariCP**
- 너무 작으면 대기 발생, 너무 크면 DB 서버 부하와 컨텍스트 스위칭 증가

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      connection-timeout: 3000   # ms
```

> HikariCP 문서에서 제시하는 출발점 공식: `connections = (CPU 코어 수 × 2) + 유효 디스크 수`. 실제 값은 부하 테스트로 조정합니다.

## 6. 면접 질문

1. **레플리케이션의 장점과 문제점은?**
   → 읽기 부하 분산과 고가용성을 얻지만, 비동기 복제의 지연으로 방금 쓴 데이터가 Replica에서 보이지 않을 수 있습니다.
2. **파티셔닝과 샤딩의 차이는?**
   → 파티셔닝은 테이블을 나누는 것 자체(보통 같은 서버)이고, 샤딩은 수평 분할한 데이터를 여러 서버에 분산하는 것입니다.
3. **해시 샤딩의 단점과 해결책은?**
   → 샤드 수가 바뀌면 대부분의 데이터를 재배치해야 합니다. 일관된 해싱으로 이동량을 줄입니다.
4. **커넥션 풀을 쓰는 이유는?**
   → DB 연결 생성 비용이 커서 미리 만든 연결을 재사용해 응답 시간을 줄이고 DB 연결 수를 제한하기 위해서입니다.

## 핵심 정리
- Scale-Up(한계) vs Scale-Out(복잡)
- 레플리케이션: Primary 쓰기 + Replica 읽기, 복제 지연 주의
- 파티셔닝(테이블 분할) / 샤딩(서버 분산), 해시 샤딩은 일관된 해싱으로 보완
- 커넥션 풀(HikariCP)로 연결 재사용
