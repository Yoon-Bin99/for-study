# 05. HTTP

> **학습 목표**
> - HTTP의 특징(무상태, 비연결)과 메시지 구조를 설명할 수 있다.
> - HTTP 메서드의 의미와 멱등성·안전성을 구분할 수 있다.
> - 주요 상태 코드를 상황에 맞게 사용할 수 있다.
> - HTTP/1.0, 1.1, 2, 3의 차이를 설명할 수 있다.
> - HTTP 캐시(Cache-Control, ETag)를 설명할 수 있다.

---

## 1. HTTP란?

**HyperText Transfer Protocol**. 웹에서 클라이언트와 서버가 데이터를 주고받는 **응용 계층 프로토콜**입니다. HTML뿐 아니라 JSON, 이미지, 파일 등 거의 모든 데이터를 HTTP로 전송합니다.

### 특징
| 특징 | 설명 |
|---|---|
| **클라이언트-서버 구조** | 클라이언트가 요청(Request), 서버가 응답(Response) |
| **무상태 (Stateless)** | 서버가 **이전 요청을 기억하지 않음**. 각 요청은 독립적 |
| **비연결 (Connectionless)** | 원래는 응답 후 연결을 끊음 (HTTP/1.1부터는 Keep-Alive로 재사용) |
| 텍스트 기반 (1.1까지) | 사람이 읽을 수 있는 형식 (HTTP/2부터는 바이너리) |

### 무상태의 장단점
- 장점: 어떤 서버가 응답해도 됨 → **서버를 쉽게 늘릴 수 있음(수평 확장)**
- 단점: 로그인 상태 같은 정보를 매 요청마다 보내야 함 → **쿠키, 세션, 토큰**으로 보완 (→ `08.웹통신기술.md`)

## 2. HTTP 메시지 구조

### 요청
```
POST /api/members HTTP/1.1                ← 시작 줄: 메서드, 경로, 버전
Host: api.example.com                     ← 헤더
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Content-Length: 38
                                          ← 빈 줄 (헤더 끝)
{"name": "김철수", "email": "a@b.com"}    ← 바디
```

### 응답
```
HTTP/1.1 201 Created                      ← 상태 줄: 버전, 상태 코드, 이유
Content-Type: application/json
Location: /api/members/42

{"id": 42, "name": "김철수"}
```

### 주요 헤더
| 헤더 | 의미 |
|---|---|
| `Host` | 요청 대상 도메인 (한 서버에 여러 도메인 운영 시 구분, 1.1 필수) |
| `Content-Type` | 바디 형식 (`application/json`, `text/html; charset=UTF-8`, `multipart/form-data`) |
| `Content-Length` | 바디 크기 |
| `Accept` | 클라이언트가 받을 수 있는 형식 |
| `Authorization` | 인증 정보 |
| `Cookie` / `Set-Cookie` | 쿠키 전달 / 설정 |
| `User-Agent` | 클라이언트 정보 |
| `Cache-Control` | 캐시 정책 |
| `Location` | 리다이렉트 위치, 생성된 리소스 위치 |

## 3. HTTP 메서드

| 메서드 | 의미 | 바디 | 안전 | 멱등 |
|---|---|---|---|---|
| **GET** | 리소스 조회 | 보통 X | O | O |
| **POST** | 리소스 생성, 처리 요청 | O | X | **X** |
| **PUT** | 리소스 **전체 대체** (없으면 생성) | O | X | O |
| **PATCH** | 리소스 **부분 수정** | O | X | X (구현에 따라) |
| **DELETE** | 리소스 삭제 | 보통 X | X | O |
| HEAD | GET과 같지만 헤더만 | X | O | O |
| OPTIONS | 지원 메서드 확인, **CORS 사전 요청** | X | O | O |

- **안전 (Safe)**: 서버 리소스를 **변경하지 않음**
- **멱등 (Idempotent)**: **같은 요청을 여러 번 보내도 결과(서버 상태)가 같음**
  - `DELETE /members/1` 을 두 번 → 결과적으로 1번 회원은 삭제된 상태 (응답 코드는 다를 수 있음)
  - `POST /orders` 를 두 번 → **주문이 2개** 생김 → 멱등 X
- 멱등이 중요한 이유: 네트워크 오류로 응답을 못 받았을 때 **안전하게 재시도해도 되는지** 판단 기준

### PUT vs PATCH
```
기존: {"name": "김철수", "age": 25, "city": "대전"}

PUT   {"name": "김철수", "age": 26}  → {"name": "김철수", "age": 26}          (city 사라짐)
PATCH {"age": 26}                   → {"name": "김철수", "age": 26, "city": "대전"}
```

### GET vs POST
| 비교 | GET | POST |
|---|---|---|
| 데이터 위치 | URL 쿼리 스트링 (`?page=1`) | 바디 |
| 노출 | URL, 브라우저 기록, 서버 로그에 남음 | 바디라 덜 노출 (그래도 HTTPS 필요) |
| 길이 | URL 길이 제한 (브라우저·서버마다 다름) | 사실상 제한 없음 |
| 캐시 | 가능 | 일반적으로 X |
| 북마크 | 가능 | X |

## 4. 상태 코드

| 범위 | 의미 |
|---|---|
| 1xx | 정보 (처리 중) |
| **2xx** | **성공** |
| **3xx** | **리다이렉션** |
| **4xx** | **클라이언트 오류** |
| **5xx** | **서버 오류** |

| 코드 | 의미 | 사용 예 |
|---|---|---|
| **200 OK** | 성공 | 조회 성공 |
| **201 Created** | 생성됨 | POST로 회원 가입 (Location 헤더) |
| **204 No Content** | 성공, 바디 없음 | DELETE 성공 |
| **301 Moved Permanently** | 영구 이동 | 도메인 변경 (검색 엔진도 새 URL로) |
| **302 Found** | 임시 이동 | 로그인 후 리다이렉트 |
| **304 Not Modified** | 캐시 사용 | 리소스가 안 바뀜 → 바디 없이 응답 |
| **400 Bad Request** | 잘못된 요청 | 유효성 검사 실패, JSON 형식 오류 |
| **401 Unauthorized** | **인증 필요** | 로그인 안 함, 토큰 만료 |
| **403 Forbidden** | **권한 없음** | 로그인은 했지만 관리자 페이지 접근 |
| **404 Not Found** | 리소스 없음 | 없는 회원 조회 |
| **405 Method Not Allowed** | 메서드 지원 X | |
| **409 Conflict** | 충돌 | 이메일 중복 가입, 낙관적 락 충돌 |
| **429 Too Many Requests** | 요청 과다 | Rate Limit 초과 |
| **500 Internal Server Error** | 서버 내부 오류 | 처리 안 된 예외 |
| **502 Bad Gateway** | 게이트웨이 오류 | Nginx 뒤 애플리케이션 서버가 죽음 |
| **503 Service Unavailable** | 일시적 서비스 불가 | 점검, 과부하 |
| **504 Gateway Timeout** | 게이트웨이 시간 초과 | 뒤의 서버 응답이 너무 느림 |

> **401 vs 403**: 401은 "**누구세요?**" (인증 실패), 403은 "**당신인 건 알지만 안 돼요**" (인가 실패)

## 5. HTTP 버전별 발전

### HTTP/1.0
- 요청마다 **TCP 연결을 새로** 맺고 끊음 → 3-way handshake 반복으로 느림

### HTTP/1.1 (1997)
- **지속 연결 (Persistent Connection, Keep-Alive)**: 하나의 TCP 연결로 여러 요청 처리 (기본값)
- **파이프라이닝**: 응답을 기다리지 않고 여러 요청을 연속 전송 (하지만 응답은 순서대로 → 거의 안 쓰임)
- `Host` 헤더 필수 → 가상 호스팅
- 문제: **HOL (Head-of-Line) Blocking** — 앞의 응답이 느리면 뒤의 응답이 모두 대기
  → 브라우저는 도메인당 TCP 연결을 6개 정도 동시에 열어 우회

### HTTP/2 (2015)
| 기능 | 설명 |
|---|---|
| **바이너리 프레이밍** | 메시지를 바이너리 프레임으로 나눠 전송 → 파싱 효율 |
| **멀티플렉싱** | **하나의 TCP 연결에서 여러 요청·응답을 동시에** 섞어 전송 (스트림) → HTTP 레벨 HOL 해결 |
| **헤더 압축 (HPACK)** | 반복되는 헤더를 압축 |
| 서버 푸시 | 요청 전에 필요한 리소스를 미리 전송 (실제로는 거의 안 쓰여 브라우저들이 지원 중단) |
| 스트림 우선순위 | 중요한 리소스 먼저 |

- 남은 문제: **TCP 레벨 HOL Blocking** — TCP 패킷 하나가 손실되면, 그 연결의 **모든 스트림이** 재전송을 기다림

### HTTP/3 (2022)
- **TCP 대신 UDP 기반의 QUIC** 프로토콜 사용
- 스트림이 **독립적** → 한 스트림의 패킷 손실이 다른 스트림에 영향 X → **TCP HOL 해결**
- **연결 수립이 빠름**: TCP + TLS 핸드셰이크를 합쳐 **1-RTT** (재연결은 0-RTT 가능)
- **연결 마이그레이션**: IP가 바뀌어도(와이파이 → LTE) 연결 ID로 연결 유지
- TLS 1.3 암호화 내장

| 버전 | 전송 | 핵심 |
|---|---|---|
| 1.0 | TCP | 요청마다 연결 |
| 1.1 | TCP | Keep-Alive, 파이프라이닝 |
| 2 | TCP | 바이너리, 멀티플렉싱, 헤더 압축 |
| 3 | **UDP (QUIC)** | TCP HOL 해결, 빠른 연결, 연결 이동 |

## 6. HTTP 캐시

같은 리소스를 매번 다운로드하지 않도록 브라우저(또는 프록시, CDN)에 저장합니다.

### Cache-Control
| 값 | 의미 |
|---|---|
| `max-age=3600` | 3600초 동안 캐시를 그대로 사용 (서버에 묻지 않음) |
| `no-cache` | 캐시는 저장하되, **쓰기 전에 매번 서버에 검증** |
| `no-store` | **저장하지 마** (민감 정보) |
| `public` / `private` | 공유 캐시(CDN, 프록시)에 저장 가능 / 브라우저만 |
| `must-revalidate` | 만료되면 반드시 검증 |

> `no-cache`는 "캐시하지 마"가 아니라 "**검증하고 써**"라는 뜻입니다. 캐시를 아예 막으려면 `no-store`.

### 검증 (조건부 요청)
캐시가 만료됐을 때, 리소스가 바뀌었는지만 확인합니다. 안 바뀌었으면 **304 Not Modified**(바디 없음)로 응답해 전송량을 아낍니다.

```
1차 응답:  ETag: "abc123"     /  Last-Modified: Mon, 09 Nov 2026 10:00:00 GMT
재요청:    If-None-Match: "abc123"  / If-Modified-Since: Mon, 09 Nov 2026 10:00:00 GMT
           → 같으면 304, 다르면 200 + 새 데이터
```

- **ETag**: 리소스 내용의 해시 같은 고유 값 → 더 정확
- **Last-Modified**: 수정 시각 → 초 단위라 부정확할 수 있음

### CDN (Content Delivery Network)
전 세계에 분산된 캐시 서버에 정적 리소스(이미지, JS, CSS, 동영상)를 저장해 **사용자와 가까운 서버**에서 응답 → 지연 감소, 원 서버 부하 감소 (CloudFront, Cloudflare)

## 7. 면접 질문

1. **HTTP가 무상태인 이유와 장단점은?**
   → 서버가 클라이언트 상태를 저장하지 않아 어떤 서버든 요청을 처리할 수 있어 확장성이 좋지만, 매 요청에 인증 정보 등을 실어야 해서 쿠키·세션·토큰으로 보완합니다.
2. **멱등성이란? 어떤 메서드가 멱등인가요?**
   → 같은 요청을 여러 번 보내도 서버 상태가 같은 성질로, GET·PUT·DELETE·HEAD·OPTIONS는 멱등이고 POST는 멱등이 아닙니다.
3. **401과 403의 차이는?**
   → 401은 인증이 안 된 상태, 403은 인증은 됐지만 권한이 없는 상태입니다.
4. **HTTP/1.1, 2, 3의 차이는?**
   → 1.1은 Keep-Alive로 연결을 재사용하지만 HOL 블로킹이 있고, 2는 하나의 TCP 연결에서 멀티플렉싱·헤더 압축을 지원하며, 3은 UDP 기반 QUIC으로 TCP 레벨 HOL 블로킹을 해결하고 연결 수립을 빠르게 했습니다.
5. **PUT과 PATCH의 차이는?**
   → PUT은 리소스 전체를 대체하고, PATCH는 일부만 수정합니다.

## 핵심 정리
- HTTP = 무상태 + 클라이언트-서버, 요청/응답 메시지 = 시작 줄 + 헤더 + 빈 줄 + 바디
- 멱등: GET, PUT, DELETE (O) / POST (X)
- 2xx 성공, 3xx 리다이렉트, 4xx 클라이언트(401 인증, 403 인가), 5xx 서버
- 1.1 Keep-Alive → 2 멀티플렉싱 → 3 QUIC(UDP)
- 캐시: max-age / no-cache(검증) / no-store(저장 X), ETag + 304
