# 06. HTTPS와 TLS

> **학습 목표**
> - HTTP의 보안 문제와 HTTPS가 이를 해결하는 방법을 설명할 수 있다.
> - 대칭키와 비대칭키 암호화의 차이와, HTTPS가 둘을 함께 쓰는 이유를 설명할 수 있다.
> - 인증서와 CA의 역할, 인증서 검증 과정을 설명할 수 있다.
> - TLS 핸드셰이크 과정을 순서대로 설명할 수 있다.

---

## 1. HTTP의 보안 문제

HTTP는 데이터를 **평문(암호화 X)** 으로 보냅니다.

| 위협 | 설명 | 해결 |
|---|---|---|
| **도청** | 중간에서 패킷을 보면 비밀번호가 그대로 보임 | **암호화** |
| **변조** | 중간에서 내용을 바꿔치기 (광고 삽입 등) | **무결성 검증** (MAC) |
| **위장** | 가짜 서버가 진짜인 척 | **인증** (인증서) |

**HTTPS = HTTP + TLS (Transport Layer Security)**. TLS는 SSL의 후속 버전입니다. (SSL은 취약해서 더 이상 쓰지 않지만 관습적으로 "SSL 인증서"라고 부릅니다.)

```
HTTP        HTTPS
[HTTP]      [HTTP]
            [TLS ]   ← 암호화·인증·무결성
[TCP ]      [TCP ]
[IP  ]      [IP  ]
```
- 기본 포트: HTTP 80, **HTTPS 443**

## 2. 암호화 기초

### 대칭키 암호화
**암호화와 복호화에 같은 키**를 씁니다.
```
평문 ──[키 K로 암호화]──> 암호문 ──[키 K로 복호화]──> 평문
```
- 예: **AES**, ChaCha20
- 장점: **빠름**
- 단점: **키를 상대에게 안전하게 전달하기 어려움** (키 배송 문제). 키를 평문으로 보내면 도청당함

### 비대칭키(공개키) 암호화
**공개키와 개인키 한 쌍**을 씁니다. 한 키로 암호화하면 **다른 키로만** 복호화됩니다.
```
공개키(Public Key): 누구에게나 공개
개인키(Private Key): 본인만 보관

1) 기밀성: 공개키로 암호화 → 개인키를 가진 사람만 복호화
2) 전자 서명: 개인키로 서명 → 공개키로 검증 → "이 사람이 보낸 게 맞다"
```
- 예: **RSA**, **ECC (ECDHE, ECDSA)**
- 장점: 키 배송 문제 해결
- 단점: 대칭키보다 **수백~수천 배 느림**

### HTTPS의 해결책: 둘을 섞는다
1. **비대칭키(또는 키 교환 알고리즘)** 로 **대칭키(세션 키)를 안전하게 공유**
2. 실제 데이터는 빠른 **대칭키**로 암호화

### 해시와 MAC
- **해시 함수** (SHA-256): 임의 데이터를 고정 길이 값으로. 원본을 복원할 수 없고, 조금만 바뀌어도 값이 완전히 달라짐
- **MAC** (HMAC): 해시 + 비밀키 → 메시지가 **변조되지 않았음**을 검증
- TLS 1.2 이후에는 암호화와 무결성 검증을 한 번에 하는 **AEAD**(AES-GCM 등)를 주로 씁니다.

> 비밀번호 저장은 암호화가 아니라 **해시(+ 솔트, bcrypt/Argon2)** 로 합니다. 복호화할 필요가 없고, 해서도 안 되기 때문입니다.

## 3. 인증서와 CA

### 왜 필요한가?
공개키를 받았는데, **그게 진짜 그 서버의 공개키인지** 어떻게 알까요? 공격자가 중간에서 자기 공개키를 주면(중간자 공격, MITM) 모든 통신이 공격자에게 노출됩니다.

### 인증서 (Certificate)
**"이 공개키는 example.com의 것이 맞다"** 라고 **신뢰할 수 있는 기관(CA)** 이 서명해 준 문서입니다.

```
인증서 (X.509)
+---------------------------------------+
| 도메인: www.example.com                 |
| 서버의 공개키                            |
| 발급자(CA): Let's Encrypt               |
| 유효 기간                               |
| CA의 전자 서명 (CA 개인키로 서명한 값)     |
+---------------------------------------+
```

### CA (Certificate Authority)
- 인증서를 발급하는 **신뢰할 수 있는 기관** (DigiCert, Let's Encrypt, Sectigo ...)
- **브라우저와 OS에는 신뢰하는 루트 CA의 공개키가 미리 내장**되어 있습니다.

### 인증서 체인과 검증
```
[루트 CA 인증서]         ← 브라우저/OS에 내장, 스스로 서명
      ↓ 서명
[중간 CA 인증서]
      ↓ 서명
[서버 인증서 (example.com)]
```

브라우저의 검증:
1. 서버 인증서의 서명을 **중간 CA 공개키로 검증**
2. 중간 CA 인증서의 서명을 **루트 CA 공개키로 검증** (루트는 내장되어 있으니 신뢰)
3. 도메인이 일치하는지, 유효 기간이 지나지 않았는지, 폐기(revoked)되지 않았는지 확인
4. 하나라도 실패하면 "**안전하지 않은 연결**" 경고

## 4. TLS 핸드셰이크

### TLS 1.2 (RSA 키 교환 기준, 개념 이해용)
```
클라이언트                                         서버
   │ ── 1. Client Hello ─────────────────────────> │
   │    (지원 TLS 버전, 암호 스위트 목록, 클라이언트 랜덤)│
   │                                               │
   │ <── 2. Server Hello ───────────────────────── │
   │    (선택한 암호 스위트, 서버 랜덤)                 │
   │ <── 3. Certificate (서버 인증서) ─────────────── │
   │ <── Server Hello Done ─────────────────────── │
   │                                               │
   │  4. 인증서 검증 (CA 공개키로)                     │
   │  5. Pre-Master Secret 생성                     │
   │ ── 6. Client Key Exchange ──────────────────> │
   │    (Pre-Master Secret을 서버 공개키로 암호화)      │
   │                                  서버 개인키로 복호화
   │                                               │
   │  7. 양쪽이 클라이언트 랜덤 + 서버 랜덤 + Pre-Master로 │
   │     같은 세션 키(대칭키) 생성                       │
   │                                               │
   │ ── 8. Change Cipher Spec, Finished ─────────> │
   │ <── Change Cipher Spec, Finished ──────────── │
   │                                               │
   │ ====== 이후 세션 키(대칭키)로 암호화 통신 ====== │
```
→ **2-RTT** 소요

> RSA 키 교환은 서버 개인키가 나중에 유출되면 **과거에 녹화된 통신까지 모두 복호화**됩니다. 그래서 현재는 매번 임시 키를 만드는 **ECDHE 키 교환**을 써서 **전방 비밀성(Forward Secrecy)** 을 보장합니다. 이 방식에서 서버 인증서의 개인키는 키 교환 값에 **서명**해 서버가 진짜임을 증명하는 데 쓰입니다.

### TLS 1.3 (2018, 현재 표준)
- **1-RTT**로 단축: Client Hello에 키 교환 값(키 쉐어)을 미리 같이 보냄
- 재접속 시 **0-RTT** 가능 (재전송 공격 위험이 있어 제한적으로 사용)
- RSA 키 교환, 취약한 암호(RC4, SHA-1 등) **제거**, ECDHE만 허용 → 전방 비밀성 필수
- 인증서도 암호화되어 전송

| 항목 | TLS 1.2 | TLS 1.3 |
|---|---|---|
| 핸드셰이크 | 2-RTT | **1-RTT** (재연결 0-RTT) |
| 키 교환 | RSA, DHE, ECDHE | **(EC)DHE만** |
| 전방 비밀성 | 선택 | **필수** |

## 5. HTTPS 관련 실무

| 개념 | 설명 |
|---|---|
| **SSL 종료 (TLS Termination)** | 로드밸런서(AWS ALB)나 Nginx에서 HTTPS를 풀고, 내부 서버와는 HTTP로 통신 → 앱 서버 부담 감소 |
| **HSTS** | `Strict-Transport-Security` 헤더로 "앞으로 이 사이트는 무조건 HTTPS로만 접속해" 지시 → SSL 스트리핑 공격 방지 |
| **Let's Encrypt** | 무료 인증서, 90일마다 자동 갱신 (certbot) |
| **SNI** | 하나의 IP에서 여러 도메인 인증서를 쓰기 위해 Client Hello에 도메인 이름을 포함 |
| AWS ACM | AWS에서 무료로 인증서 발급·자동 갱신 (ALB, CloudFront에 연결) |

## 6. 면접 질문

1. **HTTPS는 어떻게 동작하나요?**
   → TLS 핸드셰이크에서 서버 인증서를 CA 공개키로 검증해 서버를 인증하고, 비대칭키 방식의 키 교환으로 대칭 세션 키를 안전하게 공유한 뒤, 이후 데이터는 세션 키로 암호화해 통신합니다.
2. **대칭키와 비대칭키를 함께 쓰는 이유는?**
   → 비대칭키는 키 배송 문제를 해결하지만 느리고, 대칭키는 빠르지만 키 공유가 어렵기 때문에 비대칭키로 대칭키를 공유하고 데이터는 대칭키로 암호화합니다.
3. **인증서는 왜 필요한가요?**
   → 받은 공개키가 정말 해당 서버의 것인지 신뢰할 수 있는 CA의 서명으로 보증해 중간자 공격을 막기 위해서입니다.
4. **TLS 1.3이 1.2보다 빠른 이유는?**
   → Client Hello에서 키 교환 정보를 미리 보내 핸드셰이크를 1-RTT로 줄였기 때문입니다.

---

## 핵심 정리
- HTTPS = HTTP + TLS → 암호화(도청) + 무결성(변조) + 인증(위장)
- 비대칭키로 대칭 세션 키 공유 → 데이터는 대칭키로
- 인증서 = CA가 서명한 "이 공개키는 이 도메인 것", 체인으로 루트 CA까지 검증
- TLS 1.2: 2-RTT / TLS 1.3: 1-RTT, ECDHE 전방 비밀성 필수
