# Part 1. DNS (Domain Name System)

## 1. 개념

사람은 `www.google.com` 같은 **도메인 이름**을 기억하지만, 컴퓨터는 **IP 주소**로 통신합니다. DNS는 **도메인 이름을 IP 주소로 바꿔 주는 분산 데이터베이스 시스템**입니다. "인터넷의 전화번호부"

- 주로 **UDP 53번 포트** (응답이 크거나 영역 전송 시 TCP 53)

---

## 2. 도메인 계층 구조

```
                      . (루트)
          ┌───────────┼───────────┐
         com          kr          org       ← TLD (최상위 도메인)
          │           │
        google        co                    ← 2차 도메인
          │           │
         www        naver                   ← 서브 도메인
```

`www.google.com.` 은 오른쪽에서 왼쪽으로 읽습니다: 루트(.) → com → google → www

| 서버 | 역할 |
|---|---|
| **루트 DNS 서버** | TLD 서버의 주소를 알려 줌 (전 세계 13개 이름의 루트 서버, 실제로는 애니캐스트로 수백 대) |
| **TLD DNS 서버** | `.com`, `.kr` 등을 담당, 해당 도메인의 권한 있는 서버 주소를 알려 줌 |
| **권한 있는(Authoritative) DNS 서버** | 실제 도메인의 IP 정보를 가진 서버 (AWS Route 53, 가비아 DNS) |
| **로컬 DNS 서버 (Recursive Resolver)** | 사용자의 질의를 대신 처리해 주는 서버 (통신사 DNS, 8.8.8.8, 1.1.1.1) |

---

## 3. DNS 질의 과정

```
[브라우저] www.example.com의 IP는?

1. 브라우저 캐시 확인
2. OS 캐시 확인 (+ hosts 파일)
3. 로컬 DNS 서버(리졸버)에 질의 ─────────────────┐
                                              │ (재귀적 질의: "답을 찾아서 알려 줘")
   로컬 DNS 서버 ──→ 루트 서버: "www.example.com?" │
                  ←── ".com은 TLD 서버 a.gtld... 에 물어봐"
   로컬 DNS 서버 ──→ .com TLD 서버
                  ←── "example.com은 ns1.example.com에 물어봐"
   로컬 DNS 서버 ──→ example.com 권한 있는 서버
                  ←── "93.184.216.34 (TTL 3600)"
                                              │ (반복적 질의: 로컬 DNS가 차례로 물어봄)
4. 로컬 DNS 서버가 결과를 캐싱하고 브라우저에 응답 ←─┘
5. 브라우저도 캐싱
```

| 질의 방식 | 설명 |
|---|---|
| **재귀적 질의** (Recursive) | 클라이언트 → 로컬 DNS: "**최종 답을 줘**" |
| **반복적 질의** (Iterative) | 로컬 DNS → 루트/TLD/권한 서버: 각 서버는 "**다음에 물어볼 곳**"만 알려 줌 |

### DNS 캐싱과 TTL
- 모든 단계에서 결과를 **TTL(Time To Live) 동안 캐싱** → 대부분의 질의는 캐시에서 끝남
- TTL이 길면 빠르지만, IP를 바꿨을 때 **전파가 늦어짐**
- 서버 이전 전에는 TTL을 미리 짧게 줄여 두는 것이 실무 팁

## 4. DNS 레코드 타입

| 타입 | 의미 | 예 |
|---|---|---|
| **A** | 도메인 → **IPv4** | `example.com → 93.184.216.34` |
| **AAAA** | 도메인 → **IPv6** | `example.com → 2606:2800:...` |
| **CNAME** | 도메인 → **다른 도메인** (별칭) | `www.example.com → example.com` |
| **MX** | 메일 서버 | `example.com → mail.example.com` (우선순위 포함) |
| **NS** | 이 도메인을 담당하는 네임 서버 | `example.com → ns1.example.com` |
| **TXT** | 텍스트 정보 | 도메인 소유 인증, SPF(메일 발신 서버 지정) |
| SOA | 영역의 관리 정보 | |
| PTR | **IP → 도메인** (역방향 조회) | |

> CNAME은 루트 도메인(`example.com` 자체)에는 쓸 수 없습니다(다른 레코드와 공존 불가). 그래서 AWS Route 53은 **Alias 레코드**를 제공해 루트 도메인을 ALB, CloudFront에 연결합니다.

```bash
nslookup google.com
dig google.com A          # 상세 조회
dig +trace google.com     # 루트부터 질의 과정 추적
```

### DNS 활용
- **DNS 기반 로드 밸런싱**: 하나의 도메인에 여러 A 레코드 → 라운드 로빈
- **GeoDNS**: 사용자 위치에 따라 가까운 서버 IP 응답 (CDN)

# Part 2. 브라우저에 URL을 입력하면 일어나는 일

> 면접 단골 질문입니다. **계층별로, 순서대로** 설명할 수 있어야 합니다.

`https://www.example.com/products?id=1` 입력

## 1. URL 파싱
```
https://   www.example.com   :443   /products   ?id=1
 스킴           호스트           포트     경로        쿼리
```
- 스킴이 https면 기본 포트 443
- HSTS 목록에 있으면 http로 입력해도 https로 변경

## 2. DNS 조회 (응용 계층)
브라우저 캐시 → OS 캐시(hosts) → 로컬 DNS 서버 → (루트 → TLD → 권한 서버) → **IP 획득**

## 3. TCP 연결 (전송 계층)
서버 IP:443으로 **3-way handshake** (SYN → SYN+ACK → ACK)

이 과정에서 패킷이 실제로 이동하려면:
- **네트워크 계층**: 목적지 IP가 다른 네트워크 → **기본 게이트웨이(라우터)** 로 보내야 함 → 라우터들이 라우팅 테이블을 보고 목적지까지 전달
- **데이터링크 계층**: 게이트웨이의 MAC 주소를 **ARP**로 알아내 프레임 전송
- 공유기에서 **NAT**로 사설 IP → 공인 IP 변환

## 4. TLS 핸드셰이크
- Client Hello → Server Hello + 인증서
- 브라우저가 **인증서를 CA로 검증**
- 키 교환 → **세션 키(대칭키)** 생성
- (HTTP/3라면 3, 4 단계를 QUIC이 UDP 위에서 한 번에 처리)

## 5. HTTP 요청 전송
```
GET /products?id=1 HTTP/1.1
Host: www.example.com
Cookie: SESSION=abc...
```

## 6. 서버 처리
```
[로드밸런서 (AWS ALB, L7)]   ← TLS 종료, 헬스 체크된 서버로 분산
        ↓
[웹 서버 (Nginx)]           ← 정적 파일 응답, 리버스 프록시
        ↓
[WAS (Spring Boot / Tomcat)] ← 스레드 풀의 스레드가 요청 처리
   DispatcherServlet → Controller → Service → Repository
        ↓                                   ↓
   [Redis 캐시]                          [DB (MySQL)]
```

## 7. HTTP 응답
```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Cache-Control: max-age=60
```

## 8. 브라우저 렌더링
```
HTML 파싱 → DOM 트리
CSS 파싱  → CSSOM 트리
          ↓ 결합
       렌더 트리 → 레이아웃(위치·크기 계산) → 페인트(픽셀 그리기) → 합성(Composite)
```
- HTML 중간에 `<script>`를 만나면 파싱이 멈춤 → `defer`, `async`로 해결
- 이미지, CSS, JS 등 추가 리소스를 다시 요청 (HTTP/2면 같은 연결로 멀티플렉싱)

## 9. 연결 유지 / 종료
- Keep-Alive로 연결을 재사용하다가, 일정 시간 지나면 **4-way handshake**로 종료

## 한눈에 보기
```
URL 입력
 → DNS 조회 (도메인 → IP)
 → TCP 3-way handshake
   (아래에서는 라우팅, ARP, NAT가 동작)
 → TLS 핸드셰이크 (인증서 검증, 세션 키)
 → HTTP 요청
 → 로드밸런서 → 웹 서버 → WAS → DB
 → HTTP 응답
 → 브라우저 렌더링 (DOM + CSSOM → 렌더 트리 → 레이아웃 → 페인트)
```

## 면접 질문

1. **DNS 동작 과정을 설명해 주세요.**
   → 브라우저·OS 캐시를 확인하고 없으면 로컬 DNS 서버에 재귀 질의합니다. 로컬 DNS 서버는 루트, TLD, 권한 있는 DNS 서버에 차례로 반복 질의해 IP를 얻고 TTL 동안 캐싱한 뒤 응답합니다.
2. **A 레코드와 CNAME의 차이는?**
   → A는 도메인을 IP 주소에, CNAME은 도메인을 다른 도메인에 연결합니다.
3. **www.google.com을 입력하면 어떤 일이 일어나나요?**
   → URL 파싱 → DNS로 IP 조회 → TCP 3-way handshake → TLS 핸드셰이크 → HTTP 요청 → 서버 처리 → 응답 → 브라우저 렌더링 순서이며, 패킷 전송 과정에서 라우팅·ARP·NAT가 동작합니다.

---

## 핵심 정리
- DNS: 도메인 → IP, 계층 구조(루트 → TLD → 권한 서버), 재귀(클라이언트) + 반복(리졸버)
- 레코드: A(IPv4), AAAA(IPv6), CNAME(별칭), MX(메일), NS
- URL 입력 → DNS → TCP → TLS → HTTP → 서버 → 응답 → 렌더링
