## 1. 인증(Authentication) vs 인가(Authorization)

| 구분 | 질문 | 예 | 실패 시 |
|---|---|---|---|
| **인증** | **누구인가?** | 로그인 | 401 |
| **인가** | **무엇을 할 수 있는가?** | 관리자만 삭제 가능 | 403 |

HTTP는 무상태라서 "로그인한 사용자"를 기억하지 못합니다. 그래서 아래 방법들을 씁니다.

## 2. 쿠키 (Cookie)

**서버가 브라우저에 저장하게 하는 작은 데이터(약 4KB)** 입니다. 브라우저는 같은 도메인으로 요청할 때 **자동으로 쿠키를 함께 보냅니다.**

```
응답: Set-Cookie: theme=dark; Max-Age=3600; Path=/; HttpOnly; Secure; SameSite=Lax
요청: Cookie: theme=dark
```

| 속성 | 의미 |
|---|---|
| `Expires` / `Max-Age` | 만료 시점. 없으면 **세션 쿠키** (브라우저 닫으면 삭제) |
| `Domain`, `Path` | 쿠키를 보낼 범위 |
| **`HttpOnly`** | **JavaScript에서 접근 불가** (`document.cookie` X) → **XSS로 탈취 방지** |
| **`Secure`** | **HTTPS에서만** 전송 |
| **`SameSite`** | 다른 사이트에서 시작된 요청에 쿠키를 보낼지 → **CSRF 방지** |

| SameSite 값 | 동작 |
|---|---|
| `Strict` | 다른 사이트에서 오는 요청에는 절대 안 보냄 |
| `Lax` (크롬 기본) | 다른 사이트에서 오는 **링크 이동(GET)** 에만 보냄 |
| `None` | 항상 보냄 (`Secure` 필수) |

- 단점: 사용자가 **조작 가능**, 용량 작음 → **민감 정보를 직접 저장하면 안 됨**

## 3. 세션 (Session)

**사용자 정보는 서버에 저장하고, 브라우저에는 그 정보를 찾을 수 있는 세션 ID만** 쿠키로 줍니다.

```
1. 로그인 요청 (아이디/비밀번호)
2. 서버: 세션 저장소에 {sessionId: "abc123" → userId: 42, role: USER} 저장
3. 응답: Set-Cookie: JSESSIONID=abc123; HttpOnly
4. 이후 요청: Cookie: JSESSIONID=abc123
5. 서버: 세션 저장소에서 abc123 조회 → 사용자 42
```

| 장점 | 단점 |
|---|---|
| 민감 정보가 서버에만 있어 안전 | 서버가 상태를 가짐 → **메모리 사용**, 요청마다 조회 |
| **서버에서 강제 로그아웃(세션 삭제)** 이 쉬움 | **서버를 여러 대로 늘리면 세션 공유 문제** |

### 서버 확장 시 세션 공유
| 방법 | 설명 |
|---|---|
| 스티키 세션 | 로드밸런서가 같은 사용자를 **항상 같은 서버로** → 그 서버가 죽으면 세션 유실, 부하 불균형 |
| 세션 클러스터링 | 서버끼리 세션 복제 → 서버가 많아지면 비용 큼 |
| **외부 세션 저장소** | **Redis**에 세션 저장 (Spring Session) → 가장 일반적 |

## 4. 토큰 기반 인증: JWT (JSON Web Token)

**사용자 정보를 담고 서명한 토큰**을 클라이언트가 보관하고, 요청마다 보냅니다. 서버는 **서명만 검증**하면 되므로 저장소 조회가 필요 없습니다(무상태).

### 구조
```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIiwiZXhwIjoxNzYyNjc4MDAwfQ . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
      Header                          Payload                                         Signature
```

| 부분 | 내용 |
|---|---|
| **Header** | 알고리즘(`HS256`, `RS256`), 타입 |
| **Payload** | **클레임**: `sub`(사용자 ID), `exp`(만료), `iat`(발급 시각), `role` 등 |
| **Signature** | `HMACSHA256(base64(header) + "." + base64(payload), 비밀키)` |

> **Payload는 암호화가 아니라 Base64 인코딩일 뿐**입니다. 누구나 디코딩해서 볼 수 있으므로 **비밀번호 같은 민감 정보를 넣으면 안 됩니다.** 서명은 **변조 여부**만 검증합니다.

```
요청: Authorization: Bearer eyJhbGciOi...
```

### 장단점
| 장점 | 단점 |
|---|---|
| **서버가 상태를 저장하지 않음** → 수평 확장 쉬움 | **발급 후 강제 무효화가 어려움** (탈취되면 만료까지 유효) |
| MSA에서 각 서비스가 독립적으로 검증 가능 | 토큰이 커서 매 요청 트래픽 증가 |
| 모바일 등 쿠키가 불편한 환경에 적합 | Payload 노출 |

### Access Token + Refresh Token
| 토큰 | 수명 | 용도 |
|---|---|---|
| **Access Token** | **짧게** (15분~1시간) | API 요청 인증 |
| **Refresh Token** | **길게** (2주) | Access Token 재발급. 서버(Redis/DB)에 저장해 **무효화 가능**하게 관리 |

```
1. 로그인 → Access + Refresh 발급
2. API 요청 (Access)
3. Access 만료 → 401
4. Refresh로 재발급 요청 → 서버가 저장된 Refresh와 비교 → 새 Access (+ Refresh Rotation)
5. 로그아웃 → 서버에서 Refresh 삭제, Access는 블랙리스트(Redis)에 남은 만료 시간만큼 등록
```

### 토큰 저장 위치
| 위치 | XSS | CSRF |
|---|---|---|
| localStorage | **취약** (JS로 읽힘) | 안전 (자동 전송 X) |
| HttpOnly 쿠키 | 안전 | **취약** → SameSite, CSRF 토큰으로 방어 |

> 일반적으로 **Refresh Token은 HttpOnly + Secure + SameSite 쿠키**, Access Token은 메모리(변수)에 두는 방식이 권장됩니다.

### 세션 vs JWT
| 항목 | 세션 | JWT |
|---|---|---|
| 상태 저장 | 서버 (Stateful) | 클라이언트 (Stateless) |
| 확장성 | 세션 공유 필요 | 쉬움 |
| 강제 로그아웃 | 쉬움 | 어려움 (블랙리스트 필요) |
| 보안 | 세션 ID만 노출 | Payload 노출, 탈취 시 위험 |
| 적합 | 전통적인 웹, 단일 서버 | MSA, 모바일, 여러 서비스 |

## 5. OAuth 2.0

**사용자 비밀번호를 주지 않고, 제3자 서비스(구글, 카카오)의 권한을 위임받는** 프레임워크입니다. "카카오로 로그인"

| 역할 | 예 |
|---|---|
| Resource Owner | 사용자 |
| Client | 우리 서비스 |
| Authorization Server | 카카오 인증 서버 |
| Resource Server | 카카오 API 서버 (프로필 정보) |

### Authorization Code Grant (가장 일반적)
```
1. 사용자: "카카오로 로그인" 클릭
2. 우리 서비스 → 카카오 로그인 페이지로 리다이렉트 (client_id, redirect_uri, scope)
3. 사용자가 카카오에 로그인하고 정보 제공 동의
4. 카카오 → redirect_uri로 리다이렉트 + **Authorization Code** (짧은 수명)
5. 우리 서버 → 카카오: Code + client_secret 으로 **Access Token 요청** (서버 대 서버)
6. 카카오 → Access Token 발급
7. 우리 서버 → 카카오 API: Access Token으로 사용자 정보 조회
8. 우리 서비스의 회원으로 가입/로그인 처리 (자체 세션 or JWT 발급)
```
- Code를 거치는 이유: **Access Token이 브라우저(URL)에 노출되지 않게** 서버끼리 교환하기 위해
- 모바일·SPA는 **PKCE**를 추가로 사용
- 로그인(인증) 정보 표준화는 OAuth 위의 **OpenID Connect(OIDC)** 가 담당 (ID Token)

## 6. 웹 보안: XSS와 CSRF

| 공격 | 방법 | 방어 |
|---|---|---|
| **XSS** (Cross-Site Scripting) | 게시글 등에 **악성 스크립트를 심어** 다른 사용자 브라우저에서 실행 → 쿠키·토큰 탈취 | 입력값 **이스케이프**(`<` → `&lt;`), HttpOnly, CSP 헤더 |
| **CSRF** (Cross-Site Request Forgery) | 로그인된 사용자가 악성 사이트를 방문하면, **사용자 모르게 다른 사이트로 요청**(쿠키 자동 전송 악용) | **CSRF 토큰**, SameSite 쿠키, Referer 검증 |

## 7. REST (Representational State Transfer)

**자원(Resource)을 URI로 표현하고, 행위는 HTTP 메서드로 표현**하는 아키텍처 스타일입니다.

### REST 원칙 (제약 조건)
| 원칙 | 의미 |
|---|---|
| 클라이언트-서버 | 역할 분리 |
| **무상태** | 서버가 클라이언트 상태를 저장 X |
| 캐시 가능 | 응답에 캐시 가능 여부 명시 |
| **균일한 인터페이스** | 자원 식별(URI), 표현으로 조작, 자기 서술적 메시지, HATEOAS |
| 계층화 | 중간에 프록시, 로드밸런서가 있어도 됨 |
| (선택) Code on Demand | 서버가 코드(JS)를 내려줄 수 있음 |

### 좋은 REST API 설계
```
나쁨                              좋음
GET  /getMembers                  GET    /members
POST /createMember                POST   /members
GET  /member/delete?id=1          DELETE /members/1
GET  /members/1/getOrders         GET    /members/1/orders
```

| 규칙 | 예 |
|---|---|
| URI는 **명사(자원)**, 행위는 메서드 | `/members` (O), `/getMembers` (X) |
| 컬렉션은 **복수형** | `/members`, `/orders` |
| 계층 관계는 `/` | `/members/1/orders` |
| 소문자, 하이픈(`-`) 사용, 밑줄 X | `/order-items` |
| 파일 확장자 X | `/members/1.json` (X) → `Accept` 헤더 |
| 필터·정렬·페이징은 **쿼리 스트링** | `/members?role=admin&sort=name&page=2` |
| 적절한 **상태 코드** | 생성 201, 삭제 204, 없음 404 |

> 실제 API 대부분은 HATEOAS까지 지키지 않아 엄밀히는 "REST**ful**"한 HTTP API입니다.

## 8. SOP와 CORS

### SOP (Same-Origin Policy, 동일 출처 정책)
브라우저는 **다른 출처(Origin)의 리소스를 JavaScript로 읽는 것을 기본적으로 막습니다.** (악성 사이트가 내 은행 사이트 응답을 읽지 못하게)

**출처(Origin) = 스킴 + 호스트 + 포트**
```
https://example.com:443/a 와 비교
https://example.com/b          → 같은 출처 (경로는 무관)
http://example.com             → 다름 (스킴)
https://api.example.com        → 다름 (호스트)
https://example.com:8080       → 다름 (포트)
```

> 프론트 `http://localhost:3000`에서 백엔드 `http://localhost:8080`을 호출하면 **포트가 달라서** 다른 출처입니다. 그래서 개발 중 CORS 에러를 자주 만납니다.

### CORS (Cross-Origin Resource Sharing)
서버가 **"이 출처는 내 리소스를 읽어도 돼"** 라고 응답 헤더로 허용하는 방식입니다.

```
요청: Origin: http://localhost:3000
응답: Access-Control-Allow-Origin: http://localhost:3000
```

> **CORS 에러는 브라우저가 막는 것**입니다. 요청은 서버까지 도착하고 서버는 응답했지만, 허용 헤더가 없어서 **브라우저가 JS에 응답을 넘겨주지 않는** 것입니다. Postman이나 서버 간 통신에서는 CORS가 없습니다.

### Preflight 요청
단순 요청(GET/HEAD/POST + 기본 헤더 + 특정 Content-Type)이 아니면, 브라우저가 본 요청 전에 **OPTIONS 메서드로 허용 여부를 먼저 확인**합니다.
```
OPTIONS /api/members
Origin: http://localhost:3000
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

응답:
Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 3600            ← preflight 결과 캐싱
```
- `Content-Type: application/json`이나 `Authorization` 헤더를 쓰면 preflight가 발생합니다.
- 쿠키를 함께 보내려면 `Access-Control-Allow-Credentials: true`, 이때 `Allow-Origin`에 `*`를 쓸 수 없음

```java
// Spring
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:3000")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "PATCH")
                .allowCredentials(true);
    }
}
```

## 9. 실시간 통신: 폴링, SSE, WebSocket

| 방식 | 동작 | 장점 | 단점 | 사용 예 |
|---|---|---|---|---|
| **폴링** | 클라이언트가 **주기적으로** 요청 | 구현 쉬움 | 변경 없어도 계속 요청 → 낭비, 지연 | 간단한 상태 확인 |
| **롱 폴링** | 요청을 보내면 서버가 **새 데이터가 생길 때까지 응답을 보류** | 폴링보다 효율적 | 연결 유지 비용 | 과거 채팅 |
| **SSE** (Server-Sent Events) | HTTP 연결을 유지하며 **서버 → 클라이언트 단방향** 스트림 | HTTP 그대로 사용, 자동 재연결 | 단방향, 텍스트만 | 알림, 주식 시세, **LLM 답변 스트리밍** |
| **WebSocket** | HTTP로 시작해 **프로토콜 업그레이드** → **양방향** 지속 연결 | 실시간 양방향, 오버헤드 적음 | 상태 유지(스케일 아웃 시 메시지 브로커 필요) | 채팅, 게임, 협업 편집 |

### WebSocket 연결
```
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols     ← 이후 HTTP가 아닌 WebSocket 프레임으로 통신
Upgrade: websocket
```
- `ws://`, 보안은 `wss://`
- Spring에서는 STOMP + 메시지 브로커(Redis Pub/Sub, RabbitMQ)로 여러 서버 간 메시지 전달

## 10. 면접 질문

1. **쿠키와 세션의 차이는?**
   → 쿠키는 브라우저에 저장되어 요청마다 자동 전송되고, 세션은 서버에 사용자 정보를 저장하고 브라우저에는 세션 ID만 쿠키로 줍니다. 세션이 더 안전하지만 서버 자원을 씁니다.
2. **JWT의 장단점은?**
   → 서버가 상태를 저장하지 않아 확장이 쉽지만, 발급 후 무효화가 어렵고 Payload가 노출됩니다. 그래서 짧은 Access Token과 서버에서 관리하는 Refresh Token을 함께 씁니다.
3. **CORS란? 에러가 나면 어떻게 해결하나요?**
   → 다른 출처의 리소스 접근을 서버가 응답 헤더로 허용하는 방식입니다. 서버에서 Access-Control-Allow-Origin 등 허용 헤더를 설정해 해결합니다.
4. **REST API란?**
   → 자원을 URI로, 행위를 HTTP 메서드로, 결과를 상태 코드로 표현하는 무상태 API 설계 방식입니다.
5. **WebSocket과 SSE의 차이는?**
   → WebSocket은 양방향 지속 연결이고, SSE는 HTTP 기반 서버→클라이언트 단방향 스트림입니다.

## 핵심 정리
- 인증(401) vs 인가(403)
- 쿠키(브라우저 저장, HttpOnly·Secure·SameSite) / 세션(서버 저장, Redis 공유) / JWT(무상태, Access+Refresh)
- OAuth 2.0: Authorization Code → 서버가 Token 교환
- REST: 명사 URI + 메서드 + 상태 코드
- CORS: 출처 = 스킴+호스트+포트, 브라우저 정책, preflight = OPTIONS
- 실시간: 폴링 < 롱 폴링 < SSE(단방향) / WebSocket(양방향)
