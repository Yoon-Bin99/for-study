## 1. 컴퓨터의 구성: 폰 노이만 구조

**프로그램(명령어)과 데이터를 같은 메모리에 저장**하고, CPU가 메모리에서 명령어를 하나씩 가져와 실행하는 구조입니다. 현대 컴퓨터의 기본 구조입니다.

```
+-----------------------------+
|            CPU              |
|  +-------+   +-----------+  |
|  |  ALU  |   | 제어 장치    |  |
|  +-------+   +-----------+  |
|  |      레지스터           |  |
|  +-----------------------+  |
+--------------+--------------+
               │ 시스템 버스 (주소·데이터·제어 버스)
     +---------+---------+
     │                   │
+---------+        +-----------+
| 메모리    |        | 입출력 장치  |
| (명령어+  |        |           |
|  데이터)  |        +-----------+
+---------+
```

### 폰 노이만 병목 (Von Neumann Bottleneck)
CPU는 매우 빠른데 메모리는 상대적으로 느리고, 명령어와 데이터가 **같은 버스**를 쓰기 때문에 CPU가 메모리를 기다리는 병목이 생깁니다.
→ 해결: **캐시 메모리**, 파이프라인, **하버드 구조**(명령어와 데이터 메모리·버스를 분리, CPU 내부 L1 캐시에 적용)

## 2. CPU 구성 요소

| 구성 요소 | 역할 |
|---|---|
| **ALU** (산술논리연산장치) | 덧셈, 뺄셈, AND, OR, 비교 등 **실제 계산** |
| **제어 장치** (Control Unit) | 명령어를 **해석**하고 각 장치에 제어 신호를 보냄 |
| **레지스터** | CPU 내부의 **가장 빠른 임시 저장소** (수십 개, 각 64비트) |

### 주요 레지스터
| 레지스터 | 역할 |
|---|---|
| **PC** (Program Counter) | **다음에 실행할 명령어의 주소** |
| **IR** (Instruction Register) | **현재 실행 중인 명령어** |
| MAR (Memory Address Register) | 메모리에 접근할 주소 |
| MBR / MDR (Memory Buffer/Data Register) | 메모리에서 읽거나 쓸 데이터 |
| 범용 레지스터 | 연산에 쓰이는 데이터 |
| 플래그 레지스터 (상태 레지스터) | 연산 결과 상태 (0인지, 음수인지, 캐리, 오버플로) |
| **SP** (Stack Pointer) | 스택의 꼭대기 주소 |

> **컨텍스트 스위칭** 때 PCB에 저장하는 것이 바로 이 레지스터들(특히 PC)입니다. (→ `03.운영체제/02.프로세스와스레드.md`)

## 3. 명령어 사이클 (Instruction Cycle)

CPU는 다음 과정을 **무한히 반복**합니다.

```
   ┌──────────────────────────────────────┐
   ↓                                      │
[1. 인출 Fetch] → [2. 해독 Decode] → [3. 실행 Execute] → [4. 저장 Write-back]
                                                         │
                                         인터럽트 확인 ←─┘
```

| 단계 | 동작 |
|---|---|
| **1. 인출 (Fetch)** | PC가 가리키는 주소의 명령어를 메모리에서 가져와 IR에 저장, **PC 증가** |
| **2. 해독 (Decode)** | 제어 장치가 IR의 명령어를 해석 (어떤 연산? 피연산자는?) |
| **3. 실행 (Execute)** | ALU가 연산 수행, 또는 메모리 접근 |
| **4. 저장 (Write-back)** | 결과를 레지스터나 메모리에 저장 |
| (인터럽트 사이클) | 인터럽트가 있으면 현재 상태 저장 후 ISR로 이동 |

### 명령어 형식
```
| 연산 코드 (Opcode) | 피연산자 (Operand) |
   ADD                R1, R2, R3      → R1 = R2 + R3
   LOAD               R1, [1000]      → R1 = 메모리[1000]
   JUMP               2000            → PC = 2000
```

### 주소 지정 방식
| 방식 | 의미 | 예 |
|---|---|---|
| 즉시 (Immediate) | 피연산자가 **값 자체** | `ADD R1, #5` |
| 직접 (Direct) | 피연산자가 **메모리 주소** | `LOAD R1, [1000]` |
| 간접 (Indirect) | 피연산자가 가리키는 곳에 **실제 주소** | 포인터의 포인터 |
| 레지스터 | 피연산자가 레지스터 | `ADD R1, R2` |
| 레지스터 간접 | 레지스터에 담긴 값이 주소 | `LOAD R1, [R2]` |
| 상대 (Relative) | PC + 오프셋 | 분기 명령 |

## 4. CISC vs RISC

| 항목 | CISC (Complex Instruction Set) | RISC (Reduced Instruction Set) |
|---|---|---|
| 명령어 수 | **많고 복잡** | **적고 단순** |
| 명령어 길이 | 가변 | **고정** |
| 실행 시간 | 명령어마다 다름 (여러 클럭) | 대부분 **1클럭** |
| 메모리 접근 | 여러 명령어가 메모리 직접 접근 | **LOAD/STORE만** 메모리 접근 |
| 파이프라인 | 어려움 | **유리** |
| 코드 크기 | 작음 | 큼 (명령어 수가 많아짐) |
| 대표 | **x86** (Intel, AMD) | **ARM** (스마트폰, Apple M 시리즈, AWS Graviton), RISC-V |

> 현대 x86 CPU는 내부적으로 복잡한 명령어를 단순한 **마이크로 연산(μop)** 으로 쪼개 RISC처럼 실행합니다. 경계가 흐려졌지만, ARM은 **전력 효율**이 좋아 모바일·서버(Graviton)에서 점유율이 늘고 있습니다.

## 5. 클럭과 성능

- **클럭 속도 (Hz)**: CPU가 1초에 몇 번 박자를 치는가. 3GHz = 초당 30억 사이클
- **CPI** (Cycles Per Instruction): 명령어 하나에 평균 몇 사이클
- **IPC** (Instructions Per Cycle): 사이클당 명령어 수 (CPI의 역수)

```
CPU 실행 시간 = 명령어 수 × CPI × 클럭 주기
             = 명령어 수 × CPI / 클럭 속도
```

클럭만 높인다고 빨라지지 않는 이유: 발열, 전력 증가 (→ 클럭 경쟁 대신 **멀티코어**로 발전)

### 멀티코어와 하이퍼스레딩
| 개념 | 설명 |
|---|---|
| **코어 (Core)** | 명령어를 실행하는 독립적인 처리 유닛. 4코어 = CPU 안에 실행 장치 4개 |
| **하드웨어 스레드 (하이퍼스레딩, SMT)** | 코어 하나가 **두 개의 명령어 흐름**을 번갈아 처리 (레지스터 세트 2개). OS에는 논리 코어 2개로 보임 |
| 소프트웨어 스레드 | OS가 관리하는 실행 흐름 (Java Thread) |

## 6. 프로그램이 실행되기까지

```
[소스 코드] hello.c
     ↓ 전처리기 (#include, #define 처리)
[전처리된 코드]
     ↓ 컴파일러
[어셈블리어] hello.s
     ↓ 어셈블러
[목적 파일 (기계어)] hello.o
     ↓ 링커 (라이브러리, 다른 목적 파일 연결)
[실행 파일] hello (.exe)
     ↓ 로더 (메모리에 적재)
[프로세스 실행]
```

### 컴파일러 vs 인터프리터
| 방식 | 설명 | 예 |
|---|---|---|
| 컴파일 | 실행 전에 **전체를 기계어로 번역** → 실행 빠름 | C, C++, Go, Rust |
| 인터프리트 | 실행하면서 **한 줄씩 번역** → 시작 빠름, 실행 느림 | Python, JavaScript(초기) |
| **하이브리드 (JIT)** | 중간 코드로 컴파일 → 실행 중 자주 쓰는 코드를 기계어로 컴파일 | **Java**, C#, 현대 JS 엔진(V8) |

### Java의 실행 과정
```
Hello.java ──javac──> Hello.class (바이트코드, 플랫폼 독립)
                           ↓
                 [JVM] 클래스 로더 → 바이트코드 검증
                           ↓
                 인터프리터로 실행 + 자주 실행되는 코드(Hot Spot)는
                 JIT 컴파일러가 기계어로 컴파일해 캐싱
```
→ "Write Once, Run Anywhere": 바이트코드는 같고, OS별 JVM이 다름

## 7. 면접 질문

1. **폰 노이만 구조란? 병목은?**
   → 명령어와 데이터를 같은 메모리에 저장하고 CPU가 순차적으로 가져와 실행하는 구조입니다. CPU와 메모리 속도 차이와 공유 버스 때문에 병목이 생기며 캐시로 완화합니다.
2. **명령어 사이클을 설명해 주세요.**
   → PC가 가리키는 명령어를 인출해 IR에 저장하고 PC를 증가시킨 뒤, 제어 장치가 해독하고, ALU가 실행해 결과를 저장하며, 끝에 인터럽트를 확인합니다.
3. **CISC와 RISC의 차이는?**
   → CISC는 복잡하고 다양한 가변 길이 명령어를, RISC는 단순한 고정 길이 명령어로 파이프라인에 유리하고 전력 효율이 좋습니다.
4. **Java가 플랫폼 독립적인 이유는?**
   → 소스 코드를 OS와 무관한 바이트코드로 컴파일하고, 각 OS에 맞는 JVM이 이를 실행하기 때문입니다.

## 핵심 정리
- 폰 노이만 = 명령어·데이터 같은 메모리 → 병목 → 캐시
- CPU = ALU(계산) + 제어 장치(해석) + 레지스터(PC, IR, SP ...)
- 명령어 사이클: 인출 → 해독 → 실행 → 저장 (+ 인터럽트)
- CISC(x86) vs RISC(ARM)
- Java: 바이트코드 + JVM(인터프리터 + JIT)
