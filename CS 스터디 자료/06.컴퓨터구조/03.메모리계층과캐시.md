# 03. 메모리 계층과 캐시 (Memory Hierarchy & Cache)

> **학습 목표**

> - 캐시 매핑 방식(직접, 연관, 집합 연관)을 비교할 수 있다.

## 1. 메모리 계층 구조

```
              속도 빠름 / 용량 작음 / 비쌈
                      ▲
            ┌─────────────────┐
            │    레지스터       │  ~0.3ns    수백 B     CPU 내부
            ├─────────────────┤
            │   L1 캐시        │  ~1ns      수십 KB    코어마다
            ├─────────────────┤
            │   L2 캐시        │  ~4ns      수백 KB~MB 코어마다
            ├─────────────────┤
            │   L3 캐시        │  ~10~40ns  수십 MB    코어 공유
            ├─────────────────┤
            │ 메인 메모리 (DRAM)│  ~100ns    수십 GB
            ├─────────────────┤
            │   SSD           │  ~100μs    TB
            ├─────────────────┤
            │   HDD           │  ~10ms     TB
            └─────────────────┘
                      ▼
              속도 느림 / 용량 큼 / 쌈
```
(수치는 대략적인 크기 비교용입니다)

### 왜 계층을 나누는가?
빠른 메모리는 비싸고 작고, 큰 메모리는 느립니다. **자주 쓰는 데이터를 빠른 곳에** 두면, 비용은 낮추면서 **평균 속도를 빠른 메모리에 가깝게** 만들 수 있습니다.

### 휘발성
| 휘발성 (전원 끄면 사라짐) | 비휘발성 |
|---|---|
| 레지스터, 캐시(SRAM), 메인 메모리(DRAM) | SSD, HDD, ROM |

| 비교 | SRAM | DRAM |
|---|---|---|
| 용도 | **캐시** | **메인 메모리** |
| 구조 | 트랜지스터 여러 개 | 트랜지스터 + 커패시터 |
| 속도 | 빠름 | 느림 |
| 재충전(Refresh) | 불필요 | **주기적으로 필요** (커패시터 방전) |
| 가격·집적도 | 비쌈, 낮음 | 쌈, 높음 |

## 2. 캐시 메모리 (Cache)

**CPU와 메인 메모리 사이에서 자주 쓰는 데이터를 저장하는 작고 빠른 메모리**입니다.

```
CPU 요청 → L1에 있나? ─Yes─> 캐시 히트 (빠름)
              │No
              ↓
           L2에 있나? → L3에 있나? → 메인 메모리에서 가져오며 캐시에 저장 (캐시 미스)
```

### 지역성 (Locality) — 캐시가 효과적인 이유
| 지역성 | 의미 | 예 |
|---|---|---|
| **시간 지역성** | 최근 접근한 데이터는 **곧 다시** 접근 | 반복문의 `i`, `sum` 변수 |
| **공간 지역성** | 접근한 데이터 **근처**를 곧 접근 | 배열 순차 순회, 명령어 순차 실행 |

캐시는 공간 지역성을 활용해 데이터 하나만이 아니라 **캐시 라인(Cache Line, 보통 64바이트)** 단위로 주변까지 함께 가져옵니다.

### 성능 지표
```
적중률 (Hit Rate) = 히트 수 / 전체 접근 수
평균 메모리 접근 시간 (AMAT) = 히트 시간 + 미스율 × 미스 페널티

예: 히트 1ns, 미스율 5%, 미스 페널티 100ns
AMAT = 1 + 0.05 × 100 = 6ns   (캐시 없이는 100ns)
```

### 캐시 미스의 종류 (3C)
| 종류 | 원인 |
|---|---|
| **Compulsory (필수 미스, Cold Miss)** | 처음 접근해서 캐시에 없음 (피할 수 없음) |
| **Capacity (용량 미스)** | 캐시가 작아서 필요한 데이터를 다 못 담음 |
| **Conflict (충돌 미스)** | 매핑 방식 때문에 같은 자리를 두고 경쟁 |

## 3. 캐시 매핑 방식

메인 메모리의 블록을 **캐시의 어느 위치에** 저장할까?

### 3-1. 직접 매핑 (Direct Mapped)
메모리 블록이 **정해진 캐시 라인 하나에만** 들어갑니다.
```
캐시 라인 번호 = 메모리 블록 번호 % 캐시 라인 수

캐시 라인 4개일 때: 블록 0, 4, 8, 12 → 모두 라인 0
```
- 단순하고 빠름
- **충돌 미스가 많음** (블록 0과 4를 번갈아 쓰면 계속 교체)

### 3-2. 완전 연관 매핑 (Fully Associative)
메모리 블록이 **캐시의 어디에나** 들어갈 수 있습니다.
- 충돌 미스 없음
- 찾을 때 **모든 라인을 동시에 비교**해야 함 → 회로 복잡, 비쌈

### 3-3. 집합 연관 매핑 (Set Associative)
캐시를 여러 **집합(Set)** 으로 나누고, 블록은 **정해진 집합 안의 아무 라인**에나 들어갑니다. 둘의 절충안.
```
4-way 집합 연관: 집합 하나에 라인 4개
집합 번호 = 블록 번호 % 집합 수 → 그 집합 안 4개 중 빈 곳(또는 교체)
```
- **현대 CPU 캐시 대부분이 사용** (L1: 8-way, L3: 16-way 등)

| 방식 | 위치 자유도 | 충돌 미스 | 하드웨어 비용 |
|---|---|---|---|
| 직접 매핑 | 1곳 | 많음 | 낮음 |
| 집합 연관 | 집합 내 N곳 | 중간 | 중간 |
| 완전 연관 | 모든 곳 | 없음 | 높음 |

### 주소 구성
```
| 태그 (Tag) | 인덱스 (Index) | 오프셋 (Offset) |
   어느 블록?    어느 집합/라인?    라인 안 몇 번째 바이트?
```

### 교체 정책
캐시가 꽉 찼을 때 무엇을 내보낼까? → **LRU**(가장 오래 안 쓴 것)가 일반적, 하드웨어 비용 때문에 근사 LRU 사용 (→ `03.운영체제/07.가상메모리.md`의 페이지 교체와 같은 원리)

## 4. 캐시 쓰기 정책

CPU가 데이터를 **수정**하면 캐시와 메모리 중 어디에 쓸까?

| 정책 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **Write-Through** | 캐시와 메모리에 **동시에** 쓰기 | 항상 일관성 유지, 단순 | 쓰기마다 메모리 접근 → 느림 (쓰기 버퍼로 완화) |
| **Write-Back** | **캐시에만** 쓰고, 그 라인이 교체될 때 메모리에 반영 (**Dirty 비트**로 표시) | 빠름, 메모리 트래픽 감소 | 일관성 관리 복잡, 장애 시 유실 |

> Redis 캐시 전략의 Write-Through / Write-Back과 같은 개념입니다. (→ `04.데이터베이스/07.NoSQL.md`)

## 5. 캐시 일관성 (Cache Coherence)

멀티코어에서는 **코어마다 L1·L2 캐시를 따로** 가집니다. 같은 메모리 주소의 값을 두 코어가 각자 캐시에 들고 있다가 한쪽이 수정하면, 다른 코어는 **옛날 값**을 보게 됩니다.

```
메모리: x = 0
코어 1 캐시: x = 0 → x = 1로 수정
코어 2 캐시: x = 0  ← 여전히 0을 읽음!
```

### 해결: MESI 프로토콜
각 캐시 라인을 4가지 상태로 관리하며, 수정 시 다른 코어의 같은 라인을 **무효화**합니다.

| 상태 | 의미 |
|---|---|
| **M**odified | 이 캐시만 가지고 있고, **수정됨** (메모리와 다름) |
| **E**xclusive | 이 캐시만 가지고 있고, 메모리와 같음 |
| **S**hared | 여러 캐시가 공유, 메모리와 같음 |
| **I**nvalid | 무효 (사용 불가) |

> 이 하드웨어 수준의 문제가 Java에서 **`volatile`이 필요한 이유(가시성)** 와 연결됩니다. 다만 Java의 가시성 문제는 캐시뿐 아니라 컴파일러·CPU의 **명령어 재정렬**, 레지스터 보관 때문에도 생기며, Java 메모리 모델(JMM)이 이를 규정합니다. (→ `03.운영체제/04.동기화.md`)

### False Sharing (거짓 공유)
서로 **다른 변수**인데 **같은 캐시 라인(64B)** 에 있으면, 한 코어가 하나를 수정할 때마다 다른 코어의 캐시 라인 전체가 무효화되어 성능이 떨어집니다.
→ 패딩으로 변수를 다른 캐시 라인에 배치 (Java `@Contended`)

## 6. 코드로 보는 캐시 효과

```java
int N = 10000;
int[][] arr = new int[N][N];

// 빠름: 행 우선 순회 → 메모리상 연속 접근 (공간 지역성 ↑)
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += arr[i][j];

// 느림: 열 우선 순회 → 매번 다른 행(다른 메모리 위치)으로 점프 → 캐시 미스 ↑
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += arr[i][j];
```
같은 O(N²)인데도 실행 시간이 **수 배 이상** 차이 날 수 있습니다.

> 배열이 연결리스트보다 실제로 빠른 이유도 **캐시 지역성** 때문입니다. (→ `01.자료구조/01.배열.md`)

## 7. 면접 질문

1. **메모리를 계층 구조로 만드는 이유는?**
   → 빠른 메모리는 비싸고 작으므로, 자주 쓰는 데이터를 빠른 계층에 두어 비용 대비 평균 접근 속도를 높이기 위해서입니다.
2. **캐시의 지역성이란?**
   → 최근 접근한 데이터를 다시 접근하는 시간 지역성과, 접근한 데이터 근처를 곧 접근하는 공간 지역성입니다.
3. **Write-Through와 Write-Back의 차이는?**
   → Write-Through는 캐시와 메모리에 동시에 써서 일관성이 좋지만 느리고, Write-Back은 캐시에만 쓰고 교체 시 반영해 빠르지만 관리가 복잡합니다.
4. **캐시 일관성 문제란?**
   → 멀티코어에서 각 코어의 캐시에 같은 데이터의 서로 다른 값이 존재하는 문제로, MESI 같은 프로토콜로 해결합니다.

## 핵심 정리
- 레지스터 > L1 > L2 > L3 > DRAM > SSD > HDD (빠름·작음 → 느림·큼)
- 캐시 = SRAM, 지역성(시간·공간) 덕분에 효과, 64B 캐시 라인
- 매핑: 직접(충돌 많음) / 집합 연관(현대 CPU) / 완전 연관(비쌈)
- 쓰기: Write-Through vs Write-Back
- 멀티코어: 캐시 일관성(MESI), False Sharing
