# 01. 객체지향 프로그래밍 (OOP)

> **학습 목표**
> - 절차지향과 객체지향의 차이를 설명할 수 있다.
> - 객체지향 4대 특성(추상화, 캡슐화, 상속, 다형성)을 코드로 설명할 수 있다.
> - 오버로딩과 오버라이딩, 추상 클래스와 인터페이스를 구분할 수 있다.
> - 상속보다 조합을 권장하는 이유를 설명할 수 있다.

---

## 1. 프로그래밍 패러다임

| 패러다임 | 핵심 | 예 |
|---|---|---|
| 절차지향 | **순서대로 실행되는 함수(절차)** 중심, 데이터와 함수가 분리 | C |
| **객체지향** | 데이터와 그 데이터를 다루는 기능을 **객체**로 묶고, 객체 간 **협력**으로 프로그램 구성 | Java, C#, Kotlin |
| 함수형 | **순수 함수**와 불변 데이터 중심, 부수 효과 최소화 | Haskell, (Java Stream, Lambda) |

> 객체지향이 절차지향보다 "더 좋다"가 아니라, **변경이 잦고 규모가 큰 소프트웨어를 유지보수하기 쉽게** 만들기 위한 방법입니다.

### 클래스와 객체
- **클래스**: 객체를 만들기 위한 **설계도** (속성 + 행위)
- **객체 (인스턴스)**: 클래스로 만든 **실체**, 메모리(Heap)에 생성됨

```java
public class Account {             // 클래스
    private long balance;          // 속성 (상태)
    public void deposit(long amount) { balance += amount; }  // 행위
}

Account a = new Account();         // 객체 (인스턴스)
```

## 2. 객체지향 4대 특성

### 2-1. 추상화 (Abstraction)
**복잡한 대상에서 핵심적인 특징만 뽑아내고, 불필요한 세부는 감추는 것**입니다.

```java
// 결제라는 개념의 핵심: "금액을 결제한다"
public interface PaymentMethod {
    void pay(long amount);
}
```
- 사용하는 쪽은 "결제한다"만 알면 되고, 카드사 통신 방식 같은 세부는 몰라도 됩니다.

### 2-2. 캡슐화 (Encapsulation)
**데이터(필드)와 그 데이터를 다루는 메서드를 하나로 묶고, 외부에서 내부 데이터에 직접 접근하지 못하게 숨기는 것**(정보 은닉)입니다.

```java
// 나쁜 예: 누구나 balance를 마음대로 바꿈
public class Account {
    public long balance;
}
account.balance = -1000000;   // 음수 잔액이 가능해짐

// 좋은 예: 규칙을 객체 안에서 지킴
public class Account {
    private long balance;

    public void withdraw(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("금액은 양수여야 합니다");
        if (balance < amount) throw new IllegalStateException("잔액 부족");
        balance -= amount;
    }

    public long getBalance() { return balance; }
}
```

| 접근 제어자 | 같은 클래스 | 같은 패키지 | 자식 클래스 | 전체 |
|---|---|---|---|---|
| `private` | O | X | X | X |
| (default) | O | O | X | X |
| `protected` | O | O | O | X |
| `public` | O | O | O | O |

> **무분별한 Setter는 캡슐화를 깨뜨립니다.** `setBalance()` 대신 `deposit()`, `withdraw()`처럼 **의도가 드러나는 메서드**를 만들고, 규칙을 그 안에서 검증하세요. JPA 엔티티에서도 같은 원칙이 적용됩니다.

> **"묻지 말고 시켜라 (Tell, Don't Ask)"**: `if (account.getBalance() >= amount) account.setBalance(...)` 처럼 데이터를 꺼내서 밖에서 판단하지 말고, `account.withdraw(amount)` 처럼 객체에게 시키세요.

### 2-3. 상속 (Inheritance)
**부모 클래스의 속성과 기능을 자식 클래스가 물려받아 재사용하고 확장하는 것**입니다.

```java
public class Animal {
    protected String name;
    public void eat() { System.out.println(name + "이(가) 먹는다"); }
}

public class Dog extends Animal {
    public void bark() { System.out.println("멍멍"); }
}
```
- Java는 클래스 **단일 상속**만 가능 (다이아몬드 문제 방지), 인터페이스는 여러 개 구현 가능
- **is-a 관계**일 때만 사용: Dog **is an** Animal (O), Car is an Engine (X → has-a, 조합)

### 2-4. 다형성 (Polymorphism)
**같은 타입(인터페이스)의 참조로, 실제 객체에 따라 다른 동작을 하는 것**입니다. 객체지향의 핵심입니다.

```java
public interface PaymentMethod { void pay(long amount); }

public class CardPayment implements PaymentMethod {
    public void pay(long amount) { System.out.println("카드로 " + amount + "원 결제"); }
}
public class KakaoPayPayment implements PaymentMethod {
    public void pay(long amount) { System.out.println("카카오페이로 " + amount + "원 결제"); }
}

// 사용하는 쪽: 구체 클래스를 몰라도 됨
public class OrderService {
    private final PaymentMethod paymentMethod;
    public OrderService(PaymentMethod paymentMethod) { this.paymentMethod = paymentMethod; }

    public void order(long price) {
        paymentMethod.pay(price);   // 실제 객체에 따라 다르게 동작 (동적 바인딩)
    }
}

new OrderService(new CardPayment()).order(10000);
new OrderService(new KakaoPayPayment()).order(10000);
```

- 새 결제 수단(네이버페이)이 추가되어도 **OrderService는 수정하지 않습니다** → 개방-폐쇄 원칙 (→ `02.SOLID원칙.md`)
- Spring의 **의존성 주입(DI)** 이 바로 이 구조입니다.

## 3. 오버로딩 vs 오버라이딩

| 항목 | 오버로딩 (Overloading) | 오버라이딩 (Overriding) |
|---|---|---|
| 의미 | **같은 이름, 다른 매개변수**의 메서드를 여러 개 정의 | 부모의 메서드를 자식이 **재정의** |
| 위치 | 같은 클래스 | 상속 관계 |
| 시그니처 | 매개변수 **개수나 타입이 달라야** 함 | 이름, 매개변수, 반환 타입 **같아야** 함 |
| 결정 시점 | **컴파일 타임** (정적 바인딩) | **런타임** (동적 바인딩) |
| 다형성 | 정적 다형성 | **동적 다형성** |

```java
// 오버로딩
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
int add(int a, int b, int c) { return a + b + c; }

// 오버라이딩
class Animal { void sound() { System.out.println("..."); } }
class Cat extends Animal {
    @Override
    void sound() { System.out.println("야옹"); }
}
Animal a = new Cat();
a.sound();   // "야옹" ← 참조 타입(Animal)이 아니라 실제 객체(Cat)의 메서드
```

## 4. 추상 클래스 vs 인터페이스

| 항목 | 추상 클래스 | 인터페이스 |
|---|---|---|
| 키워드 | `abstract class` | `interface` |
| 상속 | **단일 상속** (`extends`) | **다중 구현** (`implements`) |
| 필드 | 일반 필드 가능 (상태 보유) | **상수만** (`public static final`) |
| 메서드 | 추상 + 일반 메서드 | 추상 + `default`·`static`·`private` 메서드 (Java 8, 9+) |
| 생성자 | 있음 | 없음 |
| 관계 | **is-a** (같은 종류, 공통 코드 공유) | **can-do** (할 수 있는 능력, 역할) |
| 예 | `AbstractList`, 템플릿 메서드 패턴 | `Comparable`, `Runnable`, `PaymentMethod` |

```java
// 추상 클래스: 공통 상태와 코드 공유
public abstract class Shape {
    protected String color;
    public abstract double area();               // 자식이 반드시 구현
    public void describe() {                     // 공통 기능
        System.out.println(color + " 도형, 넓이 = " + area());
    }
}

// 인터페이스: 역할 정의
public interface Flyable { void fly(); }
public interface Swimmable { void swim(); }
public class Duck implements Flyable, Swimmable { ... }   // 다중 구현
```

> 실무에서는 **인터페이스를 우선** 고려합니다. 역할과 구현을 분리하기 쉽고, 다중 구현이 가능하며, 테스트에서 가짜 구현(Mock)으로 바꾸기 쉽기 때문입니다.

## 5. 상속보다 조합 (Composition over Inheritance)

### 상속의 문제점
1. **강한 결합**: 부모 클래스의 내부 구현이 바뀌면 자식이 깨질 수 있음 (캡슐화 위반)
2. **불필요한 기능까지 상속**: `Stack extends Vector` → 스택인데 중간 삽입(`add(index, e)`)이 가능해짐
3. **클래스 폭발**: 기능 조합마다 자식 클래스가 필요 (`카드결제할인주문`, `카드결제무할인주문` ...)
4. 컴파일 시점에 관계가 고정되어 **런타임에 바꿀 수 없음**

### 유명한 예: 부모 구현에 의존하는 문제
```java
public class CountingSet<E> extends HashSet<E> {
    private int addCount = 0;
    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);    // HashSet.addAll이 내부에서 add()를 호출 → 두 번 셈!
    }
}
// addAll(List.of(1, 2, 3)) 후 addCount = 6 (기대값 3)
```

### 조합으로 해결
```java
public class CountingSet<E> {
    private final Set<E> set = new HashSet<>();   // 상속 대신 필드로 보유 (has-a)
    private int addCount = 0;

    public boolean add(E e) { addCount++; return set.add(e); }
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return set.addAll(c);    // 내부 구현과 무관하게 정확
    }
}
```

| 비교 | 상속 | 조합 |
|---|---|---|
| 관계 | is-a | has-a |
| 결합도 | 높음 (구현에 의존) | 낮음 (인터페이스에 의존) |
| 변경 | 컴파일 타임 고정 | **런타임에 교체 가능** |
| 재사용 | 화이트박스 (내부가 보임) | 블랙박스 |

> 상속은 **진짜 is-a 관계이고, 부모가 확장을 고려해 설계·문서화된 경우**에만 사용하세요. (이펙티브 자바 아이템 18, 19)

## 6. 객체지향 설계의 목표: 응집도와 결합도

| 개념 | 의미 | 목표 |
|---|---|---|
| **응집도 (Cohesion)** | 모듈 내부 요소들이 **하나의 목적**을 위해 얼마나 밀접한가 | **높게** |
| **결합도 (Coupling)** | 모듈 간 **의존 정도** | **낮게** |

→ "**높은 응집도, 낮은 결합도**": 변경이 생겼을 때 수정 범위가 한 곳에 모이고, 다른 곳으로 퍼지지 않게

## 7. 면접 질문

1. **객체지향 프로그래밍이란?**
   → 데이터와 그 데이터를 다루는 기능을 객체로 묶고, 객체 간의 협력으로 프로그램을 구성하는 패러다임입니다. 추상화·캡슐화·상속·다형성으로 변경에 유연한 구조를 만듭니다.
2. **캡슐화란? 왜 중요한가요?**
   → 데이터와 메서드를 묶고 내부를 숨기는 것으로, 객체 스스로 상태의 규칙을 지키게 해 외부의 잘못된 변경을 막고 내부 구현을 바꿔도 외부에 영향을 주지 않게 합니다.
3. **다형성이란?**
   → 같은 인터페이스로 실제 객체에 따라 다른 동작을 하게 하는 것으로, 사용하는 코드를 바꾸지 않고 구현을 교체·확장할 수 있게 합니다.
4. **오버로딩과 오버라이딩의 차이는?**
   → 오버로딩은 같은 이름에 매개변수가 다른 메서드를 여러 개 정의하는 것(컴파일 타임 결정), 오버라이딩은 부모 메서드를 자식이 재정의하는 것(런타임 결정)입니다.
5. **추상 클래스와 인터페이스의 차이는?**
   → 추상 클래스는 단일 상속으로 상태와 공통 구현을 공유하는 is-a 관계에, 인터페이스는 다중 구현이 가능해 역할(능력)을 정의하는 데 씁니다.
6. **상속보다 조합을 권장하는 이유는?**
   → 상속은 부모 구현에 강하게 결합되어 부모 변경에 취약하고 캡슐화를 깨뜨리지만, 조합은 인터페이스를 통해 느슨하게 결합되고 런타임에 교체할 수 있기 때문입니다.

## 핵심 정리
- 4대 특성: 추상화(핵심만) / 캡슐화(숨기고 규칙 지키기) / 상속(is-a 재사용) / 다형성(같은 타입, 다른 동작)
- 오버로딩(컴파일, 매개변수 다름) vs 오버라이딩(런타임, 재정의)
- 추상 클래스(is-a, 상태 공유) vs 인터페이스(can-do, 다중 구현)
- 상속보다 조합, 높은 응집도 + 낮은 결합도
