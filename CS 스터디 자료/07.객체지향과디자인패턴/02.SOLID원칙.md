# 02. SOLID 원칙

> **학습 목표**
> - SOLID 5가지 원칙을 각각 위반 예시와 개선 예시로 설명할 수 있다.
> - DI(의존성 주입)와 IoC(제어의 역전)가 SOLID와 어떻게 연결되는지 설명할 수 있다.

---

## 개요

| 원칙 | 이름 | 한 줄 요약 |
|---|---|---|
| **S** | 단일 책임 원칙 (SRP) | 클래스는 **변경될 이유가 하나**여야 한다 |
| **O** | 개방-폐쇄 원칙 (OCP) | **확장에는 열려 있고, 변경에는 닫혀** 있어야 한다 |
| **L** | 리스코프 치환 원칙 (LSP) | 자식은 **부모를 대체**할 수 있어야 한다 |
| **I** | 인터페이스 분리 원칙 (ISP) | 클라이언트는 **쓰지 않는 메서드에 의존하면 안** 된다 |
| **D** | 의존 역전 원칙 (DIP) | **구체가 아닌 추상**에 의존해야 한다 |

---

## 1. SRP: 단일 책임 원칙 (Single Responsibility Principle)

> **한 클래스는 하나의 책임만 가져야 한다.** = 클래스를 변경해야 하는 이유는 하나뿐이어야 한다.

### 위반
```java
public class MemberService {
    public void join(Member m) {
        // 1. 유효성 검사
        if (m.getEmail() == null) throw new IllegalArgumentException();
        // 2. DB 저장 (JDBC 코드 직접 작성)
        Connection conn = DriverManager.getConnection(...);
        // ...
        // 3. 이메일 발송 (SMTP 코드 직접 작성)
        // ...
    }
}
```
- DB가 바뀌어도, 이메일 템플릿이 바뀌어도, 검증 규칙이 바뀌어도 **이 클래스를 수정**해야 합니다.

### 개선
```java
public class MemberService {
    private final MemberValidator validator;
    private final MemberRepository repository;
    private final EmailSender emailSender;

    public void join(Member m) {
        validator.validate(m);
        repository.save(m);
        emailSender.sendWelcome(m.getEmail());
    }
}
```
- 각 클래스는 **자기 책임 하나**만 변경 이유로 가집니다.
- Spring의 **Controller(요청/응답) - Service(비즈니스 로직) - Repository(데이터 접근)** 계층 분리도 SRP의 적용입니다.

> "책임"의 기준은 **누가 변경을 요구하는가(액터)** 입니다. 회계팀이 요구하는 급여 계산과 인사팀이 요구하는 근무 시간 보고가 한 클래스에 있으면, 한 팀의 요구 변경이 다른 팀 기능을 깨뜨릴 수 있습니다.

## 2. OCP: 개방-폐쇄 원칙 (Open-Closed Principle)

> **기능을 추가(확장)할 때 기존 코드를 수정하지 않아야 한다.**

### 위반
```java
public class DiscountService {
    public long discount(String grade, long price) {
        if (grade.equals("VIP")) return price * 20 / 100;
        else if (grade.equals("GOLD")) return price * 10 / 100;
        // 새 등급 "SILVER" 추가 → 이 메서드를 수정해야 함
        return 0;
    }
}
```

### 개선: 다형성 활용
```java
public interface DiscountPolicy {
    boolean supports(String grade);
    long discount(long price);
}

public class VipDiscountPolicy implements DiscountPolicy {
    public boolean supports(String grade) { return grade.equals("VIP"); }
    public long discount(long price) { return price * 20 / 100; }
}

public class GoldDiscountPolicy implements DiscountPolicy { ... }

// 새 등급은 새 클래스만 추가 → DiscountService는 수정 X
public class SilverDiscountPolicy implements DiscountPolicy { ... }

public class DiscountService {
    private final List<DiscountPolicy> policies;   // Spring이 모든 구현체를 주입

    public long discount(String grade, long price) {
        return policies.stream()
                .filter(p -> p.supports(grade))
                .findFirst()
                .map(p -> p.discount(price))
                .orElse(0L);
    }
}
```
- **전략 패턴**이 대표적인 OCP 구현 방법입니다. (→ `03.디자인패턴.md`)

## 3. LSP: 리스코프 치환 원칙 (Liskov Substitution Principle)

> **자식 클래스는 부모 클래스를 대신해도 프로그램이 올바르게 동작해야 한다.** = 자식은 부모의 **약속(계약)** 을 지켜야 한다.

### 위반: 직사각형-정사각형 문제
```java
public class Rectangle {
    protected int width, height;
    public void setWidth(int w) { width = w; }
    public void setHeight(int h) { height = h; }
    public int area() { return width * height; }
}

public class Square extends Rectangle {   // 수학적으로 정사각형은 직사각형이니까?
    @Override public void setWidth(int w) { width = height = w; }
    @Override public void setHeight(int h) { width = height = h; }
}

// 부모 타입을 믿고 쓰는 코드
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;   // Square를 넣으면 16 → 실패!
}
```
- "너비를 바꾸면 높이는 그대로"라는 Rectangle의 **약속을 Square가 깨뜨렸습니다.**

### 개선
- 상속 관계를 끊고 공통 인터페이스 `Shape { int area(); }`로 분리
- 또는 **불변 객체**로 만들어 setter 자체를 없앰

### LSP 위반 신호
- 자식이 부모 메서드를 오버라이딩해서 **예외를 던지거나 아무것도 안 함** (`UnsupportedOperationException`)
- 사용하는 쪽에서 `if (obj instanceof Square)` 같은 **타입 검사**가 필요함

> Java의 `List.of()`가 반환하는 불변 리스트에 `add()`를 호출하면 `UnsupportedOperationException`이 납니다. 엄밀히는 LSP와 충돌하는 설계로 자주 언급됩니다.

## 4. ISP: 인터페이스 분리 원칙 (Interface Segregation Principle)

> **클라이언트는 자신이 사용하지 않는 메서드에 의존하면 안 된다.** = 큰 인터페이스 하나보다 **역할별 작은 인터페이스 여러 개**가 낫다.

### 위반
```java
public interface Worker {
    void work();
    void eat();
    void sleep();
}

public class Robot implements Worker {
    public void work() { ... }
    public void eat() { throw new UnsupportedOperationException(); }    // 로봇은 안 먹음
    public void sleep() { throw new UnsupportedOperationException(); }
}
```

### 개선
```java
public interface Workable { void work(); }
public interface Eatable  { void eat(); }
public interface Sleepable { void sleep(); }

public class Human implements Workable, Eatable, Sleepable { ... }
public class Robot implements Workable { ... }
```
- 인터페이스가 바뀌어도 그 기능을 쓰지 않는 클래스는 영향을 받지 않습니다.

## 5. DIP: 의존 역전 원칙 (Dependency Inversion Principle)

> **고수준 모듈(비즈니스 로직)은 저수준 모듈(구체적인 구현)에 의존하면 안 된다. 둘 다 추상화(인터페이스)에 의존해야 한다.**

### 위반
```java
public class OrderService {
    private final MySqlOrderRepository repository = new MySqlOrderRepository();   // 구체 클래스에 직접 의존
}
```
- DB를 MongoDB로 바꾸면 OrderService를 **수정**해야 함
- 테스트할 때 가짜 저장소로 바꾸기 어려움

### 개선
```java
public interface OrderRepository { void save(Order order); }

public class MySqlOrderRepository implements OrderRepository { ... }
public class MongoOrderRepository implements OrderRepository { ... }

public class OrderService {
    private final OrderRepository repository;     // 추상화에 의존

    public OrderService(OrderRepository repository) {   // 외부에서 주입 (DI)
        this.repository = repository;
    }
}
```

### 왜 "역전"인가?
```
Before:  OrderService ──의존──> MySqlOrderRepository
                    (고수준이 저수준에 의존)

After:   OrderService ──의존──> <<interface>> OrderRepository <──구현── MySqlOrderRepository
                    (저수준이 고수준이 정한 추상화에 의존 → 의존 방향이 역전)
```
- 인터페이스의 **소유권이 고수준(비즈니스) 쪽**에 있다는 점이 핵심입니다.

## 6. DI와 IoC (Spring과의 연결)

### IoC (Inversion of Control, 제어의 역전)
- 객체의 **생성과 생명주기, 의존 관계 연결**을 개발자가 아니라 **프레임워크(컨테이너)가 담당**하는 것
- "Don't call us, we'll call you" (할리우드 원칙)
- 라이브러리는 **내가** 호출, 프레임워크는 **프레임워크가** 내 코드를 호출

### DI (Dependency Injection, 의존성 주입)
- 객체가 필요한 의존 객체를 **직접 만들지 않고 외부에서 주입**받는 것 → IoC를 구현하는 방법
- DIP를 실현하는 수단

```java
@Service
@RequiredArgsConstructor     // final 필드로 생성자 자동 생성 (Lombok)
public class OrderService {
    private final OrderRepository orderRepository;   // Spring이 구현체를 찾아 주입
    private final DiscountPolicy discountPolicy;
}
```

| 주입 방식 | 특징 |
|---|---|
| **생성자 주입** (권장) | **불변(final)**, 필수 의존성 누락을 컴파일 시점에 확인, 순환 참조를 시작 시점에 발견, 테스트 쉬움 |
| Setter 주입 | 선택적 의존성, 변경 가능 |
| 필드 주입 (`@Autowired` 필드) | 간단하지만 테스트 어렵고 final 불가 → **비권장** |

> Spring의 DI 컨테이너 덕분에 OCP와 DIP를 지키면서도, 구현체를 바꿀 때 **설정만 바꾸면** 됩니다.

## 7. 면접 질문

1. **SOLID 원칙을 설명해 주세요.**
   → 단일 책임(변경 이유 하나), 개방-폐쇄(확장에 열리고 수정에 닫힘), 리스코프 치환(자식이 부모를 대체 가능), 인터페이스 분리(쓰지 않는 메서드에 의존 X), 의존 역전(추상화에 의존)입니다.
2. **OCP를 지키는 방법은?**
   → 변하는 부분을 인터페이스로 추상화하고 다형성으로 구현을 교체해, 새 기능은 새 클래스 추가만으로 확장합니다.
3. **LSP 위반 사례는?**
   → 정사각형이 직사각형을 상속해 너비·높이 설정 동작을 바꾸는 경우로, 부모 타입을 기대하는 코드가 잘못 동작합니다.
4. **DI와 IoC의 차이는?**
   → IoC는 객체 생성과 제어 흐름을 프레임워크에 넘기는 개념이고, DI는 의존 객체를 외부에서 주입하는 IoC의 구현 방법입니다.
5. **생성자 주입을 권장하는 이유는?**
   → final로 불변성을 보장하고, 필수 의존성 누락을 막으며, 순환 참조를 빨리 발견하고, 테스트에서 의존성을 쉽게 바꿀 수 있기 때문입니다.

## 핵심 정리
- **S**: 변경 이유 하나 / **O**: 수정 없이 확장 (다형성) / **L**: 자식은 부모의 약속을 지킴
- **I**: 작은 인터페이스 여러 개 / **D**: 구체가 아닌 추상에 의존
- IoC = 제어를 프레임워크에, DI = 외부에서 주입 (생성자 주입 권장)
