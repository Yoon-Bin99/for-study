# 03. 디자인 패턴 (Design Patterns)

> **학습 목표**
> - 디자인 패턴의 의미와 GoF 분류(생성·구조·행위)를 설명할 수 있다.
> - 자주 쓰는 패턴(싱글톤, 팩토리, 빌더, 전략, 템플릿 메서드, 옵저버, 프록시, 어댑터, 데코레이터)을 코드로 설명할 수 있다.
> - Spring에서 각 패턴이 어디에 쓰이는지 연결할 수 있다.

---

## 1. 디자인 패턴이란?

**소프트웨어 설계에서 반복적으로 나타나는 문제에 대한, 검증된 해결 방법의 이름 붙은 템플릿**입니다. GoF(Gang of Four)가 23가지로 정리했습니다.

- 장점: 개발자 간 **공통 언어** ("여기 전략 패턴으로 하죠"), 검증된 구조
- 주의: 패턴을 위한 패턴은 과설계. **문제가 있을 때** 적용하세요.

| 분류 | 관심사 | 대표 패턴 |
|---|---|---|
| **생성 (Creational)** | 객체를 **어떻게 만들까** | 싱글톤, 팩토리 메서드, 추상 팩토리, 빌더, 프로토타입 |
| **구조 (Structural)** | 클래스·객체를 **어떻게 조합할까** | 어댑터, 프록시, 데코레이터, 퍼사드, 컴포지트 |
| **행위 (Behavioral)** | 객체 간 **책임과 소통** | 전략, 템플릿 메서드, 옵저버, 커맨드, 상태, 이터레이터 |

# 생성 패턴

## 2. 싱글톤 (Singleton)

**클래스의 인스턴스를 오직 하나만** 만들고, 어디서든 그 인스턴스에 접근하게 합니다.

사용처: 설정 정보, 커넥션 풀, 로거, 캐시 등 **공유 자원**

```java
// 1) 이른 초기화 (Eager) — 클래스 로딩 시 생성, 스레드 안전
public class Config {
    private static final Config INSTANCE = new Config();
    private Config() {}                              // 외부 생성 금지
    public static Config getInstance() { return INSTANCE; }
}

// 2) 지연 초기화 — 스레드 안전하지 않음 (멀티스레드에서 2개 생길 수 있음)
public class LazyConfig {
    private static LazyConfig instance;
    private LazyConfig() {}
    public static LazyConfig getInstance() {
        if (instance == null) instance = new LazyConfig();   // 경쟁 상태!
        return instance;
    }
}

// 3) Holder 방식 (권장) — 지연 초기화 + 스레드 안전 (클래스 로딩은 JVM이 동기화)
public class HolderConfig {
    private HolderConfig() {}
    private static class Holder {
        private static final HolderConfig INSTANCE = new HolderConfig();
    }
    public static HolderConfig getInstance() { return Holder.INSTANCE; }
}

// 4) Enum 방식 — 직렬화·리플렉션 공격에도 안전 (이펙티브 자바 권장)
public enum EnumConfig { INSTANCE; }
```

### 싱글톤의 단점
- 전역 상태 → **테스트 어려움** (Mock으로 바꾸기 어려움), 숨겨진 의존성
- **상태(필드)를 가지면 멀티스레드에서 위험**
- private 생성자 → 상속 불가

> **Spring 빈은 기본적으로 싱글톤 스코프**입니다. 하지만 위처럼 클래스가 직접 싱글톤을 구현하는 게 아니라 **컨테이너가 하나만 만들어 관리**하므로 단점이 없습니다. 대신 **빈에 변경 가능한 필드(상태)를 두면 안 됩니다** (여러 요청 스레드가 공유).

## 3. 팩토리 메서드 / 정적 팩토리 메서드

### 정적 팩토리 메서드 (Static Factory Method)
생성자 대신 **이름이 있는 static 메서드**로 객체를 만듭니다. (GoF 패턴은 아니지만 매우 자주 씀)
```java
public class Member {
    private final String email;
    private final Role role;
    private Member(String email, Role role) { this.email = email; this.role = role; }

    public static Member createUser(String email)  { return new Member(email, Role.USER); }
    public static Member createAdmin(String email) { return new Member(email, Role.ADMIN); }
}

// JDK 예
List.of(1, 2, 3);
Integer.valueOf(10);        // 캐시된 인스턴스 재사용 가능 (-128 ~ 127)
LocalDate.of(2026, 11, 9);
```
장점: **이름으로 의도 표현**, 매번 새 객체를 만들 필요 없음(캐싱), 하위 타입 반환 가능

### 팩토리 메서드 패턴 (GoF)
**객체 생성을 서브클래스(또는 별도 메서드)에 위임**해, 사용하는 쪽이 구체 클래스를 몰라도 되게 합니다.
```java
public interface Notification { void send(String msg); }
public class EmailNotification implements Notification { ... }
public class SmsNotification implements Notification { ... }

public class NotificationFactory {
    public static Notification create(String type) {
        return switch (type) {
            case "EMAIL" -> new EmailNotification();
            case "SMS"   -> new SmsNotification();
            default      -> throw new IllegalArgumentException(type);
        };
    }
}
```
> 위 예처럼 조건문으로 고르는 것은 엄밀히는 "단순 팩토리"입니다. GoF의 팩토리 메서드는 **생성 메서드를 추상 메서드로 두고 서브클래스가 오버라이딩**해 무엇을 만들지 정합니다.

## 4. 빌더 (Builder)

**매개변수가 많은 객체를 단계적으로, 읽기 쉽게** 생성합니다.

```java
// 문제: 생성자 매개변수가 많으면 순서를 헷갈림
new Pizza("L", true, false, true, false, true);   // 각 true/false가 뭔지?

// 빌더
public class Pizza {
    private final String size;
    private final boolean cheese, pepperoni, bacon;

    private Pizza(Builder b) {
        this.size = b.size; this.cheese = b.cheese;
        this.pepperoni = b.pepperoni; this.bacon = b.bacon;
    }

    public static Builder builder(String size) { return new Builder(size); }

    public static class Builder {
        private final String size;           // 필수
        private boolean cheese, pepperoni, bacon;   // 선택
        private Builder(String size) { this.size = size; }
        public Builder cheese()    { this.cheese = true; return this; }
        public Builder pepperoni() { this.pepperoni = true; return this; }
        public Builder bacon()     { this.bacon = true; return this; }
        public Pizza build()       { return new Pizza(this); }
    }
}

Pizza p = Pizza.builder("L").cheese().bacon().build();
```
- **가독성**, **불변 객체** 생성, 선택적 매개변수 처리
- Lombok `@Builder`, `StringBuilder`, Spring `UriComponentsBuilder`, `ResponseEntity.ok().header(...).body(...)`

# 구조 패턴

## 5. 어댑터 (Adapter)

**호환되지 않는 인터페이스를 가진 클래스를, 클라이언트가 기대하는 인터페이스로 변환**합니다. 110V 플러그를 220V 콘센트에 꽂는 변환 어댑터.

```java
// 우리 시스템이 기대하는 인터페이스
public interface PaymentGateway { void pay(long amount); }

// 외부 라이브러리 (수정 불가, 메서드 이름·형식이 다름)
public class TossPaymentsSdk {
    public void requestPayment(String amountString, String currency) { ... }
}

// 어댑터
public class TossPaymentAdapter implements PaymentGateway {
    private final TossPaymentsSdk sdk;
    public TossPaymentAdapter(TossPaymentsSdk sdk) { this.sdk = sdk; }

    @Override
    public void pay(long amount) {
        sdk.requestPayment(String.valueOf(amount), "KRW");   // 변환
    }
}
```
- Spring MVC의 **HandlerAdapter**: 다양한 형태의 컨트롤러를 DispatcherServlet이 같은 방식으로 호출
- `Arrays.asList()`: 배열 → List 인터페이스

## 6. 프록시 (Proxy)

**실제 객체 대신 대리 객체를 두어, 접근을 제어하거나 부가 기능을 추가**합니다. 클라이언트는 프록시인지 모르고 같은 인터페이스로 사용합니다.

```java
public interface ProductService { Product find(Long id); }

public class RealProductService implements ProductService {
    public Product find(Long id) { /* DB 조회 */ }
}

// 캐싱 프록시
public class CachingProductProxy implements ProductService {
    private final ProductService target;
    private final Map<Long, Product> cache = new ConcurrentHashMap<>();

    public CachingProductProxy(ProductService target) { this.target = target; }

    @Override
    public Product find(Long id) {
        return cache.computeIfAbsent(id, target::find);   // 없을 때만 실제 객체 호출
    }
}
```

| 프록시 용도 | 설명 |
|---|---|
| 접근 제어 (보호 프록시) | 권한 확인 후 호출 |
| 지연 로딩 (가상 프록시) | 실제로 필요할 때 객체 생성 |
| 캐싱, 로깅, 트랜잭션 | 부가 기능 |

> **Spring에서 매우 중요합니다.**
> - **`@Transactional`**: 프록시가 메서드 호출 전에 트랜잭션 시작, 끝나면 커밋/롤백 → 그래서 **같은 클래스 내부 호출(this.method())은 프록시를 거치지 않아 트랜잭션이 적용되지 않습니다.** (→ `04.데이터베이스/05.트랜잭션.md`)
> - **Spring AOP** (`@Aspect`): JDK 동적 프록시 또는 CGLIB 프록시
> - **JPA 지연 로딩**: `member.getTeam()`이 반환하는 것은 실제 Team이 아니라 프록시. 실제로 필드를 사용할 때 DB 조회

## 7. 데코레이터 (Decorator)

**객체를 감싸서 기능을 동적으로 덧붙입니다.** 구조는 프록시와 같지만 **목적이 기능 추가(꾸미기)** 이고, 여러 겹으로 쌓을 수 있습니다.

```java
// Java I/O가 대표적인 데코레이터
BufferedReader br = new BufferedReader(          // 버퍼링 기능 추가
                        new InputStreamReader(   // 바이트 → 문자 변환 기능 추가
                            new FileInputStream("a.txt")));   // 실제 파일 읽기
```

| 비교 | 프록시 | 데코레이터 |
|---|---|---|
| 목적 | **접근 제어** (캐시, 권한, 지연 로딩) | **기능 추가** |
| 실제 객체 | 프록시가 생성·관리하기도 함 | 외부에서 받아 감쌈 |

# 행위 패턴

## 8. 전략 (Strategy)

**알고리즘(전략)을 인터페이스로 분리하고, 실행 중에 교체**할 수 있게 합니다. **OCP의 대표적인 구현**입니다.

```java
public interface DiscountStrategy { long apply(long price); }

public class NoDiscount implements DiscountStrategy {
    public long apply(long price) { return price; }
}
public class RateDiscount implements DiscountStrategy {
    private final int rate;
    public RateDiscount(int rate) { this.rate = rate; }
    public long apply(long price) { return price * (100 - rate) / 100; }
}
public class FixedDiscount implements DiscountStrategy {
    public long apply(long price) { return Math.max(0, price - 1000); }
}

public class Order {
    private DiscountStrategy strategy;
    public void setStrategy(DiscountStrategy s) { this.strategy = s; }
    public long finalPrice(long price) { return strategy.apply(price); }
}

order.setStrategy(new RateDiscount(10));
// 람다로도 가능: order.setStrategy(price -> price / 2);
```
- `Comparator`가 대표적인 전략 패턴입니다: `list.sort(Comparator.comparing(Person::getAge))`
- Spring: 여러 구현체를 `List<DiscountPolicy>`나 `Map<String, DiscountPolicy>`로 주입받아 선택

## 9. 템플릿 메서드 (Template Method)

**알고리즘의 전체 흐름(뼈대)은 부모 클래스에 정의하고, 일부 단계만 자식 클래스가 구현**합니다.

```java
public abstract class DataExporter {
    // 템플릿 메서드: 순서는 고정 (final로 재정의 금지)
    public final void export() {
        connect();
        String data = fetchData();     // 자식이 구현
        String formatted = format(data);   // 자식이 구현
        write(formatted);
        disconnect();
    }

    private void connect()    { System.out.println("연결"); }
    private void disconnect() { System.out.println("해제"); }
    private void write(String s) { System.out.println("저장: " + s); }

    protected abstract String fetchData();
    protected abstract String format(String data);
}

public class CsvExporter extends DataExporter {
    protected String fetchData() { return "a,b,c"; }
    protected String format(String data) { return data.replace(",", ";"); }
}
```
- 중복 코드 제거, 흐름 통제
- 단점: **상속 기반** → 부모와 강하게 결합
- Spring: `JdbcTemplate`, `RestTemplate`, `AbstractController` — 반복되는 연결·예외·자원 해제는 템플릿이 처리하고 핵심 로직만 콜백으로 전달 (**템플릿 콜백 패턴**, 전략 패턴의 변형)

| 비교 | 전략 | 템플릿 메서드 |
|---|---|---|
| 방식 | **조합** (인터페이스 주입) | **상속** |
| 교체 시점 | 런타임 | 컴파일 타임 |
| 결합도 | 낮음 | 높음 |

## 10. 옵저버 (Observer)

**한 객체(주제)의 상태가 바뀌면, 그 객체에 의존하는 여러 객체(관찰자)에게 자동으로 알립니다.** (발행-구독, Pub/Sub의 기본)

```java
public interface OrderListener { void onOrderCompleted(Order order); }

public class OrderService {
    private final List<OrderListener> listeners = new ArrayList<>();
    public void addListener(OrderListener l) { listeners.add(l); }

    public void complete(Order order) {
        // 주문 완료 처리...
        listeners.forEach(l -> l.onOrderCompleted(order));   // 모두에게 알림
    }
}

orderService.addListener(order -> emailService.send(order));
orderService.addListener(order -> pointService.addPoint(order));
orderService.addListener(order -> slackNotifier.notify(order));
```
- 주제와 관찰자가 **느슨하게 결합** → 새 후속 작업(알림 추가)이 생겨도 OrderService 수정 X
- Spring: **`ApplicationEventPublisher` + `@EventListener`**, `@TransactionalEventListener`(커밋 후 실행)
- 확장: Kafka, RabbitMQ 같은 메시지 브로커 기반 이벤트 기반 아키텍처, JavaScript 이벤트 리스너

```java
// Spring 이벤트
@Service @RequiredArgsConstructor
public class OrderService {
    private final ApplicationEventPublisher publisher;
    @Transactional
    public void complete(Order order) {
        // ...
        publisher.publishEvent(new OrderCompletedEvent(order.getId()));
    }
}

@Component
public class EmailHandler {
    @TransactionalEventListener   // 트랜잭션 커밋 후 실행
    public void handle(OrderCompletedEvent e) { /* 메일 발송 */ }
}
```

## 11. 그 외 알아 둘 패턴

| 패턴 | 한 줄 설명 | 예 |
|---|---|---|
| **퍼사드 (Facade)** | 복잡한 하위 시스템을 **단순한 하나의 인터페이스**로 감쌈 | 여러 서비스를 조합하는 `OrderFacade` |
| 컴포지트 (Composite) | 개별 객체와 객체 묶음을 **같은 방식으로** 다룸 (트리) | 파일-폴더, UI 컴포넌트 트리 |
| 커맨드 (Command) | 요청을 **객체로 캡슐화** → 큐잉, 실행 취소 | `Runnable`, Undo 기능 |
| 상태 (State) | 상태별 행동을 **상태 객체로 분리** | 주문 상태(결제대기 → 결제완료 → 배송중) |
| 이터레이터 (Iterator) | 내부 구조를 노출하지 않고 **순회** | `Iterator`, for-each |
| **MVC** (아키텍처 패턴) | Model(데이터) - View(화면) - Controller(요청 처리) 분리 | Spring MVC |

## 12. Spring에서 만나는 패턴 정리

| Spring 기능 | 패턴 |

| `@Transactional`, AOP, JPA 지연 로딩 | **프록시** |

| `DispatcherServlet` | 프론트 컨트롤러 |

## 13. 면접 질문

1. **싱글톤 패턴이란? 주의할 점은?**
   → 인스턴스를 하나만 만들어 공유하는 패턴으로, 멀티스레드 환경에서 생성 시 경쟁 상태와 공유 상태(필드) 변경에 주의해야 하며 테스트가 어려워질 수 있습니다.
2. **전략 패턴과 템플릿 메서드 패턴의 차이는?**
   → 둘 다 변하는 부분을 분리하지만, 전략은 인터페이스 조합으로 런타임에 교체하고 템플릿 메서드는 상속으로 일부 단계를 재정의합니다.
3. **프록시 패턴이 Spring에서 어떻게 쓰이나요?**
   → @Transactional, AOP, JPA 지연 로딩이 프록시 기반으로, 실제 객체 호출 전후에 트랜잭션·부가 기능을 처리합니다. 그래서 내부 호출에는 적용되지 않습니다.
4. **옵저버 패턴이란?**
   → 주제 객체의 상태 변화를 등록된 관찰자들에게 자동으로 알리는 패턴으로, 발행자와 구독자를 느슨하게 결합시킵니다.
5. **빌더 패턴을 쓰는 이유는?**
   → 매개변수가 많을 때 가독성을 높이고 선택적 매개변수를 쉽게 처리하며 불변 객체를 만들기 좋기 때문입니다.

## 핵심 정리
- 생성(싱글톤·팩토리·빌더) / 구조(어댑터·프록시·데코레이터·퍼사드) / 행위(전략·템플릿 메서드·옵저버)
- 싱글톤: Holder/Enum 방식, Spring 빈은 상태 없이
- 프록시 = Spring의 핵심 (@Transactional, AOP, 지연 로딩)
- 전략(조합, 런타임 교체) vs 템플릿 메서드(상속)
- 옵저버 = 이벤트, Pub/Sub
