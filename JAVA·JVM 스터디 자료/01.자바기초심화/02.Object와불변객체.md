# 02. Object 클래스, equals·hashCode, 불변 객체, record

> **학습 목표**
> - equals와 hashCode의 규약과 함께 재정의해야 하는 이유를 설명할 수 있다.
> - 불변 객체를 만드는 방법과 장점을 설명할 수 있다.
> - record를 언제 쓰는지 설명할 수 있다.
> - 얕은 복사와 깊은 복사, 방어적 복사를 설명할 수 있다.

---

## 1. Object의 주요 메서드

모든 클래스는 `java.lang.Object`를 상속합니다.

| 메서드 | 기본 동작 | 재정의 |
|---|---|---|
| `equals(Object)` | `==` (같은 객체인가) | **논리적으로 같은지** 비교하려면 |
| `hashCode()` | 객체마다 다른 값 (주소 기반 아님, JVM이 생성) | equals를 재정의하면 **반드시** |
| `toString()` | `클래스명@해시16진수` | 디버깅·로그용으로 권장 |
| `getClass()` | 런타임 클래스 | final |
| `clone()` | 얕은 복사 (Cloneable 필요) | 비권장 |
| `wait/notify` | 모니터 동기화 | final |

## 2. equals와 hashCode

### equals 규약
| 규약 | 의미 |
|---|---|
| 반사성 | `x.equals(x)` = true |
| 대칭성 | `x.equals(y)` ⇔ `y.equals(x)` |
| 추이성 | x=y, y=z이면 x=z |
| 일관성 | 값이 안 바뀌면 결과도 같음 |
| null | `x.equals(null)` = false |

### hashCode 규약
- **equals가 true인 두 객체는 hashCode가 같아야 한다**
- hashCode가 같다고 equals가 true일 필요는 없음 (충돌 허용)

### 함께 재정의하지 않으면?
```java
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;     // 패턴 매칭 (Java 16+)
        return x == p.x && y == p.y;
    }
    // hashCode 재정의 안 함!
}

Set<Point> set = new HashSet<>();
set.add(new Point(1, 2));
set.contains(new Point(1, 2));    // false!  ← 해시가 달라 다른 버킷을 찾음
```
HashMap·HashSet은 **hashCode로 버킷을 찾고 → equals로 비교**하기 때문입니다.

```java
@Override
public int hashCode() {
    return Objects.hash(x, y);
}
```

### 주의할 점
| 주의 | 설명 |
|---|---|
| **HashMap 키는 불변으로** | 키 객체의 필드가 바뀌면 hashCode가 바뀌어 다시 찾을 수 없음 |
| JPA 엔티티의 equals | id 기반으로 하되, **저장 전(id null)** 상태를 고려. 프록시 때문에 `getClass()` 대신 `instanceof` 사용 |
| Lombok `@EqualsAndHashCode` | 엔티티에 쓰면 연관관계까지 비교해 무한 루프·지연 로딩 위험 → 엔티티에는 지양 |
| 상속과 equals | 하위 클래스가 필드를 추가하면 대칭성·추이성을 지키기 어려움 → 조합 사용 |

## 3. 불변 객체 (Immutable Object)

**생성 후 상태가 바뀌지 않는 객체**입니다. (String, Integer, LocalDate, BigDecimal)

### 만드는 방법
```java
public final class Money {                       // ① 상속 금지
    private final long amount;                   // ② 모든 필드 private final
    private final String currency;

    public Money(long amount, String currency) {
        if (amount < 0) throw new IllegalArgumentException("금액은 0 이상");
        this.amount = amount;
        this.currency = Objects.requireNonNull(currency);
    }

    // ③ setter 없음, 변경이 필요하면 새 객체 반환
    public Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("통화 다름");
        return new Money(amount + other.amount, currency);
    }

    public long getAmount() { return amount; }
}
```
| 규칙 | |
|---|---|
| 클래스 `final` | 하위 클래스가 가변으로 만드는 것 방지 |
| 필드 `private final` | |
| setter 없음 | 변경은 새 객체 반환 (`plus`, `withXxx`) |
| **가변 필드는 방어적 복사** | List, Date, 배열을 받거나 돌려줄 때 복사 |

### 방어적 복사
```java
public final class Order {
    private final List<OrderItem> items;

    public Order(List<OrderItem> items) {
        this.items = List.copyOf(items);          // 받을 때 복사 (원본 리스트가 바뀌어도 영향 X)
    }

    public List<OrderItem> getItems() {
        return items;                             // List.copyOf는 이미 불변 리스트
    }
}
```
> `Collections.unmodifiableList(list)`는 **원본의 읽기 전용 뷰**라서, 원본이 바뀌면 같이 바뀝니다. `List.copyOf()`는 **복사본**입니다.

### 장점
- **스레드 안전** (동기화 불필요)
- 실수로 상태가 바뀌는 버그 없음, 추론이 쉬움
- HashMap 키, Set 원소로 안전
- 값 객체(VO)로 쓰기 좋음 (Money, Email, Address)

> 단점: 값이 바뀔 때마다 새 객체 → 객체 생성 비용. 대부분 무시할 수준이고, JVM은 짧게 사는 객체를 매우 효율적으로 처리합니다.

## 4. record (Java 16+)

**불변 데이터 운반 클래스**를 한 줄로 만듭니다.
```java
public record MemberResponse(Long id, String email, String name) { }
```
자동으로 만들어지는 것:
- `private final` 필드, 모든 필드를 받는 생성자
- 접근자 `id()`, `email()` (get 접두사 없음)
- `equals`, `hashCode`, `toString`

```java
public record Email(String value) {
    public Email {                                   // 컴팩트 생성자: 검증
        if (value == null || !value.contains("@")) {
            throw new IllegalArgumentException("이메일 형식 오류");
        }
    }
}

public record Point(int x, int y) {
    public static Point origin() { return new Point(0, 0); }   // 정적 메서드 가능
    public double distance() { return Math.sqrt(x * x + y * y); }
}
```

| 적합 | 부적합 |
|---|---|
| **DTO** (요청·응답), 값 객체, 이벤트, 설정 (`@ConfigurationProperties`) | **JPA 엔티티** (기본 생성자·가변성·프록시 필요) |
| 메서드 반환용 튜플 | 상속이 필요한 경우 (record는 다른 클래스를 상속 불가, 인터페이스 구현은 가능) |

> record의 필드가 List 같은 가변 객체면 내부는 바뀔 수 있습니다. 컴팩트 생성자에서 `items = List.copyOf(items);` 로 방어하세요.

## 5. 얕은 복사 vs 깊은 복사

```java
List<Member> original = new ArrayList<>(List.of(new Member("kim")));
List<Member> shallow = new ArrayList<>(original);   // 리스트는 새로, 안의 Member는 같은 객체

shallow.get(0).setName("lee");
original.get(0).getName();   // "lee" ← 원소 객체를 공유
```
| 복사 | 의미 |
|---|---|
| 얕은 복사 | 껍데기만 새로, **내부 객체는 공유** |
| 깊은 복사 | 내부 객체까지 모두 새로 |

> `clone()`은 설계 문제가 많아(이펙티브 자바 아이템 13) **복사 생성자나 정적 팩토리**(`Member.copyOf(m)`)를 권장합니다. 불변 객체는 복사할 필요 자체가 없습니다.

## 6. 면접 질문

1. **equals를 재정의할 때 hashCode도 재정의해야 하는 이유는?**
   → HashMap·HashSet은 hashCode로 버킷을 찾고 equals로 비교하므로, 논리적으로 같은 객체가 다른 hashCode를 가지면 찾을 수 없거나 중복 저장되기 때문입니다.
2. **불변 객체를 만드는 방법과 장점은?**
   → 클래스를 final로, 필드를 private final로 하고 setter 없이 변경 시 새 객체를 반환하며 가변 필드는 방어적으로 복사합니다. 스레드 안전하고 상태 변경 버그가 없으며 맵 키로 안전합니다.
3. **record는 언제 쓰나요?**
   → 요청·응답 DTO나 값 객체처럼 불변 데이터를 담는 클래스에 쓰며, JPA 엔티티처럼 가변성과 기본 생성자가 필요한 곳에는 쓰지 않습니다.
4. **unmodifiableList와 List.copyOf의 차이는?**
   → unmodifiableList는 원본의 읽기 전용 뷰라 원본이 바뀌면 함께 바뀌고, List.copyOf는 독립된 불변 복사본입니다.

---

## 핵심 정리
- equals 재정의 ⇒ **hashCode도 반드시** (`Objects.hash`), HashMap 키는 불변
- 불변 객체: final 클래스 + private final 필드 + setter X + 방어적 복사(`List.copyOf`)
- record = 불변 DTO·값 객체, 엔티티에는 X
- 얕은 복사는 내부 공유, clone 대신 복사 생성자
