# 03. 예외 처리

> **학습 목표**
> - Error, Checked Exception, Unchecked Exception을 구분할 수 있다.
> - try-with-resources로 자원을 안전하게 닫을 수 있다.
> - 예외를 잡을지 던질지, 어떤 예외를 만들지 설계할 수 있다.
> - Spring 트랜잭션 롤백과 예외 종류의 관계를 설명할 수 있다.

---

## 1. 예외 계층

```
Throwable
├── Error                       ← JVM 수준의 심각한 문제, 잡지 않음
│     OutOfMemoryError, StackOverflowError
└── Exception
      ├── (Checked Exception)    ← 컴파일러가 처리(catch 또는 throws)를 강제
      │     IOException, SQLException, InterruptedException
      └── RuntimeException       ← Unchecked: 처리 강제 X
            NullPointerException, IllegalArgumentException, IllegalStateException,
            IndexOutOfBoundsException, ArithmeticException
```

| 구분 | Checked | Unchecked (RuntimeException) |
|---|---|---|
| 컴파일러 강제 | **O** (catch 또는 throws 필수) | X |
| 의미 | 호출자가 **복구할 수 있는** 상황 (파일 없음, 네트워크) | **프로그래밍 오류**, 복구 불가 (null, 잘못된 인자) |
| Spring 트랜잭션 기본 | **롤백 X** | **롤백 O** |
| 현대 Java·Spring 경향 | 줄이는 추세 | **대부분 Unchecked** |

> Spring은 JDBC의 Checked `SQLException`을 Unchecked `DataAccessException` 계층으로 변환해 줍니다. "처리할 수 없는 Checked 예외를 계속 throws로 전파"하는 문제를 없애기 위해서입니다.

## 2. try-catch-finally

```java
try {
    process();
} catch (IllegalArgumentException | IllegalStateException e) {   // 멀티 catch (Java 7+)
    log.warn("잘못된 요청: {}", e.getMessage());
} catch (Exception e) {                                           // 넓은 타입은 아래에
    log.error("처리 실패", e);
    throw e;
} finally {
    cleanup();                                                    // 예외 여부와 상관없이 실행
}
```

### finally의 함정
```java
try {
    return 1;
} finally {
    return 2;          // ❌ 2가 반환되고, try의 예외까지 삼켜 버림 → finally에서 return 금지
}
```

## 3. try-with-resources (Java 7+)

`AutoCloseable`을 구현한 자원을 **자동으로 닫습니다.**
```java
// ❌ 옛날 방식: close를 빠뜨리거나, close의 예외가 원래 예외를 덮어씀
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader(path));
    return br.readLine();
} finally {
    if (br != null) br.close();
}

// ✅ try-with-resources
try (BufferedReader br = Files.newBufferedReader(Path.of(path));
     PreparedStatement ps = conn.prepareStatement(sql)) {          // 여러 개 가능, 역순으로 닫힘
    return br.readLine();
}
```
- 본문의 예외와 close의 예외가 모두 나면, **본문 예외가 던져지고 close 예외는 `getSuppressed()`** 에 담김

## 4. 예외 처리 원칙

### ❌ 예외 삼키기
```java
try {
    pay();
} catch (Exception e) {
    // 아무것도 안 함 → 장애 원인을 영원히 모름
}

catch (Exception e) {
    e.printStackTrace();        // 표준 에러로만 출력 → 로그 시스템에 안 남음
}
```

### ✅ 원인(cause)을 포함해 변환
```java
try {
    externalPaymentClient.pay(req);
} catch (IOException e) {
    throw new PaymentFailedException("결제 서버 통신 실패 orderId=" + orderId, e);   // ★ e를 cause로
}
```
> cause를 빠뜨리면 원래 스택 트레이스가 사라져 근본 원인을 추적할 수 없습니다.

| 원칙 | 설명 |
|---|---|
| **처리할 수 있는 곳에서만 잡는다** | 잡아서 할 일이 없으면 던진다 |
| 로그는 한 번만 | 잡을 때마다 로그 + 다시 던지기 → 같은 에러가 여러 번 기록 |
| 구체적인 예외를 잡는다 | `catch (Exception)`은 최상위 경계(전역 핸들러)에서만 |
| 흐름 제어에 예외 쓰지 않기 | 예외는 비쌈(스택 트레이스 생성), 반복문 탈출용 X |
| 의미 있는 메시지 | 어떤 값으로 실패했는지 (`orderId=42`) — 단, 개인정보는 제외 |
| `InterruptedException`은 삼키지 않기 | 잡으면 `Thread.currentThread().interrupt()`로 상태 복원 |

## 5. 커스텀 예외 설계 (Spring 서비스)

```java
public enum ErrorCode {
    MEMBER_NOT_FOUND(HttpStatus.NOT_FOUND, "회원을 찾을 수 없습니다."),
    DUPLICATE_EMAIL(HttpStatus.CONFLICT, "이미 사용 중인 이메일입니다."),
    INSUFFICIENT_STOCK(HttpStatus.BAD_REQUEST, "재고가 부족합니다.");

    private final HttpStatus status;
    private final String message;

    ErrorCode(HttpStatus status, String message) { this.status = status; this.message = message; }
    public HttpStatus status() { return status; }
    public String message() { return message; }
}

public class BusinessException extends RuntimeException {     // Unchecked
    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.message());
        this.errorCode = errorCode;
    }
    public ErrorCode getErrorCode() { return errorCode; }
}
```
```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handle(BusinessException e) {
        ErrorCode code = e.getErrorCode();
        return ResponseEntity.status(code.status()).body(new ErrorResponse(code.name(), code.message()));
    }
}
```
> 비즈니스 예외는 **스택 트레이스가 필요 없는 경우**가 많습니다. 성능이 중요하면 `super(message, null, false, false)` 생성자로 스택 트레이스 생성을 끌 수 있습니다.

## 6. 예외와 트랜잭션 롤백 (Spring)

| 예외 | `@Transactional` 기본 동작 |
|---|---|
| `RuntimeException`, `Error` | **롤백** |
| Checked Exception | **커밋** (롤백 안 됨!) |

```java
@Transactional(rollbackFor = Exception.class)     // Checked도 롤백하려면
public void order() throws IOException { ... }
```
> 서비스 안에서 예외를 잡아서 삼키면 트랜잭션은 정상 커밋됩니다. 반대로 내부 `@Transactional` 메서드에서 예외가 나 롤백 마크가 찍힌 뒤 바깥에서 잡으면 `UnexpectedRollbackException`이 납니다. (→ Spring JPA 자료 `01.스프링핵심/06.트랜잭션.md`)

## 7. 면접 질문

1. **Checked와 Unchecked Exception의 차이는?**
   → Checked는 컴파일러가 처리를 강제하며 복구 가능한 상황에 쓰고, Unchecked는 RuntimeException 하위로 처리를 강제하지 않으며 주로 프로그래밍 오류를 나타냅니다. Spring 트랜잭션은 기본적으로 Unchecked에서만 롤백합니다.
2. **try-with-resources의 장점은?**
   → AutoCloseable 자원을 자동으로 닫아 누수를 막고, close 중 발생한 예외가 원래 예외를 덮지 않고 suppressed로 보존됩니다.
3. **예외를 다른 예외로 감쌀 때 주의할 점은?**
   → 원래 예외를 cause로 넘겨 스택 트레이스를 보존해야 근본 원인을 추적할 수 있습니다.
4. **Error는 왜 잡지 않나요?**
   → OutOfMemoryError처럼 JVM 수준의 심각한 문제라 애플리케이션이 정상적으로 복구할 수 없기 때문입니다.

---

## 핵심 정리
- Error(잡지 않음) / Checked(처리 강제, 복구 가능) / Unchecked(프로그래밍 오류, Spring 기본 롤백)
- 자원은 **try-with-resources**, finally에서 return 금지
- 예외 삼키지 않기, 변환 시 **cause 포함**, 로그는 한 번
- 비즈니스 예외는 RuntimeException + ErrorCode + 전역 핸들러
- Checked 예외는 기본 커밋 → `rollbackFor`
