## 1. HashMap 구조 (Java 8+)

```
table (Node<K,V>[], 길이는 항상 2의 거듭제곱, 기본 16)
[0] → null
[1] → Node(k1,v1) → Node(k9,v9)                  ← 충돌: 연결리스트 (체이닝)
[2] → TreeNode ... (레드블랙 트리)                 ← 한 버킷에 8개 이상 + 테이블 64 이상이면 트리화
[3] → Node(k3,v3)
...
```

### put(key, value) 과정
```
1. hash = key.hashCode() ^ (key.hashCode() >>> 16)    상위 16비트를 하위에 섞어 분포 개선
2. index = hash & (table.length - 1)                  % 대신 비트 AND (길이가 2의 거듭제곱이라 가능)
3. 버킷이 비었으면 새 노드
4. 있으면 순회하며 hash가 같고 equals가 true인 키를 찾음
     → 있으면 값 교체 (기존 값 반환)
     → 없으면 리스트 끝에 추가 (리스트 길이 ≥ 8 → 트리화 검토)
5. size > threshold(용량 × 0.75) 이면 resize
```

### get(key)
```
hash 계산 → 인덱스 → 버킷의 노드들 중 hash 같고 equals true인 것 반환
```
> 그래서 **hashCode가 잘 분산될수록 빠르고**, 모든 키가 같은 hashCode를 반환하면 한 버킷에 몰려 O(n)(트리화 후 O(log n))이 됩니다.

### 트리화 (Treeify)
| 조건 | 동작 |
|---|---|
| 한 버킷의 노드 수 **≥ 8** 이고 테이블 크기 **≥ 64** | 연결리스트 → **레드블랙 트리** (최악 O(n) → O(log n)) |
| 노드 수 ≥ 8 인데 테이블 < 64 | 트리화 대신 **resize** |
| 트리 노드 수 **≤ 6** | 다시 연결리스트로 |
> 해시 충돌을 일부러 일으키는 **HashDoS 공격**에 대한 방어이기도 합니다.

### 리사이즈 (Resize)
- 기본 용량 16, 부하율 0.75 → 원소가 **12개를 넘으면 32로** 2배 확장
- 모든 노드를 새 테이블로 재배치 → **O(n) 비용**
- Java 8은 재배치 시 각 노드가 `원래 인덱스` 또는 `원래 인덱스 + 이전 용량` 둘 중 하나로만 가서 효율적

```java
// 크기를 미리 알면 초기 용량 지정 → 리사이즈 방지
Map<String, Integer> map = new HashMap<>(expectedSize * 4 / 3 + 1);
Map<String, Integer> map2 = HashMap.newHashMap(expectedSize);    // Java 19+
```

### 그 밖의 특징
- **null 키 1개 허용** (해시 0번 버킷), null 값 허용
- **순서 보장 X** (리사이즈 후 순서가 바뀔 수 있음)
- **스레드 안전 X**: 여러 스레드가 동시에 put하면 데이터 유실, (Java 7까지는 리사이즈 중 무한 루프)

## 2. HashSet

**내부적으로 HashMap을 사용**합니다. 원소를 키로, 값은 공용 더미 객체를 넣습니다.
```java
// HashSet 내부 (요약)
private transient HashMap<E, Object> map;
private static final Object PRESENT = new Object();
public boolean add(E e) { return map.put(e, PRESENT) == null; }
```
→ 원소 클래스는 **equals와 hashCode를 올바르게** 구현해야 합니다.

## 3. LinkedHashMap

HashMap + **모든 엔트리를 잇는 이중 연결리스트**
- 기본: **삽입 순서** 유지
- `accessOrder = true`: **접근 순서** (get할 때마다 맨 뒤로) → **LRU 캐시**

```java
public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LruCache(int capacity) {
        super(16, 0.75f, true);              // accessOrder = true
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;            // 넘치면 가장 오래 사용 안 한 항목 제거
    }
}
```
> 실무 캐시는 만료 시간·통계·동시성까지 지원하는 **Caffeine** 라이브러리를 씁니다 (Spring Cache 로컬 캐시 기본 선택지).

## 4. TreeMap / TreeSet

**레드블랙 트리** (균형 이진 탐색 트리)
- 키가 **정렬된 상태**로 유지, 모든 연산 **O(log n)**
- 키는 `Comparable`이거나 생성 시 `Comparator` 제공
- **equals가 아니라 compareTo(compare) 결과로 같은 키를 판단** → compareTo가 0이면 같은 키로 취급

```java
TreeMap<Integer, String> scores = new TreeMap<>(Map.of(60, "D", 70, "C", 80, "B", 90, "A"));
scores.floorEntry(85).getValue();      // "B"  (85 이하 중 가장 큰 키)
scores.ceilingKey(75);                 // 80
scores.headMap(80);                    // {60=D, 70=C}  (80 미만)
scores.tailMap(80, true);              // {80=B, 90=A}
scores.firstKey();  scores.lastEntry();  scores.descendingMap();
```
> 점수 구간 → 등급, 시간대별 요금, 가장 가까운 예약 시간 찾기 같은 **범위 질의**에 유용합니다.

## 5. 스레드 안전한 Map

| 구현 | 동기화 방식 | 성능 | 비고 |
|---|---|---|---|
| `Hashtable` | **모든 메서드 synchronized** (맵 전체 락) | 낮음 | 레거시, null 불허 |
| `Collections.synchronizedMap(map)` | 래퍼가 전체 락 | 낮음 | 순회 시 직접 동기화 필요 |
| **`ConcurrentHashMap`** | **버킷 단위** CAS + synchronized | **높음** | **권장**, null 불허 |

### ConcurrentHashMap (Java 8+)
```
- 빈 버킷에 넣을 때: CAS(Compare-And-Swap)로 락 없이
- 버킷에 노드가 있으면: 그 버킷의 첫 노드에만 synchronized
- 읽기(get): 락 없음 (volatile 읽기)
- 리사이즈: 여러 스레드가 나눠서 도움
→ 서로 다른 버킷에 쓰는 스레드는 서로 막지 않음
```
> Java 7까지는 테이블을 여러 **세그먼트**로 나눠 세그먼트별로 락을 걸었습니다. Java 8부터 버킷 단위로 더 세밀해졌습니다.

### 복합 연산은 원자적 메서드로
```java
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();

// ❌ 경쟁 상태: get과 put 사이에 다른 스레드가 끼어듦
Integer old = counts.get(key);
counts.put(key, old == null ? 1 : old + 1);

// ✅ 원자적
counts.merge(key, 1, Integer::sum);
counts.compute(key, (k, v) -> v == null ? 1 : v + 1);
counts.computeIfAbsent(key, k -> loadFromDb(k));

// 고빈도 카운터
ConcurrentHashMap<String, LongAdder> adders = new ConcurrentHashMap<>();
adders.computeIfAbsent(key, k -> new LongAdder()).increment();
```
> `ConcurrentHashMap`의 각 메서드는 스레드 안전하지만, **여러 메서드를 조합한 로직은 원자적이지 않습니다.** `computeIfAbsent`의 함수 안에서 같은 맵을 수정하면 안 됩니다(데드락·예외).

### null을 허용하지 않는 이유
`map.get(key)`가 null이면 "키가 없음"인지 "값이 null"인지 구분할 수 없고, 멀티스레드에서는 `containsKey`로 확인한 뒤 get하는 사이에 상태가 바뀔 수 있어 모호함을 없애기 위해서입니다.

## 6. 면접 질문

1. **HashMap의 동작 원리는?**
   → 키의 hashCode를 섞어 배열 인덱스를 구하고 해당 버킷에 저장하며, 충돌 시 연결리스트로 잇고, 한 버킷이 8개 이상이고 테이블이 64 이상이면 레드블랙 트리로 바꿉니다. 원소 수가 용량의 75%를 넘으면 2배로 리사이즈합니다.
2. **HashMap 용량이 2의 거듭제곱인 이유는?**
   → 나머지 연산 대신 `hash & (n-1)` 비트 연산으로 인덱스를 빠르게 구하고, 리사이즈 시 노드를 효율적으로 재배치하기 위해서입니다.
3. **ConcurrentHashMap이 Hashtable보다 빠른 이유는?**
   → Hashtable은 모든 연산에 맵 전체 락을 걸지만, ConcurrentHashMap은 CAS와 버킷 단위 동기화를 쓰고 읽기에는 락을 걸지 않아 서로 다른 버킷 작업이 동시에 진행되기 때문입니다.
4. **LinkedHashMap으로 LRU 캐시를 만드는 방법은?**
   → accessOrder를 true로 생성해 접근할 때마다 순서를 갱신하고, removeEldestEntry를 오버라이드해 용량을 넘으면 가장 오래된 항목을 제거합니다.

## 핵심 정리
- HashMap: `hash ^ (hash>>>16)` → `& (n-1)` → 체이닝 → **8개·64 이상 트리화**, 0.75 넘으면 2배 리사이즈
- HashSet = HashMap의 키, equals·hashCode 필수
- LinkedHashMap: 삽입/접근 순서, `accessOrder + removeEldestEntry` = LRU
- TreeMap: 레드블랙 트리, 정렬·범위 질의, compareTo로 키 동일성 판단
- ConcurrentHashMap: CAS + 버킷 락, 읽기 무락, null 불허, 복합 연산은 `merge/compute`
