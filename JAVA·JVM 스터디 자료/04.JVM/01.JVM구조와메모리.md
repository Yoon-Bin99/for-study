# 01. JVM 구조와 런타임 데이터 영역

> **학습 목표**
> - JDK, JRE, JVM의 관계와 자바 프로그램의 실행 과정을 설명할 수 있다.
> - JVM의 구성 요소(클래스 로더, 런타임 데이터 영역, 실행 엔진)를 그릴 수 있다.
> - Heap, Stack, Metaspace 등 메모리 영역에 무엇이 저장되는지 설명할 수 있다.
> - 스레드별 영역과 공유 영역을 구분하고, 각 영역의 OOM·StackOverflow 원인을 설명할 수 있다.

---

## 1. JDK, JRE, JVM

```
+─────────────────── JDK (개발 도구) ────────────────────+
|  javac, jar, jshell, jcmd, jstack, jmap, jfr ...       |
|  +─────────────── JRE (실행 환경) ─────────────────+    |
|  |  표준 라이브러리 (java.lang, java.util ...)        |    |
|  |  +──────────── JVM (가상 머신) ─────────────+    |    |
|  |  |  클래스 로더, 메모리 관리(GC), 실행 엔진(JIT) |    |    |
|  |  +─────────────────────────────────────────+    |    |
|  +───────────────────────────────────────────────+    |
+───────────────────────────────────────────────────────+
```
> Java 11부터 별도 JRE 배포는 없어졌습니다. 운영 이미지는 `eclipse-temurin:21-jre`처럼 JRE만 담은 이미지를 쓰거나 `jlink`로 필요한 모듈만 담은 런타임을 만듭니다.

### 실행 과정
```
Hello.java ──javac──> Hello.class (바이트코드, OS 독립)
                          ↓  java Hello
                    [JVM: 클래스 로더] 로딩 → 링크(검증·준비·해석) → 초기화
                          ↓
                    [실행 엔진] 인터프리터로 실행 + 자주 실행되는 코드는 JIT가 기계어로 컴파일
                          ↓
                    OS / 하드웨어
```
→ **"Write Once, Run Anywhere"**: 바이트코드는 같고, OS마다 JVM이 다릅니다.

## 2. JVM 구성

```
+──────────────────────────── JVM ─────────────────────────────+
|  [클래스 로더 서브시스템]  .class → 메모리에 로딩                    |
|                                                              |
|  [런타임 데이터 영역]                                            |
|   공유 (모든 스레드)              스레드별                         |
|   +──────────────+            +─────────+ +─────────+         |
|   | Heap         |            | Stack   | | Stack   | ...     |
|   |  (객체, 배열)  |            | PC      | | PC      |         |
|   +──────────────+            | Native  | | Native  |         |
|   | Metaspace    |            | Stack   | | Stack   |         |
|   | (클래스 정보)  |            +─────────+ +─────────+         |
|   +──────────────+             스레드 1     스레드 2             |
|                                                              |
|  [실행 엔진]  인터프리터 / JIT 컴파일러 / GC                        |
|  [JNI] ↔ 네이티브 라이브러리                                      |
+──────────────────────────────────────────────────────────────+
```

## 3. 런타임 데이터 영역

| 영역 | 공유 | 저장 내용 | 오류 |
|---|---|---|---|
| **PC Register** | 스레드별 | 현재 실행 중인 바이트코드 명령 주소 | - |
| **JVM Stack** | 스레드별 | **스택 프레임**: 지역 변수, 매개변수, 연산 중간값, 복귀 주소 | `StackOverflowError` (깊은 재귀), `OutOfMemoryError` (스레드 생성 시 메모리 부족) |
| Native Method Stack | 스레드별 | JNI 네이티브 메서드 호출 | |
| **Heap** | **공유** | **`new`로 만든 모든 객체와 배열**, String Pool | `OutOfMemoryError: Java heap space` |
| **Metaspace** (Method Area) | **공유** | **클래스 메타데이터**: 클래스 구조, 메서드 바이트코드, 런타임 상수 풀 (static 변수 값은 Java 8부터 Heap의 Class 객체에 저장) | `OutOfMemoryError: Metaspace` |

### Stack과 Heap 예시
```java
public void order() {
    int quantity = 3;                        // Stack: 기본형 값
    Member member = new Member("kim");       // Stack: 참조(주소) / Heap: Member 객체
    process(member, quantity);               // 새 스택 프레임이 쌓임
}                                            // 메서드 종료 → 프레임 제거 (member 참조 사라짐)
                                             // Heap의 Member는 아무도 참조하지 않으면 GC 대상
```
```
Stack (스레드 1)                    Heap
+────────────────────────+        +──────────────────+
| process() 프레임         |        | Member("kim")    | ← GC가 관리
|   m = 0x10, q = 3      | ──┐    +──────────────────+
+────────────────────────+   ├──> |                  |
| order() 프레임           |   │    +──────────────────+
|   quantity = 3          |   │
|   member = 0x10         | ──┘
+────────────────────────+
```

### PermGen → Metaspace (Java 8)
| | PermGen (~Java 7) | **Metaspace (Java 8+)** |
|---|---|---|
| 위치 | **Heap 안** 고정 크기 | **네이티브 메모리** (OS가 관리하는 메모리) |
| 크기 | `-XX:MaxPermSize`로 고정 → OOM 잦음 | 기본적으로 **자동 확장** (`-XX:MaxMetaspaceSize`로 제한 가능) |
| String Pool | PermGen (Java 6) → Heap (Java 7+) | Heap |

> Metaspace OOM은 주로 **클래스를 계속 동적으로 생성**할 때(프록시·리플렉션·스크립트 엔진 남용, 핫 리로드 반복, 클래스로더 누수) 발생합니다.

## 4. 스레드와 메모리

- 스레드 하나마다 **Stack(기본 512KB~1MB)** 을 가짐 → `-Xss`로 조절
- 플랫폼 스레드 1000개 ≈ 스택만 수백 MB~1GB
- **가상 스레드**는 스택을 Heap에 필요한 만큼만 저장해 훨씬 가벼움

### JVM이 쓰는 메모리 = Heap만이 아니다
```
컨테이너 메모리 제한 1GB
  = Heap (-Xmx)
  + Metaspace
  + 스레드 스택 × 스레드 수
  + Code Cache (JIT 컴파일된 코드)
  + Direct Buffer (NIO, Netty)
  + GC 자체 자료구조, JVM 내부
```
> 그래서 컨테이너 메모리 제한을 1GB로 주고 `-Xmx1g`를 주면 **컨테이너가 OOM Kill(137)** 됩니다. 컨테이너에서는 `-XX:MaxRAMPercentage=75` 정도로 힙을 비율로 지정합니다. (→ 인프라 자료 `03.도커/02.도커이미지와Dockerfile.md`)

## 5. 주요 JVM 메모리 옵션

| 옵션 | 의미 |
|---|---|
| `-Xms512m` / `-Xmx512m` | 힙 초기 / 최대 크기 (서버는 같게 두어 확장·축소 비용 제거) |
| `-XX:MaxRAMPercentage=75.0` | 컨테이너·머신 메모리 대비 최대 힙 비율 |
| `-Xss512k` | 스레드 스택 크기 |
| `-XX:MaxMetaspaceSize=256m` | Metaspace 상한 |
| `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps` | OOM 시 **힙 덤프 자동 생성** (운영 필수) |

## 6. 면접 질문

1. **JVM 메모리 구조를 설명해 주세요.**
   → 모든 스레드가 공유하는 Heap(객체·배열)과 Metaspace(클래스 메타데이터), 스레드마다 생기는 JVM Stack(스택 프레임: 지역 변수·매개변수), PC Register, Native Method Stack으로 나뉩니다.
2. **Stack과 Heap의 차이는?**
   → Stack은 스레드별로 메서드 호출 프레임과 지역 변수를 저장하고 메서드가 끝나면 자동 해제되며, Heap은 모든 스레드가 공유하는 객체 저장 공간으로 GC가 관리합니다.
3. **PermGen이 Metaspace로 바뀐 이유는?**
   → 고정 크기 PermGen에서 클래스 메타데이터 때문에 OOM이 자주 발생해, 네이티브 메모리를 쓰고 자동 확장되는 Metaspace로 바뀌었습니다.
4. **StackOverflowError와 OutOfMemoryError의 차이는?**
   → StackOverflowError는 재귀가 너무 깊어 스레드 스택이 넘친 것이고, OutOfMemoryError는 Heap·Metaspace 등에서 더 이상 메모리를 할당할 수 없을 때 발생합니다.

## 핵심 정리
- JDK ⊃ JRE ⊃ JVM, .java → javac → .class(바이트코드) → JVM(클래스 로더 → 실행 엔진)
- 공유: **Heap**(객체), **Metaspace**(클래스 정보, 네이티브 메모리) / 스레드별: **Stack**, PC, Native Stack
- StackOverflowError(깊은 재귀) vs OOM(heap space / Metaspace)
- JVM 메모리 = Heap + 비힙 → 컨테이너는 `MaxRAMPercentage`, OOM 시 힙 덤프 옵션
