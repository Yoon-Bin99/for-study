# 02. 가비지 컬렉션 (GC)

> **학습 목표**
> - GC가 "쓰레기"를 판단하는 기준(Reachability, GC Root)을 설명할 수 있다.
> - Mark-Sweep-Compact, 세대별 가설과 Young/Old 영역의 동작을 설명할 수 있다.
> - Stop-The-World와 GC 종류(Serial, Parallel, G1, ZGC, Shenandoah)를 비교할 수 있다.
> - GC 로그를 켜고, 메모리 누수의 흔한 원인을 설명할 수 있다.

---

## 1. GC란?

**더 이상 사용되지 않는 객체의 메모리를 자동으로 회수**하는 JVM 기능입니다. C/C++의 `free()`를 직접 하지 않아도 되지만, GC가 도는 동안 애플리케이션이 **멈출 수 있습니다**.

### 무엇이 쓰레기인가: Reachability
**GC Root에서 참조를 따라 도달할 수 없는 객체**가 수거 대상입니다.
```
GC Root
 ├─ 스택의 지역 변수·매개변수 (실행 중인 메서드)
 ├─ static 변수
 ├─ 활성 스레드
 └─ JNI 참조
      │
      ↓ 참조
   [A] → [B] → [C]        ← 도달 가능 (살아 있음)
   [D] ⇄ [E]               ← 서로 참조해도 Root에서 못 가면 → 쓰레기 (순환 참조도 수거)
```
> 참조 카운팅이 아니라 **도달 가능성**으로 판단하기 때문에 순환 참조도 문제없이 수거됩니다.

---

## 2. 기본 알고리즘

| 단계 | 동작 |
|---|---|
| **Mark** | GC Root부터 따라가며 살아 있는 객체 표시 |
| **Sweep** | 표시되지 않은 객체 메모리 해제 |
| **Compact** | 살아남은 객체를 한쪽으로 모아 **단편화 제거** (큰 객체 할당 가능하게) |
| Copy | 살아 있는 객체만 다른 영역으로 복사 (Young 영역에서 사용) |

### Stop-The-World (STW)
GC를 수행하기 위해 **애플리케이션 스레드를 모두 멈추는 것**입니다. GC 튜닝의 목표는 대부분 **STW 시간을 줄이는 것**입니다.
- 요청 처리 중 수백 ms~수 초 멈추면 → API 응답 지연, 타임아웃, 헬스 체크 실패

---

## 3. 세대별 GC (Generational GC)

### 약한 세대 가설 (Weak Generational Hypothesis)
1. **대부분의 객체는 금방 쓰레기가 된다** (요청 처리 중 만든 DTO, 임시 객체)
2. 오래된 객체가 새 객체를 참조하는 경우는 드물다

→ 힙을 **Young과 Old로 나누고**, 자주 비는 Young만 자주 청소합니다.

```
Heap
+──────────────────── Young Generation ────────────────────+──────── Old Generation ────────+
|  Eden                    | Survivor 0 | Survivor 1        |  오래 살아남은 객체               |
|  (새 객체 할당)            |   (S0)     |   (S1)            |                               |
+──────────────────────────+────────────+───────────────────+───────────────────────────────+
     Minor GC: 자주, 빠름                                       Major / Full GC: 드물게, 느림
```

### 객체의 일생
```
1. new → Eden에 할당
2. Eden이 가득 참 → Minor GC
   살아 있는 객체를 Survivor(S0)로 복사, 나이(age) +1, Eden 비움
3. 다음 Minor GC: Eden + S0의 생존 객체 → S1로 복사 (S0 비움) — 두 Survivor를 번갈아 사용
4. 나이가 임계값(기본 최대 15)을 넘으면 → Old로 승격 (Promotion)
5. Old가 가득 차면 → Major GC / Full GC (오래 걸림)
```

| GC | 대상 | 빈도 | 시간 |
|---|---|---|---|
| **Minor GC** | Young | 자주 | 짧음 (살아 있는 객체만 복사) |
| Major GC | Old | 드묾 | 김 |
| **Full GC** | Heap 전체 (+ Metaspace) | 드묾 | **가장 김** — 반복되면 장애 신호 |

> 큰 객체(배열 등)는 Eden을 건너뛰고 바로 Old에 할당되기도 합니다 (G1에서는 Humongous 영역).

## 4. GC 종류

| GC | 특징 | STW | 적합 |
|---|---|---|---|
| Serial | 싱글 스레드 | 김 | 아주 작은 힙, 단일 코어 |
| Parallel | Young·Old를 **멀티스레드**로, **처리량 우선** | 중간~김 | 배치 (응답 시간보다 총 처리량) |
| CMS | Old를 동시에 처리 | 짧음 | **Java 14에서 제거** |
| **G1** (Garbage First) | 힙을 **Region**(1~32MB)으로 나눠 쓰레기가 많은 Region부터 수거, **목표 정지 시간** 설정 | 짧음 (기본 목표 200ms) | **Java 9+ 기본**, 대부분의 서버 |
| **ZGC** | 거의 모든 작업을 **애플리케이션과 동시에**, 정지 시간 **1ms 미만** 목표, 수 TB 힙 | 매우 짧음 | 큰 힙, **지연 시간 민감** 서비스 |
| Shenandoah | ZGC와 비슷한 저지연 (Red Hat) | 매우 짧음 | 저지연 |

### G1 구조
```
+---+---+---+---+---+---+---+---+
| E | E | S | O | O | H | E |   |     E: Eden, S: Survivor, O: Old, H: Humongous(큰 객체)
+---+---+---+---+---+---+---+---+     Region 역할이 고정되지 않고 필요에 따라 바뀜
| O |   | E | O | E |   | O | S |
+---+---+---+---+---+---+---+---+
→ 정지 시간 목표(-XX:MaxGCPauseMillis=200) 안에서 쓰레기가 많은 Region부터(Garbage First) 수거
```

### ZGC
- 컬러 포인터와 로드 배리어로 **객체 이동(압축)까지 동시 수행**
- Java 21에서 **세대별(Generational) ZGC** 추가, 23부터 기본 모드
- 정지 시간이 힙 크기와 거의 무관

```bash
java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -jar app.jar   # 기본값이므로 생략 가능
java -XX:+UseZGC -jar app.jar
java -XX:+UseParallelGC -jar batch.jar
```
> 대부분은 **기본값(G1)으로 충분**합니다. 응답 시간 p99가 GC 때문에 튄다면 ZGC를 검토하고, 반드시 부하 테스트로 비교하세요.

## 5. GC 로그와 모니터링

```bash
# Java 9+ 통합 로깅
java -Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m -jar app.jar
```
```
[2026-11-09T10:00:00.123+0900][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 512M->128M(1024M) 8.512ms
                                              ↑ 종류                                  ↑ 전→후(전체)    ↑ 정지 시간
```

| 볼 지표 | 위험 신호 |
|---|---|
| GC 정지 시간 | p99가 수백 ms 이상 |
| GC 빈도 | Minor GC가 초당 여러 번 → 객체를 너무 많이 생성 |
| **Full GC 발생** | 반복되면 **메모리 누수나 힙 부족** |
| GC 후 Old 사용량 | GC 후에도 계속 증가하는 **톱니 모양 우상향** → 누수 |

- 도구: **GCeasy**(로그 분석), JDK Mission Control + **JFR**, Grafana(Micrometer `jvm.gc.pause`)

## 6. 메모리 누수 (Memory Leak)

GC가 있어도 **참조가 남아 있으면 수거되지 않습니다.** 자바의 메모리 누수는 "필요 없는데 참조가 남아 있는 것"입니다.

| 원인 | 예 | 해결 |
|---|---|---|
| **static 컬렉션에 계속 추가** | `static Map<Long, Data> cache`에 넣기만 하고 지우지 않음 | 크기 제한·만료가 있는 캐시(Caffeine) |
| **ThreadLocal 미정리** | 스레드 풀 스레드에 값이 계속 남음 | `finally { threadLocal.remove(); }` |
| 리스너·콜백 미해제 | 등록만 하고 해제 X | 해제, 약한 참조 |
| 닫지 않은 자원 | Connection, Stream | try-with-resources |
| 잘못된 equals/hashCode인 Map 키 | 같은 키가 중복으로 계속 쌓임 | 올바른 구현 |
| 큰 컬렉션을 한 번에 로딩 | `findAll()`로 수백만 건 | 페이징, 스트리밍 |

### 참조 종류
| 참조 | GC 동작 | 용도 |
|---|---|---|
| Strong (일반) | 도달 가능하면 수거 X | 기본 |
| `SoftReference` | **메모리가 부족할 때** 수거 | 메모리 민감 캐시 |
| `WeakReference` | **다음 GC 때** 수거 | `WeakHashMap`, 리스너 |
| `PhantomReference` | 수거 후 정리 작업 알림 | `Cleaner` (자원 정리) |

> `finalize()`는 실행 시점이 보장되지 않고 성능에 나빠 **deprecated**되었습니다. 자원 정리는 try-with-resources나 `Cleaner`를 씁니다.

## 7. GC 부담을 줄이는 코드 습관

- 반복문 안에서 불필요한 객체 생성 줄이기 (문자열 `+=`, 박싱)
- 큰 데이터는 **한 번에 메모리에 올리지 않기** (페이징, 청크, 스트리밍)
- 캐시는 **크기·만료 제한**
- `System.gc()` 호출하지 않기 (Full GC 유발 가능)

## 8. 면접 질문

1. **GC는 어떤 객체를 수거하나요?**
   → 스택의 지역 변수, static 변수 같은 GC Root에서 참조를 따라 도달할 수 없는 객체를 수거하며, 순환 참조도 Root에서 도달할 수 없으면 수거됩니다.
2. **Young과 Old 영역을 나누는 이유는?**
   → 대부분의 객체가 금방 쓰레기가 된다는 약한 세대 가설에 따라, 자주 비는 Young 영역만 자주 짧게 청소하고 오래 살아남은 객체는 Old에 모아 드물게 청소해 효율을 높이기 위해서입니다.
3. **Stop-The-World란?**
   → GC를 수행하기 위해 애플리케이션 스레드가 모두 멈추는 것으로, GC 튜닝은 주로 이 시간을 줄이는 것을 목표로 합니다.
4. **G1 GC와 ZGC의 차이는?**
   → G1은 힙을 Region으로 나눠 목표 정지 시간 안에서 쓰레기가 많은 영역부터 수거하는 Java 9+ 기본 GC이고, ZGC는 객체 이동까지 동시에 수행해 정지 시간을 1ms 미만으로 유지하는 저지연 GC입니다.
5. **자바에서도 메모리 누수가 생기나요?**
   → 생깁니다. static 컬렉션에 계속 쌓이거나 ThreadLocal을 정리하지 않는 등 필요 없는 객체에 대한 참조가 남아 있으면 GC가 수거하지 못합니다.

---

## 핵심 정리
- GC 대상 = **GC Root에서 도달 불가능**한 객체 (순환 참조 OK)
- Mark → Sweep → Compact, **STW** 줄이기가 핵심
- 세대별: Eden → Survivor(S0↔S1, age) → Old, Minor GC(빠름) vs Full GC(느림, 반복 시 위험)
- **G1(기본, Region, 목표 정지 시간)**, ZGC(1ms 미만, 21+ 세대별), Parallel(처리량), CMS 제거
- GC 로그 `-Xlog:gc*`, 누수: static 컬렉션·ThreadLocal·미해제 자원
