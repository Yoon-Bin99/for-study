# 03. 클래스 로딩과 JIT 컴파일

> **학습 목표**
> - 클래스 로딩 과정(로딩 → 링크 → 초기화)과 클래스가 로딩되는 시점을 설명할 수 있다.
> - 클래스 로더 계층과 부모 위임 모델을 설명할 수 있다.
> - 인터프리터와 JIT 컴파일러의 역할, 계층형 컴파일, 워밍업을 설명할 수 있다.
> - JVM 시작 속도를 개선하는 방법(CDS, AOT, 네이티브 이미지)을 안다.

---

## 1. 클래스 로딩 과정

```
[로딩 Loading]       .class 파일을 읽어 Metaspace에 클래스 정보 저장, Heap에 Class 객체 생성
      ↓
[링크 Linking]
   ├ 검증 Verify     바이트코드가 올바르고 안전한지 확인
   ├ 준비 Prepare    static 변수 메모리 할당 + 기본값(0, null)으로 초기화
   └ 해석 Resolve    심볼릭 참조(이름)를 실제 메모리 참조로 (필요할 때 지연 해석)
      ↓
[초기화 Initialization]  static 변수에 실제 값 대입, static 블록 실행 (<clinit>)
```

### 클래스는 언제 로딩·초기화되나? (지연 로딩)
JVM은 시작할 때 모든 클래스를 올리지 않고 **처음 사용될 때** 초기화합니다.
| 초기화되는 경우 | 되지 않는 경우 |
|---|---|
| `new`로 인스턴스 생성 | 클래스 참조만 (`Member.class`) |
| static 메서드 호출 | `static final` 컴파일 타임 상수 사용 (값이 인라인됨) |
| static 필드 사용 (상수 제외) | 배열 선언 `new Member[10]` |
| 하위 클래스 초기화 (부모 먼저) | |
| 리플렉션 `Class.forName("...")` | |

### 이를 이용한 싱글톤 (Holder 패턴)
```java
public class Config {
    private Config() {}
    private static class Holder {                // Config.getInstance()를 처음 호출할 때 Holder 초기화
        static final Config INSTANCE = new Config();
    }
    public static Config getInstance() { return Holder.INSTANCE; }
}
```
→ **클래스 초기화는 JVM이 스레드 안전하게 한 번만** 수행하므로 동기화 없이 지연 초기화 + 스레드 안전

## 2. 클래스 로더 계층과 부모 위임 모델

```
[Bootstrap ClassLoader]     JVM 내장 (C++), java.base (java.lang, java.util ...)
        ↑ 부모
[Platform ClassLoader]      java.sql 등 플랫폼 모듈   (Java 8까지 Extension ClassLoader)
        ↑ 부모
[Application (System) ClassLoader]   클래스패스의 애플리케이션 클래스, 라이브러리
        ↑ 부모
[사용자 정의 ClassLoader]    톰캣 웹앱 로더, Spring Boot LaunchedClassLoader, 플러그인
```

### 부모 위임 (Parent Delegation)
```
"com.example.Member를 로딩해 줘"
 1. Application 로더 → 먼저 부모(Platform)에게 위임
 2. Platform → 부모(Bootstrap)에게 위임
 3. Bootstrap: 없음 → Platform: 없음 → Application: 클래스패스에서 찾아 로딩
```
| 이유 | 설명 |
|---|---|
| **보안** | 누가 `java.lang.String`을 직접 만들어도 Bootstrap의 진짜 String이 먼저 로딩됨 |
| 중복 방지 | 같은 클래스가 여러 번 로딩되지 않음 |

> **같은 이름의 클래스라도 로더가 다르면 다른 클래스**입니다. 그래서 Spring DevTools 재시작 후 `ClassCastException: Member cannot be cast to Member` 같은 이상한 에러가 날 수 있습니다.

### Spring Boot 실행 가능한 jar
```
app.jar
├── META-INF/MANIFEST.MF     Main-Class: org.springframework.boot.loader.launch.JarLauncher
├── BOOT-INF/classes/        우리 코드
└── BOOT-INF/lib/            의존성 jar들 (jar 안의 jar)
```
→ 표준 클래스 로더는 jar 안의 jar를 읽지 못하므로 **Spring Boot의 전용 로더**가 이를 처리합니다.

## 3. 실행 엔진: 인터프리터와 JIT

| 방식 | 동작 | 장단점 |
|---|---|---|
| **인터프리터** | 바이트코드를 **한 줄씩 해석**해 실행 | 시작 빠름, 반복 실행 시 느림 |
| **JIT 컴파일러** (Just-In-Time) | **자주 실행되는 코드(Hot Spot)** 를 실행 중에 **기계어로 컴파일**해 캐시(Code Cache) | 컴파일 비용이 있지만 이후 매우 빠름 |

> HotSpot JVM이라는 이름 자체가 "핫 스팟을 찾아 컴파일한다"는 뜻입니다.

### 계층형 컴파일 (Tiered Compilation)
```
Level 0: 인터프리터          — 실행 횟수·분기 통계 수집
Level 1~3: C1 컴파일러       — 빠르게 컴파일, 가벼운 최적화 (+ 프로파일링)
Level 4: C2 컴파일러         — 수집된 프로파일로 공격적 최적화 (오래 걸리지만 매우 빠른 코드)
```

### JIT의 최적화
| 최적화 | 설명 |
|---|---|
| **메서드 인라이닝** | 작은 메서드 호출을 호출 위치에 펼쳐 넣음 (getter 호출 비용 0) |
| 탈출 분석 (Escape Analysis) | 메서드 밖으로 나가지 않는 객체는 **Heap 할당을 생략**(스칼라 치환) |
| 루프 최적화 | 루프 펼치기, 범위 검사 제거 |
| 락 제거 | 다른 스레드와 공유되지 않는 객체의 synchronized 제거 |
| 역최적화 (Deoptimization) | 가정이 깨지면(새 하위 클래스 로딩 등) 다시 인터프리터로 |

### 워밍업 (Warm-up)
JVM 애플리케이션은 **시작 직후에는 느리고**, 코드가 JIT 컴파일되면서 빨라집니다.
- 배포 직후 새 인스턴스에 트래픽이 몰리면 응답 지연·타임아웃
- 대응: readiness probe 통과 전 **워밍업 요청**, 로드밸런서 **슬로 스타트**(점진적 트래픽 증가), 성능 테스트는 워밍업 후 측정 (**JMH** 사용)

## 4. 시작 속도와 메모리 개선

| 기술 | 설명 |
|---|---|
| **CDS / AppCDS** (Class Data Sharing) | 로딩·검증된 클래스 정보를 파일로 저장해 다음 시작 때 재사용 → 시작 시간 단축 (Spring Boot 3.3+ 지원) |
| **AOT 캐시** (Java 24~25, Project Leyden) | 클래스 로딩·링크 결과와 메서드 프로파일까지 미리 저장해 시작·워밍업 단축 (`-XX:AOTCache`) |
| **GraalVM 네이티브 이미지** | 빌드 시 **기계어 실행 파일**로 미리 컴파일 → 시작 수십 ms, 메모리 적음 / 빌드 느림, 리플렉션 제약, 최대 처리량은 JIT보다 낮을 수 있음 (Spring Boot AOT + `nativeCompile`) |
| CRaC (Coordinated Restore at Checkpoint) | 워밍업된 JVM 상태를 스냅숏으로 저장했다가 복원 |

> 서버리스(Lambda)나 빠른 스케일 아웃이 중요하면 네이티브 이미지·SnapStart를, 오래 실행되는 일반 API 서버는 JIT(일반 JVM)가 유리한 경우가 많습니다.

## 5. 면접 질문

1. **클래스 로딩 과정은?**
   → 클래스 파일을 읽어 메모리에 올리는 로딩, 바이트코드 검증·static 변수 기본값 할당·참조 해석을 하는 링크, static 변수에 값을 넣고 static 블록을 실행하는 초기화 순서로 진행되며, 클래스가 처음 사용될 때 지연 로딩됩니다.
2. **부모 위임 모델이란? 왜 필요한가요?**
   → 클래스 로더가 클래스를 직접 찾기 전에 부모 로더에게 먼저 위임하는 방식으로, 핵심 클래스를 사용자 클래스가 대체하지 못하게 해 보안을 지키고 중복 로딩을 막습니다.
3. **JIT 컴파일러란?**
   → 실행 중 자주 호출되는 코드를 감지해 기계어로 컴파일하고 캐싱하는 컴파일러로, 인터프리터보다 빠른 실행을 제공하며 인라이닝·탈출 분석 같은 최적화를 합니다.
4. **JVM 애플리케이션이 시작 직후 느린 이유는?**
   → 처음에는 인터프리터로 실행되다가 실행 통계가 쌓인 뒤 JIT 컴파일이 진행되기 때문에, 핫 코드가 컴파일되기 전까지 느립니다.

---

## 핵심 정리
- 로딩 → 링크(검증·준비·해석) → 초기화, **처음 사용 시 지연 로딩** (Holder 싱글톤)
- 로더 계층 Bootstrap → Platform → Application, **부모 위임**(보안·중복 방지), 로더가 다르면 다른 클래스
- 인터프리터 + JIT(C1 → C2 계층형), 인라이닝·탈출 분석, **워밍업** 필요
- 시작 개선: CDS, AOT 캐시(24~25), GraalVM 네이티브 이미지
