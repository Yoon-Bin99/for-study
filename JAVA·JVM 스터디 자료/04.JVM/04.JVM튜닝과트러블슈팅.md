# 04. JVM 모니터링과 트러블슈팅

> **학습 목표**
> - OutOfMemoryError의 종류와 원인을 구분할 수 있다.
> - 힙 덤프와 스레드 덤프를 생성하고 분석할 수 있다.
> - CPU 100%, 응답 지연, 데드락 상황을 진단할 수 있다.
> - jcmd, jstat, JFR, Actuator 등 도구를 사용할 수 있다.

---

## 1. 도구 모음

| 도구 | 용도 |
|---|---|
| **`jcmd`** | 만능 도구: 힙 덤프, 스레드 덤프, GC 실행, JFR, 설정 확인 |
| `jps` | 실행 중인 JVM 프로세스 목록 |
| `jstat -gcutil <pid> 1000` | GC·힙 영역 사용률을 1초마다 |
| `jstack <pid>` | 스레드 덤프 |
| `jmap -dump` | 힙 덤프 (jcmd 권장) |
| **JFR (Java Flight Recorder)** | 운영 환경에서 낮은 부하(~1%)로 CPU·메모리 할당·락·I/O 기록 |
| JDK Mission Control (JMC) | JFR 파일 분석 GUI |
| **Eclipse MAT**, VisualVM | 힙 덤프 분석 |
| async-profiler | CPU·할당 프로파일링, **플레임 그래프** |
| **Spring Boot Actuator** | `/actuator/metrics`, `/actuator/threaddump`, `/actuator/heapdump` (외부 노출 금지) |

```bash
jcmd                                            # JVM 목록
jcmd <pid> VM.flags                             # 적용된 JVM 옵션
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print > threads.txt           # 스레드 덤프
jcmd <pid> GC.heap_dump /tmp/heap.hprof         # 힙 덤프 (STW 발생, 힙 크기만큼 디스크 필요)
jcmd <pid> JFR.start duration=60s filename=/tmp/rec.jfr
```
> 컨테이너에서는 `kubectl exec -it <pod> -- jcmd 1 Thread.print`처럼 실행합니다 (앱이 PID 1일 때). JRE 이미지에는 jcmd가 없을 수 있어 JDK 이미지나 디버그 컨테이너가 필요합니다.

## 2. OutOfMemoryError 종류

| 메시지 | 원인 | 대응 |
|---|---|---|
| **`Java heap space`** | 힙 부족: **메모리 누수** 또는 한 번에 너무 많은 데이터 (findAll, 대용량 파일) | 힙 덤프 분석, 페이징·스트리밍, 힙 증설 |
| `GC overhead limit exceeded` | GC에 시간의 98% 이상을 쓰는데 2% 미만 회수 (사실상 힙 부족) | 위와 같음 |
| `Metaspace` | 클래스가 너무 많이 로딩 (동적 프록시·클래스 생성 남용, 클래스로더 누수) | MaxMetaspaceSize 확인, 동적 생성 코드 점검 |
| `unable to create native thread` | OS 스레드 한도·메모리 부족 (스레드를 무제한 생성) | 스레드 풀 사용, 가상 스레드 |
| `Direct buffer memory` | NIO Direct 버퍼 부족 (Netty 등) | `-XX:MaxDirectMemorySize`, 버퍼 해제 |
| 컨테이너 **Exit 137 (OOMKilled)** | JVM이 아니라 **컨테이너 메모리 제한 초과** — JVM 로그에 OOM이 없음 | 힙 비율 낮추기 (비힙 메모리 고려) |

### 힙 덤프 분석 (Eclipse MAT)
```
1. -XX:+HeapDumpOnOutOfMemoryError 로 OOM 순간의 덤프 확보
2. MAT로 열기 → Leak Suspects 리포트
3. Dominator Tree: 가장 많은 메모리를 잡고 있는 객체
4. 경로 추적 (Path to GC Roots): 누가 이 객체를 참조하고 있는지
   예) static HashMap → 수백만 개의 SessionData
```
> 힙 덤프에는 **개인정보·비밀번호·토큰이 그대로** 들어 있습니다. 보안에 주의해 다루고, 분석 후 삭제하세요.

## 3. 스레드 덤프 읽기

```
"http-nio-8080-exec-12" #45 daemon prio=5 tid=0x... nid=0x2f03 waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.example.order.StockService.decrease(StockService.java:42)
        - waiting to lock <0x000000076b2a1c30> (a com.example.order.Stock)
        at com.example.order.OrderService.order(OrderService.java:30)
        ...
```
| 스레드 상태 | 의미 |
|---|---|
| RUNNABLE | 실행 중 (또는 I/O 중 — 네이티브 소켓 읽기도 RUNNABLE로 보임) |
| **BLOCKED** | **synchronized 락을 기다림** |
| WAITING / TIMED_WAITING | `wait()`, `park()`, `sleep()`, 락(ReentrantLock) 대기, 스레드 풀 작업 대기 |

### 활용
- **3~5초 간격으로 여러 번** 떠서 비교 → 계속 같은 위치에 있는 스레드가 병목
- 같은 락을 기다리는 BLOCKED 스레드가 많으면 → **락 경합**
- `Found one Java-level deadlock` → **데드락** (jstack이 자동 탐지)
- 대부분의 Tomcat 스레드가 같은 외부 호출(`SocketInputStream.read`)에 걸려 있으면 → **외부 API·DB 지연**, 타임아웃 부재
- 대부분 `HikariPool.getConnection`에서 대기 → **DB 커넥션 풀 고갈**

> 분석 도구: fastThread.io, IntelliJ 스레드 덤프 분석기

## 4. 상황별 진단

### CPU 100%
```bash
top -H -p <pid>                       # CPU를 많이 쓰는 스레드의 TID(10진수)
printf '%x\n' <TID>                   # 16진수로 변환
jcmd <pid> Thread.print | grep -A 20 'nid=0x<16진수>'   # 해당 스레드의 스택
```
흔한 원인: **무한 루프**, 정규식 폭주(ReDoS), 과도한 GC(→ GC 로그 확인), 대량 직렬화·정렬

### 응답 지연 (CPU는 한가함)
```
1. 스레드 덤프: Tomcat 스레드가 어디서 기다리는지
2. DB: 느린 쿼리, 락 대기, 커넥션 풀 대기 (hikaricp_connections_pending)
3. 외부 API: 타임아웃 설정 여부
4. GC 로그: 긴 STW
5. 분산 추적으로 어느 구간인지
```

### 메모리가 계속 증가
```
1. GC 로그 / Grafana: GC 후 Old 사용량이 계속 우상향인가?
   - 우상향 → 누수 → 힙 덤프 두 번(시간 간격) 떠서 비교
   - 톱니 모양으로 일정 → 정상
2. 힙이 아닌 컨테이너 메모리만 증가 → 스레드 수, Direct 버퍼, Metaspace (NMT: -XX:NativeMemoryTracking=summary)
```

## 5. 운영 JVM 기본 옵션 예시

```bash
java \
  -XX:MaxRAMPercentage=75.0 \
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps \
  -Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m \
  -XX:+ExitOnOutOfMemoryError \
  -jar app.jar
```
| 옵션 | 이유 |
|---|---|
| `MaxRAMPercentage` | 컨테이너 제한에 맞춘 힙 |
| `HeapDumpOnOutOfMemoryError` | 사후 분석 |
| GC 로그 | 지연 원인 분석 |
| `ExitOnOutOfMemoryError` | OOM 후 이상 상태로 계속 떠 있지 않고 종료 → 오케스트레이터가 재시작 |

> **튜닝 원칙**: 측정 없이 옵션부터 바꾸지 않기. 대부분의 성능 문제는 JVM 옵션이 아니라 **쿼리·N+1·외부 호출·불필요한 객체 생성**에 있습니다.

## 6. 면접 질문

1. **OutOfMemoryError가 발생하면 어떻게 원인을 찾나요?**
   → 메시지로 영역(heap, Metaspace, native thread)을 구분하고, HeapDumpOnOutOfMemoryError로 받은 힙 덤프를 MAT로 열어 큰 객체와 GC Root까지의 참조 경로를 추적해 누수 지점을 찾습니다.
2. **스레드 덤프로 무엇을 알 수 있나요?**
   → 각 스레드의 상태와 스택을 보고 락 경합, 데드락, 외부 호출이나 커넥션 풀 대기 같은 병목 위치를 파악할 수 있으며, 여러 번 떠서 비교합니다.
3. **CPU가 100%일 때 원인을 찾는 방법은?**
   → top -H로 CPU를 많이 쓰는 스레드 ID를 찾고 16진수로 바꿔 스레드 덤프의 nid와 매칭해 해당 스택을 확인하며, GC 로그로 과도한 GC 여부도 확인합니다.
4. **컨테이너에서 Exit 137로 죽었는데 JVM 로그에 OOM이 없다면?**
   → JVM 힙이 아니라 컨테이너 메모리 제한을 넘어 커널이 강제 종료한 것이므로, 힙 외 메모리를 고려해 힙 비율을 낮추거나 메모리 제한을 늘립니다.

## 핵심 정리
- 도구: **jcmd**(덤프·JFR), jstat, MAT(힙 덤프), JFR/JMC, async-profiler, Actuator
- OOM: heap space(누수·대량 로딩) / Metaspace / native thread / 컨테이너 137
- 스레드 덤프: BLOCKED(락), 같은 위치 반복(병목), 데드락 자동 탐지, 여러 번 비교
- CPU 100%: `top -H` → 16진수 → nid 매칭
- 운영 옵션: MaxRAMPercentage + 힙 덤프 + GC 로그 + ExitOnOOM, 측정 먼저
