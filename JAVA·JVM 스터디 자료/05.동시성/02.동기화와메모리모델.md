## 1. 멀티스레드의 세 가지 문제

### ① 원자성 (Atomicity)
```java
class Counter {
    private int count = 0;
    public void increment() { count++; }    // 읽기 → +1 → 쓰기 (3단계), 중간에 끼어들 수 있음
}
// 두 스레드가 각각 10만 번 → 결과가 20만보다 작음
```

### ② 가시성 (Visibility)
한 스레드가 바꾼 값을 **다른 스레드가 못 볼 수** 있습니다 (CPU 캐시, 레지스터, 컴파일러 최적화).
```java
class Worker {
    private boolean running = true;
    public void run() {
        while (running) { }       // JIT가 running을 레지스터에 올려 두면 영원히 안 끝날 수 있음
    }
    public void stop() { running = false; }   // 다른 스레드에서 호출
}
```

### ③ 순서성 (Ordering, 재정렬)
컴파일러·CPU는 성능을 위해 **명령 순서를 바꿀 수** 있습니다. 단일 스레드에서는 결과가 같지만, 다른 스레드가 보면 순서가 뒤바뀌어 보일 수 있습니다.
```java
// 스레드 A                 // 스레드 B
data = 42;                  if (ready) {
ready = true;                   System.out.println(data);   // 0이 출력될 수도 있음
                            }
```

## 2. 자바 메모리 모델과 happens-before

JMM은 "어떤 쓰기가 어떤 읽기에 **보이는 것이 보장**되는가"를 정의합니다. 핵심은 **happens-before** 관계입니다.
> A happens-before B 이면, **A의 결과(메모리 쓰기)가 B에게 보이고**, A가 B보다 먼저 일어난 것처럼 보장됩니다.

| happens-before 규칙 | |
|---|---|
| 프로그램 순서 | 같은 스레드 안에서는 앞의 코드 → 뒤의 코드 |
| **모니터 락** | `synchronized` 해제 → 같은 락의 다음 획득 |
| **volatile** | volatile 쓰기 → 같은 변수의 이후 읽기 |
| 스레드 시작 | `t.start()` 호출 전의 작업 → t 안의 작업 |
| 스레드 종료 | t의 작업 → `t.join()` 반환 이후 |
| 동시성 유틸 | `ExecutorService.submit` 전 → 작업 실행, `Future.get` 이후 등 |

→ 동기화 도구를 쓰면 **세 가지 문제가 모두 해결**되고, 쓰지 않으면 아무것도 보장되지 않습니다.

## 3. synchronized

```java
public class Counter {
    private int count = 0;

    public synchronized void increment() { count++; }    // 인스턴스(this)의 모니터 락
    public synchronized int get() { return count; }       // 읽기도 동기화해야 가시성 보장

    public void add(int n) {
        synchronized (this) {                              // 블록: 필요한 부분만
            count += n;
        }
    }

    public static synchronized void staticMethod() { }     // Counter.class의 락
}
```
| 특징 | |
|---|---|
| 원자성 + 가시성 + 순서성 | 모두 보장 |
| **재진입 가능 (Reentrant)** | 같은 스레드는 이미 가진 락을 다시 얻을 수 있음 |
| 자동 해제 | 블록을 벗어나면(예외 포함) 해제 |
| 한계 | 타임아웃·인터럽트로 대기 취소 불가, 공정성 없음 |

> 락 객체로 **`String` 리터럴이나 `Integer`** 를 쓰지 마세요. 다른 코드와 같은 객체를 공유할 수 있습니다. `private final Object lock = new Object();`를 씁니다.

## 4. volatile

```java
private volatile boolean running = true;
```
- 읽기·쓰기가 **메인 메모리 기준**으로 보이게 함 (**가시성**) + 앞뒤 명령 재정렬 금지 (**순서성**)
- **원자성은 보장하지 않음**: `volatile int count; count++;`는 여전히 경쟁 상태

| 적합 | 부적합 |
|---|---|
| **한 스레드가 쓰고 여러 스레드가 읽는 플래그** (`running`, `shutdownRequested`) | `count++` 같은 복합 연산 |
| 안전한 발행 (불변 객체 참조를 교체) | 여러 변수를 함께 바꿔야 하는 경우 |

### Double-Checked Locking과 volatile
```java
public class Singleton {
    private static volatile Singleton instance;          // volatile 필수
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }
}
```
> volatile이 없으면 재정렬로 **생성이 끝나지 않은 객체**를 다른 스레드가 볼 수 있습니다. 실무에서는 Holder 패턴이나 enum 싱글톤, 또는 Spring 빈을 씁니다.

## 5. Atomic 클래스 (CAS)

**락 없이** 원자적 연산을 제공합니다. 하드웨어의 **CAS(Compare-And-Swap)** 명령을 사용합니다.
```java
AtomicInteger count = new AtomicInteger();
count.incrementAndGet();
count.addAndGet(5);
count.compareAndSet(10, 0);                       // 현재 10이면 0으로 (성공 여부 반환)
count.updateAndGet(x -> Math.max(x, newValue));

AtomicReference<Config> config = new AtomicReference<>(initial);
config.set(newConfig);

LongAdder hits = new LongAdder();                 // 경합이 심한 카운터: 내부적으로 셀을 나눠 누적
hits.increment();
hits.sum();
```
```
CAS(주소, 기대값, 새값):  현재 값 == 기대값 이면 새값으로 바꾸고 true, 아니면 false
→ 실패하면 다시 읽어서 재시도 (스핀)
```
| 비교 | synchronized | Atomic (CAS) |
|---|---|---|
| 방식 | 락 (블로킹) | 락 없음 (논블로킹, 재시도) |
| 경합 적을 때 | 느림 | **빠름** |
| 경합 심할 때 | 대기 | 재시도 폭증 → `LongAdder` |
| 범위 | 여러 변수·복잡한 로직 | **단일 변수** |

## 6. ReentrantLock과 그 밖의 락

```java
private final ReentrantLock lock = new ReentrantLock();

public void transfer() {
    lock.lock();
    try {
        // 임계 영역
    } finally {
        lock.unlock();                                // ★ 반드시 finally
    }
}

// 시간 제한 획득 (데드락 회피)
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try { ... } finally { lock.unlock(); }
} else {
    throw new IllegalStateException("락 획득 실패");
}
```
| 기능 | synchronized | ReentrantLock |
|---|---|---|
| 타임아웃 `tryLock(time)` | X | **O** |
| 인터럽트로 대기 취소 | X | O (`lockInterruptibly`) |
| 공정성 (먼저 온 순서) | X | O (`new ReentrantLock(true)`) |
| 조건 변수 여러 개 | wait/notify 하나 | `Condition` 여러 개 |
| 해제 | 자동 | **직접 (finally)** |

| 그 밖의 락 | 용도 |
|---|---|
| `ReentrantReadWriteLock` | 읽기는 동시에, 쓰기는 혼자 (읽기가 압도적으로 많을 때) |
| `StampedLock` | 낙관적 읽기 지원 (고성능, 재진입 불가) |

> 이 락들은 **하나의 JVM 안에서만** 유효합니다. 서버가 여러 대면 DB 락이나 Redis 분산 락이 필요합니다. (→ Spring JPA 자료 `03.JPA실전/05.동시성과락.md`, 미들웨어 자료 `01.Redis/03.Redis활용패턴.md`)

## 7. 스레드 안전한 설계

| 전략 | 설명 | 예 |
|---|---|---|
| **공유하지 않기** | 지역 변수, 요청마다 새 객체 | 스택은 스레드마다 따로 |
| **불변 객체** | 상태가 안 바뀌면 동기화 불필요 | record, String, `List.copyOf` |
| 스레드 안전한 컬렉션 | 검증된 구현 사용 | `ConcurrentHashMap`, `CopyOnWriteArrayList` |
| ThreadLocal | 스레드별 복사본 | SecurityContext, 트랜잭션 |
| 동기화 | 최소 범위로 | synchronized, Lock |

> **Spring 싱글톤 빈에 변경 가능한 필드를 두지 마세요.** 모든 요청 스레드가 같은 빈을 공유합니다.
```java
@Service
public class BadService {
    private int count;                       // ❌ 모든 요청이 공유 → 경쟁 상태
    private Member currentMember;            // ❌ 다른 사용자의 정보가 섞임
}
```

## 8. 면접 질문

1. **volatile과 synchronized의 차이는?**
   → volatile은 변수의 가시성과 재정렬 방지만 보장하고 원자성은 보장하지 않아 플래그에 적합하며, synchronized는 락으로 원자성·가시성·순서성을 모두 보장합니다.
2. **CAS란?**
   → 메모리의 현재 값이 기대값과 같을 때만 새 값으로 바꾸는 원자적 하드웨어 명령으로, Atomic 클래스가 락 없이 원자 연산을 구현하는 데 사용하며 실패하면 재시도합니다.
3. **happens-before란?**
   → 한 작업의 메모리 쓰기 결과가 다른 작업에서 보이는 것을 보장하는 자바 메모리 모델의 관계로, 락 해제와 획득, volatile 쓰기와 읽기, 스레드 start와 join 등이 이를 만듭니다.
4. **ReentrantLock을 synchronized 대신 쓰는 경우는?**
   → 락 획득에 타임아웃을 주거나, 대기 중 인터럽트로 취소하거나, 공정성이나 여러 조건 변수가 필요할 때 씁니다.
5. **Spring 빈은 싱글톤인데 스레드 안전한가요?**
   → 빈 자체가 상태(변경 가능한 필드)를 갖지 않으면 안전합니다. 요청별 데이터는 지역 변수나 파라미터로 다뤄야 합니다.

## 핵심 정리
- 세 가지 문제: **원자성(count++), 가시성(캐시), 순서성(재정렬)**
- JMM의 **happens-before**: 락 해제→획득, volatile 쓰기→읽기, start, join
- synchronized(모두 보장, 재진입) / **volatile(가시성만, 플래그)** / Atomic·LongAdder(CAS, 단일 변수) / ReentrantLock(tryLock, 공정성)
- JVM 락은 서버 한 대 안에서만 → 다중 서버는 DB·Redis 락
- 스레드 안전 설계: 공유 X, 불변, 동시성 컬렉션, 싱글톤 빈에 상태 X
