# 04. 동시성 컬렉션, 동기화 도구, ThreadLocal

> **학습 목표**
> - 동시성 컬렉션(ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue)의 용도를 설명할 수 있다.
> - CountDownLatch, CyclicBarrier, Semaphore를 사용할 수 있다.
> - ThreadLocal의 원리, Spring에서의 활용, 메모리 누수 위험을 설명할 수 있다.

---

## 1. 동시성 컬렉션

| 클래스 | 특징 | 적합 |
|---|---|---|
| **`ConcurrentHashMap`** | 버킷 단위 동기화, 읽기 무락 | 공유 캐시, 카운터 맵 (→ `02.컬렉션/02.Map과Set내부구조.md`) |
| **`CopyOnWriteArrayList`** | **쓸 때마다 배열 전체 복사**, 읽기 무락, 순회 중 수정 안전 | **읽기가 압도적, 쓰기 드묾** (리스너 목록, 설정) |
| `ConcurrentLinkedQueue` | 논블로킹 큐 (CAS) | 생산자-소비자 (대기 불필요) |
| **`BlockingQueue`** | 비면 꺼낼 때, 가득 차면 넣을 때 **대기** | **생산자-소비자** |
| `ConcurrentSkipListMap/Set` | 정렬 + 동시성 | 동시성 TreeMap |

### BlockingQueue: 생산자-소비자
```java
BlockingQueue<Order> queue = new ArrayBlockingQueue<>(1000);   // 크기 제한

// 생산자
queue.put(order);                          // 가득 차면 대기
queue.offer(order, 1, TimeUnit.SECONDS);   // 시간 제한

// 소비자
Order o = queue.take();                    // 비어 있으면 대기
Order o2 = queue.poll(1, TimeUnit.SECONDS);
```
| 구현 | 특징 |
|---|---|
| `ArrayBlockingQueue` | 고정 크기 배열 |
| `LinkedBlockingQueue` | 연결 리스트, 크기 지정 가능 (기본 무제한) |
| `PriorityBlockingQueue` | 우선순위 |
| `DelayQueue` | 지연 시간이 지난 것만 꺼냄 |
| `SynchronousQueue` | 저장 공간 0, 바로 전달 (CachedThreadPool 내부) |

## 2. 동기화 도구

### CountDownLatch: N개 작업이 끝날 때까지 대기
```java
int n = 3;
CountDownLatch latch = new CountDownLatch(n);
ExecutorService pool = Executors.newFixedThreadPool(n);

for (int i = 0; i < n; i++) {
    pool.submit(() -> {
        try { loadData(); }
        finally { latch.countDown(); }          // 하나 끝날 때마다 -1
    });
}
latch.await(10, TimeUnit.SECONDS);              // 0이 될 때까지 대기
```
> **동시성 테스트**에 자주 씁니다: 100개 스레드가 동시에 재고 차감 → 모두 끝나면 재고 검증 (→ 테스트코드 자료 `03.테스트설계/04.동시성과시간테스트.md`)

### CyclicBarrier: N개 스레드가 모두 도착하면 함께 진행 (재사용 가능)
```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("모두 도착"));
// 각 스레드: barrier.await();
```

### Semaphore: 동시 접근 수 제한
```java
Semaphore semaphore = new Semaphore(10);        // 외부 API는 동시에 10개까지만

public Result call() throws InterruptedException {
    semaphore.acquire();
    try {
        return externalApi.call();
    } finally {
        semaphore.release();
    }
}
```
> 가상 스레드로 수만 개 요청을 동시에 처리할 때, **외부 시스템을 보호하기 위해** 세마포어로 동시 호출 수를 제한합니다. (Spring Framework 7은 `@ConcurrencyLimit` 제공)

| 도구 | 용도 | 재사용 |
|---|---|---|
| CountDownLatch | 한 스레드가 **N개 작업 완료**를 기다림 | X |
| CyclicBarrier | **N개 스레드가 서로** 기다림 | O |
| Semaphore | 동시 접근 **N개 제한** | O |
| Phaser | 단계별 동기화 (유연) | O |

## 3. ThreadLocal

**스레드마다 독립적인 값을 저장**하는 변수입니다. 같은 ThreadLocal 객체라도 스레드마다 다른 값을 봅니다.

```java
public class RequestContext {
    private static final ThreadLocal<String> REQUEST_ID = new ThreadLocal<>();

    public static void set(String id) { REQUEST_ID.set(id); }
    public static String get() { return REQUEST_ID.get(); }
    public static void clear() { REQUEST_ID.remove(); }
}
```
```
원리: 각 Thread 객체 안에 ThreadLocalMap이 있고, ThreadLocal을 키로 값을 저장
Thread A.threadLocals = { REQUEST_ID → "req-1" }
Thread B.threadLocals = { REQUEST_ID → "req-2" }
```

### Spring에서 ThreadLocal을 쓰는 곳
| 기능 | 저장 내용 |
|---|---|
| **`SecurityContextHolder`** | 현재 로그인 사용자 |
| **`TransactionSynchronizationManager`** | 현재 트랜잭션의 DB 커넥션 → 같은 트랜잭션의 모든 Repository가 **같은 커넥션** 사용 |
| `RequestContextHolder` | 현재 HTTP 요청 |
| `LocaleContextHolder` | 로케일 |
| SLF4J **MDC** | 로그에 붙일 requestId, traceId |

### ⚠️ 반드시 remove: 스레드 풀과 메모리 누수
```java
@Component
public class RequestIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        RequestContext.set(UUID.randomUUID().toString());
        try {
            chain.doFilter(req, res);
        } finally {
            RequestContext.clear();             // ★ 안 지우면?
        }
    }
}
```
| 지우지 않으면 | 결과 |
|---|---|
| **데이터 오염** | Tomcat 스레드는 재사용됨 → **다음 요청이 이전 사용자의 값을 봄** (보안 사고) |
| 메모리 누수 | 스레드가 살아 있는 동안 값이 계속 남음 (큰 객체면 심각) |

### 다른 스레드로는 전파되지 않음
```java
RequestContext.set("req-1");
CompletableFuture.runAsync(() -> RequestContext.get());   // null
```
→ 필요한 값을 인자로 넘기거나, `InheritableThreadLocal`(스레드 풀에서는 오염 위험), Spring `TaskDecorator`로 복사

```java
executor.setTaskDecorator(runnable -> {
    Map<String, String> mdc = MDC.getCopyOfContextMap();     // 제출 시점의 MDC 복사
    return () -> {
        try {
            if (mdc != null) MDC.setContextMap(mdc);
            runnable.run();
        } finally {
            MDC.clear();
        }
    };
});
```

### 가상 스레드와 ThreadLocal
가상 스레드는 수백만 개가 생길 수 있어 ThreadLocal에 큰 값을 넣으면 메모리 부담이 커집니다. 불변 컨텍스트 전달에는 **Scoped Values**(Java 25 정식)가 권장됩니다. (→ `05.가상스레드.md`)

## 4. 면접 질문

1. **CopyOnWriteArrayList는 언제 쓰나요?**
   → 쓰기 때마다 배열을 복사하므로 쓰기는 비싸지만 읽기에 락이 없어, 읽기가 압도적으로 많고 쓰기가 드문 리스너 목록 같은 곳에 씁니다.
2. **CountDownLatch와 CyclicBarrier의 차이는?**
   → CountDownLatch는 한 스레드가 N개 작업 완료를 기다리며 재사용할 수 없고, CyclicBarrier는 N개 스레드가 서로 모두 도착할 때까지 기다리며 재사용할 수 있습니다.
3. **ThreadLocal이란? 주의할 점은?**
   → 스레드마다 독립된 값을 저장하는 변수로 SecurityContext, 트랜잭션 커넥션, MDC에 쓰입니다. 스레드 풀에서 스레드가 재사용되므로 사용 후 반드시 remove해야 다른 요청에 값이 섞이거나 메모리 누수가 생기지 않습니다.
4. **Spring 트랜잭션은 어떻게 같은 커넥션을 공유하나요?**
   → TransactionSynchronizationManager가 현재 트랜잭션의 커넥션을 ThreadLocal에 보관하고, 같은 스레드의 Repository들이 이를 꺼내 쓰기 때문입니다.

## 핵심 정리
- 동시성 컬렉션: ConcurrentHashMap / CopyOnWriteArrayList(읽기 위주) / **BlockingQueue(생산자-소비자)**
- CountDownLatch(완료 대기, 동시성 테스트) / CyclicBarrier(서로 대기) / **Semaphore(동시 수 제한)**
- ThreadLocal = 스레드별 값 → SecurityContext, 트랜잭션, MDC
- **finally에서 remove** (스레드 재사용 오염·누수), 다른 스레드로 전파 X → TaskDecorator
