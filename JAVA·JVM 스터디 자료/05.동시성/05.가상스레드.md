# 05. 가상 스레드 (Virtual Threads, Java 21+)

> **학습 목표**
> - 플랫폼 스레드와 가상 스레드의 차이, 가상 스레드의 동작 원리(마운트·언마운트)를 설명할 수 있다.
> - 가상 스레드가 효과적인 작업과 그렇지 않은 작업을 구분할 수 있다.
> - 피닝(pinning), ThreadLocal, 풀링 금지 등 주의점을 설명할 수 있다.
> - Spring Boot에서 가상 스레드를 활성화하고 외부 자원을 보호할 수 있다.

---

## 1. 왜 필요한가?

전통적인 서버(Tomcat)는 **요청 하나 = 스레드 하나**입니다.
```
요청 처리 시간 200ms 중
  CPU 사용 10ms + DB 대기 120ms + 외부 API 대기 70ms
→ 스레드는 대부분의 시간을 "기다리며" OS 스레드와 메모리(스택 ~1MB)를 붙잡고 있음
→ 스레드 200개면 동시 요청 200개가 한계
```
대안이었던 **리액티브(WebFlux)** 는 적은 스레드로 많은 요청을 처리하지만, 코드가 콜백·체인 구조라 **작성·디버깅이 어렵습니다.**

**가상 스레드**: 동기식(blocking) 코드를 그대로 쓰면서, 대기할 때는 OS 스레드를 놓아 주어 **수십만~수백만 개의 동시 작업**을 처리합니다.

---

## 2. 동작 원리

```
        가상 스레드 (수백만 개 가능, Heap에 스택 저장)
   VT1   VT2   VT3   VT4   VT5   VT6 ...
    │     │     │
    ↓ mount(올라탐)
 [캐리어 스레드 1] [캐리어 스레드 2] ... [캐리어 스레드 N]   ← 플랫폼 스레드 (기본: CPU 코어 수, ForkJoinPool)
    ↓
   OS 스레드 / CPU
```
```
1. VT1이 캐리어 스레드에 마운트되어 실행
2. VT1이 블로킹 I/O (DB 쿼리, HTTP 호출, sleep) → 스택을 Heap에 저장하고 **언마운트**
3. 캐리어 스레드는 즉시 다른 가상 스레드(VT2)를 실행
4. I/O가 끝나면 VT1은 다시 아무 캐리어 스레드에 마운트되어 이어서 실행
```

| 비교 | 플랫폼 스레드 | 가상 스레드 |
|---|---|---|
| 매핑 | OS 스레드와 1:1 | 캐리어 스레드 위에 M:N |
| 생성 비용 | 큼 (ms 단위, OS 호출) | **매우 작음** (μs, 일반 객체 수준) |
| 스택 | 고정 (~1MB) | Heap에 **필요한 만큼** (수 KB~) |
| 개수 | 수천 개 | **수백만 개** |
| 블로킹 시 | OS 스레드도 대기 | **언마운트 → 캐리어는 다른 일** |
| 풀링 | 필요 | **하지 않음** (작업마다 새로 생성) |
| 데몬 | 설정 가능 | 항상 데몬 |

> 가상 스레드는 "더 빠른 스레드"가 아니라 **"더 많은 스레드"** 입니다. 각 작업의 처리 속도가 빨라지는 것이 아니라, **동시에 처리할 수 있는 양(처리량)** 이 늘어납니다.

---

## 3. 사용법

```java
// 하나 실행
Thread vt = Thread.ofVirtual().name("vt-1").start(() -> callApi());
Thread.startVirtualThread(() -> callApi());

// 작업마다 가상 스레드 (권장)
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> results = IntStream.range(0, 10_000)
            .mapToObj(i -> executor.submit(() -> {
                Thread.sleep(1000);              // 1초 대기 작업 1만 개
                return "done " + i;
            }))
            .toList();
}   // 약 1초 남짓에 모두 완료 (플랫폼 스레드 200개 풀이면 약 50초)

Thread.currentThread().isVirtual();
```

### Spring Boot (3.2+)
```yaml
spring:
  threads:
    virtual:
      enabled: true
```
→ Tomcat 요청 처리, `@Async`, 스케줄링(`@Scheduled`), Kafka·RabbitMQ 리스너 등이 가상 스레드를 사용합니다.

## 4. 효과가 있는 작업 vs 없는 작업

| 효과 큼 | 효과 없음 / 역효과 |
|---|---|
| **I/O 대기가 많은** 작업: DB 쿼리, 외부 API, 파일, 메시지 | **CPU 위주** 작업 (암호화, 이미지 처리, 대량 계산) → 캐리어 수(코어 수)가 한계 |
| 동시 요청이 많은 웹 서버 | 동시성이 낮은 서비스 |
| 마이크로서비스 간 호출이 많은 API | 이미 리액티브로 잘 구성된 시스템 |

## 5. 주의점

### ① 피닝 (Pinning)
가상 스레드가 블로킹되어도 **캐리어 스레드에서 내려오지 못하는** 상황입니다. 캐리어가 묶이면 다른 가상 스레드도 실행하지 못합니다.
| 원인 | 상태 |
|---|---|
| `synchronized` 블록·메서드 안에서 블로킹 | **Java 21~23: 피닝 발생** → `ReentrantLock`으로 교체 권장<br>**Java 24+: 해결** (JEP 491) |
| 네이티브 메서드(JNI) 호출 중 블로킹 | 여전히 피닝 |

```java
// Java 21~23에서 피닝을 피하려면
private final ReentrantLock lock = new ReentrantLock();
public void update() {
    lock.lock();
    try {
        repository.save(...);     // 블로킹 I/O
    } finally {
        lock.unlock();
    }
}
```
> 피닝은 JFR 이벤트 `jdk.VirtualThreadPinned`로 확인합니다. 오래된 JDBC 드라이버·라이브러리가 내부에서 synchronized를 쓰면 영향을 받으므로 **최신 버전**을 쓰세요.

### ② 풀링하지 않는다
```java
// ❌ 가상 스레드를 풀에 담기 — 의미 없음
Executors.newFixedThreadPool(100, Thread.ofVirtual().factory());
// ✅ 작업마다 새로 만들기
Executors.newVirtualThreadPerTaskExecutor();
```
풀은 "비싼 스레드를 재사용"하고 "동시성을 제한"하려고 쓰는데, 가상 스레드는 싸고, 동시성 제한은 따로 하는 것이 맞습니다.

### ③ 외부 자원 보호: 동시성 제한은 따로
가상 스레드 덕분에 동시 요청 1만 개를 받아도, **DB 커넥션 풀은 여전히 10~50개**입니다.
```
가상 스레드 10,000개 → HikariCP 커넥션 20개를 두고 대기 → 커넥션 타임아웃
                    → 외부 API에 동시 10,000건 → 상대 서버 장애·레이트 리밋
```
```java
private final Semaphore apiLimit = new Semaphore(50);   // 외부 API 동시 호출 50개로 제한
```
> 병목이 스레드에서 **DB 커넥션·외부 API·락**으로 옮겨갈 뿐입니다. 커넥션 풀 크기, 타임아웃, 세마포어, 서킷 브레이커를 함께 설계하세요.

### ④ ThreadLocal
- 동작은 하지만, 가상 스레드가 수백만 개면 **ThreadLocal 값도 수백만 개** → 메모리 부담
- ThreadLocal로 **비싼 객체를 캐시**하던 패턴(스레드마다 SimpleDateFormat 하나 등)은 무의미 (가상 스레드는 재사용되지 않음)
- 불변 컨텍스트 전달에는 **Scoped Values**(Java 25 정식) 권장

### ⑤ 그 밖에
- CPU 작업은 기존 플랫폼 스레드 풀(ForkJoinPool 등)로 분리
- 스레드 덤프가 매우 커질 수 있음 → `jcmd <pid> Thread.dump_to_file -format=json <파일>`
- 우선순위·데몬 설정 불가

## 6. 구조적 동시성 (Structured Concurrency, 미리보기)

여러 하위 작업을 **하나의 단위로** 다루는 API입니다. 하나가 실패하면 나머지를 취소하고, 모두 끝나야 범위를 벗어납니다. (Java 21~25 기준 미리보기 기능으로 API가 계속 바뀌고 있음)
```
try (scope = 새 범위) {
    회원 조회 작업 fork
    주문 조회 작업 fork
    scope.join()            → 하나라도 실패하면 나머지 취소, 예외 전파
    두 결과 조합
}                           → 범위를 벗어나면 남은 작업이 없음이 보장됨
```

## 7. 가상 스레드 vs 리액티브 (WebFlux)

| 비교 | 가상 스레드 + Spring MVC | WebFlux (리액티브) |
|---|---|---|
| 코드 | **동기식 그대로** (읽기·디버깅 쉬움) | Mono/Flux 체인 |
| 학습 비용 | 낮음 | 높음 |
| 기존 라이브러리 | JDBC, JPA 그대로 | R2DBC 등 논블로킹 드라이버 필요 |
| 역압(backpressure)·스트리밍 | 직접 구현 | **기본 지원** |
| 적합 | **대부분의 I/O 위주 웹 서비스** | 스트리밍, 대규모 이벤트 처리, 이미 리액티브 생태계 |

## 8. 면접 질문

1. **가상 스레드란?**
   → JVM이 관리하는 경량 스레드로, 소수의 캐리어 플랫폼 스레드 위에서 실행되며 블로킹 I/O를 만나면 언마운트되어 캐리어를 다른 작업에 양보하므로 수백만 개의 동시 작업을 처리할 수 있습니다.
2. **가상 스레드가 모든 작업을 빠르게 하나요?**
   → 아닙니다. 개별 작업 속도가 아니라 I/O 대기가 많은 작업의 동시 처리량을 늘려 주며, CPU 위주 작업은 코어 수가 한계라 효과가 없습니다.
3. **피닝이란? 어떻게 대응하나요?**
   → 가상 스레드가 블로킹되어도 캐리어에서 내려오지 못하는 현상으로, Java 21~23에서는 synchronized 안의 블로킹이 원인이라 ReentrantLock으로 바꾸고, Java 24부터는 synchronized 피닝이 해결되었습니다.
4. **가상 스레드를 도입할 때 주의할 점은?**
   → 풀링하지 않고 작업마다 생성하며, 동시 요청이 늘어나는 만큼 DB 커넥션 풀이나 외부 API가 병목이 되므로 세마포어·타임아웃으로 보호하고, ThreadLocal에 큰 값을 두지 않습니다.

---

## 핵심 정리
- 가상 스레드 = 캐리어(플랫폼) 위의 경량 스레드, **블로킹 시 언마운트** → 대량 동시 I/O
- "빠른 스레드"가 아니라 "많은 스레드" (CPU 작업엔 효과 X)
- `Executors.newVirtualThreadPerTaskExecutor()`, Spring `spring.threads.virtual.enabled=true`
- 주의: **피닝**(synchronized, Java 24에서 해결), **풀링 금지**, **외부 자원은 세마포어로 보호**, ThreadLocal → Scoped Values
