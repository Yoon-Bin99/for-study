# 01. 스프링과 스프링 부트

> **학습 목표**
> - 스프링이 해결하려는 문제(객체 생성·의존 관리)와 IoC·DI 개념을 설명할 수 있다.
> - 스프링 프레임워크와 스프링 부트의 차이를 설명할 수 있다.
> - 자동 구성(Auto Configuration)의 동작 원리를 이해한다.
> - Spring Boot 3과 4(Framework 7)의 주요 변화를 알고 있다.

---

## 1. 스프링이 없던 시절의 문제

```java
public class OrderService {
    // 서비스가 직접 구현체를 고르고 생성함
    private final OrderRepository repository = new JdbcOrderRepository();
    private final PaymentClient payment = new TossPaymentClient();
}
```
| 문제 | 설명 |
|---|---|
| 강한 결합 | `JdbcOrderRepository` → `JpaOrderRepository`로 바꾸려면 **서비스 코드를 수정** |
| 테스트 어려움 | 가짜(Mock) 결제 클라이언트로 갈아끼울 수 없음 |
| OCP·DIP 위반 | 인터페이스에 의존하는 척하지만 실제로는 구현체에 의존 |

## 2. IoC와 DI

- **IoC (Inversion of Control, 제어의 역전)**: 객체의 생성과 연결을 **내가 아니라 프레임워크(컨테이너)** 가 담당
- **DI (Dependency Injection, 의존성 주입)**: 필요한 의존 객체를 **외부에서 넣어 줌**

```java
@Service
public class OrderService {
    private final OrderRepository repository;     // 인터페이스에만 의존
    private final PaymentClient payment;

    public OrderService(OrderRepository repository, PaymentClient payment) {   // 생성자 주입
        this.repository = repository;
        this.payment = payment;
    }
}
```
```
     [스프링 컨테이너]
  JpaOrderRepository 생성 ──┐
  TossPaymentClient  생성 ──┼──▶ new OrderService(repo, payment) 주입
                            │
  테스트에서는 FakePaymentClient를 넣으면 끝
```
> 프레임워크 vs 라이브러리: **라이브러리는 내 코드가 호출**하고, **프레임워크는 내 코드를 호출**합니다(제어의 역전).

---

## 3. 스프링 프레임워크의 구성

| 모듈 | 역할 |
|---|---|
| Core Container | IoC 컨테이너, 빈, DI (`→ 02.빈과컨테이너.md`) |
| AOP | 공통 관심사 분리, 프록시 (`→ 03.AOP와프록시.md`) |
| Data Access | 트랜잭션 추상화, JDBC, ORM 연동 (`→ 06.트랜잭션.md`) |
| Web | Spring MVC, WebFlux (`→ 04.스프링MVC요청흐름.md`) |
| Test | 스프링 테스트 컨텍스트 |

스프링의 핵심 가치는 **POJO(평범한 자바 객체)** 로 비즈니스 로직을 작성하게 하고, 기술(트랜잭션·보안·웹)은 **DI·AOP·추상화(PSA)** 로 분리하는 것입니다.

| 3대 기술 | 의미 | 예 |
|---|---|---|
| IoC/DI | 객체 생성·연결을 컨테이너가 | 생성자 주입 |
| AOP | 공통 기능을 핵심 로직 밖으로 | `@Transactional`, 로깅 |
| PSA (Portable Service Abstraction) | 기술이 바뀌어도 같은 인터페이스 | `PlatformTransactionManager`(JDBC·JPA 동일 사용), `@Cacheable`(Redis·Caffeine) |

## 4. 스프링 부트

스프링 프레임워크는 강력하지만 **설정이 많았습니다**(XML, 톰캣 설치·배포, 라이브러리 버전 맞추기).

| 기능 | 스프링 부트가 해 주는 것 |
|---|---|
| **스타터 의존성** | `spring-boot-starter-webmvc` 하나로 MVC·Jackson·Tomcat·검증 등 묶음 + **버전 호환 관리** |
| **자동 구성** | 클래스패스를 보고 필요한 빈을 자동 등록 (DataSource, EntityManagerFactory, ObjectMapper...) |
| **내장 서버** | Tomcat/Jetty 내장 → `java -jar app.jar` 로 실행 |
| **외부 설정** | `application.yml`, 환경 변수, 프로필 (`→ 07.설정과프로필.md`) |
| **Actuator** | 헬스 체크, 메트릭, 운영 엔드포인트 |

### 자동 구성의 원리
```java
@SpringBootApplication     // = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```
```
1. @EnableAutoConfiguration
2. META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 에 나열된
   자동 구성 클래스 후보를 읽음 (예: DataSourceAutoConfiguration)
3. 각 클래스의 조건을 검사
   @ConditionalOnClass(DataSource.class)        → 해당 클래스가 클래스패스에 있으면
   @ConditionalOnMissingBean(DataSource.class)  → 사용자가 직접 등록한 빈이 없으면
   @ConditionalOnProperty("spring.datasource.url") → 설정이 있으면
4. 조건을 통과한 구성만 빈으로 등록
```
> **사용자가 직접 등록한 빈이 우선**입니다(`@ConditionalOnMissingBean`). 어떤 자동 구성이 적용됐는지는 `--debug` 실행이나 Actuator `/actuator/conditions`로 확인합니다.

## 5. Spring Boot 3 → 4 주요 변화 (2025.11 출시)

| 항목 | Boot 3.x (Framework 6) | Boot 4.x (Framework 7) |
|---|---|---|
| Java | 17+ | 17+ (Java 25 지원, 21+ 권장) |
| Jakarta EE | 10 (`jakarta.*`) | **11** (Servlet 6.1, JPA 3.2) |
| JSON | Jackson 2 (`com.fasterxml.jackson`) | **Jackson 3** (`tools.jackson`, `JsonMapper`) |
| 스타터 | `spring-boot-starter-web` | **모듈화**: `spring-boot-starter-webmvc` 등 (기존 이름은 deprecated) |
| Hibernate | 6.x | **7.x** |
| Null 안전성 | Spring 자체 애노테이션 | **JSpecify** (`@Nullable`, `@NullMarked`) |
| 새 기능 | – | API 버전 관리, `@Retryable`·`@ConcurrencyLimit` 코어 내장, HTTP Interface 클라이언트 그룹 |
| 서버 | Tomcat, Jetty, Undertow | Tomcat, Jetty (**Undertow 제외**) |

> Boot 2 → 3의 가장 큰 변화는 `javax.*` → **`jakarta.*`** 패키지 변경(Jakarta EE 9+)과 Java 17 필수였습니다. 오래된 블로그 예제의 `javax.persistence`는 지금은 `jakarta.persistence`입니다.

## 6. 면접 질문

1. **IoC와 DI란?**
   → IoC는 객체의 생성과 의존 관계 설정을 개발자가 아닌 컨테이너가 담당하는 것이고, DI는 그 방법으로 필요한 의존 객체를 외부(생성자 등)에서 주입하는 것입니다. 덕분에 구현체 교체와 테스트가 쉬워집니다.
2. **스프링과 스프링 부트의 차이는?**
   → 스프링은 DI·AOP·트랜잭션 등을 제공하는 프레임워크이고, 스프링 부트는 그 위에서 스타터 의존성, 자동 구성, 내장 서버, 외부 설정을 제공해 설정 없이 바로 실행 가능한 애플리케이션을 만들게 해 줍니다.
3. **자동 구성은 어떻게 동작하나요?**
   → `@EnableAutoConfiguration`이 AutoConfiguration.imports에 등록된 구성 클래스를 읽고, `@ConditionalOnClass`, `@ConditionalOnMissingBean` 같은 조건을 통과한 것만 빈으로 등록합니다. 사용자가 직접 정의한 빈이 우선합니다.
4. **PSA란?**
   → 기술이 바뀌어도 동일한 추상화 인터페이스로 사용할 수 있게 한 것으로, 예를 들어 `@Transactional`은 JDBC든 JPA든 같은 방식으로 동작합니다.

---

## 핵심 정리
- 스프링 = **IoC/DI + AOP + PSA** 로 비즈니스 로직(POJO)과 기술을 분리
- 부트 = **스타터 + 자동 구성(@Conditional) + 내장 서버 + 외부 설정**
- Boot 4: Jakarta EE 11, Jackson 3, 모듈화 스타터, Hibernate 7, JSpecify
