# 02. 빈과 스프링 컨테이너

> **학습 목표**
> - 빈 등록 방법(컴포넌트 스캔, `@Bean`)과 의존성 주입 방식을 비교할 수 있다.
> - 생성자 주입을 권장하는 이유를 설명할 수 있다.
> - 빈의 생명주기와 스코프, 싱글톤 빈의 주의점을 이해한다.
> - 같은 타입의 빈이 여러 개일 때 해결 방법을 안다.

---

## 1. 스프링 컨테이너

```
ApplicationContext (스프링 컨테이너)
 ├─ BeanFactory 기능: 빈 생성, 의존 관계 주입, 조회
 └─ + 메시지 소스, 이벤트 발행, 환경 변수(Environment), 리소스 로딩
```
- **빈(Bean)**: 스프링 컨테이너가 생성·관리하는 객체
- 기본적으로 **싱글톤**: 애플리케이션 전체에서 하나의 인스턴스를 공유

---

## 2. 빈 등록 방법

### ① 컴포넌트 스캔 (내가 만든 클래스)
```java
@Component    // 일반
@Service      // 비즈니스 로직 (의미 구분용)
@Repository   // 데이터 접근 (+ DB 예외를 스프링 DataAccessException으로 변환)
@Controller / @RestController
@Configuration // 설정 클래스
```
`@SpringBootApplication`이 있는 패키지와 **그 하위 패키지**를 스캔합니다. 그래서 메인 클래스는 최상위 패키지에 둡니다.

### ② `@Bean` (외부 라이브러리 객체, 세밀한 설정)
```java
@Configuration
public class ClientConfig {

    @Bean
    public RestClient paymentRestClient(RestClient.Builder builder) {
        return builder.baseUrl("https://api.payment.com")
                .defaultHeader("X-Client", "order-service")
                .build();
    }
}
```
> `@Configuration` 클래스는 CGLIB 프록시로 만들어져서, `@Bean` 메서드를 여러 번 호출해도 **같은 싱글톤 객체**를 돌려줍니다. (`@Configuration(proxyBeanMethods = false)`면 이 처리를 생략해 시작이 빨라짐)

## 3. 의존성 주입 방식

| 방식 | 코드 | 평가 |
|---|---|---|
| **생성자 주입** | 생성자 파라미터 | ✅ **권장** |
| 수정자(setter) 주입 | `@Autowired setXxx()` | 선택적 의존성일 때만 |
| 필드 주입 | `@Autowired private Xxx x;` | ❌ 테스트에서 주입 불가, 비권장 |

```java
@Service
@RequiredArgsConstructor     // Lombok: final 필드로 생성자 생성
public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentClient paymentClient;
}
// 생성자가 하나면 @Autowired 생략 가능
```

### 생성자 주입을 권장하는 이유
1. **불변(final)**: 주입 후 바뀌지 않음
2. **누락 방지**: 의존성이 없으면 컴파일·시작 시점에 실패
3. **테스트 용이**: `new OrderService(fakeRepo, fakeClient)` 로 스프링 없이 테스트
4. **순환 참조 조기 발견**: A→B→A 이면 애플리케이션 시작 시 에러 (Boot 2.6+ 기본 금지)
5. 생성자 파라미터가 너무 많아지면 **클래스가 너무 많은 책임**을 가진 신호로 볼 수 있음

## 4. 같은 타입의 빈이 여러 개일 때

```java
public interface DiscountPolicy { int discount(int price); }
@Component class FixDiscountPolicy implements DiscountPolicy { ... }
@Component class RateDiscountPolicy implements DiscountPolicy { ... }

// 주입 시 NoUniqueBeanDefinitionException
```
| 해결 | 방법 |
|---|---|
| `@Primary` | 기본으로 쓸 빈 지정 |
| `@Qualifier("rate")` | 이름으로 지정 (`@Primary`보다 우선) |
| 파라미터 이름 | 빈 이름과 같으면 매칭 (최후 수단) |
| **모두 주입** | `List<DiscountPolicy>`, `Map<String, DiscountPolicy>` → 전략 패턴 |

```java
@Service
public class DiscountService {
    private final Map<String, DiscountPolicy> policies;   // 빈 이름 → 빈

    public DiscountService(Map<String, DiscountPolicy> policies) {
        this.policies = policies;
    }

    public int discount(String policyName, int price) {
        DiscountPolicy policy = policies.get(policyName);
        if (policy == null) throw new IllegalArgumentException("없는 정책: " + policyName);
        return policy.discount(price);
    }
}
```

## 5. 빈 생명주기

```
컨테이너 생성 → 빈 생성(생성자) → 의존 관계 주입 → 초기화 콜백 → 사용 → 소멸 전 콜백 → 컨테이너 종료
                                            ↑                         ↑
                                    @PostConstruct              @PreDestroy
```
```java
@Component
public class ExternalConnection {
    @PostConstruct
    void connect() { /* 커넥션 열기, 캐시 워밍업 */ }

    @PreDestroy
    void close() { /* 자원 정리 */ }
}
// 외부 라이브러리: @Bean(initMethod = "init", destroyMethod = "close")
```
> 애플리케이션이 **완전히 준비된 뒤** 작업하려면 `@EventListener(ApplicationReadyEvent.class)`를 씁니다. `@PostConstruct` 시점에는 프록시(@Transactional 등)가 아직 적용되지 않았을 수 있습니다.

### BeanPostProcessor
빈 생성 후 초기화 전후에 끼어들어 **빈을 가공하거나 바꿔치기**합니다. `@Transactional`, `@Async` 같은 AOP 프록시가 이 단계에서 원본 대신 등록됩니다. (`→ 03.AOP와프록시.md`)

## 6. 빈 스코프

| 스코프 | 생성 시점 | 소멸 |
|---|---|---|
| **singleton** (기본) | 컨테이너 시작 | 컨테이너 종료 |
| prototype | 조회할 때마다 새로 | **컨테이너가 관리 안 함** (@PreDestroy 호출 X) |
| request | HTTP 요청마다 | 요청 끝 |
| session | HTTP 세션마다 | 세션 끝 |

싱글톤 빈에서 request 스코프 빈을 쓰려면 `ObjectProvider<T>`나 `@Scope(proxyMode = ScopedProxyMode.TARGET_CLASS)`로 **지연 조회**해야 합니다.

## 7. 싱글톤 빈의 주의점: 상태를 갖지 마라

```java
@Service
public class PriceService {
    private int total;                 // ❌ 모든 요청(스레드)이 공유하는 필드

    public int calculate(int price) {
        total = price * 2;             // 요청 A가 쓰고
        return total;                  // 요청 B가 덮어쓴 값을 A가 읽을 수 있음
    }
}
```
```java
@Service
public class PriceService {
    public int calculate(int price) {
        int total = price * 2;         // ✅ 지역 변수는 스레드마다 별도 (스택)
        return total;
    }
}
```
> 싱글톤 빈은 **무상태(stateless)** 로 설계합니다. 필드는 `final` 의존성이나 불변 설정값만 둡니다. (`→ JAVA·JVM 스터디 자료의 05.동시성/02.동기화와메모리모델.md`)

## 8. 면접 질문

1. **생성자 주입을 권장하는 이유는?**
   → final로 불변성을 보장하고, 의존성 누락을 시작 시점에 발견하며, 스프링 없이 new로 테스트할 수 있고, 순환 참조를 조기에 발견할 수 있기 때문입니다.
2. **같은 타입 빈이 여러 개면?**
   → `@Primary`로 기본 빈을 정하거나 `@Qualifier`로 지정하고, 모두 필요하면 List나 Map으로 주입받아 전략 패턴으로 사용합니다.
3. **싱글톤 빈에서 주의할 점은?**
   → 여러 스레드가 같은 인스턴스를 공유하므로 변경 가능한 필드(상태)를 두면 동시성 문제가 생깁니다. 무상태로 설계하고 지역 변수를 사용합니다.
4. **`@PostConstruct`에서 `@Transactional` 메서드를 호출하면?**
   → 초기화 시점에는 프록시가 적용되기 전이거나 자기 호출이 되어 트랜잭션이 적용되지 않을 수 있습니다. ApplicationReadyEvent 이후에 실행하는 것이 안전합니다.

## 핵심 정리
- 빈 = 컨테이너가 관리하는 객체, 기본 **싱글톤**
- 등록: 컴포넌트 스캔(내 클래스) / `@Bean`(외부 객체)
- 주입: **생성자 주입** + `@RequiredArgsConstructor`
- 중복 빈: `@Primary` < `@Qualifier`, 전략 패턴은 `Map<String, T>`
- 싱글톤 빈은 **무상태**로
