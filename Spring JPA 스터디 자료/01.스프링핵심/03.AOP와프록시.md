# 03. AOP와 프록시

> **학습 목표**
> - AOP가 해결하는 문제(공통 관심사)와 용어를 설명할 수 있다.
> - 스프링 AOP가 프록시로 동작하는 원리(JDK 동적 프록시 vs CGLIB)를 이해한다.
> - **자기 호출(self-invocation) 문제**와 해결법을 설명할 수 있다.
> - `@Aspect`로 실행 시간 측정 같은 공통 기능을 구현할 수 있다.

---

## 1. 왜 AOP인가?

```java
public void order() {
    long start = System.currentTimeMillis();     // 공통: 시간 측정
    log.info("order start");                     // 공통: 로깅
    tx.begin();                                  // 공통: 트랜잭션
    try {
        // ── 핵심 비즈니스 로직 ──
        tx.commit();
    } catch (Exception e) {
        tx.rollback(); throw e;
    } finally {
        log.info("order end {}ms", System.currentTimeMillis() - start);
    }
}
// 모든 서비스 메서드에 같은 코드가 반복됨
```
**AOP (Aspect-Oriented Programming)**: 여러 곳에 흩어진 **공통 관심사(횡단 관심사, cross-cutting concern)** 를 한 곳(Aspect)에 모아 핵심 로직과 분리합니다.

```
          주문 서비스   회원 서비스   결제 서비스
             │            │            │
로깅    ─────┼────────────┼────────────┼─────  ← Aspect 하나로
트랜잭션 ─────┼────────────┼────────────┼─────  ← Aspect 하나로
보안    ─────┼────────────┼────────────┼─────
```
스프링의 `@Transactional`, `@Cacheable`, `@Async`, `@PreAuthorize`, `@Retryable`이 모두 AOP로 동작합니다.

---

## 2. 용어

| 용어 | 의미 | 예 |
|---|---|---|
| **Aspect** | 공통 기능 모듈 (Advice + Pointcut) | `@Aspect` 클래스 |
| **Advice** | 실제로 실행할 공통 코드와 시점 | `@Around`, `@Before`, `@AfterReturning`, `@AfterThrowing`, `@After` |
| **Pointcut** | 어디에 적용할지 (조건식) | `execution(* com.shop..*Service.*(..))` |
| **Join Point** | 적용 가능한 지점 | 스프링 AOP에서는 **메서드 실행**만 |
| **Target** | Advice가 적용되는 원본 객체 | `OrderService` |
| **Proxy** | Target을 감싼 대리 객체 | `OrderService$$SpringCGLIB$$0` |
| **Weaving** | Aspect를 Target에 적용하는 것 | 스프링은 **런타임 프록시** 방식 |

## 3. 프록시로 동작하는 원리

```
       Controller
           │  orderService.order()   ← 실제로는 프록시를 호출
           ▼
   ┌──────────────────────────┐
   │ OrderService 프록시 (빈) │
   │  1. 트랜잭션 시작        │
   │  2. target.order() ──────┼──▶ 실제 OrderService.order()
   │  3. 커밋 / 롤백          │
   └──────────────────────────┘
```
1. 빈 생성 후 **BeanPostProcessor**(AnnotationAwareAspectJAutoProxyCreator)가 Pointcut에 맞는 빈인지 검사
2. 맞으면 **원본 대신 프록시를 컨테이너에 등록**
3. 다른 빈은 프록시를 주입받아 호출 → 프록시가 Advice 실행 후 원본 호출

### JDK 동적 프록시 vs CGLIB

| 비교 | JDK 동적 프록시 | CGLIB |
|---|---|---|
| 방식 | **인터페이스** 기반 (`Proxy.newProxyInstance`) | **클래스 상속** (바이트코드 생성) |
| 조건 | 인터페이스 필수 | 인터페이스 없어도 됨 |
| 제약 | 인터페이스 타입으로만 주입 가능 | `final` 클래스·메서드 불가, `private` 메서드 불가 |
| 스프링 부트 기본 | – | ✅ **CGLIB** (`proxyTargetClass=true`) |

> 원리 자체(리플렉션, `InvocationHandler`)는 `JAVA·JVM 스터디 자료의 01.자바기초심화/05.enum과애노테이션과리플렉션.md` 참고.

## 4. 자기 호출 (Self-invocation) 문제 ★

```java
@Service
public class OrderService {

    public void placeOrder() {
        // ... 
        saveHistory();          // ❌ this.saveHistory() → 프록시를 거치지 않음!
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveHistory() { ... }   // 트랜잭션이 적용되지 않음
}
```
```
Controller ──▶ [프록시].placeOrder() ──▶ [원본].placeOrder()
                                              │ this.saveHistory()
                                              ▼
                                         [원본].saveHistory()   ← 프록시를 안 거침 → Advice 없음
```

### 해결 방법
| 방법 | 설명 | 평가 |
|---|---|---|
| **별도 클래스로 분리** | `HistoryService.saveHistory()`를 주입받아 호출 | ✅ 가장 권장 (책임 분리) |
| 자기 자신 주입 | `@Lazy` 로 자기 프록시를 주입 | 동작은 하지만 구조가 어색 |
| `AopContext.currentProxy()` | `exposeProxy=true` 설정 필요 | 스프링 의존, 비권장 |
| AspectJ 위빙 | 컴파일·로드 타임 위빙 | 설정 복잡 |

```java
@Service
@RequiredArgsConstructor
public class OrderService {
    private final HistoryService historyService;

    public void placeOrder() {
        historyService.saveHistory();    // ✅ 프록시를 통해 호출
    }
}
```

### 그 밖에 AOP가 적용되지 않는 경우
- `private` 메서드 (CGLIB가 오버라이드 불가)
- `final` 클래스·메서드
- 스프링 빈이 아닌 객체 (`new`로 만든 객체)
- `@PostConstruct` 안에서 자기 메서드 호출

## 5. `@Aspect` 직접 만들기: 실행 시간 측정

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface LogExecutionTime { }
```
```java
@Slf4j
@Aspect
@Component
public class ExecutionTimeAspect {

    @Around("@annotation(com.shop.common.LogExecutionTime)")
    public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();                      // 원본 메서드 실행
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            log.info("{} 실행 시간 {}ms", joinPoint.getSignature().toShortString(), elapsedMs);
        }
    }
}
```
```java
@LogExecutionTime
public OrderResponse placeOrder(OrderRequest request) { ... }
```
- 의존성: `spring-boot-starter-aop` (Boot 4에서는 `spring-boot-starter-aspectj`로 이름이 바뀜)
- `@Around`에서 `proceed()`를 호출하지 않으면 **원본이 실행되지 않습니다**
- 여러 Aspect의 순서는 `@Order`로 지정 (숫자가 작을수록 바깥쪽)

### Pointcut 표현식
```
execution(* com.shop..*Service.*(..))
          │  │                │   └ 파라미터 아무거나
          │  │                └ 모든 메서드
          │  └ com.shop 및 하위 패키지의 ~Service 클래스
          └ 반환 타입 아무거나
@annotation(com.shop.LogExecutionTime)   이 애노테이션이 붙은 메서드
within(com.shop.order..*)                 이 패키지 안의 모든 메서드
```

## 6. 면접 질문

1. **AOP란? 스프링에서 어떻게 구현되나요?**
   → 로깅·트랜잭션 같은 횡단 관심사를 핵심 로직에서 분리하는 프로그래밍 기법으로, 스프링은 빈 후처리기가 대상 빈 대신 프록시를 등록하고, 프록시가 Advice를 실행한 뒤 원본 메서드를 호출하는 런타임 프록시 방식으로 구현합니다.
2. **JDK 동적 프록시와 CGLIB의 차이는?**
   → JDK 프록시는 인터페이스를 구현해 만들고, CGLIB는 클래스를 상속해 바이트코드로 만듭니다. CGLIB는 인터페이스가 없어도 되지만 final 클래스나 메서드에는 적용할 수 없고, 스프링 부트는 기본으로 CGLIB를 사용합니다.
3. **같은 클래스 안에서 `@Transactional` 메서드를 호출하면?**
   → 내부 호출은 this를 통해 원본 객체의 메서드를 직접 호출하므로 프록시를 거치지 않아 트랜잭션이 적용되지 않습니다. 해당 메서드를 별도 빈으로 분리해 해결합니다.

---

## 핵심 정리
- AOP = 공통 관심사를 Aspect로 분리, 스프링은 **런타임 프록시** (메서드 실행 지점만)
- 부트 기본 **CGLIB** (상속) → final·private 불가
- **자기 호출은 프록시를 우회** → 별도 빈으로 분리
- `@Around` + `proceed()` 로 직접 Aspect 구현
