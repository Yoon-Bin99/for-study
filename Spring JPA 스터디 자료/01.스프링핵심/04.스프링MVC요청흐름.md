# 04. 스프링 MVC 요청 흐름

> **학습 목표**
> - 요청이 들어와서 응답이 나갈 때까지 거치는 컴포넌트(Filter, DispatcherServlet, Interceptor, ArgumentResolver, MessageConverter)를 순서대로 설명할 수 있다.
> - Filter와 Interceptor의 차이를 설명할 수 있다.
> - `@RequestBody`, `@ModelAttribute`, `@RequestParam`의 차이를 안다.
> - Tomcat 스레드 모델과 요청 처리의 관계를 이해한다.

---

## 1. 전체 흐름

```
클라이언트
   │ HTTP 요청
   ▼
[Tomcat]  커넥터가 요청 수신 → 스레드 풀에서 스레드 할당 (요청 1개 = 스레드 1개)
   │
   ▼
[Filter Chain]  ← 서블릿 영역: 인코딩, CORS, 로깅, **Spring Security**
   │
   ▼
[DispatcherServlet]  ← 프론트 컨트롤러: 모든 요청의 입구
   │ 1. HandlerMapping: URL·HTTP 메서드로 처리할 컨트롤러 메서드 찾기
   │ 2. HandlerAdapter: 그 메서드를 실행할 어댑터 선택
   ▼
[Interceptor.preHandle]  ← 스프링 영역: 인증 확인, 로깅
   │
   ▼
[ArgumentResolver]  파라미터 만들기: @RequestBody(JSON→객체), @PathVariable, @AuthenticationPrincipal ...
   │
   ▼
[Controller → Service → Repository]
   │ 반환값
   ▼
[ReturnValueHandler + HttpMessageConverter]  객체 → JSON (Jackson)
   │
[Interceptor.postHandle / afterCompletion]
   │  (예외 발생 시 → HandlerExceptionResolver → @RestControllerAdvice)
   ▼
[Filter Chain 역순] → Tomcat → 클라이언트 응답
```

---

## 2. DispatcherServlet (프론트 컨트롤러 패턴)

모든 요청을 **하나의 서블릿**이 받아 공통 처리 후 알맞은 컨트롤러에 위임합니다.
| 구성 요소 | 역할 |
|---|---|
| HandlerMapping | 요청 → 핸들러(컨트롤러 메서드) 찾기 (`RequestMappingHandlerMapping`) |
| HandlerAdapter | 다양한 형태의 핸들러 실행 (`RequestMappingHandlerAdapter`) |
| HandlerMethodArgumentResolver | 메서드 파라미터 생성 |
| HttpMessageConverter | 요청 본문 ↔ 객체 변환 (JSON은 Jackson) |
| HandlerExceptionResolver | 예외를 응답으로 변환 (`→ 05.예외처리와검증.md`) |
| ViewResolver | 뷰 이름 → 템플릿 (REST API에서는 거의 안 씀) |

## 3. Filter vs Interceptor

| 비교 | Filter | Interceptor |
|---|---|---|
| 소속 | **서블릿** (Jakarta Servlet) | **스프링 MVC** |
| 위치 | DispatcherServlet **앞** | DispatcherServlet **뒤**, 컨트롤러 앞 |
| 대상 | 모든 요청 (정적 리소스 포함) | 컨트롤러로 가는 요청 |
| 핸들러 정보 | 모름 | 어떤 컨트롤러 메서드인지 앎 (`HandlerMethod`) |
| 요청·응답 객체 교체 | 가능 (래핑) | 불가 |
| 예외 | `@RestControllerAdvice`로 처리 불가 | 처리 가능 |
| 대표 용도 | 인코딩, CORS, **보안(Spring Security)**, 요청 로깅·MDC | 로그인 확인, 권한·감사 로그, 공통 헤더 |

```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = Optional.ofNullable(request.getHeader("X-Trace-Id"))
                .orElse(UUID.randomUUID().toString());
        MDC.put("traceId", traceId);                 // 로그에 traceId 자동 포함
        response.setHeader("X-Trace-Id", traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.clear();                             // 스레드 재사용 → 반드시 정리
        }
    }
}
```
```java
@Component
public class AuditInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (handler instanceof HandlerMethod hm && hm.hasMethodAnnotation(AdminOnly.class)) {
            // 관리자 API 호출 기록
        }
        return true;     // false면 컨트롤러 실행 안 함
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    private final AuditInterceptor auditInterceptor;
    public WebConfig(AuditInterceptor auditInterceptor) { this.auditInterceptor = auditInterceptor; }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(auditInterceptor).addPathPatterns("/api/admin/**");
    }
}
```

## 4. 요청 데이터 받기

```java
@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    @GetMapping("/{orderId}")                                 // /api/orders/42
    public OrderResponse get(@PathVariable Long orderId) { ... }

    @GetMapping                                               // /api/orders?status=PAID&page=0
    public Page<OrderResponse> search(@RequestParam(required = false) OrderStatus status,
                                      Pageable pageable) { ... }

    @PostMapping
    public ResponseEntity<OrderResponse> create(@RequestBody @Valid OrderCreateRequest request) {
        OrderResponse response = orderService.create(request);
        return ResponseEntity.created(URI.create("/api/orders/" + response.id())).body(response);
    }
}
```
| 애노테이션 | 데이터 위치 | 변환 |
|---|---|---|
| `@PathVariable` | URL 경로 `/orders/{id}` | 문자열 → 타입 변환 |
| `@RequestParam` | 쿼리 스트링, 폼 | 단일 값 |
| `@ModelAttribute` (생략 가능) | 쿼리 스트링·폼 → **객체** 바인딩 | 검색 조건 객체 |
| `@RequestBody` | **HTTP 본문 (JSON)** | HttpMessageConverter(Jackson) |
| `@RequestHeader`, `@CookieValue` | 헤더, 쿠키 | |

> 요청·응답 DTO는 **record**로 만들고, **엔티티를 직접 반환하지 않습니다**. (지연 로딩 예외, 순환 참조, 내부 필드 노출, API 스펙이 엔티티 변경에 묶이는 문제)

## 5. Tomcat 스레드 모델

```yaml
server:
  tomcat:
    threads:
      max: 200          # 동시에 처리할 수 있는 요청 수 (기본 200)
      min-spare: 10
    accept-count: 100   # 스레드가 모두 바쁠 때 대기 큐
    max-connections: 8192
```
- 요청 하나가 끝날 때까지 **스레드 하나를 점유** → 외부 API가 느려지면 스레드가 고갈되어 전체 장애
- 대응: **타임아웃 설정**, 서킷 브레이커, 가상 스레드(`spring.threads.virtual.enabled=true`, `→ JAVA·JVM 스터디 자료의 05.동시성/05.가상스레드.md`)
- 요청 처리 스레드가 재사용되므로 ThreadLocal(MDC, SecurityContext)은 **반드시 정리**

## 6. 면접 질문

1. **스프링 MVC의 요청 처리 흐름을 설명해 주세요.**
   → 톰캣이 요청을 받아 스레드를 할당하고, 필터 체인을 거쳐 DispatcherServlet이 HandlerMapping으로 컨트롤러 메서드를 찾습니다. 인터셉터를 거쳐 ArgumentResolver가 파라미터를 만들고 컨트롤러를 실행한 뒤, 반환값을 MessageConverter가 JSON으로 변환해 응답합니다.
2. **Filter와 Interceptor의 차이는?**
   → 필터는 서블릿 스펙으로 DispatcherServlet 앞에서 모든 요청에 동작하고 요청 객체를 래핑할 수 있으며, 인터셉터는 스프링 MVC 기능으로 컨트롤러 앞뒤에서 핸들러 정보를 알고 동작합니다. 보안·인코딩은 필터, 컨트롤러 단위 공통 처리는 인터셉터가 적합합니다.
3. **`@RequestBody`와 `@ModelAttribute`의 차이는?**
   → `@RequestBody`는 HTTP 본문(JSON)을 MessageConverter로 객체로 바꾸고, `@ModelAttribute`는 쿼리 파라미터나 폼 데이터를 객체 필드에 바인딩합니다.

---

## 핵심 정리
- Tomcat → **Filter** → **DispatcherServlet** → HandlerMapping → **Interceptor** → ArgumentResolver → Controller → MessageConverter
- Filter(서블릿, 보안·인코딩) vs Interceptor(스프링, 핸들러 정보)
- JSON 본문은 `@RequestBody`, 쿼리는 `@RequestParam`/`@ModelAttribute`
- 요청 1개 = 스레드 1개 → 타임아웃·ThreadLocal 정리 필수
