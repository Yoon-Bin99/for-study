# 05. 예외 처리와 입력 검증

> **학습 목표**
> - `@RestControllerAdvice`로 API 예외 응답을 일관되게 만들 수 있다.
> - RFC 9457 ProblemDetail 표준 응답 형식을 이해한다.
> - Bean Validation(`@Valid`, `@Validated`)으로 입력을 검증하고, 검증 실패 응답을 만들 수 있다.
> - 어떤 검증을 어느 계층에서 해야 하는지 구분할 수 있다.

---

## 1. 예외 처리 흐름

```
Controller/Service에서 예외 발생
   ▼
DispatcherServlet → HandlerExceptionResolver 체인
   1. ExceptionHandlerExceptionResolver  ← @ExceptionHandler, @RestControllerAdvice  ★
   2. ResponseStatusExceptionResolver    ← @ResponseStatus, ResponseStatusException
   3. DefaultHandlerExceptionResolver    ← 스프링 내부 예외 (400, 405, 415 ...)
   ▼ 아무도 처리 못하면
WAS → /error → BasicErrorController (기본 에러 JSON)
```
> Filter(Spring Security 포함)에서 발생한 예외는 DispatcherServlet 밖이라 `@RestControllerAdvice`가 잡지 못합니다. 보안 예외는 `AuthenticationEntryPoint`, `AccessDeniedHandler`에서 처리합니다.

## 2. 비즈니스 예외 설계

```java
@Getter
@RequiredArgsConstructor
public enum ErrorCode {
    ORDER_NOT_FOUND(HttpStatus.NOT_FOUND, "O001", "주문을 찾을 수 없습니다."),
    OUT_OF_STOCK(HttpStatus.CONFLICT, "O002", "재고가 부족합니다."),
    ALREADY_SHIPPED(HttpStatus.CONFLICT, "O003", "이미 배송된 주문입니다."),
    INVALID_INPUT(HttpStatus.BAD_REQUEST, "C001", "입력값이 올바르지 않습니다."),
    INTERNAL_ERROR(HttpStatus.INTERNAL_SERVER_ERROR, "C999", "서버 오류가 발생했습니다.");

    private final HttpStatus status;
    private final String code;
    private final String message;
}

@Getter
public class BusinessException extends RuntimeException {
    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }
}
```
```java
Order order = orderRepository.findById(id)
        .orElseThrow(() -> new BusinessException(ErrorCode.ORDER_NOT_FOUND));
```
> 런타임 예외(Unchecked)를 쓰는 이유와 롤백 규칙은 `JAVA·JVM 스터디 자료의 01.자바기초심화/03.예외처리.md`, `06.트랜잭션.md` 참고.

## 3. 전역 예외 처리: `@RestControllerAdvice` + ProblemDetail

스프링 6부터 **RFC 9457 (Problem Details for HTTP APIs)** 표준 응답 객체 `ProblemDetail`을 지원합니다.
```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "재고가 부족합니다.",
  "instance": "/api/orders",
  "code": "O002"
}
```
```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {
    // ResponseEntityExceptionHandler: 스프링 MVC 내부 예외(400, 405, 415 등)를 ProblemDetail로 변환

    @ExceptionHandler(BusinessException.class)
    public ProblemDetail handleBusiness(BusinessException e) {
        ErrorCode code = e.getErrorCode();
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(code.getStatus(), code.getMessage());
        problem.setProperty("code", code.getCode());
        return problem;
    }

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException e, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "입력값이 올바르지 않습니다.");
        problem.setProperty("code", ErrorCode.INVALID_INPUT.getCode());
        problem.setProperty("errors", e.getBindingResult().getFieldErrors().stream()
                .map(fe -> Map.of("field", fe.getField(), "message", String.valueOf(fe.getDefaultMessage())))
                .toList());
        return ResponseEntity.badRequest().body(problem);
    }

    @ExceptionHandler(Exception.class)
    public ProblemDetail handleUnexpected(Exception e) {
        log.error("예상하지 못한 예외", e);                    // 스택 트레이스는 로그에만
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
                ErrorCode.INTERNAL_ERROR.getMessage());     // 클라이언트에는 내부 정보 노출 X
    }
}
```
```yaml
spring:
  mvc:
    problemdetails:
      enabled: true   # 스프링 내부 예외도 ProblemDetail 형식으로 (ResponseEntityExceptionHandler를 상속했다면 불필요)
```

| 원칙 | 이유 |
|---|---|
| 응답 형식을 **하나로 통일** | 클라이언트가 한 가지 방식으로 파싱 |
| **에러 코드**를 별도로 | 메시지는 바뀌어도 코드로 분기 가능 |
| 500에서 **내부 정보 숨기기** | 스택 트레이스·SQL 노출은 보안 취약점 |
| 4xx는 warn/info, 5xx는 error 로그 | 클라이언트 실수로 알림이 울리지 않게 |

## 4. 입력 검증: Bean Validation

의존성: `spring-boot-starter-validation` (Hibernate Validator)

```java
public record OrderCreateRequest(
        @NotNull Long productId,
        @Min(1) @Max(100) int quantity,
        @NotBlank @Size(max = 200) String address,
        @Email String email,
        @Valid @NotNull CouponRequest coupon    // 중첩 객체도 검증하려면 @Valid
) { }
```
| 애노테이션 | 검사 |
|---|---|
| `@NotNull` | null 아님 |
| `@NotEmpty` | null·빈 문자열/컬렉션 아님 |
| `@NotBlank` | null·빈 문자열·공백만 아님 (문자열 전용) |
| `@Size(min, max)` | 길이·크기 |
| `@Min`, `@Max`, `@Positive` | 숫자 범위 |
| `@Email`, `@Pattern(regexp=)` | 형식 |
| `@Past`, `@Future` | 날짜 |

```java
@PostMapping
public OrderResponse create(@RequestBody @Valid OrderCreateRequest request) { ... }
// 실패 시 MethodArgumentNotValidException → 400
```

### `@Valid` vs `@Validated`
| | `@Valid` (Jakarta 표준) | `@Validated` (스프링) |
|---|---|---|
| 그룹 검증 | ✗ | ✅ `@Validated(OnCreate.class)` |
| 클래스에 붙여 메서드 파라미터 검증 | ✗ | ✅ (AOP 프록시로 동작) |

```java
@Validated
@RestController
public class ProductController {
    @GetMapping("/api/products")
    public List<ProductResponse> list(@RequestParam @Max(100) int size) { ... }
    // Spring 6.1+: 컨트롤러 메서드 파라미터 검증은 @Validated 없이도 내장 지원 → HandlerMethodValidationException
}
```

### 커스텀 검증
```java
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = PhoneValidator.class)
public @interface Phone {
    String message() default "휴대폰 번호 형식이 아닙니다.";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class PhoneValidator implements ConstraintValidator<Phone, String> {
    private static final Pattern PATTERN = Pattern.compile("^01[016-9]-?\\d{3,4}-?\\d{4}$");
    @Override
    public boolean isValid(String value, ConstraintValidatorContext ctx) {
        return value == null || PATTERN.matcher(value).matches();   // null은 @NotNull에 맡김
    }
}
```

## 5. 어디서 무엇을 검증할까?

| 계층 | 검증 내용 | 예 |
|---|---|---|
| **Controller (DTO)** | 형식·필수값·범위 (요청만 보고 알 수 있는 것) | 수량 1~100, 이메일 형식 |
| **Service / 도메인** | 비즈니스 규칙 (DB·상태를 봐야 아는 것) | 재고 부족, 이미 취소된 주문, 중복 이메일 |
| **DB** | 최후의 방어선 | `NOT NULL`, `UNIQUE`, FK |

```java
// 도메인 객체가 스스로 규칙을 지킴
public void cancel() {
    if (this.status == OrderStatus.SHIPPED) {
        throw new BusinessException(ErrorCode.ALREADY_SHIPPED);
    }
    this.status = OrderStatus.CANCELED;
}
```
> 중복 이메일은 서비스에서 `existsByEmail`로 확인하더라도 **동시 요청**이 통과할 수 있으므로 DB **UNIQUE 제약**이 꼭 필요합니다. (`DataIntegrityViolationException`을 409로 변환)

## 6. 면접 질문

1. **스프링에서 예외를 전역으로 처리하는 방법은?**
   → `@RestControllerAdvice`와 `@ExceptionHandler`로 예외 타입별 응답을 한 곳에서 정의합니다. ErrorCode enum과 비즈니스 예외를 두고, 응답은 ProblemDetail 같은 일관된 형식으로 반환합니다.
2. **필터에서 발생한 예외도 `@RestControllerAdvice`가 처리하나요?**
   → 아닙니다. 필터는 DispatcherServlet 앞에서 동작하므로 처리되지 않으며, 시큐리티 예외는 AuthenticationEntryPoint와 AccessDeniedHandler로 처리합니다.
3. **`@NotNull`, `@NotEmpty`, `@NotBlank`의 차이는?**
   → NotNull은 null만, NotEmpty는 null과 빈 값을, NotBlank는 null·빈 문자열·공백 문자열까지 막습니다.
4. **검증은 어느 계층에서 하나요?**
   → 형식·범위는 요청 DTO에서, DB나 상태가 필요한 비즈니스 규칙은 서비스와 도메인에서, 최종적으로 DB 제약 조건으로 보장합니다.

---

## 핵심 정리
- `@RestControllerAdvice` + `ErrorCode` + `BusinessException` + **ProblemDetail(RFC 9457)**
- 500 응답에는 내부 정보 X, 로그에만
- `@Valid` → `MethodArgumentNotValidException`(400), 그룹·메서드 검증은 `@Validated`
- 형식은 DTO, 비즈니스 규칙은 도메인, 최후 방어는 DB 제약
