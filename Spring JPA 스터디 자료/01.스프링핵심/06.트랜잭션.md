# 06. 트랜잭션 (@Transactional)

> **학습 목표**
> - 스프링 트랜잭션 추상화와 `@Transactional`의 동작 원리(프록시)를 설명할 수 있다.
> - 전파 속성(REQUIRED, REQUIRES_NEW 등)과 롤백 규칙을 이해한다.
> - `readOnly`, 격리 수준, 타임아웃 옵션의 의미를 안다.
> - 트랜잭션이 적용되지 않는 대표적인 실수를 피할 수 있다.

---

## 1. 트랜잭션 복습

**트랜잭션**: 모두 성공하거나 모두 실패해야 하는 작업 단위 (ACID). 
예: 주문 생성 + 재고 차감 + 포인트 차감 → 하나라도 실패하면 전부 취소
> ACID, 격리 수준, 이상 현상은 `CS 스터디 자료의 데이터베이스/트랜잭션` 문서 참고.

### 스프링 없이 직접 관리하면
```java
Connection con = dataSource.getConnection();
try {
    con.setAutoCommit(false);
    // 비즈니스 로직 (같은 커넥션을 계속 넘겨야 함)
    con.commit();
} catch (Exception e) {
    con.rollback();
} finally {
    con.close();
}
```
→ 서비스 계층에 JDBC 코드가 섞이고, JPA로 바꾸면 코드도 바뀝니다.

## 2. 스프링 트랜잭션 추상화

```
          @Transactional
                │
     PlatformTransactionManager   ← 추상화 (PSA)
       ├── DataSourceTransactionManager  (JDBC, MyBatis)
       ├── JpaTransactionManager         (JPA)  ← spring-boot-starter-data-jpa가 자동 등록
       └── ...
                │
     TransactionSynchronizationManager  ← 커넥션을 ThreadLocal에 보관
```
트랜잭션 동안 같은 스레드의 Repository들이 **같은 커넥션(같은 EntityManager)** 을 사용합니다. 그래서 커넥션을 파라미터로 넘기지 않아도 됩니다.

### 프록시로 동작
```
Controller → [OrderService 프록시]
               1. transactionManager.getTransaction()   → 커넥션 획득, autocommit=false
               2. target.placeOrder()                    → 실제 로직
               3. 정상 종료: commit / 런타임 예외: rollback
               4. 커넥션 반납
```
> 프록시 기반이라 **자기 호출, private 메서드에는 적용되지 않습니다.** (`→ 03.AOP와프록시.md`)

## 3. 사용법과 위치

```java
@Service
@Transactional(readOnly = true)              // 클래스 기본: 읽기 전용
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final StockService stockService;

    public OrderResponse getOrder(Long id) { ... }      // readOnly = true 적용

    @Transactional                            // 쓰기 메서드만 따로 (메서드가 클래스보다 우선)
    public Long placeOrder(OrderCreateRequest request) {
        stockService.decrease(request.productId(), request.quantity());
        Order order = orderRepository.save(Order.create(request));
        return order.getId();
    }
}
```
- 트랜잭션은 **서비스 계층**에 둡니다 (비즈니스 단위 = 트랜잭션 단위)
- `jakarta.transaction.Transactional`보다 **`org.springframework.transaction.annotation.Transactional`** 사용 (옵션이 더 많음)

---

## 4. 롤백 규칙 ★

| 예외 | 기본 동작 |
|---|---|
| `RuntimeException`, `Error` (Unchecked) | **롤백** |
| `Exception` (Checked, 예: IOException) | **커밋** ❗ |

```java
@Transactional(rollbackFor = Exception.class)    // 체크 예외도 롤백
@Transactional(noRollbackFor = NotifyFailedException.class)
```
> 체크 예외는 "복구 가능한 예외"라는 설계 철학 때문에 커밋됩니다. 실무에서는 비즈니스 예외를 **RuntimeException**으로 만들어 혼란을 줄입니다.

### 예외를 잡아 버리면?
```java
@Transactional
public void placeOrder() {
    try {
        pointService.use();          // 내부에서 RuntimeException
    } catch (RuntimeException e) {
        log.warn("포인트 실패 무시");   // 잡아서 삼킴
    }
}
```
- `pointService.use()`가 **같은 트랜잭션(REQUIRED)** 에 참여했다면, 예외가 그 프록시를 통과할 때 트랜잭션에 **rollback-only** 표시가 됩니다.
- 바깥에서 예외를 잡아도 커밋 시점에 `UnexpectedRollbackException` 발생 → **전체 롤백**
- 독립적으로 실패를 허용하려면 `REQUIRES_NEW`로 분리합니다.

## 5. 전파 속성 (Propagation)

이미 트랜잭션이 진행 중일 때 새 `@Transactional` 메서드를 호출하면 어떻게 할까?

| 속성 | 기존 트랜잭션 있음 | 없음 |
|---|---|---|
| **REQUIRED** (기본) | **참여** (하나의 물리 트랜잭션) | 새로 시작 |
| **REQUIRES_NEW** | 기존을 **보류**하고 **새 트랜잭션** (새 커넥션) | 새로 시작 |
| SUPPORTS | 참여 | 트랜잭션 없이 실행 |
| MANDATORY | 참여 | 예외 |
| NOT_SUPPORTED | 기존 보류, 트랜잭션 없이 | 없이 실행 |
| NEVER | 예외 | 없이 실행 |
| NESTED | 세이브포인트로 중첩 (JDBC만, JPA 미지원) | 새로 시작 |

```
REQUIRED (기본)
 [외부 tx ────────────────────────────]
     └ 내부 메서드 참여 ─┘   내부에서 롤백 → 전체 롤백

REQUIRES_NEW
 [외부 tx ───────┐ 보류      ┌────────]
                 [내부 tx 새로]          내부 롤백은 내부만, 외부는 계속
```
### REQUIRES_NEW 사용 예: 실패해도 남겨야 하는 로그
```java
@Service
public class AuditLogService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void save(String action) { ... }   // 주문이 롤백돼도 감사 로그는 커밋
}
```
> REQUIRES_NEW는 **커넥션을 하나 더** 씁니다. 트래픽이 많을 때 커넥션 풀이 고갈되어 **데드락**처럼 멈출 수 있으니(외부 tx가 커넥션을 잡은 채 내부 tx가 새 커넥션을 기다림) 꼭 필요한 곳에만 씁니다.

## 6. 주요 옵션

### readOnly = true
- JPA: **플러시 모드 MANUAL** → 변경 감지(dirty checking)와 스냅샷 비교 생략 → 성능 향상
- 실수로 엔티티를 수정해도 DB에 반영되지 않음
- DB 드라이버·라우팅에 읽기 전용 힌트 → **읽기 전용 복제본(Replica)으로 라우팅**하는 데 활용 (`LazyConnectionDataSourceProxy` + `AbstractRoutingDataSource`)

### isolation, timeout
```java
@Transactional(isolation = Isolation.READ_COMMITTED, timeout = 3)   // 3초 넘으면 롤백
```
- 기본값은 **DB 기본 격리 수준** (MySQL InnoDB: REPEATABLE READ, PostgreSQL·Oracle: READ COMMITTED)

## 7. 트랜잭션 안에서 하면 안 되는 것

```java
@Transactional
public void placeOrder(...) {
    orderRepository.save(order);
    paymentClient.pay(...);          // ❌ 외부 API (느리면 DB 커넥션을 계속 점유)
    emailSender.send(...);           // ❌ 롤백돼도 메일은 이미 발송됨
}
```
| 문제 | 해결 |
|---|---|
| 긴 트랜잭션 → 커넥션·락 오래 점유 | 외부 호출을 트랜잭션 **밖으로** |
| 롤백돼도 되돌릴 수 없는 작업(메일, 메시지) | **커밋 후 실행**: `@TransactionalEventListener(phase = AFTER_COMMIT)` |
| 메시지 발행과 DB 저장의 원자성 | **Transactional Outbox 패턴** (`→ 미들웨어 스터디 자료의 02.Kafka/03.전달보장과순서.md`) |

```java
@Transactional
public Long placeOrder(OrderCreateRequest request) {
    Order order = orderRepository.save(Order.create(request));
    eventPublisher.publishEvent(new OrderPlacedEvent(order.getId()));
    return order.getId();
}

@Component
public class OrderEventHandler {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)   // 커밋 성공 후에만
    public void sendMail(OrderPlacedEvent event) { ... }
}
```

## 8. 면접 질문

1. **`@Transactional`의 동작 원리는?**
   → 스프링이 빈을 프록시로 감싸서, 메서드 호출 전에 트랜잭션 매니저로 트랜잭션을 시작하고 커넥션을 ThreadLocal에 보관한 뒤, 정상 종료면 커밋, 런타임 예외면 롤백합니다.
2. **체크 예외가 발생하면 롤백되나요?**
   → 기본적으로 커밋됩니다. 런타임 예외와 Error만 롤백되며, 체크 예외도 롤백하려면 rollbackFor를 지정합니다.
3. **REQUIRED와 REQUIRES_NEW의 차이는?**
   → REQUIRED는 기존 트랜잭션에 참여해 하나의 트랜잭션으로 묶이고, REQUIRES_NEW는 기존 트랜잭션을 보류하고 별도 커넥션으로 독립 트랜잭션을 시작해 각각 커밋·롤백됩니다.
4. **내부 메서드의 예외를 바깥에서 catch 했는데 왜 롤백되나요?**
   → 같은 트랜잭션에 참여한 내부 메서드에서 런타임 예외가 발생하면 트랜잭션에 rollback-only 표시가 되어, 바깥에서 잡아도 커밋 시점에 UnexpectedRollbackException과 함께 롤백됩니다.
5. **`readOnly = true`의 효과는?**
   → JPA에서 플러시를 하지 않아 변경 감지와 스냅샷 비교를 생략해 성능이 좋아지고, 읽기 복제본 라우팅에 활용할 수 있습니다.

---

## 핵심 정리
- `@Transactional` = **프록시 + PlatformTransactionManager + ThreadLocal 커넥션**
- 롤백: **Unchecked만** (Checked는 커밋 → `rollbackFor`)
- 전파: REQUIRED(참여, 기본) / REQUIRES_NEW(독립, 커넥션 추가)
- 클래스에 `readOnly = true`, 쓰기 메서드에 `@Transactional`
- 외부 API·메일은 트랜잭션 밖 또는 **AFTER_COMMIT**
