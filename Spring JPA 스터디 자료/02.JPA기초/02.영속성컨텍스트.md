# 02. 영속성 컨텍스트

> **학습 목표**
> - 영속성 컨텍스트와 엔티티 생명주기(비영속·영속·준영속·삭제)를 설명할 수 있다.
> - 1차 캐시, 동일성 보장, 쓰기 지연, 변경 감지, 플러시를 이해한다.
> - 트랜잭션 범위와 영속성 컨텍스트의 관계를 이해한다.
> - `save()` 대신 변경 감지로 수정하는 이유를 설명할 수 있다.

---

## 1. 영속성 컨텍스트란?

**엔티티를 영구 저장하는 환경**으로, 애플리케이션과 DB 사이의 **논리적인 캐시·작업 공간**입니다. `EntityManager`를 통해 접근합니다.

```
  애플리케이션
      │ em.persist(member) / em.find(Member.class, 1L)
      ▼
 ┌───────── 영속성 컨텍스트 ──────────┐
 │  1차 캐시 (Map<@Id, 엔티티>)        │
 │   id=1 → Member(name="kim")        │
 │   id=2 → Member(name="lee")        │
 │  스냅샷 (최초 상태 복사본)            │
 │  쓰기 지연 SQL 저장소 [INSERT, UPDATE]│
 └────────────────┬──────────────────┘
                  │ flush (커밋 직전)
                  ▼
                 DB
```
> 스프링에서는 **트랜잭션 하나 = 영속성 컨텍스트 하나**가 기본입니다. 같은 트랜잭션 안의 모든 Repository가 같은 영속성 컨텍스트를 공유합니다.

---

## 2. 엔티티 생명주기

```
            new Member()
                │
           [비영속 new]
                │ persist()
                ▼
           [영속 managed]  ◀── find(), JPQL 조회 결과
           │      │    ▲
  detach() │      │    │ merge()
  clear()  ▼      │    │
       [준영속 detached]
                  │ remove()
                  ▼
           [삭제 removed]  → flush 시 DELETE
```
| 상태 | 설명 |
|---|---|
| 비영속 | 객체만 생성, 영속성 컨텍스트와 무관 |
| **영속** | 영속성 컨텍스트가 관리 중 → 변경 감지, 지연 로딩 가능 |
| 준영속 | 관리하다가 분리됨 (트랜잭션 종료, `detach`, `clear`) → 변경 감지 ✗, 지연 로딩 시 **예외** |
| 삭제 | 삭제 예약 |

## 3. 영속성 컨텍스트의 기능

### ① 1차 캐시
```java
Member a = em.find(Member.class, 1L);   // DB 조회 (SELECT) → 1차 캐시에 저장
Member b = em.find(Member.class, 1L);   // 1차 캐시에서 반환, SQL 없음
```
- 트랜잭션 범위의 짧은 캐시라 **성능 이점은 크지 않습니다.** (애플리케이션 전체 캐시는 2차 캐시·Redis)
- JPQL(`findByName` 등)은 **항상 DB에 SQL을 실행**합니다. 결과는 1차 캐시와 비교해 이미 있으면 기존 엔티티를 사용합니다.

### ② 동일성 보장
```java
a == b;   // true — 같은 트랜잭션에서 같은 ID는 같은 인스턴스
```
→ 애플리케이션 수준에서 **REPEATABLE READ** 수준의 일관성을 제공

### ③ 쓰기 지연 (Transactional write-behind)
```java
em.persist(memberA);   // INSERT SQL을 쓰기 지연 저장소에 보관
em.persist(memberB);
tx.commit();           // flush → INSERT 2개 실행 → 커밋
```
- `hibernate.jdbc.batch_size` 설정 시 모아서 **JDBC 배치**로 전송
- ⚠️ ID 생성 전략이 **IDENTITY**(MySQL AUTO_INCREMENT)면 ID를 알기 위해 `persist()` 즉시 INSERT → **배치 INSERT 불가** (`→ 03.엔티티매핑.md`)

### ④ 변경 감지 (Dirty Checking) ★
```java
@Transactional
public void changeName(Long id, String name) {
    Member member = memberRepository.findById(id).orElseThrow();
    member.changeName(name);        // 값만 바꿈. save() 호출 X
}                                   // 커밋 → flush → 스냅샷과 비교 → UPDATE 자동 실행
```
```
flush 시점
1. 1차 캐시의 엔티티와 스냅샷(처음 조회 상태)을 비교
2. 바뀐 엔티티의 UPDATE SQL 생성 → 쓰기 지연 저장소
3. SQL 전송
```
- 기본적으로 **모든 컬럼을 UPDATE** (SQL 재사용 위해). 컬럼이 많으면 `@DynamicUpdate`로 바뀐 컬럼만
- **영속 상태**의 엔티티만 변경 감지 대상

### ⑤ 지연 로딩
연관 엔티티를 실제로 쓸 때 조회 (`→ 05.프록시와지연로딩.md`)

## 4. 플러시 (Flush)

**영속성 컨텍스트의 변경 내용을 DB에 반영(SQL 전송)** 하는 것. 1차 캐시를 비우는 것이 **아닙니다.** 커밋과도 다릅니다(플러시 후 롤백 가능).

| 플러시 시점 | 설명 |
|---|---|
| 트랜잭션 커밋 직전 | 자동 |
| **JPQL 쿼리 실행 직전** | 자동 (쿼리 결과에 아직 반영 안 된 변경이 빠지지 않도록) |
| `em.flush()` | 직접 호출 (테스트 등) |

```java
em.persist(member);                        // 아직 INSERT 안 됨
List<Member> list = em.createQuery("select m from Member m", Member.class)
        .getResultList();                  // 직전에 자동 flush → member 포함됨
```
> `@Transactional(readOnly = true)`는 Hibernate 세션 플러시 모드를 MANUAL로 설정해 **플러시·변경 감지를 생략**합니다.

## 5. save()를 다시 호출하지 않아도 되는 이유

```java
// ❌ 불필요한 save
Member member = memberRepository.findById(id).orElseThrow();
member.changeName(name);
memberRepository.save(member);     // 이미 영속 상태 → merge 호출 (불필요)

// ✅ 변경 감지
member.changeName(name);
```

### merge 주의 (준영속 엔티티 수정)
```java
// 컨트롤러에서 받은 DTO로 엔티티를 new 해서 id를 세팅하고 save → merge
Member detached = new Member(id, request.name(), null);   // email = null
memberRepository.save(detached);
```
- merge는 DB에서 조회한 영속 엔티티에 **준영속 객체의 모든 필드 값을 덮어씀** → 요청에 없던 필드가 **null로 덮어써질 수 있음**
- ✅ **조회 → 엔티티의 의미 있는 메서드로 변경 → 변경 감지**가 원칙
- Hibernate 7에서는 세션의 `update()`, `saveOrUpdate()` 같은 준영속 재연결 API가 **제거**되어 `merge()`만 남았습니다.

## 6. 트랜잭션 범위와 준영속

```java
// 서비스
@Transactional(readOnly = true)
public Order findOrder(Long id) { return orderRepository.findById(id).orElseThrow(); }

// 컨트롤러 (OSIV off)
Order order = orderService.findOrder(id);     // 트랜잭션 종료 → 준영속
order.getMember().getName();                   // ❌ LazyInitializationException
```
→ 서비스에서 **DTO로 변환해 반환**하거나 **fetch join**으로 필요한 데이터를 미리 조회합니다. (`→ 03.JPA실전/04.성능최적화.md`의 OSIV)

## 7. 면접 질문

1. **영속성 컨텍스트란? 이점은?**
   → 엔티티를 관리하는 1차 캐시이자 작업 공간으로, 1차 캐시와 동일성 보장, 쓰기 지연, 변경 감지, 지연 로딩을 제공합니다. 스프링에서는 트랜잭션 단위로 생성됩니다.
2. **변경 감지는 어떻게 동작하나요?**
   → 엔티티를 처음 영속화할 때 스냅샷을 저장하고, 플러시 시점에 현재 엔티티와 스냅샷을 비교해 변경된 엔티티의 UPDATE SQL을 자동으로 생성해 실행합니다.
3. **플러시란? 언제 일어나나요?**
   → 영속성 컨텍스트의 변경 내용을 DB에 SQL로 반영하는 것으로, 트랜잭션 커밋 직전, JPQL 실행 직전, 직접 flush 호출 시 일어납니다. 1차 캐시를 비우지는 않습니다.
4. **merge의 문제점은?**
   → 준영속 객체의 모든 값을 영속 엔티티에 덮어쓰기 때문에 값이 없는 필드는 null로 바뀔 수 있습니다. 엔티티를 조회한 뒤 필요한 필드만 바꿔 변경 감지를 사용하는 것이 안전합니다.

---

## 핵심 정리
- 영속성 컨텍스트 = **트랜잭션 범위**의 엔티티 관리 공간
- 기능: **1차 캐시·동일성·쓰기 지연·변경 감지·지연 로딩**
- 수정은 `save()`가 아니라 **조회 후 변경 → 변경 감지**
- 플러시 = SQL 반영 (커밋 직전, JPQL 직전), 캐시 비우기 아님
- 트랜잭션 밖 = 준영속 → 지연 로딩 예외
