# 03. 엔티티 매핑

> **학습 목표**
> - `@Entity`, `@Table`, `@Column`, `@Id`, `@Enumerated` 등 기본 매핑을 할 수 있다.
> - 기본 키 생성 전략(IDENTITY, SEQUENCE, UUID)의 차이와 장단점을 설명할 수 있다.
> - `@Embedded` 값 타입, `@MappedSuperclass` 공통 필드, Auditing을 활용할 수 있다.
> - 좋은 엔티티 설계 원칙(기본 생성자, setter 지양)을 안다.

---

## 1. 기본 엔티티

```java
@Entity
@Table(name = "orders",
       indexes = @Index(name = "idx_orders_member_created", columnList = "member_id, created_at"))
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)     // JPA는 기본 생성자 필요 (프록시·리플렉션용)
public class Order extends BaseTimeEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 30)
    private String orderNo;

    @Enumerated(EnumType.STRING)                        // ★ ORDINAL 금지
    @Column(nullable = false, length = 20)
    private OrderStatus status;

    @Column(nullable = false)
    private long totalPrice;

    @Embedded
    private Address address;

    @Version                                             // 낙관적 락 (→ 03.JPA실전/05.동시성과락.md)
    private Long version;

    private Order(String orderNo, Address address, long totalPrice) {
        this.orderNo = orderNo;
        this.address = address;
        this.totalPrice = totalPrice;
        this.status = OrderStatus.CREATED;
    }

    public static Order create(String orderNo, Address address, long totalPrice) {
        return new Order(orderNo, address, totalPrice);
    }

    public void cancel() {
        if (status == OrderStatus.SHIPPED) throw new IllegalStateException("배송된 주문은 취소 불가");
        this.status = OrderStatus.CANCELED;
    }
}
```

| 애노테이션 | 의미 |
|---|---|
| `@Entity` | JPA가 관리하는 엔티티 (기본 생성자 필수, final 클래스 불가) |
| `@Table(name)` | 테이블 이름 (`order`는 SQL 예약어라 `orders`) |
| `@Column` | `nullable`, `length`, `unique`, `columnDefinition`, `updatable=false` |
| `@Enumerated` | enum 저장 방식 |
| `@Lob` | 큰 텍스트·바이너리 |
| `@Transient` | 매핑하지 않는 필드 |
| `java.time.*` | `LocalDateTime`, `LocalDate` 등은 애노테이션 없이 매핑 |

### `EnumType.ORDINAL`을 쓰면 안 되는 이유
```java
enum OrderStatus { CREATED, PAID, SHIPPED }     // ORDINAL: 0, 1, 2 로 저장
enum OrderStatus { CREATED, CANCELED, PAID, SHIPPED }   // 중간에 추가하면
// 기존 PAID(1)가 이제 CANCELED로 읽힘 → 데이터 오염
```

## 2. 기본 키 생성 전략

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **IDENTITY** | DB AUTO_INCREMENT (MySQL) | 간단 | `persist()` 시 **즉시 INSERT** → JDBC **배치 INSERT 불가** |
| **SEQUENCE** | DB 시퀀스 (PostgreSQL, Oracle) | `allocationSize`(기본 50)만큼 미리 받아 **배치 INSERT 가능** | MySQL은 시퀀스 없음 |
| TABLE | 키 생성 전용 테이블 | 모든 DB | 느림, 락 경합 |
| **UUID** | `@GeneratedValue(strategy = GenerationType.UUID)` 또는 `@UuidGenerator` | 분산 환경에서 충돌 없이 생성, ID 추측 불가 | 16바이트, **랜덤 UUID(v4)는 B-Tree 인덱스 단편화** |

```java
// PostgreSQL 권장
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
@SequenceGenerator(name = "order_seq", sequenceName = "order_seq", allocationSize = 50)
private Long id;
```

### 기본 키 선택 기준
- **자연 키(주민번호, 이메일) ✗** → 바뀔 수 있음. **대리 키(Long, UUID)** 사용
- 외부에 노출되는 ID는 순차 Long이면 **추측 가능**(다른 사람 주문 /orders/43) → 권한 검사 필수, 필요하면 별도 공개용 ID(UUID, 주문번호)
- UUID를 PK로 쓴다면 **시간순 정렬되는 UUID v7** 이 인덱스에 유리 (Hibernate 7: `@UuidGenerator(style = UuidGenerator.Style.VERSION_7)`, 아직 incubating)

## 3. 값 타입: `@Embeddable`

```java
@Embeddable
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@EqualsAndHashCode
public class Address {
    @Column(length = 10)
    private String zipcode;
    private String street;
    private String detail;

    public Address(String zipcode, String street, String detail) { ... }
}
```
- 테이블은 `orders(zipcode, street, detail)` 컬럼으로 펼쳐짐
- 의미 있는 단위로 묶어 **응집도 ↑**, 검증·로직을 값 객체 안에 (`Money`, `Address`, `Period`)
- **불변**으로 만들기 (setter X) — 여러 엔티티가 같은 인스턴스를 공유하면 한쪽 변경이 다른 쪽에 전파되는 부작용
- 같은 타입을 두 번 쓰면 `@AttributeOverrides`로 컬럼 이름 변경 (집 주소, 회사 주소)
- Hibernate 6.2+ / JPA 3.2: **record를 `@Embeddable`** 로 사용 가능

## 4. 공통 필드: `@MappedSuperclass` + Auditing

```java
@Getter
@MappedSuperclass                                  // 테이블 X, 필드만 상속
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseTimeEntity {

    @CreatedDate
    @Column(updatable = false, nullable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(nullable = false)
    private LocalDateTime updatedAt;
}

@Configuration
@EnableJpaAuditing
public class JpaConfig { }
```
- `@CreatedBy`, `@LastModifiedBy` + `AuditorAware<Long>` 빈으로 작성자 자동 기록 (SecurityContext에서 사용자 ID)

## 5. 상속 매핑 (참고)

| 전략 | 테이블 | 특징 |
|---|---|---|
| JOINED | 부모·자식 각각 테이블 + 조인 | 정규화, 조회 시 조인 |
| SINGLE_TABLE (기본) | 한 테이블 + 구분 컬럼(DTYPE) | 조회 빠름, 자식 컬럼은 nullable |
| TABLE_PER_CLASS | 자식마다 테이블 | 비권장 (UNION 쿼리) |

> 실무에서는 상속 매핑보다 **단순한 테이블 + 타입 컬럼** 또는 조합(embedded)을 선호하는 경우가 많습니다.

## 6. 좋은 엔티티 설계 원칙

| 원칙 | 이유 |
|---|---|
| `@NoArgsConstructor(access = PROTECTED)` | JPA용 기본 생성자는 열어 두되 무분별한 `new` 방지 |
| **setter 지양**, 의도가 드러나는 메서드 | `order.setStatus(CANCELED)` 대신 `order.cancel()` — 규칙 검증을 엔티티 안에 |
| 정적 팩토리 / 빌더로 생성 | 필수 값 누락 방지 |
| `@Data`, `@ToString` 주의 | 연관 엔티티까지 toString → **무한 루프·지연 로딩 발생** |
| `equals/hashCode` 신중하게 | 기본(동일성)이 가장 안전. 필요하면 **ID 기반 + 프록시 고려** (`getClass()` 대신 `Hibernate.getClass()`) |
| **엔티티를 API 응답으로 직접 반환 ✗** | DTO로 변환 |
| `nullable`, `length`, `unique` 명시 | 스키마와 의도가 문서화되고 `ddl-auto: validate`로 검증 |

## 7. 면접 질문

1. **`EnumType.ORDINAL`을 쓰면 안 되는 이유는?**
   → enum의 순서 숫자로 저장하기 때문에 중간에 값을 추가하거나 순서를 바꾸면 기존 데이터가 다른 값으로 해석됩니다. STRING을 사용합니다.
2. **IDENTITY 전략의 단점은?**
   → DB가 INSERT 시점에 ID를 생성하므로 persist 시 즉시 INSERT가 실행되어 쓰기 지연을 활용한 JDBC 배치 INSERT를 할 수 없습니다. 대량 저장은 SEQUENCE 전략이나 JdbcTemplate batchUpdate를 사용합니다.
3. **엔티티에 기본 생성자가 필요한 이유는?**
   → JPA 구현체가 리플렉션으로 객체를 생성하고 지연 로딩 프록시가 엔티티를 상속하기 때문이며, 외부 생성을 막기 위해 protected로 둡니다.
4. **엔티티에 setter를 지양하는 이유는?**
   → 어디서든 값을 바꿀 수 있어 변경 지점 추적이 어렵고 도메인 규칙이 흩어지기 때문에, cancel처럼 의도가 드러나는 메서드로 규칙과 함께 변경합니다.

---

## 핵심 정리
- `@Enumerated(EnumType.STRING)` 필수, `@Column`으로 제약 명시
- PK: MySQL IDENTITY(배치 X), PostgreSQL SEQUENCE(배치 O), UUID는 v7 고려
- `@Embeddable` 불변 값 객체, `@MappedSuperclass` + Auditing으로 생성·수정 시간
- PROTECTED 기본 생성자, **setter 대신 도메인 메서드**, 엔티티 직접 반환 ✗
