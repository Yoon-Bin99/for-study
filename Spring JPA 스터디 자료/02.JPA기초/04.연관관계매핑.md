# 04. 연관관계 매핑

> **학습 목표**
> - 단방향·양방향 연관관계와 **연관관계의 주인** 개념을 설명할 수 있다.
> - `@ManyToOne`, `@OneToMany`, `@OneToOne`, `@ManyToMany`의 올바른 사용법을 안다.
> - 양방향 관계에서 연관관계 편의 메서드를 만드는 이유를 이해한다.
> - cascade와 orphanRemoval을 언제 써야 하는지 판단할 수 있다.

---

## 1. 테이블과 객체의 연관관계 차이

```
테이블: 외래 키 하나로 양쪽 조인 가능
  member(id, name, team_id FK) ── team(id, name)
  SELECT * FROM member m JOIN team t ON m.team_id = t.id   (회원 → 팀)
  SELECT * FROM team t JOIN member m ON m.team_id = t.id   (팀 → 회원)

객체: 참조가 있는 쪽에서만 탐색 가능
  member.getTeam()      ✅ (Member에 team 필드)
  team.getMembers()     ❌ (Team에 members 필드가 없으면)
```
→ 객체의 양방향 = 사실은 **단방향 두 개**. 그런데 외래 키는 하나 → **둘 중 누가 외래 키를 관리할지** 정해야 합니다.

---

## 2. 다대일 단방향 (가장 기본, 가장 많이 씀)

```java
@Entity
public class Member {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)        // ★ 항상 LAZY
    @JoinColumn(name = "team_id")              // 외래 키 컬럼
    private Team team;
}
```
> **외래 키가 있는 쪽(N쪽)에 `@ManyToOne`** 을 둡니다. 처음 설계는 **단방향으로 충분**하고, 반대 방향 조회가 꼭 필요할 때만 양방향을 추가합니다.

---

## 3. 양방향과 연관관계의 주인

```java
@Entity
public class Team {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "team")              // 주인이 아님 → 읽기 전용
    private List<Member> members = new ArrayList<>();
}
```
| 구분 | 연관관계의 **주인** | 주인이 아닌 쪽 |
|---|---|---|
| 위치 | **외래 키가 있는 쪽** (N, `@ManyToOne`) | `mappedBy` 지정한 쪽 |
| 외래 키 등록·수정 | ✅ | ❌ (값을 넣어도 DB에 반영 안 됨) |
| 조회 | ✅ | ✅ |

### 흔한 실수
```java
Team team = new Team("A");
em.persist(team);

Member member = new Member("kim");
team.getMembers().add(member);     // ❌ 주인이 아닌 쪽에만 설정 → team_id = NULL
em.persist(member);
```

### 연관관계 편의 메서드
```java
public class Member {
    public void changeTeam(Team team) {
        if (this.team != null) {
            this.team.getMembers().remove(this);   // 기존 팀에서 제거
        }
        this.team = team;                           // 주인 쪽 (DB 반영)
        team.getMembers().add(this);                // 객체 상태도 일관되게 (같은 트랜잭션에서 바로 조회 시)
    }
}
```
> 양쪽에 다 값을 넣어야 **flush 전 같은 트랜잭션** 안에서도, 그리고 JPA 없는 순수 객체 테스트에서도 일관된 상태가 됩니다.

## 4. 일대다 단방향 (비권장)

```java
@OneToMany
@JoinColumn(name = "team_id")       // Team이 Member 테이블의 FK를 관리
private List<Member> members;
```
- 엔티티는 Team인데 FK는 member 테이블 → **추가 UPDATE SQL** 발생, 이해하기 어려움
- → **다대일 단방향 또는 양방향**으로 대체

---

## 5. 일대일 `@OneToOne`

```java
@Entity
public class Member {
    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "locker_id", unique = true)
    private Locker locker;
}
```
- 외래 키를 **주 테이블(자주 조회하는 쪽)** 에 두는 것이 일반적
- ⚠️ 외래 키가 **없는 쪽**(`mappedBy`)에서 조회하면 **LAZY가 동작하지 않을 수 있음** — 프록시를 만들려면 값이 있는지(null인지) 알아야 해서 추가 조회를 함

---

## 6. 다대다 `@ManyToMany` (사용 ✗)

```
member ── member_product(member_id, product_id) ── product
```
- 연결 테이블에 **주문 수량, 주문 일시** 같은 컬럼을 추가할 수 없음
- → 연결 테이블을 **엔티티로 승격**: `Member 1:N OrderItem N:1 Product`

```java
@Entity
public class OrderItem {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    private Order order;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_id")
    private Product product;

    private int quantity;
    private long orderPrice;      // 주문 당시 가격
}
```

## 7. cascade와 orphanRemoval

```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> orderItems = new ArrayList<>();

    public void addItem(OrderItem item) {
        orderItems.add(item);
        item.assignOrder(this);
    }
}

Order order = Order.create(...);
order.addItem(item1);
order.addItem(item2);
orderRepository.save(order);     // cascade → item1, item2도 함께 persist
order.getOrderItems().remove(0); // orphanRemoval → DELETE
```
| 옵션 | 의미 |
|---|---|
| `cascade = PERSIST` | 부모 저장 시 자식도 저장 |
| `cascade = REMOVE` | 부모 삭제 시 자식도 삭제 |
| `cascade = ALL` | 전부 |
| `orphanRemoval = true` | 컬렉션에서 빠진 자식(고아)을 삭제 |

### 사용 기준
- ✅ 자식의 **생명주기를 부모가 완전히 소유**할 때 (Order–OrderItem, Post–Attachment)
- ❌ 자식을 **다른 엔티티도 참조**할 때 (OrderItem → Product에 cascade REMOVE: 주문 삭제 시 상품까지 삭제!)
- `CascadeType.REMOVE`와 orphanRemoval은 자식을 **한 건씩 DELETE** → 대량 삭제는 벌크 쿼리로

> 이렇게 부모를 통해서만 자식을 다루는 묶음을 DDD에서 **애그리거트(Aggregate)** 라고 합니다. 애그리거트 루트(Order)를 통해서만 내부(OrderItem)를 변경합니다.

## 8. 연관관계 설계 체크리스트

| 체크 | 권장 |
|---|---|
| 페치 전략 | **모든 연관관계 LAZY** (`@ManyToOne`, `@OneToOne`은 기본이 EAGER라 명시 필요) |
| 방향 | **단방향 우선**, 필요할 때 양방향 |
| 주인 | **외래 키가 있는 쪽** (`@ManyToOne`) |
| 컬렉션 초기화 | `= new ArrayList<>()` 필드에서 초기화 (null 방지, Hibernate 컬렉션 래핑) |
| 다대다 | 연결 엔티티로 |
| cascade | 생명주기를 소유할 때만 |
| 다른 애그리거트 참조 | 객체 대신 **ID로 참조**도 고려 (`private Long memberId;`) → 결합도 ↓ |

## 9. 면접 질문

1. **연관관계의 주인이란?**
   → 양방향 관계에서 외래 키를 관리(등록·수정)하는 쪽으로, 외래 키가 있는 N쪽(@ManyToOne)이 주인이고, 반대쪽은 mappedBy로 지정해 읽기만 합니다.
2. **양방향 관계에서 주인이 아닌 쪽에만 값을 넣으면?**
   → DB에 외래 키가 저장되지 않아 null이 됩니다. 주인 쪽에 값을 설정하고, 객체 일관성을 위해 편의 메서드로 양쪽 모두 설정합니다.
3. **`@ManyToMany`를 쓰지 않는 이유는?**
   → 연결 테이블에 수량·일시 같은 추가 컬럼을 넣을 수 없고 예상치 못한 쿼리가 나가므로, 연결 테이블을 엔티티로 만들어 일대다·다대일로 풀어냅니다.
4. **cascade는 언제 쓰나요?**
   → 자식의 생명주기를 부모가 완전히 소유할 때(주문과 주문 항목)만 쓰고, 자식을 다른 엔티티가 참조한다면 사용하지 않습니다.

---

## 핵심 정리
- 기본은 **`@ManyToOne(fetch = LAZY)` 단방향**
- 주인 = **외래 키 있는 쪽**, `mappedBy`는 읽기 전용 → **편의 메서드**로 양쪽 설정
- 일대다 단방향·다대다 ✗ → 연결 엔티티
- cascade·orphanRemoval은 **생명주기 소유(애그리거트)** 일 때만
