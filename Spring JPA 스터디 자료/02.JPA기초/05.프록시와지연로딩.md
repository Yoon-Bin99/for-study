# 05. 프록시와 지연 로딩

> **학습 목표**
> - JPA 프록시 객체의 구조와 초기화 과정을 설명할 수 있다.
> - 즉시 로딩(EAGER)과 지연 로딩(LAZY)의 차이와 **LAZY를 기본으로 해야 하는 이유**를 설명할 수 있다.
> - `LazyInitializationException`의 원인과 해결법을 안다.
> - 프록시 때문에 생기는 함정(타입 비교, equals)을 피할 수 있다.

---

## 1. 왜 프록시가 필요한가?

회원을 조회할 때 **팀 정보가 항상 필요하지는 않습니다.**
```java
Member member = em.find(Member.class, 1L);
System.out.println(member.getName());          // 팀 정보는 안 씀
// 매번 member JOIN team 하면 낭비
```
→ 연관 엔티티는 **가짜 객체(프록시)** 로 채워 두고, 실제로 사용할 때 조회합니다.

---

## 2. 프록시의 구조

```
em.getReference(Member.class, 1L)  또는 LAZY 연관 엔티티

 ┌──────────────────────┐
 │ Member$HibernateProxy │  ← 실제 Member 클래스를 상속 (바이트코드 생성)
 │  id = 1               │  ← ID는 알고 있음
 │  target = null ───────┼──▶ (아직 실제 엔티티 없음)
 └──────────────────────┘

member.getName() 호출
 1. target == null → 영속성 컨텍스트에 초기화 요청
 2. DB 조회 (SELECT ... FROM member WHERE id = 1)
 3. 실제 Member 엔티티 생성, target에 연결
 4. target.getName() 위임
```
| 특징 | 설명 |
|---|---|
| 상속 기반 | 실제 클래스를 상속 → 엔티티 클래스·메서드가 **final이면 안 됨** |
| 한 번만 초기화 | 프록시가 실제 엔티티로 **바뀌는 것이 아니라**, 내부 target을 통해 접근 |
| ID 조회는 초기화 X | `member.getTeam().getId()` 는 SQL 없음 (Hibernate) |
| 영속성 컨텍스트 필요 | 준영속 상태에서 초기화하면 `LazyInitializationException` |
| 1차 캐시에 있으면 | 이미 실제 엔티티가 영속성 컨텍스트에 있으면 `getReference()`도 실제 엔티티 반환 (동일성 보장) |

```java
Hibernate.isInitialized(member.getTeam());   // 초기화 여부
Hibernate.initialize(member.getTeam());       // 강제 초기화
```

## 3. 즉시 로딩 vs 지연 로딩

```java
@ManyToOne(fetch = FetchType.EAGER)   // 즉시: Member 조회 시 Team도 함께 (JOIN 또는 추가 SELECT)
@ManyToOne(fetch = FetchType.LAZY)    // 지연: Team은 프록시, 사용할 때 SELECT
```
| 연관관계 | JPA 기본값 |
|---|---|
| `@ManyToOne`, `@OneToOne` | **EAGER** ❗ → LAZY로 바꿔야 함 |
| `@OneToMany`, `@ManyToMany` | LAZY |

### EAGER를 쓰면 안 되는 이유
1. **예상하지 못한 SQL**: 연관이 많으면 조회 한 번에 조인이 줄줄이
2. **JPQL에서 N+1 발생**
```java
List<Member> members = em.createQuery("select m from Member m", Member.class).getResultList();
// 1. SELECT * FROM member              → 회원 100명
// 2. EAGER라서 각 회원의 team을 즉시 로딩 → SELECT * FROM team WHERE id = ? × (팀 수만큼)
```
JPQL은 SQL로 그대로 번역되어 member만 조회한 뒤, EAGER 설정을 보고 **팀을 따로 조회**합니다.

→ **모든 연관관계는 LAZY**, 함께 필요한 경우만 **fetch join / @EntityGraph** 로 한 번에 조회 (`→ 03.JPA실전/01.N+1문제.md`)

## 4. LazyInitializationException

```
org.hibernate.LazyInitializationException: could not initialize proxy [Team#1] - no Session
```
**원인**: 트랜잭션(영속성 컨텍스트)이 끝난 후 프록시를 초기화하려고 함

```java
@Transactional(readOnly = true)
public Member find(Long id) { return memberRepository.findById(id).orElseThrow(); }

// 컨트롤러 (OSIV off)
Member member = memberService.find(1L);
return new MemberResponse(member.getName(), member.getTeam().getName());   // ❌ 예외
```
| 해결 | 설명 |
|---|---|
| ✅ **서비스에서 DTO로 변환** | 트랜잭션 안에서 필요한 값을 꺼내 DTO 반환 |
| ✅ **fetch join / @EntityGraph** | 처음부터 함께 조회 |
| OSIV 켜기 | 컨트롤러·뷰까지 영속성 컨텍스트 유지 → 커넥션 오래 점유 (`→ 03.JPA실전/04.성능최적화.md`) |
| ❌ EAGER로 변경 | N+1 등 다른 문제 |
| ❌ `hibernate.enable_lazy_load_no_trans` | 초기화할 때마다 새 커넥션 → 안티 패턴 |

## 5. 프록시 함정

### ① 타입 비교
```java
Member m = em.getReference(Member.class, 1L);
m.getClass() == Member.class;    // false! (Member$HibernateProxy...)
m instanceof Member;             // true  ✅ instanceof 사용
```

### ② equals 구현
```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Member other)) return false;          // getClass() 비교 ✗
    return id != null && id.equals(other.getId());           // 필드 직접 접근(other.id) ✗ → getter 사용
}
@Override
public int hashCode() { return getClass().hashCode(); }       // ID 생성 전후 값이 바뀌지 않게 (상수)
```
- 프록시의 필드는 비어 있으므로 `other.id`가 아니라 **`other.getId()`** 로 접근

### ③ 상속 관계 다운캐스팅
`Item` 프록시는 `Album`으로 캐스팅되지 않을 수 있음 → `Hibernate.unproxy(item)` 후 캐스팅

## 6. 면접 질문

1. **JPA 프록시란?**
   → 실제 엔티티를 상속한 가짜 객체로 ID만 가지고 있다가, 실제 데이터에 처음 접근할 때 영속성 컨텍스트를 통해 DB를 조회해 내부 target을 초기화하고 호출을 위임합니다.
2. **지연 로딩을 기본으로 써야 하는 이유는?**
   → 즉시 로딩은 필요 없는 연관 엔티티까지 조회하고 JPQL에서 N+1 문제를 일으키며 SQL을 예측하기 어렵습니다. 모두 LAZY로 두고 필요한 경우 fetch join으로 함께 조회합니다.
3. **LazyInitializationException의 원인과 해결은?**
   → 영속성 컨텍스트가 종료된 준영속 상태에서 프록시를 초기화할 때 발생합니다. 트랜잭션 안에서 DTO로 변환하거나 fetch join으로 미리 조회해 해결합니다.

---

## 핵심 정리
- 프록시 = 엔티티 **상속** 가짜 객체, 처음 사용할 때 초기화 (ID 조회는 X)
- `@ManyToOne`, `@OneToOne` 기본 EAGER → **전부 LAZY로**
- 필요할 때만 **fetch join**, 예외는 **트랜잭션 안에서 DTO 변환**
- 프록시 비교는 `instanceof`, equals는 **getter**로
