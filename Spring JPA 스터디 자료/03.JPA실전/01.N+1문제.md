# 01. N+1 문제

> **학습 목표**
> - N+1 문제가 무엇이고 왜 발생하는지 설명할 수 있다.
> - fetch join, `@EntityGraph`, `default_batch_fetch_size`, DTO 조회로 해결할 수 있다.
> - 컬렉션 fetch join과 페이징을 함께 쓸 때의 문제를 이해한다.
> - 각 해결책을 상황에 맞게 선택할 수 있다.

---

## 1. N+1 문제란?

**쿼리 1번**으로 N개의 엔티티를 조회했는데, 각 엔티티의 연관 데이터를 조회하느라 **추가 쿼리가 N번** 실행되는 문제입니다.

```java
List<Order> orders = orderRepository.findAll();          // 1번: SELECT * FROM orders  (100건)
for (Order order : orders) {
    System.out.println(order.getMember().getName());     // N번: SELECT * FROM member WHERE id = ?
}
// 총 101번 쿼리
```
```
SELECT * FROM orders;
SELECT * FROM member WHERE id = 1;
SELECT * FROM member WHERE id = 2;
SELECT * FROM member WHERE id = 3;
... (회원 수만큼)
```
> 같은 회원은 1차 캐시에서 꺼내므로 정확히는 "서로 다른 연관 엔티티 수"만큼 실행됩니다. 로컬에선 데이터가 적어 티가 안 나다가 **운영에서 갑자기 느려지는** 대표적인 원인입니다.

### EAGER로 바꾸면 해결될까? ❌
JPQL `select o from Order o`는 orders만 조회하는 SQL로 번역되고, 그 후 EAGER 설정 때문에 **즉시 N번 추가 조회** → 똑같이 N+1. 발생 시점만 앞당겨집니다.

---

## 2. 해결 ① fetch join

**JPQL에서 연관 엔티티를 SQL JOIN으로 한 번에 조회**합니다.
```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("select o from Order o join fetch o.member where o.status = :status")
    List<Order> findAllWithMember(@Param("status") OrderStatus status);
}
```
```sql
SELECT o.*, m.* FROM orders o INNER JOIN member m ON o.member_id = m.id WHERE o.status = ?
```
- **ToOne 관계**(`@ManyToOne`, `@OneToOne`)는 여러 개를 fetch join 해도 데이터가 늘어나지 않음 → **자유롭게 사용**
- `join fetch`는 INNER JOIN → 연관이 없을 수 있으면 `left join fetch`

### 일반 join vs fetch join
| | `join` | `join fetch` |
|---|---|---|
| SELECT 대상 | Order만 (조건 필터링용) | Order + **Member 함께 영속화** |
| 연관 엔티티 | 여전히 프록시 → 사용 시 N+1 | 실제 엔티티 |

---

## 3. 해결 ② `@EntityGraph`

JPQL 없이 메서드 이름 쿼리에 fetch join을 적용합니다. (LEFT OUTER JOIN)
```java
@EntityGraph(attributePaths = {"member", "delivery"})
List<Order> findByStatus(OrderStatus status);

@EntityGraph(attributePaths = "member")
@Query("select o from Order o where o.createdAt >= :from")
List<Order> findRecent(@Param("from") LocalDateTime from);
```

## 4. 컬렉션 fetch join의 문제 ★

```java
@Query("select o from Order o join fetch o.orderItems")
List<Order> findAllWithItems();
```
```
orders 2건, 각각 주문 항목 3개 → SQL 결과 6행 (일대다 조인 = 데이터 뻥튀기)
```
- **Hibernate 6+** 는 같은 엔티티 중복을 자동으로 제거 (예전에는 `distinct` 필요)
- ⚠️ **페이징 불가**: 
```java
@Query("select o from Order o join fetch o.orderItems")
Page<Order> findAllWithItems(Pageable pageable);
// WARN HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
// → 전체 데이터를 메모리로 읽은 뒤 애플리케이션에서 페이징 → OOM 위험
```
- ⚠️ 컬렉션 **두 개 이상** fetch join → `MultipleBagFetchException` (List 두 개) 또는 카테시안 곱

> `hibernate.query.fail_on_pagination_over_collection_fetch=true`로 설정하면 메모리 페이징 시 경고 대신 **예외**를 던져 실수를 막을 수 있습니다.

---

## 5. 해결 ③ `default_batch_fetch_size` (컬렉션 + 페이징의 정답)

지연 로딩 시 연관 엔티티를 **한 번에 IN 쿼리로 묶어서** 조회합니다.
```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100     # 보통 100~1000
```
```java
// ToOne은 fetch join, 컬렉션은 지연 로딩 + 배치 사이즈
@Query("select o from Order o join fetch o.member")
Page<Order> findPage(Pageable pageable);       // 페이징 OK (ToOne fetch join)

for (Order o : page) {
    o.getOrderItems().size();                    // 지연 로딩
}
```
```sql
SELECT ... FROM orders o JOIN member m ... LIMIT 20;                       -- 1번
SELECT ... FROM order_item WHERE order_id IN (?, ?, ?, ... 20개);           -- 1번
```
→ **1 + N → 1 + 1** (N/배치크기)

| 방식 | 설명 |
|---|---|
| 전역 | `default_batch_fetch_size` |
| 개별 | `@BatchSize(size = 100)` 를 컬렉션 필드나 엔티티 클래스에 |

## 6. 해결 ④ DTO로 직접 조회

화면·API에 필요한 컬럼만 조회합니다.
```java
public record OrderSummary(Long orderId, String memberName, OrderStatus status, long totalPrice) { }

@Query("""
       select new com.shop.order.dto.OrderSummary(o.id, m.name, o.status, o.totalPrice)
       from Order o join o.member m
       where o.status = :status
       """)
List<OrderSummary> findSummaries(@Param("status") OrderStatus status);
```
- 장점: 필요한 컬럼만, 영속성 컨텍스트 관리 비용 X → **조회 성능 최고**
- 단점: 재사용성 낮음, 변경 감지 불가 (조회 전용), 패키지 경로 문자열
- QueryDSL `Projections.constructor` 또는 `@QueryProjection`으로 더 편하게 (`→ 03.QueryDSL과동적쿼리.md`)

## 7. 선택 가이드

```
1. 기본: 모든 연관관계 LAZY + default_batch_fetch_size: 100
2. ToOne 관계가 함께 필요 → fetch join / @EntityGraph (페이징 OK)
3. 컬렉션이 함께 필요
   ├── 페이징 없음 → 컬렉션 fetch join (하나만)
   └── 페이징 있음 → ToOne만 fetch join + 컬렉션은 batch size
4. 그래도 느리거나 컬럼이 많음 → DTO 직접 조회
5. 통계·복잡한 조회 → 네이티브 쿼리 / 별도 조회 모델
```

### N+1 탐지
- 로컬에서 `org.hibernate.SQL: debug`로 **쿼리 개수 확인 습관**
- `hibernate.generate_statistics=true` → 세션별 쿼리 수 로그
- 테스트에서 쿼리 수 검증 (Hibernate `Statistics`, datasource-proxy 등)
- APM(Pinpoint, Datadog, New Relic)에서 요청당 SQL 수 모니터링

## 8. 면접 질문

1. **N+1 문제란? 왜 발생하나요?**
   → 1번의 쿼리로 N개의 엔티티를 조회한 뒤, 각 엔티티의 연관 데이터를 지연 로딩하면서 N번의 추가 쿼리가 실행되는 문제입니다. JPQL이 연관 엔티티를 함께 조회하지 않고 엔티티 단위로 SQL을 만들기 때문에 발생합니다.
2. **EAGER로 바꾸면 해결되나요?**
   → 아닙니다. JPQL은 대상 엔티티만 조회한 뒤 EAGER 설정을 보고 연관 엔티티를 즉시 추가 조회하므로 똑같이 N+1이 발생합니다.
3. **해결 방법은?**
   → fetch join이나 @EntityGraph로 한 번에 조회하고, 컬렉션과 페이징이 함께 필요하면 default_batch_fetch_size로 IN 쿼리로 묶어 조회하며, 필요하면 DTO로 직접 조회합니다.
4. **컬렉션 fetch join과 페이징을 같이 쓰면?**
   → 일대다 조인으로 행이 늘어나 DB 수준 페이징이 불가능해, Hibernate가 전체를 메모리에 올린 뒤 페이징하므로 OOM 위험이 있습니다. ToOne만 fetch join하고 컬렉션은 배치 사이즈로 해결합니다.

---

## 핵심 정리
- N+1 = 1번 조회 + 연관 데이터 N번 조회, **EAGER로는 해결 X**
- **ToOne → fetch join**, **컬렉션 + 페이징 → batch_fetch_size**
- 컬렉션 fetch join: 페이징 ✗, 2개 이상 ✗
- 조회 전용·성능 중요 → **DTO 직접 조회**
- 로컬에서 **SQL 개수를 항상 확인**
