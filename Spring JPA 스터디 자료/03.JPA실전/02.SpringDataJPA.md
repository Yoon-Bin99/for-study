# 02. Spring Data JPA

> **학습 목표**
> - `JpaRepository`가 제공하는 기능과 구현체(SimpleJpaRepository)의 동작을 이해한다.
> - 쿼리 메서드, `@Query`, 프로젝션, 페이징·정렬을 사용할 수 있다.
> - `save()`의 persist/merge 판단 기준을 설명할 수 있다.
> - 벌크 연산(`@Modifying`)의 주의점을 안다.

---

## 1. Repository 인터페이스

```java
public interface MemberRepository extends JpaRepository<Member, Long> { }
// 구현 클래스를 만들지 않아도 스프링이 프록시(SimpleJpaRepository)를 생성해 빈으로 등록
```
```
Repository ← CrudRepository ← ListCrudRepository ← JpaRepository
              save, findById,                        flush, saveAllAndFlush,
              delete, count ...                      deleteAllInBatch, getReferenceById
        PagingAndSortingRepository ← (함께 상속)  findAll(Pageable), findAll(Sort)
```
| 메서드 | 설명 |
|---|---|
| `save(entity)` | 새 엔티티면 persist, 아니면 merge |
| `findById(id)` | `Optional<T>` 반환 |
| `getReferenceById(id)` | 프록시 반환 (SELECT 없이 연관관계 설정할 때) |
| `findAll(Pageable)` | 페이징 |
| `deleteAllInBatch()` | 한 번의 DELETE 쿼리 |

> `SimpleJpaRepository`는 클래스에 `@Transactional(readOnly = true)`, 쓰기 메서드에 `@Transactional`이 붙어 있어 **서비스에 트랜잭션이 없어도** 개별 메서드는 트랜잭션 안에서 실행됩니다.

## 2. 쿼리 메서드 (메서드 이름으로 쿼리 생성)

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    List<Order> findByMemberIdAndStatus(Long memberId, OrderStatus status);

    List<Order> findByCreatedAtBetweenOrderByCreatedAtDesc(LocalDateTime from, LocalDateTime to);

    Optional<Order> findByOrderNo(String orderNo);

    boolean existsByOrderNo(String orderNo);

    long countByStatus(OrderStatus status);

    List<Order> findTop10ByStatusOrderByIdDesc(OrderStatus status);
}
```
| 키워드 | SQL |
|---|---|
| `And`, `Or` | AND, OR |
| `Between`, `LessThan`, `GreaterThanEqual` | 범위 |
| `Like`, `Containing`, `StartingWith` | LIKE |
| `In`, `NotIn` | IN |
| `IsNull`, `IsNotNull` | NULL 검사 |
| `OrderBy...Desc` | 정렬 |
| `Top10`, `First` | LIMIT |

> 조건이 2~3개를 넘으면 메서드 이름이 너무 길어집니다 → `@Query` 또는 QueryDSL. 애플리케이션 시작 시 문법을 검증하므로 오타는 바로 발견됩니다.

## 3. `@Query` (JPQL 직접 작성)

```java
@Query("select o from Order o join fetch o.member m where m.email = :email")
List<Order> findByMemberEmail(@Param("email") String email);

@Query(value = "SELECT * FROM orders WHERE created_at >= :from", nativeQuery = true)
List<Order> findRecentNative(@Param("from") LocalDateTime from);
```
- JPQL은 **엔티티와 필드 이름** 기준 (`Order`, `o.member`), SQL은 테이블·컬럼 기준
- `@Query`의 JPQL도 시작 시 문법 검증

## 5. 페이징과 정렬

```java
Page<Order> findByStatus(OrderStatus status, Pageable pageable);
Slice<Order> findSliceByStatus(OrderStatus status, Pageable pageable);
```
```java
PageRequest pageable = PageRequest.of(0, 20, Sort.by(Sort.Direction.DESC, "createdAt"));
Page<Order> page = orderRepository.findByStatus(OrderStatus.PAID, pageable);
page.getContent();        // 데이터
page.getTotalElements();  // 전체 개수 (count 쿼리 추가 실행)
page.getTotalPages();
```
| 반환 | count 쿼리 | 용도 |
|---|---|---|
| `Page` | ✅ 실행 | 페이지 번호 UI |
| `Slice` | ❌ (size+1개 조회해 다음 페이지 여부만) | **무한 스크롤**, "더보기" |
| `List` | ❌ | 단순 |

```java
// fetch join + 페이징이면 count 쿼리는 조인 없이 따로
@Query(value = "select o from Order o join fetch o.member",
       countQuery = "select count(o) from Order o")
Page<Order> findPageWithMember(Pageable pageable);
```
> 컨트롤러에서 `Pageable`을 바로 받을 수 있습니다: `/api/orders?page=0&size=20&sort=createdAt,desc` (최대 크기는 `spring.data.web.pageable.max-page-size`로 제한)

### 오프셋 페이징의 한계 → 커서(키셋) 페이징
```sql
-- OFFSET 100000: 앞의 10만 건을 읽고 버림 → 뒤로 갈수록 느림
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 100000;
-- 커서: 마지막으로 본 id 이후만
SELECT * FROM orders WHERE id < :lastId ORDER BY id DESC LIMIT 20;
```
```java
List<Order> findTop20ByIdLessThanOrderByIdDesc(Long lastId);
// Spring Data 3.1+: Window<T>, ScrollPosition.keyset() 지원
```

## 6. save()의 동작: persist vs merge

```java
// SimpleJpaRepository
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        em.persist(entity);
        return entity;
    } else {
        return em.merge(entity);
    }
}
```
**새 엔티티 판단 기준**: ID가 `null`(참조 타입)이거나 `0`(기본 타입)이면 새 엔티티

⚠️ **ID를 직접 할당**하는 엔티티(UUID를 생성자에서 세팅, 주문번호 PK 등)는 항상 "새 엔티티가 아님" → `merge` 호출 → **SELECT 후 INSERT** (불필요한 조회)
```java
@Entity
public class Coupon implements Persistable<String> {
    @Id
    private String code;

    @CreatedDate
    private LocalDateTime createdAt;

    @Override public String getId() { return code; }
    @Override public boolean isNew() { return createdAt == null; }   // 생성일이 없으면 새 엔티티
}
```

## 7. 벌크 연산 (`@Modifying`)

```java
@Modifying(clearAutomatically = true)
@Query("update Product p set p.price = p.price * 1.1 where p.category = :category")
int increasePrice(@Param("category") Category category);
```
- 변경 감지는 한 건씩 UPDATE → 대량 수정은 **벌크 쿼리 한 번**
- ⚠️ 벌크 연산은 **영속성 컨텍스트를 무시하고 DB에 직접** 실행 → 이미 조회한 엔티티는 옛날 값
- → `clearAutomatically = true` (실행 후 영속성 컨텍스트 초기화) 또는 벌크 연산을 트랜잭션 **처음에** 실행

## 9. 면접 질문

1. **Spring Data JPA는 구현 없이 어떻게 동작하나요?**
   → 스프링이 애플리케이션 시작 시 Repository 인터페이스의 프록시를 만들고, 기본 메서드는 SimpleJpaRepository에 위임하며, 쿼리 메서드는 메서드 이름을 파싱해 JPQL을 생성합니다.
2. **`save()`는 언제 persist, 언제 merge 하나요?**
   → ID가 null이면 새 엔티티로 보고 persist, 아니면 merge 합니다. ID를 직접 할당하면 merge로 인해 SELECT가 먼저 실행되므로 Persistable을 구현해 isNew를 재정의합니다.
3. **Page와 Slice의 차이는?**
   → Page는 전체 개수를 위한 count 쿼리를 추가로 실행하고, Slice는 요청 크기보다 하나 더 조회해 다음 페이지 존재 여부만 알려 무한 스크롤에 적합합니다.
4. **벌크 연산의 주의점은?**
   → 영속성 컨텍스트를 거치지 않고 DB에 직접 반영되므로, 이미 조회된 엔티티와 DB 값이 달라집니다. 실행 후 영속성 컨텍스트를 clear 하거나 먼저 실행합니다.

## 핵심 정리
- `JpaRepository` = 인터페이스만 → 프록시(SimpleJpaRepository)
- 단순 조건은 **쿼리 메서드**, 복잡하면 `@Query`, 동적이면 **QueryDSL**
- `Page`(count O) / `Slice`(무한 스크롤) / 대용량은 **커서 페이징**
- `save()` = isNew ? persist : merge → ID 직접 할당 시 `Persistable`
- `@Modifying` 벌크 연산 후 **영속성 컨텍스트 clear**
