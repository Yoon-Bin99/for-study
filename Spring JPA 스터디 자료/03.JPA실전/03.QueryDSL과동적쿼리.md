# 03. QueryDSL과 동적 쿼리

> **학습 목표**
> - 문자열 JPQL의 한계와 QueryDSL의 장점을 설명할 수 있다.
> - QueryDSL 설정과 Q타입 생성 원리를 이해한다.
> - `BooleanExpression`으로 재사용 가능한 동적 조건을 작성할 수 있다.
> - DTO 프로젝션, 페이징, Spring Data JPA와의 결합 방법을 안다.

---

## 1. 왜 QueryDSL인가?

검색 조건이 **있을 수도 없을 수도** 있는 화면 (상태, 기간, 회원 이름...)
```java
// 문자열 JPQL로 동적 쿼리 → if 지옥, 오타는 실행해야 발견
String jpql = "select o from Order o join o.member m where 1=1";
if (cond.status() != null) jpql += " and o.status = :status";
if (cond.memberName() != null) jpql += " and m.name like :name";   // 공백 하나 빠지면 런타임 에러
```
| 비교 | 문자열 JPQL | Criteria API | **QueryDSL** |
|---|---|---|---|
| 문법 오류 발견 | 런타임 | 컴파일 | **컴파일** |
| 가독성 | 좋음(정적) | **매우 나쁨** | **좋음 (SQL과 비슷)** |
| 동적 쿼리 | 문자열 조립 | 가능 | **쉬움** |
| IDE 자동 완성 | ✗ | △ | ✅ |

## 2. 설정

> 원조 `com.querydsl`은 2024년 이후 업데이트가 사실상 멈췄고, 현재는 **OpenFeign 포크**(`io.github.openfeign.querydsl`)가 유지 보수되고 있습니다. 패키지 이름(`com.querydsl.*`)은 같아서 코드는 그대로 사용합니다.

```groovy
dependencies {
    // OpenFeign 포크 (버전은 Maven Central에서 최신 확인)
    implementation "io.github.openfeign.querydsl:querydsl-jpa:${querydslVersion}"
    annotationProcessor "io.github.openfeign.querydsl:querydsl-apt:${querydslVersion}:jakarta"
    annotationProcessor 'jakarta.persistence:jakarta.persistence-api'

    // (기존 프로젝트) 원조: com.querydsl:querydsl-jpa:5.1.0:jakarta
}
```
```java
@Configuration
public class QuerydslConfig {
    @Bean
    public JPAQueryFactory jpaQueryFactory(EntityManager em) {
        return new JPAQueryFactory(em);
    }
}
```

### Q타입
컴파일 시 **애노테이션 프로세서**가 `@Entity`를 읽어 `QOrder`, `QMember` 같은 메타 클래스를 `build/generated` 아래에 생성합니다.
```java
public class QOrder extends EntityPathBase<Order> {
    public static final QOrder order = new QOrder("order1");
    public final NumberPath<Long> id = createNumber("id", Long.class);
    public final EnumPath<OrderStatus> status = createEnum("status", OrderStatus.class);
    public final QMember member;
    ...
}
```
→ 필드 이름이 바뀌면 Q타입도 바뀌어 **컴파일 에러로 바로 발견**됩니다. (Q타입은 Git에 커밋하지 않음)

## 3. 기본 문법

```java
import static com.shop.order.domain.QOrder.order;
import static com.shop.member.domain.QMember.member;

List<Order> result = queryFactory
        .selectFrom(order)
        .join(order.member, member).fetchJoin()
        .where(order.status.eq(OrderStatus.PAID),            // 콤마 = AND
               order.totalPrice.goe(10_000))
        .orderBy(order.createdAt.desc())
        .offset(0).limit(20)
        .fetch();
```
| 메서드 | 결과 |
|---|---|
| `fetch()` | List |
| `fetchOne()` | 단건 (없으면 null, 2개 이상이면 예외) |
| `fetchFirst()` | `limit(1).fetchOne()` |

| 조건 | 예 |
|---|---|
| `eq`, `ne` | `order.status.eq(PAID)` |
| `goe`, `gt`, `loe`, `lt`, `between` | 범위 |
| `in`, `notIn` | 목록 |
| `contains`, `startsWith`, `like` | 문자열 |
| `isNull`, `isNotNull` | null |
| `and`, `or`, `not` | 조합 |

## 4. 동적 쿼리: BooleanExpression ★

```java
public record OrderSearchCondition(OrderStatus status, String memberName,
                                   LocalDate from, LocalDate to) { }
```
```java
@Repository
@RequiredArgsConstructor
public class OrderQueryRepository {

    private final JPAQueryFactory queryFactory;

    public List<Order> search(OrderSearchCondition cond) {
        return queryFactory
                .selectFrom(order)
                .join(order.member, member).fetchJoin()
                .where(
                        statusEq(cond.status()),
                        memberNameContains(cond.memberName()),
                        createdBetween(cond.from(), cond.to())
                )                                    // null인 조건은 무시됨
                .orderBy(order.id.desc())
                .fetch();
    }

    private BooleanExpression statusEq(OrderStatus status) {
        return status == null ? null : order.status.eq(status);
    }

    private BooleanExpression memberNameContains(String name) {
        return StringUtils.hasText(name) ? member.name.contains(name) : null;
    }

    private BooleanExpression createdBetween(LocalDate from, LocalDate to) {
        if (from == null && to == null) return null;
        if (from == null) return order.createdAt.lt(to.plusDays(1).atStartOfDay());
        if (to == null) return order.createdAt.goe(from.atStartOfDay());
        return order.createdAt.goe(from.atStartOfDay())
                .and(order.createdAt.lt(to.plusDays(1).atStartOfDay()));
    }
}
```
- `where()`에 **null을 넘기면 무시** → 조건 메서드를 조합만 하면 됨
- 조건 메서드를 **재사용**하고 조합 가능 (`statusEq(PAID).and(...)`)
- ⚠️ 모든 조건이 null이면 **전체 조회** → 기본 기간 제한이나 limit를 두세요

> `BooleanBuilder`로도 동적 쿼리를 만들 수 있지만, 조건이 한 메서드에 쌓여 가독성이 떨어집니다.

## 5. DTO 프로젝션

```java
public record OrderSummary(Long orderId, String memberName, OrderStatus status, long totalPrice) { }

List<OrderSummary> list = queryFactory
        .select(Projections.constructor(OrderSummary.class,
                order.id, member.name, order.status, order.totalPrice))
        .from(order)
        .join(order.member, member)
        .where(statusEq(cond.status()))
        .fetch();
```
| 방식 | 특징 |
|---|---|
| `Projections.constructor` | 생성자 순서로 매핑 (타입 불일치는 런타임 발견) |
| `Projections.fields` | 필드 이름으로 (`.as("alias")`) |
| `@QueryProjection` | DTO 생성자에 붙이면 `QOrderSummary` 생성 → **컴파일 타임 검사**, 단 DTO가 QueryDSL에 의존 |

## 6. 페이징

```java
public Page<OrderSummary> searchPage(OrderSearchCondition cond, Pageable pageable) {
    List<OrderSummary> content = queryFactory
            .select(Projections.constructor(OrderSummary.class,
                    order.id, member.name, order.status, order.totalPrice))
            .from(order)
            .join(order.member, member)
            .where(statusEq(cond.status()), memberNameContains(cond.memberName()))
            .orderBy(order.id.desc())
            .offset(pageable.getOffset())
            .limit(pageable.getPageSize())
            .fetch();

    JPAQuery<Long> countQuery = queryFactory
            .select(order.count())
            .from(order)
            .join(order.member, member)              // 조건에 member가 필요할 때만 조인
            .where(statusEq(cond.status()), memberNameContains(cond.memberName()));

    return PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne);
    // 첫 페이지인데 데이터가 size보다 적으면 count 쿼리 생략
}
```
> `fetchResults()`, `fetchCount()`는 **deprecated**입니다. count 쿼리는 위처럼 따로 작성합니다.

## 7. Spring Data JPA와 결합

```java
public interface OrderRepositoryCustom {
    Page<OrderSummary> search(OrderSearchCondition cond, Pageable pageable);
}

@RequiredArgsConstructor
public class OrderRepositoryImpl implements OrderRepositoryCustom {   // 이름: Repository + Impl
    private final JPAQueryFactory queryFactory;
    @Override
    public Page<OrderSummary> search(...) { ... }
}

public interface OrderRepository extends JpaRepository<Order, Long>, OrderRepositoryCustom { }
```
- 엔티티 저장·단순 조회는 `OrderRepository`, **화면 전용 복잡한 조회**는 별도 `OrderQueryRepository` 클래스로 분리하는 방식도 많이 씁니다 (CQRS의 가벼운 형태)

## 8. 그 밖의 문법

```java
// 서브쿼리
QOrder sub = new QOrder("sub");
queryFactory.selectFrom(order)
        .where(order.totalPrice.gt(
                JPAExpressions.select(sub.totalPrice.avg()).from(sub)))
        .fetch();

// 그룹핑
queryFactory.select(order.status, order.count(), order.totalPrice.sum())
        .from(order)
        .groupBy(order.status)
        .having(order.count().gt(10))
        .fetch();      // List<Tuple>

// CASE
new CaseBuilder().when(order.totalPrice.goe(100_000)).then("VIP").otherwise("NORMAL");

// 벌크 수정 (영속성 컨텍스트 무시 주의)
queryFactory.update(order).set(order.status, OrderStatus.EXPIRED)
        .where(order.createdAt.lt(LocalDateTime.now().minusDays(30))).execute();
```
> JPQL 한계: **FROM 절 서브쿼리**(인라인 뷰)는 Hibernate 6+에서 지원되지만 QueryDSL JPA에서는 제한적입니다. 복잡하면 쿼리를 나누거나 네이티브 쿼리를 사용합니다.

## 9. 면접 질문

1. **QueryDSL을 쓰는 이유는?**
   → 쿼리를 자바 코드로 작성해 컴파일 시점에 문법 오류를 잡을 수 있고, IDE 자동 완성과 함께 동적 쿼리를 조건 메서드 조합으로 깔끔하게 작성할 수 있기 때문입니다.
2. **동적 쿼리를 어떻게 작성하나요?**
   → 조건마다 BooleanExpression을 반환하는 메서드를 만들고, 값이 없으면 null을 반환하면 where 절에서 무시됩니다. 조건을 재사용하고 조합할 수 있습니다.
3. **Q타입은 어떻게 생성되나요?**
   → 컴파일 시 애노테이션 프로세서가 @Entity 클래스를 읽어 필드 정보를 담은 메타 클래스를 생성합니다.

## 핵심 정리
- QueryDSL = **타입 안전한 JPQL 빌더**, 원조는 정체 → **OpenFeign 포크**
- 동적 쿼리: **`BooleanExpression` 메서드 + null 무시**
- DTO는 `Projections.constructor` / `@QueryProjection`
- 페이징 count는 따로 + `PageableExecutionUtils.getPage`
- 저장은 JpaRepository, 복잡한 조회는 **QueryRepository 분리**
