# 04. JPA 성능 최적화

> **학습 목표**
> - OSIV의 동작과 끄는 이유를 설명할 수 있다.
> - 대량 INSERT·UPDATE를 효율적으로 처리할 수 있다.
> - 조회 성능을 위한 엔티티 조회 vs DTO 조회 선택, 읽기 전용 최적화를 할 수 있다.
> - 커넥션 풀과 2차 캐시를 이해하고 성능 문제를 진단할 수 있다.

---

## 1. 성능 문제의 주요 원인

| 순위 | 원인 | 해결 문서 |
|---|---|---|
| 1 | **N+1** | `01.N+1문제.md` |
| 2 | 인덱스 없는 조회 | 실행 계획(EXPLAIN) 확인 (`CS 스터디 자료`의 인덱스 문서) |
| 3 | 불필요한 데이터 조회 (전체 컬럼, 큰 컬렉션) | DTO 조회, 페이징 |
| 4 | 대량 처리를 한 건씩 | 배치 INSERT, 벌크 UPDATE |
| 5 | 긴 트랜잭션·OSIV로 커넥션 고갈 | OSIV off, 외부 호출 분리 |

## 2. OSIV (Open Session In View)

```
OSIV ON (스프링 부트 기본값 true, 시작 시 경고 로그)
 요청 ──[Filter/Interceptor]──[Controller]──[Service @Transactional]──[Controller]──[View/JSON]── 응답
       |◀───────────────── 영속성 컨텍스트 + DB 커넥션 유지 ───────────────────────▶|
                                 |◀── 트랜잭션 ──▶|

OSIV OFF
                                 |◀── 트랜잭션 + 영속성 컨텍스트 + 커넥션 ──▶|
```
| | OSIV ON | OSIV OFF (권장) |
|---|---|---|
| 컨트롤러에서 지연 로딩 | 가능 | `LazyInitializationException` |
| DB 커넥션 점유 | **요청 전체** (외부 API 대기 중에도) | 트랜잭션 동안만 |
| 트래픽 많을 때 | **커넥션 풀 고갈** 위험 | 안전 |

```yaml
spring:
  jpa:
    open-in-view: false
```
→ OSIV를 끄면 **서비스 계층에서 필요한 데이터를 모두 로딩해 DTO로 반환**해야 합니다. 조회 전용 서비스(`OrderQueryService`)를 따로 두면 정리가 쉽습니다.

## 3. 대량 쓰기

### ① JDBC 배치 (Hibernate)
```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 500
        order_inserts: true      # 같은 테이블 INSERT끼리 모아서
        order_updates: true
```
```java
@Transactional
public void saveAll(List<Product> products) {
    for (int i = 0; i < products.size(); i++) {
        em.persist(products.get(i));
        if (i % 500 == 0) {
            em.flush();      // SQL 전송
            em.clear();      // 1차 캐시 비우기 → 메모리 누적 방지
        }
    }
}
```
⚠️ **IDENTITY 전략(MySQL AUTO_INCREMENT)은 Hibernate 배치 INSERT가 안 됩니다.**

### ② JdbcTemplate batchUpdate (MySQL에서 대량 INSERT)
```java
jdbcTemplate.batchUpdate(
        "INSERT INTO product(name, price) VALUES (?, ?)",
        products, 1000,
        (ps, p) -> {
            ps.setString(1, p.getName());
            ps.setLong(2, p.getPrice());
        });
```
```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/shop?rewriteBatchedStatements=true   # MySQL: 여러 INSERT를 multi-values 하나로
```
→ 1만 건 기준 수십 배 빨라지는 경우가 흔합니다.

### ③ 벌크 UPDATE/DELETE
변경 감지로 1만 건 수정 = UPDATE 1만 번 → `@Modifying` 벌크 쿼리 1번 (`→ 02.SpringDataJPA.md`)

> 수백만 건 이상의 정기 처리는 **Spring Batch** 로 청크 단위 처리 (`→ 미들웨어 스터디 자료의 05.배치와스케줄링/01.SpringBatch.md`)

## 4. 조회 최적화

### 엔티티 조회 vs DTO 조회
| | 엔티티 조회 | DTO 조회 |
|---|---|---|
| 조회 컬럼 | 전체 | **필요한 것만** |
| 영속성 컨텍스트 | 관리 (스냅샷 비용) | 관리 X |
| 변경 감지 | 가능 | 불가 |
| 용도 | **수정**이 필요한 로직 | **조회 전용 API**, 목록 화면 |

### 읽기 전용 최적화
```java
@Transactional(readOnly = true)      // 플러시 생략, 스냅샷 비교 생략
public List<OrderResponse> findOrders() { ... }

@QueryHints(@QueryHint(name = "org.hibernate.readOnly", value = "true"))
List<Order> findByStatus(OrderStatus status);   // 엔티티를 읽기 전용으로 로딩 (스냅샷 저장 X)
```

### 대량 조회 (전체 데이터 처리)
```java
// ❌ findAll() 100만 건 → OOM
// ✅ 페이징(커서)으로 나누어 처리, 또는 Stream + 주기적 clear
@QueryHints(@QueryHint(name = HibernateHints.HINT_FETCH_SIZE, value = "1000"))
@Query("select p from Product p")
Stream<Product> streamAll();       // 반드시 트랜잭션 안에서, try-with-resources로 닫기
```

## 5. 커넥션 풀 (HikariCP)

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20         # 너무 크면 DB가 버티지 못함
      minimum-idle: 20              # 고정 크기 권장
      connection-timeout: 3000      # 커넥션 대기 최대 3초 (기본 30초는 너무 김)
      max-lifetime: 1800000         # DB wait_timeout보다 짧게
      leak-detection-threshold: 10000   # 10초 이상 반납 안 되면 경고 로그
```
- 풀 크기는 무조건 크게가 아닙니다. **DB의 max_connections ÷ 애플리케이션 인스턴스 수** 를 넘지 않도록
- HikariCP 문서의 출발점 공식: `connections ≈ (코어 수 × 2) + 유효 디스크 수` — 이후 부하 테스트로 조정
- `HikariPool-1 - Connection is not available, request timed out` → 긴 트랜잭션, OSIV, 커넥션 누수, REQUIRES_NEW 남용 의심
- Actuator 메트릭 `hikaricp.connections.active`, `hikaricp.connections.pending` 모니터링

## 6. 2차 캐시 (참고)

```
1차 캐시: 트랜잭션(영속성 컨텍스트) 범위
2차 캐시: 애플리케이션(EntityManagerFactory) 범위 — Ehcache, Caffeine, Infinispan
```
- 거의 바뀌지 않는 데이터(코드 테이블, 카테고리)에 적합
- 다중 서버면 **서버 간 불일치** 문제 → 실무에선 2차 캐시보다 **Spring Cache + Redis** 로 DTO를 캐싱하는 경우가 많음 (`→ 미들웨어 스터디 자료의 01.Redis/02.캐시전략.md`)

## 7. 성능 진단 순서

```
1. 느린 API 특정 (APM, 액추에이터, 로그의 응답 시간)
2. 요청당 SQL 개수 확인 → 많으면 N+1
3. 느린 SQL 확인 (slow query log) → EXPLAIN → 인덱스·쿼리 수정
4. 커넥션 풀 대기(pending) 확인 → 트랜잭션 길이, OSIV
5. 데이터량 확인 → 페이징, DTO 조회, 캐시
6. 개선 전후를 부하 테스트(nGrinder, k6)로 수치 비교
```

## 8. 면접 질문

1. **OSIV란? 왜 끄나요?**
   → 영속성 컨텍스트와 DB 커넥션을 요청 시작부터 응답까지 유지해 컨트롤러·뷰에서도 지연 로딩을 가능하게 하는 기능입니다. 커넥션을 오래 점유해 트래픽이 많으면 커넥션 풀이 고갈되므로 끄고, 서비스에서 DTO로 변환해 반환합니다.
2. **대량 INSERT를 빠르게 하려면?**
   → Hibernate batch_size를 설정하고 주기적으로 flush·clear 하되, MySQL IDENTITY 전략은 배치가 안 되므로 JdbcTemplate batchUpdate와 rewriteBatchedStatements 옵션을 사용합니다.
3. **커넥션 풀이 고갈되는 원인은?**
   → 긴 트랜잭션(트랜잭션 안의 외부 API 호출), OSIV, 커넥션 누수, REQUIRES_NEW 남용, 풀 크기 대비 과도한 동시 요청 등이 원인입니다.

## 핵심 정리
- 1순위 N+1, 2순위 인덱스 → **SQL 개수와 실행 계획 확인**
- **OSIV off** + 서비스에서 DTO 변환
- 대량 쓰기: batch_size + flush/clear, MySQL은 **JdbcTemplate batchUpdate + rewriteBatchedStatements**
- 조회 전용은 **readOnly + DTO 조회**
- HikariCP: 적정 크기, 짧은 connection-timeout, leak 감지
