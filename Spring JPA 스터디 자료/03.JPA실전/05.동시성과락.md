# 05. 동시성 제어와 락

> **학습 목표**
> - 동시 요청에서 발생하는 갱신 분실(Lost Update) 문제를 설명할 수 있다.
> - 낙관적 락(`@Version`)과 비관적 락(`SELECT ... FOR UPDATE`)의 동작과 선택 기준을 안다.
> - 원자적 UPDATE, 분산 락 등 다른 해결책과 비교할 수 있다.
> - 재고 차감, 쿠폰 발급 같은 실무 시나리오에 적용할 수 있다.

---

## 1. 문제: 갱신 분실 (Lost Update)

재고 10개인 상품을 두 사람이 동시에 1개씩 구매
```
 시간   요청 A                         요청 B
  1    SELECT stock → 10
  2                                   SELECT stock → 10
  3    stock = 9, UPDATE (9)
  4                                   stock = 9, UPDATE (9)
 결과: 2개 팔렸는데 재고 9   ← A의 변경이 사라짐
```
```java
@Transactional
public void decrease(Long productId, int quantity) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.decrease(quantity);     // 변경 감지 → UPDATE product SET stock = 9 ...
}
```
> `synchronized`로 막으면? → **서버가 여러 대**면 소용없고, `@Transactional` 프록시 바깥에서 커밋되기 전에 락이 풀려 한 서버에서도 완벽하지 않습니다. (`→ JAVA·JVM 스터디 자료의 05.동시성/02.동기화와메모리모델.md`)

DB 트랜잭션 격리 수준(REPEATABLE READ)만으로는 이 문제가 막히지 않습니다. (MySQL InnoDB의 일반 SELECT는 스냅샷 읽기)

---

## 2. 해결책 한눈에 보기

| 방법 | 원리 | 적합한 상황 |
|---|---|---|
| **원자적 UPDATE** | `UPDATE ... SET stock = stock - 1 WHERE stock >= 1` | 단순 수량 증감 (가장 간단·빠름) |
| **낙관적 락** | 버전 비교, 충돌 시 예외 → 재시도 | **충돌이 드문** 경우 (게시글 수정, 설정 변경) |
| **비관적 락** | `SELECT ... FOR UPDATE` 로 행 잠금 | **충돌이 잦은** 경우 (인기 상품 재고) |
| **분산 락** (Redis) | 서버 밖의 공통 락 | DB 여러 개, DB 외 자원, 락 범위가 넓을 때 |
| 유니크 제약 | DB가 중복 거부 | 중복 발급·중복 가입 방지 |
| 큐로 직렬화 | 요청을 한 줄로 세움 | 선착순 대량 트래픽 |

## 3. 원자적 UPDATE

```java
@Modifying(clearAutomatically = true)
@Query("update Product p set p.stock = p.stock - :qty where p.id = :id and p.stock >= :qty")
int decreaseStock(@Param("id") Long id, @Param("qty") int qty);
```
```java
@Transactional
public void order(Long productId, int qty) {
    int updated = productRepository.decreaseStock(productId, qty);
    if (updated == 0) throw new BusinessException(ErrorCode.OUT_OF_STOCK);
    // 이후 주문 생성
}
```
- DB가 UPDATE 시 행 락을 걸고 **현재 값 기준으로** 계산 → 갱신 분실 없음
- 단점: 도메인 로직이 엔티티 밖(SQL)으로 나감, 복잡한 규칙은 표현 어려움

## 4. 낙관적 락 (Optimistic Lock)

"충돌이 거의 없을 것이다" → 락을 걸지 않고, **커밋 시점에 버전으로 충돌을 감지**
```java
@Entity
public class Product {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private int stock;

    @Version
    private Long version;
}
```
```sql
-- 조회: version = 3
UPDATE product SET stock = 9, version = 4 WHERE id = 1 AND version = 3;
-- 다른 트랜잭션이 먼저 version을 4로 바꿨다면 → 0건 수정
--   → ObjectOptimisticLockingFailureException (스프링) 발생
```
### 재시도
```java
@Service
@RequiredArgsConstructor
public class StockFacade {
    private final StockService stockService;     // @Transactional은 이 안에 (재시도마다 새 트랜잭션)

    public void decrease(Long id, int qty) {
        int maxRetry = 3;
        for (int attempt = 1; ; attempt++) {
            try {
                stockService.decrease(id, qty);
                return;
            } catch (ObjectOptimisticLockingFailureException e) {
                if (attempt == maxRetry) throw new BusinessException(ErrorCode.CONFLICT_TRY_AGAIN);
                sleepQuietly(50L * attempt);       // 잠깐 쉬었다가 재시도
            }
        }
    }
}
```
> Spring Framework 7부터는 코어에 `@Retryable(includes = ObjectOptimisticLockingFailureException.class, maxRetries = 3)` 이 있어 재시도를 선언적으로 처리할 수 있습니다(`@EnableResilientMethods` 필요). 재시도는 **트랜잭션 바깥**에서 해야 매번 새 트랜잭션으로 최신 값을 다시 읽습니다.

| 장점 | 단점 |
|---|---|
| DB 락 없음 → 대기 없음, 처리량 좋음 | 충돌이 많으면 **재시도 폭증** → 오히려 느림 |
| 데드락 없음 | 재시도 로직 필요 |
| 사용자 화면의 "다른 사람이 먼저 수정했습니다" 처리에 적합 | |

## 5. 비관적 락 (Pessimistic Lock)

"충돌이 자주 날 것이다" → **읽을 때부터 행을 잠금**
```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}
```
```sql
SELECT * FROM product WHERE id = 1 FOR UPDATE;
-- 다른 트랜잭션은 이 행을 FOR UPDATE / UPDATE 하려면 커밋될 때까지 대기
```
```java
@Transactional
public void decrease(Long id, int qty) {
    Product product = productRepository.findByIdForUpdate(id).orElseThrow();
    product.decrease(qty);
}
```
| 모드 | SQL | 의미 |
|---|---|---|
| `PESSIMISTIC_WRITE` | `FOR UPDATE` | 배타 락 (읽기 락·쓰기 모두 대기) |
| `PESSIMISTIC_READ` | `FOR SHARE` | 공유 락 (다른 쓰기 대기) |

| 장점 | 단점 |
|---|---|
| 충돌이 많아도 재시도 없이 **순서대로 처리** | 대기 발생 → 처리량 ↓ |
| 데이터 정합성 확실 | **데드락** 위험 (여러 행을 다른 순서로 잠그면) |
| | 락 타임아웃 설정 필요, 트랜잭션을 **짧게** |

> 데드락 방지: 여러 행을 잠글 때 **항상 같은 순서**(ID 오름차순)로 잠급니다. MySQL에서 **인덱스가 없는 조건**으로 FOR UPDATE 하면 훨씬 넓은 범위가 잠길 수 있습니다.

## 6. 분산 락 (Redis)

```java
RLock lock = redissonClient.getLock("lock:product:" + productId);
boolean acquired = lock.tryLock(3, 5, TimeUnit.SECONDS);   // 최대 3초 대기, 5초 후 자동 해제
if (!acquired) throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS);
try {
    stockService.decrease(productId, qty);      // ★ 트랜잭션은 락 "안쪽"에서 시작·커밋
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```
- ⚠️ **락 해제 → 커밋** 순서면 커밋 전에 다른 요청이 옛 값을 읽음 → 락 획득 후 트랜잭션 시작, **커밋 후 락 해제**
- DB 부하를 줄이고 여러 DB·외부 자원을 묶을 수 있지만 Redis 장애·락 만료 같은 고려 사항이 늘어남
- 상세 구현: `→ 미들웨어 스터디 자료의 01.Redis/03.Redis활용패턴.md`

## 7. 시나리오별 선택

| 시나리오 | 추천 |
|---|---|
| 재고 차감 (일반) | **원자적 UPDATE** 또는 비관적 락 |
| 인기 상품 선착순 (초당 수천 건) | Redis 원자 연산(DECR/Lua)으로 1차 차단 → DB 반영, 또는 **큐** |
| 게시글·프로필 수정 | **낙관적 락** (`@Version`) + "다시 시도" 안내 |
| 쿠폰 1인 1회 발급 | **유니크 제약** (member_id, coupon_id) + 예외 처리 |
| 포인트 차감 | 비관적 락 또는 원자적 UPDATE (+ 포인트 이력 테이블) |
| 여러 서비스·DB에 걸친 작업 | 분산 락 또는 **Saga** 패턴 |

### 동시성 테스트
```java
@Test
void 동시에_100명이_주문해도_재고가_정확히_차감된다() throws InterruptedException {
    int threads = 100;
    ExecutorService executor = Executors.newFixedThreadPool(32);
    CountDownLatch latch = new CountDownLatch(threads);
    for (int i = 0; i < threads; i++) {
        executor.submit(() -> {
            try { stockService.decrease(productId, 1); }
            finally { latch.countDown(); }
        });
    }
    latch.await();
    assertThat(productRepository.findById(productId).orElseThrow().getStock()).isZero();   // 초기 100
}
```
> 테스트 클래스에 `@Transactional`을 붙이면 모든 스레드가 같은 트랜잭션이 아니어서 결과를 볼 수 없습니다. 동시성 테스트는 트랜잭션 없이 실행하고 데이터를 직접 정리합니다. (`→ 테스트코드 스터디 자료의 03.테스트설계/04.동시성과시간테스트.md`)

## 8. 면접 질문

1. **낙관적 락과 비관적 락의 차이는?**
   → 낙관적 락은 충돌이 드물다고 보고 버전 컬럼으로 커밋 시점에 충돌을 감지해 예외 후 재시도하고, 비관적 락은 충돌이 잦다고 보고 SELECT FOR UPDATE로 조회 시점부터 행을 잠가 다른 트랜잭션을 대기시킵니다.
2. **재고 차감 동시성 문제를 어떻게 해결하나요?**
   → 단순 차감이면 조건부 원자적 UPDATE로 해결하고, 도메인 로직이 필요하면 비관적 락을, 트래픽이 매우 많으면 Redis 원자 연산이나 큐로 DB 앞에서 제어합니다.
3. **synchronized로 해결할 수 없나요?**
   → 하나의 JVM 안에서만 동작해 서버가 여러 대면 효과가 없고, @Transactional 프록시 바깥에서 커밋되기 전에 락이 풀려 단일 서버에서도 정합성이 깨질 수 있습니다.
4. **분산 락 사용 시 주의점은?**
   → 락 획득 후 트랜잭션을 시작하고 커밋 후 락을 해제해야 하며, 락 만료 시간과 대기 시간, Redis 장애 시 대응을 고려해야 합니다.

## 핵심 정리
- 문제: **갱신 분실**, synchronized·격리 수준만으로는 해결 X
- 단순 증감 → **원자적 UPDATE** (`WHERE stock >= qty`)
- 충돌 드묾 → **낙관적 락 `@Version` + 트랜잭션 밖 재시도**
- 충돌 잦음 → **비관적 락 `FOR UPDATE` + 타임아웃**, 같은 순서로 잠금
- 다중 서버·DB 외 자원 → **분산 락** (락 안에서 트랜잭션 커밋)
- 중복 방지 → **유니크 제약**
