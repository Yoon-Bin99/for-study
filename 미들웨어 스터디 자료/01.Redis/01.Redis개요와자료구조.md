# 01. Redis 개요와 자료구조

> **학습 목표**
> - Redis가 빠른 이유(인메모리, 단일 스레드 이벤트 루프)를 설명할 수 있다.
> - String, Hash, List, Set, Sorted Set 등 자료구조와 대표 활용 사례를 연결할 수 있다.
> - TTL, 키 설계, 메모리 정책(eviction)을 이해한다.
> - `KEYS` 같은 위험한 명령과 큰 키(Big Key) 문제를 피할 수 있다.

---

## 1. Redis란?

**Re**mote **Di**ctionary **S**erver — 메모리에 데이터를 저장하는 **Key-Value 저장소**입니다.
| 특징 | 설명 |
|---|---|
| **인메모리** | 디스크가 아닌 RAM → 읽기·쓰기 **마이크로초~1ms** |
| **다양한 자료구조** | 단순 문자열이 아니라 List, Hash, Set, Sorted Set... |
| **단일 스레드 명령 처리** | 명령이 하나씩 순서대로 실행 → 각 명령이 **원자적** |
| 영속성(선택) | RDB 스냅샷, AOF 로그 (`→ 04.영속성과고가용성.md`) |
| 복제·클러스터 | 고가용성, 수평 확장 |

### 대표 용도
캐시, 세션 저장소, **분산 락**, 선착순·재고 카운터, 랭킹, 레이트 리밋, 실시간 조회수, 메시지(Pub/Sub, Stream)

### 라이선스 이슈 (알아 두기)
| 시기 | 변화 |
|---|---|
| 2024.3 | Redis 7.4부터 BSD → **소스 공개 라이선스(RSALv2/SSPL)** 로 변경 |
| 2024 | 리눅스 재단이 마지막 BSD 버전을 포크해 **Valkey** 출범 (AWS ElastiCache·MemoryDB 등이 지원) |
| 2025.5 | **Redis 8**부터 **AGPLv3** 를 선택지에 추가해 다시 오픈소스로 |
> 명령어·프로토콜은 Valkey와 Redis가 거의 호환되어, 이 문서 내용은 둘 다에 적용됩니다.

## 2. 왜 빠른가? 단일 스레드인데?

```
 클라이언트 요청들 ──▶ [ 이벤트 루프 (I/O 멀티플렉싱: epoll) ]
                              │ 명령을 하나씩 실행 (메모리 연산이라 매우 빠름)
                              ▼
                         [ 메모리 데이터 ]
```
- **메모리 접근**이라 디스크 I/O 대기가 없음
- 명령 실행은 단일 스레드 → **락·컨텍스트 스위칭 비용 없음**, 명령마다 원자성 보장
- 네트워크 I/O는 epoll로 다중화 (Redis 6+ 는 네트워크 읽기·쓰기를 별도 I/O 스레드로 처리 가능)
- ⚠️ 반대로 **오래 걸리는 명령 하나가 전체를 멈춤** → `KEYS *`, 큰 컬렉션 전체 조회 금지

## 3. 자료구조와 활용

### String
```
SET product:1:name "키보드"
SET session:abc123 "{...}" EX 1800      # 30분 후 만료
GET product:1:name
INCR post:42:views                      # 원자적 증가 → 조회수
DECRBY stock:1 3                        # 원자적 감소 → 재고
SET lock:order:42 "uuid" NX PX 5000     # 없을 때만 저장 + 5초 만료 → 분산 락
```
| 활용 | 명령 |
|---|---|
| 캐시 (JSON 직렬화) | `SET key value EX ttl` |
| 카운터 (조회수, 재고) | `INCR`, `DECR`, `INCRBY` |
| 분산 락 | `SET key value NX PX ms` |

### Hash (필드-값 묶음 = 객체)
```
HSET member:1 name "kim" grade "GOLD" point 1000
HGET member:1 grade
HINCRBY member:1 point 500
HGETALL member:1            # 필드가 아주 많으면 HSCAN
```
→ 객체 일부 필드만 읽고 수정할 때 String(JSON 전체)보다 효율적. 장바구니(`cart:{memberId}` → 상품ID: 수량)

### List (양방향 연결 리스트, 순서 O, 중복 O)
```
LPUSH notifications:1 "msg3"   # 앞에 추가
LRANGE notifications:1 0 9     # 최근 10개
LTRIM notifications:1 0 99     # 최근 100개만 유지
RPOP / BRPOP queue             # 간단한 작업 큐 (BRPOP: 데이터 올 때까지 대기)
```

### Set (순서 X, 중복 X)
```
SADD coupon:1:issued 1001 1002     # 쿠폰 받은 회원
SISMEMBER coupon:1:issued 1001     # 이미 받았나? O(1)
SCARD coupon:1:issued              # 발급 수
SINTER follow:1 follow:2           # 공통 팔로우
```
→ **중복 방지**(1인 1쿠폰), 좋아요한 사용자, 태그

### Sorted Set (점수로 정렬된 Set) ★
```
ZADD ranking:2026-11 1500 "kim" 2300 "lee" 980 "park"
ZINCRBY ranking:2026-11 100 "kim"          # 점수 증가
ZREVRANGE ranking:2026-11 0 9 WITHSCORES   # 상위 10명
ZREVRANK ranking:2026-11 "kim"             # 내 순위 (0부터)
ZRANGEBYSCORE delay:queue 0 1731100000     # 시간이 된 작업 (score = 실행 시각)
```
→ **실시간 랭킹**, 인기 검색어, **대기열**(score = 진입 시각), 지연 작업 큐. 내부는 Skip List로 O(log N)

### 그 밖의 자료구조
| 자료구조 | 용도 |
|---|---|
| **Bitmap** (`SETBIT`) | 출석 체크, 일별 활성 사용자 (사용자 ID = 비트 위치, 1억 명도 약 12MB) |
| **HyperLogLog** (`PFADD`, `PFCOUNT`) | 순 방문자 수 **근사 집계** (키당 최대 12KB, 오차 약 0.81%) |
| **Geo** (`GEOADD`, `GEOSEARCH`) | 주변 매장 찾기 |
| **Stream** (`XADD`, `XREADGROUP`) | 컨슈머 그룹이 있는 로그형 메시지 큐 |
| Pub/Sub | 실시간 브로드캐스트 (저장 X, 구독자 없으면 유실) |

## 4. TTL과 메모리 정책

```
SET cache:product:1 "..." EX 600     # 10분
EXPIRE key 60 / TTL key / PERSIST key
```
- 만료된 키 삭제: 접근 시 확인(lazy) + 주기적 샘플링(active)
- **캐시 키에는 반드시 TTL** → 메모리 무한 증가 방지, 오래된 데이터 자동 정리

### maxmemory-policy (메모리가 가득 찼을 때)
| 정책 | 동작 | 용도 |
|---|---|---|
| `noeviction` (기본) | 쓰기 명령 에러 | 데이터 저장소 (유실 금지) |
| **`allkeys-lru`** | 모든 키 중 오래 안 쓴 것 삭제 | **캐시 전용** |
| `allkeys-lfu` | 자주 안 쓴 것 삭제 | 인기 데이터가 뚜렷한 캐시 |
| `volatile-lru` | TTL 있는 키 중 LRU | 캐시 + 영구 데이터 혼용 |

## 5. 키 설계

```
{도메인}:{ID}:{속성}
product:1:detail
member:1001:cart
ranking:daily:2026-11-09
lock:stock:42
```
| 원칙 | 이유 |
|---|---|
| 콜론(`:`) 구분, 일관된 규칙 | 가독성, 도구에서 그룹핑 |
| **너무 길지 않게** | 키도 메모리 사용 |
| 버전 포함 고려 | `product:v2:1` — 캐시 구조 변경 시 충돌 방지 |
| 클러스터면 해시 태그 | `{order:42}:items`, `{order:42}:status` → 같은 슬롯 (멀티 키 명령 가능) |

## 6. 주의할 명령과 Big Key

| 위험 | 이유 | 대안 |
|---|---|---|
| **`KEYS *`** | 모든 키 순회 O(N) → 수 초간 **전체 서버 멈춤** | **`SCAN`** (커서로 조금씩) |
| `FLUSHALL` | 전체 삭제 | 운영에서 `rename-command`로 비활성화 |
| `HGETALL`, `SMEMBERS`, `LRANGE 0 -1` (큰 컬렉션) | 응답이 거대 → 블로킹 | `HSCAN`, `SSCAN`, 범위 조회 |
| **Big Key** (수 MB 값, 수십만 원소) | 조회·삭제·복제 시 지연, 네트워크 폭증 | 키 분할 (`ranking:2026-11:part1`), 삭제는 **`UNLINK`**(비동기) |
| Hot Key (한 키에 트래픽 집중) | 클러스터에서 한 노드만 과부하 | 로컬 캐시 병행, 키 복제 분산 |

## 7. 면접 질문

1. **Redis는 단일 스레드인데 왜 빠른가요?**
   → 데이터가 메모리에 있어 디스크 I/O가 없고, 단일 스레드로 명령을 처리해 락과 컨텍스트 스위칭 비용이 없으며, I/O 멀티플렉싱으로 많은 연결을 효율적으로 처리하기 때문입니다.
2. **Sorted Set은 어디에 쓰나요?**
   → 점수 기준으로 정렬된 집합이라 실시간 랭킹, 대기열 순번, 실행 시각을 점수로 둔 지연 작업 큐에 사용하며 삽입·순위 조회가 O(log N)입니다.
3. **운영에서 `KEYS` 명령을 쓰면 안 되는 이유는?**
   → 모든 키를 순회하는 O(N) 명령이라 키가 많으면 실행되는 동안 단일 스레드가 막혀 다른 모든 요청이 지연됩니다. SCAN으로 나누어 조회합니다.
4. **캐시용 Redis의 메모리 정책은?**
   → 캐시 키에 TTL을 두고, maxmemory를 설정한 뒤 allkeys-lru나 allkeys-lfu로 오래되거나 덜 쓰는 키를 자동으로 제거합니다.

## 핵심 정리
- Redis = **인메모리 + 단일 스레드 명령 처리(원자적) + 다양한 자료구조**
- String(캐시·카운터·락) · Hash(객체) · List(최근 목록) · Set(중복 방지) · **Sorted Set(랭킹·대기열)**
- 캐시 키는 **TTL 필수**, 캐시 전용이면 `allkeys-lru`
- `KEYS` ✗ → `SCAN`, Big Key 분할, 삭제는 `UNLINK`
- 2024 라이선스 변경 → **Valkey 포크**, Redis 8은 AGPLv3 추가
