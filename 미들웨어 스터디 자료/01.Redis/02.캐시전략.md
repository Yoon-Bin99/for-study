# 02. 캐시 전략

> **학습 목표**
> - 캐시를 적용할 데이터와 적용하면 안 되는 데이터를 구분할 수 있다.
> - Cache-Aside, Write-Through, Write-Behind 패턴을 비교할 수 있다.
> - 캐시 일관성 문제와 무효화 전략을 설명할 수 있다.
> - 캐시 스탬피드, 관통, 눈사태 문제와 해결책을 안다.
> - 로컬 캐시와 분산 캐시(Redis)를 함께 쓰는 구조를 이해한다.

---

## 1. 캐시란?

**자주 쓰는 데이터를 빠른 저장소에 복사해 두는 것**
```
요청 ──▶ [캐시: Redis ~1ms] ──(없으면)──▶ [DB ~10~100ms]
```
| 효과 | 설명 |
|---|---|
| 응답 속도 ↑ | DB 조회·계산 생략 |
| **DB 부하 ↓** | 읽기 트래픽 대부분을 캐시가 흡수 |
| 비용 ↓ | DB 스펙을 올리는 것보다 저렴 |

### 캐시하기 좋은 데이터
| 적합 ✅ | 부적합 ❌ |
|---|---|
| **읽기 많고 변경 적음** (상품 상세, 카테고리, 공지) | 자주 바뀌는 데이터 (실시간 재고, 잔액) |
| 계산 비용이 큼 (랭킹, 통계, 추천) | **정확성이 생명** (결제 금액, 포인트 잔액 → 반드시 DB) |
| 약간 오래돼도 괜찮음 | 사용자마다 다르고 재사용 안 됨 |
> **캐시 적중률(Hit Ratio)** 을 측정하세요. 적중률이 낮으면 캐시는 메모리 낭비 + 복잡도만 늘립니다.

## 2. 읽기 전략: Cache-Aside (Lazy Loading) ★

가장 많이 쓰는 방식. **애플리케이션이 캐시를 직접 관리**합니다.
```
조회
1. 캐시 조회 → 있으면(Hit) 반환
2. 없으면(Miss) DB 조회
3. 결과를 캐시에 저장 (TTL과 함께) 후 반환

수정
1. DB 수정
2. 캐시 삭제 (다음 조회 때 새로 채워짐)
```
```java
public ProductResponse getProduct(Long id) {
    String key = "product:" + id;
    ProductResponse cached = redisCache.get(key, ProductResponse.class);
    if (cached != null) return cached;

    ProductResponse response = ProductResponse.from(productRepository.findById(id).orElseThrow());
    redisCache.set(key, response, Duration.ofMinutes(10));
    return response;
}
```
| 장점 | 단점 |
|---|---|
| 필요한 데이터만 캐시 | 첫 요청은 항상 느림 (Miss) |
| 캐시 장애 시 DB로 동작 (가용성) | 캐시와 DB 불일치 가능 (TTL·무효화로 관리) |

> 스프링에서는 `@Cacheable`로 같은 동작을 선언적으로 구현합니다. (`→ 05.SpringDataRedis.md`)

## 3. 쓰기 전략

| 전략 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **캐시 무효화** (Cache-Aside와 함께) | DB 쓰기 → 캐시 **삭제** | 단순, 가장 흔함 | 다음 조회 Miss |
| Write-Through | 캐시와 DB에 **동시에** 씀 | 캐시 항상 최신 | 쓰기 느림, 안 읽을 데이터도 캐시 |
| **Write-Behind (Write-Back)** | 캐시에만 쓰고 **나중에 모아서 DB 반영** | 쓰기 매우 빠름, DB 부하 ↓ | 캐시 장애 시 **데이터 유실** |
| Read-Through | 캐시가 DB 조회를 대신 (라이브러리 기능) | 코드 단순 | 캐시 계층 의존 |

### Write-Behind 예: 조회수
```
조회할 때마다 DB UPDATE (초당 수천 건) ❌
→ Redis INCR post:42:views                       (매 요청)
→ 스케줄러가 1분마다 Redis 값을 읽어 DB에 일괄 반영   (유실 허용 범위: 최대 1분)
```

### 왜 "수정"이 아니라 "삭제"인가?
```
수정(갱신) 방식에서의 경쟁 조건
 A: DB 가격 1000 → 2000 수정
 B: DB 가격 2000 → 3000 수정
 B: 캐시 = 3000
 A: 캐시 = 2000   ← 늦게 도착한 A가 덮어씀 → 캐시(2000) ≠ DB(3000), TTL까지 유지
```
→ **삭제**하면 다음 조회가 DB 최신값으로 다시 채우므로 불일치 가능성이 줄어듭니다. 그래도 남는 틈이 있어 **TTL은 항상 둡니다** (최후의 일관성 보장).

### 트랜잭션과 캐시 삭제 순서
```java
@Transactional
public void updatePrice(Long id, long price) {
    productRepository.findById(id).orElseThrow().changePrice(price);
    // 여기서 캐시를 지우면? 커밋 전에 다른 요청이 옛 DB 값을 읽어 캐시에 다시 채울 수 있음
}
```
→ **커밋 후 삭제**: `@TransactionalEventListener(phase = AFTER_COMMIT)` 또는 `@CacheEvict`를 트랜잭션 밖 메서드에

## 4. 캐시 장애 패턴 ★

### ① 캐시 스탬피드 (Cache Stampede, Thundering Herd)
**인기 키가 만료되는 순간** 수천 개 요청이 동시에 Miss → 모두 DB로 몰림
```
 product:1 만료 ── 동시에 3000 요청 ── 전부 DB 조회 ── DB 과부하
```
| 해결 | 설명 |
|---|---|
| **락 (Mutex)** | 한 요청만 DB 조회해 캐시를 채우고 나머지는 대기·재시도 (`SET lock NX`) |
| `@Cacheable(sync = true)` | 같은 JVM 안에서 같은 키 동시 로딩을 하나로 (서버 간에는 X) |
| **TTL 지터(Jitter)** | TTL에 랜덤 추가 (600초 ± 60초) → 동시 만료 방지 |
| 사전 갱신 (Refresh-Ahead) | 만료 전에 백그라운드에서 미리 갱신, 확률적 조기 만료(PER) |

### ② 캐시 관통 (Cache Penetration)
**DB에도 없는 데이터**를 계속 조회 (존재하지 않는 ID 공격) → 매번 Miss → DB
| 해결 | 설명 |
|---|---|
| **Null 캐싱** | "없음"도 짧은 TTL(30초~1분)로 캐시 |
| Bloom Filter | 존재 가능한 ID 집합으로 먼저 걸러냄 |
| 입력 검증 | 범위 밖 ID 차단, 레이트 리밋 |

### ③ 캐시 눈사태 (Cache Avalanche)
**많은 키가 동시에 만료**되거나 **Redis 자체가 장애** → DB로 트래픽 폭주
| 해결 | 설명 |
|---|---|
| TTL 지터 | 만료 시점 분산 |
| Redis 고가용성 | Sentinel·Cluster (`→ 04.영속성과고가용성.md`) |
| **서킷 브레이커 + 폴백** | Redis 장애 시 타임아웃을 짧게 두고, DB 보호를 위해 일부 요청 제한 |
| 다단계 캐시 | 로컬 캐시가 1차 방어 |

## 5. 로컬 캐시 vs 분산 캐시

| 비교 | 로컬 캐시 (Caffeine) | 분산 캐시 (Redis) |
|---|---|---|
| 위치 | 애플리케이션 메모리(JVM 힙) | 별도 서버 |
| 속도 | **나노초** (네트워크 없음) | ~1ms (네트워크) |
| 서버 간 공유 | ❌ 서버마다 다름 → **불일치** | ✅ |
| 용량 | 힙 크기 제한 (GC 영향) | 크게 |
| 적합 | 거의 안 바뀌는 데이터 (설정, 코드 테이블), Hot Key | 일반 캐시, 세션, 공유 상태 |

### 2단계 캐시
```
요청 → [L1 Caffeine (30초)] → [L2 Redis (10분)] → DB
변경 시: Redis 삭제 + Pub/Sub으로 모든 서버에 "L1 삭제" 브로드캐스트
```

## 6. 면접 질문

1. **Cache-Aside 패턴을 설명해 주세요.**
   → 조회 시 캐시를 먼저 확인하고 없으면 DB에서 조회해 캐시에 저장하며, 수정 시 DB를 갱신하고 캐시를 삭제하는 방식입니다. 필요한 데이터만 캐시되고 캐시 장애 시에도 DB로 동작합니다.
2. **캐시와 DB의 데이터 일관성은 어떻게 맞추나요?**
   → 수정 시 캐시를 갱신하지 않고 삭제해 경쟁 조건을 줄이고, 트랜잭션 커밋 후에 삭제하며, TTL로 불일치 기간의 상한을 둡니다. 정확성이 중요한 데이터는 캐시하지 않습니다.
3. **캐시 스탬피드란? 해결 방법은?**
   → 인기 키가 만료되는 순간 많은 요청이 동시에 DB로 몰리는 현상으로, 락으로 한 요청만 캐시를 채우게 하거나, TTL에 지터를 주고, 만료 전에 미리 갱신해 해결합니다.
4. **로컬 캐시와 Redis의 차이는?**
   → 로컬 캐시는 네트워크 없이 매우 빠르지만 서버마다 데이터가 달라질 수 있고, Redis는 서버 간 공유되지만 네트워크 비용이 있습니다. 거의 변하지 않는 데이터는 로컬, 공유가 필요한 데이터는 Redis에 둡니다.

## 핵심 정리
- 캐시 대상: **읽기 많고 변경 적고, 약간 오래돼도 되는** 데이터
- 기본은 **Cache-Aside + 수정 시 삭제(커밋 후) + TTL**
- 쓰기 폭주(조회수)는 **Write-Behind**
- 장애 패턴: **스탬피드(락·지터)**, 관통(Null 캐싱·Bloom), 눈사태(지터·HA·서킷 브레이커)
- 로컬(Caffeine) + 분산(Redis) 2단계 캐시
