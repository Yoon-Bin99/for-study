## 1. 분산 락 (Distributed Lock)

서버가 여러 대일 때 **같은 자원에 대한 작업을 한 번에 하나만** 실행하기 위한 공용 락입니다.
> 언제 분산 락을 쓰고 언제 DB 락을 쓰는지는 `Spring JPA 스터디 자료의 03.JPA실전/05.동시성과락.md` 참고.

### ① 기본 원리: SET NX PX
```
SET lock:stock:42 "a1b2-uuid" NX PX 5000
  NX : 키가 없을 때만 저장 (= 락 획득)
  PX : 5초 후 자동 만료 (서버가 죽어도 락이 영원히 남지 않게)
→ OK  : 획득 성공
→ nil : 다른 누군가가 이미 보유
```
### 해제는 "내 락일 때만" (Lua로 원자적으로)
```lua
-- KEYS[1] = 락 키, ARGV[1] = 내가 저장한 UUID
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```
```
왜 확인이 필요한가?
 A가 락 획득(5초) → A 작업이 7초 걸림 → 5초에 락 만료
 → B가 락 획득 → A가 끝나고 DEL → B의 락을 지워 버림 → C도 진입
```

### ② Redisson (실무 권장)
```groovy
implementation 'org.redisson:redisson-spring-boot-starter:<최신 버전>'
```
```java
@Component
@RequiredArgsConstructor
public class DistributedLockExecutor {

    private final RedissonClient redissonClient;

    public <T> T executeWithLock(String key, long waitSec, long leaseSec, Supplier<T> task) {
        RLock lock = redissonClient.getLock("lock:" + key);
        boolean acquired = false;
        try {
            acquired = lock.tryLock(waitSec, leaseSec, TimeUnit.SECONDS);
            if (!acquired) {
                throw new BusinessException(ErrorCode.LOCK_ACQUISITION_FAILED);
            }
            return task.get();                    // ★ 이 안에서 트랜잭션 시작·커밋
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```
```java
public void decreaseStock(Long productId, int qty) {
    lockExecutor.executeWithLock("stock:" + productId, 3, 5,
            () -> { stockService.decrease(productId, qty); return null; });   // stockService.decrease는 @Transactional
}
```
| Redisson 기능 | 설명 |
|---|---|
| `tryLock(wait, lease)` | 최대 wait초 대기, lease초 후 자동 해제 |
| **Watchdog** | lease를 지정하지 않으면(-1) 작업 중 락 만료를 30초 단위로 자동 연장 |
| Pub/Sub 기반 대기 | 락 해제 알림을 받아 재시도 → 스핀 락처럼 Redis를 계속 두드리지 않음 |
| 재진입(Reentrant), 공정 락, 읽기·쓰기 락 | |

### 분산 락 주의점
| 주의 | 설명 |
|---|---|
| **락 → 트랜잭션 → 커밋 → 락 해제** 순서 | 트랜잭션 안에서 락을 풀면, 커밋 전에 다른 요청이 옛 값을 읽음 |
| lease 시간 | 작업 시간보다 길게, 너무 길면 장애 시 오래 막힘 |
| Redis 장애 | 락 서비스 전체가 멈춤 → 타임아웃·폴백 설계 |
| 정확성 한계 | 마스터 장애로 복제 전 페일오버되면 락이 사라질 수 있음 (Redlock 논쟁) → **최종 정합성은 DB 제약·버전으로 한 번 더** 보장 |

## 2. Lua 스크립트: 여러 명령을 원자적으로

Redis는 Lua 스크립트를 **실행하는 동안 다른 명령을 끼워 넣지 않습니다.** "확인 후 변경"을 한 번에 처리할 수 있습니다.
```lua
-- 재고 확인 후 차감 (KEYS[1] = stock:42, ARGV[1] = 수량)
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
local qty = tonumber(ARGV[1])
if stock < qty then
    return -1
end
return redis.call('DECRBY', KEYS[1], qty)
```
```java
private static final RedisScript<Long> DECREASE_SCRIPT = RedisScript.of("""
        local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
        local qty = tonumber(ARGV[1])
        if stock < qty then return -1 end
        return redis.call('DECRBY', KEYS[1], qty)
        """, Long.class);

Long result = redisTemplate.execute(DECREASE_SCRIPT, List.of("stock:" + productId), String.valueOf(qty));
if (result == null || result < 0) throw new BusinessException(ErrorCode.OUT_OF_STOCK);
```
> `MULTI/EXEC` 트랜잭션은 명령을 묶어 실행할 뿐 **중간 결과로 분기할 수 없습니다**. 조건 분기가 필요하면 Lua를 씁니다. 스크립트는 짧게 유지하세요(실행 중 Redis 전체가 대기).

## 3. 선착순 쿠폰 발급

요구사항: 쿠폰 100장, **1인 1장**, 동시 접속 수만 명
```
1. SADD coupon:{id}:issued {memberId}   → 0이면 이미 발급 (중복 차단)
2. INCR coupon:{id}:count               → 100 초과면 마감
3. 통과한 요청만 DB 저장 (또는 Kafka로 비동기 저장)
```
```lua
-- KEYS[1] = issued Set, KEYS[2] = count, ARGV[1] = memberId, ARGV[2] = 최대 수량
if redis.call('SISMEMBER', KEYS[1], ARGV[1]) == 1 then
    return -1                                   -- 이미 발급
end
local issued = redis.call('SCARD', KEYS[1])
if issued >= tonumber(ARGV[2]) then
    return -2                                   -- 마감
end
redis.call('SADD', KEYS[1], ARGV[1])
return 1                                        -- 발급 성공
```
```
[사용자] → [API 서버] → Redis Lua (중복·수량 원자 검사, 수 ms)
                         └ 성공 → Kafka "coupon-issued" 발행 → [컨슈머] → DB 저장
```
- Redis가 **트래픽을 앞단에서 차단** → DB에는 성공한 100건만
- DB에도 `UNIQUE(coupon_id, member_id)` 를 두어 최종 보장
- 대기열 UI가 필요하면 Sorted Set(score = 진입 시각)으로 순번 관리

## 4. 레이트 리밋 (Rate Limiting)

```
고정 윈도우: 1분에 100회
INCR rate:{userId}:{yyyyMMddHHmm}   → 1이면 EXPIRE 60
값 > 100 → 429 Too Many Requests
```
| 알고리즘 | 특징 |
|---|---|
| 고정 윈도우 (INCR + EXPIRE) | 단순, 경계에서 2배 허용 문제 (59초에 100, 61초에 100) |
| 슬라이딩 윈도우 로그 (Sorted Set) | `ZADD` 요청 시각, `ZREMRANGEBYSCORE`로 1분 이전 삭제, `ZCARD`로 개수 → 정확, 메모리 사용 많음 |
| **토큰 버킷** | 일정 속도로 토큰 충전, 순간 버스트 허용 → API 게이트웨이 표준 (Bucket4j + Redis) |
```lua
-- 고정 윈도우를 원자적으로 (INCR와 EXPIRE 사이에 장애가 나도 키가 영구히 남지 않게)
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return current
```

## 5. 실시간 랭킹

```java
// 점수 반영
redisTemplate.opsForZSet().incrementScore("ranking:weekly:2026-W46", "member:" + memberId, score);

// 상위 10명
Set<ZSetOperations.TypedTuple<String>> top10 =
        redisTemplate.opsForZSet().reverseRangeWithScores("ranking:weekly:2026-W46", 0, 9);

// 내 순위 (0부터 시작)
Long rank = redisTemplate.opsForZSet().reverseRank("ranking:weekly:2026-W46", "member:" + memberId);
```
- 기간별 키 (`daily`, `weekly`) + TTL
- DB `ORDER BY score DESC` (매번 정렬) 대비 **O(log N)** 갱신, 상위 조회 O(log N + M)

## 6. 세션 저장소 (Spring Session)

```
서버 여러 대 + 로드 밸런서 → 서버 A에서 로그인했는데 서버 B로 가면 세션 없음
→ 세션을 Redis에 저장해 모든 서버가 공유
```
```groovy
implementation 'org.springframework.session:spring-session-data-redis'
```
```yaml
spring:
  session:
    timeout: 30m
    redis:
      namespace: shop:session
```
> JWT 방식에서도 Redis는 **리프레시 토큰 저장, 로그아웃 토큰 블랙리스트**에 많이 씁니다. (`인증·인가 스터디 자료` 참고)

## 7. 면접 질문

1. **Redis로 분산 락을 어떻게 구현하나요?**
   → SET NX PX로 키가 없을 때만 값을 저장해 락을 얻고 만료 시간을 둬서 장애 시 자동 해제되게 하며, 해제할 때는 Lua로 내 값인지 확인 후 삭제합니다. 실무에선 대기·자동 연장을 지원하는 Redisson을 사용합니다.
2. **분산 락과 트랜잭션의 순서는?**
   → 락을 먼저 얻고 그 안에서 트랜잭션을 시작해 커밋한 뒤 락을 해제해야 합니다. 커밋 전에 락을 풀면 다른 요청이 커밋되지 않은 이전 값을 읽을 수 있습니다.
3. **Lua 스크립트를 쓰는 이유는?**
   → 여러 명령을 하나의 원자적 단위로 실행해, 확인 후 변경 같은 로직 사이에 다른 요청이 끼어들지 못하게 하기 위해서입니다.
4. **선착순 쿠폰 시스템을 설계한다면?**
   → Redis Set과 Lua로 중복 발급과 수량 초과를 원자적으로 차단해 트래픽을 앞단에서 처리하고, 성공 건만 Kafka로 비동기 저장하며, DB 유니크 제약으로 최종 정합성을 보장합니다.

## 핵심 정리
- 분산 락: **`SET NX PX` + 소유자 확인 해제(Lua)**, 실무는 **Redisson `tryLock`**
- **락 획득 → 트랜잭션 커밋 → 락 해제**, 최종 정합성은 DB 제약으로
- 원자적 복합 연산은 **Lua 스크립트**
- 선착순: Set + Lua + 비동기 저장 + DB 유니크
- 레이트 리밋(INCR/토큰 버킷), 랭킹(Sorted Set), 세션 공유(Spring Session)
