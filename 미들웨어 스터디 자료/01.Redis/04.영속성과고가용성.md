# 04. 영속성과 고가용성

> **학습 목표**
> - RDB와 AOF의 차이와 선택 기준을 설명할 수 있다.
> - Replication, Sentinel, Cluster 구성의 차이를 이해한다.
> - Redis Cluster의 해시 슬롯과 멀티 키 제약을 안다.
> - 관리형 서비스(ElastiCache)와 운영 주의점을 안다.

---

## 1. 영속성: 메모리 데이터를 디스크에

Redis는 메모리 저장소라 **재시작하면 데이터가 사라집니다.** 영속성 옵션으로 복구할 수 있습니다.

| 방식 | RDB (스냅샷) | AOF (Append Only File) |
|---|---|---|
| 저장 내용 | 특정 시점의 **전체 데이터 덤프** | **모든 쓰기 명령 로그** |
| 방식 | `fork()` 후 자식 프로세스가 파일로 | 명령을 파일 끝에 추가 |
| 파일 크기 | 작음 (압축) | 큼 (주기적 rewrite로 축소) |
| 복구 속도 | **빠름** | 느림 (명령 재실행) |
| 유실 범위 | 마지막 스냅샷 이후 (분~시간) | `appendfsync everysec`: **최대 1초** |
| 설정 예 | `save 900 1` (900초 동안 1번 이상 변경 시) | `appendonly yes` |

```
appendfsync always    매 명령 fsync → 가장 안전, 매우 느림
appendfsync everysec  1초마다 (기본, 권장)
appendfsync no        OS에 맡김
```
### 선택 기준
| 용도 | 권장 |
|---|---|
| **순수 캐시** | 영속성 끔 또는 RDB만 (재시작 시 DB에서 다시 채움) |
| 세션, 랭킹, 카운터 | **RDB + AOF** (Redis 7+ 는 AOF 안에 RDB 베이스를 포함하는 multi-part AOF) |
| 원본 데이터 | Redis를 **원본 저장소로 쓰지 않는 것**이 원칙 |

> ⚠️ RDB 저장과 AOF rewrite는 `fork()`를 사용합니다. 쓰기가 많으면 Copy-on-Write로 **메모리가 최대 2배** 가까이 필요할 수 있으니 maxmemory를 물리 메모리보다 여유 있게 잡습니다.

## 2. 복제 (Replication)

```
      [Master]  ← 쓰기
      ↙     ↘    비동기 복제
 [Replica]  [Replica]  ← 읽기 분산
```
- **비동기 복제** → 마스터가 죽으면 아직 복제되지 않은 쓰기는 유실 가능
- 레플리카로 **읽기 분산**, 백업
- 마스터가 죽어도 자동 전환은 안 됨 → Sentinel 또는 Cluster 필요

---

## 3. Sentinel (자동 장애 조치)

```
 [Sentinel 1] [Sentinel 2] [Sentinel 3]   ← 감시 (홀수, 과반수 합의)
        │ 감시          │
   [Master] ── [Replica] ── [Replica]
```
1. Sentinel들이 마스터를 주기적으로 확인
2. **과반수(quorum)** 가 마스터 장애에 동의하면
3. 레플리카 하나를 **새 마스터로 승격** (Failover)
4. 클라이언트에 새 마스터 주소 안내 (Lettuce·Redisson이 Sentinel 모드 지원)
> 데이터는 마스터 한 대에 모두 있으므로 **용량은 확장되지 않습니다.**

---

## 4. Cluster (수평 확장 + 고가용성)

```
 키 → CRC16(key) mod 16384 → 해시 슬롯 (0~16383)

 [Master A: 0~5460]     [Master B: 5461~10922]    [Master C: 10923~16383]
       │                      │                          │
  [Replica A']           [Replica B']               [Replica C']
```
| 특징 | 설명 |
|---|---|
| **샤딩** | 16384개 슬롯을 마스터들이 나눠 가짐 → 데이터·쓰기 분산 |
| 자동 Failover | 마스터가 죽으면 그 레플리카가 승격 (Sentinel 불필요) |
| 클라이언트 | 슬롯 맵을 알고 해당 노드로 직접 요청, 틀리면 `MOVED` 리다이렉트 |
| **멀티 키 제약** | `MGET`, Lua, 트랜잭션은 **같은 슬롯의 키끼리만** → 해시 태그 `{user:1}:cart`, `{user:1}:profile` |
| DB 번호 | `SELECT 1` 불가, DB 0만 사용 |

### 구성 비교
| | 단일 + Replica | Sentinel | **Cluster** |
|---|---|---|---|
| 자동 장애 조치 | ✗ | ✅ | ✅ |
| 쓰기·용량 확장 | ✗ | ✗ | ✅ |
| 멀티 키 명령 | 자유 | 자유 | 같은 슬롯만 |
| 복잡도 | 낮음 | 중간 | 높음 |
| 적합 | 개발·소규모 | 중간 규모 | 대규모 |

> 비동기 복제 특성상 Sentinel·Cluster 모두 장애 조치 과정에서 **일부 쓰기가 유실될 수 있습니다.** Redis에는 잃어도 복구 가능한 데이터만 두거나, 원본은 DB에 둡니다.

## 5. 관리형 서비스

| 서비스 | 특징 |
|---|---|
| **AWS ElastiCache** (Redis OSS / **Valkey**) | Replication·Cluster 모드, 자동 장애 조치, 백업. Valkey 엔진이 더 저렴 |
| AWS MemoryDB | **내구성 있는**(멀티 AZ 트랜잭션 로그) Redis 호환 DB |
| Redis Cloud | Redis Inc. 제공 |
> 직접 운영(EC2·K8s)보다 관리형을 쓰면 장애 조치·패치·백업을 맡길 수 있습니다.

## 6. 운영 체크리스트

| 항목 | 내용 |
|---|---|
| 메모리 | `maxmemory` + eviction 정책, `used_memory` 모니터링, fork 여유분 |
| 느린 명령 | `SLOWLOG GET`, `KEYS`·큰 컬렉션 전체 조회 금지 |
| Big Key·Hot Key | `redis-cli --bigkeys`, `--hotkeys`(LFU 정책 필요) |
| 연결 | 커넥션 풀, **타임아웃 짧게** (Redis 장애가 애플리케이션 전체 장애로 번지지 않게) |
| 보안 | `requirepass`/ACL, 외부 노출 금지(보안 그룹), TLS |
| 위험 명령 | `FLUSHALL`, `KEYS`, `CONFIG` 이름 변경·ACL로 차단 |
| 메트릭 | 적중률(`keyspace_hits/misses`), 연결 수, 지연 시간, 복제 지연 → Prometheus `redis_exporter` |

## 7. 면접 질문

1. **RDB와 AOF의 차이는?**
   → RDB는 특정 시점의 전체 데이터를 스냅샷으로 저장해 파일이 작고 복구가 빠르지만 마지막 스냅샷 이후 데이터가 유실될 수 있고, AOF는 모든 쓰기 명령을 기록해 유실이 최대 1초 수준으로 적지만 파일이 크고 복구가 느립니다.
2. **Sentinel과 Cluster의 차이는?**
   → Sentinel은 마스터 한 대와 레플리카를 감시해 장애 시 자동으로 승격시키는 고가용성 구성이고, Cluster는 해시 슬롯으로 데이터를 여러 마스터에 나누어 저장해 고가용성과 함께 수평 확장을 제공합니다.
3. **Redis Cluster에서 멀티 키 명령의 제약은?**
   → 키들이 다른 슬롯(다른 노드)에 있을 수 있어 MGET, Lua, 트랜잭션은 같은 슬롯의 키끼리만 가능하며, 해시 태그로 관련 키를 같은 슬롯에 둡니다.

---

## 핵심 정리
- 영속성: **RDB(스냅샷, 빠른 복구)** vs **AOF(명령 로그, 유실 최소)**, 캐시는 생략 가능
- Replication(비동기) → **Sentinel(자동 장애 조치)** → **Cluster(샤딩 16384 슬롯 + 장애 조치)**
- Cluster 멀티 키는 **해시 태그**로 같은 슬롯에
- 비동기 복제 → 장애 조치 시 유실 가능 → **원본은 DB**
- 운영: maxmemory·SLOWLOG·Big Key·짧은 타임아웃·ACL
