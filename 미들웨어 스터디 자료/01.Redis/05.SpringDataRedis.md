# 05. Spring Data Redis

> **학습 목표**
> - Spring Boot에서 Redis 연결(Lettuce)과 `RedisTemplate`/`StringRedisTemplate`을 설정할 수 있다.
> - 직렬화 방식을 이해하고 선택할 수 있다.
> - `@Cacheable`, `@CacheEvict`로 캐시를 선언적으로 적용하고 TTL을 캐시별로 설정할 수 있다.
> - 캐시 적용 시 흔한 실수(자기 호출, 직렬화 오류, 장애 전파)를 피할 수 있다.

---

## 1. 설정

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-redis'   // Lettuce 클라이언트 포함
    implementation 'org.springframework.boot:spring-boot-starter-cache'
}
```
```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      password: ${REDIS_PASSWORD:}
      timeout: 1s                # 명령 타임아웃 (짧게!)
      connect-timeout: 1s
      # cluster:
      #   nodes: node1:6379,node2:6379,node3:6379
```
| 클라이언트 | 특징 |
|---|---|
| **Lettuce** (기본) | Netty 기반 비동기, **연결 하나를 여러 스레드가 공유** (스레드 안전) |
| Jedis | 동기, 커넥션 풀 필요 |
| Redisson | 분산 락·고급 자료구조 (`→ 03.Redis활용패턴.md`) |

## 2. RedisTemplate

```java
@RequiredArgsConstructor
@Component
public class ViewCountRepository {

    private final StringRedisTemplate redisTemplate;      // 키·값 모두 String (가장 단순, 권장)

    public long increase(Long postId) {
        return redisTemplate.opsForValue().increment("post:" + postId + ":views");
    }

    public void saveRecent(Long memberId, Long productId) {
        String key = "recent:" + memberId;
        redisTemplate.opsForList().leftPush(key, String.valueOf(productId));
        redisTemplate.opsForList().trim(key, 0, 19);       // 최근 20개
        redisTemplate.expire(key, Duration.ofDays(7));
    }
}
```
| 메서드 | 자료구조 |
|---|---|
| `opsForValue()` | String |
| `opsForHash()` | Hash |
| `opsForList()` | List |
| `opsForSet()` | Set |
| `opsForZSet()` | Sorted Set |
| `execute(RedisScript, keys, args)` | Lua |
| `executePipelined(...)` | 파이프라인 (여러 명령을 한 번에 전송 → 왕복 감소) |

### 직렬화
기본 `RedisTemplate<Object, Object>`는 **JDK 직렬화**를 사용해 Redis에 `\xac\xed\x00...` 같은 바이트가 저장됩니다. (읽기 어렵고, 클래스 변경에 취약, 다른 언어에서 못 읽음)
```java
@Configuration
public class RedisConfig {

    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);
        template.setKeySerializer(RedisSerializer.string());
        template.setHashKeySerializer(RedisSerializer.string());
        template.setValueSerializer(RedisSerializer.json());       // Jackson JSON
        template.setHashValueSerializer(RedisSerializer.json());
        return template;
    }
}
```
| 직렬화 | 저장 형태 | 특징 |
|---|---|---|
| JDK (기본) | 바이너리 | ❌ 비권장 |
| `StringRedisSerializer` | 문자열 | 키에 사용 |
| `RedisSerializer.json()` (Generic Jackson) | JSON + **`@class` 타입 정보** | 어떤 객체든 저장, 패키지·클래스명 변경 시 역직렬화 실패 |
| 타입 지정 Jackson 직렬화 | JSON (타입 정보 없음) | 캐시마다 타입 지정, 가장 깔끔 |
> Boot 4(Spring Data Redis 4)는 **Jackson 3** 기반 직렬화기를 제공하고 Jackson 2 기반 클래스(`GenericJackson2JsonRedisSerializer`)는 deprecated입니다. `RedisSerializer.json()` 팩토리를 쓰면 버전에 맞는 구현이 선택됩니다.

## 3. 스프링 캐시 추상화: `@Cacheable`

```java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration defaults = RedisCacheConfiguration.defaultCacheConfig()
                .serializeKeysWith(RedisSerializationContext.SerializationPair.fromSerializer(RedisSerializer.string()))
                .serializeValuesWith(RedisSerializationContext.SerializationPair.fromSerializer(RedisSerializer.json()))
                .entryTtl(Duration.ofMinutes(10))             // 기본 TTL
                .disableCachingNullValues()
                .prefixCacheNameWith("shop:");

        Map<String, RedisCacheConfiguration> perCache = Map.of(
                "product", defaults.entryTtl(Duration.ofMinutes(30)),
                "category", defaults.entryTtl(Duration.ofHours(6)),
                "ranking", defaults.entryTtl(Duration.ofMinutes(1)));

        return RedisCacheManager.builder(factory)
                .cacheDefaults(defaults)
                .withInitialCacheConfigurations(perCache)
                .build();
    }
}
```
```java
@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductRepository productRepository;

    @Cacheable(cacheNames = "product", key = "#id")          // 키: shop:product::42
    @Transactional(readOnly = true)
    public ProductResponse getProduct(Long id) {
        return ProductResponse.from(productRepository.findById(id).orElseThrow());
    }

    @CacheEvict(cacheNames = "product", key = "#id")          // 수정 시 삭제
    @Transactional
    public void updatePrice(Long id, long price) {
        productRepository.findById(id).orElseThrow().changePrice(price);
    }

    @Caching(evict = {
            @CacheEvict(cacheNames = "product", key = "#id"),
            @CacheEvict(cacheNames = "category", allEntries = true)})
    @Transactional
    public void delete(Long id) { ... }
}
```
| 애노테이션 | 동작 |
|---|---|
| `@Cacheable` | 캐시에 있으면 메서드 실행 X, 없으면 실행 후 저장 (**Cache-Aside**) |
| `@CacheEvict` | 캐시 삭제 (`beforeInvocation = false` 기본: 메서드 성공 후 삭제) |
| `@CachePut` | 항상 실행하고 결과로 캐시 갱신 |
| `@Caching` | 여러 개 조합 |

| 옵션 | 예 |
|---|---|
| `key` (SpEL) | `"#id"`, `"#cond.status + ':' + #pageable.pageNumber"` |
| `condition` | `"#id > 0"` (실행 전 조건) |
| `unless` | `"#result == null"` (결과 보고 저장 안 함) |
| `sync = true` | 같은 키 동시 Miss 시 하나만 실행 (JVM 내) |

### `@CacheEvict`와 트랜잭션 순서 주의
- 같은 메서드에 `@Transactional` + `@CacheEvict`면 프록시 순서에 따라 **커밋 전에 캐시가 삭제**될 수 있습니다 → 그 사이 다른 요청이 옛 값을 다시 캐시
- 확실하게 하려면 캐시 삭제를 `@TransactionalEventListener(phase = AFTER_COMMIT)`에서 수행하거나, 트랜잭션 메서드를 호출하는 **바깥 메서드**에 `@CacheEvict`
> 트랜잭션을 인식하는 캐시(`RedisCacheManager.builder(...).transactionAware()`)를 쓰면 put/evict가 커밋 후에 실행됩니다.

## 4. 자주 하는 실수

| 실수 | 결과 | 해결 |
|---|---|---|
| **같은 클래스 내부 호출** | 프록시를 안 거쳐 캐시 미적용 | 별도 빈으로 분리 (`Spring JPA 스터디 자료`의 AOP 문서) |
| **엔티티를 캐시** | 지연 로딩 프록시 직렬화 실패, 엔티티 변경 시 캐시 깨짐 | **DTO(record)를 캐시** |
| TTL 없음 | 메모리 무한 증가, 영원히 오래된 데이터 | 캐시별 TTL |
| 클래스 구조 변경 후 배포 | 기존 캐시 역직렬화 실패 → 500 에러 | 캐시 이름·키 접두사에 **버전**, 배포 시 해당 캐시 삭제 |
| **Redis 장애가 서비스 장애로** | 캐시 조회 타임아웃 동안 요청 스레드가 묶임 | **짧은 타임아웃** + `CacheErrorHandler`로 예외를 무시하고 DB 조회 |
| `Page<T>` 그대로 캐시 | `PageImpl` 역직렬화 문제 | 캐시용 DTO로 변환 |

### 캐시 장애 시 DB로 우회
```java
@Configuration
public class CacheErrorConfig implements CachingConfigurer {
    @Override
    public CacheErrorHandler errorHandler() {
        return new SimpleCacheErrorHandler() {
            @Override
            public void handleCacheGetError(RuntimeException e, Cache cache, Object key) {
                log.warn("캐시 조회 실패 cache={} key={}", cache.getName(), key, e);   // 던지지 않음 → 메서드 실행(DB)
            }
            @Override
            public void handleCachePutError(RuntimeException e, Cache cache, Object key, Object value) {
                log.warn("캐시 저장 실패 cache={} key={}", cache.getName(), key, e);
            }
        };
    }
}
```

## 6. 면접 질문

1. **`@Cacheable`은 어떻게 동작하나요?**
   → AOP 프록시가 메서드 호출 전에 캐시 키로 조회해 값이 있으면 메서드를 실행하지 않고 반환하고, 없으면 메서드를 실행한 결과를 캐시에 저장합니다. 프록시 기반이라 내부 호출에는 적용되지 않습니다.
2. **Redis에 객체를 저장할 때 직렬화는 어떻게 하나요?**
   → 기본 JDK 직렬화는 읽기 어렵고 클래스 변경에 취약하므로 키는 String, 값은 JSON 직렬화를 사용하고, 엔티티 대신 DTO를 저장합니다.
3. **Redis가 장애 나면 캐시를 쓰는 서비스는 어떻게 되나요?**
   → 타임아웃이 길면 요청 스레드가 묶여 전체 장애로 번질 수 있으므로, 짧은 타임아웃과 CacheErrorHandler로 캐시 오류를 무시하고 DB로 조회하게 하며, 필요하면 서킷 브레이커로 DB 부하를 제한합니다.

## 핵심 정리
- `spring-boot-starter-data-redis`(Lettuce) + **짧은 타임아웃**
- 단순 값은 **`StringRedisTemplate`**, 객체는 **JSON 직렬화** (JDK 직렬화 ✗)
- `@EnableCaching` + `RedisCacheManager`로 **캐시별 TTL**, `@Cacheable`/`@CacheEvict`
- **DTO를 캐시**, 내부 호출 주의, 커밋 후 삭제
- `CacheErrorHandler`로 **Redis 장애 시 DB 우회**
