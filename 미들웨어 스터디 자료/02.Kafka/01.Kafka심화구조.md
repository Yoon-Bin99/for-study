# 01. Kafka 심화 구조

> **학습 목표**
> - 토픽·파티션·오프셋·컨슈머 그룹의 관계를 그림으로 설명할 수 있다.
> - 복제(Leader/Follower, ISR)와 `acks`, `min.insync.replicas`의 관계를 이해한다.
> - 파티션 수와 키 설계가 처리량·순서에 미치는 영향을 안다.
> - 리밸런싱과 KRaft(ZooKeeper 제거), Kafka 4.x의 변화를 설명할 수 있다.

---

## 1. Kafka란? 왜 쓰는가?

**분산 이벤트 스트리밍 플랫폼** — 메시지를 디스크 로그에 순서대로 저장하고, 여러 소비자가 각자 속도로 읽어 갑니다.
```
[주문 서비스] ──"주문 생성" 이벤트──▶ [Kafka: order-created 토픽]
                                         ├──▶ [결제 서비스]
                                         ├──▶ [알림 서비스]
                                         └──▶ [검색 색인·통계]
```
| 이점 | 설명 |
|---|---|
| **느슨한 결합** | 주문 서비스는 누가 이벤트를 받는지 모름 → 소비자 추가가 자유로움 |
| 비동기·완충 | 트래픽 폭주 시 Kafka에 쌓아 두고 소비자가 처리할 수 있는 속도로 |
| **재처리** | 메시지가 읽어도 삭제되지 않음 (보존 기간 동안) → 오프셋을 되돌려 다시 처리 |
| 높은 처리량 | 순차 디스크 쓰기, 배치, 제로 카피 → 초당 수십만~수백만 건 |

| 비교 | Kafka | RabbitMQ (`→ 04.메시지큐/01.RabbitMQ.md`) |
|---|---|---|
| 모델 | **로그(pull)**, 읽어도 남음 | **큐(push)**, 확인(ack)하면 삭제 |
| 강점 | 대용량 스트림, 재처리, 여러 소비자 | 유연한 라우팅, 작업 큐, 낮은 지연 |

## 2. 핵심 구조

```
                    Topic: order-created (파티션 3개, 복제 3)
 Broker 1                 Broker 2                 Broker 3
 ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
 │ P0 (Leader)  │        │ P0 (Follower)│        │ P0 (Follower)│
 │ P1 (Follower)│        │ P1 (Leader)  │        │ P1 (Follower)│
 │ P2 (Follower)│        │ P2 (Follower)│        │ P2 (Leader)  │
 └──────────────┘        └──────────────┘        └──────────────┘

 파티션 P0 = 순서가 보장되는 append-only 로그
 ┌───┬───┬───┬───┬───┬───┐
 │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ ← 새 메시지는 끝에 추가
 └───┴───┴───┴───┴───┴───┘
           ↑ 컨슈머 그룹 A의 커밋된 오프셋 = 3 (다음에 읽을 위치)
```
| 용어 | 설명 |
|---|---|
| **Broker** | Kafka 서버 한 대 |
| **Topic** | 메시지 분류 (테이블과 비슷한 논리 단위) |
| **Partition** | 토픽을 나눈 **병렬 처리 단위**, 파티션 **안에서만 순서 보장** |
| **Offset** | 파티션 안에서 메시지의 위치(번호) |
| **Producer** | 메시지 발행 |
| **Consumer Group** | 같은 그룹의 컨슈머들이 파티션을 **나눠서** 처리 |
| **Leader / Follower** | 파티션마다 리더가 읽기·쓰기 담당, 팔로워는 복제 |

## 3. 프로듀서: 어느 파티션으로 갈까?

| 키 | 파티션 결정 |
|---|---|
| **키 있음** | `hash(key) % 파티션 수` → **같은 키는 항상 같은 파티션** → 순서 보장 |
| 키 없음 | Sticky Partitioner: 배치 단위로 한 파티션에 모았다가 다음 파티션으로 (고르게 분산) |
```java
kafkaTemplate.send("order-events", String.valueOf(orderId), event);   // 키 = 주문 ID
// 같은 주문의 "생성 → 결제 → 배송" 이벤트가 같은 파티션 → 순서대로 소비
```
> ⚠️ **파티션 수를 늘리면** `hash % N`이 바뀌어 같은 키가 다른 파티션으로 갈 수 있습니다 → 그 시점 전후로 순서가 깨질 수 있음. 파티션 수는 처음에 여유 있게 정합니다. (파티션은 늘릴 수만 있고 줄일 수 없음)

### 배치와 압축
```
linger.ms=5~20           # 조금 기다렸다가 모아서 전송 → 처리량 ↑
batch.size=65536
compression.type=lz4     # 또는 zstd → 네트워크·디스크 절약
```

## 4. 컨슈머 그룹

```
 토픽 (파티션 4개)            컨슈머 그룹 "payment-service"
  P0 ─────────────────────▶ Consumer 1
  P1 ─────────────────────▶ Consumer 1
  P2 ─────────────────────▶ Consumer 2
  P3 ─────────────────────▶ Consumer 2

                              컨슈머 그룹 "notification-service"  ← 다른 그룹은 처음부터 독립적으로 전부 읽음
  P0~P3 ──────────────────▶ Consumer A
```
| 규칙 | 의미 |
|---|---|
| 한 파티션은 그룹 내 **컨슈머 하나**에만 할당 | 파티션 안 순서 유지 |
| 컨슈머 수 > 파티션 수 | **남는 컨슈머는 놀게 됨** → 최대 병렬도 = 파티션 수 |
| 그룹마다 오프셋 따로 | 여러 서비스가 같은 이벤트를 각자 소비 |
| 오프셋 커밋 | `__consumer_offsets` 내부 토픽에 "어디까지 처리했는지" 저장 |

### 리밸런싱 (Rebalancing)
컨슈머가 추가·종료·장애 → 파티션 재할당
| 문제 | 설명 |
|---|---|
| 예전 방식 (Eager) | 재할당 동안 **그룹 전체 소비 중단** (Stop-the-world) |
| 처리 시간 > `max.poll.interval.ms` (기본 5분) | 컨슈머가 죽은 것으로 간주 → 리밸런싱 → **중복 처리** |
| 대응 | `max.poll.records` 줄이기, 처리 시간 단축, Cooperative Sticky 할당, **Static Membership** (`group.instance.id`) |
| **Kafka 4.0: 새 리밸런스 프로토콜 (KIP-848) GA** | 브로커(그룹 코디네이터)가 할당을 관리하고 **점진적**으로 재할당 → 중단 최소화. 컨슈머 `group.protocol=consumer` 로 사용 |

## 5. 복제와 내구성

```
 파티션 P0 (replication.factor = 3)
   Leader (Broker 1)  ◀── 프로듀서 쓰기
     ├── Follower (Broker 2)  ✅ ISR
     └── Follower (Broker 3)  ✅ ISR   (뒤처지면 ISR에서 제외)
```
- **ISR (In-Sync Replicas)**: 리더와 충분히 동기화된 복제본 목록
- 리더 장애 → ISR 중 하나가 새 리더

### acks 설정
| acks | 의미 | 유실 위험 | 속도 |
|---|---|---|---|
| `0` | 응답 안 기다림 | 높음 | 가장 빠름 |
| `1` | 리더 저장만 확인 | 리더 장애 시 유실 | 빠름 |
| **`all` (-1)** | **ISR 모두** 저장 확인 | 최소 | 느림 |
> Kafka 3.0부터 프로듀서 기본값이 **`acks=all`, `enable.idempotence=true`** 입니다.

### min.insync.replicas
```
replication.factor = 3
min.insync.replicas = 2     # acks=all일 때 최소 2개 복제본에 저장돼야 성공
→ 브로커 1대 장애: 계속 쓰기 가능
→ 브로커 2대 장애: 쓰기 거부 (NotEnoughReplicas) — 유실 대신 가용성을 포기
```
**권장 조합**: `replication.factor=3`, `min.insync.replicas=2`, `acks=all`

## 6. 저장과 보존

```
retention.ms=604800000      # 7일 보관 (기본)
retention.bytes=-1          # 크기 제한 없음
cleanup.policy=delete       # 기간 지나면 삭제
cleanup.policy=compact      # 키별 "최신 값"만 남김 (상태 스냅샷, 설정·회원 정보 변경 이벤트)
```
- 파티션은 **세그먼트 파일**로 나뉘어 저장, 오래된 세그먼트 단위로 삭제
- 빠른 이유: **순차 쓰기**(append), OS 페이지 캐시, **제로 카피**(sendfile)로 디스크 → 네트워크 직접 전송

## 7. KRaft와 Kafka 4.x

| 항목 | 예전 | Kafka 4.0 (2025.3) 이후 |
|---|---|---|
| 메타데이터 관리 | **ZooKeeper** 별도 클러스터 | **KRaft** (Kafka 내장 Raft 컨트롤러) — **ZooKeeper 완전 제거** |
| 리밸런스 | 클라이언트 주도 | KIP-848 서버 주도 프로토콜 GA |
| 큐 방식 소비 | 불가 (파티션 수 = 병렬 한계) | **Share Group** (KIP-932, Queues for Kafka): 파티션 수보다 많은 컨슈머가 메시지 단위로 나눠 처리 — 4.0 얼리 액세스, 이후 버전에서 안정화 진행 |
| Java | 브로커 Java 11 | 브로커 **Java 17**, 클라이언트 Java 11+ |
> 오래된 자료의 `--zookeeper localhost:2181` 옵션은 더 이상 쓰지 않습니다. CLI는 `--bootstrap-server`를 사용합니다.

## 8. 면접 질문

1. **파티션과 컨슈머 그룹의 관계는?**
   → 한 파티션은 같은 그룹의 컨슈머 하나에만 할당되어 파티션 안의 순서가 보장되고, 그룹의 최대 병렬도는 파티션 수입니다. 다른 그룹은 같은 메시지를 독립적으로 소비합니다.
2. **Kafka에서 순서를 보장하려면?**
   → 순서는 파티션 안에서만 보장되므로, 순서가 필요한 이벤트(같은 주문)에 같은 키를 지정해 같은 파티션으로 보냅니다.
3. **메시지 유실을 막는 설정은?**
   → 복제 계수 3, min.insync.replicas 2, 프로듀서 acks=all과 멱등성 활성화, 컨슈머는 처리 완료 후 오프셋을 커밋합니다.
4. **리밸런싱이란? 문제와 대응은?**
   → 컨슈머 그룹 구성이 바뀔 때 파티션을 재할당하는 과정으로, 예전 방식은 그룹 전체가 멈추고 처리 시간이 길면 불필요한 리밸런싱과 중복 처리가 생깁니다. poll 레코드 수 조절, 정적 멤버십, 점진적 리밸런싱(KIP-848)으로 줄입니다.
5. **ZooKeeper와 KRaft의 차이는?**
   → 예전에는 메타데이터를 외부 ZooKeeper가 관리했지만, KRaft는 Kafka 내부 Raft 컨트롤러가 관리해 운영 구성이 단순해지고 확장성이 좋아졌으며, Kafka 4.0부터는 KRaft만 지원합니다.

## 핵심 정리
- Topic → **Partition(순서·병렬 단위)** → Offset, **키로 파티션 결정**
- 컨슈머 그룹: 파티션 1개 = 컨슈머 1개, **병렬도 = 파티션 수**, 그룹별 독립 오프셋
- 내구성: **RF=3, min.insync=2, acks=all, 멱등 프로듀서**
- 리밸런싱 주의 (`max.poll.interval.ms`), Kafka 4: **KRaft만**, KIP-848, Share Group
