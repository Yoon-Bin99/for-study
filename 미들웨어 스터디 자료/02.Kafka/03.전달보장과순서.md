# 03. 전달 보장과 순서

> **학습 목표**
> - At-most-once, At-least-once, Exactly-once의 의미와 Kafka에서의 구현을 설명할 수 있다.
> - 중복 소비가 왜 발생하는지 이해하고 **멱등 컨슈머**를 구현할 수 있다.
> - DB 저장과 이벤트 발행의 원자성 문제를 **Transactional Outbox 패턴**으로 해결할 수 있다.
> - 순서 보장 조건과 순서가 깨지는 경우를 안다.

---

## 1. 전달 보장 수준

| 수준 | 의미 | 결과 |
|---|---|---|
| **At-most-once** | 최대 한 번 | **유실 가능**, 중복 없음 |
| **At-least-once** | 최소 한 번 | 유실 없음, **중복 가능** ← 실무 기본 |
| **Exactly-once** | 정확히 한 번 | 유실·중복 없음 (조건이 까다롭고 비용 큼) |

### 컨슈머 커밋 시점이 결정한다
```
At-most-once : 커밋 → 처리     (처리 중 죽으면 그 메시지는 이미 커밋됨 → 유실)
At-least-once: 처리 → 커밋     (처리 후 커밋 전에 죽으면 → 재시작 시 다시 처리 → 중복)
```
> 네트워크와 장애가 있는 분산 시스템에서 **"정확히 한 번 처리"를 메시지 시스템만으로 보장하기는 어렵습니다.** 실무의 정답은 **At-least-once + 멱등 처리 = 효과적인 Exactly-once**입니다.

## 2. 프로듀서 측 보장

| 설정 | 효과 |
|---|---|
| `acks=all` + `min.insync.replicas=2` | 브로커 장애에도 유실 방지 |
| `retries` (기본 매우 큼) + `delivery.timeout.ms` | 일시 오류 자동 재시도 |
| **`enable.idempotence=true`** (3.0+ 기본) | 재시도로 인한 **중복 저장 방지** (프로듀서 ID + 시퀀스 번호로 브로커가 중복 제거) + 파티션 내 순서 유지 |

```
멱등성 없이 재시도
 Producer ──msg──▶ Broker (저장 성공)
 Producer ◀──X── (ack 유실)
 Producer ──msg──▶ Broker (또 저장) → 중복

멱등성 사용
 Producer ──msg(PID=7, seq=42)──▶ Broker (저장)
 Producer ──msg(PID=7, seq=42)──▶ Broker: "이미 받은 seq" → 무시하고 ack
```

### Kafka 트랜잭션 (Exactly-once, Kafka 안에서)
```
consume(입력 토픽) → process → produce(출력 토픽) + 오프셋 커밋 을 하나의 트랜잭션으로
```
- `transactional.id` 설정, 컨슈머는 `isolation.level=read_committed`
- Kafka Streams의 `processing.guarantee=exactly_once_v2`
- ⚠️ **Kafka 밖(DB, 외부 API)의 부수 효과까지 묶지는 못함** → DB 연동에는 멱등 컨슈머 + Outbox

---

## 3. 중복 소비가 발생하는 경우

| 원인 | 설명 |
|---|---|
| 처리 후 커밋 전 장애 | 재시작하면 마지막 커밋 오프셋부터 다시 |
| **리밸런싱** | 처리 시간이 `max.poll.interval.ms` 초과 → 파티션이 다른 컨슈머로 → 같은 메시지 재처리 |
| 프로듀서 중복 발행 | 멱등성이 없거나, 애플리케이션이 같은 이벤트를 두 번 발행 (Outbox 재전송 포함) |
| 재시도 후 성공 | 외부 API는 성공했는데 응답 타임아웃 → 재시도 |

## 4. 멱등 컨슈머 (Idempotent Consumer) ★

**같은 메시지를 여러 번 처리해도 결과가 한 번 처리한 것과 같도록** 만듭니다.

### ① 처리 기록 테이블 (이벤트 ID 기반)
```sql
CREATE TABLE processed_event (
    event_id     VARCHAR(64) PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL
);
```
```java
@Service
@RequiredArgsConstructor
public class PaymentEventHandler {

    private final ProcessedEventRepository processedEventRepository;
    private final PaymentService paymentService;

    @Transactional
    public void handle(OrderCreatedEvent event) {
        if (processedEventRepository.existsById(event.eventId())) {
            return;                                          // 이미 처리 → 무시
        }
        paymentService.createPayment(event.orderId(), event.totalPrice());
        processedEventRepository.save(new ProcessedEvent(event.eventId()));
        // 같은 트랜잭션 → 비즈니스 처리와 처리 기록이 함께 커밋 or 함께 롤백
        // 동시에 같은 이벤트가 들어오면 PK 중복 예외 → 한쪽만 성공
    }
}
```

### ② 비즈니스 키 유니크 제약
```sql
ALTER TABLE payment ADD CONSTRAINT uk_payment_order UNIQUE (order_id);
-- 같은 주문에 결제가 두 번 생기지 않음 → DataIntegrityViolationException 은 "이미 처리"로 간주
```

### ③ 연산 자체를 멱등하게
| 멱등 ❌ | 멱등 ✅ |
|---|---|
| `point = point + 100` | `INSERT point_history(event_id, 100)` (유니크) 후 합계 |
| `status`를 무조건 다음 단계로 | `UPDATE ... SET status='PAID' WHERE id=? AND status='CREATED'` |
| 외부 API에 그냥 재요청 | **멱등 키 헤더**(`Idempotency-Key: eventId`)를 지원하는 API 사용 |

## 5. Transactional Outbox 패턴 ★

### 문제: DB 저장과 메시지 발행은 원자적이지 않다
```java
@Transactional
public void placeOrder(...) {
    orderRepository.save(order);
    kafkaTemplate.send("order-created", event);   // ① 발행 성공 후 DB 커밋 실패 → 없는 주문의 이벤트
}                                                   // ② DB 커밋 성공 후 발행 실패 → 이벤트 유실
```
| 시도 | 문제 |
|---|---|
| 트랜잭션 안에서 발행 | 롤백돼도 메시지는 이미 나감 |
| `AFTER_COMMIT`에서 발행 | 커밋 후 발행 직전 서버가 죽으면 **유실** |
| 2PC (분산 트랜잭션) | Kafka가 XA를 지원하지 않음, 느리고 복잡 |

### 해결: 이벤트를 같은 DB 트랜잭션으로 "outbox 테이블"에 저장
```
 ┌──────────── 하나의 DB 트랜잭션 ────────────┐
 │ INSERT INTO orders ...                    │
 │ INSERT INTO outbox (event_id, aggregate_id, type, payload, status='PENDING') │
 └───────────────────────────────────────────┘
                    │
       [Relay: 폴링 스케줄러 또는 CDC(Debezium)]
                    │  PENDING 이벤트를 읽어 Kafka 발행 → 성공 시 SENT
                    ▼
                 [Kafka]
```
```java
@Transactional
public Long placeOrder(OrderCreateRequest request) {
    Order order = orderRepository.save(Order.create(request));
    outboxRepository.save(OutboxEvent.of("order-created", order.getId(),
            new OrderCreatedEvent(UUID.randomUUID().toString(), order.getId(), ...)));
    return order.getId();
}
```
```java
@Component
@RequiredArgsConstructor
public class OutboxRelay {

    private final OutboxRepository outboxRepository;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelay = 1000)
    public void relay() {
        List<OutboxEvent> events = outboxRepository.findTop100ByStatusOrderByIdAsc(OutboxStatus.PENDING);
        for (OutboxEvent e : events) {
            try {
                kafkaTemplate.send(e.getTopic(), e.getAggregateId(), e.getPayload()).get(3, TimeUnit.SECONDS);
                e.markSent();
            } catch (Exception ex) {
                e.increaseRetry();                       // 다음 주기에 재시도, 횟수 초과 시 알림
                break;                                   // 같은 애그리거트 순서를 지키려면 중단
            }
        }
        outboxRepository.saveAll(events);
    }
}
```
| 릴레이 방식 | 특징 |
|---|---|
| **폴링** (`@Scheduled`) | 구현 간단, 약간의 지연, 서버 여러 대면 중복 실행 방지 필요 (ShedLock, `SELECT ... FOR UPDATE SKIP LOCKED`) |
| **CDC** (Debezium + Kafka Connect) | DB 변경 로그(binlog)를 읽어 발행 → 지연 짧고 애플리케이션 코드 없음, 인프라 복잡 |

> Outbox도 "발행 성공 → SENT 저장 전 장애" 시 **재발행(중복)** 이 생깁니다. 그래서 **Outbox(유실 방지) + 멱등 컨슈머(중복 방지)** 를 함께 씁니다.

## 6. 순서 보장

| 조건 | 설명 |
|---|---|
| **같은 키 → 같은 파티션** | 파티션 안에서만 순서 보장 |
| 멱등 프로듀서 | 재시도해도 파티션 내 순서 유지 (`max.in.flight.requests.per.connection ≤ 5`) |
| 파티션당 컨슈머 하나 | 컨슈머 그룹 규칙으로 자동 |
| 컨슈머 내부 **순차 처리** | 리스너 안에서 다른 스레드 풀로 넘기면 순서 깨짐 |

### 순서가 깨지는 경우
- **파티션 수 증가** (키 → 파티션 매핑 변경)
- 논블로킹 재시도(`@RetryableTopic`): 실패 메시지가 재시도 토픽으로 빠짐
- Outbox 릴레이가 병렬 발행
- 서로 다른 토픽 사이 (주문 토픽과 결제 토픽 간에는 순서 없음)

### 순서를 완벽히 의존하지 않는 설계
```
이벤트에 버전·발생 시각 포함 → 컨슈머가 "내가 가진 것보다 오래된 이벤트면 무시"
UPDATE product_view SET ... , version = :v WHERE id = :id AND version < :v
```

## 7. 면접 질문

1. **Kafka의 전달 보장 수준을 설명해 주세요.**
   → 처리 전에 커밋하면 유실 가능한 At-most-once, 처리 후 커밋하면 중복 가능한 At-least-once, 멱등 프로듀서와 트랜잭션으로 Kafka 내부에서 구현하는 Exactly-once가 있습니다. 실무에서는 At-least-once에 멱등 컨슈머를 결합합니다.
2. **중복 메시지는 어떻게 처리하나요?**
   → 이벤트에 고유 ID를 두고 처리 기록 테이블이나 비즈니스 키 유니크 제약으로 이미 처리한 이벤트를 무시하며, 처리와 기록을 같은 트랜잭션으로 묶습니다.
3. **Outbox 패턴이란?**
   → 비즈니스 데이터와 발행할 이벤트를 같은 DB 트랜잭션으로 outbox 테이블에 저장하고, 별도 릴레이가 이를 읽어 Kafka로 발행하는 패턴으로 DB 저장과 이벤트 발행의 원자성 문제(유실·유령 이벤트)를 해결합니다.
4. **Kafka에서 순서가 깨지는 경우는?**
   → 키가 없거나 다를 때, 파티션 수를 늘렸을 때, 논블로킹 재시도로 메시지가 재시도 토픽으로 빠질 때, 컨슈머가 내부에서 병렬 처리할 때 깨질 수 있습니다.

## 핵심 정리
- 실무 = **At-least-once + 멱등 컨슈머**
- 프로듀서: `acks=all` + **멱등성**(중복 저장 방지), Kafka 트랜잭션은 Kafka 내부까지만
- 멱등 컨슈머: **이벤트 ID 처리 기록 / 유니크 제약 / 조건부 UPDATE**
- DB + 발행 원자성 = **Transactional Outbox** (폴링 or CDC) + 멱등 컨슈머
- 순서 = **같은 키·같은 파티션·순차 처리**, 버전으로 방어
