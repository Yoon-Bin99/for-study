# 04. Kafka 운영과 모니터링

> **학습 목표**
> - 컨슈머 랙(Lag)의 의미와 대응 방법을 설명할 수 있다.
> - 파티션 수, 보존 기간, 브로커 설정 등 운영 설계 기준을 안다.
> - 주요 모니터링 지표와 도구를 안다.
> - 스키마 관리와 관리형 서비스(MSK) 선택 기준을 이해한다.

---

## 1. 컨슈머 랙 (Consumer Lag) ★

```
 파티션 P0
 ┌───┬───┬───┬───┬───┬───┬───┬───┐
 │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │
 └───┴───┴───┴───┴───┴───┴───┴───┘
           ↑ 커밋 오프셋(3)        ↑ 최신 오프셋(Log End Offset = 8)
           Lag = 8 - 3 = 5   ← 아직 처리하지 못한 메시지 수
```
- 랙이 **계속 증가** = 생산 속도 > 소비 속도 → 처리 지연, 보존 기간을 넘기면 **데이터 손실**
```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group payment-service
# TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# order-created  0          1500            1520            20
```
### 랙이 늘어날 때 대응
| 원인 | 대응 |
|---|---|
| 컨슈머 수 부족 | 컨슈머(파드) 증설 — **파티션 수까지만** 의미 있음 |
| 파티션 수 부족 | 파티션 증설 (키 순서 영향 고려) |
| 처리 로직이 느림 (외부 API, 건별 DB 저장) | 배치 리스너 + 벌크 저장, 비동기화, 쿼리 튜닝 |
| 특정 파티션만 랙 (핫 파티션) | **키 쏠림** 확인 → 키 설계 변경 |
| 리밸런싱 반복 | `max.poll.records`·처리 시간 확인, 정적 멤버십 |
| 실패 재시도로 정체 | DLT로 빼고 진행 |
> K8s에서는 **KEDA**의 Kafka 스케일러로 랙 기준 컨슈머 자동 확장이 가능합니다.

## 2. 운영 설계 기준

### 파티션 수
```
필요 파티션 수 ≥ max(목표 처리량 / 프로듀서 파티션당 처리량,
                    목표 처리량 / 컨슈머 1개 처리량)
예: 목표 초당 3,000건, 컨슈머 1개가 초당 300건 처리 → 최소 10개 (+ 여유분 → 12)
```
| 너무 적으면 | 너무 많으면 |
|---|---|
| 병렬도 부족, 확장 불가 | 브로커 메모리·파일 핸들 증가, 리더 선출·리밸런싱 느려짐 |
> 팁: 컨슈머 수의 약수가 많은 수(6, 12, 24)로 정하면 컨슈머를 늘릴 때 고르게 분배됩니다.

### 주요 설정
| 설정 | 권장 |
|---|---|
| `replication.factor` | 3 |
| `min.insync.replicas` | 2 |
| `unclean.leader.election.enable` | false (ISR 밖 복제본이 리더가 되어 유실되는 것 방지) |
| `auto.create.topics.enable` | false (오타 토픽 자동 생성 방지) |
| `retention.ms` | 재처리에 필요한 기간 (보통 3~7일) |
| 메시지 크기 | `message.max.bytes` 기본 약 1MB → 큰 파일은 S3에 두고 **경로만** 전송 |
| 랙 인식 | `broker.rack` = AZ → 복제본을 다른 AZ에 분산 |

### 메시지 설계
```json
{
  "eventId": "6f1c2b8e-1d2a-4c3b-9e0f-7a8b9c0d1e2f",
  "eventType": "OrderCreated",
  "version": 1,
  "occurredAt": "2026-11-09T10:15:30Z",
  "aggregateId": "42",
  "payload": { "orderId": 42, "memberId": 7, "totalPrice": 20000 }
}
```
- **eventId**(멱등), **eventType·version**(스키마 진화), 발생 시각, 집계 ID(키)
- 필드 **추가는 OK**, 삭제·타입 변경은 하위 호환성 깨짐 → 새 버전 이벤트로

## 3. 스키마 관리

| 방식 | 설명 |
|---|---|
| JSON + 문서 | 간단, 스키마 검증 없음 → 생산자 변경으로 소비자가 깨지기 쉬움 |
| **Schema Registry + Avro/Protobuf** | 스키마를 중앙 등록, **호환성 규칙**(BACKWARD 등) 검사 → 깨지는 변경은 등록 거부 |
> 서비스·팀이 많아질수록 Schema Registry(Confluent, AWS Glue Schema Registry, Apicurio)의 가치가 커집니다.

## 4. 모니터링 지표

| 영역 | 지표 | 의미 |
|---|---|---|
| **컨슈머** | **Consumer Lag** (그룹·파티션별) | 처리 지연 — 가장 중요한 알림 대상 |
| 컨슈머 | 리밸런싱 횟수, 처리 시간, 에러율, DLT 유입량 | |
| 브로커 | **UnderReplicatedPartitions** | 0이 아니면 복제 지연·브로커 이상 |
| 브로커 | OfflinePartitionsCount, ActiveControllerCount | 리더 없는 파티션, 컨트롤러 상태 |
| 브로커 | 요청 지연(Produce/Fetch), 디스크 사용률, 네트워크 | |
| 프로듀서 | record-error-rate, request-latency, 배치 크기 | |

### 도구
| 도구 | 용도 |
|---|---|
| **Kafka UI** (provectus, kafbat), AKHQ, Redpanda Console | 토픽·메시지·컨슈머 그룹 조회 |
| Burrow, kafka-lag-exporter | 랙 모니터링 |
| Prometheus JMX Exporter + Grafana | 브로커 메트릭 |
| Micrometer (Spring Kafka) | 애플리케이션 프로듀서·컨슈머 메트릭 → `/actuator/prometheus` |

## 5. 자주 쓰는 CLI

```bash
# 토픽
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic order-created \
  --partitions 6 --replication-factor 3
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic order-created

# 메시지 확인
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic order-created \
  --from-beginning --property print.key=true --max-messages 10

# 오프셋 되돌리기 (재처리) — 컨슈머를 멈춘 상태에서
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group payment-service \
  --topic order-created --reset-offsets --to-datetime 2026-11-09T00:00:00.000 --execute
```
> 오프셋을 되돌려 재처리할 수 있는 것은 Kafka의 큰 장점이지만, **컨슈머가 멱등**해야 안전합니다.

## 6. 관리형 vs 직접 운영

| 선택지 | 특징 |
|---|---|
| **Amazon MSK** | AWS 관리형 Kafka (Provisioned / **Serverless**), IAM 인증 |
| Confluent Cloud | Kafka 개발사, Schema Registry·Connect·ksqlDB 통합 |
| K8s + **Strimzi** 오퍼레이터 | 직접 운영, 유연하지만 운영 부담 |
| Redpanda | Kafka API 호환, C++ 구현, ZooKeeper·JVM 없음 |
> 메시지량이 적고 단순한 비동기 작업이면 Kafka 대신 **SQS** 같은 관리형 큐가 더 경제적일 수 있습니다. (`→ 04.메시지큐/02.SQS와SNS.md`)

## 7. 면접 질문

1. **컨슈머 랙이란? 늘어나면 어떻게 하나요?**
   → 최신 오프셋과 컨슈머가 커밋한 오프셋의 차이로 아직 처리하지 못한 메시지 수입니다. 컨슈머를 파티션 수까지 늘리고, 필요하면 파티션을 늘리며, 처리 로직을 배치화·최적화하고, 특정 파티션만 늘면 키 쏠림을 확인합니다.
2. **파티션 수는 어떻게 정하나요?**
   → 목표 처리량을 컨슈머 하나의 처리량으로 나눈 값에 여유를 더해 정하고, 늘릴 수는 있지만 줄일 수 없고 늘리면 키 순서가 바뀌므로 처음에 여유 있게 잡습니다.
3. **Kafka에서 꼭 모니터링해야 할 지표는?**
   → 컨슈머 랙, UnderReplicatedPartitions와 OfflinePartitions, 요청 지연과 디스크 사용률, 그리고 애플리케이션의 에러율과 DLT 유입량입니다.

## 핵심 정리
- **Consumer Lag** = 최신 오프셋 − 커밋 오프셋 → 가장 중요한 지표
- 랙 대응: 컨슈머 증설(≤ 파티션) → 파티션 증설 → 처리 최적화 → 키 쏠림 확인
- 운영 기본: RF 3, min.insync 2, unclean 선출 off, 자동 토픽 생성 off
- 이벤트에 **eventId·type·version**, 큰 스키마 체계는 **Schema Registry**
- 관리형: MSK / Confluent, 직접: Strimzi
