# 01. Elasticsearch 개요와 역색인

> **학습 목표**
> - RDB `LIKE` 검색의 한계와 검색 엔진이 필요한 이유를 설명할 수 있다.
> - 역색인(Inverted Index)과 분석(Analyzer) 과정을 이해한다.
> - 인덱스·도큐먼트·매핑·샤드·레플리카 개념을 설명할 수 있다.
> - `text`와 `keyword` 타입의 차이를 알고 매핑을 설계할 수 있다.

---

## 1. 왜 검색 엔진인가?

```sql
SELECT * FROM product WHERE name LIKE '%무선 키보드%';
```
| 문제 | 설명 |
|---|---|
| **인덱스를 못 탐** | 앞에 `%`가 붙으면 B-Tree 인덱스 사용 불가 → 전체 스캔 |
| 형태소·동의어 무시 | "키보드"로 "키보드를", "keyboard"를 찾지 못함 |
| 관련도 순위 없음 | 일치하면 다 같은 결과, "얼마나 잘 맞는지" 정렬 불가 |
| 오타·부분 일치 | "키보트" 검색 불가 |

**Elasticsearch**: Apache Lucene 기반의 **분산 검색·분석 엔진**. JSON 도큐먼트를 저장하고 REST API로 검색합니다.
| 용도 | 예 |
|---|---|
| 전문 검색 (Full-text) | 상품·게시글 검색, 자동 완성 |
| 로그·메트릭 분석 | ELK/Elastic Stack (Logstash·Beats → ES → Kibana) |
| 집계 | 카테고리별 개수, 가격 분포 |
| 벡터 검색 | 임베딩 기반 의미 검색, RAG의 검색 단계 (dense_vector, kNN) |

### 라이선스와 OpenSearch
| 시기 | 변화 |
|---|---|
| 2021 | Elastic이 Apache 2.0 → SSPL/Elastic License로 변경 → AWS가 포크한 **OpenSearch** 등장 |
| 2024 | Elasticsearch에 **AGPLv3** 선택지 추가 |
> AWS의 관리형 서비스는 **Amazon OpenSearch Service**입니다. 기본 개념과 쿼리 DSL은 대부분 같습니다.

## 2. 역색인 (Inverted Index) ★

책 맨 뒤의 **"찾아보기(색인)"** 와 같습니다. 문서 → 단어가 아니라 **단어 → 문서 목록**을 저장합니다.
```
문서
 1: "무선 기계식 키보드"
 2: "유선 키보드"
 3: "무선 마우스"

역색인
 ┌──────────┬──────────┐
 │ 단어(term) │ 문서 ID   │
 ├──────────┼──────────┤
 │ 무선      │ 1, 3      │
 │ 기계식    │ 1         │
 │ 키보드    │ 1, 2      │
 │ 유선      │ 2         │
 │ 마우스    │ 3         │
 └──────────┴──────────┘

"무선 키보드" 검색 → 무선{1,3} ∪ 키보드{1,2} → 1(두 단어 모두 일치, 점수↑), 2, 3
```
- 단어로 바로 문서를 찾으므로 문서가 수억 건이어도 빠름
- 단어 빈도·문서 길이 등으로 **관련도 점수(BM25)** 계산 → 잘 맞는 문서부터

## 3. 분석 (Analysis): 텍스트 → 토큰

색인할 때와 검색할 때 **같은 분석기**로 텍스트를 토큰으로 나눕니다.
```
"The Quick 무선-키보드!"
   │ ① Character Filter : HTML 제거, 특수문자 치환
   │ ② Tokenizer        : 단어로 분리  → [The, Quick, 무선, 키보드]
   │ ③ Token Filter     : 소문자, 불용어 제거, 동의어, 형태소 → [quick, 무선, 키보드]
   ▼
 역색인에 저장
```
```http
POST _analyze
{
  "analyzer": "standard",
  "text": "The Quick 무선-키보드!"
}
```
> 한국어는 조사·어미가 붙어 공백 분리만으로는 부족합니다. **Nori 형태소 분석기**를 사용합니다. (`→ 02.검색쿼리와한글분석.md`)

## 4. 핵심 개념

| Elasticsearch | RDB 비유 | 설명 |
|---|---|---|
| **Index** | 테이블 | 도큐먼트 모음 |
| **Document** | 행 | JSON 객체, `_id` 로 식별 |
| Field | 컬럼 | |
| **Mapping** | 스키마 | 필드 타입·분석기 정의 |
| Query DSL | SQL | JSON 기반 검색 문법 |

### 클러스터 구조
```
 Cluster
 ├─ Node 1: [P0] [R1]
 ├─ Node 2: [P1] [R2]
 └─ Node 3: [P2] [R0]
 P = Primary Shard, R = Replica Shard (다른 노드에 복제)
```
| 개념 | 설명 |
|---|---|
| **Shard** | 인덱스를 나눈 단위 (Lucene 인덱스 하나), 여러 노드에 분산 → 수평 확장 |
| **Replica** | 샤드 복제본 → 장애 대비 + **검색 처리량 증가** |
| Primary 샤드 수 | 인덱스 생성 후 **변경 불가** (reindex 필요) → 샤드당 10~50GB 정도를 기준으로 설계 |
| 노드 역할 | master(클러스터 관리), data(저장·검색), ingest(전처리), coordinating(요청 분배) |

### 거의 실시간 (Near Real-Time)
- 색인된 문서는 **refresh(기본 1초)** 이후 검색 가능 → 저장 직후 검색하면 안 보일 수 있음
- 대량 색인 시 `refresh_interval: -1`로 끄고 끝난 후 다시 켜면 빠름

## 5. 매핑: text vs keyword ★

```http
PUT /products
{
  "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
  "mappings": {
    "properties": {
      "name":      { "type": "text", "analyzer": "standard",
                     "fields": { "raw": { "type": "keyword" } } },
      "brand":     { "type": "keyword" },
      "category":  { "type": "keyword" },
      "price":     { "type": "long" },
      "createdAt": { "type": "date" },
      "inStock":   { "type": "boolean" }
    }
  }
}
```
| 타입 | 분석 | 용도 | 검색 |
|---|---|---|---|
| **text** | ✅ 토큰으로 분리 | **전문 검색** (상품명, 본문) | `match` |
| **keyword** | ❌ 값 전체가 하나의 토큰 | **정확히 일치, 필터, 정렬, 집계** (브랜드, 상태, 태그) | `term` |
| long, double, date, boolean | | 범위·정렬 | `range` |
| `dense_vector` | | 임베딩 벡터 | `knn` |

- `fields`(multi-field): 같은 값을 `name`(text)과 `name.raw`(keyword) 두 가지로 색인
- **동적 매핑에 맡기지 말 것**: 문자열이 자동으로 text+keyword로 만들어져 공간 낭비, 숫자 문자열이 잘못 추론됨 → 매핑을 명시하고 `"dynamic": "strict"` 고려
- 기존 필드의 타입은 **변경 불가** → 새 인덱스 생성 후 `_reindex` + **별칭(alias)** 전환

## 6. 기본 API

```http
PUT /products/_doc/1
{ "name": "무선 기계식 키보드", "brand": "logi", "price": 89000, "inStock": true }
```
```http
GET /products/_search
{
  "query": { "match": { "name": "무선 키보드" } }
}
```
| 작업 | API |
|---|---|
| 생성·덮어쓰기 | `PUT /index/_doc/{id}` |
| 부분 수정 | `POST /index/_update/{id}` |
| 삭제 | `DELETE /index/_doc/{id}` |
| 대량 처리 | `POST /_bulk` (색인은 **반드시 벌크로**) |
| 검색 | `GET /index/_search` |

> 수정은 내부적으로 **삭제 표시 + 새 문서 색인**입니다. 자주 바뀌는 필드(재고 수량, 조회수)를 ES에 실시간 반영하면 부담이 큽니다.

## 7. RDB와 함께 쓰는 구조

```
 쓰기 ──▶ [MySQL (원본, 트랜잭션)] ──동기화──▶ [Elasticsearch (검색용 복제본)]
 검색 ──────────────────────────────────────▶ [Elasticsearch] → ID 목록 → (필요 시) DB 조회
```
- ES는 트랜잭션·조인이 약하고 결과적 일관성 → **원본은 RDB, ES는 검색용**
- 동기화 방식은 `→ 03.Spring연동과데이터동기화.md`

## 8. 면접 질문

1. **역색인이란?**
   → 문서별 단어 목록이 아니라 단어별로 그 단어가 포함된 문서 목록을 저장하는 구조로, 검색어의 토큰으로 바로 문서를 찾을 수 있어 대량 문서에서도 빠른 전문 검색이 가능합니다.
2. **`LIKE '%검색어%'` 대신 Elasticsearch를 쓰는 이유는?**
   → 앞에 와일드카드가 있는 LIKE는 인덱스를 쓰지 못해 전체 스캔하고, 형태소·동의어·오타를 처리하지 못하며 관련도 순 정렬이 불가능하기 때문입니다.
3. **text와 keyword의 차이는?**
   → text는 분석기로 토큰화되어 전문 검색에 쓰고, keyword는 값 전체를 하나로 저장해 정확한 일치 필터, 정렬, 집계에 사용합니다.
4. **샤드와 레플리카의 역할은?**
   → 샤드는 인덱스를 나누어 여러 노드에 분산 저장해 수평 확장을 가능하게 하고, 레플리카는 샤드의 복제본으로 장애에 대비하고 검색 처리량을 높입니다. 프라이머리 샤드 수는 생성 후 바꿀 수 없습니다.

## 핵심 정리
- 검색 엔진 = **역색인(단어 → 문서) + 분석기 + 관련도 점수(BM25)**
- 분석: Character Filter → **Tokenizer** → Token Filter, 한글은 **Nori**
- Index·Document·**Mapping**, Shard(확장)·Replica(장애·처리량), refresh 1초 (NRT)
- **text(전문 검색) vs keyword(필터·정렬·집계)**, 매핑은 명시적으로
- 원본은 RDB, ES는 **검색용 복제본**
