> - RDB와 Elasticsearch의 데이터 동기화 방식(동기 이중 쓰기, 이벤트, CDC, 배치)을 비교할 수 있다.

## 1. 의존성과 설정

```groovy
implementation 'org.springframework.boot:spring-boot-starter-data-elasticsearch'
```
```yaml
spring:
  elasticsearch:
    uris: http://localhost:9200
    username: elastic
    password: ${ES_PASSWORD}
    connection-timeout: 2s
    socket-timeout: 5s
```
- Spring Data Elasticsearch 5.x 이상은 공식 **Elasticsearch Java API Client**(`co.elastic.clients`) 기반입니다. 예전 `RestHighLevelClient` 예제는 deprecated·제거된 API입니다.

## 2. 도큐먼트 매핑

```java
@Document(indexName = "products")
@Setting(settingPath = "elasticsearch/product-settings.json")      // Nori 분석기 설정 (→ 02 문서)
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class ProductDocument {

    @Id
    private Long id;

    @MultiField(
            mainField = @Field(type = FieldType.Text, analyzer = "korean_index", searchAnalyzer = "korean_search"),
            otherFields = @InnerField(suffix = "raw", type = FieldType.Keyword))
    private String name;

    @Field(type = FieldType.Keyword)
    private String brand;

    @Field(type = FieldType.Keyword)
    private String category;

    @Field(type = FieldType.Long)
    private long price;

    @Field(type = FieldType.Boolean)
    private boolean inStock;

    @Field(type = FieldType.Date, format = DateFormat.date_hour_minute_second_millis)
    private LocalDateTime createdAt;

    public static ProductDocument from(Product p) { ... }      // 엔티티 → 검색용 도큐먼트 변환
}
```
> **JPA 엔티티와 도큐먼트는 분리**합니다. 검색에 필요한 필드만, 검색에 좋은 형태(카테고리 이름 비정규화 등)로 만듭니다.

## 3. Repository와 쿼리

```java
public interface ProductSearchRepository extends ElasticsearchRepository<ProductDocument, Long> {

    List<ProductDocument> findByBrand(String brand);                      // 메서드 이름 쿼리

    Page<ProductDocument> findByNameAndInStockTrue(String name, Pageable pageable);
}
```
### 복잡한 검색: NativeQuery (Java API Client의 Query DSL)
```java
@Repository
@RequiredArgsConstructor
public class ProductSearchQueryRepository {

    private final ElasticsearchOperations operations;

    public SearchHits<ProductDocument> search(ProductSearchCondition cond, Pageable pageable) {
        NativeQuery query = NativeQuery.builder()
                .withQuery(q -> q.bool(b -> {
                    if (StringUtils.hasText(cond.keyword())) {
                        b.must(m -> m.multiMatch(mm -> mm
                                .query(cond.keyword())
                                .fields("name^3", "brand^2")));
                    }
                    if (cond.category() != null) {
                        b.filter(f -> f.term(t -> t.field("category").value(cond.category())));
                    }
                    if (cond.maxPrice() != null) {
                        b.filter(f -> f.range(r -> r.number(n -> n.field("price").lte(cond.maxPrice().doubleValue()))));
                    }
                    b.filter(f -> f.term(t -> t.field("inStock").value(true)));
                    return b;
                }))
                .withPageable(pageable)
                .withSort(s -> s.score(sc -> sc.order(SortOrder.Desc)))
                .withSort(s -> s.field(fs -> fs.field("id").order(SortOrder.Asc)))
                .build();

        return operations.search(query, ProductDocument.class);
    }
}
```
```java
SearchHits<ProductDocument> hits = repository.search(cond, PageRequest.of(0, 20));
hits.getTotalHits();
hits.getSearchHits().forEach(h -> log.info("{} score={}", h.getContent().getName(), h.getScore()));
```
> Java API Client의 range 쿼리 빌더는 클라이언트 8.15부터 `number()`, `date()`, `term()` 같은 타입별 빌더로 바뀌었습니다. 오래된 예제의 `r.field("price").lte(JsonData.of(...))` 형태가 컴파일되지 않으면 이 부분을 확인하세요.

## 4. 데이터 동기화 ★

원본은 RDB, 검색은 ES → **두 저장소를 어떻게 맞출까?**

| 방식 | 구조 | 장점 | 단점 |
|---|---|---|---|
| **동기 이중 쓰기** | 서비스에서 DB 저장 후 ES 저장 | 단순, 즉시 반영 | ES 장애 = 서비스 장애, **트랜잭션 불일치** (DB 롤백·ES 성공 등) |
| **이벤트 (AFTER_COMMIT)** | 커밋 후 이벤트 → 비동기 색인 | 서비스와 분리 | 서버 다운 시 이벤트 유실 |
| **Outbox + Kafka** | outbox → Kafka → 색인 컨슈머 | **유실 없음**, 재처리 가능, 여러 소비자 | 구성 복잡 |
| **CDC** (Debezium) | DB binlog → Kafka → 색인 | 애플리케이션 코드 변경 없음, 누락 없음 | 인프라 운영 부담, 테이블 구조 그대로 → 변환 필요 |
| **배치** | 주기적으로 변경분(`updated_at > 마지막 실행`) 색인 | 단순, 대량 효율적 | 지연(분~시간), 삭제 감지 어려움 |

### 실무 조합 예
```
실시간성 필요: 상품 등록·수정 → Outbox → Kafka "product-changed" → [색인 컨슈머] → ES upsert
안전망      : 매일 새벽 배치로 전체(또는 변경분) 재색인 → 누락·불일치 보정
```
```java
@Component
@RequiredArgsConstructor
public class ProductIndexConsumer {

    private final ProductRepository productRepository;
    private final ProductSearchRepository searchRepository;

    @KafkaListener(topics = "product-changed", groupId = "product-indexer")
    public void onChanged(ProductChangedEvent event) {
        productRepository.findById(event.productId())                     // 이벤트 내용이 아니라 DB 최신 상태로
                .map(ProductDocument::from)
                .ifPresentOrElse(searchRepository::save,                  // upsert (같은 ID 덮어쓰기 → 멱등)
                        () -> searchRepository.deleteById(event.productId()));
    }
}
```
- **ID 기준 덮어쓰기(upsert)는 멱등** → 중복 이벤트에 안전
- 이벤트 payload 대신 **DB에서 최신 상태를 다시 읽으면** 순서가 바뀌어 도착해도 최종 상태가 맞음
- 이벤트 흐름과 Outbox는 `→ 02.Kafka/03.전달보장과순서.md`

## 5. 무중단 재색인 (별칭 전환)

매핑 변경(필드 타입, 분석기 변경)은 기존 인덱스에서 불가 → **새 인덱스를 만들어 다시 색인**
```
1. products_v2 인덱스 생성 (새 매핑)
2. 데이터 색인: _reindex API 또는 DB에서 배치로 bulk 색인
   (그동안 들어온 변경은 v1·v2 양쪽에 쓰거나, 완료 후 변경분 재적용)
3. 별칭 전환 (원자적)
4. 확인 후 products_v1 삭제
```
```http
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products_v1", "alias": "products" } },
    { "add":    { "index": "products_v2", "alias": "products" } }
  ]
}
```
> 애플리케이션은 항상 **별칭(`products`)** 으로 접근하게 해 두면, 인덱스 교체 시 코드 변경·다운타임이 없습니다.

### 대량 색인 팁
- `_bulk`로 1,000~5,000건씩 (5~15MB 정도)
- 색인 중 `refresh_interval: -1`, `number_of_replicas: 0` → 끝나고 원래대로
- DB 조회는 커서(키셋) 페이징으로 (`→ Spring JPA 스터디 자료의 03.JPA실전/02.SpringDataJPA.md`)

## 6. 운영 주의점

| 항목 | 내용 |
|---|---|
| 샤드 크기 | 샤드당 10~50GB, 너무 작은 샤드가 많으면(oversharding) 오버헤드 |
| JVM 힙 | 물리 메모리의 50% 이하 (나머지는 Lucene이 쓰는 OS 파일 캐시) |
| 클러스터 상태 | `GET _cluster/health` → green(정상) / yellow(레플리카 미할당) / red(프라이머리 미할당) |
| 느린 쿼리 | slow log, `"profile": true` |
| 비싼 쿼리 피하기 | 앞쪽 와일드카드(`*키보드`), 큰 `from`, 스크립트 정렬 |
| 보안 | 인증·TLS, 외부 노출 금지 |
| 로그 용도 | 날짜별 인덱스 + **ILM**(Index Lifecycle Management)로 hot → warm → 삭제 |

## 7. 면접 질문

1. **DB와 Elasticsearch 데이터는 어떻게 동기화하나요?**
   → 원본은 DB에 두고, 변경 시 Outbox와 Kafka로 이벤트를 발행해 색인 컨슈머가 DB의 최신 상태를 읽어 ID 기준으로 upsert 하며, 정기 배치 재색인으로 누락을 보정합니다. 규모가 크면 CDC를 고려합니다.
2. **동기 이중 쓰기의 문제는?**
   → ES 장애나 지연이 서비스 장애로 번지고, DB 롤백과 ES 저장 성공처럼 두 저장소가 불일치할 수 있습니다.
3. **매핑을 바꿔야 할 때 무중단으로 하는 방법은?**
   → 새 매핑으로 새 인덱스를 만들어 재색인한 뒤, 애플리케이션이 사용하는 별칭을 원자적으로 새 인덱스로 전환하고 이전 인덱스를 삭제합니다.

## 핵심 정리
- Spring Data Elasticsearch (Java API Client 기반), **엔티티와 도큐먼트 분리**
- 복잡한 검색은 `NativeQuery` + bool(must/filter)
- 동기화: **Outbox/Kafka 또는 CDC + upsert(멱등) + 정기 재색인**, 동기 이중 쓰기 지양
- 매핑 변경 = **새 인덱스 + 재색인 + 별칭 전환**
- 운영: 샤드 크기, 힙 50%, cluster health, ILM
