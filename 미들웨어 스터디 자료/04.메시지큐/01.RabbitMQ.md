# 01. RabbitMQ

> **학습 목표**
> - 메시지 큐를 쓰는 이유와 AMQP 모델(Exchange, Queue, Binding)을 설명할 수 있다.
> - Exchange 타입(direct, topic, fanout)별 라우팅을 이해한다.
> - ack, prefetch, DLX, 재시도로 메시지를 안전하게 처리할 수 있다.
> - Kafka와 RabbitMQ 중 상황에 맞게 선택할 수 있다.

---

## 1. 메시지 큐를 쓰는 이유

```
동기 호출                                   메시지 큐
[주문] ──HTTP──▶ [메일] (3초)               [주문] ──▶ [Queue] ──▶ [메일 워커]
 → 메일 서버가 느리면 주문도 느려짐           → 주문은 큐에 넣고 바로 응답
 → 메일 서버 장애 = 주문 실패                 → 메일 서버 장애 시 큐에 쌓였다가 복구 후 처리
```
| 효과 | 설명 |
|---|---|
| **비동기 처리** | 오래 걸리는 작업(메일, 이미지 변환, PDF 생성)을 분리 → 응답 속도 ↑ |
| **완충 (버퍼)** | 트래픽 폭주를 큐가 흡수, 워커는 일정한 속도로 처리 |
| 장애 격리 | 소비자 장애가 생산자에 전파되지 않음 |
| 수평 확장 | 워커만 늘리면 처리량 증가 (경쟁 소비자 패턴) |

## 2. AMQP 모델

```
 Producer ──▶ [Exchange] ──(Binding: routing key 규칙)──▶ [Queue] ──▶ Consumer
                  │
                  └──────────────────────────────▶ [Queue] ──▶ Consumer
```
| 구성 요소 | 역할 |
|---|---|
| **Exchange** | 메시지를 받아 **어느 큐로 보낼지 결정** (우체국) |
| **Queue** | 메시지를 저장하고 소비자에게 전달 |
| **Binding** | Exchange와 Queue를 연결하는 규칙 (routing key, 패턴) |
| Routing Key | 메시지에 붙이는 주소 |
| Virtual Host | 논리적 분리 (환경·서비스별) |
> 프로듀서는 큐를 직접 모르고 **Exchange에만** 보냅니다 → 라우팅을 유연하게 바꿀 수 있습니다.

### Exchange 타입
| 타입 | 라우팅 | 예 |
|---|---|---|
| **direct** | routing key가 **정확히 일치**하는 큐 | `email`, `sms` 별 큐 |
| **topic** | **패턴** 일치 (`*` 한 단어, `#` 0개 이상) | `order.created.kr` → `order.*.kr`, `order.#` |
| **fanout** | 바인딩된 **모든 큐**에 복사 (routing key 무시) | 주문 완료 → 메일·포인트·통계 큐 모두 |
| headers | 헤더 값으로 | 드물게 사용 |

```
topic exchange "order"
  order.created.kr  ──▶ [kr-order-queue]   (binding: order.*.kr)
                    └─▶ [audit-queue]      (binding: order.#)
  order.canceled.us ──▶ [audit-queue]
```

## 3. 안전한 메시지 처리

### ① 메시지 확인 (ack)
| 모드 | 동작 |
|---|---|
| auto ack | 전달하는 순간 삭제 → 처리 중 죽으면 **유실** |
| **manual ack** | 처리 완료 후 `ack` → 그때 삭제. 컨슈머가 죽으면 **다른 컨슈머에게 재전달** |
| `nack` / `reject` | 처리 실패 → 재큐잉(`requeue=true`) 또는 DLX로 |
> Spring AMQP의 기본 `AcknowledgeMode.AUTO`는 "리스너가 **정상 종료하면 ack, 예외면 nack**"을 스프링이 대신 해 주는 방식이라 RabbitMQ의 auto ack와 다릅니다.

### ② prefetch (QoS)
```
prefetch = 한 컨슈머가 ack 없이 동시에 받을 수 있는 메시지 수
너무 크면: 한 컨슈머가 메시지를 쌓아 두고 다른 컨슈머는 놀고, 죽으면 많은 메시지가 재전달
너무 작으면: 왕복 대기로 처리량 ↓
→ Spring AMQP 기본 250, 처리 시간이 긴 작업은 1~10
```

### ③ 내구성
- Exchange·Queue를 **durable**로 선언, 메시지는 **persistent**(delivery mode 2)
- 프로듀서 **Publisher Confirms**: 브로커가 메시지 저장을 확인해 주면 성공 처리
- 라우팅할 큐가 없으면 버려짐 → `mandatory` + Returns 콜백으로 감지

### ④ DLX (Dead Letter Exchange)
```
 [work-queue] ── 거부(requeue=false) / TTL 만료 / 큐 길이 초과 ──▶ [DLX] ──▶ [work-queue.dlq]
```
- **requeue=true로 무한 재시도 금지** → 실패 메시지가 큐 앞에서 계속 돌며 다른 메시지를 막음(Poison message)
- 재시도는 **횟수 제한 + 지연** → 초과 시 DLQ로 보내고 알림

### ⑤ 큐 타입 (RabbitMQ 4.x)
| 큐 | 특징 |
|---|---|
| Classic | 단일 노드, 가볍고 빠름 |
| **Quorum** | **Raft 기반 복제** → 고가용성·데이터 안전 (권장), 재전달 횟수 제한 내장 |
| Stream | Kafka처럼 로그 보관·재소비 |
> RabbitMQ 4.0(2024)에서 예전 고가용성 방식인 **classic mirrored queue가 제거**되었습니다. 복제가 필요하면 Quorum Queue를 사용합니다.

## 4. Spring AMQP

```groovy
implementation 'org.springframework.boot:spring-boot-starter-amqp'
```
```yaml
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: shop
    password: ${RABBITMQ_PASSWORD}
    publisher-confirm-type: correlated
    publisher-returns: true
    listener:
      simple:
        prefetch: 10
        concurrency: 3
        max-concurrency: 10
        retry:
          enabled: true          # 리스너 재시도 (스프링 내부)
          max-attempts: 3
          initial-interval: 1s
          multiplier: 2
        default-requeue-rejected: false   # 재시도 소진 후 재큐잉 X → DLX로
```
```java
@Configuration
public class RabbitConfig {

    public static final String EXCHANGE = "notification.exchange";
    public static final String QUEUE = "notification.email";
    public static final String DLX = "notification.dlx";
    public static final String DLQ = "notification.email.dlq";

    @Bean TopicExchange notificationExchange() { return new TopicExchange(EXCHANGE); }
    @Bean DirectExchange deadLetterExchange() { return new DirectExchange(DLX); }

    @Bean
    Queue emailQueue() {
        return QueueBuilder.durable(QUEUE)
                .quorum()
                .deadLetterExchange(DLX)
                .deadLetterRoutingKey(DLQ)
                .build();
    }

    @Bean Queue emailDlq() { return QueueBuilder.durable(DLQ).build(); }

    @Bean
    Binding emailBinding() {
        return BindingBuilder.bind(emailQueue()).to(notificationExchange()).with("notification.email.#");
    }

    @Bean
    Binding dlqBinding() {
        return BindingBuilder.bind(emailDlq()).to(deadLetterExchange()).with(DLQ);
    }

    @Bean
    MessageConverter messageConverter() {
        return new JacksonJsonMessageConverter();    // Boot 3 / Spring AMQP 3.x: Jackson2JsonMessageConverter
    }
}
```
```java
// 발행
rabbitTemplate.convertAndSend(RabbitConfig.EXCHANGE, "notification.email.welcome",
        new EmailMessage(memberId, "가입을 환영합니다"));

// 소비
@RabbitListener(queues = RabbitConfig.QUEUE)
public void sendEmail(EmailMessage message) {
    emailSender.send(message);       // 예외 → 재시도 3회 → 실패 시 DLQ (멱등하게 구현)
}
```
> Spring AMQP 4(Boot 4)에서는 Jackson 3 기반 `JacksonJsonMessageConverter`가 추가되고 Jackson 2 기반 컨버터는 deprecated입니다. 사용하는 버전의 클래스 이름을 확인하세요.

### 지연 메시지
- TTL + DLX 조합 (메시지가 대기 큐에서 만료되면 작업 큐로 이동)
- 또는 `rabbitmq-delayed-message-exchange` 플러그인

## 5. Kafka vs RabbitMQ

| 비교 | Kafka | RabbitMQ |
|---|---|---|
| 모델 | **분산 로그**, 컨슈머가 pull | **메시지 브로커**, 브로커가 push |
| 메시지 보관 | 보존 기간 동안 **유지** (재처리 가능) | ack 후 **삭제** |
| 처리량 | **매우 높음** (초당 수십만~) | 높음 (초당 수만) |
| 라우팅 | 토픽·파티션 (단순) | **Exchange로 유연한 라우팅** |
| 순서 | 파티션 단위 보장 | 큐 단위 (경쟁 소비자면 깨짐) |
| 소비자 확장 | 파티션 수가 한계 | 큐에 컨슈머 추가하면 끝 |
| 메시지별 처리 | 오프셋 단위 (개별 ack 개념 약함) | **메시지별 ack·재전달·우선순위·TTL** |
| 적합 | 이벤트 스트리밍, 로그·데이터 파이프라인, 여러 서비스가 같은 이벤트 소비, 재처리 | **작업 큐**(메일, 이미지 처리), 복잡한 라우팅, RPC, 낮은 지연 |

## 6. 면접 질문

1. **메시지 큐를 사용하는 이유는?**
   → 오래 걸리는 작업을 비동기로 분리해 응답 속도를 높이고, 트래픽을 완충하며, 생산자와 소비자의 장애를 격리하고 워커를 늘려 수평 확장할 수 있기 때문입니다.
2. **RabbitMQ의 Exchange 타입을 설명해 주세요.**
   → direct는 라우팅 키가 정확히 일치하는 큐로, topic은 패턴이 일치하는 큐로, fanout은 바인딩된 모든 큐로 메시지를 보냅니다.
3. **메시지 유실을 막으려면?**
   → durable 큐와 persistent 메시지, Publisher Confirms로 발행을 확인하고, 컨슈머는 처리 후 ack 하며, 실패 메시지는 재시도 후 DLX로 보내고, 복제가 필요하면 Quorum 큐를 사용합니다.
4. **Kafka와 RabbitMQ는 언제 각각 쓰나요?**
   → 대용량 이벤트 스트리밍, 여러 서비스의 독립 소비, 재처리가 필요하면 Kafka를, 메시지별 확인·재시도·라우팅이 중요한 작업 큐에는 RabbitMQ를 선택합니다.

## 핵심 정리
- AMQP: Producer → **Exchange**(direct/topic/fanout) → Binding → **Queue** → Consumer
- 안전: **manual ack(스프링 AUTO) + prefetch + durable/persistent + Publisher Confirms**
- 실패: **재시도 횟수 제한 → DLX/DLQ**, requeue 무한 루프 금지
- RabbitMQ 4: mirrored queue 제거 → **Quorum Queue**
- Kafka = 로그·스트림·재처리 / RabbitMQ = 작업 큐·라우팅
