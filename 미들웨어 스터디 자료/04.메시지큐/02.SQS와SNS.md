# 02. AWS SQS와 SNS

> **학습 목표**
> - SQS(큐)와 SNS(발행·구독)의 차이를 설명할 수 있다.
> - SQS의 가시성 타임아웃, 롱 폴링, DLQ, Standard/FIFO 차이를 이해한다.
> - SNS + SQS 팬아웃 구조를 설계할 수 있다.
> - Spring Cloud AWS로 SQS 메시지를 주고받을 수 있다.

---

## 1. SQS와 SNS

| | **SQS** (Simple Queue Service) | **SNS** (Simple Notification Service) |
|---|---|---|
| 모델 | **큐** (1:1, 한 메시지를 한 소비자가) | **Pub/Sub** (1:N, 모든 구독자에게 복사) |
| 소비 방식 | 소비자가 **Polling** | SNS가 구독자에게 **Push** |
| 저장 | 최대 14일 보관 (기본 4일) | 저장 X (전달 실패 시 재시도 후 DLQ) |
| 구독자 | – | SQS, Lambda, HTTP, 이메일, SMS, 모바일 푸시 |
| 비유 | RabbitMQ의 Queue | RabbitMQ의 fanout Exchange |

> 완전 관리형이라 **브로커 운영(서버, 디스크, 복제)이 필요 없습니다.** 메시지량이 많지 않은 AWS 기반 서비스에서는 Kafka·RabbitMQ보다 운영 비용이 훨씬 낮습니다.

## 2. SQS 동작 원리

```
 Producer ──SendMessage──▶ [SQS Queue] ◀──ReceiveMessage(Polling)── Consumer
                                │                                   │ 처리 완료
                                │ ◀────────DeleteMessage────────────┘
```
### 가시성 타임아웃 (Visibility Timeout) ★
```
1. Consumer A가 메시지를 받음 → 메시지가 다른 소비자에게 "안 보이게" 됨 (기본 30초)
2-a. A가 처리 후 DeleteMessage → 삭제 완료
2-b. A가 시간 안에 삭제하지 못함 (처리 지연·장애) → 다시 보이게 됨 → B가 받음 (중복 처리!)
```
- 가시성 타임아웃 > **최대 처리 시간** 으로 설정 (처리 시간이 길면 `ChangeMessageVisibility`로 연장)
- 그래도 at-least-once → **멱등 처리 필수**

### 롱 폴링 (Long Polling)
- `WaitTimeSeconds=20`: 메시지가 없으면 최대 20초 기다렸다가 응답 → **빈 응답·요청 비용 감소**
- 숏 폴링(0초)은 빈 요청이 많아 비용 낭비

### DLQ (Dead Letter Queue)
```
Redrive Policy: maxReceiveCount = 5
→ 같은 메시지를 5번 받았는데도 삭제되지 않으면 DLQ로 이동
```
DLQ에 쌓이면 CloudWatch 알람, 원인 해결 후 **DLQ Redrive**로 원래 큐에 되돌림

### Standard vs FIFO
| | Standard | **FIFO** (`.fifo`) |
|---|---|---|
| 처리량 | 거의 무제한 | 높은 처리량 모드에서 초당 수천~수만 건 (일반 모드 300 TPS, 배치 시 3,000) |
| 순서 | **보장 안 함** (최선) | **MessageGroupId 단위로 보장** |
| 중복 | 가끔 **중복 전달** | **5분간 중복 제거** (MessageDeduplicationId 또는 내용 기반) |
| 적합 | 대부분의 비동기 작업 | 주문 상태 변경처럼 **순서·중복이 중요한** 작업 |
> FIFO의 `MessageGroupId`는 Kafka의 **파티션 키**와 비슷합니다. 같은 그룹은 순서대로, 다른 그룹은 병렬로 처리됩니다.

## 3. SNS + SQS 팬아웃 ★

```
                         ┌──▶ [SQS: payment-queue] ──▶ 결제 서비스
 [주문 서비스] ──▶ [SNS: order-created] ──┼──▶ [SQS: notification-queue] ──▶ 알림 서비스
                         └──▶ [SQS: analytics-queue] ──▶ 통계 (Lambda)
```
| 장점 | 설명 |
|---|---|
| 생산자는 SNS 토픽 하나만 알면 됨 | 소비 서비스 추가 = 구독 추가 |
| 각 소비자는 **자기 큐**를 가짐 | 처리 속도·장애가 서로 영향 없음, 각자 DLQ |
| 내구성 | SNS는 저장하지 않지만 SQS가 보관 |
| **메시지 필터링** | 구독별 필터 정책 (`{"eventType": ["ORDER_CANCELED"]}`) → 필요한 이벤트만 |

> 순서·중복 제거가 필요하면 **SNS FIFO 토픽 → SQS FIFO 큐** 조합을 사용합니다. AWS의 이벤트 라우팅 서비스로는 규칙 기반 라우팅이 풍부한 **EventBridge**도 있습니다.

## 4. Spring Cloud AWS

```groovy
implementation platform('io.awspring.cloud:spring-cloud-aws-dependencies:<버전>')
implementation 'io.awspring.cloud:spring-cloud-aws-starter-sqs'
implementation 'io.awspring.cloud:spring-cloud-aws-starter-sns'
```
> Spring Cloud AWS 3.x는 Boot 3 기준입니다. Boot 4에서 쓸 때는 프로젝트의 호환표에서 지원 버전을 먼저 확인하세요.

```yaml
spring:
  cloud:
    aws:
      region:
        static: ap-northeast-2
      # 자격 증명은 코드·설정에 쓰지 말고 IAM Role(EC2·ECS·EKS IRSA/Pod Identity) 사용
```
```java
// 발행
@Component
@RequiredArgsConstructor
public class NotificationPublisher {
    private final SqsTemplate sqsTemplate;

    public void publish(EmailMessage message) {
        sqsTemplate.send(to -> to.queue("notification-queue").payload(message));
    }
}

// 소비
@Component
public class NotificationListener {

    @SqsListener(value = "notification-queue", maxConcurrentMessages = "10", maxMessagesPerPoll = "10")
    public void handle(EmailMessage message) {
        emailSender.send(message);      // 정상 종료 → 메시지 자동 삭제(ack), 예외 → 삭제 안 함 → 가시성 타임아웃 후 재전달 → DLQ
    }
}
```
| 설정 | 의미 |
|---|---|
| `maxConcurrentMessages` | 동시에 처리할 메시지 수 |
| `maxMessagesPerPoll` | 한 번에 가져올 메시지 수 (최대 10) |
| `acknowledgementMode` | `ON_SUCCESS`(기본) / `ALWAYS` / `MANUAL` |
| 메시지 크기 | 최대 256KB (SQS 기본) → 큰 데이터는 S3에 두고 키만 전송 |

## 5. 선택 가이드

| 상황 | 추천 |
|---|---|
| AWS 기반, 단순 비동기 작업 (메일, 이미지, 정산 요청) | **SQS** |
| 한 이벤트를 여러 서비스가 소비 | **SNS + SQS 팬아웃** (또는 EventBridge) |
| 순서·중복 제거 중요 | SQS FIFO (+ SNS FIFO) |
| 대용량 이벤트 스트림, 재처리, 스트림 처리 | **Kafka (MSK)** |
| 복잡한 라우팅, 메시지 우선순위, 온프레미스 | **RabbitMQ** (Amazon MQ) |

## 6. 면접 질문

1. **SQS와 SNS의 차이는?**
   → SQS는 메시지를 저장하고 소비자가 폴링해 한 소비자가 처리하는 큐이고, SNS는 메시지를 저장하지 않고 모든 구독자에게 푸시하는 발행·구독 서비스입니다.
2. **가시성 타임아웃이란?**
   → 소비자가 메시지를 받은 뒤 다른 소비자에게 보이지 않는 시간으로, 이 시간 안에 삭제하지 않으면 다시 보이게 되어 재처리됩니다. 처리 시간보다 길게 설정하고 멱등하게 처리해야 합니다.
3. **SNS + SQS 팬아웃 구조의 장점은?**
   → 생산자는 토픽에만 발행하고 각 소비 서비스가 자기 큐를 가지므로 서비스 추가가 쉽고, 소비자별 처리 속도와 장애가 격리되며 각자 DLQ와 재시도를 가질 수 있습니다.
4. **Standard 큐와 FIFO 큐의 차이는?**
   → Standard는 처리량이 거의 무제한이지만 순서를 보장하지 않고 중복 전달이 있을 수 있으며, FIFO는 메시지 그룹 단위로 순서를 보장하고 일정 시간 중복을 제거하지만 처리량 제한이 있습니다.

## 핵심 정리
- **SQS = 큐(폴링, 1:1, 최대 14일)**, **SNS = Pub/Sub(푸시, 1:N)**
- SQS 핵심: **가시성 타임아웃 > 처리 시간**, **롱 폴링 20초**, maxReceiveCount → **DLQ**
- Standard(무제한, 순서 X, 중복 가능) vs **FIFO(그룹별 순서, 중복 제거)**
- **SNS → SQS 팬아웃** + 필터 정책
- Spring Cloud AWS `SqsTemplate` / `@SqsListener`, 자격 증명은 **IAM Role**
