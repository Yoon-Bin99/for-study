# 01. Spring Batch

> **학습 목표**
> - 배치 처리가 필요한 상황과 Spring Batch의 구조(Job, Step, Chunk)를 설명할 수 있다.
> - Reader·Processor·Writer로 청크 지향 Step을 구현할 수 있다.
> - JobParameters, 재시작, skip·retry로 안정적인 배치를 만들 수 있다.
> - 대용량 처리 성능(페이징 Reader, 커서, 병렬화)과 Spring Batch 5 → 6의 변화를 안다.

---

## 1. 배치 처리란?

**대량의 데이터를 정해진 시점에 일괄 처리**하는 작업입니다. 사용자 요청과 분리된 백그라운드 작업이죠.
| 예 | 설명 |
|---|---|
| 정산 | 전날 주문을 판매자별로 집계해 정산 데이터 생성 |
| 통계 | 일별 매출·방문자 통계 테이블 생성 |
| 데이터 정리 | 1년 지난 로그 삭제, 휴면 회원 전환 |
| 대량 발송 | 쿠폰 만료 안내 메일 |
| 데이터 이관 | 외부 파일(CSV) → DB, DB → 검색 엔진 재색인 |

### 왜 그냥 `@Scheduled` + for문이 아니라 Spring Batch?
| 직접 구현 시 문제 | Spring Batch가 제공 |
|---|---|
| 100만 건을 한 트랜잭션으로 → 메모리 부족, 실패 시 전부 롤백 | **청크 단위 커밋** (1,000건씩) |
| 50만 번째에서 실패 → 처음부터 다시? | **실패 지점부터 재시작** (메타데이터에 진행 상황 기록) |
| 잘못된 데이터 한 건 때문에 전체 실패 | **skip / retry** 정책 |
| 같은 날짜 배치를 두 번 실행 | JobParameters로 **중복 실행 방지** |
| 실행 이력·소요 시간 | 메타데이터 테이블(`BATCH_JOB_EXECUTION` 등) |

## 2. 구조

```
 Job (일별 정산)
  ├─ Step 1: 주문 집계 (Chunk)
  │     ItemReader ──▶ ItemProcessor ──▶ ItemWriter
  │      (읽기)          (가공·필터)        (쓰기)
  ├─ Step 2: 정산 파일 생성 (Chunk)
  └─ Step 3: 완료 알림 (Tasklet)

 JobRepository: 실행 상태·진행 위치 저장
 JobOperator (Batch 6) / JobLauncher (Batch 5): Job 실행
```
| 개념 | 설명 |
|---|---|
| **Job** | 배치 작업 전체 (Step들의 흐름) |
| **Step** | 독립적인 처리 단계 |
| **JobInstance** | Job + **JobParameters** 의 논리적 실행 단위 (예: 정산 Job + date=2026-11-09) |
| **JobExecution** | JobInstance의 실제 실행 시도 (실패 후 재실행하면 Execution이 하나 더) |
| ExecutionContext | 재시작에 필요한 상태 저장 (몇 번째까지 읽었는지) |

### Chunk 처리 흐름
```
chunk size = 1000
반복 {
   read() × 1000  → process() × 1000  → write(1000건 묶음)  → 커밋
}
실패하면 해당 청크만 롤백, 이전 청크는 이미 커밋됨 → 재시작 시 다음 청크부터
```
| Step 종류 | 용도 |
|---|---|
| **Chunk 지향** | 대량 데이터 읽기·가공·쓰기 |
| **Tasklet** | 단순 작업 하나 (파일 삭제, 프로시저 호출, 알림) |

## 3. 예제: 휴면 회원 전환 (Batch 5 API, Boot 3)

```java
@Configuration
@RequiredArgsConstructor
public class DormantMemberJobConfig {

    private static final int CHUNK_SIZE = 1000;
    private final EntityManagerFactory emf;

    @Bean
    public Job dormantMemberJob(JobRepository jobRepository, Step dormantMemberStep) {
        return new JobBuilder("dormantMemberJob", jobRepository)
                .start(dormantMemberStep)
                .build();
    }

    @Bean
    public Step dormantMemberStep(JobRepository jobRepository, PlatformTransactionManager tx) {
        return new StepBuilder("dormantMemberStep", jobRepository)
                .<Member, Member>chunk(CHUNK_SIZE, tx)
                .reader(dormantCandidateReader(null))
                .processor(dormantProcessor())
                .writer(memberWriter())
                .faultTolerant()
                .skip(InvalidMemberException.class).skipLimit(100)          // 잘못된 데이터 100건까지 건너뜀
                .retry(TransientDataAccessException.class).retryLimit(3)    // 일시 오류 재시도
                .build();
    }

    @Bean
    @StepScope                                                    // JobParameters를 실행 시점에 주입
    public JpaPagingItemReader<Member> dormantCandidateReader(
            @Value("#{jobParameters['baseDate']}") LocalDate baseDate) {
        return new JpaPagingItemReaderBuilder<Member>()
                .name("dormantCandidateReader")
                .entityManagerFactory(emf)
                .pageSize(CHUNK_SIZE)
                .queryString("""
                        select m from Member m
                        where m.lastLoginAt < :threshold and m.status = 'ACTIVE'
                        order by m.id
                        """)
                .parameterValues(Map.of("threshold", baseDate.minusYears(1).atStartOfDay()))
                .build();
    }

    @Bean
    public ItemProcessor<Member, Member> dormantProcessor() {
        return member -> {
            if (member.isExcludedFromDormancy()) return null;    // null 반환 = 필터링 (쓰지 않음)
            member.toDormant();
            return member;
        };
    }

    @Bean
    public JpaItemWriter<Member> memberWriter() {
        return new JpaItemWriterBuilder<Member>().entityManagerFactory(emf).build();
    }
}
```
```bash
java -jar batch.jar --spring.batch.job.name=dormantMemberJob baseDate=2026-11-09
```

### Spring Batch 6 (Boot 4)에서 달라진 점
```java
@Bean
public Step dormantMemberStep(JobRepository jobRepository,
                              ItemReader<Member> reader, ItemProcessor<Member, Member> processor,
                              ItemWriter<Member> writer) {
    RetryPolicy retryPolicy = RetryPolicy.builder()                    // Spring Framework 7 core retry
            .maxRetries(3)
            .includes(Set.of(TransientDataAccessException.class))
            .build();
    SkipPolicy skipPolicy = new LimitCheckingExceptionHierarchySkipPolicy(
            Set.of(InvalidMemberException.class), 100);

    return new ChunkOrientedStepBuilder<Member, Member>("dormantMemberStep", jobRepository, 1000)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .faultTolerant()
            .retryPolicy(retryPolicy)
            .skipPolicy(skipPolicy)
            .build();
}
```
| 항목 | Batch 5 (Boot 3) | **Batch 6 (Boot 4)** |
|---|---|---|
| 청크 Step | `StepBuilder.chunk(size, tx)` (TaskletStep 기반) | **`ChunkOrientedStepBuilder`** (새 `ChunkOrientedStep`) |
| 트랜잭션 매니저 | 필수 | **선택** (없으면 ResourcelessTransactionManager) |
| 기본 JobRepository | JDBC (메타데이터 테이블 필요) | **Resourceless (메모리, DB 불필요)** → 이력 저장·재시작이 필요하면 **`@EnableJdbcJobRepository`** |
| 실행 | `JobLauncher` + `JobExplorer` 따로 | **`JobOperator`가 JobLauncher를 상속**, `JobRepository`가 JobExplorer를 상속 |
| retry | Spring Retry 라이브러리 | **Spring Framework 7 core retry** (`RetryPolicy`) |
| skip | `skip()`, `skipLimit()` | **`SkipPolicy`** 기반 |
| CLI | `CommandLineJobRunner` | `CommandLineJobOperator` |
| XML 설정 | 지원 | deprecated |
> 운영 배치는 **재시작·실행 이력**이 중요하므로 Batch 6에서도 JDBC JobRepository를 명시적으로 구성하는 것이 일반적입니다. 세부 변경은 공식 마이그레이션 가이드를 확인하세요.

## 4. JobParameters와 재시작

| 규칙 | 설명 |
|---|---|
| 같은 Job + 같은 식별 파라미터 = **같은 JobInstance** | |
| 이미 **COMPLETED** 된 Instance 재실행 | `JobInstanceAlreadyCompleteException` → 같은 날짜 정산을 실수로 두 번 돌리지 않게 |
| **FAILED** Instance 재실행 | **실패한 Step·청크부터 재시작** (ExecutionContext의 읽기 위치 사용) |
| 매번 새로 실행해야 하면 | `RunIdIncrementer` 또는 실행 시각 파라미터 (단, 중복 방지가 사라짐) |

> 재시작을 하려면 Reader가 **읽은 위치를 저장**할 수 있어야 합니다 (`saveState=true`, 기본). 정렬 기준이 고정(`order by id`)되어 있어야 재시작 위치가 의미 있습니다.

## 5. 대용량 처리 성능 ★

### Reader 선택
| Reader | 방식 | 주의 |
|---|---|---|
| `JpaPagingItemReader` | 페이지마다 쿼리 (`LIMIT offset, size`) | **뒤로 갈수록 느림**(offset), 처리 중 데이터가 바뀌면 **누락** |
| `JdbcCursorItemReader` | DB 커서로 스트리밍 | 커넥션을 Step 내내 점유, 빠름 |
| **No-offset (Zero-offset) 페이징** | `WHERE id > :lastId ORDER BY id LIMIT 1000` | **페이지 깊이와 무관하게 일정한 속도**, 직접 구현하거나 `JdbcPagingItemReader`(정렬 키 기반) 사용 |
| `JpaCursorItemReader` | JPA 스트림 | 영속성 컨텍스트 관리 주의 |

### 페이징 누락 문제
```
조건: status = 'ACTIVE' 인 회원을 DORMANT로 변경 (페이지 크기 1000, offset 페이징)
1페이지: ACTIVE 1~1000 처리 → DORMANT로 바뀜
2페이지: OFFSET 1000 → 하지만 ACTIVE는 이제 1001번부터 시작하므로 1001~2000을 건너뛰고 2001~3000을 읽음
→ 절반이 누락
```
→ **No-offset(ID 커서) 페이징** 또는 커서 Reader, 또는 처리 대상 ID를 먼저 확정

### Writer 성능
- `JpaItemWriter`는 변경 감지로 **건건이 UPDATE** → 대량이면 `JdbcBatchItemWriter`(JDBC 배치) 권장
- MySQL은 `rewriteBatchedStatements=true` (`→ Spring JPA 스터디 자료의 03.JPA실전/04.성능최적화.md`)
- 단순 일괄 변경은 Reader 없이 **벌크 UPDATE 한 번**이 가장 빠를 수 있음 (Tasklet)

### 병렬화
| 방식 | 설명 |
|---|---|
| Multi-threaded Step | 청크를 여러 스레드로 (Reader가 스레드 안전해야, 재시작 어려움) |
| **Partitioning** | 데이터 범위(ID 구간)를 나눠 Step을 병렬 실행 → 대용량 표준 방식 |
| Parallel Steps | 서로 독립적인 Step 동시 실행 (`split`) |
| Remote Chunking/Partitioning | 여러 서버로 분산 |

### 청크 크기
- 보통 **100~1,000**, Reader의 pageSize와 맞춤
- 너무 크면 롤백 범위·메모리 ↑, 너무 작으면 커밋 오버헤드 ↑ → 측정으로 결정

## 6. 실행·운영

| 실행 방법 | 특징 |
|---|---|
| **K8s CronJob / ECS Scheduled Task** | 배치 jar를 컨테이너로 주기 실행 → 끝나면 종료, 리소스 효율적 (권장) |
| Jenkins·Airflow 등 워크플로 도구 | 의존 관계·재실행 UI |
| 애플리케이션 내 `@Scheduled` + JobOperator | 간단하지만 API 서버와 자원 공유, 다중 서버 중복 실행 주의 (`→ 02.스케줄링과분산환경.md`) |

| 운영 체크 | 내용 |
|---|---|
| 배치 전용 애플리케이션 | API 서버와 분리 (`spring.main.web-application-type=none`) |
| 종료 코드 | 실패 시 **0이 아닌 exit code** → CronJob·CI가 실패 감지 |
| 알림 | `JobExecutionListener`로 실패 시 Slack 알림 |
| 멱등성 | 같은 날짜 재실행 시 중복 데이터 X (삭제 후 생성, upsert) |
| 메타데이터 정리 | `BATCH_*` 테이블이 계속 쌓임 → 주기적 정리 |

## 7. 면접 질문

1. **Spring Batch를 쓰는 이유는?**
   → 대량 데이터를 청크 단위로 나누어 커밋해 메모리와 롤백 범위를 제한하고, 실행 메타데이터로 실패 지점부터 재시작하며, skip·retry 정책과 중복 실행 방지, 실행 이력 관리를 제공하기 때문입니다.
2. **Chunk 지향 처리란?**
   → Reader로 한 건씩 읽고 Processor로 가공한 뒤 정해진 개수가 모이면 Writer로 한 번에 쓰고 커밋하는 방식으로, 실패 시 해당 청크만 롤백됩니다.
3. **JpaPagingItemReader로 조건 컬럼을 수정하면 생기는 문제는?**
   → 처리한 데이터가 조회 조건에서 빠지면서 offset이 밀려 일부 데이터를 건너뛰는 누락이 발생합니다. ID 기준 No-offset 페이징이나 커서 Reader를 사용합니다.
4. **Spring Batch 6의 주요 변화는?**
   → 새로운 ChunkOrientedStep과 빌더, 기본 Resourceless JobRepository와 @EnableJdbcJobRepository, JobOperator로의 실행 통합, Spring Framework 7 기반 retry와 SkipPolicy 기반 skip 등이 있습니다.

## 핵심 정리
- 배치 = Job → Step → **Chunk(Reader → Processor → Writer, 청크마다 커밋)**
- **JobParameters로 중복 실행 방지**, 실패 시 **실패 지점부터 재시작**
- skip(잘못된 데이터) / retry(일시 오류)
- 대용량: **No-offset 페이징**(누락·성능), `JdbcBatchItemWriter`, Partitioning
- Batch 6: `ChunkOrientedStepBuilder`, Resourceless 기본 + `@EnableJdbcJobRepository`, `JobOperator`
- 실행은 **K8s CronJob** 등 별도 프로세스, 실패 시 non-zero exit code
