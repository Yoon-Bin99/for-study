# 02. 스케줄링과 분산 환경

> **학습 목표**
> - `@Scheduled`의 cron, fixedRate, fixedDelay 차이와 스레드 풀 설정을 이해한다.
> - 서버가 여러 대일 때 스케줄러가 중복 실행되는 문제를 ShedLock 등으로 해결할 수 있다.
> - Quartz, K8s CronJob 등 스케줄링 방식을 비교하고 선택할 수 있다.

---

## 1. `@Scheduled`

```java
@Configuration
@EnableScheduling
public class SchedulingConfig { }
```
```java
@Slf4j
@Component
@RequiredArgsConstructor
public class CouponScheduler {

    private final CouponService couponService;

    @Scheduled(cron = "0 0 3 * * *", zone = "Asia/Seoul")      // 매일 새벽 3시
    public void expireCoupons() {
        int count = couponService.expireOutdated();
        log.info("만료 처리 쿠폰 {}건", count);
    }

    @Scheduled(fixedDelay = 10_000)        // 이전 실행이 "끝난 후" 10초 뒤
    public void relayOutbox() { ... }

    @Scheduled(fixedRate = 60_000, initialDelay = 5_000)   // 시작 기준 1분마다 (이전 실행과 무관)
    public void refreshRanking() { ... }
}
```
| 옵션 | 기준 | 주의 |
|---|---|---|
| `cron` | 달력 시각 | **zone 명시** (서버 UTC면 9시간 차이) |
| `fixedDelay` | 이전 실행 **종료** 후 | 겹치지 않음 (폴링·릴레이에 적합) |
| `fixedRate` | 이전 실행 **시작** 후 | 실행이 주기보다 길면 밀려서 연속 실행 |
| `initialDelay` | 첫 실행 지연 | |
| 설정 값 | `cron = "${coupon.expire.cron}"` | 환경별로 다르게, `"-"`이면 비활성화 |

### cron 표현식 (스프링: 6자리, 초부터)
```
 ┌ 초 (0-59)
 │ ┌ 분 (0-59)
 │ │ ┌ 시 (0-23)
 │ │ │ ┌ 일 (1-31)
 │ │ │ │ ┌ 월 (1-12)
 │ │ │ │ │ ┌ 요일 (0-7, MON-SUN)
 0 0 3 * * *        매일 03:00:00
 0 */10 * * * *     10분마다
 0 0 9 * * MON-FRI  평일 09:00
 0 0 0 1 * *        매월 1일 자정
```
> Linux crontab·K8s CronJob은 **5자리(분부터)** 입니다. 섞어 쓰다 자주 실수합니다.

### 스레드 풀
- 기본 스케줄러는 **스레드 1개** → 한 작업이 오래 걸리면 **다른 스케줄 작업이 모두 밀림**
```yaml
spring:
  task:
    scheduling:
      pool:
        size: 5
      thread-name-prefix: sched-
  threads:
    virtual:
      enabled: true     # 가상 스레드 사용 시 스케줄 작업도 가상 스레드에서 실행
```
- 스케줄 메서드 안에서 **예외를 잡고 로그**를 남기세요 (예외가 나도 다음 주기는 실행되지만, 로그가 없으면 실패를 모름)
- 스케줄 메서드는 **트랜잭션 경계 밖**에 두고, 실제 로직은 `@Transactional` 서비스로 위임

## 2. 분산 환경의 문제: 중복 실행 ★

```
 [서버 A] @Scheduled 03:00 쿠폰 만료 ──┐
 [서버 B] @Scheduled 03:00 쿠폰 만료 ──┼──▶ 같은 작업이 3번 실행
 [서버 C] @Scheduled 03:00 쿠폰 만료 ──┘    → 알림 메일 3통, 정산 3배, 락 경합
```
| 해결 | 설명 |
|---|---|
| **ShedLock** | DB·Redis에 락을 걸어 **한 서버만 실행** (가장 간단) |
| 별도 배치 서버 1대 | 단일 장애점, 배포 구조 분리 |
| **K8s CronJob** | 스케줄을 인프라가 관리 → 애플리케이션은 실행만 |
| Quartz 클러스터 | DB 기반 클러스터링, 미실행(misfire) 처리 |
| 작업 자체를 멱등하게 | 중복 실행돼도 결과가 같게 (조건부 UPDATE) — **항상 병행** |

### ShedLock
```groovy
implementation 'net.javacrumbs.shedlock:shedlock-spring:<버전>'
implementation 'net.javacrumbs.shedlock:shedlock-provider-jdbc-template:<버전>'
```
```sql
CREATE TABLE shedlock (
    name       VARCHAR(64)  NOT NULL PRIMARY KEY,
    lock_until TIMESTAMP(3) NOT NULL,
    locked_at  TIMESTAMP(3) NOT NULL,
    locked_by  VARCHAR(255) NOT NULL
);
```
```java
@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "10m")
public class ShedLockConfig {

    @Bean
    public LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(
                JdbcTemplateLockProvider.Configuration.builder()
                        .withJdbcTemplate(new JdbcTemplate(dataSource))
                        .usingDbTime()                     // 서버 간 시계 차이 대신 DB 시간 사용
                        .build());
    }
}
```
```java
@Scheduled(cron = "0 0 3 * * *", zone = "Asia/Seoul")
@SchedulerLock(name = "expireCoupons", lockAtMostFor = "30m", lockAtLeastFor = "1m")
public void expireCoupons() { ... }
```
| 옵션 | 의미 |
|---|---|
| `lockAtMostFor` | 실행 서버가 죽어도 이 시간 후 락 해제 (**작업 최대 시간보다 길게**) |
| `lockAtLeastFor` | 작업이 아주 빨리 끝나도 최소 이 시간은 락 유지 → 서버 간 시계 차이로 인한 **재실행 방지** |
> ShedLock은 "**같은 시각의 중복 실행**"을 막는 도구이지, 큐처럼 작업을 분배하지는 않습니다. 실행되지 못한 스케줄을 나중에 보충하지도 않습니다.

## 3. 스케줄링 방식 비교

| 방식 | 장점 | 단점 | 적합 |
|---|---|---|---|
| `@Scheduled` (+ShedLock) | 가장 간단, 코드와 함께 배포 | API 서버 자원 공유, 실행 이력 없음 | 가벼운 주기 작업 (캐시 갱신, Outbox 릴레이) |
| **Quartz** | 동적 스케줄 등록·변경, **클러스터링**, misfire 처리, 영속 Job | 설정 복잡, 전용 테이블 | 사용자가 예약하는 작업 (예약 발송), 스케줄을 런타임에 바꿔야 할 때 |
| **K8s CronJob** | 실행마다 새 파드 → 자원 격리, 실패 재시도·이력, 동시 실행 정책 | 컨테이너 시작 시간, 짧은 주기(초 단위)엔 부적합 | **Spring Batch** 같은 무거운 정기 작업 |
| AWS EventBridge Scheduler + ECS/Lambda | 서버리스, 관리 불필요 | AWS 종속 | AWS 기반 정기 작업 |
| Airflow, Jenkins | DAG(작업 간 의존), 재실행 UI | 별도 플랫폼 운영 | 데이터 파이프라인, 여러 배치의 순서 관리 |

### K8s CronJob 예
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: settlement-batch
spec:
  schedule: "0 2 * * *"            # 5자리 (분 시 일 월 요일)
  timeZone: "Asia/Seoul"
  concurrencyPolicy: Forbid        # 이전 실행이 안 끝났으면 새 실행 건너뜀 → 중복 방지
  startingDeadlineSeconds: 600
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 2              # 실패 시 재시도 횟수
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: batch
              image: registry.example.com/shop-batch:1.4.0
              args: ["--spring.batch.job.name=settlementJob", "targetDate=yesterday"]
```
> K8s CronJob 자세한 내용은 `인프라 스터디 자료`의 쿠버네티스 문서를 참고하세요.

## 4. 지연·예약 작업 (특정 시각에 한 번)

"주문 후 30분 내 미결제 시 자동 취소", "예약 발송" 처럼 **건마다 시각이 다른** 작업
| 방법 | 설명 |
|---|---|
| **주기적 스캔** | 1분마다 `WHERE status='PENDING' AND created_at < now()-30m` 조회 → 처리 (단순·확실, 인덱스 필요) |
| Redis Sorted Set | score = 실행 시각, 주기적으로 `ZRANGEBYSCORE 0 now` (`→ 01.Redis/01.Redis개요와자료구조.md`) |
| 메시지 지연 | RabbitMQ TTL+DLX/지연 플러그인, SQS DelaySeconds(최대 15분) |
| Quartz 동적 Job | 건마다 트리거 등록 (건수가 아주 많으면 부담) |
| EventBridge Scheduler | 일회성 스케줄 대량 생성 가능 |

## 5. 면접 질문

1. **fixedRate와 fixedDelay의 차이는?**
   → fixedRate는 이전 실행의 시작 시점 기준으로 주기적으로 실행하고, fixedDelay는 이전 실행이 끝난 시점부터 지정 시간 후에 실행해 실행이 겹치지 않습니다.
2. **서버가 여러 대일 때 스케줄러 중복 실행을 어떻게 막나요?**
   → ShedLock으로 DB나 Redis에 락을 걸어 한 서버만 실행하게 하거나, 스케줄을 K8s CronJob처럼 인프라로 옮기고, 작업 자체도 중복 실행돼도 안전하도록 멱등하게 만듭니다.
3. **`@Scheduled`, Quartz, CronJob은 언제 각각 쓰나요?**
   → 가벼운 주기 작업은 @Scheduled와 ShedLock, 런타임에 스케줄을 등록·변경하거나 클러스터링이 필요하면 Quartz, 무거운 정기 배치는 자원을 격리할 수 있는 K8s CronJob을 사용합니다.
4. **스케줄 작업이 다른 스케줄 작업을 지연시키는 이유는?**
   → 스프링의 기본 스케줄러 스레드가 하나라 한 작업이 오래 걸리면 다른 작업이 대기하므로, 스케줄링 스레드 풀 크기를 늘리거나 무거운 작업을 비동기로 분리합니다.

## 핵심 정리
- `@Scheduled`: **cron(zone 명시, 스프링 6자리)** / fixedDelay(종료 기준) / fixedRate(시작 기준), 기본 스레드 **1개**
- 다중 서버 = **중복 실행** → **ShedLock**(`lockAtMostFor`, `lockAtLeastFor`) + 멱등 작업
- 동적 스케줄·클러스터 → **Quartz**, 무거운 배치 → **K8s CronJob(`concurrencyPolicy: Forbid`)**
- 건별 예약 작업 → 주기 스캔 / Redis Sorted Set / 지연 메시지
