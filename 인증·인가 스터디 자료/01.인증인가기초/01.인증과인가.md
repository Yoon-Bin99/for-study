# 01. 인증과 인가 (Authentication & Authorization)

> **학습 목표**
> - 인증과 인가의 차이를 예시로 설명할 수 있다.
> - 인증 수단(지식·소유·생체)과 다중 인증을 설명할 수 있다.
> - HTTP의 무상태성 때문에 인증 상태를 유지하는 방법이 필요한 이유를 설명할 수 있다.
> - 접근 제어 모델(RBAC, ABAC, ACL)을 비교할 수 있다.

---

## 1. 인증 vs 인가

| 구분 | **인증 (Authentication, AuthN)** | **인가 (Authorization, AuthZ)** |
|---|---|---|
| 질문 | **너 누구야?** | **너 이거 해도 돼?** |
| 확인 대상 | 신원 (Identity) | 권한 (Permission) |
| 순서 | 먼저 | 인증 **다음** |
| 예 | 아이디·비밀번호 로그인, 소셜 로그인 | 관리자만 회원 삭제, 본인 글만 수정 |
| 실패 시 HTTP | **401 Unauthorized** | **403 Forbidden** |
| Spring Security | `AuthenticationManager`, `AuthenticationProvider` | `AuthorizationManager`, `@PreAuthorize` |

```
회사 출입 비유
인증: 사원증을 찍어 "김윤빈 사원"임을 확인
인가: 김윤빈 사원은 개발팀 사무실은 들어갈 수 있지만, 서버실은 들어갈 수 없음
```

> **401의 이름이 Unauthorized인 이유**: HTTP 표준의 역사적 이름 실수입니다. 의미는 "**인증되지 않음(Unauthenticated)**" 입니다. 로그인은 했는데 권한이 없으면 403입니다.

## 2. 인증 수단 (Factor)

| 요소 | 의미 | 예 |
|---|---|---|
| **지식 기반** (Something you know) | 알고 있는 것 | 비밀번호, PIN, 보안 질문 |
| **소유 기반** (Something you have) | 가지고 있는 것 | 휴대폰(SMS·OTP 앱), 보안키(YubiKey), 공동인증서 |
| **생체 기반** (Something you are) | 신체 특성 | 지문, 얼굴 |

### 다중 인증 (MFA, Multi-Factor Authentication)
**서로 다른 종류의 요소를 2개 이상** 조합합니다.
- 비밀번호 + OTP 앱 → MFA (지식 + 소유)
- 비밀번호 + 보안 질문 → **MFA 아님** (둘 다 지식)
- 비밀번호가 유출되어도 두 번째 요소가 없으면 로그인 불가

### 패스키 (Passkey, WebAuthn)
- 비밀번호 대신 **기기에 저장된 개인키**로 서명해 인증 (공개키 암호화)
- 서버에는 공개키만 저장 → **유출돼도 쓸모없음**, **피싱에 강함**(도메인에 묶여 있음)
- 지문·얼굴 인식으로 기기 잠금 해제 → 소유 + 생체를 한 번에

> Spring Security 6.4+는 패스키, 7.0은 MFA를 기본 지원합니다. (→ `04.보안심화/03.MFA와최신기능.md`)

## 3. 왜 "인증 상태 유지"가 필요한가?

HTTP는 **무상태(Stateless)** 입니다. 서버는 이전 요청을 기억하지 않습니다.

```
요청 1: POST /login (아이디, 비밀번호) → "로그인 성공"
요청 2: GET /my/orders                 → 서버: "너 누구야?" (요청 1을 기억 못 함)
```

매 요청마다 비밀번호를 보낼 수는 없으므로, **로그인 성공 후 "이미 인증된 사용자"임을 증명할 수단**이 필요합니다.

| 방식 | 증명 수단 | 상태 저장 위치 | 문서 |
|---|---|---|---|
| **세션** | 세션 ID (쿠키) | **서버** | `03.세션과쿠키.md` |
| **토큰 (JWT)** | 서명된 토큰 | **클라이언트** (서버는 검증만) | `04.토큰과JWT.md` |
| **OAuth 2.0 / OIDC** | 외부 인증 서버가 발급한 토큰 | 인증 서버 + 클라이언트 | `05.OAuth2와OIDC.md` |
| HTTP Basic | 매 요청마다 `아이디:비밀번호`를 Base64로 | 없음 | 내부 도구, 서버 간 통신 (HTTPS 필수) |
| API Key | 고정 키를 헤더로 | 서버 | 서버 간, 외부 개발자용 API |

## 4. 인가 모델 (접근 제어)

### RBAC (Role-Based Access Control, 역할 기반)
**사용자 → 역할 → 권한** 으로 연결합니다. 가장 많이 씁니다.
```
김철수 ── ROLE_ADMIN ── 회원 조회, 회원 삭제, 공지 작성
이영희 ── ROLE_USER  ── 상품 조회, 주문
```
- 장점: 단순, 관리 쉬움
- 단점: "**본인 글만** 수정 가능" 같은 조건은 역할만으로 표현 불가

### ABAC (Attribute-Based, 속성 기반)
**사용자·리소스·환경의 속성**으로 판단합니다.
```
허용 조건: 사용자.id == 게시글.작성자ID
          AND 사용자.부서 == "인사팀"
          AND 현재시각 in 업무시간
```
- 장점: 세밀한 제어 / 단점: 복잡, 성능

### ACL (Access Control List)
**리소스마다 접근 가능한 사용자 목록**을 둡니다. (구글 드라이브 파일 공유: 이 파일은 A 편집, B 보기)

| 모델 | 기준 | 예 | Spring Security |
|---|---|---|---|
| **RBAC** | 역할 | 관리자 메뉴 | `hasRole("ADMIN")` |
| ABAC | 속성·조건 | 본인 글만, 업무 시간에만 | `@PreAuthorize("#id == authentication.principal.id")`, 커스텀 `AuthorizationManager` |
| ACL | 리소스별 목록 | 문서 공유 | spring-security-acl 모듈 |

> 실무에서는 **RBAC + 소유자 검사(본인 리소스인가)** 조합이 가장 흔합니다. (→ `03.스프링시큐리티실전/06.권한설계와메서드보안.md`)

## 5. 인증·인가 설계 원칙

| 원칙 | 설명 |
|---|---|
| **기본 거부 (Deny by Default)** | 명시적으로 허용하지 않은 것은 모두 막는다 (`anyRequest().authenticated()`) |
| **최소 권한** | 필요한 권한만 부여 |
| **서버에서 검증** | 프론트에서 버튼을 숨기는 것은 UX일 뿐, **보안은 반드시 서버에서** |
| 실패 정보 최소화 | "아이디가 없습니다" / "비밀번호가 틀렸습니다"를 구분하지 않기 → "아이디 또는 비밀번호가 올바르지 않습니다" (계정 존재 여부 노출 방지) |
| **IDOR 방지** | `/orders/42`를 `/orders/43`으로 바꿨을 때 남의 주문이 보이면 안 됨 → 리소스 소유자 검사 |

> **IDOR (Insecure Direct Object Reference)** 는 OWASP Top 10의 1위인 **취약한 접근 제어(Broken Access Control)** 의 대표 사례입니다. 인증은 됐지만 인가 검사가 빠진 경우입니다.

## 6. 면접 질문

1. **인증과 인가의 차이는?**
   → 인증은 사용자가 누구인지 확인하는 것이고, 인가는 인증된 사용자가 특정 리소스나 기능에 접근할 권한이 있는지 확인하는 것입니다. 실패 시 각각 401, 403을 반환합니다.
2. **401과 403의 차이는?**
   → 401은 인증 정보가 없거나 유효하지 않은 경우, 403은 인증은 되었지만 해당 리소스에 대한 권한이 없는 경우입니다.
3. **MFA란?**
   → 지식·소유·생체 중 서로 다른 종류의 인증 요소를 두 개 이상 조합해, 하나가 유출되어도 계정을 보호하는 방식입니다.
4. **RBAC와 ABAC의 차이는?**
   → RBAC는 사용자에게 부여된 역할로 권한을 판단하고, ABAC는 사용자·리소스·환경의 속성 조건으로 판단해 더 세밀한 제어가 가능합니다.

---

## 핵심 정리
- 인증(누구?) → 인가(해도 돼?), 401 vs 403
- 인증 요소: 지식·소유·생체, MFA = 서로 다른 종류 2개 이상, 패스키
- HTTP 무상태 → 세션 / JWT / OAuth2로 인증 상태 유지
- 인가 모델: RBAC(역할) + 소유자 검사가 실무 기본
- 기본 거부, 서버 검증, IDOR 방지
