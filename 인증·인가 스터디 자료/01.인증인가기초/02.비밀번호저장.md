# 02. 비밀번호 안전하게 저장하기

> **학습 목표**
> - 암호화와 해시의 차이, 비밀번호를 해시로 저장하는 이유를 설명할 수 있다.
> - 솔트, 키 스트레칭, 레인보우 테이블을 설명할 수 있다.
> - bcrypt, Argon2, PBKDF2, scrypt의 특징을 비교할 수 있다.
> - Spring Security의 `PasswordEncoder`와 `DelegatingPasswordEncoder`를 사용할 수 있다.

---

## 1. 비밀번호는 절대 그대로 저장하지 않는다

| 저장 방식 | DB가 유출되면? |
|---|---|
| ❌ 평문 | 모든 비밀번호 즉시 노출. 사용자는 다른 사이트에서도 같은 비밀번호를 쓰는 경우가 많아 피해 확산 |
| ❌ 양방향 암호화 (AES) | **키도 함께 유출되면** 전부 복호화 가능. 관리자도 비밀번호를 볼 수 있음 |
| ❌ 단순 해시 (MD5, SHA-256) | 빠르게 계산되므로 **무차별 대입·레인보우 테이블**로 대부분 복원 |
| ✅ **느린 적응형 해시 + 솔트** (bcrypt, Argon2) | 하나하나 깨는 데 매우 오래 걸림 |

---

## 2. 암호화 vs 해시

| 비교 | 암호화 (Encryption) | 해시 (Hash) |
|---|---|---|
| 방향 | **양방향** (키로 복호화) | **단방향** (원래 값 복원 불가) |
| 키 | 필요 | 없음 (솔트는 비밀이 아님) |
| 출력 | 입력 길이에 비례 | **고정 길이** |
| 용도 | 카드 번호, 주민번호처럼 **나중에 원본이 필요한** 데이터 | **비밀번호** (원본이 필요 없고, 같은지만 비교) |

```
로그인 검증
가입 시:    hash("myPass123!") → "$2a$10$N9qo8uLOickgx2ZMRZoMye..." 저장
로그인 시:  hash(입력값) 을 계산해 저장된 값과 비교 → 같으면 성공
```

> 암호화 방식 전반(대칭키·비대칭키, AES 운영 모드, 키 관리)은 → `06.암호화기초.md`

> 그래서 "비밀번호 찾기"는 원래 비밀번호를 **보여 주는 게 아니라 재설정**하게 합니다. 비밀번호를 알려 주는 사이트는 평문이나 양방향 암호화로 저장하고 있다는 뜻입니다.

---

## 3. 단순 해시가 위험한 이유

### 무차별 대입 (Brute Force)
SHA-256은 **빠르게 계산되도록** 설계됐습니다. 최신 GPU는 초당 수십억 번 이상 계산할 수 있어, 짧은 비밀번호는 금방 찾아냅니다.

### 레인보우 테이블 (Rainbow Table)
**자주 쓰는 비밀번호의 해시를 미리 계산해 둔 거대한 표**
```
"123456"   → 8d969eef6ecad3c29a3a629280e686cf...
"password" → 5e884898da28047151d0e56f8dc62927...
→ 유출된 해시를 표에서 찾기만 하면 끝
```
같은 비밀번호는 **같은 해시**가 되므로, 한 번 깨면 같은 비밀번호를 쓰는 모든 사용자가 노출됩니다.

---

## 4. 해결책 1: 솔트 (Salt)

**사용자마다 다른 랜덤 값을 비밀번호에 섞어서** 해시합니다.

```
사용자 A: hash("123456" + "x9K2p")  → a1b2c3...
사용자 B: hash("123456" + "Qm7zL")  → f9e8d7...   ← 같은 비밀번호인데 다른 해시
```
- 레인보우 테이블 무력화 (솔트마다 표를 새로 만들어야 함)
- 같은 비밀번호를 쓰는 사용자를 구분할 수 없음
- 솔트는 **비밀이 아니며** 해시와 함께 저장 (bcrypt는 결과 문자열 안에 포함)

### 페퍼 (Pepper)
모든 사용자에게 공통으로 섞는 **비밀 값**으로, DB가 아닌 별도 저장소(환경 변수, KMS)에 둡니다. DB만 유출되면 해시를 깰 수 없게 하는 추가 방어입니다.

---

## 5. 해결책 2: 키 스트레칭 (Key Stretching)

**해시를 의도적으로 느리게** 만듭니다. 해시를 수천~수만 번 반복하거나 많은 메모리를 쓰게 합니다.
- 정상 사용자: 로그인 한 번에 0.1~1초 → 체감 없음
- 공격자: 수십억 개를 시도해야 함 → 사실상 불가능
- **적응형(Adaptive)**: 컴퓨터가 빨라지면 **비용 인자(work factor)** 를 올려 더 느리게

---

## 6. 비밀번호 해시 알고리즘

| 알고리즘 | 특징 | 권장 여부 |
|---|---|---|
| **Argon2id** | 2015 비밀번호 해싱 대회 우승. **메모리를 많이 써서** GPU·ASIC 공격에 강함 | **OWASP 1순위 권장** |
| **bcrypt** | 1999년부터 검증됨, 비용 인자(2^cost 반복), 입력 **72바이트 제한** | **널리 사용, 여전히 안전** (Spring 기본) |
| scrypt | 메모리 집약적 | 권장 |
| PBKDF2 | 반복 해시, **FIPS 인증** (정부·금융 규정 요구 시) | 반복 횟수를 충분히 크게 |
| MD5, SHA-1, SHA-256 (단독) | 빠름 | ❌ 비밀번호용 사용 금지 |

### bcrypt 결과 읽기
```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 │   │  └───── 솔트 (22자) ─────┘└──────── 해시 (31자) ────────┘
 │   └── 비용 인자: 2^10 = 1024번 반복
 └── 알고리즘 버전
```
→ 솔트가 문자열 안에 들어 있어서 **별도 컬럼이 필요 없습니다.** 컬럼 길이는 넉넉히(VARCHAR(100) 이상) 잡으세요.

## 7. Spring Security의 PasswordEncoder

```java
public interface PasswordEncoder {
    String encode(CharSequence rawPassword);                         // 해시 생성 (매번 다른 솔트)
    boolean matches(CharSequence rawPassword, String encodedPassword); // 검증
    default boolean upgradeEncoding(String encodedPassword) { return false; }
}
```

### 기본 사용
```java
@Configuration
public class PasswordConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class MemberService {
    private final MemberRepository memberRepository;
    private final PasswordEncoder passwordEncoder;

    @Transactional
    public Long signUp(SignUpRequest req) {
        String encoded = passwordEncoder.encode(req.password());   // 저장 전에 반드시 인코딩
        return memberRepository.save(new Member(req.email(), encoded)).getId();
    }
}
```

> **주의**: `encode()`는 호출할 때마다 **다른 결과**가 나옵니다(솔트가 매번 다름). 그래서 `encode(입력) == 저장값`으로 비교하면 항상 실패합니다. 반드시 **`matches(입력, 저장값)`** 를 쓰세요.

### DelegatingPasswordEncoder
저장된 값 앞에 **`{알고리즘}` 접두사**를 붙여 여러 알고리즘을 함께 지원합니다.
```
{bcrypt}$2a$10$dXJ3SW6G7P50lGmMkkmwe.20cQQubK3.HZWzG3YB1tlRy.fqvM/BG
{argon2}$argon2id$v=19$m=16384,t=2,p=1$...
{noop}password                ← 평문 (테스트 전용!)
```
- 새 비밀번호는 기본 알고리즘(**bcrypt**)으로 저장
- 예전 알고리즘으로 저장된 값도 접두사를 보고 검증
- **알고리즘 교체(마이그레이션)** 가 쉬움: 로그인 성공 시 새 알고리즘으로 다시 저장 (`UserDetailsPasswordService`)

```java
// 특정 알고리즘을 직접 지정하고 싶을 때
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12);      // 비용 인자 12
    // 또는 Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()  (Bouncy Castle 의존성 필요)
}
```
> Spring Security 7.0부터는 Password4j 기반 인코더(`Argon2Password4jPasswordEncoder`, `BcryptPassword4jPasswordEncoder` 등)도 제공됩니다.

### 비용 인자 정하기
- 서버에서 **해시 한 번에 약 0.5~1초 이하**가 되도록 측정해서 결정 (bcrypt 기본 10)
- 너무 크게 잡으면 로그인 요청이 몰릴 때 **CPU가 포화**되어 서비스 장애 → 로그인 API에 레이트 리밋을 함께 적용

## 8. 비밀번호 정책

최신 가이드(NIST SP 800-63B)는 예전 관행과 다릅니다.

| 권장 | 비권장 |
|---|---|
| **최소 길이**(8자 이상, 가능하면 더 길게), 긴 비밀번호 허용 | 대문자·숫자·특수문자 **강제 조합 규칙** |
| **유출된 비밀번호 목록과 대조**해 거부 (`password123`) | 주기적인 **강제 변경** (사용자가 `Pass1!` → `Pass2!` 식으로 바꿔 오히려 약해짐) |
| 로그인 시도 횟수 제한, MFA | 비밀번호 힌트, 보안 질문 |
| 붙여넣기 허용 (비밀번호 관리자 사용) | |

> Spring Security 6.3+에는 유출 비밀번호 검사용 `HaveIBeenPwnedRestApiPasswordChecker`가 있습니다.

## 9. 면접 질문

1. **비밀번호를 암호화가 아닌 해시로 저장하는 이유는?**
   → 서버도 원본 비밀번호를 알 필요가 없고 일치 여부만 확인하면 되므로, 복호화할 수 없는 단방향 해시로 저장해 유출 시 피해를 줄이기 위해서입니다.
2. **솔트란?**
   → 사용자마다 다른 랜덤 값을 비밀번호에 섞어 해시하는 것으로, 같은 비밀번호도 다른 해시가 되게 해 레인보우 테이블 공격을 무력화합니다.
3. **SHA-256 대신 bcrypt를 쓰는 이유는?**
   → SHA-256은 너무 빨라 무차별 대입에 취약하고, bcrypt는 솔트를 내장하고 비용 인자로 계산을 의도적으로 느리게 만들어 공격 비용을 크게 높이기 때문입니다.
4. **encode 결과를 직접 비교하면 안 되는 이유는?**
   → encode는 매번 새로운 솔트를 써서 결과가 달라지므로, 저장값에 포함된 솔트를 사용해 비교하는 matches를 써야 합니다.

## 핵심 정리
- 비밀번호 = **단방향 + 느린 해시 + 솔트** (평문·AES·MD5·SHA-256 단독 금지)
- 솔트(사용자별 랜덤, 공개 가능) / 페퍼(공통 비밀) / 키 스트레칭(의도적으로 느리게)
- Argon2id(OWASP 1순위), bcrypt(Spring 기본, 72바이트 제한)
- `PasswordEncoderFactories.createDelegatingPasswordEncoder()`, 검증은 **`matches()`**
- 정책: 길이 + 유출 목록 대조 + 시도 제한, 강제 조합·주기 변경은 비권장
