# 03. 세션과 쿠키 기반 인증

> **학습 목표**
> - 쿠키의 동작 방식과 보안 속성(HttpOnly, Secure, SameSite)을 설명할 수 있다.
> - 세션 기반 인증의 전체 흐름을 그릴 수 있다.
> - 세션 고정, 세션 하이재킹 공격과 방어를 설명할 수 있다.
> - 서버가 여러 대일 때 세션을 공유하는 방법을 설명할 수 있다.

---

## 1. 쿠키 (Cookie)

**서버가 응답 헤더로 브라우저에 저장시키고, 브라우저가 이후 요청마다 자동으로 다시 보내는 작은 데이터**입니다.

```
응답: Set-Cookie: JSESSIONID=8F3A2B...; Path=/; HttpOnly; Secure; SameSite=Lax
이후 요청: Cookie: JSESSIONID=8F3A2B...
```

### 보안 속성
| 속성 | 의미 | 막는 공격 |
|---|---|---|
| **HttpOnly** | JavaScript(`document.cookie`)로 **읽을 수 없음** | **XSS로 쿠키 탈취** |
| **Secure** | **HTTPS 연결에서만** 전송 | 네트워크 도청 |
| **SameSite** | **다른 사이트에서 시작된 요청**에 쿠키를 보낼지 | **CSRF** |
| `Domain`, `Path` | 쿠키를 보낼 범위 | |
| `Max-Age` / `Expires` | 만료 시간. 없으면 브라우저 종료 시 삭제(세션 쿠키) | |

| SameSite | 동작 |
|---|---|
| `Strict` | 다른 사이트에서 오는 요청에는 **절대** 전송 안 함 (링크 클릭으로 들어와도 로그인 안 된 상태) |
| **`Lax`** (주요 브라우저 기본) | 다른 사이트에서 **최상위 GET 이동**(링크 클릭)만 전송. POST·이미지·fetch에는 X |
| `None` | 항상 전송 (**`Secure` 필수**) — 프론트와 백엔드 도메인이 완전히 다를 때 |

> "사이트(Site)"는 등록 가능한 도메인(eTLD+1) 기준입니다. `app.example.com`과 `api.example.com`은 **같은 사이트**(SameSite 대상 아님)지만 **다른 출처(Origin)** 라서 CORS 대상입니다.

## 2. 세션 기반 인증 흐름

```
[브라우저]                                  [서버]                       [세션 저장소]
    │ POST /login (email, password)        │
    │ ───────────────────────────────────> │ 비밀번호 검증
    │                                      │ 세션 생성 ──────────────────> { "8F3A2B": {userId:42, roles:[USER]} }
    │ <─── 200 + Set-Cookie: JSESSIONID=8F3A2B; HttpOnly
    │                                      │
    │ GET /my/orders                       │
    │ Cookie: JSESSIONID=8F3A2B ─────────> │ 세션 조회 ──────────────────> userId: 42
    │                                      │ (인증된 사용자 42로 처리)
    │ <─── 200 주문 목록                     │
    │                                      │
    │ POST /logout ──────────────────────> │ 세션 삭제 ──────────────────> (삭제)
```

- 브라우저는 **의미 없는 랜덤 ID만** 가지고 있고, 실제 정보는 **서버**에 있음
- Spring Security는 인증 정보(`SecurityContext`)를 `HttpSession`에 저장 (→ `03.스프링시큐리티실전/01.폼로그인과세션인증.md`)

### 장단점
| 장점 | 단점 |
|---|---|
| 민감 정보가 **서버에만** 존재 | 서버가 상태를 가짐 → **메모리 사용**, 매 요청 조회 |
| **즉시 무효화** 가능 (강제 로그아웃, 비밀번호 변경 시 전체 로그아웃) | 서버를 늘리면 **세션 공유 문제** |
| 구현이 쉽고 프레임워크 지원이 성숙 | 쿠키 기반 → **CSRF 대비** 필요 |
| 쿠키 HttpOnly로 XSS 탈취 방어 | 모바일 앱·다른 도메인 API에서는 쿠키가 불편 |

## 3. 세션 관련 공격과 방어

### 세션 하이재킹 (Session Hijacking)
공격자가 **세션 ID를 훔쳐** 피해자로 행세합니다.
| 탈취 경로 | 방어 |
|---|---|
| XSS로 `document.cookie` 읽기 | **HttpOnly** |
| HTTP 평문 도청 | **HTTPS + Secure** |
| URL에 세션 ID 노출 (`;jsessionid=...`) | URL 세션 추적 비활성화 (Spring Boot 기본: 쿠키만 사용 설정 권장) |
| 추측 | 충분히 긴 랜덤 ID (서블릿 컨테이너 기본) |

### 세션 고정 (Session Fixation)
```
1. 공격자가 사이트에서 세션 ID "ABC"를 발급받음
2. 피해자가 세션 ID "ABC"를 쓰도록 유도 (링크 등)
3. 피해자가 로그인 → 서버가 "ABC" 세션을 인증 상태로 만듦
4. 공격자는 "ABC"를 이미 알고 있으므로 피해자 계정으로 접근
```
**방어: 로그인 성공 시 세션 ID를 새로 발급**합니다.
> Spring Security는 기본적으로 로그인 시 **세션 ID를 변경**(`changeSessionId`)합니다. 별도 설정이 없어도 방어됩니다.

### 그 밖의 관리
| 항목 | 설정 |
|---|---|
| 세션 만료 | 일정 시간 요청이 없으면 만료 (`server.servlet.session.timeout=30m`) |
| 동시 로그인 제한 | 한 계정에 세션 1개만 (`maximumSessions(1)`) |
| 로그아웃 | 세션 무효화 + 쿠키 삭제 |
| 중요 작업 | 비밀번호 변경·결제 전 **재인증** |

## 4. 서버가 여러 대일 때: 세션 공유

```
            ┌──> [서버 A]  세션 "8F3A2B" 있음
[LB] ───────┤
            └──> [서버 B]  세션 없음 → 로그인 풀림!
```

| 방법 | 설명 | 평가 |
|---|---|---|
| 스티키 세션 | LB가 같은 사용자를 같은 서버로 | 부하 쏠림, 서버 장애 시 세션 유실 |
| 세션 클러스터링 | 서버끼리 세션 복제 | 서버가 많아지면 비효율 |
| **외부 세션 저장소** | **Redis**에 세션 저장 | **가장 일반적** |

```groovy
implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.springframework.session:spring-session-data-redis'
```
```yaml
spring:
  session:
    timeout: 30m
  data:
    redis:
      host: localhost
      port: 6379
```
→ 코드 변경 없이 `HttpSession`이 Redis에 저장됩니다. 서버가 몇 대든 같은 세션을 봅니다.

## 5. 언제 세션을 쓸까?

| 상황 | 추천 |
|---|---|
| 서버 렌더링 웹(Thymeleaf), 관리자 페이지 | **세션** |
| 같은 사이트의 SPA(React) + API, 보안이 중요 (금융) | **세션 + HttpOnly 쿠키** (또는 BFF 패턴) |
| 모바일 앱, 외부 개발자용 API, MSA 서비스 간 | **토큰 (JWT, OAuth2)** |

> "세션은 구식, JWT가 최신"이 아닙니다. **즉시 무효화와 보안이 중요하면 세션이 더 단순하고 안전**한 경우가 많습니다. 금융권 웹 서비스에서 세션을 여전히 많이 쓰는 이유입니다.

## 6. 면접 질문

1. **쿠키와 세션의 차이는?**
   → 쿠키는 브라우저에 저장되어 요청마다 자동 전송되는 데이터이고, 세션은 사용자 정보를 서버에 저장하고 브라우저에는 그 정보를 찾는 세션 ID만 쿠키로 주는 방식입니다.
2. **HttpOnly, Secure, SameSite 속성은 각각 무엇을 막나요?**
   → HttpOnly는 자바스크립트의 쿠키 접근을 막아 XSS 탈취를, Secure는 HTTPS에서만 전송해 도청을, SameSite는 다른 사이트에서 시작된 요청에 쿠키가 실리지 않게 해 CSRF를 막습니다.
3. **세션 고정 공격과 방어 방법은?**
   → 공격자가 미리 알고 있는 세션 ID로 피해자가 로그인하게 만들어 그 세션을 가로채는 공격으로, 로그인 성공 시 세션 ID를 새로 발급해 막습니다.
4. **서버가 여러 대일 때 세션은 어떻게 관리하나요?**
   → Spring Session과 Redis 같은 외부 세션 저장소에 세션을 저장해 모든 서버가 공유하게 합니다.

---

## 핵심 정리
- 쿠키: 자동 전송, **HttpOnly(XSS) + Secure(도청) + SameSite(CSRF)**
- 세션: 서버에 정보, 브라우저엔 랜덤 ID → 즉시 무효화 가능, 서버 상태 부담
- 세션 고정 → 로그인 시 ID 재발급 (Spring Security 기본)
- 다중 서버 → Spring Session + Redis
- 보안·즉시 무효화가 중요하면 세션이 여전히 좋은 선택
