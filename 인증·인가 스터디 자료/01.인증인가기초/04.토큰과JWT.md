# 04. 토큰과 JWT

> **학습 목표**
> - 토큰 기반 인증의 흐름과 세션 방식과의 차이를 설명할 수 있다.
> - JWT의 구조(Header, Payload, Signature)와 서명 검증 원리를 설명할 수 있다.
> - HS256과 RS256의 차이와 사용처를 설명할 수 있다.
> - Access Token과 Refresh Token을 함께 쓰는 이유와 저장 위치별 보안을 비교할 수 있다.
> - JWT의 대표적인 보안 실수를 피할 수 있다.

---

## 1. 토큰 기반 인증

```
[클라이언트]                               [서버]
    │ POST /auth/login (email, password)   │ 검증 성공 → 토큰 발급 (서명)
    │ <──── { accessToken, refreshToken } ─ │   (서버는 아무것도 저장하지 않음*)
    │                                      │
    │ GET /api/orders                      │
    │ Authorization: Bearer eyJhbGci... ─> │ 서명 검증 + 만료 확인 → 토큰 안의 사용자 정보로 처리
    │ <──── 200                             │
```
\* Refresh Token 관리를 위해 일부는 저장합니다. (→ `03.스프링시큐리티실전/03.리프레시토큰과로그아웃.md`)

| 비교 | 세션 | 토큰 (JWT) |
|---|---|---|
| 상태 | 서버가 저장 (**Stateful**) | 토큰 자체에 정보 (**Stateless**) |
| 검증 | 세션 저장소 조회 | **서명 검증만** (저장소 조회 X) |
| 확장 | 세션 공유 필요 | 서버를 늘려도 그대로 |
| 무효화 | **즉시** (세션 삭제) | **어려움** (만료 전까지 유효) |
| 전송 | 쿠키 (자동) | 주로 `Authorization` 헤더 (명시적) |
| CSRF | 대비 필요 | 헤더 방식이면 해당 없음 |
| 크기 | 세션 ID (작음) | 수백 바이트~ (매 요청마다 전송) |
| 적합 | 웹, 즉시 무효화 중요 | **모바일, MSA, 여러 서비스·도메인** |

## 2. JWT 구조

**JWT (JSON Web Token)**: 정보를 JSON으로 담고 **서명**한 토큰 (RFC 7519)

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIiwiZXhwIjoxNzk0MjAwMDAwfQ.k2Z...
└──── Header ────────┘└──────────────────── Payload ───────────────────────┘└ Signature ┘
       Base64URL                         Base64URL
```

### Header
```json
{ "alg": "HS256", "typ": "JWT" }
```

### Payload (클레임, Claims)
```json
{
  "iss": "https://auth.example.com",
  "sub": "42",
  "aud": "order-api",
  "iat": 1794196400,
  "exp": 1794198200,
  "jti": "a7f3c2e1-...",
  "role": "USER"
}
```
| 등록 클레임 | 의미 |
|---|---|
| `iss` (issuer) | 발급자 |
| **`sub`** (subject) | **주체 (사용자 ID)** |
| `aud` (audience) | 대상 (이 토큰을 받을 서비스) |
| **`exp`** (expiration) | **만료 시각** (Unix 초) |
| `iat` (issued at) | 발급 시각 |
| `nbf` (not before) | 이 시각 이전엔 무효 |
| `jti` (JWT ID) | 토큰 고유 ID (블랙리스트·재사용 탐지) |
| 그 외 | 직접 정의 (`role`, `name`) — 비공개 클레임 |

### Signature
```
HMACSHA256( base64url(header) + "." + base64url(payload), 비밀키 )
```

### ⚠️ Payload는 암호화가 아니다
- Base64URL은 **인코딩**일 뿐 → 누구나 디코딩해서 읽을 수 있습니다 ([jwt.io](https://jwt.io)에 붙여 넣으면 바로 보임)
- **서명은 "변조되지 않았음"만 보장**합니다. 비밀은 보장하지 않습니다.
- → **비밀번호, 주민번호, 개인정보를 넣지 마세요.** (내용까지 숨기려면 JWE 암호화)

## 3. 서명 검증 원리

```
공격자가 payload의 "role":"USER"를 "ADMIN"으로 바꾸면?
→ 서버가 (header + 변조된 payload)로 서명을 다시 계산
→ 토큰에 붙은 서명과 다름 → 거부
→ 비밀키를 모르는 공격자는 올바른 서명을 만들 수 없음
```

### HS256 vs RS256
| 비교 | **HS256** (HMAC, 대칭키) | **RS256 / ES256** (비대칭키) |
|---|---|---|
| 키 | **하나의 비밀키**로 서명·검증 | **개인키로 서명**, **공개키로 검증** |
| 검증하는 쪽 | 비밀키를 알아야 함 → 검증 서버도 **위조 가능** | 공개키만 있으면 됨 → **위조 불가** |
| 키 배포 | 모든 서비스에 비밀키 공유 (위험) | 공개키를 **JWKS 엔드포인트**로 공개 |
| 적합 | **단일 서비스** (발급과 검증이 같은 서버) | **여러 서비스·MSA·외부 인증 서버** (OAuth2, Keycloak, Cognito) |

> HS256 비밀키는 **최소 256비트(32바이트) 이상의 랜덤 값**이어야 합니다. `"secret"` 같은 짧은 키는 오프라인 무차별 대입으로 깨집니다. 키는 코드가 아닌 환경 변수·Secrets Manager에 둡니다.

### JWKS (JSON Web Key Set)
인증 서버가 공개키를 공개하는 표준 엔드포인트 (`/.well-known/jwks.json`). 리소스 서버는 이를 받아 서명을 검증하고, 키 교체(`kid` 헤더로 구분)도 자동으로 따라갑니다.

## 4. Access Token + Refresh Token

JWT는 **발급 후 무효화가 어렵다**는 문제가 있습니다. 그래서 수명을 나눕니다.

| 토큰 | 수명 | 용도 | 탈취 시 |
|---|---|---|---|
| **Access Token** | **짧게** (5~30분) | API 요청 인증 | 짧은 시간만 악용 가능 |
| **Refresh Token** | **길게** (1~2주) | Access Token 재발급 전용 | 서버에서 **무효화 가능하게 관리** (저장소에 보관) |

```
1. 로그인 → Access(30분) + Refresh(14일)
2. API 호출: Authorization: Bearer <Access>
3. Access 만료 → 401 (토큰 만료 에러 코드)
4. POST /auth/reissue (Refresh) → 서버가 저장된 Refresh와 비교
     → 새 Access + 새 Refresh 발급 (Rotation: 기존 Refresh 폐기)
5. 로그아웃 → 저장된 Refresh 삭제 (+ Access를 남은 시간 동안 블랙리스트)
```

### Refresh Token Rotation과 재사용 탐지
- 재발급할 때마다 **Refresh Token도 새로** 발급하고 이전 것은 폐기
- **이미 폐기된 Refresh Token이 다시 사용되면** → 탈취로 간주하고 그 사용자의 **모든 토큰 무효화**

## 5. 토큰은 어디에 저장할까? (웹 브라우저)

| 저장 위치 | XSS | CSRF | 비고 |
|---|---|---|---|
| **localStorage / sessionStorage** | ❌ **취약** (JS로 읽힘) | ✅ 안전 (자동 전송 X) | 구현 쉬움 |
| **HttpOnly 쿠키** | ✅ 안전 (JS가 못 읽음) | ⚠️ 대비 필요 (SameSite, CSRF 토큰) | |
| 메모리 (JS 변수) | 상대적으로 안전 | ✅ 안전 | 새로고침하면 사라짐 → Refresh로 복구 |

### 많이 쓰는 조합
```
Access Token  → 메모리 (Authorization 헤더로 전송)
Refresh Token → HttpOnly + Secure + SameSite=Strict 쿠키, Path=/auth/reissue 로 범위 제한
```

> XSS가 있으면 어떤 저장 방식이든 공격자가 **사용자 브라우저에서 API를 대신 호출**할 수 있습니다. 저장 위치 선택은 피해를 줄이는 것이고, **근본 대책은 XSS 자체를 막는 것**입니다.

> **BFF (Backend For Frontend) 패턴**: 토큰을 브라우저에 전혀 주지 않고, 같은 도메인의 BFF 서버가 토큰을 보관하며 브라우저와는 세션 쿠키로만 통신합니다. 보안 요구가 높은 서비스에서 권장되는 추세입니다.

## 6. JWT 보안 실수

| 실수 | 결과 | 대책 |
|---|---|---|
| **`alg: none`** 허용 | 서명 없는 토큰을 통과시킴 | 라이브러리에서 **허용 알고리즘을 고정** |
| 알고리즘 혼동 (RS256 공개키를 HS256 비밀키로 사용) | 공개키로 위조 가능 | 검증 시 알고리즘 명시 |
| 약한 HS256 키 | 무차별 대입으로 키 탈취 | 256비트 이상 랜덤 키 |
| **`exp` 검증 안 함**, 너무 긴 수명 | 영구 토큰 | 짧은 Access 수명, 라이브러리 기본 검증 사용 |
| Payload에 민감 정보 | 정보 노출 | 식별자와 최소한의 권한만 |
| `iss`, `aud` 검증 안 함 | 다른 서비스용 토큰으로 접근 | 발급자·대상 검증 |
| 토큰을 URL 쿼리에 | 서버 로그·브라우저 기록·Referer로 유출 | 헤더 사용 |
| 로그에 토큰 출력 | 유출 | 마스킹 |

> 직접 파싱하지 말고 **검증된 라이브러리**(jjwt, Nimbus JOSE + JWT, Spring Security OAuth2 Resource Server)를 쓰세요.

## 7. 면접 질문

1. **JWT의 구조는?**
   → Header(알고리즘), Payload(클레임), Signature(서명)를 Base64URL로 인코딩해 점으로 이은 형태입니다.
2. **JWT Payload에 민감 정보를 넣으면 안 되는 이유는?**
   → Payload는 암호화가 아닌 인코딩이라 누구나 디코딩해 읽을 수 있고, 서명은 변조 여부만 보장하기 때문입니다.
3. **JWT의 단점과 보완 방법은?**
   → 발급 후 서버에서 무효화하기 어렵습니다. Access Token 수명을 짧게 하고, 서버에서 관리하는 Refresh Token으로 재발급하며, 로그아웃 시 블랙리스트와 Refresh 삭제로 보완합니다.
4. **HS256과 RS256의 차이는?**
   → HS256은 하나의 비밀키로 서명·검증하는 대칭 방식이라 검증하는 쪽도 위조할 수 있고, RS256은 개인키로 서명하고 공개키로 검증해 여러 서비스가 안전하게 검증할 수 있습니다.
5. **세션과 JWT 중 무엇을 선택하겠습니까?**
   → 단일 웹 서비스이고 즉시 무효화가 중요하면 세션, 모바일·MSA처럼 여러 서비스가 독립적으로 검증해야 하면 JWT를 선택합니다.

## 핵심 정리
- 토큰 인증 = 서버 무상태, 서명 검증만 / 단점: 무효화 어려움
- JWT = Header.Payload.Signature, **Payload는 누구나 읽음**
- HS256(대칭, 단일 서비스) vs RS256(비대칭, 공개키 검증, JWKS)
- 짧은 Access + 서버 관리 Refresh(Rotation, 재사용 탐지)
- 웹 저장: Access는 메모리, Refresh는 HttpOnly 쿠키 (또는 BFF)
- `alg` 고정, `exp`·`iss`·`aud` 검증, 강한 키, 검증된 라이브러리
