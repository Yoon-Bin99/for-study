# 05. OAuth 2.0과 OpenID Connect

> **학습 목표**
> - OAuth 2.0이 해결하는 문제와 4가지 역할을 설명할 수 있다.
> - Authorization Code + PKCE 흐름을 단계별로 설명할 수 있다.
> - 각 Grant Type의 용도와 폐기된 방식을 구분할 수 있다.
> - OAuth 2.0(인가)과 OIDC(인증)의 차이, ID Token과 Access Token의 차이를 설명할 수 있다.
> - "소셜 로그인"이 실제로 어떻게 동작하는지 설명할 수 있다.

---

## 1. OAuth 2.0이 해결하는 문제

> "우리 서비스에서 사용자의 **구글 캘린더 일정**을 읽고 싶다."

### 나쁜 방법
사용자에게 **구글 비밀번호를 받아서** 우리 서버가 대신 로그인
- 우리 서비스가 구글 계정 **전체 권한**을 가짐 (메일, 드라이브까지)
- 우리가 해킹당하면 구글 계정까지 유출
- 권한을 일부만 주거나 나중에 회수할 방법이 없음

### OAuth 2.0
**비밀번호를 주지 않고, 필요한 권한(scope)만, 제한된 기간 동안 위임**하는 **인가(Authorization) 프레임워크**입니다. (RFC 6749)
```
사용자: "이 앱이 내 캘린더를 '읽기만' 하도록 허락할게"
구글:   → 앱에게 "캘린더 읽기" 권한만 담긴 Access Token 발급
```

---

## 2. 4가지 역할

| 역할 | 설명 | 예 (카카오 로그인) |
|---|---|---|
| **Resource Owner** | 리소스의 주인 = **사용자** | 카카오 회원 |
| **Client** | 권한을 위임받으려는 **애플리케이션** | **우리 서비스** |
| **Authorization Server** | 사용자 인증 후 **토큰을 발급** | 카카오 인증 서버 (kauth.kakao.com) |
| **Resource Server** | 보호된 리소스(API)를 제공, 토큰 검증 | 카카오 API 서버 (kapi.kakao.com) |

### 사전 준비: 클라이언트 등록
개발자 콘솔(Kakao Developers, Google Cloud Console)에 앱을 등록하면 받는 것:
- **Client ID**: 앱 식별자 (공개)
- **Client Secret**: 앱 비밀번호 (**서버에만 보관**)
- **Redirect URI**: 인증 후 돌아올 주소 (등록된 주소로만 리다이렉트 → 탈취 방지)

## 3. Authorization Code Grant (+ PKCE)

**가장 안전하고 표준적인 방식**입니다. 웹 서버, SPA, 모바일 모두 이 방식을 씁니다.

```
 사용자(브라우저)          우리 서비스(Client)          카카오 인증 서버           카카오 API
      │                        │                         │                      │
 ① "카카오로 로그인" 클릭 ──────>│                         │                      │
      │ <── ② 302 리다이렉트: kauth.kakao.com/oauth/authorize                      │
      │        ?response_type=code&client_id=...&redirect_uri=...                 │
      │        &scope=profile_nickname&state=랜덤값&code_challenge=...             │
      │ ────────────────────────────────────────────────> │                      │
      │ ③ 카카오 로그인 화면 + 동의 화면 (사용자가 카카오에 직접 비밀번호 입력)        │
      │ <── ④ 302: redirect_uri?code=AUTH_CODE&state=랜덤값                        │
      │ ─────────────────────> │                         │                      │
      │                        │ ⑤ state 검증            │                      │
      │                        │ POST /oauth/token ─────> │                      │
      │                        │ (code, client_secret,    │                      │
      │                        │  code_verifier)          │                      │
      │                        │ <── ⑥ Access Token (+ Refresh, ID Token)        │
      │                        │ ⑦ GET /v2/user/me (Bearer Access Token) ──────────> │
      │                        │ <── 사용자 정보 (id, 닉네임, 이메일) ──────────────── │
      │                        │ ⑧ 회원 조회·가입 → 우리 서비스의 세션/JWT 발급         │
      │ <── 로그인 완료 ─────────│                         │                      │
```

### 왜 Code를 한 번 더 거치나?
- ④의 리다이렉트는 **브라우저 URL**을 통과하므로 기록·로그·확장 프로그램에 노출될 수 있음
- 그래서 브라우저에는 **수명이 짧고 한 번만 쓸 수 있는 Code**만 주고
- **Access Token은 ⑤~⑥에서 서버 대 서버로**(Client Secret과 함께) 받음 → 브라우저에 노출 X

### state 파라미터
- 요청 시 랜덤 값을 보내고, 돌아올 때 같은 값인지 확인
- **CSRF 방지**: 공격자가 자기 계정의 code로 피해자를 로그인시키는 공격 차단

### PKCE (Proof Key for Code Exchange, "픽시")
Client Secret을 안전하게 보관할 수 없는 **SPA·모바일 앱**을 위해 만들어졌고, 지금은 **모든 클라이언트에 권장**됩니다.
```
1. 클라이언트가 랜덤 code_verifier 생성
2. code_challenge = BASE64URL(SHA256(code_verifier)) 를 인가 요청에 포함
3. 토큰 요청 시 원래 code_verifier를 보냄
4. 인증 서버가 해시해서 비교 → 같아야 토큰 발급
→ 중간에 Code를 가로채도 code_verifier가 없으면 토큰을 받을 수 없음
```

## 4. Grant Type 정리

| Grant Type | 사용처 | 상태 |
|---|---|---|
| **Authorization Code (+ PKCE)** | 사용자가 있는 모든 앱 (웹, SPA, 모바일) | ✅ **표준** |
| **Client Credentials** | **서버 대 서버** (사용자 없음): 배치, 내부 서비스 간 호출 | ✅ |
| Refresh Token | Access Token 재발급 | ✅ |
| Device Code | 입력이 불편한 기기 (스마트 TV) → 휴대폰으로 인증 | ✅ |
| ~~Implicit~~ | 브라우저에서 바로 토큰 받기 | ❌ **폐기** (토큰이 URL에 노출) |
| ~~Resource Owner Password~~ | 앱이 사용자 ID·비밀번호를 직접 받음 | ❌ **폐기** (OAuth의 취지에 반함) |

> OAuth 2.1(초안)은 PKCE 필수, Implicit·Password 제거, Redirect URI 정확히 일치 등 보안 모범 사례를 정리한 버전입니다. Spring Security 7.0에서도 Password Grant 지원이 제거되었습니다.

### Scope
권한의 범위입니다. 사용자는 동의 화면에서 어떤 scope를 허락하는지 봅니다.
```
scope=profile_nickname account_email      (카카오)
scope=openid profile email                (구글, OIDC)
```

## 5. OAuth 2.0은 "인증"이 아니다 → OIDC

OAuth 2.0은 **인가(권한 위임)** 프로토콜입니다. Access Token은 "이 토큰을 가진 앱은 캘린더를 읽을 수 있다"는 뜻이지 "**이 사용자가 누구인지**"를 표준으로 알려 주지 않습니다.

그래서 각 서비스는 "Access Token으로 사용자 정보 API를 호출"하는 방식으로 로그인을 구현했고, 방식이 제각각이었습니다.

### OpenID Connect (OIDC)
**OAuth 2.0 위에 인증(로그인) 계층을 표준화**한 것입니다.
- scope에 **`openid`** 를 넣으면
- 토큰 응답에 **ID Token**(사용자가 누구인지 담은 **JWT**)이 추가됨
- 표준 UserInfo 엔드포인트, 표준 클레임(`sub`, `email`, `name`)
- **Discovery**: `/.well-known/openid-configuration`에 엔드포인트·공개키 정보 공개

| 비교 | **Access Token** | **ID Token** |
|---|---|---|
| 목적 | **API 접근 권한** (인가) | **사용자 신원 증명** (인증) |
| 받는 쪽 | Resource Server (API) | **Client** (우리 앱) |
| 형식 | 정해지지 않음 (JWT 또는 불투명 문자열) | **항상 JWT** |
| 용도 | `Authorization: Bearer`로 API 호출 | 로그인한 사용자 확인 (`sub`, `email`) |
| 주의 | | **ID Token을 API 호출에 쓰면 안 됨** |

ID Token Payload 예:
```json
{
  "iss": "https://accounts.google.com",
  "sub": "110169484474386276334",
  "aud": "우리-client-id",
  "email": "yoon@example.com",
  "email_verified": true,
  "name": "윤빈",
  "iat": 1794196400,
  "exp": 1794200000,
  "nonce": "n-0S6_WzA2Mj"
}
```
- 클라이언트는 서명(JWKS), `iss`, **`aud`(내 client_id인지)**, `exp`, `nonce`를 검증

| 제공자 | OIDC 지원 |
|---|---|
| 구글, 애플, 마이크로소프트 | ✅ |
| 카카오 | ✅ (OIDC 활성화 설정 시 ID Token 발급) |
| 네이버 | OAuth 2.0 + 사용자 정보 API 방식 |

## 6. 소셜 로그인 ≠ 우리 서비스 로그인

소셜 로그인의 결과는 "**카카오가 이 사용자를 인증해 줬다**"는 사실까지입니다. 이후는 우리 서비스의 몫입니다.

```
1. 카카오 사용자 정보 받음 (provider = kakao, providerId = 123456789)
2. (provider, providerId)로 우리 회원 테이블 조회
     없으면 → 회원 가입 처리 (추가 정보 입력 화면, 약관 동의)
     있으면 → 로그인
3. 우리 서비스의 인증 수단 발급 (세션 또는 우리 서비스의 JWT)
4. 카카오 Access Token은 카카오 API를 계속 쓸 게 아니면 보관할 필요 없음
```

> **회원 식별은 이메일이 아니라 (provider, providerId)로** 합니다. 이메일은 바뀌거나 제공되지 않을 수 있고, 제공자마다 검증 여부가 다릅니다. 같은 이메일로 여러 소셜 계정을 연결할지는 정책으로 결정합니다.

## 8. 면접 질문

1. **OAuth 2.0이란?**
   → 사용자가 비밀번호를 공유하지 않고 제3자 애플리케이션에 필요한 범위의 권한만 위임할 수 있게 하는 인가 프레임워크입니다.
2. **Authorization Code 방식에서 Code를 거치는 이유는?**
   → 브라우저를 통과하는 리다이렉트에는 짧은 수명의 일회용 Code만 노출하고, Access Token은 Client Secret과 함께 서버 간 통신으로 받아 토큰 노출을 막기 위해서입니다.
3. **PKCE란?**
   → 클라이언트가 만든 code_verifier의 해시를 인가 요청에 넣고 토큰 요청 때 원본을 보내 검증하는 방식으로, Code가 탈취되어도 토큰을 발급받지 못하게 합니다.
4. **OAuth 2.0과 OIDC의 차이는?**
   → OAuth 2.0은 권한 위임을 위한 인가 프로토콜이고, OIDC는 그 위에 ID Token과 표준 사용자 정보를 더해 인증(로그인)을 표준화한 프로토콜입니다.
5. **ID Token과 Access Token의 차이는?**
   → ID Token은 클라이언트가 사용자의 신원을 확인하기 위한 JWT이고, Access Token은 리소스 서버의 API에 접근하기 위한 권한 증명입니다.

---

## 핵심 정리
- OAuth 2.0 = 비밀번호 없이 **권한 위임**(인가), 역할: Resource Owner / Client / Authorization Server / Resource Server
- **Authorization Code + PKCE + state**가 표준, Implicit·Password는 폐기
- 서버 간: Client Credentials
- OIDC = OAuth 2.0 + **ID Token(JWT)** → 인증 표준화
- 소셜 로그인 후 (provider, providerId)로 회원 매핑 → 우리 서비스의 세션/JWT 발급
