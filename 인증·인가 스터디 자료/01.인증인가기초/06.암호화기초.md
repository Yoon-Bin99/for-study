# 06. 암호화 기초: 인코딩·해시·대칭키·비대칭키

> **학습 목표**
> - 인코딩, 암호화(양방향), 해시(단방향)를 구분할 수 있다.
> - 대칭키 암호(AES)의 운영 모드(ECB, CBC, GCM)와 IV의 역할을 설명할 수 있다.
> - 비대칭키 암호(RSA, ECC)가 쓰이는 곳(키 교환, 전자서명)을 설명할 수 있다.
> - MAC과 전자서명의 차이를 설명할 수 있다.
> - Java로 AES-GCM 암호화를 구현하고, DB 개인정보 컬럼을 암호화·검색할 수 있다.
> - 키 관리(KMS, 봉투 암호화, 키 교체)와 개인정보보호법의 암호화 대상을 설명할 수 있다.

---

## 1. 큰 그림: 인코딩 vs 암호화 vs 해시

| 구분 | 목적 | 되돌리기 | 키 | 예 |
|---|---|---|---|---|
| **인코딩** | 데이터 **형식 변환** (전송·저장 편의) | 누구나 가능 | **없음** | Base64, URL 인코딩, UTF-8 |
| **양방향 암호화** | **기밀성** (허가된 사람만 읽기) | **키가 있으면** 복호화 | 필요 | AES, RSA |
| **단방향 암호화 (해시)** | **무결성·비교** (원본 없이 같은지 확인) | **불가능** | 없음 (HMAC은 키 사용) | SHA-256, bcrypt |

```
인코딩:   "hello" → Base64 → "aGVsbG8="           → 누구나 디코딩 가능 (보안 X)
암호화:   "hello" → AES(키) → "x9#kQ2..."          → 키로 복호화 → "hello"
해시:     "hello" → SHA-256 → "2cf24dba5fb0a30e..." → 원본으로 되돌릴 수 없음
```

> **"Base64로 암호화했다"는 틀린 말입니다.** JWT의 Payload, HTTP Basic 인증의 `아이디:비밀번호`도 Base64일 뿐이라 누구나 읽을 수 있습니다.

### 국내에서 쓰는 용어
| 흔히 부르는 이름 | 정확한 의미 | 용도 |
|---|---|---|
| **단방향 암호화** | 해시 함수 | **비밀번호** 저장 |
| **양방향 암호화** | 대칭키·비대칭키 암호화 | 주민번호, 계좌번호 등 **원본이 다시 필요한** 정보 |

### 무엇을 써야 할까?
| 상황 | 방법 |
|---|---|
| 비밀번호 저장 | **bcrypt / Argon2** (느린 해시 + 솔트) (→ `02.비밀번호저장.md`) |
| 주민번호·카드번호·계좌번호 저장 | **AES-256-GCM** 등 양방향 암호화 |
| 파일이 변조되지 않았는지 확인 | SHA-256 |
| 메시지가 변조되지 않았고, 비밀키를 공유한 상대가 보냈는지 | **HMAC** (웹훅 서명, JWT HS256) |
| 누가 보냈는지 제3자도 검증 | **전자서명** (RSA, ECDSA, JWT RS256) |
| 통신 구간 보호 | **TLS** (HTTPS) |

## 2. 해시 (단방향 암호화)

임의 길이의 입력을 **고정 길이의 값**으로 바꾸는 함수입니다.

### 좋은 암호학적 해시의 조건
| 성질 | 의미 |
|---|---|
| **역상 저항성** | 해시값으로 원본을 찾을 수 없음 |
| 제2 역상 저항성 | 주어진 입력과 같은 해시를 갖는 다른 입력을 찾을 수 없음 |
| **충돌 저항성** | 같은 해시를 갖는 두 입력을 찾을 수 없음 |
| 눈사태 효과 | 입력이 1비트만 바뀌어도 결과가 완전히 달라짐 |

| 알고리즘 | 출력 | 상태 |
|---|---|---|
| MD5 | 128비트 | ❌ **충돌 공격 가능** (보안 용도 사용 금지, 파일 중복 확인 정도만) |
| SHA-1 | 160비트 | ❌ 충돌 실증됨 (2017), 사용 중단 |
| **SHA-256** (SHA-2 계열) | 256비트 | ✅ 표준 |
| SHA-3 | 가변 | ✅ |

```java
byte[] hash = MessageDigest.getInstance("SHA-256").digest("hello".getBytes(StandardCharsets.UTF_8));
String hex = HexFormat.of().formatHex(hash);    // 2cf24dba5fb0a30e...
```

> SHA-256은 **빠르기 때문에** 비밀번호 저장에는 부적합합니다. 비밀번호는 일부러 느리게 만든 bcrypt·Argon2를 씁니다.

## 3. 대칭키 암호 (양방향, 같은 키)

**암호화와 복호화에 같은 키**를 씁니다. 빠르기 때문에 **실제 데이터 암호화는 거의 대칭키**로 합니다.

| 알고리즘 | 키 길이 | 상태 |
|---|---|---|
| **AES** | 128 / 192 / **256비트** | ✅ 국제 표준 |
| **ARIA**, **SEED** | 128~256 / 128비트 | ✅ **국내 표준** (공공·금융권에서 요구하는 경우 많음) |
| ChaCha20-Poly1305 | 256비트 | ✅ 모바일·TLS |
| DES, 3DES, RC4 | | ❌ 사용 금지 |

### 블록 암호와 운영 모드
AES는 **16바이트 블록 단위**로 암호화합니다. 긴 데이터를 여러 블록으로 어떻게 이어서 처리할지가 **운영 모드**입니다.

| 모드 | 동작 | 특징 | 권장 |
|---|---|---|---|
| **ECB** | 블록을 **각각 독립적으로** 암호화 | **같은 평문 블록 → 같은 암호문 블록** → 패턴 노출 | ❌ **사용 금지** |
| CBC | 이전 암호문 블록과 XOR 후 암호화, 시작에 **IV** 필요 | 패턴 숨김, 무결성 검증 없음 → 패딩 오라클 공격 위험, 별도 MAC 필요 | ⚠️ 레거시 |
| CTR | 카운터를 암호화해 평문과 XOR | 병렬 처리 가능, 무결성 없음 | ⚠️ |
| **GCM** | CTR + **인증 태그** (AEAD) | **암호화 + 무결성(변조 검증)을 한 번에** | ✅ **권장** |

```
ECB의 문제 (같은 블록이 같은 암호문)
평문:   [AAAA...16바이트][AAAA...16바이트][BBBB...]
암호문: [x9Kq...       ][x9Kq...       ][7mZ2...]   ← 반복이 그대로 보임
```
> Java에서 `Cipher.getInstance("AES")`처럼 **모드를 생략하면 기본값이 `AES/ECB/PKCS5Padding`** 입니다. 반드시 `AES/GCM/NoPadding`처럼 명시하세요.

### IV (Initialization Vector, 초기화 벡터) / Nonce
- 같은 키로 같은 평문을 암호화해도 **매번 다른 암호문**이 나오게 하는 랜덤 값
- **비밀이 아님** → 암호문 앞에 붙여서 저장
- **GCM에서 같은 키로 같은 IV를 재사용하면 보안이 완전히 무너집니다** (키 스트림 노출, 위조 가능). 매번 `SecureRandom`으로 새로 생성 (12바이트)

### AEAD (Authenticated Encryption with Associated Data)
암호화와 동시에 **인증 태그**를 만들어, 복호화할 때 **변조 여부를 자동으로 검증**합니다. 누군가 암호문을 1비트라도 바꾸면 복호화가 실패합니다. (AES-GCM, ChaCha20-Poly1305)

## 4. Java로 AES-256-GCM 구현

```java
public final class AesGcmCipher {

    private static final String TRANSFORMATION = "AES/GCM/NoPadding";
    private static final int IV_LENGTH = 12;          // GCM 권장 IV 길이 (바이트)
    private static final int TAG_LENGTH_BIT = 128;    // 인증 태그 길이
    private static final SecureRandom RANDOM = new SecureRandom();

    private final SecretKey key;

    public AesGcmCipher(byte[] keyBytes) {
        if (keyBytes.length != 32) {
            throw new IllegalArgumentException("AES-256 키는 32바이트여야 합니다.");
        }
        this.key = new SecretKeySpec(keyBytes, "AES");
    }

    /** 결과 = Base64( IV(12바이트) + 암호문 + 인증태그 ) */
    public String encrypt(String plainText) {
        try {
            byte[] iv = new byte[IV_LENGTH];
            RANDOM.nextBytes(iv);                                    // ★ 매번 새 IV
            Cipher cipher = Cipher.getInstance(TRANSFORMATION);
            cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(TAG_LENGTH_BIT, iv));
            byte[] cipherText = cipher.doFinal(plainText.getBytes(StandardCharsets.UTF_8));
            byte[] result = ByteBuffer.allocate(iv.length + cipherText.length).put(iv).put(cipherText).array();
            return Base64.getEncoder().encodeToString(result);
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException("암호화 실패", e);
        }
    }

    public String decrypt(String encoded) {
        try {
            ByteBuffer buffer = ByteBuffer.wrap(Base64.getDecoder().decode(encoded));
            byte[] iv = new byte[IV_LENGTH];
            buffer.get(iv);
            byte[] cipherText = new byte[buffer.remaining()];
            buffer.get(cipherText);
            Cipher cipher = Cipher.getInstance(TRANSFORMATION);
            cipher.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(TAG_LENGTH_BIT, iv));
            return new String(cipher.doFinal(cipherText), StandardCharsets.UTF_8);
        } catch (AEADBadTagException e) {
            throw new IllegalStateException("변조되었거나 키가 다릅니다.", e);   // 무결성 검증 실패
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException("복호화 실패", e);
        }
    }
}
```

```java
// 키 생성 (한 번 만들어 KMS·Secrets Manager에 보관)
KeyGenerator generator = KeyGenerator.getInstance("AES");
generator.init(256);
String base64Key = Base64.getEncoder().encodeToString(generator.generateKey().getEncoded());
```

| 확인한 동작 | 결과 |
|---|---|
| 암호화 → 복호화 | 원문 복원 |
| 같은 값을 두 번 암호화 | **매번 다른 암호문** (IV가 다름) |
| 암호문 1비트 변조 | `AEADBadTagException` → 복호화 거부 |
| 다른 키로 복호화 | 거부 |

> Spring Security의 `spring-security-crypto`에도 AES-GCM 기반 `Encryptors.stronger(password, salt)`(바이트), `Encryptors.delux(password, salt)`(문자열)가 있습니다. 비밀번호에서 키를 만들어(PBKDF2) 쓰는 방식입니다.

## 5. 비대칭키 암호 (공개키·개인키)

**공개키와 개인키 한 쌍**을 씁니다. 한쪽으로 처리한 것은 **다른 쪽으로만** 풀 수 있습니다.

| 용도 | 방향 | 예 |
|---|---|---|
| **암호화 (기밀성)** | **공개키로 암호화 → 개인키로 복호화** | 상대의 공개키로 암호화하면 상대만 읽을 수 있음 |
| **전자서명 (인증·부인 방지)** | **개인키로 서명 → 공개키로 검증** | JWT RS256, 인증서, 공동인증서, 코드 서명 |
| **키 교환** | 서로의 공개 값으로 같은 비밀값 도출 | **ECDHE** (TLS 1.3) |

| 알고리즘 | 특징 | 권장 키 길이 |
|---|---|---|
| **RSA** | 오래 검증됨, 암호화·서명 모두 | **2048비트 이상** (장기 보관은 3072 이상) |
| **ECC** (ECDSA, ECDH, Ed25519) | **짧은 키로 같은 보안** (256비트 ECC ≈ 3072비트 RSA), 빠름 | P-256, Ed25519 |

### 대칭키 vs 비대칭키
| 비교 | 대칭키 | 비대칭키 |
|---|---|---|
| 키 | 하나 (양쪽이 공유) | 공개키 + 개인키 |
| 속도 | **빠름** | 수백~수천 배 느림 |
| 키 전달 문제 | **있음** (어떻게 안전하게 공유?) | 없음 (공개키는 공개해도 됨) |
| 용도 | **대용량 데이터 암호화** | 키 교환, 전자서명, 소량 데이터 |

### 하이브리드 암호화
둘의 장점을 합칩니다. **HTTPS, KMS 봉투 암호화, PGP 메일**이 모두 이 방식입니다.
```
1. 랜덤 대칭키(세션 키)를 만든다
2. 데이터는 대칭키(AES)로 암호화         ← 빠름
3. 대칭키는 받는 사람의 공개키로 암호화     ← 키 전달 문제 해결 (TLS 1.3은 ECDHE 키 교환으로 대체)
4. [암호화된 데이터 + 암호화된 대칭키]를 보낸다
```

### 전자서명 예시
```java
KeyPairGenerator generator = KeyPairGenerator.getInstance("RSA");
generator.initialize(2048);
KeyPair pair = generator.generateKeyPair();

byte[] message = "주문 42, 금액 10000원".getBytes(StandardCharsets.UTF_8);

// 서명 (개인키)
Signature signer = Signature.getInstance("SHA256withRSA");
signer.initSign(pair.getPrivate());
signer.update(message);
byte[] signature = signer.sign();

// 검증 (공개키) — 메시지가 1바이트라도 바뀌면 false
Signature verifier = Signature.getInstance("SHA256withRSA");
verifier.initVerify(pair.getPublic());
verifier.update(message);
boolean valid = verifier.verify(signature);
```
> RSA로 직접 데이터를 암호화할 때는 패딩으로 **OAEP**(`RSA/ECB/OAEPWithSHA-256AndMGF1Padding`)를 씁니다. 오래된 PKCS#1 v1.5 암호화 패딩은 공격이 알려져 있습니다. (이름의 ECB는 RSA에서는 의미 없는 관례 표기입니다)

## 6. MAC vs 전자서명

| 비교 | **MAC (HMAC)** | **전자서명** |
|---|---|---|
| 키 | **대칭키** (양쪽이 같은 비밀키) | **비대칭키** (개인키로 서명, 공개키로 검증) |
| 보장 | 무결성 + **비밀키를 가진 쪽**이 만들었음 | 무결성 + **개인키 소유자**가 만들었음 |
| 제3자 검증 | 불가 (키를 공유해야 함) | **가능** (공개키만 있으면) |
| **부인 방지** | X (양쪽 모두 만들 수 있음) | **O** (개인키는 서명자만 가짐) |
| 속도 | 빠름 | 느림 |
| 예 | **웹훅 서명 검증**, JWT HS256, API 요청 서명(AWS SigV4) | JWT RS256, TLS 인증서, 공동인증서 |

```java
// 웹훅 검증: 결제사가 보낸 X-Signature 헤더를 HMAC으로 다시 계산해 비교
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(new SecretKeySpec(webhookSecret, "HmacSHA256"));
byte[] expected = mac.doFinal(requestBody);
boolean valid = MessageDigest.isEqual(expected, HexFormat.of().parseHex(signatureHeader));  // ★ 상수 시간 비교
```
> 서명·MAC 값은 `Arrays.equals`나 `String.equals` 대신 **`MessageDigest.isEqual`** 로 비교하세요. 앞에서부터 비교하다 멈추는 방식은 **응답 시간 차이로 값을 추측하는 타이밍 공격**에 취약합니다.

## 7. DB 개인정보 컬럼 암호화 (JPA)

### AttributeConverter로 자동 암·복호화
```java
@Converter
@Component
@RequiredArgsConstructor
public class EncryptedStringConverter implements AttributeConverter<String, String> {

    private final AesGcmCipher cipher;      // 키는 KMS·Secrets Manager에서 로딩해 빈으로 등록

    @Override
    public String convertToDatabaseColumn(String attribute) {
        return attribute == null ? null : cipher.encrypt(attribute);
    }

    @Override
    public String convertToEntityAttribute(String dbData) {
        return dbData == null ? null : cipher.decrypt(dbData);
    }
}
```
```java
@Entity
public class Customer {
    @Id @GeneratedValue
    private Long id;

    @Convert(converter = EncryptedStringConverter.class)
    @Column(length = 512)                    // 암호문은 원문보다 길어짐 (IV + 태그 + Base64)
    private String residentNumber;           // 주민등록번호

    @Column(length = 64)
    private String residentNumberIndex;      // 검색용 블라인드 인덱스 (아래)
}
```
> Spring Boot에서 `@Converter` 클래스는 Hibernate가 스프링 빈으로 생성해 의존성 주입이 가능합니다(Spring의 `SpringBeanContainer` 연동). 환경에 따라 동작하지 않으면 생성자 주입 대신 정적 홀더로 키를 넘기세요.

### 암호화된 값으로 검색하기: 블라인드 인덱스
GCM은 같은 값도 매번 다른 암호문이 나오므로 `WHERE resident_number = ?`로 찾을 수 없습니다.

```
저장: residentNumber      = AES-GCM(원문)        → 복호화용
      residentNumberIndex = HMAC-SHA256(키2, 원문) → 검색용 (같은 입력 → 같은 값, 원문 복원 불가)
검색: WHERE resident_number_index = HMAC-SHA256(키2, 입력값)
```
```java
public final class BlindIndex {
    private final SecretKeySpec key;

    public BlindIndex(byte[] keyBytes) {          // 암호화 키와 다른 별도 키
        this.key = new SecretKeySpec(keyBytes, "HmacSHA256");
    }

    public String of(String value) {
        try {
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(key);
            String normalized = value.replace("-", "").trim();     // 형식을 통일한 뒤 계산
            return HexFormat.of().formatHex(mac.doFinal(normalized.getBytes(StandardCharsets.UTF_8)));
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException(e);
        }
    }
}
```
| 한계 | 설명 |
|---|---|
| **정확히 일치**만 검색 | `LIKE '%1234'` 부분 검색 불가 → 필요하면 뒷자리만 별도 인덱스 |
| 값의 종류가 적으면 추측 가능 | 성별·생년처럼 경우의 수가 적은 값은 인덱스를 만들지 않기 |
| 그냥 SHA-256은 안 됨 | 주민번호는 경우의 수가 적어 전부 계산해 볼 수 있음 → **키가 있는 HMAC** 사용 |

### 그 밖의 선택지
| 방식 | 설명 |
|---|---|
| **애플리케이션 암호화** (위 방식) | 가장 흔함, DB 관리자도 원문을 볼 수 없음 |
| DB 암호화 함수 (`AES_ENCRYPT`) | 쿼리에 키가 노출될 수 있음 → 비권장 |
| **TDE** (Transparent Data Encryption), RDS 스토리지 암호화 | 디스크·백업 파일 탈취 대비. **DB에 접속한 사람에게는 평문**으로 보임 |
| 암호화 솔루션 (API·플러그인 방식) | 금융권·공공에서 상용 제품(D'Amo, Petra 등) 사용 |

> 화면·로그에는 **마스킹**해서 보여 줍니다 (`900101-1******`). 복호화는 꼭 필요한 기능에서만, 복호화 이력은 감사 로그로 남깁니다.

## 8. 키 관리

**암호화의 보안은 결국 키를 얼마나 잘 지키느냐에 달려 있습니다.** 암호문과 키가 같이 유출되면 암호화는 의미가 없습니다.

| ❌ 하지 말 것 | ✅ 할 것 |
|---|---|
| 키를 소스 코드·`application.yml`에 작성 | **KMS**, Secrets Manager, Vault에 보관 |
| 키를 Git에 커밋 | 환경 변수·런타임 주입, 접근 권한 최소화 |
| 모든 용도에 같은 키 | **용도별 키 분리** (암호화용, 블라인드 인덱스용, JWT 서명용) |
| 키를 한 번 만들고 영원히 사용 | **주기적 교체** (Key Rotation) |
| 키와 암호문을 같은 DB에 저장 | 분리 보관 |

### 봉투 암호화 (Envelope Encryption) — AWS KMS
```
                KMS (마스터 키, 밖으로 절대 나오지 않음 — HSM 안에 보관)
                 │ ① GenerateDataKey
                 ↓
   평문 데이터 키 + 암호화된 데이터 키
       │                    │
 ② 데이터를 AES로 암호화      │
   (사용 후 평문 키는 메모리에서 폐기)
       ↓                    ↓
   [암호화된 데이터]  +  [암호화된 데이터 키]  → 함께 저장
 
 복호화: 암호화된 데이터 키를 KMS에 보내 복호화(Decrypt) → 그 키로 데이터 복호화
```
- 마스터 키는 KMS 밖으로 나오지 않음 → 키 유출 위험 최소화
- 데이터가 커도 KMS에는 **작은 데이터 키만** 오감 (KMS 요청 크기 제한·비용 절약)
- KMS 사용 이력은 **CloudTrail**에 기록 → 누가 언제 복호화했는지 감사
- S3, EBS, RDS 암호화가 내부적으로 이 방식을 씁니다

### 키 교체 (Key Rotation)
암호문 앞에 **키 버전**을 붙여 두면 새 키로 바꾸면서도 이전 데이터를 읽을 수 있습니다.
```
v1:Base64(IV + 암호문)   ← 예전 키로 암호화된 값
v2:Base64(IV + 암호문)   ← 새 키
복호화: 접두사를 보고 해당 버전의 키 선택 → 배치로 v1 데이터를 v2로 재암호화
```

## 9. 법·규정: 무엇을 암호화해야 하나 (개인정보보호법)

「개인정보의 안전성 확보조치 기준」(개인정보보호위원회 고시, 2023년 개정으로 공공·민간·정보통신서비스 기준 통합) 제7조 요약입니다.

| 구분 | 대상 | 방법 |
|---|---|---|
| **저장 — 인증정보** | **비밀번호**, 생체인식정보 등 | 비밀번호는 **일방향 암호화(해시)** |
| **저장 — 이용자 정보** | **주민등록번호, 여권번호, 운전면허번호, 외국인등록번호, 신용카드번호, 계좌번호**, 생체인식정보 | **양방향 암호화** (안전한 알고리즘) |
| 저장 — 그 외 정보주체의 고유식별정보 | 인터넷 구간·DMZ에 저장 시 | 암호화. 내부망은 **주민등록번호는 반드시**, 나머지는 영향평가·위험도 분석 결과에 따라 |
| **전송** | 인증정보(정보통신망), 개인정보(인터넷 구간) | **TLS 등** 암호화 |
| 업무용 PC·모바일·이동식 저장장치 | 위 정보를 저장할 때 | 암호화 |
| 키 관리 | 일정 규모 이상 처리자 | 키 생성·이용·보관·배포·파기 **절차 수립** |

- "안전한 알고리즘"은 KISA 「암호 알고리즘 및 키 길이 이용 안내서」 등을 참고합니다. (대칭키: AES·ARIA·SEED·LEA, 해시: SHA-256 이상, 공개키: RSA 2048비트 이상 등)
- 금융권은 「전자금융감독규정」, 신용정보법 등 **추가 규정**이 있어 더 엄격합니다.

> 이 표는 학습용 요약입니다. 실제 서비스의 법적 준수 여부는 고시 원문과 회사의 개인정보보호 담당 부서·법무 검토로 확인하세요.

## 10. 면접 질문

1. **인코딩, 암호화, 해시의 차이는?**
   → 인코딩은 키 없이 누구나 되돌릴 수 있는 형식 변환이고, 암호화는 키가 있어야 복호화할 수 있는 기밀성 보호이며, 해시는 원본으로 되돌릴 수 없는 고정 길이 값으로 무결성 확인과 비밀번호 저장에 씁니다.
2. **단방향 암호화와 양방향 암호화는 각각 언제 쓰나요?**
   → 원본이 다시 필요 없고 일치 여부만 확인하는 비밀번호는 단방향(bcrypt 등), 업무상 원본을 다시 봐야 하는 주민번호·계좌번호는 양방향(AES 등)으로 암호화합니다.
3. **대칭키와 비대칭키의 차이와 함께 쓰는 이유는?**
   → 대칭키는 빠르지만 키를 안전하게 공유하기 어렵고, 비대칭키는 키 공유 문제는 없지만 느립니다. 그래서 비대칭키(또는 키 교환)로 대칭키를 공유하고 데이터는 대칭키로 암호화하는 하이브리드 방식을 씁니다.
4. **AES ECB 모드를 쓰면 안 되는 이유는?**
   → 같은 평문 블록이 항상 같은 암호문 블록이 되어 데이터의 패턴이 노출되기 때문입니다. IV를 쓰고 무결성까지 검증하는 GCM을 씁니다.
5. **GCM에서 IV를 재사용하면?**
   → 같은 키·IV 조합에서는 키 스트림이 같아져 평문 관계가 노출되고 인증 태그 위조까지 가능해지므로, 암호화할 때마다 새 랜덤 IV를 써야 합니다.
6. **MAC과 전자서명의 차이는?**
   → MAC은 공유한 대칭키로 무결성과 발신자를 확인하지만 제3자 검증과 부인 방지가 안 되고, 전자서명은 개인키로 서명해 누구나 공개키로 검증할 수 있고 부인 방지가 됩니다.
7. **암호화된 주민번호로 회원을 검색하려면?**
   → 랜덤 IV 때문에 암호문으로는 검색할 수 없으므로, 별도 키로 계산한 HMAC 값을 블라인드 인덱스 컬럼에 저장해 일치 검색에 사용합니다.
8. **봉투 암호화란?**
   → KMS의 마스터 키로 데이터 키를 암호화하고 데이터는 데이터 키로 암호화해, 마스터 키는 KMS 밖으로 나오지 않게 하면서 대용량 데이터를 효율적으로 암호화하는 방식입니다.

## 핵심 정리
- 인코딩(보안 X) / 양방향 암호화(키로 복호화) / 단방향 해시(복원 불가)
- 비밀번호 → bcrypt·Argon2, 주민번호·계좌번호 → **AES-256-GCM**
- AES: **ECB 금지**, GCM = 암호화 + 무결성, **IV는 매번 랜덤**(비밀 아님)
- 비대칭키: 공개키 암호화 / 개인키 서명 / ECDHE 키 교환, RSA 2048+ 또는 ECC, 실제는 하이브리드
- MAC(대칭, 부인 방지 X) vs 전자서명(비대칭, 부인 방지 O), 비교는 상수 시간
- DB: AttributeConverter + **블라인드 인덱스(HMAC)**, 마스킹
- 키: KMS 봉투 암호화, 용도별 분리, 버전 붙여 교체
- 법: 비밀번호 일방향, 고유식별정보·카드·계좌번호 암호화, 전송 구간 암호화
