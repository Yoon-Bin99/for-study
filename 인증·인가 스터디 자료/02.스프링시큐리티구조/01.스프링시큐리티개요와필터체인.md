# 01. Spring Security 개요와 필터 체인

> **학습 목표**
> - Spring Security가 서블릿 필터 기반으로 동작하는 구조(DelegatingFilterProxy → FilterChainProxy → SecurityFilterChain)를 그릴 수 있다.
> - 주요 보안 필터의 순서와 역할을 설명할 수 있다.
> - `SecurityFilterChain` 빈으로 보안 설정을 작성할 수 있다.
> - 여러 개의 필터 체인과 커스텀 필터를 등록할 수 있다.
> - Spring Security 6 → 7의 주요 변경 사항을 안다.

---

## 1. Spring Security란?

Spring 애플리케이션에 **인증, 인가, 공격 방어**(CSRF, 세션 고정, 보안 헤더 등)를 제공하는 프레임워크입니다.

### 버전 정리
| Spring Boot | Spring Security | 비고 |
|---|---|---|
| 2.7 | 5.7 / 5.8 | `WebSecurityConfigurerAdapter` 지원 종료 예고 |
| **3.x** | **6.x** | `WebSecurityConfigurerAdapter` 제거, `authorizeHttpRequests`, Jakarta EE |
| **4.x** | **7.x** | **람다 DSL만 지원**(`and()` 제거), `authorizeRequests` 제거, `PathPatternRequestMatcher`, MFA, Authorization Server 통합 |

> 이 자료의 예제는 **Spring Boot 3(Security 6.x)와 Spring Boot 4(Security 7.x)에서 모두 동작하는 람다 DSL**로 작성했습니다. 인터넷의 오래된 예제(`extends WebSecurityConfigurerAdapter`, `.antMatchers()`, `.and()`)는 현재 버전에서 동작하지 않습니다.

```java
// ❌ 옛날 방식 (Security 5 이하)
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    protected void configure(HttpSecurity http) throws Exception {
        http.csrf().disable().authorizeRequests().antMatchers("/api/**").authenticated().and()...
    }
}

// ✅ 현재 방식 (Security 6, 7)
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth.requestMatchers("/api/**").authenticated());
    return http.build();
}
```

## 2. 왜 필터인가?

```
요청 → [서블릿 컨테이너(Tomcat)의 필터들] → [DispatcherServlet] → [인터셉터] → [Controller]
              ↑ Spring Security는 여기서 동작
```
- **DispatcherServlet에 도달하기 전**에 인증·인가를 처리 → 컨트롤러가 실행되기도 전에 차단
- 정적 리소스, 에러 페이지 등 모든 요청에 일관되게 적용

---

## 3. 전체 구조

```
           서블릿 컨테이너 (Tomcat)
+──────────────────────────────────────────────────────────────────+
|  Filter → Filter → [DelegatingFilterProxy] → Filter → Servlet     |
|                           │ (스프링 빈에게 위임)                     |
+───────────────────────────┼──────────────────────────────────────+
                            ↓
                 [FilterChainProxy]  (빈 이름: springSecurityFilterChain)
                            │ 요청 URL에 맞는 체인 선택
            ┌───────────────┼────────────────────┐
            ↓               ↓                    ↓
  [SecurityFilterChain 1]  [SecurityFilterChain 2]   ...
   securityMatcher: /api/**   securityMatcher: /**
     ├ SecurityContextHolderFilter
     ├ CsrfFilter
     ├ LogoutFilter
     ├ (인증 필터들)
     ├ ExceptionTranslationFilter
     └ AuthorizationFilter
```

| 구성 요소 | 역할 |
|---|---|
| **DelegatingFilterProxy** | 서블릿 컨테이너에 등록된 필터. 실제 일은 **스프링 컨테이너의 빈에게 위임** (서블릿 필터는 스프링 빈을 직접 못 쓰기 때문) |
| **FilterChainProxy** | Spring Security의 진입점. 요청에 맞는 **SecurityFilterChain을 선택**해 실행. 디버깅 시 여기에 중단점 |
| **SecurityFilterChain** | 보안 필터들의 묶음. **여러 개** 정의 가능 (API용, 관리자용) |

## 4. 주요 보안 필터 (실행 순서대로)

| 순서 | 필터 | 역할 |
|---|---|---|
| 1 | `DisableEncodeUrlFilter` | URL에 세션 ID 붙이는 것 방지 |
| 2 | `WebAsyncManagerIntegrationFilter` | 비동기 요청에 SecurityContext 연동 |
| 3 | **`SecurityContextHolderFilter`** | 저장소(세션 등)에서 **SecurityContext를 불러와** `SecurityContextHolder`에 설정 |
| 4 | `HeaderWriterFilter` | 보안 헤더 추가 (X-Frame-Options, X-Content-Type-Options, HSTS 등) |
| 5 | **`CorsFilter`** | CORS 처리 (Preflight 응답) |
| 6 | **`CsrfFilter`** | CSRF 토큰 검증 |
| 7 | `LogoutFilter` | 로그아웃 요청 처리 |
| 8 | `OAuth2AuthorizationRequestRedirectFilter` | 소셜 로그인 시작 (카카오로 리다이렉트) |
| 9 | `OAuth2LoginAuthenticationFilter` | 소셜 로그인 콜백 처리 |
| 10 | **`UsernamePasswordAuthenticationFilter`** | **폼 로그인** (`POST /login`) 처리 |
| 11 | `DefaultLoginPageGeneratingFilter` | 기본 로그인 페이지 생성 |
| 12 | `BearerTokenAuthenticationFilter` | **JWT(Bearer 토큰)** 인증 (Resource Server) |
| 13 | `BasicAuthenticationFilter` | HTTP Basic 인증 |
| 14 | `RequestCacheAwareFilter` | 로그인 전에 가려던 요청 복원 |
| 15 | `SecurityContextHolderAwareRequestFilter` | `request.isUserInRole()` 등 서블릿 API 연동 |
| 16 | `AnonymousAuthenticationFilter` | 인증이 없으면 **익명 사용자**(`AnonymousAuthenticationToken`)로 채움 |
| 17 | `SessionManagementFilter` 등 | 세션 관련 처리 |
| 18 | **`ExceptionTranslationFilter`** | 뒤에서 발생한 **인증·인가 예외를 401/403 응답으로 변환** |
| 19 | **`AuthorizationFilter`** | **인가 검사** (마지막 관문) |

> 설정에 따라 포함되는 필터가 달라집니다. `formLogin()`을 켜야 `UsernamePasswordAuthenticationFilter`가 들어가고, `oauth2ResourceServer()`를 켜야 `BearerTokenAuthenticationFilter`가 들어갑니다.

### 실제 필터 목록 확인하기
```yaml
logging:
  level:
    org.springframework.security: TRACE    # 요청마다 어떤 필터를 거치는지 로그로 출력
```
```
Securing GET /api/orders
Invoking DisableEncodeUrlFilter (1/12)
Invoking SecurityContextHolderFilter (3/12)
...
Invoking AuthorizationFilter (12/12)
```
> 학습할 때 TRACE 로그를 켜 두면 동작 원리를 이해하기 가장 좋습니다. (운영에서는 끄기)

## 5. 아무 설정도 안 하면? (Spring Boot 자동 설정)

`spring-boot-starter-security`만 추가하면:
- **모든 요청에 인증 필요**
- 기본 로그인 페이지(`/login`), 로그아웃(`/logout`)
- HTTP Basic 인증
- 사용자 `user` + **콘솔에 출력되는 랜덤 비밀번호**
- CSRF 방어, 보안 헤더, 세션 고정 방어 활성화

```
Using generated security password: 8e557245-73e2-4286-969a-ff57fe326336
```
→ 직접 `SecurityFilterChain` 빈을 등록하면 기본 설정은 물러납니다.

## 6. SecurityFilterChain 작성

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                         // REST API + 토큰 방식일 때 (→ CSRF 문서)
            .cors(Customizer.withDefaults())                      // CorsConfigurationSource 빈 사용
            .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .formLogin(form -> form.disable())
            .httpBasic(basic -> basic.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**", "/error").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()                     // ★ 기본 거부: 나머지는 인증 필요
            );
        return http.build();
    }
}
```

### 세션 생성 정책
| 정책 | 의미 |
|---|---|
| `IF_REQUIRED` (기본) | 필요하면 세션 생성 |
| `ALWAYS` | 항상 생성 |
| `NEVER` | Spring Security가 만들지는 않지만, 있으면 사용 |
| **`STATELESS`** | **세션을 만들지도 쓰지도 않음** → JWT 방식 |

### 정적 리소스
```java
// 권장: 필터 체인 안에서 permitAll (보안 헤더 등은 계속 적용됨)
.requestMatchers("/css/**", "/js/**", "/images/**", "/favicon.ico").permitAll()
// Spring Boot 제공 유틸
.requestMatchers(PathRequest.toStaticResources().atCommonLocations()).permitAll()
```
> `WebSecurityCustomizer`의 `web.ignoring()`은 **보안 필터 자체를 건너뛰어** 보안 헤더도 빠지므로, 정적 리소스에도 권장되지 않습니다.

## 7. 여러 개의 SecurityFilterChain

API는 JWT(무상태), 관리자 화면은 폼 로그인(세션)처럼 **경로별로 다른 보안 정책**이 필요할 때 씁니다.

```java
@Bean
@Order(1)                                            // 먼저 검사
public SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")                  // ★ 이 체인이 담당할 경로
        .csrf(csrf -> csrf.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth.anyRequest().authenticated());
    return http.build();
}

@Bean
@Order(2)
public SecurityFilterChain webChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
            .requestMatchers("/login").permitAll()
            .anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());       // securityMatcher가 없으면 나머지 전부
    return http.build();
}
```
- FilterChainProxy는 **`@Order` 순서대로 `securityMatcher`를 비교해 처음 일치한 체인 하나만** 실행
- `securityMatcher`(어떤 요청을 이 체인이 맡나) ≠ `requestMatchers`(맡은 요청 중 어떤 권한이 필요하나)

## 8. 커스텀 필터 추가

```java
public class JwtAuthenticationFilter extends OncePerRequestFilter {   // 요청당 한 번만 실행 보장
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        // 토큰 검증 → SecurityContextHolder에 Authentication 설정
        chain.doFilter(request, response);            // ★ 반드시 다음 필터로 넘기기
    }
}
```
```java
http.addFilterBefore(new JwtAuthenticationFilter(jwtProvider), UsernamePasswordAuthenticationFilter.class);
```
| 메서드 | 위치 |
|---|---|
| `addFilterBefore(filter, X.class)` | X 앞에 |
| `addFilterAfter(filter, X.class)` | X 뒤에 |
| `addFilterAt(filter, X.class)` | X와 같은 위치 (X를 대체하지는 않음) |

> ⚠️ **커스텀 필터를 `@Component`로 등록하면 두 번 실행될 수 있습니다.** Spring Boot는 `Filter` 타입 빈을 **서블릿 컨테이너에도 자동 등록**하기 때문입니다. 필터는 빈으로 만들지 말고 `new`로 생성해 넘기거나, 빈으로 만들어야 한다면 `FilterRegistrationBean`으로 자동 등록을 끄세요.
```java
@Bean
public FilterRegistrationBean<JwtAuthenticationFilter> jwtFilterRegistration(JwtAuthenticationFilter filter) {
    FilterRegistrationBean<JwtAuthenticationFilter> reg = new FilterRegistrationBean<>(filter);
    reg.setEnabled(false);       // 서블릿 컨테이너에는 등록하지 않음 (시큐리티 체인에서만 실행)
    return reg;
}
```

## 9. 면접 질문

1. **Spring Security는 어떻게 동작하나요?**
   → 서블릿 필터 기반으로, DelegatingFilterProxy가 요청을 스프링 빈인 FilterChainProxy에 위임하고, FilterChainProxy가 요청에 맞는 SecurityFilterChain의 보안 필터들을 순서대로 실행해 DispatcherServlet 이전에 인증과 인가를 처리합니다.
2. **DelegatingFilterProxy가 필요한 이유는?**
   → 서블릿 컨테이너의 필터는 스프링 컨테이너의 빈을 직접 사용할 수 없으므로, 서블릿 필터로 등록된 프록시가 스프링 빈에 처리를 위임하기 위해서입니다.
3. **securityMatcher와 requestMatchers의 차이는?**
   → securityMatcher는 해당 SecurityFilterChain이 처리할 요청을 고르고, requestMatchers는 그 체인 안에서 경로별 인가 규칙을 정합니다.
4. **커스텀 필터를 @Component로 등록하면 생기는 문제는?**
   → Spring Boot가 서블릿 컨테이너에도 필터로 등록해 시큐리티 체인과 서블릿 체인에서 두 번 실행될 수 있습니다.

## 핵심 정리
- Security 6/7: **`SecurityFilterChain` 빈 + 람다 DSL** (Adapter, antMatchers, and() X)
- DelegatingFilterProxy → **FilterChainProxy** → SecurityFilterChain(들) → 보안 필터
- 핵심 필터: SecurityContextHolderFilter → Cors → Csrf → 인증 필터들 → Anonymous → **ExceptionTranslationFilter → AuthorizationFilter**
- `logging.level.org.springframework.security=TRACE`로 필터 흐름 확인
- 여러 체인: `@Order` + `securityMatcher`, 커스텀 필터: `OncePerRequestFilter` + `addFilterBefore` (@Component 중복 등록 주의)
