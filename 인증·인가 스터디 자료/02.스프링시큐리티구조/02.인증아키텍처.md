# 02. 인증 아키텍처 (Authentication)

> **학습 목표**
> - SecurityContextHolder, SecurityContext, Authentication의 관계를 설명할 수 있다.
> - AuthenticationManager → ProviderManager → AuthenticationProvider로 이어지는 인증 흐름을 그릴 수 있다.
> - UserDetails, UserDetailsService, PasswordEncoder로 DB 기반 로그인을 구현할 수 있다.
> - 컨트롤러에서 현재 로그인 사용자를 꺼내는 방법을 알고, 스레드 전파 문제를 설명할 수 있다.

---

## 1. 핵심 객체

```
SecurityContextHolder        (현재 스레드의 보안 정보 보관함, 기본 ThreadLocal)
 └── SecurityContext
      └── Authentication      (현재 사용자의 인증 정보)
           ├── principal      "누구인가"     → 보통 UserDetails 객체 (또는 사용자 ID)
           ├── credentials    "증명 수단"    → 비밀번호 (인증 후에는 지워짐)
           ├── authorities    "권한 목록"    → [ROLE_USER, ROLE_ADMIN] (GrantedAuthority)
           ├── details        부가 정보      → IP, 세션 ID
           └── authenticated  인증 완료 여부
```

| 객체 | 설명 |
|---|---|
| **SecurityContextHolder** | SecurityContext를 저장하는 곳. 기본 전략은 **ThreadLocal** → 같은 요청(스레드) 안 어디서든 꺼낼 수 있음 |
| **SecurityContext** | Authentication을 담는 그릇 |
| **Authentication** | 인증 **요청**(인증 전: 아이디·비밀번호)이자 인증 **결과**(인증 후: 사용자 정보·권한) |
| **GrantedAuthority** | 권한 하나 (`"ROLE_USER"`, `"order:read"`) |

```java
// 현재 사용자 꺼내기 (어디서든)
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
String username = auth.getName();
Collection<? extends GrantedAuthority> authorities = auth.getAuthorities();

// 직접 설정하기 (JWT 필터 등에서)
SecurityContext context = SecurityContextHolder.createEmptyContext();
context.setAuthentication(authentication);
SecurityContextHolder.setContext(context);
```

### Authentication 구현체
| 구현체 | 사용처 |
|---|---|
| **`UsernamePasswordAuthenticationToken`** | 아이디·비밀번호 로그인, **JWT 필터에서 직접 만들 때도 흔히 사용** |
| `AnonymousAuthenticationToken` | 로그인하지 않은 사용자 |
| `RememberMeAuthenticationToken` | 자동 로그인 |
| `JwtAuthenticationToken` | Resource Server의 JWT 인증 |
| `OAuth2AuthenticationToken` | 소셜 로그인 |

```java
// 인증 전 (요청): authenticated = false
UsernamePasswordAuthenticationToken.unauthenticated(email, rawPassword);
// 인증 후 (결과): authenticated = true, 권한 포함
UsernamePasswordAuthenticationToken.authenticated(principal, null, authorities);
```

## 2. 인증 흐름

```
[UsernamePasswordAuthenticationFilter]  POST /login (username, password)
   │ ① 미인증 토큰 생성: UsernamePasswordAuthenticationToken(username, password)
   ↓
[AuthenticationManager]  (인터페이스, 구현체는 ProviderManager)
   │ ② 등록된 Provider 중 이 토큰을 처리할 수 있는(supports) 것에게 위임
   ↓
[AuthenticationProvider]  (DaoAuthenticationProvider)
   │ ③ UserDetailsService.loadUserByUsername(username) → DB에서 사용자 조회
   │ ④ PasswordEncoder.matches(입력 비밀번호, DB의 해시)
   │ ⑤ 계정 상태 확인 (잠김, 비활성, 만료)
   │ ⑥ 성공 → 인증된 Authentication 반환 (principal = UserDetails, authorities, credentials 제거)
   ↓
[필터]  ⑦ SecurityContextHolder에 저장 + SecurityContextRepository(세션)에 저장
        ⑧ AuthenticationSuccessHandler 호출 (리다이렉트 / JSON 응답)
        실패 시 → AuthenticationFailureHandler
```

| 구성 요소 | 역할 |
|---|---|
| **AuthenticationManager** | `authenticate(Authentication)` 하나만 있는 인터페이스. 인증의 입구 |
| **ProviderManager** | AuthenticationManager의 기본 구현. **여러 Provider를 순서대로** 시도 |
| **AuthenticationProvider** | 실제 인증 로직. `supports()`로 처리 가능한 토큰 타입을 알림 |
| **DaoAuthenticationProvider** | UserDetailsService + PasswordEncoder로 **아이디·비밀번호 인증** |
| **UserDetailsService** | username으로 사용자 정보(UserDetails)를 **조회**하는 인터페이스 → **우리가 구현** |
| **UserDetails** | Spring Security가 이해하는 사용자 정보 형식 |
| **PasswordEncoder** | 비밀번호 비교 |

> **보안 포인트**: 사용자가 없을 때(`UsernameNotFoundException`)도 기본적으로 **`BadCredentialsException`으로 감춰서** "아이디 또는 비밀번호가 틀렸다"고만 응답합니다. 또한 사용자가 없을 때도 비밀번호 해시 비교를 수행해 **응답 시간 차이로 계정 존재 여부를 알아내는 공격**을 막습니다.

## 3. DB 기반 로그인 구현

### Member 엔티티
```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Member {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(nullable = false)
    private String password;            // BCrypt 해시

    @Enumerated(EnumType.STRING)
    private Role role;                  // USER, ADMIN

    private boolean locked;

    public Member(String email, String encodedPassword, Role role) {
        this.email = email;
        this.password = encodedPassword;
        this.role = role;
    }
}

public enum Role { USER, ADMIN }
```

### UserDetails 구현
```java
public class CustomUserDetails implements UserDetails {
    private final Long id;
    private final String email;
    private final String password;
    private final Role role;
    private final boolean locked;

    public CustomUserDetails(Member member) {
        this.id = member.getId();
        this.email = member.getEmail();
        this.password = member.getPassword();
        this.role = member.getRole();
        this.locked = member.isLocked();
    }

    public Long getId() { return id; }

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));   // hasRole("ADMIN")은 ROLE_ADMIN을 찾음
    }

    @Override public String getPassword() { return password; }
    @Override public String getUsername() { return email; }      // 로그인 ID
    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return !locked; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled() { return true; }
}
```
> **엔티티를 principal로 그대로 쓰지 마세요.** 세션에 직렬화되고, 지연 로딩 프록시 문제, 비밀번호 노출 위험이 있습니다. 필요한 값만 담은 별도 객체를 만드세요.

### UserDetailsService 구현
```java
@Service
@RequiredArgsConstructor
public class CustomUserDetailsService implements UserDetailsService {
    private final MemberRepository memberRepository;

    @Override
    @Transactional(readOnly = true)
    public UserDetails loadUserByUsername(String email) throws UsernameNotFoundException {
        Member member = memberRepository.findByEmail(email)
                .orElseThrow(() -> new UsernameNotFoundException("사용자 없음: " + email));
        return new CustomUserDetails(member);
    }
}
```

### 설정
```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    // 로그인 API에서 직접 인증을 호출할 때 필요 (JWT 로그인 등)
    @Bean
    public AuthenticationManager authenticationManager(AuthenticationConfiguration config) throws Exception {
        return config.getAuthenticationManager();
    }
}
```
> `UserDetailsService` 빈과 `PasswordEncoder` 빈이 **각각 하나씩** 있으면, Spring Security가 자동으로 `DaoAuthenticationProvider`를 구성합니다.

### 로그인 API에서 직접 인증 (JSON 로그인)
```java
@RestController
@RequiredArgsConstructor
@RequestMapping("/api/auth")
public class AuthController {
    private final AuthenticationManager authenticationManager;

    @PostMapping("/login")
    public ResponseEntity<?> login(@RequestBody @Valid LoginRequest req) {
        Authentication auth = authenticationManager.authenticate(
                UsernamePasswordAuthenticationToken.unauthenticated(req.email(), req.password()));
        // 실패하면 BadCredentialsException, LockedException 등이 던져짐 → 401 처리
        CustomUserDetails user = (CustomUserDetails) auth.getPrincipal();
        // → 세션 저장 또는 JWT 발급 (→ 03.스프링시큐리티실전)
        return ResponseEntity.ok().build();
    }
}
```

## 4. 커스텀 AuthenticationProvider

아이디·비밀번호 외의 방식(OTP, 사내 SSO, API 키)으로 인증할 때 만듭니다.
(`ApiKeyAuthenticationToken`은 `AbstractAuthenticationToken`을 상속해 직접 만든 토큰 클래스라고 가정합니다.)
```java
@Component
@RequiredArgsConstructor
public class ApiKeyAuthenticationProvider implements AuthenticationProvider {
    private final ApiKeyRepository apiKeyRepository;

    @Override
    public Authentication authenticate(Authentication authentication) throws AuthenticationException {
        String key = (String) authentication.getCredentials();
        ApiClient client = apiKeyRepository.findActiveByKey(key)
                .orElseThrow(() -> new BadCredentialsException("유효하지 않은 API 키"));
        return ApiKeyAuthenticationToken.authenticated(client, List.of(new SimpleGrantedAuthority("ROLE_PARTNER")));
    }

    @Override
    public boolean supports(Class<?> authentication) {
        return ApiKeyAuthenticationToken.class.isAssignableFrom(authentication);   // 이 타입만 처리
    }
}
```

## 5. 컨트롤러에서 현재 사용자 꺼내기

```java
// 1) @AuthenticationPrincipal (권장)
@GetMapping("/api/me")
public MeResponse me(@AuthenticationPrincipal CustomUserDetails user) {
    return new MeResponse(user.getId(), user.getUsername());
}

// 2) Authentication 파라미터
@GetMapping("/api/me2")
public String me2(Authentication authentication) {
    return authentication.getName();
}

// 3) SecurityContextHolder (서비스 계층 등 어디서든)
String email = SecurityContextHolder.getContext().getAuthentication().getName();
```
> 로그인하지 않은 상태(익명)에서 `@AuthenticationPrincipal`은 **null**이 됩니다. 인가 설정으로 막혀 있는지 확인하세요.

> 서비스 계층이 `SecurityContextHolder`에 직접 의존하면 테스트가 어려워집니다. **컨트롤러에서 사용자 ID를 꺼내 서비스 메서드 인자로 넘기는 방식**을 권장합니다.

## 6. 스레드와 SecurityContext

SecurityContextHolder는 **ThreadLocal**이라 **다른 스레드에서는 비어 있습니다.**
```java
@Async
public void sendEmail() {
    SecurityContextHolder.getContext().getAuthentication();   // null!
}
```
해결:
```java
@Bean
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.initialize();
    return new DelegatingSecurityContextAsyncTaskExecutor(executor);   // SecurityContext 전파
}
```
> 더 좋은 방법은 비동기 작업에 **필요한 값(사용자 ID)을 인자로 넘기는 것**입니다.

| 전략 | 설명 |
|---|---|
| `MODE_THREADLOCAL` (기본) | 스레드별 |
| `MODE_INHERITABLETHREADLOCAL` | 자식 스레드에 상속 (스레드 풀에서는 오염 위험) |
| `MODE_GLOBAL` | 애플리케이션 전체 공유 (데스크톱 앱용) |

> 요청이 끝나면 Spring Security가 `SecurityContextHolder`를 비웁니다. 스레드 풀의 스레드를 재사용해도 이전 사용자 정보가 남지 않는 이유입니다.

## 7. 면접 질문

1. **Spring Security의 인증 흐름을 설명해 주세요.**
   → 인증 필터가 요청에서 자격 증명을 꺼내 미인증 Authentication을 만들고 AuthenticationManager(ProviderManager)에 넘기면, 지원하는 AuthenticationProvider가 UserDetailsService로 사용자를 조회하고 PasswordEncoder로 비밀번호를 검증해 인증된 Authentication을 반환하며, 이를 SecurityContextHolder에 저장합니다.
2. **SecurityContextHolder는 어떻게 사용자 정보를 저장하나요?**
   → 기본적으로 ThreadLocal에 저장해 같은 요청을 처리하는 스레드 어디서든 꺼낼 수 있고, 요청이 끝나면 비웁니다.
3. **UserDetailsService의 역할은?**
   → username으로 저장소에서 사용자 정보를 조회해 Spring Security가 이해하는 UserDetails로 반환하는 인터페이스입니다.
4. **@Async 메서드에서 인증 정보가 null인 이유는?**
   → SecurityContext가 ThreadLocal에 저장되어 다른 스레드로 전파되지 않기 때문이며, DelegatingSecurityContextAsyncTaskExecutor를 쓰거나 필요한 값을 인자로 넘깁니다.

## 핵심 정리
- SecurityContextHolder(ThreadLocal) → SecurityContext → Authentication(principal, credentials, authorities)
- 흐름: 인증 필터 → AuthenticationManager(ProviderManager) → AuthenticationProvider(Dao) → UserDetailsService + PasswordEncoder
- 우리가 구현: **UserDetails + UserDetailsService** (권한은 `ROLE_` 접두사)
- JSON 로그인: `AuthenticationConfiguration.getAuthenticationManager()` 빈 → `authenticate()`
- 현재 사용자: `@AuthenticationPrincipal`, 다른 스레드에는 전파 X
