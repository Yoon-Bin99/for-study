# 03. 인가 아키텍처 (Authorization)

> **학습 목표**
> - AuthorizationFilter와 AuthorizationManager가 요청을 인가하는 방식을 설명할 수 있다.
> - `authorizeHttpRequests`의 규칙 순서와 주요 표현식을 사용할 수 있다.
> - Role과 Authority의 차이, 역할 계층을 설명할 수 있다.
> - 메서드 보안(`@PreAuthorize` 등)의 동작 원리(AOP 프록시)와 주의점을 설명할 수 있다.

---

## 1. 인가의 두 단계

```
요청 ──> [AuthorizationFilter]  URL 단위 인가 ("/api/admin/** 은 ADMIN만")
              │ 통과
              ↓
         [DispatcherServlet → Controller]
              ↓
         [@PreAuthorize 프록시]   메서드 단위 인가 ("이 주문의 주인만")
              ↓
         [Service 메서드]
```

| 단계 | 방법 | 적합한 검사 |
|---|---|---|
| **요청 수준** | `authorizeHttpRequests` | 경로·HTTP 메서드 기준의 **큰 틀** (로그인 필요 여부, 관리자 영역) |
| **메서드 수준** | `@PreAuthorize`, `@PostAuthorize` | **세밀한 규칙** (파라미터·반환값·소유자 기반) |

---

## 2. AuthorizationManager

Spring Security 6부터 인가의 중심 인터페이스입니다. (예전 `AccessDecisionManager`·`AccessDecisionVoter`는 7.0에서 별도 모듈로 분리)

```java
@FunctionalInterface
public interface AuthorizationManager<T> {
    // 6.4+ 의 기본 메서드. (6.x 초기의 check()는 7.0에서 제거)
    AuthorizationResult authorize(Supplier<Authentication> authentication, T object);
}
```
- `T`: 보호 대상 (`HttpServletRequest`, 메서드 호출 `MethodInvocation`)
- `Supplier<Authentication>`: 필요할 때만 인증 정보를 꺼냄 (지연 로딩)
- 결과: 허용 / 거부 / 판단 보류

```
[AuthorizationFilter]
   └─> RequestMatcherDelegatingAuthorizationManager
         ├─ "/api/auth/**"   → permitAll
         ├─ "/api/admin/**"  → AuthorityAuthorizationManager(hasRole ADMIN)
         └─ anyRequest       → AuthenticatedAuthorizationManager
   거부되면 AccessDeniedException → ExceptionTranslationFilter가 401/403으로 변환
```

## 3. authorizeHttpRequests

```java
http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/auth/**", "/error").permitAll()
        .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
        .requestMatchers(HttpMethod.POST, "/api/products/**").hasRole("SELLER")
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .requestMatchers("/actuator/health").permitAll()
        .requestMatchers("/actuator/**").hasRole("ADMIN")
        .anyRequest().authenticated()
);
```

### ⚠️ 규칙은 위에서부터 순서대로, 처음 일치한 규칙 하나만 적용
```java
// ❌ 잘못된 순서: /api/admin/** 도 /api/** 에 먼저 걸려 USER도 접근 가능
.requestMatchers("/api/**").hasRole("USER")
.requestMatchers("/api/admin/**").hasRole("ADMIN")

// ✅ 구체적인 규칙을 먼저
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/**").hasRole("USER")
```
→ 항상 **구체적인 것 → 일반적인 것**, 마지막은 **`anyRequest()`** 로 기본 정책 (`authenticated()` 또는 `denyAll()`)

### 주요 규칙
| 메서드 | 의미 |
|---|---|
| `permitAll()` | 누구나 (익명 포함) |
| `denyAll()` | 아무도 |
| `authenticated()` | 로그인한 사용자 (익명 X) |
| `anonymous()` | 로그인하지 **않은** 사용자만 (회원 가입 페이지 등) |
| `hasRole("ADMIN")` | `ROLE_ADMIN` 권한 보유 |
| `hasAnyRole("ADMIN", "MANAGER")` | 그중 하나 |
| `hasAuthority("order:write")` | 정확히 그 권한 문자열 |
| `hasAnyAuthority(...)` | 그중 하나 |
| `access(AuthorizationManager)` | 커스텀 규칙 |
| `fullyAuthenticated()` | Remember-me가 아닌 실제 로그인 |

### 경로 패턴
| 패턴 | 의미 |
|---|---|
| `/api/products` | 정확히 그 경로 |
| `/api/products/*` | 한 단계 (`/api/products/1`) |
| `/api/products/**` | 하위 전체 (`/api/products/1/reviews`) |
| `/api/{id}/orders` | 경로 변수 |

> Spring Security 7은 `PathPatternRequestMatcher`(Spring MVC와 같은 경로 매칭 방식)를 기본으로 씁니다. 6.x에서 쓰던 `AntPathRequestMatcher`, `MvcRequestMatcher`는 제거되었습니다. 문자열로 `requestMatchers("/api/**")`를 쓰면 두 버전 모두 동작합니다.

### `/error` 경로를 허용하는 이유
Spring Security 6부터 인가는 **모든 디스패치 타입**(REQUEST, ERROR, FORWARD)에 적용됩니다. 컨트롤러에서 예외가 나서 `/error`로 포워드될 때 그 경로가 막혀 있으면, **실제 오류(400, 500) 대신 401·403이 응답되어 원인 파악이 어려워집니다.**
```java
.requestMatchers("/error").permitAll()
// 또는
.dispatcherTypeMatchers(DispatcherType.ERROR, DispatcherType.FORWARD).permitAll()
```

### 커스텀 규칙
```java
.requestMatchers("/api/internal/**").access((authentication, context) ->
        new AuthorizationDecision(context.getRequest().getRemoteAddr().startsWith("10.0.")))
```

## 4. Role vs Authority

| 구분 | Role | Authority |
|---|---|---|
| 실체 | **`ROLE_` 접두사가 붙은 Authority** | 권한 문자열 그 자체 |
| 저장 | `"ROLE_ADMIN"` | `"order:write"`, `"SCOPE_read"` |
| 검사 | `hasRole("ADMIN")` → 내부적으로 `"ROLE_ADMIN"` 비교 | `hasAuthority("order:write")` |
| 의미 | 큰 단위 역할 (관리자, 판매자) | 세밀한 권한 (주문 쓰기) |

```java
new SimpleGrantedAuthority("ROLE_ADMIN");    // hasRole("ADMIN") ✅, hasAuthority("ROLE_ADMIN") ✅
new SimpleGrantedAuthority("ADMIN");         // hasRole("ADMIN") ❌  ← 흔한 실수!
```

> OAuth2 Resource Server는 JWT의 `scope` 클레임을 **`SCOPE_` 접두사**를 붙인 Authority로 변환합니다. (`scope: "read"` → `SCOPE_read`)

### 역할 계층 (Role Hierarchy)
"ADMIN은 USER가 할 수 있는 것을 모두 할 수 있다"를 표현합니다.
```java
@Bean
static RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.fromHierarchy("""
            ROLE_ADMIN > ROLE_MANAGER
            ROLE_MANAGER > ROLE_USER
            """);
}
```
→ ADMIN은 `hasRole("USER")` 규칙도 통과합니다. (`fromHierarchy`는 Spring Security 6.3+)

`authorizeHttpRequests`는 등록된 `RoleHierarchy` 빈을 사용합니다. 메서드 보안(`@PreAuthorize`)에도 적용하려면 공식 문서대로 표현식 핸들러에 연결합니다.
```java
@Bean
static MethodSecurityExpressionHandler methodSecurityExpressionHandler(RoleHierarchy roleHierarchy) {
    DefaultMethodSecurityExpressionHandler handler = new DefaultMethodSecurityExpressionHandler();
    handler.setRoleHierarchy(roleHierarchy);
    return handler;
}
```

## 5. 메서드 보안 (Method Security)

```java
@Configuration
@EnableMethodSecurity      // prePostEnabled = true 기본 (Spring Security 6+)
public class MethodSecurityConfig { }
```

| 애노테이션 | 시점 | 예 |
|---|---|---|
| **`@PreAuthorize`** | 메서드 **실행 전** | `@PreAuthorize("hasRole('ADMIN')")` |
| `@PostAuthorize` | 실행 **후 반환값**으로 판단 | `@PostAuthorize("returnObject.ownerId == authentication.principal.id")` |
| `@PreFilter` / `@PostFilter` | 컬렉션 인자·반환값 필터링 | `@PostFilter("filterObject.ownerId == authentication.principal.id")` |
| `@Secured("ROLE_ADMIN")` | 실행 전 (SpEL 없음) | `securedEnabled = true` 필요 |
| `@RolesAllowed("ADMIN")` | JSR-250 표준 | `jsr250Enabled = true` 필요 |

### SpEL 표현식
```java
@PreAuthorize("hasRole('ADMIN')")
public void deleteMember(Long memberId) { ... }

@PreAuthorize("#memberId == authentication.principal.id or hasRole('ADMIN')")   // 본인 또는 관리자
public MemberResponse getMember(Long memberId) { ... }

@PreAuthorize("@orderAuthz.isOwner(#orderId, authentication)")                  // 빈 메서드 호출
public OrderResponse getOrder(Long orderId) { ... }
```
| 표현 | 의미 |
|---|---|
| `authentication` | 현재 Authentication |
| `principal` | `authentication.principal` |
| `#파라미터명` | 메서드 인자 (컴파일 시 `-parameters` 옵션 필요, Spring Boot Gradle 기본 활성) |
| `returnObject` | 반환값 (`@PostAuthorize`) |
| `@빈이름.메서드()` | 스프링 빈 호출 |

### 동작 원리: AOP 프록시
```
Controller → [프록시: @PreAuthorize 검사] → 실제 Service 메서드
                  ↓ 거부
            AccessDeniedException
```
→ `@Transactional`과 같은 **프록시 기반**이라 같은 한계가 있습니다.

| 주의 | 이유 |
|---|---|
| **같은 클래스 내부 호출(`this.method()`)은 검사되지 않음** | 프록시를 거치지 않음 |
| `private` 메서드에는 적용 X | 프록시가 가로챌 수 없음 |
| `@PostAuthorize`는 **이미 실행된 후** 판단 | 데이터 변경 메서드에 쓰면 변경은 이미 일어남 → **조회에만** |

## 6. 요청 수준 vs 메서드 수준 어디에?

| 상황 | 위치 |
|---|---|
| 로그인 필요 여부, 공개 API | **요청 수준** |
| 관리자 영역 전체 (`/admin/**`) | **요청 수준** |
| **본인 리소스만** (주문, 게시글 수정) | **메서드 수준** 또는 서비스 로직 |
| 같은 URL인데 역할마다 다른 동작 | 메서드 수준 / 서비스 로직 |

> **둘 다 쓰는 것이 안전**합니다(심층 방어). 요청 수준은 "누구나 들어오는 문"을 막고, 메서드 수준은 "들어와서 남의 것을 건드리는 것"을 막습니다. (→ `03.스프링시큐리티실전/06.권한설계와메서드보안.md`)

## 7. 면접 질문

1. **Spring Security에서 인가는 어떻게 처리되나요?**
   → AuthorizationFilter가 요청에 매칭되는 AuthorizationManager로 접근 허용 여부를 판단하고, 거부되면 AccessDeniedException을 던져 ExceptionTranslationFilter가 401 또는 403으로 응답합니다. 메서드 수준은 @PreAuthorize 같은 애노테이션을 AOP 프록시가 검사합니다.
2. **requestMatchers 순서가 중요한 이유는?**
   → 위에서부터 처음 일치한 규칙 하나만 적용되므로, 넓은 패턴이 먼저 오면 뒤의 구체적인 규칙이 무시되기 때문입니다.
3. **hasRole과 hasAuthority의 차이는?**
   → hasRole은 ROLE_ 접두사를 자동으로 붙여 비교하고, hasAuthority는 권한 문자열을 그대로 비교합니다.
4. **@PreAuthorize가 동작하지 않는 경우는?**
   → @EnableMethodSecurity가 없거나, 같은 클래스 안에서 내부 호출하거나, private 메서드인 경우입니다. 프록시를 거치지 않기 때문입니다.

## 핵심 정리
- 인가 = 요청 수준(`authorizeHttpRequests`, AuthorizationFilter) + 메서드 수준(`@PreAuthorize`, AOP)
- 중심 인터페이스: **AuthorizationManager** (`authorize`)
- 규칙은 **위에서부터 첫 일치**, 구체적 → 일반적, 마지막 `anyRequest()`
- `/error` 허용 (안 하면 실제 에러가 401/403으로 가려짐)
- Role = `ROLE_` 접두사 Authority, 역할 계층 `RoleHierarchyImpl.fromHierarchy`
- 메서드 보안은 프록시 → 내부 호출·private 불가, @PostAuthorize는 조회에만
