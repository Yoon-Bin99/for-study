# 03. 리프레시 토큰, 재발급, 로그아웃

> **학습 목표**
> - Refresh Token을 Redis에 저장하고 재발급 API를 구현할 수 있다.
> - Refresh Token Rotation과 재사용 탐지를 구현할 수 있다.
> - 로그아웃 시 Refresh Token 삭제와 Access Token 블랙리스트를 구현할 수 있다.
> - Refresh Token을 HttpOnly 쿠키로 전달할 수 있다.

---

## 1. 설계

```
로그인        → Access(30분, JWT) + Refresh(14일, 랜덤 문자열)
               Refresh는 HttpOnly 쿠키로, Redis에 해시로 저장

API 호출      → Authorization: Bearer <Access>
Access 만료   → 401 TOKEN_EXPIRED
재발급        → POST /api/auth/reissue (쿠키의 Refresh)
               Redis에서 확인 → 기존 Refresh 폐기 → 새 Access + 새 Refresh (Rotation)
재사용 감지    → 이미 폐기된 Refresh가 다시 오면 → 탈취로 보고 그 사용자의 모든 Refresh 삭제
로그아웃       → Refresh 삭제 + Access의 jti를 남은 유효 시간만큼 블랙리스트
```

### Refresh Token을 JWT로 만들어야 할까?
| 방식 | 장단점 |
|---|---|
| JWT | 자체 만료 정보 포함 / 어차피 서버 저장소에서 확인해야 하므로 이점이 적음 |
| **불투명 랜덤 문자열** (이 문서) | 단순, 노출돼도 정보 없음, **서버 저장소가 유일한 진실** |

### Redis 키 설계
| 키 | 값 | TTL | 용도 |
|---|---|---|---|
| `refresh:{SHA256(token)}` | memberId | 14일 | 유효한 Refresh |
| `refresh:used:{SHA256(token)}` | memberId | 14일 | 이미 사용(교체)된 Refresh → **재사용 탐지** |
| `refresh:member:{memberId}` | Set of 해시 | 14일 | 사용자의 모든 Refresh (전체 로그아웃) |
| `blacklist:{jti}` | "logout" | Access 남은 시간 | 로그아웃된 Access |

> 토큰 원문이 아니라 **해시를 키로 저장**하면 Redis 내용이 유출돼도 토큰으로 쓸 수 없습니다.

## 2. RefreshTokenService

```java
@Service
@RequiredArgsConstructor
public class RefreshTokenService {

    private static final String KEY = "refresh:";
    private static final String USED_KEY = "refresh:used:";
    private static final String MEMBER_KEY = "refresh:member:";

    private final StringRedisTemplate redis;
    private final JwtProperties properties;
    private final SecureRandom random = new SecureRandom();

    /** 새 Refresh Token 발급 (원문은 클라이언트에게만, 서버에는 해시만 저장) */
    public String issue(Long memberId) {
        byte[] bytes = new byte[32];
        random.nextBytes(bytes);
        String token = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
        String hash = sha256(token);
        Duration ttl = properties.refreshTokenValidity();

        redis.opsForValue().set(KEY + hash, memberId.toString(), ttl);
        redis.opsForSet().add(MEMBER_KEY + memberId, hash);
        redis.expire(MEMBER_KEY + memberId, ttl);
        return token;
    }

    /** Rotation: 기존 토큰을 폐기하고 memberId 반환. 재사용이 감지되면 전체 폐기 */
    public Long rotate(String token) {
        String hash = sha256(token);
        String memberId = redis.opsForValue().getAndDelete(KEY + hash);   // 원자적으로 조회 + 삭제

        if (memberId == null) {
            String reusedBy = redis.opsForValue().get(USED_KEY + hash);
            if (reusedBy != null) {
                revokeAll(Long.valueOf(reusedBy));          // ★ 탈취 의심: 해당 사용자 전체 로그아웃
            }
            throw new BadCredentialsException("유효하지 않은 Refresh Token");
        }

        redis.opsForValue().set(USED_KEY + hash, memberId, properties.refreshTokenValidity());
        redis.opsForSet().remove(MEMBER_KEY + memberId, hash);
        return Long.valueOf(memberId);
    }

    public void revoke(String token) {
        String hash = sha256(token);
        String memberId = redis.opsForValue().getAndDelete(KEY + hash);
        if (memberId != null) {
            redis.opsForSet().remove(MEMBER_KEY + memberId, hash);
        }
    }

    /** 모든 기기에서 로그아웃 (비밀번호 변경, 탈취 의심 시) */
    public void revokeAll(Long memberId) {
        Set<String> hashes = redis.opsForSet().members(MEMBER_KEY + memberId);
        if (hashes != null && !hashes.isEmpty()) {
            redis.delete(hashes.stream().map(h -> KEY + h).toList());
        }
        redis.delete(MEMBER_KEY + memberId);
    }

    private static String sha256(String value) {
        try {
            byte[] digest = MessageDigest.getInstance("SHA-256").digest(value.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(digest);
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
```

> `getAndDelete`(Redis `GETDEL`, Redis 6.2+)로 **조회와 삭제를 원자적으로** 처리해야, 같은 Refresh로 동시에 두 번 재발급 요청이 와도 하나만 성공합니다.

> 네트워크 문제로 클라이언트가 새 토큰을 받지 못하고 이전 토큰으로 재시도하면 재사용으로 오인될 수 있습니다. 엄격한 서비스는 이를 감수하고, 일부 서비스는 수 초의 유예 시간을 둡니다.

## 3. Access Token 블랙리스트

```java
@Component
@RequiredArgsConstructor
public class AccessTokenBlacklist {
    private static final String KEY = "blacklist:";
    private final StringRedisTemplate redis;

    public void add(String jti, Instant expiresAt) {
        Duration remaining = Duration.between(Instant.now(), expiresAt);
        if (!remaining.isNegative() && !remaining.isZero()) {
            redis.opsForValue().set(KEY + jti, "logout", remaining);   // 만료되면 자동 삭제
        }
    }

    public boolean contains(String jti) {
        return Boolean.TRUE.equals(redis.hasKey(KEY + jti));
    }
}
```

필터에 블랙리스트 확인 추가:
```java
// JwtAuthenticationFilter 안
Claims claims = jwtTokenProvider.parse(token);
if (blacklist.contains(claims.getId())) {
    request.setAttribute("auth.error", "LOGGED_OUT_TOKEN");
} else {
    SecurityContextHolder.getContext().setAuthentication(jwtTokenProvider.getAuthentication(claims));
}
```
(`JwtTokenProvider`에 `Claims`를 받는 `getAuthentication(Claims)` 오버로드를 추가합니다.)

> 블랙리스트를 쓰면 요청마다 Redis를 조회하므로 "완전한 무상태"는 아닙니다. 하지만 **로그아웃된 토큰만** 저장하므로 세션보다 훨씬 가볍습니다. Access Token 수명이 충분히 짧다면(5~10분) 블랙리스트 없이 Refresh 삭제만으로 운영하기도 합니다.

## 4. 쿠키로 Refresh Token 전달

```java
@Component
@RequiredArgsConstructor
public class RefreshTokenCookie {
    public static final String NAME = "refresh_token";
    private final JwtProperties properties;

    public ResponseCookie create(String token) {
        return ResponseCookie.from(NAME, token)
                .httpOnly(true)                  // JS 접근 차단 (XSS)
                .secure(true)                    // HTTPS만 (로컬 개발 시 프로필로 분리)
                .sameSite("Strict")              // 다른 사이트 요청에 전송 X (CSRF)
                .path("/api/auth")               // 재발급·로그아웃 API에만 전송
                .maxAge(properties.refreshTokenValidity())
                .build();
    }

    public ResponseCookie delete() {
        return ResponseCookie.from(NAME, "").httpOnly(true).secure(true)
                .sameSite("Strict").path("/api/auth").maxAge(0).build();
    }
}
```

## 5. AuthController 완성

```java
public record AccessTokenResponse(String accessToken) { }
```

```java
@RestController
@RequiredArgsConstructor
@RequestMapping("/api/auth")
public class AuthController {

    private final AuthService authService;
    private final RefreshTokenCookie refreshTokenCookie;

    @PostMapping("/login")
    public ResponseEntity<AccessTokenResponse> login(@RequestBody @Valid LoginRequest req) {
        TokenResponse tokens = authService.login(req);
        return ResponseEntity.ok()
                .header(HttpHeaders.SET_COOKIE, refreshTokenCookie.create(tokens.refreshToken()).toString())
                .body(new AccessTokenResponse(tokens.accessToken()));        // Access만 바디로
    }

    @PostMapping("/reissue")
    public ResponseEntity<AccessTokenResponse> reissue(
            @CookieValue(name = RefreshTokenCookie.NAME, required = false) String refreshToken) {
        if (refreshToken == null) {
            throw new BadCredentialsException("Refresh Token 없음");
        }
        TokenResponse tokens = authService.reissue(refreshToken);
        return ResponseEntity.ok()
                .header(HttpHeaders.SET_COOKIE, refreshTokenCookie.create(tokens.refreshToken()).toString())
                .body(new AccessTokenResponse(tokens.accessToken()));
    }

    @PostMapping("/logout")
    public ResponseEntity<Void> logout(
            @RequestHeader(value = HttpHeaders.AUTHORIZATION, required = false) String authorization,
            @CookieValue(name = RefreshTokenCookie.NAME, required = false) String refreshToken) {
        authService.logout(authorization, refreshToken);
        return ResponseEntity.noContent()
                .header(HttpHeaders.SET_COOKIE, refreshTokenCookie.delete().toString())
                .build();
    }
}
```

```java
// AuthService에 추가
private final MemberRepository memberRepository;
private final AccessTokenBlacklist blacklist;

public TokenResponse reissue(String refreshToken) {
    Long memberId = refreshTokenService.rotate(refreshToken);
    Member member = memberRepository.findById(memberId)
            .orElseThrow(() -> new BadCredentialsException("사용자 없음"));
    if (member.isLocked()) {
        throw new LockedException("잠긴 계정");          // 재발급 시 계정 상태 재확인
    }
    return new TokenResponse(
            jwtTokenProvider.createAccessToken(member.getId(), member.getRole()),   // 최신 권한 반영
            refreshTokenService.issue(member.getId()));
}

public void logout(String authorization, String refreshToken) {
    if (refreshToken != null) {
        refreshTokenService.revoke(refreshToken);
    }
    if (authorization != null && authorization.startsWith("Bearer ")) {
        try {
            Claims claims = jwtTokenProvider.parse(authorization.substring(7));
            blacklist.add(claims.getId(), claims.getExpiration().toInstant());
        } catch (JwtException e) {
            // 이미 만료·무효한 토큰이면 블랙리스트 불필요
        }
    }
}
```
> 재발급 시점에 **DB에서 계정 상태와 권한을 다시 읽어** 새 Access Token에 반영합니다. 권한 변경이나 계정 정지가 늦어도 Access Token 수명 안에 반영됩니다.

## 6. 프론트엔드 처리 흐름

```
1. 로그인 → accessToken을 메모리(변수, 상태 관리)에 저장, refresh는 쿠키(브라우저가 관리)
2. API 요청마다 Authorization 헤더에 accessToken
3. 401 + TOKEN_EXPIRED 응답 → POST /api/auth/reissue (credentials: 'include')
     → 성공: 새 accessToken으로 원래 요청 재시도
     → 실패: 로그인 화면으로
4. 새로고침 → 메모리가 비었으므로 앱 시작 시 reissue 호출로 복구
```
- 동시에 여러 요청이 401을 받으면 **재발급은 한 번만** 하도록 큐잉 (재발급 요청이 여러 번 가면 Rotation 때문에 재사용 탐지에 걸릴 수 있음)
- 다른 도메인(api.example.com ↔ app.example.com)이면 CORS `allowCredentials(true)` 필요 (→ `07.CORS와CSRF설정.md`)

## 7. 면접 질문

1. **Refresh Token Rotation이란? 왜 필요한가요?**
   → 재발급할 때마다 Refresh Token도 새로 발급하고 이전 것을 폐기하는 방식으로, 탈취된 토큰의 유효 기간을 줄이고 이미 폐기된 토큰이 다시 사용되면 탈취로 판단해 전체 세션을 무효화할 수 있습니다.
2. **JWT 로그아웃은 어떻게 구현하나요?**
   → 서버에 저장된 Refresh Token을 삭제해 재발급을 막고, 아직 유효한 Access Token은 jti를 남은 유효 시간 동안 Redis 블랙리스트에 넣어 필터에서 거부합니다.
3. **Refresh Token을 Redis에 해시로 저장하는 이유는?**
   → 저장소가 유출되어도 원문 토큰을 알 수 없어 재사용할 수 없게 하기 위해서입니다.
4. **Refresh Token을 HttpOnly 쿠키로 주는 이유는?**
   → 자바스크립트로 읽을 수 없어 XSS로 탈취되지 않고, SameSite와 Path 제한으로 필요한 요청에만 전송되게 하기 위해서입니다.

## 핵심 정리
- Refresh = 랜덤 문자열, Redis에 **해시**로 저장, TTL
- 재발급: `getAndDelete`로 원자적 폐기 → 새 Access + 새 Refresh (**Rotation**), 폐기된 토큰 재사용 → **전체 폐기**
- 로그아웃: Refresh 삭제 + Access jti 블랙리스트(남은 시간 TTL)
- 쿠키: HttpOnly + Secure + SameSite=Strict + Path=/api/auth
- 재발급 시 DB에서 계정 상태·권한 재확인
