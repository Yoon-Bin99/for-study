# 06. 권한 설계와 메서드 보안

> **학습 목표**
> - 역할(Role)과 세부 권한(Permission)을 DB로 설계할 수 있다.
> - "본인 리소스만 접근" 규칙을 안전하게 구현할 수 있다(IDOR 방지).
> - `@PreAuthorize`와 권한 검사 빈, 커스텀 애노테이션으로 권한 로직을 정리할 수 있다.
> - 권한 검사를 어느 계층에 둘지 판단할 수 있다.

---

## 1. 권한 모델 고르기

| 규모 | 모델 | 예 |
|---|---|---|
| 작은 서비스 | **역할 enum 하나** (USER, ADMIN) | `Member.role` |
| 관리자 기능이 많음 | **역할 + 세부 권한** (RBAC) | ADMIN: `member:read`, `member:delete`, `notice:write` |
| 조직·팀 단위 | 리소스별 역할 | 프로젝트 A에서는 OWNER, B에서는 VIEWER |
| 매우 복잡 | 정책 엔진 (ABAC) | OPA, Cedar, AWS Verified Permissions |

### RBAC 테이블 설계
```
member ──< member_role >── role ──< role_permission >── permission
                            ADMIN                       member:read
                            MANAGER                     member:delete
                            USER                        order:read ...
```
```java
// UserDetails.getAuthorities(): 역할과 권한을 모두 넣기
List<GrantedAuthority> authorities = new ArrayList<>();
for (Role role : member.getRoles()) {
    authorities.add(new SimpleGrantedAuthority("ROLE_" + role.getName()));          // hasRole
    role.getPermissions().forEach(p -> authorities.add(new SimpleGrantedAuthority(p.getName())));  // hasAuthority
}
```
```java
.requestMatchers(HttpMethod.DELETE, "/api/admin/members/**").hasAuthority("member:delete")
```
> 권한이 많으면 JWT에 전부 넣지 말고 **역할만 넣은 뒤 서버에서 역할 → 권한으로 펼치는** 것이 토큰 크기와 변경 반영에 유리합니다.

## 2. 가장 중요한 규칙: 본인 리소스만 (IDOR 방지)

```
GET /api/orders/42   ← 내 주문
GET /api/orders/43   ← 남의 주문인데 보이면? → 취약점 (IDOR)
```
URL 수준 인가(`authenticated()`)는 "로그인했는가"만 확인합니다. **이 주문이 이 사용자의 것인지**는 별도로 검사해야 합니다.

### 방법 1: 조회 쿼리에 소유자 조건 포함 (가장 확실)
```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    Optional<Order> findByIdAndMemberId(Long id, Long memberId);
}

@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;

    @Transactional(readOnly = true)
    public OrderResponse getMyOrder(Long orderId, Long memberId) {
        Order order = orderRepository.findByIdAndMemberId(orderId, memberId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));     // ★ 남의 것이면 404
        return OrderResponse.from(order);
    }
}

@GetMapping("/api/orders/{orderId}")
public OrderResponse getOrder(@PathVariable Long orderId, @AuthenticationPrincipal AuthMember member) {
    return orderService.getMyOrder(orderId, member.id());
}
```
> 남의 리소스에 403 대신 **404를 주면** "그 ID의 리소스가 존재한다"는 정보도 숨길 수 있습니다.

### 방법 2: 권한 검사 빈 + @PreAuthorize
관리자는 모두 볼 수 있고 일반 사용자는 본인 것만 보는 식의 규칙에 좋습니다.
```java
@Component("orderAuthz")
@RequiredArgsConstructor
public class OrderAuthorization {
    private final OrderRepository orderRepository;

    public boolean isOwner(Long orderId, Authentication authentication) {
        if (!(authentication.getPrincipal() instanceof AuthMember member)) {
            return false;
        }
        return orderRepository.existsByIdAndMemberId(orderId, member.id());
    }
}
```
```java
@PreAuthorize("hasRole('ADMIN') or @orderAuthz.isOwner(#orderId, authentication)")
@Transactional(readOnly = true)
public OrderResponse getOrder(Long orderId) { ... }
```

### 방법 3: 도메인 객체가 스스로 검사
```java
public class Post {
    public void edit(Long requesterId, String title, String content) {
        if (!this.authorId.equals(requesterId)) {
            throw new AccessDeniedException("본인 글만 수정할 수 있습니다.");
        }
        this.title = title;
        this.content = content;
    }
}
```
→ 어디서 호출하든 규칙이 지켜집니다 (서비스 우회 불가).

| 방법 | 장점 | 단점 |
|---|---|---|
| **쿼리 조건** | 누락 위험 낮음, 정보 노출 없음 | 관리자 예외 처리가 별도 |
| @PreAuthorize + 빈 | 선언적, 관리자 규칙 조합 쉬움 | 추가 쿼리, 내부 호출 시 미적용 |
| 도메인 검사 | 규칙이 도메인에 응집 | 조회 후 검사 |

## 3. 메서드 보안 활용

```java
@Configuration
@EnableMethodSecurity
public class MethodSecurityConfig { }
```

### 예제 모음
```java
@Service
public class AdminMemberService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteMember(Long memberId) { ... }

    @PreAuthorize("hasAuthority('member:read')")
    public Page<MemberResponse> search(MemberSearchCondition cond, Pageable pageable) { ... }

    // 반환값 기반 (조회에만 사용 — 실행 후 판단)
    @PostAuthorize("returnObject.authorId == authentication.principal.id or hasRole('ADMIN')")
    public PostDetailResponse getPrivatePost(Long postId) { ... }
}
```

### 커스텀 메타 애노테이션으로 중복 줄이기
```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("hasRole('ADMIN')")
public @interface AdminOnly { }

@AdminOnly
public void deleteMember(Long memberId) { ... }
```
Spring Security 6.3+는 **템플릿 파라미터**도 지원합니다.
```java
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("hasAuthority('{value}')")
public @interface HasPermission { String value(); }

@Bean
static AnnotationTemplateExpressionDefaults templateExpressionDefaults() {   // 6.4+ (6.3은 PrePostTemplateDefaults)
    return new AnnotationTemplateExpressionDefaults();
}

@HasPermission("member:delete")
public void deleteMember(Long memberId) { ... }
```

### 클래스 전체에 적용
```java
@Service
@PreAuthorize("hasRole('ADMIN')")          // 모든 public 메서드에 적용
public class AdminStatisticsService { ... }
```

## 4. 권한 검사는 어느 계층에?

```
[URL 인가]          로그인 필요? 관리자 영역?            ← 큰 문 (SecurityFilterChain)
[Controller]        사용자 ID를 인증 정보에서 꺼냄         ← 입력 신뢰 경계
[Service]           @PreAuthorize, 소유자 검사          ← ★ 핵심 규칙
[Repository/Query]  WHERE member_id = ?                 ← 데이터 접근 제한
[Domain]            객체 스스로 규칙 검사                 ← 마지막 방어선
```

| 원칙 | 설명 |
|---|---|
| **서비스 계층에서 강제** | 컨트롤러만 검사하면 다른 진입점(배치, 메시지 리스너, 다른 컨트롤러)에서 우회됨 |
| 프론트 검사는 UX일 뿐 | 버튼을 숨겨도 API는 호출 가능 |
| 사용자 ID는 인증 정보에서만 | 요청 파라미터의 memberId를 믿지 않기 |
| 목록 조회도 필터링 | 단건만 막고 목록 API에서 남의 데이터가 섞여 나오는 실수 주의 |
| 일괄 작업 주의 | `DELETE /api/posts?ids=1,2,3` 에서 각 ID의 소유자를 모두 확인 |

## 5. 관리자 기능 보안 체크리스트

- [ ] 관리자 API는 경로를 분리 (`/api/admin/**`) + `hasRole('ADMIN')`
- [ ] 가능하면 **사내망·VPN·IP 제한**, 별도 도메인
- [ ] 관리자 계정은 **MFA**
- [ ] 관리자 작업은 **감사 로그**(누가, 언제, 무엇을, 이전 값 → 새 값)
- [ ] 역할 부여·변경 API 자체도 최고 권한만
- [ ] 자기 자신의 권한을 올리는 요청 차단 (`PATCH /api/members/me {role: ADMIN}` 같은 **Mass Assignment** 방지 → 요청 DTO에 role 필드를 두지 않기)

## 6. 면접 질문

1. **IDOR란? 어떻게 막나요?**
   → 요청의 리소스 ID만 바꿔 다른 사용자의 데이터에 접근하는 취약점으로, 인증 정보의 사용자 ID로 소유자 조건을 걸어 조회하거나 서비스 계층에서 소유자 검사를 수행해 막습니다.
2. **권한 검사를 컨트롤러가 아닌 서비스 계층에서 해야 하는 이유는?**
   → 서비스는 여러 컨트롤러, 배치, 메시지 리스너 등 다양한 진입점에서 호출되므로, 서비스에서 강제해야 우회되지 않기 때문입니다.
3. **@PreAuthorize에서 소유자 검사를 하려면?**
   → 소유 여부를 확인하는 스프링 빈 메서드를 만들고 `@PreAuthorize("@빈이름.isOwner(#id, authentication)")`처럼 SpEL로 호출합니다.

## 핵심 정리
- 작으면 역할 enum, 커지면 역할 + 권한(RBAC), 토큰엔 역할만
- **IDOR 방지 = 소유자 검사**: `findByIdAndMemberId` / `@PreAuthorize("@authz.isOwner(...)")` / 도메인 검사
- 메서드 보안: `@PreAuthorize`, 메타 애노테이션(`@AdminOnly`), 클래스 단위 적용
- 서비스 계층에서 강제, 사용자 ID는 인증 정보에서만, Mass Assignment 주의
