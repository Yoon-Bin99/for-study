# 07. CORS와 CSRF 설정

> **학습 목표**
> - CORS 에러의 원인과 Spring Security에서 CORS를 올바르게 설정하는 방법을 설명할 수 있다.
> - CSRF 공격 원리와 CSRF 보호를 꺼도 되는 경우·안 되는 경우를 구분할 수 있다.
> - 쿠키 기반 SPA에서 CSRF 토큰을 설정할 수 있다.
> - Spring Security가 추가하는 보안 헤더를 설명할 수 있다.

# Part 1. CORS

## 1. 복습: 출처와 CORS

- **출처(Origin) = 스킴 + 호스트 + 포트** (`http://localhost:3000` ≠ `http://localhost:8080`)
- 브라우저는 다른 출처로의 요청 응답을 JS에 넘겨주지 않음 (SOP)
- 서버가 `Access-Control-Allow-Origin` 등의 헤더로 허용해야 함
- `Authorization` 헤더나 `Content-Type: application/json`을 쓰면 **Preflight(OPTIONS)** 요청이 먼저 감

## 2. Spring Security에서 CORS가 실패하는 흔한 이유

```
브라우저 → OPTIONS /api/orders (Preflight, Authorization 헤더 없음!)
        → Spring Security: "인증 안 된 요청이네" → 401
        → 브라우저: CORS 에러
```
Preflight 요청에는 **인증 정보가 실리지 않기 때문에**, CORS 처리가 시큐리티 인가보다 **먼저** 되어야 합니다. `http.cors()`를 켜면 `CorsFilter`가 앞쪽에서 Preflight를 처리합니다.

> Spring MVC의 `WebMvcConfigurer.addCorsMappings()`만 설정하면 DispatcherServlet 단계라서 **시큐리티 필터에서 먼저 막힐 수 있습니다.** 시큐리티를 쓰면 시큐리티 쪽에서 설정하세요.

## 3. 설정

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.cors(Customizer.withDefaults());       // 아래 CorsConfigurationSource 빈을 사용
    // ...
    return http.build();
}

@Bean
public CorsConfigurationSource corsConfigurationSource(@Value("${app.cors.allowed-origins}") List<String> origins) {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(origins);                                  // 정확한 출처 목록
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-XSRF-TOKEN"));
    config.setExposedHeaders(List.of("Location"));                      // JS에서 읽을 응답 헤더
    config.setAllowCredentials(true);                                   // 쿠키 전송 허용 (Refresh 쿠키 등)
    config.setMaxAge(3600L);                                            // Preflight 결과 1시간 캐시

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", config);
    return source;
}
```
```yaml
app:
  cors:
    allowed-origins: http://localhost:3000,https://app.example.com
```

| 주의 | 설명 |
|---|---|
| `allowCredentials(true)` + `allowedOrigins("*")` | **불가능** (브라우저가 거부). 정확한 출처 지정, 패턴이 필요하면 `setAllowedOriginPatterns("https://*.example.com")` |
| 요청 출처를 그대로 반사 | `Origin` 헤더를 검증 없이 `Allow-Origin`에 넣으면 CORS가 무의미 |
| 프론트에서 쿠키 전송 | `fetch(url, { credentials: 'include' })`, axios `withCredentials: true` |
| CORS는 보안 장치가 아님 | **브라우저**만 지키는 규칙. curl·서버 간 호출은 막지 않음 → 인증·인가는 별도로 필수 |

> 운영에서는 프론트와 API를 **같은 도메인의 다른 경로**(`example.com` / `example.com/api`)로 리버스 프록시하면 CORS 자체가 필요 없습니다.

# Part 2. CSRF

## 4. CSRF 공격 원리

```
1. 사용자가 bank.com에 로그인 (세션 쿠키 보유)
2. 공격자 사이트 evil.com 방문
   <form action="https://bank.com/transfer" method="POST">
     <input name="to" value="attacker"><input name="amount" value="1000000">
   </form>
   <script>document.forms[0].submit()</script>
3. 브라우저가 bank.com 요청에 세션 쿠키를 자동으로 붙임 → 이체 성공
```
핵심: **브라우저가 쿠키를 자동으로 보내는 성질**을 악용합니다. 공격자는 응답을 읽을 수 없지만 **상태를 바꾸는 요청**을 보낼 수 있습니다.

## 5. 방어 방법

| 방법 | 설명 |
|---|---|
| **CSRF 토큰** (Synchronizer Token) | 서버가 발급한 예측 불가 토큰을 요청에 포함해야 함. 공격자 사이트는 토큰을 알 수 없음 |
| **SameSite 쿠키** | `Lax`/`Strict`면 다른 사이트의 POST에 쿠키가 안 실림 |
| Origin/Referer 검증 | 요청 출처 확인 |
| 상태 변경은 GET으로 하지 않기 | GET은 안전한 메서드로 유지 |

## 6. CSRF 보호, 꺼도 될까?

| 상황 | CSRF 보호 |
|---|---|
| **세션 쿠키 인증** (폼 로그인, SPA + 세션) | **필수** (켜기) |
| **Authorization 헤더로 토큰 전송** (JWT를 메모리·localStorage에) | 비활성화 가능 — 브라우저가 헤더를 자동으로 붙이지 않음 |
| **JWT를 쿠키에 저장**해 인증 | **필요** — 쿠키는 자동 전송됨 |
| Refresh Token만 쿠키 (`SameSite=Strict`, Path 제한) | 재발급·로그아웃 API에 대한 위험은 낮지만, 엄격하게는 토큰·Origin 검증 추가 |
| 서버 간 API (브라우저 아님) | 불필요 |

> **"REST API니까 CSRF를 끈다"가 아니라 "쿠키로 인증하지 않으니까 끈다"** 가 올바른 이유입니다.

## 7. 서버 렌더링 (Thymeleaf)

기본 설정 그대로 두면 됩니다. Thymeleaf의 `th:action` 폼에는 CSRF hidden 필드가 자동으로 들어갑니다.
```html
<form th:action="@{/posts}" method="post">
    <!-- <input type="hidden" name="_csrf" value="..."> 자동 추가 -->
</form>
```

## 8. 쿠키 세션 + SPA (React)

SPA는 CSRF 토큰을 **쿠키에서 읽어 헤더로** 보냅니다.
```
1. 서버: Set-Cookie: XSRF-TOKEN=abc (HttpOnly X → JS가 읽을 수 있게)
2. 프론트: 쿠키 값을 읽어 요청 헤더 X-XSRF-TOKEN: abc 에 넣음
3. 서버: 쿠키 값과 헤더 값 비교 (공격자 사이트는 쿠키를 읽을 수 없어 헤더를 못 만듦)
```

### Spring Security 7
```java
http.csrf(csrf -> csrf.spa());       // 위 설정을 한 줄로
```

### Spring Security 6
```java
http
    .csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())   // XSRF-TOKEN 쿠키
        .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler()))     // 헤더의 원본 값 그대로 비교
    .addFilterAfter(new CsrfCookieFilter(), BasicAuthenticationFilter.class);
```
```java
/** 6.x는 토큰을 지연 로딩하므로, 요청마다 토큰을 로딩해 쿠키가 발급되게 함 */
public class CsrfCookieFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        CsrfToken csrfToken = (CsrfToken) request.getAttribute(CsrfToken.class.getName());
        if (csrfToken != null) {
            csrfToken.getToken();
        }
        filterChain.doFilter(request, response);
    }
}
```
> Spring Security 6의 기본 `XorCsrfTokenRequestAttributeHandler`는 BREACH 공격 방어를 위해 토큰을 매번 변형합니다. SPA가 쿠키의 원본 값을 헤더로 보내면 검증에 실패하므로, 위처럼 핸들러를 바꾸거나 공식 문서의 `SpaCsrfTokenRequestHandler` 예제를 사용합니다. 7의 `csrf.spa()`는 이를 기본 처리합니다.

```javascript
// axios는 XSRF-TOKEN 쿠키 → X-XSRF-TOKEN 헤더를 자동 처리
axios.defaults.withCredentials = true;
axios.defaults.withXSRFToken = true;     // axios 1.6+ : 다른 출처 요청에도 헤더 첨부
```

### 특정 경로만 CSRF 제외
```java
http.csrf(csrf -> csrf.ignoringRequestMatchers("/api/webhooks/**"));   // 외부 서비스 웹훅 (서명으로 검증)
```

# Part 3. 보안 헤더

Spring Security가 기본으로 추가하는 응답 헤더입니다.

| 헤더 | 의미 |
|---|---|
| `X-Content-Type-Options: nosniff` | 브라우저가 Content-Type을 추측하지 않음 |
| `X-Frame-Options: DENY` | 다른 사이트가 iframe으로 넣지 못하게 (**클릭재킹** 방어) |
| `Strict-Transport-Security` (HTTPS일 때) | 이후 HTTPS로만 접속 (HSTS) |
| `Cache-Control: no-cache, no-store ...` | 인증된 페이지를 캐시하지 않음 |
| `X-XSS-Protection: 0` | 오래된 브라우저 XSS 필터 비활성화 (최신 권장값) |

```java
http.headers(headers -> headers
        .frameOptions(frame -> frame.sameOrigin())     // 같은 출처 iframe 허용 (H2 콘솔 등)
        .contentSecurityPolicy(csp -> csp.policyDirectives(
                "default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'")));
```
> **CSP(Content-Security-Policy)** 는 허용된 출처의 스크립트만 실행하게 해 **XSS 피해를 크게 줄입니다.** 기본으로 추가되지 않으므로 직접 설정하세요.

## 9. 면접 질문

1. **Spring Security를 쓰면 CORS 설정은 어디에 해야 하나요?**
   → Preflight 요청에는 인증 정보가 없어 시큐리티 인가 단계에서 막힐 수 있으므로, http.cors()와 CorsConfigurationSource로 시큐리티 필터 체인 앞단에서 처리해야 합니다.
2. **CSRF란?**
   → 사용자가 로그인한 상태에서 공격자 사이트가 브라우저의 쿠키 자동 전송을 이용해 사용자 모르게 상태를 바꾸는 요청을 보내게 하는 공격입니다.
3. **JWT를 쓰면 CSRF를 꺼도 되나요?**
   → 토큰을 Authorization 헤더로 보내면 브라우저가 자동으로 붙이지 않으므로 끌 수 있지만, 쿠키에 저장해 인증하면 자동 전송되므로 CSRF 보호가 필요합니다.
4. **allowCredentials(true)와 allowedOrigins("*")를 함께 쓸 수 없는 이유는?**
   → 인증 정보가 포함된 요청을 모든 출처에 허용하면 위험하므로 브라우저 규격상 와일드카드를 허용하지 않아, 정확한 출처를 지정해야 합니다.

## 핵심 정리
- CORS: `http.cors()` + `CorsConfigurationSource` (MVC 설정만으론 Preflight가 막힐 수 있음), credentials면 정확한 출처
- CORS는 브라우저 규칙일 뿐, 인증·인가 대체 X
- CSRF: **쿠키 인증이면 켜기, 헤더 토큰이면 끄기 가능**
- SPA + 세션: `CookieCsrfTokenRepository.withHttpOnlyFalse()` (6: 핸들러 + 쿠키 필터, 7: `csrf.spa()`)
- 보안 헤더 기본 제공 + CSP는 직접 설정
