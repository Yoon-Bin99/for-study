# 02. MSA 환경의 인증·인가

> **학습 목표**
> - MSA에서 인증을 어디서 처리할지(게이트웨이 vs 각 서비스) 비교할 수 있다.
> - 중앙 인증 서버(Authorization Server)와 리소스 서버 구조를 설명할 수 있다.
> - 서비스 간 호출에서 사용자 토큰 전파와 Client Credentials를 구분해 쓸 수 있다.
> - 내부 헤더 신뢰, mTLS 등 신뢰 경계를 설명할 수 있다.

---

## 1. 모놀리식과 무엇이 다른가?

모놀리식은 **한 애플리케이션이 로그인·세션·인가**를 모두 처리합니다. MSA에서는:
- 서비스가 여러 개 → **각 서비스가 사용자를 어떻게 알아보나?**
- 세션을 공유하기 어려움 → **토큰(JWT)** 이 자연스러움
- 서비스끼리도 서로를 호출 → **서비스 간 인증**도 필요

---

## 2. 전체 구조

```
                   ┌──────────────────────────────┐
[클라이언트] ──①로그인──>│ 인증 서버 (Auth Service /    │
     │            │  Keycloak / Spring Auth Server)│ ── 토큰 발급 (RS256 개인키 서명)
     │            └──────────────────────────────┘     JWKS로 공개키 공개
     │ ② Authorization: Bearer <JWT>
     ↓
[API Gateway] ─ ③ 토큰 검증 (공개키) ─ 라우팅, 레이트 리밋
     │
     ├──> [회원 서비스]  ④ 토큰 재검증 + 서비스별 인가
     ├──> [주문 서비스] ──⑤ 결제 서비스 호출 (토큰 전파 or 서비스 토큰)──> [결제 서비스]
     └──> [상품 서비스]
```

| 구성 | 역할 |
|---|---|
| **인증 서버** | 로그인 처리, 토큰 발급, 사용자·클라이언트 관리 (단일 진실 공급원) |
| **API Gateway** | 진입점, **1차 토큰 검증**, 라우팅, 레이트 리밋 |
| **각 서비스 (Resource Server)** | **2차 검증 + 도메인별 세부 인가** (본인 주문인가) |

### 인증 서버 선택지
| 선택지 | 특징 |
|---|---|
| **Keycloak** | 오픈소스, 관리 UI, 소셜 로그인·MFA·SSO 내장 |
| **Spring Authorization Server** | Spring으로 직접 구성, **Spring Security 7에 통합** |
| AWS Cognito, Auth0, Okta | 관리형 서비스 |
| 직접 만든 Auth 서비스 | 로그인 + JWT 발급 (RS256 + JWKS 공개 권장) |

> 서비스가 여러 개면 **RS256(비대칭키)** 를 씁니다. HS256이면 모든 서비스가 비밀키를 알아야 해서, 한 서비스만 털려도 **토큰 위조**가 가능해집니다.

## 3. 어디서 검증할까?

| 방식 | 설명 | 장단점 |
|---|---|---|
| **게이트웨이에서만** | 게이트웨이가 검증 후 `X-User-Id` 헤더로 사용자 정보를 내부 서비스에 전달 | 서비스가 단순 / **내부망 침투 시 헤더 위조 가능**, 게이트웨이 우회 경로가 있으면 위험 |
| **각 서비스에서만** | 모든 서비스가 Resource Server로 검증 | 안전 / 서비스마다 설정 필요 (공통 라이브러리로 해결) |
| **둘 다 (권장)** | 게이트웨이: 1차 차단 / 서비스: 재검증 + 세부 인가 | **심층 방어** (Zero Trust) |

### 게이트웨이 헤더 방식의 조건
- 외부에서 들어오는 `X-User-Id` 헤더는 게이트웨이가 **반드시 제거 후 재설정**
- 내부 서비스는 **게이트웨이를 통해서만** 접근 가능 (네트워크 정책, 보안 그룹, 쿠버네티스 NetworkPolicy)
- 그래도 각 서비스에서 JWT를 재검증하는 것이 더 안전

### Spring Cloud Gateway 예시
```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com/realms/myapp
  cloud:
    gateway:
      routes:
        - id: order
          uri: http://order-service
          predicates:
            - Path=/api/orders/**
```
```java
@Bean
public SecurityWebFilterChain gatewaySecurity(ServerHttpSecurity http) {   // Gateway는 WebFlux 기반
    http.csrf(ServerHttpSecurity.CsrfSpec::disable)
        .authorizeExchange(ex -> ex
            .pathMatchers("/api/auth/**").permitAll()
            .anyExchange().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
    return http.build();
}
```
→ 기본적으로 `Authorization` 헤더가 하위 서비스로 그대로 전달됩니다.

## 4. 서비스 간 호출의 인증

### 4-1. 사용자 토큰 전파 (Token Relay)
주문 서비스가 **"이 사용자를 대신해"** 결제 서비스를 호출할 때, 받은 사용자 토큰을 그대로 전달합니다.
```java
@Bean
public RestClient paymentClient(RestClient.Builder builder) {
    return builder.baseUrl("http://payment-service")
            .requestInterceptor((request, body, execution) -> {
                Authentication auth = SecurityContextHolder.getContext().getAuthentication();
                if (auth instanceof JwtAuthenticationToken jwtAuth) {
                    request.getHeaders().setBearerAuth(jwtAuth.getToken().getTokenValue());
                }
                return execution.execute(request, body);
            })
            .build();
}
```
- 결제 서비스도 **원래 사용자 기준**으로 인가 가능
- 주의: 토큰의 `aud`가 여러 서비스를 포함해야 하고, 토큰 수명 안에 처리가 끝나야 함
- 더 엄격하게는 **토큰 교환(Token Exchange, RFC 8693)** 으로 대상 서비스용 토큰을 새로 발급

### 4-2. 서비스 자신의 인증 (Client Credentials)
배치·이벤트 처리처럼 **사용자 없이** 서비스가 스스로 호출할 때
```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          order-service:
            provider: auth
            client-id: order-service
            client-secret: ${ORDER_CLIENT_SECRET}
            authorization-grant-type: client_credentials
            scope: payment:write
        provider:
          auth:
            token-uri: https://auth.example.com/oauth2/token
```
```java
@Bean
public RestClient paymentServiceClient(RestClient.Builder builder, OAuth2AuthorizedClientManager manager) {
    OAuth2ClientHttpRequestInterceptor interceptor = new OAuth2ClientHttpRequestInterceptor(manager);   // 6.4+
    interceptor.setClientRegistrationIdResolver(request -> "order-service");
    return builder.baseUrl("http://payment-service").requestInterceptor(interceptor).build();
}
```
→ 토큰 발급·캐시·만료 시 재발급을 Spring Security가 처리합니다.

> 웹 요청 밖(배치, 스케줄러, 메시지 리스너)에서 호출한다면 HTTP 요청에 묶이지 않는 `AuthorizedClientServiceOAuth2AuthorizedClientManager`를 `OAuth2AuthorizedClientManager` 빈으로 등록해 사용하세요.

| 상황 | 방식 |
|---|---|
| 사용자 요청 처리 중 다른 서비스 호출 | **토큰 전파** (또는 토큰 교환) |
| 배치, 스케줄러, 이벤트 컨슈머 | **Client Credentials** |
| 메시지 큐(Kafka)로 전달 | 메시지에 **사용자 ID를 데이터로** 포함 (토큰은 만료되므로 넣지 않기) |

## 5. 네트워크 수준의 신뢰

| 방법 | 설명 |
|---|---|
| **mTLS** (상호 TLS) | 서버뿐 아니라 **클라이언트도 인증서로 인증** → 서비스 신원 보장, 통신 암호화. 서비스 메시(Istio, Linkerd)가 자동화 |
| 네트워크 격리 | 내부 서비스는 프라이빗 서브넷, 보안 그룹·NetworkPolicy로 허용된 호출자만 |
| **Zero Trust** | "내부망이니까 안전"이라고 가정하지 않고, **모든 요청을 인증·인가** |

---

## 6. 사용자 정보 동기화

- 토큰에는 **사용자 ID와 역할** 정도만 → 서비스는 필요한 사용자 정보를 회원 서비스 API로 조회하거나, **회원 변경 이벤트를 구독해 자기 DB에 사본** 저장
- 계정 정지·권한 변경 → 이벤트 발행 + Access Token 수명을 짧게 → 빠르게 반영

## 7. 면접 질문

1. **MSA에서 인증은 어디서 처리하나요?**
   → 인증 서버가 토큰을 발급하고, API 게이트웨이가 1차로 토큰을 검증하며, 각 서비스도 리소스 서버로서 토큰을 재검증하고 도메인별 세부 인가를 수행하는 심층 방어 구조가 일반적입니다.
2. **MSA에서 HS256 대신 RS256을 쓰는 이유는?**
   → HS256은 검증하는 모든 서비스가 비밀키를 알아야 해 한 곳이 유출되면 토큰을 위조할 수 있지만, RS256은 인증 서버만 개인키를 갖고 서비스들은 공개키로 검증만 하기 때문입니다.
3. **서비스 간 호출 시 인증은 어떻게 하나요?**
   → 사용자 요청을 대신하는 경우 사용자 토큰을 전파하고, 배치처럼 사용자 없이 호출하는 경우 Client Credentials로 서비스 자신의 토큰을 발급받아 사용합니다. 네트워크 수준에서는 mTLS를 함께 씁니다.
4. **게이트웨이가 X-User-Id 헤더로 사용자 정보를 넘기는 방식의 위험은?**
   → 게이트웨이를 우회하거나 내부망에 침투하면 헤더를 위조할 수 있으므로, 외부 헤더 제거, 네트워크 격리, 서비스별 토큰 재검증이 필요합니다.

---

## 핵심 정리
- 인증 서버(토큰 발급, RS256 + JWKS) → 게이트웨이(1차 검증) → 서비스(재검증 + 세부 인가)
- 게이트웨이 헤더 방식은 우회·위조 위험 → 심층 방어(Zero Trust)
- 서비스 간: 사용자 요청이면 **토큰 전파**, 사용자 없으면 **Client Credentials**, 메시지에는 사용자 ID만
- mTLS, 네트워크 격리, 짧은 토큰 수명 + 이벤트로 권한 변경 반영
