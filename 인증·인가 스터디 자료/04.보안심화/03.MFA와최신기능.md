# 03. MFA, 패스키, 일회용 토큰 로그인 (Spring Security 최신 기능)

> **학습 목표**
> - TOTP, SMS, 이메일, 패스키 등 2차 인증 수단의 장단점을 비교할 수 있다.
> - Spring Security 6.4의 일회용 토큰(OTT) 로그인과 패스키(WebAuthn)를 설정할 수 있다.
> - Spring Security 7의 MFA 지원(`@EnableMultiFactorAuthentication`)을 설명할 수 있다.
> - 단계적 인증(Step-up)과 재인증의 개념을 설명할 수 있다.

## 1. 2차 인증 수단 비교

| 수단 | 방식 | 보안 | 사용성 | 비고 |
|---|---|---|---|---|
| SMS 인증번호 | 문자로 6자리 | ⚠️ 낮음 (**SIM 스와핑**, 문자 가로채기) | 좋음 | 국내에서 흔하지만 권장도 낮음 |
| 이메일 코드·링크 | 메일로 코드·링크 | 중간 (메일 계정 보안에 의존) | 좋음 | |
| **TOTP** (Google Authenticator, Authy) | 앱이 30초마다 6자리 생성 (공유 비밀 + 시간) | 좋음 | 보통 | 오프라인 동작, 피싱에는 약함 |
| 푸시 승인 | 앱에 "로그인하시겠습니까?" | 좋음 | 매우 좋음 | **알림 폭탄 공격**(승인할 때까지 요청) 주의 → 번호 일치 확인 |
| **패스키 / 보안키** (WebAuthn, FIDO2) | 기기의 개인키로 서명 | **최고** (피싱 방지) | 매우 좋음 | **권장 방향** |

### TOTP 원리
```
가입 시: 서버가 비밀값(secret)을 만들어 QR 코드로 앱에 전달 (서버도 암호화해 저장)
로그인 시: 코드 = HMAC-SHA1(secret, floor(현재시각 / 30초)) 의 6자리
         앱과 서버가 각각 계산해 비교 (시계 오차를 고려해 앞뒤 1구간 허용)
```
> 2차 인증을 도입할 때는 **복구 코드**(일회용 백업 코드)도 함께 발급하세요. 휴대폰을 잃어버리면 로그인할 수 없게 됩니다.

## 2. 패스키 (Passkey, WebAuthn)

```
등록
1. 서버 → 브라우저: 챌린지(랜덤 값)
2. 기기(지문·얼굴·PIN으로 잠금 해제)가 **이 사이트 전용** 키 쌍 생성
3. 공개키를 서버에 등록 (개인키는 기기·클라우드 키체인에만)

로그인
1. 서버 → 챌린지
2. 기기가 개인키로 챌린지에 서명 (도메인이 일치할 때만)
3. 서버가 저장된 공개키로 검증
```
| 장점 | 이유 |
|---|---|
| **피싱 방지** | 키가 **도메인에 묶여** 있어 가짜 사이트(myapp-login.com)에서는 서명 자체가 안 됨 |
| 유출 무의미 | 서버에는 공개키만 → DB가 털려도 로그인 불가 |
| 재사용 불가 | 사이트마다 다른 키 |
| 편리 | 비밀번호 입력 없이 생체 인증 |

### Spring Security 설정
```groovy
// Spring Security 7: 전용 모듈
implementation 'org.springframework.security:spring-security-webauthn'
// Spring Security 6.4~6.5: 대신 implementation 'com.webauthn4j:webauthn4j-core:<버전>' 추가
```
```java
http
    .formLogin(Customizer.withDefaults())
    .webAuthn(webAuthn -> webAuthn
        .rpName("My App")                          // 사용자에게 보이는 이름
        .rpId("example.com")                       // 키가 묶일 도메인
        .allowedOrigins("https://example.com"));
```
- 기본 등록 페이지(`/webauthn/register`)와 로그인 페이지의 패스키 로그인 버튼 제공
- 기본 저장소는 메모리 → 운영에서는 JDBC 기반 저장소(`JdbcPublicKeyCredentialUserEntityRepository`, `JdbcUserCredentialRepository`) 사용
- **HTTPS 필수** (localhost 제외)

## 3. 일회용 토큰 로그인 (One-Time Token, 매직 링크)

비밀번호 없이 **이메일로 받은 일회용 링크**로 로그인합니다. (Spring Security 6.4+)

```java
http
    .formLogin(Customizer.withDefaults())
    .oneTimeTokenLogin(Customizer.withDefaults());
```
```java
@Component
@RequiredArgsConstructor
public class MagicLinkSender implements OneTimeTokenGenerationSuccessHandler {
    private final MailService mailService;
    private final OneTimeTokenGenerationSuccessHandler redirectHandler =
            new RedirectOneTimeTokenGenerationSuccessHandler("/ott/sent");

    @Override
    public void handle(HttpServletRequest request, HttpServletResponse response,
                       OneTimeToken oneTimeToken) throws IOException, ServletException {
        String link = UriComponentsBuilder.fromUriString("https://example.com/login/ott")
                .queryParam("token", oneTimeToken.getTokenValue())
                .toUriString();
        mailService.send(oneTimeToken.getUsername(), "로그인 링크", link);   // username = 이메일
        redirectHandler.handle(request, response, oneTimeToken);
    }
}
```
- 토큰은 **일회용 + 짧은 만료**(기본 5분), 기본 저장소는 메모리 → 운영은 `JdbcOneTimeTokenService`
- 링크에 토큰이 들어가므로 만료를 짧게 하고, 사용 즉시 폐기

## 4. Spring Security 7의 MFA

Spring Security 7은 **인증 수단(Factor)마다 권한을 부여**하는 방식으로 MFA를 지원합니다.

- 비밀번호로 로그인하면 → `FACTOR_PASSWORD` 권한 자동 추가
- 일회용 토큰으로 인증하면 → `FACTOR_OTT` 권한 자동 추가
- 패스키 → `FACTOR_WEBAUTHN`, X.509 → `FACTOR_X509`, OAuth2 로그인 → `FACTOR_AUTHORIZATION_CODE`

```java
@Configuration
@EnableWebSecurity
@EnableMultiFactorAuthentication(authorities = {
        FactorGrantedAuthority.PASSWORD_AUTHORITY,
        FactorGrantedAuthority.OTT_AUTHORITY })        // 모든 인가 규칙에 "비밀번호 + OTT 둘 다" 요구
public class MfaSecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .formLogin(Customizer.withDefaults())          // 1차: 비밀번호
            .oneTimeTokenLogin(Customizer.withDefaults()); // 2차: 이메일 일회용 토큰
        return http.build();
    }
}
```
```
/admin/** → ROLE_ADMIN + FACTOR_PASSWORD + FACTOR_OTT 모두 필요
그 외     → FACTOR_PASSWORD + FACTOR_OTT
비밀번호만 인증한 상태라면 → 부족한 인증 수단의 로그인 화면으로 자동 이동
```
> 7.1부터는 "패스키를 등록한 사용자에게만 MFA 요구" 같은 **조건부 MFA**도 지원합니다. 버전마다 기능이 빠르게 추가되고 있으니 공식 문서를 확인하세요.

### 6.x에서 MFA를 직접 구현한다면 (JWT 방식 예)
```
1. POST /login (비밀번호) 성공
   → MFA가 켜진 사용자면 정식 토큰 대신 "MFA 대기 토큰"(짧은 수명, 권한: MFA_PENDING) 발급
2. POST /login/mfa (MFA 대기 토큰 + TOTP 코드)
   → 코드 검증 성공 → 정식 Access + Refresh 발급
3. MFA_PENDING 권한으로는 /login/mfa 외의 API 접근 불가 (인가 규칙)
```

## 5. 단계적 인증(Step-up)과 재인증

**평소에는 가벼운 인증, 중요한 작업에서만 강한 인증**을 요구합니다.

| 작업 | 요구 |
|---|---|
| 상품 조회, 장바구니 | 로그인 |
| 주문 내역 조회 | 로그인 |
| **결제, 송금, 비밀번호·이메일 변경, 탈퇴** | **재인증**(비밀번호 재입력) 또는 **2차 인증** |
| 관리자 기능 | MFA 필수 |

구현 아이디어:
- 토큰·세션에 **마지막 강한 인증 시각**(`auth_time`)을 기록 → "10분 이내 재인증"을 인가 조건으로
- OIDC는 `max_age`, `acr_values` 파라미터로 인증 서버에 재인증·인증 수준을 요청

## 6. 그 밖의 최신 변화 (Spring Security 6.3 ~ 7.x)

| 기능 | 버전 | 설명 |
|---|---|---|
| 유출 비밀번호 검사 (`CompromisedPasswordChecker`) | 6.3 | Have I Been Pwned API로 유출 여부 확인 |
| 역할 계층 빌더 `RoleHierarchyImpl.fromHierarchy` | 6.3 | 간편한 역할 상속 |
| 메서드 보안 애노테이션 템플릿 | 6.3+ | `@HasPermission("member:delete")` |
| 일회용 토큰 로그인, 패스키(WebAuthn) | 6.4 | 비밀번호 없는 로그인 |
| `OAuth2ClientHttpRequestInterceptor` | 6.4 | RestClient에 OAuth2 토큰 자동 첨부 |
| **람다 DSL만 지원, `and()`·`authorizeRequests` 제거** | 7.0 | 마이그레이션 필수 |
| `PathPatternRequestMatcher` 기본 | 7.0 | Ant·Mvc 매처 제거 |
| **MFA**, Authorization Server·Kerberos 통합 | 7.0 | |
| SPA CSRF `csrf.spa()` | 7.0 | |
| Password4j 기반 인코더 | 7.0 | Argon2, bcrypt 등 |
| OAuth2 Password Grant 제거 | 7.0 | 표준에서 폐기된 방식 |

> Spring Boot 3 → 4 업그레이드 시 Spring Security 6 → 7 마이그레이션 가이드를 먼저 확인하세요. 6.x 마지막 버전에서 deprecated 경고를 모두 없애 두면 7로 넘어가기 쉽습니다.

## 7. 면접 질문

1. **SMS 인증보다 TOTP나 패스키가 안전한 이유는?**
   → SMS는 SIM 스와핑이나 문자 가로채기에 취약하지만, TOTP는 기기 안의 비밀값으로 생성되고, 패스키는 도메인에 묶인 개인키로 서명해 피싱까지 막기 때문입니다.
2. **패스키(WebAuthn)가 피싱에 강한 이유는?**
   → 키 쌍이 등록한 사이트의 도메인에 묶여 있어, 가짜 도메인에서는 브라우저와 기기가 서명을 만들어 주지 않기 때문입니다.
3. **단계적 인증이란?**
   → 평소에는 일반 로그인 상태로 사용하다가 결제나 개인정보 변경 같은 중요한 작업을 할 때만 재인증이나 2차 인증을 추가로 요구하는 방식입니다.
4. **Spring Security 7에서 MFA는 어떻게 구현되나요?**
   → 인증 수단마다 FACTOR_ 권한이 자동으로 부여되고, @EnableMultiFactorAuthentication으로 필요한 인증 수단 권한을 인가 규칙에 요구해, 부족하면 해당 인증 화면으로 이동시킵니다.

## 핵심 정리
- 2차 인증: SMS(약함) < 이메일 < TOTP < **패스키(피싱 방지, 권장)**, 복구 코드 필수
- 6.4: `oneTimeTokenLogin()`(매직 링크), `webAuthn()`(패스키) — 운영은 JDBC 저장소
- 7.0: **FACTOR_ 권한 + `@EnableMultiFactorAuthentication`** 으로 MFA
- 중요 작업은 재인증·Step-up
- Boot 4 / Security 7 마이그레이션: 람다 DSL, PathPattern, 제거된 API 확인
