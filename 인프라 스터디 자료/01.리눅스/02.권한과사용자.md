# 02. 권한과 사용자 관리

> **학습 목표**
> - `ls -l` 출력에서 파일 종류, 권한, 소유자를 읽을 수 있다.
> - `chmod`(숫자·기호), `chown`으로 권한과 소유자를 바꿀 수 있다.
> - root와 sudo, 사용자·그룹 관리를 설명할 수 있다.
> - SSH 키 인증의 원리와 사용법을 설명할 수 있다.

---

## 1. 권한 읽기

```bash
$ ls -l
-rwxr-xr-- 1 ubuntu dev 2048 Nov  9 10:00 deploy.sh
drwxr-xr-x 2 ubuntu dev 4096 Nov  9 10:00 logs
```

```
-  rwx  r-x  r--   1   ubuntu  dev   2048  ...  deploy.sh
│   │    │    │    │     │      │
│   │    │    │    │     │      └── 그룹
│   │    │    │    │     └── 소유자
│   │    │    │    └── 링크 수
│   │    │    └── 기타 사용자(other) 권한
│   │    └── 그룹(group) 권한
│   └── 소유자(user) 권한
└── 파일 종류: - 일반 파일, d 디렉토리, l 심볼릭 링크
```

| 권한 | 파일 | 디렉토리 |
|---|---|---|
| **r** (read, 4) | 내용 읽기 | 목록 보기 (`ls`) |
| **w** (write, 2) | 내용 수정 | 안에 파일 생성·삭제·이름 변경 |
| **x** (execute, 1) | **실행** (스크립트, 바이너리) | **들어가기** (`cd`) |

> 디렉토리에 `x`가 없으면 안에 있는 파일 권한이 있어도 접근할 수 없습니다.

## 2. chmod: 권한 변경

### 숫자 방식 (8진수)
각 자리 = r(4) + w(2) + x(1)
```
rwx = 4+2+1 = 7
r-x = 4+0+1 = 5
r-- = 4+0+0 = 4
```

| 숫자 | 권한 | 용도 |
|---|---|---|
| `755` | rwxr-xr-x | 실행 파일, 디렉토리 |
| `644` | rw-r--r-- | 일반 파일 (설정 파일) |
| `600` | rw------- | **비밀 파일 (SSH 개인키, .env)** |
| `700` | rwx------ | 개인 디렉토리 (`~/.ssh`) |
| `777` | rwxrwxrwx | **모두에게 전부 허용 → 보안상 사용 금지** |

```bash
chmod 755 deploy.sh
chmod 600 ~/.ssh/id_rsa
chmod -R 755 /opt/app       # 하위까지 재귀
```

### 기호 방식
```bash
chmod u+x deploy.sh     # 소유자(u)에게 실행(x) 추가
chmod g-w file          # 그룹(g)에서 쓰기 제거
chmod o=r file          # 기타(o)는 읽기만
chmod a+r file          # 모두(a)에게 읽기 추가
```

> 스크립트를 만들고 `./deploy.sh` 했는데 `Permission denied`가 나면 대부분 `chmod +x deploy.sh`를 안 한 것입니다.

### umask
새 파일의 기본 권한을 정합니다. 보통 `022` → 파일 644, 디렉토리 755

## 3. chown: 소유자 변경

```bash
sudo chown ubuntu file.txt              # 소유자 변경
sudo chown ubuntu:dev file.txt          # 소유자:그룹
sudo chown -R www-data:www-data /var/www   # Nginx가 읽을 수 있게
```

> Nginx, MySQL 같은 서비스는 **전용 사용자**(www-data, mysql)로 실행됩니다. 서비스가 파일을 못 읽으면 소유자·권한을 먼저 확인하세요.

## 4. 특수 권한 (간단히)

| 권한 | 의미 | 예 |
|---|---|---|
| **SetUID** (4000) | 실행 시 **파일 소유자 권한**으로 실행 | `/usr/bin/passwd` (일반 사용자가 /etc/shadow 수정) |
| SetGID (2000) | 그룹 권한으로 실행 / 디렉토리 내 새 파일이 그룹 상속 | 공유 디렉토리 |
| **Sticky Bit** (1000) | 디렉토리 안의 파일을 **소유자만 삭제** 가능 | `/tmp` (`drwxrwxrwt`) |

## 5. 사용자와 그룹

### root와 sudo
- **root**: 모든 권한을 가진 관리자 (UID 0)
- **sudo**: 일반 사용자가 **명령 하나만** root 권한으로 실행
- 평소에는 일반 사용자로 작업하고, 필요할 때만 `sudo` → 실수 방지, 기록(로그) 남음

```bash
sudo systemctl restart nginx
sudo -i                 # root 셸로 전환 (주의)
whoami                  # 현재 사용자
id                      # UID, GID, 소속 그룹
```

### 사용자·그룹 관리
```bash
sudo useradd -m -s /bin/bash deploy     # 홈 디렉토리 + bash로 사용자 생성
sudo passwd deploy
sudo usermod -aG docker deploy          # docker 그룹에 추가 (-a 없으면 기존 그룹 제거됨!)
sudo usermod -aG sudo deploy            # sudo 권한 (Ubuntu) / wheel (RHEL 계열)
groups deploy
sudo userdel -r deploy
```

> `docker` 명령을 sudo 없이 쓰려면 `docker` 그룹에 추가하고 **다시 로그인**해야 합니다. 단, docker 그룹은 사실상 root와 같은 권한이라는 점을 알아 두세요.

### 관련 파일
| 파일 | 내용 |
|---|---|
| `/etc/passwd` | 사용자 목록 (이름:x:UID:GID:설명:홈:셸) |
| `/etc/shadow` | **암호화된 비밀번호** (root만 읽기) |
| `/etc/group` | 그룹 목록 |
| `/etc/sudoers` | sudo 권한 설정 (`visudo`로 편집) |

### 서비스 계정
애플리케이션은 **로그인할 수 없는 전용 사용자**로 실행하는 것이 안전합니다.
```bash
sudo useradd -r -s /usr/sbin/nologin app
```
→ 앱이 해킹당해도 피해 범위가 그 사용자 권한으로 제한됩니다 (**최소 권한 원칙**).

## 6. SSH (Secure Shell)

원격 서버에 **암호화된 연결**로 접속하는 프로토콜입니다. (기본 포트 22)

### 비밀번호 인증 vs 키 인증
| 방식 | 설명 | 보안 |
|---|---|---|
| 비밀번호 | 서버에 비밀번호 입력 | 무차별 대입 공격에 취약 |
| **공개키 인증** | 개인키(내 PC) + 공개키(서버) | **권장**, 클라우드 기본 |

### 공개키 인증 원리
```
1. 내 PC에서 키 쌍 생성: 개인키(id_ed25519) + 공개키(id_ed25519.pub)
2. 공개키를 서버의 ~/.ssh/authorized_keys 에 등록
3. 접속 시 서버가 "이 공개키 짝인 개인키를 가졌는지 증명해" → 개인키로 서명
4. 서버가 공개키로 서명 검증 → 접속 허용
   (개인키는 네트워크로 절대 전송되지 않음)
```

```bash
# 키 생성
ssh-keygen -t ed25519 -C "my-laptop"

# 공개키를 서버에 등록
ssh-copy-id ubuntu@203.0.113.10

# 접속
ssh -i ~/.ssh/my-key.pem ubuntu@203.0.113.10

# 파일 전송
scp -i key.pem app.jar ubuntu@203.0.113.10:/opt/app/
```

> AWS EC2는 생성 시 키 페어(.pem)를 받습니다. 권한이 너무 열려 있으면 `UNPROTECTED PRIVATE KEY FILE!` 오류가 나므로 `chmod 400 key.pem`을 하세요.

### ~/.ssh/config로 편하게
```
Host prod
    HostName 203.0.113.10
    User ubuntu
    IdentityFile ~/.ssh/prod.pem

Host private-app
    HostName 10.0.2.15
    User ubuntu
    ProxyJump prod        # 배스천(점프) 서버를 거쳐 프라이빗 서버 접속
```
```bash
ssh prod
ssh private-app
```

### SSH 서버 보안 설정 (/etc/ssh/sshd_config)
```
PermitRootLogin no            # root 직접 로그인 금지
PasswordAuthentication no     # 비밀번호 로그인 금지, 키만 허용
```
→ 변경 후 `sudo systemctl restart ssh` (배포판에 따라 `sshd`)

> 최근에는 22번 포트를 열지 않고 **AWS Systems Manager Session Manager**로 접속하는 방식도 많이 씁니다. (→ `06.AWS/05.IAM과보안.md`)

## 7. 면접 질문

1. **`chmod 755`의 의미는?**
   → 소유자는 읽기·쓰기·실행, 그룹과 기타 사용자는 읽기·실행 권한입니다.
2. **SSH 개인키 파일 권한을 600(또는 400)으로 해야 하는 이유는?**
   → 다른 사용자가 개인키를 읽으면 서버에 접속할 수 있기 때문이며, SSH 클라이언트는 권한이 넓으면 접속을 거부합니다.
3. **root로 직접 작업하지 않고 sudo를 쓰는 이유는?**
   → 실수로 인한 시스템 손상을 줄이고, 누가 어떤 관리자 명령을 실행했는지 기록이 남기 때문입니다.
4. **SSH 공개키 인증의 원리는?**
   → 서버에 공개키를 등록해 두고, 접속 시 클라이언트가 개인키로 서명해 소유를 증명하면 서버가 공개키로 검증합니다. 개인키는 전송되지 않습니다.

---

## 핵심 정리
- 권한 = 소유자/그룹/기타 × r(4) w(2) x(1)
- 파일 644, 실행·디렉토리 755, 비밀 600, 777 금지
- 평소엔 일반 사용자 + sudo, 앱은 로그인 불가 전용 계정 (최소 권한)
- SSH는 키 인증, root 로그인·비밀번호 로그인 비활성화
