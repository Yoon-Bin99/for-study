# 03. 프로세스와 서비스 관리

> **학습 목표**
> - `ps`, `top`으로 프로세스 상태와 자원 사용량을 확인할 수 있다.
> - 시그널(SIGTERM, SIGKILL)의 차이와 Graceful Shutdown을 설명할 수 있다.
> - 포그라운드·백그라운드 실행과 `nohup`을 사용할 수 있다.
> - systemd로 Spring Boot 애플리케이션을 서비스로 등록하고 관리할 수 있다.
> - cron으로 작업을 예약할 수 있다.

---

## 1. 프로세스 확인

```bash
ps aux                         # 모든 프로세스
ps aux | grep java             # java 프로세스 찾기
ps -ef --forest                # 부모-자식 관계 트리
pgrep -f app.jar               # 이름으로 PID 찾기
```

`ps aux` 출력 읽기
```
USER   PID  %CPU %MEM    VSZ    RSS  TTY  STAT START  TIME COMMAND
app   1234  12.3  25.1 4.2G   1.0G   ?    Sl   10:00  5:12 java -jar app.jar
```
| 열 | 의미 |
|---|---|
| PID | 프로세스 ID |
| %CPU, %MEM | CPU·메모리 사용률 |
| VSZ | 가상 메모리 크기 |
| **RSS** | **실제 물리 메모리 사용량** |
| STAT | 상태: R 실행 중, S 대기(sleep), D I/O 대기(중단 불가), Z **좀비**, T 정지 |

### top / htop: 실시간 모니터링
```bash
top          # q 종료, P CPU순, M 메모리순, 1 코어별
htop         # 더 보기 좋은 버전 (설치 필요)
```

```
top - 10:00:00 up 30 days, load average: 0.52, 0.80, 1.20
                                          1분   5분   15분
```
- **Load Average**: 실행 중이거나 실행을 기다리는(CPU, I/O 대기 포함) 프로세스의 평균 개수
- **CPU 코어 수보다 지속적으로 크면 과부하** (4코어에서 8이면 2배 과부하)
- `nproc`로 코어 수 확인

## 2. 시그널 (Signal)

프로세스에게 보내는 **비동기 알림**입니다.

| 시그널 | 번호 | 의미 | 프로세스가 무시 가능? |
|---|---|---|---|
| SIGHUP | 1 | 터미널 종료 / 설정 다시 읽기 | O |
| SIGINT | 2 | 인터럽트 (**Ctrl + C**) | O |
| **SIGTERM** | 15 | **정상 종료 요청** (`kill` 기본값) | O (정리 작업 후 종료) |
| **SIGKILL** | 9 | **강제 종료** | **X** (즉시 죽음, 정리 불가) |
| SIGSTOP / SIGCONT | 19 / 18 | 일시 정지 / 재개 (Ctrl + Z) | X / - |

```bash
kill 1234          # SIGTERM (정상 종료 요청)
kill -9 1234       # SIGKILL (강제 종료) — 최후의 수단
kill -HUP 1234     # 설정 리로드 (Nginx 등)
pkill -f app.jar   # 이름으로
```

### Graceful Shutdown (우아한 종료)
**SIGTERM을 받으면 새 요청은 받지 않고, 처리 중인 요청을 마친 뒤 종료**하는 것입니다.

- `kill -9`로 죽이면: 처리 중인 요청 유실, DB 트랜잭션 중단, 파일 손상 위험
- 배포 시 항상 SIGTERM → 일정 시간 대기 → 그래도 안 죽으면 SIGKILL 순서
- Kubernetes도 Pod 종료 시 SIGTERM → `terminationGracePeriodSeconds`(기본 30초) 후 SIGKILL

```yaml
# Spring Boot (2.3+) application.yml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

## 3. 포그라운드와 백그라운드

```bash
java -jar app.jar          # 포그라운드: 터미널을 점유, 터미널 닫으면 같이 종료
java -jar app.jar &        # 백그라운드 실행
jobs                       # 현재 셸의 백그라운드 작업 목록
fg %1                      # 포그라운드로
Ctrl + Z → bg              # 일시 정지 후 백그라운드로

nohup java -jar app.jar > app.log 2>&1 &   # 터미널(SSH)을 끊어도 계속 실행
```

> `nohup`은 간단하지만 **서버 재부팅 시 자동 시작이 안 되고, 죽어도 다시 살아나지 않습니다.** 운영 환경에서는 **systemd** 또는 **도커/쿠버네티스**를 씁니다.

## 4. systemd: 서비스 관리

현대 리눅스의 **init 시스템(PID 1)** 으로, 부팅 시 서비스를 시작하고 관리합니다.

```bash
sudo systemctl start nginx       # 시작
sudo systemctl stop nginx        # 중지
sudo systemctl restart nginx     # 재시작
sudo systemctl reload nginx      # 설정만 다시 읽기 (무중단)
sudo systemctl status nginx      # 상태 확인
sudo systemctl enable nginx      # 부팅 시 자동 시작
sudo systemctl disable nginx
systemctl list-units --type=service --state=running
```

### Spring Boot를 서비스로 등록
`/etc/systemd/system/myapp.service`
```ini
[Unit]
Description=My Spring Boot App
After=network.target

[Service]
User=app
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/java -Xms512m -Xmx512m -jar /opt/myapp/app.jar --spring.profiles.active=prod
EnvironmentFile=/opt/myapp/.env
SuccessExitStatus=143
Restart=always
RestartSec=5
TimeoutStopSec=40

[Install]
WantedBy=multi-user.target
```

| 설정 | 의미 |
|---|---|
| `User` | 실행 사용자 (root 금지) |
| `EnvironmentFile` | 환경 변수 파일 (DB 비밀번호 등, 권한 600) |
| `Restart=always` | **죽으면 자동 재시작** |
| `SuccessExitStatus=143` | JVM이 SIGTERM으로 종료될 때 코드 143(128+15)을 정상으로 간주 |
| `TimeoutStopSec` | SIGTERM 후 SIGKILL까지 대기 시간 |
| `WantedBy=multi-user.target` | `enable` 시 일반 부팅 단계에서 시작 |

```bash
sudo systemctl daemon-reload      # 서비스 파일 수정 후 반드시
sudo systemctl enable --now myapp # 등록 + 즉시 시작
```

### journalctl: systemd 로그
```bash
journalctl -u myapp               # 해당 서비스 로그
journalctl -u myapp -f            # 실시간
journalctl -u myapp --since "1 hour ago"
journalctl -p err -b              # 이번 부팅 이후 에러만
```

## 5. cron: 작업 예약

```bash
crontab -e      # 편집
crontab -l      # 목록
```

```
┌───────── 분 (0-59)
│ ┌─────── 시 (0-23)
│ │ ┌───── 일 (1-31)
│ │ │ ┌─── 월 (1-12)
│ │ │ │ ┌─ 요일 (0-6, 0 = 일요일)
│ │ │ │ │
* * * * *  명령어
```

| 표현 | 의미 |
|---|---|
| `0 3 * * *` | 매일 새벽 3시 |
| `*/5 * * * *` | 5분마다 |
| `0 9 * * 1-5` | 평일 오전 9시 |
| `0 0 1 * *` | 매월 1일 자정 |

```bash
# 매일 새벽 3시 DB 백업, 7일 지난 로그 삭제
0 3 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
0 4 * * * find /var/log/myapp -name "*.log" -mtime +7 -delete
```

> cron은 **로그인 셸이 아니라서 PATH 등 환경 변수가 적습니다.** 스크립트에서는 명령어를 절대 경로로 쓰거나 PATH를 직접 지정하세요. Spring의 `@Scheduled`, 쿠버네티스 `CronJob`도 같은 표현식을 씁니다. (Spring은 초 필드가 추가된 6자리)

## 6. 시스템 자원 확인 명령어 모음

| 명령어 | 확인 내용 |
|---|---|
| `top`, `htop` | CPU, 메모리, 프로세스 |
| `free -h` | 메모리 (`available`이 실제 사용 가능량) |
| `df -h` / `du -sh` | 디스크 |
| `vmstat 1` | CPU·메모리·스왑·I/O 1초마다 |
| `iostat -x 1` | 디스크 I/O (sysstat 패키지) |
| `uptime` | 가동 시간, Load Average |
| `lsof -p 1234` | 프로세스가 연 파일·소켓 |
| `dmesg -T` | 커널 메시지 (**OOM Killer** 확인) |

> 프로세스가 이유 없이 죽었다면 `dmesg -T | grep -i "killed process"`로 **OOM Killer**(메모리 부족 시 커널이 프로세스를 강제 종료)를 확인하세요.

## 7. 면접 질문

1. **SIGTERM과 SIGKILL의 차이는?**
   → SIGTERM은 정상 종료 요청으로 프로세스가 정리 작업 후 종료할 수 있고, SIGKILL은 무시할 수 없는 즉시 강제 종료입니다.
2. **Graceful Shutdown이 필요한 이유는?**
   → 배포·종료 시 처리 중인 요청과 트랜잭션을 마무리해 데이터 유실과 사용자 오류를 막기 위해서입니다.
3. **nohup 대신 systemd를 쓰는 이유는?**
   → 프로세스가 죽으면 자동 재시작하고, 부팅 시 자동 시작하며, 로그와 상태를 일관되게 관리할 수 있기 때문입니다.
4. **Load Average란?**
   → 실행 중이거나 실행 대기 중인 프로세스의 평균 수로, CPU 코어 수보다 지속적으로 크면 과부하입니다.

## 핵심 정리
- `ps aux | grep`, `top`(Load Average vs 코어 수)
- SIGTERM(15, 정상 종료) → 대기 → SIGKILL(9, 강제) / Graceful Shutdown
- 운영은 nohup X → **systemd** (`Restart=always`, `enable`), 로그는 `journalctl`
- cron: `분 시 일 월 요일`, 환경 변수 주의
