# 04. 네트워크 명령어와 트러블슈팅

> **학습 목표**
> - IP, 포트, DNS, 라우팅을 확인하는 명령어를 사용할 수 있다.
> - `curl`로 API를 테스트하고 응답 시간을 측정할 수 있다.
> - 방화벽(ufw, firewalld, 보안 그룹)의 역할을 설명할 수 있다.
> - "서버에 접속이 안 된다"는 문제를 계층별로 진단할 수 있다.

---

## 1. 네트워크 정보 확인

```bash
ip addr          # (또는 ip a) 인터페이스와 IP 주소
ip route         # 라우팅 테이블, 기본 게이트웨이
hostname -I      # IP만 간단히
cat /etc/hosts   # 로컬 도메인 매핑
cat /etc/resolv.conf   # 사용 중인 DNS 서버
curl ifconfig.me # 외부에서 보이는 공인 IP
```

> 예전 `ifconfig`, `netstat`은 `net-tools` 패키지로 최신 배포판에는 기본 설치되지 않는 경우가 많습니다. 대신 `ip`, `ss`를 씁니다.

---

## 2. 포트와 연결 확인

```bash
ss -tlnp                 # ★ 열려 있는(LISTEN) TCP 포트와 프로세스
ss -tnp                  # 현재 TCP 연결
ss -s                    # 상태별 연결 수 요약 (TIME_WAIT 개수 등)
sudo lsof -i :8080       # 8080 포트를 쓰는 프로세스
```

| 옵션 | 의미 |
|---|---|
| `-t` / `-u` | TCP / UDP |
| `-l` | LISTEN 상태만 |
| `-n` | 이름 대신 숫자 (빠름) |
| `-p` | 프로세스 정보 (sudo 필요할 수 있음) |

```
State   Local Address:Port    Process
LISTEN  0.0.0.0:80            nginx
LISTEN  127.0.0.1:3306        mysqld     ← 127.0.0.1: 로컬에서만 접속 가능!
LISTEN  *:8080                java       ← 모든 인터페이스
```

> **"앱은 떴는데 외부에서 접속이 안 돼요"** 의 흔한 원인: 앱이 `127.0.0.1`(localhost)에만 바인딩됨. 외부 접속을 받으려면 `0.0.0.0`에 바인딩해야 합니다. (도커 컨테이너 안에서 특히 자주 발생)

### "Port already in use" 해결
```bash
sudo lsof -i :8080          # 누가 쓰는지 확인
kill <PID>                   # 정상 종료 요청
```

## 3. 연결 테스트

```bash
ping 8.8.8.8                 # ICMP로 도달 가능 여부 (클라우드는 ICMP를 막아 둔 경우 많음)
traceroute google.com        # 경로 추적 (Linux: traceroute, Windows: tracert)
mtr google.com               # ping + traceroute 실시간

nc -zv db.example.com 3306   # ★ 특정 포트가 열려 있는지 (TCP 연결 테스트)
telnet db.example.com 3306   # 같은 용도 (구식)
```

> ping이 안 돼도 서비스는 정상일 수 있습니다. **포트 단위 확인은 `nc -zv`** 가 정확합니다.

## 4. DNS 확인

```bash
nslookup api.example.com
dig api.example.com           # 상세 (A 레코드, TTL)
dig +short api.example.com    # IP만
dig @8.8.8.8 api.example.com  # 특정 DNS 서버로 질의
```

## 5. curl: HTTP 테스트의 기본

```bash
curl https://api.example.com/health                # GET
curl -i https://api.example.com/health             # 응답 헤더 포함
curl -I https://example.com                        # 헤더만 (HEAD)
curl -v https://example.com                        # 상세 (TLS 핸드셰이크, 요청·응답 헤더)
curl -L http://example.com                         # 리다이렉트 따라가기

# POST JSON
curl -X POST https://api.example.com/members \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer $TOKEN" \
     -d '{"name":"kim","email":"a@b.com"}'

# 응답 시간 측정
curl -o /dev/null -s -w "dns:%{time_namelookup} connect:%{time_connect} tls:%{time_appconnect} total:%{time_total} code:%{http_code}\n" https://example.com

# 파일 다운로드
curl -O https://example.com/file.tar.gz
wget https://example.com/file.tar.gz
```

> 서버 안에서 `curl localhost:8080/actuator/health`가 되는데 밖에서 안 된다면, **앱 문제가 아니라 네트워크(방화벽, 보안 그룹, 로드밸런서) 문제**입니다.

## 6. 방화벽

| 도구 | 배포판 |
|---|---|
| `ufw` | Ubuntu (iptables/nftables를 쉽게 쓰는 프론트엔드) |
| `firewalld` | RHEL 계열 |
| `iptables` / `nftables` | 커널 패킷 필터 (저수준) |

```bash
# Ubuntu ufw
sudo ufw allow 22/tcp
sudo ufw allow 80,443/tcp
sudo ufw enable
sudo ufw status

# RHEL firewalld
sudo firewall-cmd --permanent --add-port=8080/tcp
sudo firewall-cmd --reload
```

> **클라우드(AWS)에서는 OS 방화벽보다 보안 그룹(Security Group)** 이 먼저 적용됩니다. EC2 OS 방화벽은 꺼 두고 보안 그룹으로 관리하는 경우가 많습니다. (→ `06.AWS/02.VPC와네트워킹.md`)

## 7. 트러블슈팅: "접속이 안 돼요"

**아래 계층부터 위로** 하나씩 확인합니다.

```
[1] DNS가 맞는 IP를 주는가?       dig +short api.example.com
        ↓
[2] 서버까지 네트워크가 닿는가?     nc -zv <IP> 443  (ping은 참고만)
        ↓ 실패 → 보안 그룹, NACL, 방화벽, 라우팅(퍼블릭 IP, IGW) 확인
[3] 서버에서 프로세스가 떠 있는가?  systemctl status myapp / docker ps
        ↓
[4] 포트를 LISTEN 중인가?          ss -tlnp | grep 8080  (0.0.0.0인지 127.0.0.1인지)
        ↓
[5] 서버 안에서 응답하는가?         curl -i localhost:8080/actuator/health
        ↓ 실패 → 애플리케이션 로그 확인
[6] 중간 프록시/로드밸런서는?       Nginx 설정, ALB 대상 그룹 헬스 체크 상태
        ↓
[7] 애플리케이션 로그               journalctl -u myapp -f / tail -f app.log / docker logs
```

### 상황별 단서
| 증상 | 의심할 곳 |
|---|---|
| `Connection refused` | 서버까지는 도달했지만 **그 포트에 프로세스가 없음** (앱 죽음, 포트 다름, 127.0.0.1 바인딩) |
| `Connection timed out` | 패킷이 **중간에서 버려짐** → 방화벽, 보안 그룹, 라우팅 |
| `Could not resolve host` | **DNS** 문제 |
| `502 Bad Gateway` | 프록시(Nginx, ALB)는 정상, **뒤의 앱 서버가 응답 X** |
| `504 Gateway Timeout` | 뒤의 앱 서버가 **너무 느림** (DB 쿼리, 외부 API) |
| `SSL certificate problem` | 인증서 만료, 도메인 불일치, 중간 인증서 누락 |

> **refused vs timeout** 구분이 핵심입니다. refused는 "문은 있는데 아무도 없음", timeout은 "문까지 가는 길이 막힘".

## 8. 패킷 캡처 (심화)


## 9. 면접 질문

1. **특정 포트를 어떤 프로세스가 쓰는지 확인하려면?**
   → `ss -tlnp` 또는 `lsof -i :포트`를 씁니다.
2. **Connection refused와 Connection timed out의 차이는?**
   → refused는 서버에 도달했지만 해당 포트에 LISTEN 중인 프로세스가 없는 것이고, timeout은 방화벽·보안 그룹·라우팅 때문에 패킷이 중간에서 응답 없이 버려지는 것입니다.
3. **서버 안에서는 되는데 외부에서 접속이 안 되면?**
   → 앱이 127.0.0.1에만 바인딩됐는지, OS 방화벽과 클라우드 보안 그룹이 포트를 허용하는지, 로드밸런서 설정을 확인합니다.
4. **502와 504의 차이는?**
   → 502는 게이트웨이가 뒤 서버로부터 잘못된 응답을 받거나 연결에 실패한 것이고, 504는 뒤 서버의 응답이 시간 안에 오지 않은 것입니다.

## 핵심 정리
- 정보: `ip a`, `ip route`, `ss -tlnp`, `lsof -i :포트`
- 테스트: `nc -zv`(포트), `dig`(DNS), `curl -v`(HTTP)
- 0.0.0.0 vs 127.0.0.1 바인딩
- 진단 순서: DNS → 네트워크 도달 → 프로세스 → 포트 → 로컬 응답 → 프록시 → 로그
- refused(프로세스 없음) vs timeout(방화벽·라우팅)
