# 01. 웹 서버와 WAS

> **학습 목표**
> - 정적 콘텐츠와 동적 콘텐츠의 차이를 설명할 수 있다.
> - 웹 서버와 WAS의 역할 차이, 둘을 함께 쓰는 이유를 설명할 수 있다.
> - Tomcat의 스레드 풀 동작과 주요 설정을 설명할 수 있다.
> - 포워드 프록시와 리버스 프록시를 구분할 수 있다.

---

## 1. 정적 콘텐츠 vs 동적 콘텐츠

| 구분 | 정적 (Static) | 동적 (Dynamic) |
|---|---|---|
| 의미 | **이미 만들어진 파일** 그대로 전달 | 요청마다 **프로그램이 실행되어 생성** |
| 예 | HTML, CSS, JS, 이미지, React 빌드 결과물 | 로그인한 사용자의 주문 목록 API, 검색 결과 |
| 처리 | 파일을 읽어서 보냄 → 빠름 | DB 조회, 비즈니스 로직 → 상대적으로 느림 |

---

## 2. 웹 서버 vs WAS

| 구분 | 웹 서버 (Web Server) | WAS (Web Application Server) |
|---|---|---|
| 역할 | **정적 콘텐츠** 제공, HTTP 요청 처리 | **동적 콘텐츠** 생성 (애플리케이션 코드 실행) |
| 예 | **Nginx**, Apache HTTP Server | **Tomcat**, Jetty, Undertow, JBoss/WildFly |
| 강점 | 수많은 동시 연결, 정적 파일, 프록시, TLS, 캐싱 | 비즈니스 로직, DB 연동, 트랜잭션 |

> Spring Boot는 **Tomcat이 내장(Embedded Tomcat)** 되어 있어 `java -jar`만으로 WAS가 실행됩니다. WAS도 정적 파일을 줄 수 있지만, 그 일을 웹 서버에 맡기면 더 효율적입니다.

---

## 3. 왜 둘을 함께 쓰는가?

```
[클라이언트] ──HTTPS──> [Nginx (웹 서버)] ──HTTP──> [Spring Boot (WAS) × N]
                         │                                   │
                         ├ 정적 파일 직접 응답                   └ API, DB 연동
                         ├ TLS 종료
                         ├ 로드밸런싱, 캐싱, 압축
                         └ 요청 제한, 보안 필터
```

| 이유 | 설명 |
|---|---|
| **역할 분리 (효율)** | 정적 파일은 웹 서버가 빠르게 처리 → WAS는 비싼 동적 처리에 집중 |
| **보안** | WAS를 외부에 직접 노출하지 않음, 웹 서버가 앞단 방패 |
| **로드밸런싱** | 웹 서버가 여러 WAS로 요청 분산 |
| **무중단 배포** | WAS 하나씩 교체하는 동안 웹 서버가 다른 WAS로 요청 전달 |
| **TLS 처리** | 인증서·암호화는 웹 서버에서 한 번에 |
| **장애 격리** | WAS가 죽어도 웹 서버가 에러 페이지 응답 |

> 클라우드에서는 이 앞단 역할을 **AWS ALB, CloudFront**가 대신하는 경우가 많습니다. 정적 프론트엔드(React)는 **S3 + CloudFront**로, API는 **ALB → Spring Boot**로 분리하는 구성이 흔합니다.

## 4. Tomcat 동작과 스레드 풀

### 요청 처리 흐름
```
요청 → [Connector] → [스레드 풀에서 스레드 할당] → Filter → DispatcherServlet → Controller ...
                                                                    ↓
                                                    응답 후 스레드는 풀로 반납
```
- Tomcat은 기본적으로 **요청 하나당 스레드 하나**(Thread-per-request)
- 스레드를 매번 만들면 비싸므로 **스레드 풀**을 미리 만들어 재사용

### 주요 설정 (Spring Boot 기본값)
```yaml
server:
  tomcat:
    threads:
      max: 200            # 최대 작업 스레드 수
      min-spare: 10       # 최소 유지 스레드
    max-connections: 8192 # 동시에 유지할 수 있는 최대 연결 수
    accept-count: 100     # 연결이 꽉 찼을 때 OS 대기 큐 크기
    connection-timeout: 20s
```

```
동시 요청 증가 시
1) 스레드 200개까지 처리
2) 스레드가 모두 바쁘면 요청은 연결된 채 대기 (max-connections까지)
3) 연결 수도 꽉 차면 OS 대기 큐 (accept-count)
4) 그것도 차면 → 연결 거부 / 타임아웃
```

| 스레드가 너무 적으면 | 스레드가 너무 많으면 |
|---|---|
| 요청 대기 증가, 응답 지연 | 메모리 증가(스레드당 스택), 컨텍스트 스위칭 증가, **DB 커넥션 풀보다 많으면 결국 DB에서 대기** |

> 스레드 수는 DB 커넥션 풀(HikariCP), 외부 API 호출 시간과 함께 고려해야 합니다. 느린 외부 API 호출이 스레드를 모두 붙잡으면 서버 전체가 응답 불가가 됩니다 → 타임아웃 설정, 서킷 브레이커 (→ `09.아키텍처와운영/03.고가용성과장애대응.md`)

> **Java 21 가상 스레드**: `spring.threads.virtual.enabled=true` (Spring Boot 3.2+) 로 요청을 가상 스레드에서 처리하면, I/O 대기 중에 OS 스레드를 점유하지 않아 동시 처리량이 크게 늘어납니다.

## 5. 프록시 (Proxy)

### 포워드 프록시 (Forward Proxy)
```
[클라이언트] → [포워드 프록시] → [인터넷의 서버들]
```
- **클라이언트 쪽**에 위치, 클라이언트를 대신해 외부로 요청
- 용도: 회사 내부망 인터넷 접근 제어, 캐싱, 클라이언트 IP 숨김

### 리버스 프록시 (Reverse Proxy)
```
[클라이언트들] → [리버스 프록시 (Nginx)] → [내부 서버들]
```
- **서버 쪽**에 위치, 서버를 대신해 요청을 받아 내부 서버로 전달
- 클라이언트는 실제 서버가 무엇인지 모름
- 용도: **로드밸런싱, TLS 종료, 캐싱, 보안, 서버 숨김**

| 비교 | 포워드 프록시 | 리버스 프록시 |
|---|---|---|
| 위치 | 클라이언트 앞 | 서버 앞 |
| 숨기는 대상 | 클라이언트 | 서버 |
| 예 | 회사 프록시 서버, VPN 비슷한 용도 | **Nginx, AWS ALB, Cloudflare** |

### 프록시 뒤에서 클라이언트 IP 알기
프록시를 거치면 WAS가 보는 요청 IP는 **프록시의 IP**입니다. 원래 클라이언트 IP는 헤더로 전달합니다.
```
X-Forwarded-For: 203.0.113.7, 10.0.1.5     (원래 클라이언트, 거쳐 간 프록시들)
X-Forwarded-Proto: https                    (원래 프로토콜)
X-Real-IP: 203.0.113.7
```
```yaml
# Spring Boot가 이 헤더를 신뢰하게 설정
server:
  forward-headers-strategy: native   # 또는 framework
```
> 이 설정이 없으면 리다이렉트 URL이 `http://`로 만들어지거나, 로그에 모든 사용자 IP가 로드밸런서 IP로 찍힙니다.

## 6. 면접 질문

1. **웹 서버와 WAS의 차이는?**
   → 웹 서버는 정적 콘텐츠 제공과 HTTP 처리를, WAS는 애플리케이션 코드를 실행해 동적 콘텐츠를 만듭니다.
2. **웹 서버와 WAS를 분리하는 이유는?**
   → 정적 처리와 동적 처리를 분리해 효율을 높이고, WAS를 외부에 노출하지 않아 보안을 강화하며, 로드밸런싱·TLS 종료·무중단 배포를 앞단에서 처리할 수 있기 때문입니다.
3. **리버스 프록시란?**
   → 서버 앞에서 클라이언트 요청을 대신 받아 내부 서버로 전달하는 서버로, 로드밸런싱·TLS 종료·캐싱·서버 은닉에 씁니다.
4. **Tomcat 스레드 풀이 가득 차면?**
   → 새 요청은 연결된 채 대기하고, 최대 연결 수와 대기 큐까지 차면 연결이 거부되거나 타임아웃이 발생합니다.

---

## 핵심 정리
- 정적 → 웹 서버(Nginx), 동적 → WAS(Tomcat, Spring Boot 내장)
- 분리 이유: 효율, 보안, 로드밸런싱, TLS, 무중단 배포
- Tomcat: 요청당 스레드, 기본 최대 200, DB 커넥션 풀과 함께 조정
- 리버스 프록시 = 서버 앞단, X-Forwarded-For로 원래 IP 전달
