# 02. Nginx와 리버스 프록시

> **학습 목표**
> - Nginx의 이벤트 기반 구조가 많은 연결을 처리하는 원리를 설명할 수 있다.
> - Nginx 설정 파일 구조(http, server, location)를 읽고 작성할 수 있다.
> - Spring Boot 앞단 리버스 프록시, 정적 파일 서빙, HTTPS 설정을 할 수 있다.

---

## 1. Nginx란?

고성능 **웹 서버 + 리버스 프록시 + 로드밸런서**입니다. 전 세계 웹 서버 점유율 최상위권입니다.

### Apache vs Nginx
| 비교 | Apache (prefork/worker) | Nginx |
|---|---|---|
| 구조 | **연결(요청)당 프로세스·스레드** | **이벤트 기반, 비동기 논블로킹** |
| 동시 연결 | 연결이 늘면 메모리·컨텍스트 스위칭 급증 | 적은 워커로 수만 연결 처리 |
| 설정 | `.htaccess`로 디렉토리별 설정 | 중앙 설정 파일 |
| 강점 | 모듈 풍부, 동적 처리(mod_php) | **정적 파일, 프록시, 대량 동시 연결** |

### 이벤트 기반 구조
```
[Master 프로세스]  설정 읽기, 워커 관리 (root)
   ├── [Worker 1]  ┐  각 워커는 싱글 스레드 이벤트 루프로
   ├── [Worker 2]  │  epoll을 이용해 수천 개 연결을 동시에 감시하고
   └── [Worker N]  ┘  준비된 이벤트만 처리 (보통 CPU 코어 수만큼)
```
> 이것이 C10K 문제(동시 연결 1만 개)를 해결한 방식입니다. (→ CS 자료 `03.운영체제/08.파일시스템과입출력.md`의 I/O 멀티플렉싱)

## 2. 설치와 기본 명령

```bash
sudo apt install -y nginx
sudo systemctl enable --now nginx

sudo nginx -t                  # ★ 설정 문법 검사 (적용 전 반드시)
sudo systemctl reload nginx    # 무중단으로 설정 반영
sudo tail -f /var/log/nginx/access.log /var/log/nginx/error.log
```

### 파일 위치 (Ubuntu)
| 경로 | 용도 |
|---|---|
| `/etc/nginx/nginx.conf` | 메인 설정 |
| `/etc/nginx/conf.d/*.conf` | 사이트별 설정 (include됨) |
| `/etc/nginx/sites-available/`, `sites-enabled/` | Debian 계열 방식 (심볼릭 링크로 활성화) |
| `/var/log/nginx/` | 접근·에러 로그 |
| `/usr/share/nginx/html`, `/var/www/html` | 기본 정적 파일 위치 |

## 3. 설정 구조

```nginx
user www-data;
worker_processes auto;          # CPU 코어 수만큼 워커

events {
    worker_connections 1024;    # 워커당 최대 연결
}

http {                          # HTTP 설정 전체
    include       mime.types;
    sendfile      on;
    keepalive_timeout 65;
    gzip on;

    server {                    # 가상 호스트 (도메인·포트별)
        listen 80;
        server_name example.com;

        location / {            # URL 경로별 처리
            root /var/www/html;
            index index.html;
        }
    }
}
```

```
http
 └── server (도메인/포트 단위)
      └── location (경로 단위)
```

### location 매칭 우선순위
| 문법 | 의미 | 우선순위 |
|---|---|---|
| `location = /exact` | 정확히 일치 | 1 (가장 높음) |
| `location ^~ /static/` | 접두사, 일치하면 정규식 검사 안 함 | 2 |
| `location ~ \.php$` / `~*` | 정규식 (대소문자 구분 / 무시) | 3 (먼저 나온 것) |
| `location /api/` | 일반 접두사 (가장 긴 것) | 4 |

## 4. 실전 설정: Spring Boot 앞단

```nginx
upstream app_servers {                 # 백엔드 서버 그룹
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    keepalive 32;                      # 백엔드와 연결 재사용
}

server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;    # HTTP → HTTPS 리다이렉트
}

server {
    listen 443 ssl;
    http2 on;                                 # Nginx 1.25.1+ 문법 (이전 버전은 listen 443 ssl http2;)
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    client_max_body_size 20M;                 # 업로드 크기 제한 (기본 1M → 413 에러 원인)

    # React 빌드 결과물 (SPA)
    location / {
        root /var/www/frontend;
        try_files $uri $uri/ /index.html;     # 없는 경로는 index.html로 (클라이언트 라우팅)
    }

    # 정적 리소스 캐싱
    location ~* \.(js|css|png|jpg|svg|woff2)$ {
        root /var/www/frontend;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # API → Spring Boot
    location /api/ {
        proxy_pass http://app_servers;        # 끝에 / 없음 → /api/ 경로 그대로 전달
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;               # 이 시간 넘으면 504
    }

    # WebSocket
    location /ws/ {
        proxy_pass http://app_servers;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

### proxy_pass 끝의 `/` 주의
| 설정 | 요청 `/api/members` → 백엔드로 전달되는 경로 |
|---|---|
| `location /api/ { proxy_pass http://app; }` | `/api/members` (그대로) |
| `location /api/ { proxy_pass http://app/; }` | `/members` (**location 부분이 잘림**) |

## 6. 그 밖의 유용한 기능

### 요청 수 제한 (Rate Limiting)
```nginx
http {
    limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;   # IP당 초당 10개
    server {
        location /api/ {
            limit_req zone=api burst=20 nodelay;
            proxy_pass http://app_servers;
        }
    }
}
```
→ 초과 시 503 (`limit_req_status 429;`로 변경 가능)

### 접근 로그 포맷에 응답 시간 추가
```nginx
log_format timed '$remote_addr "$request" $status $body_bytes_sent '
                 'rt=$request_time urt=$upstream_response_time';
access_log /var/log/nginx/access.log timed;
```
- `$request_time`: 전체 처리 시간, `$upstream_response_time`: 백엔드 응답 시간 → 느린 API 찾기

### 자주 만나는 에러
| 에러 | 원인 |
|---|---|
| **413** Request Entity Too Large | `client_max_body_size` 부족 |
| **502** Bad Gateway | 백엔드가 꺼져 있음, upstream 주소·포트 오류 |
| **504** Gateway Timeout | 백엔드가 `proxy_read_timeout` 안에 응답 X |
| 403 Forbidden | 정적 파일 권한 (www-data가 읽을 수 없음), index 파일 없음 |
| 새로고침하면 404 (SPA) | `try_files ... /index.html` 누락 |

## 7. 면접 질문

1. **Nginx가 많은 동시 연결을 처리할 수 있는 이유는?**
   → 연결마다 스레드를 만들지 않고, 소수의 워커 프로세스가 epoll 기반 이벤트 루프로 비동기 논블로킹 처리하기 때문입니다.
2. **리버스 프록시 설정 시 X-Forwarded-For 헤더를 넣는 이유는?**
   → 백엔드가 보는 요청 IP는 Nginx IP이므로, 원래 클라이언트 IP와 프로토콜을 전달하기 위해서입니다.
3. **설정을 바꾼 뒤 restart 대신 reload를 쓰는 이유는?**
   → reload는 새 워커로 설정을 반영하고 기존 연결은 마무리하게 해서 무중단으로 적용되기 때문입니다. 적용 전에는 `nginx -t`로 문법을 검사합니다.

## 핵심 정리
- Nginx = 이벤트 기반 워커 → 대량 동시 연결
- 구조: http → server(도메인) → location(경로)
- 리버스 프록시: `upstream` + `proxy_pass` + `X-Forwarded-*` 헤더
- `nginx -t` → `reload`, 413/502/504 원인 기억
