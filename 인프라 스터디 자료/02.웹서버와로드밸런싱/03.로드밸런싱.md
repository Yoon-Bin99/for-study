# 03. 로드밸런싱 (Load Balancing)

> **학습 목표**
> - 로드밸런서가 필요한 이유와 L4/L7 로드밸런서의 차이를 설명할 수 있다.
> - 로드밸런싱 알고리즘(라운드 로빈, 최소 연결, IP 해시 등)을 비교할 수 있다.
> - 헬스 체크와 세션 고정(Sticky Session)의 개념과 문제점을 설명할 수 있다.
> - AWS ELB(ALB, NLB)의 특징을 설명할 수 있다.

---

## 1. 왜 필요한가?

```
               ┌──> [서버 1]
[사용자들] ──> [LB] ──> [서버 2]
               └──> [서버 3]
```

| 목적 | 설명 |
|---|---|
| **부하 분산** | 트래픽을 여러 서버로 나눠 한 서버에 몰리지 않게 |
| **고가용성** | 서버 하나가 죽으면 **헬스 체크로 감지**해 나머지로만 보냄 |
| **수평 확장** | 서버를 추가·제거해도 사용자는 LB 주소 하나만 앎 |
| **무중단 배포** | 서버를 하나씩 빼고 배포하고 다시 넣음 |
| TLS 종료 | 인증서 관리를 한 곳에서 |

---

## 2. L4 vs L7 로드밸런서

| 비교 | L4 (전송 계층) | L7 (응용 계층) |
|---|---|---|
| 판단 기준 | **IP + 포트** | **URL 경로, 호스트, 헤더, 쿠키, HTTP 메서드** |
| 패킷 내용 | 보지 않음 | HTTP 내용을 해석 |
| 속도 | **빠름**, 지연 적음 | 상대적으로 느림 |
| 기능 | 단순 분산 | 경로 기반 라우팅, TLS 종료, 헤더 조작, WAF 연동 |
| 프로토콜 | TCP, UDP | HTTP, HTTPS, gRPC, WebSocket |
| 예 | **AWS NLB**, LVS, HAProxy(TCP 모드) | **AWS ALB**, Nginx, HAProxy(HTTP 모드), Envoy |

### L7 경로 기반 라우팅 예
```
api.example.com/users/*   → 회원 서비스
api.example.com/orders/*  → 주문 서비스
admin.example.com/*       → 관리자 서비스     (호스트 기반)
```
→ **MSA**에서 L7 로드밸런서(또는 API 게이트웨이)가 필수적인 이유입니다.

## 3. 로드밸런싱 알고리즘

| 알고리즘 | 동작 | 적합한 경우 |
|---|---|---|
| **라운드 로빈** (Round Robin) | 순서대로 돌아가며 1 → 2 → 3 → 1 ... | 서버 성능이 같고 요청 처리 시간이 비슷할 때 (**기본값**인 경우 많음) |
| 가중 라운드 로빈 (Weighted) | 서버 성능에 비례해 가중치 (3:1) | 서버 사양이 다를 때, **카나리 배포**(새 버전에 10%) |
| **최소 연결** (Least Connections) | 현재 연결이 가장 적은 서버로 | 요청마다 처리 시간이 크게 다를 때 (긴 연결, WebSocket) |
| 최소 응답 시간 | 응답이 가장 빠른 서버로 | |
| **IP 해시** | 클라이언트 IP 해시값으로 서버 고정 | 같은 사용자를 같은 서버로 (세션 유지) |
| 랜덤 / 2개 중 덜 바쁜 쪽 (Power of Two Choices) | 무작위 2개 뽑아 연결이 적은 쪽 | 대규모 분산 환경 |

```nginx
# Nginx
upstream app {
    least_conn;                    # 최소 연결 (기본은 라운드 로빈)
    server 10.0.1.10:8080 weight=3;
    server 10.0.1.11:8080 weight=1;
    server 10.0.1.12:8080 backup;  # 다른 서버가 모두 죽었을 때만
}
```

## 4. 헬스 체크 (Health Check)

로드밸런서는 주기적으로 서버 상태를 확인해 **비정상 서버로는 트래픽을 보내지 않습니다.**

```
LB → GET /actuator/health (10초마다)
     200 OK  연속 2번 → Healthy   (트래픽 전송)
     실패    연속 3번 → Unhealthy (트래픽 차단)
```

### Spring Boot Actuator
```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      probes:
        enabled: true      # /actuator/health/liveness, /readiness
```

> **헬스 체크 엔드포인트 설계 주의**: 헬스 체크에서 DB·외부 API까지 확인하면, DB가 잠깐 느려질 때 **모든 서버가 동시에 Unhealthy**가 되어 전체 장애로 번질 수 있습니다. 로드밸런서용 헬스 체크는 "이 서버가 요청을 받을 수 있는가"만 가볍게 확인하는 것이 일반적입니다. (Kubernetes의 liveness/readiness 구분 → `04.쿠버네티스/05.스케일링과배포전략.md`)

## 5. 세션 고정 (Sticky Session)

로그인 세션을 서버 메모리에 저장하면, 다음 요청이 **다른 서버로 가면 로그인이 풀립니다.**

### 해결 1: Sticky Session
LB가 쿠키나 IP 해시로 **같은 사용자를 항상 같은 서버로** 보냄
- 문제: 특정 서버에 부하 쏠림, **그 서버가 죽으면 세션 유실**, 확장·배포 시 불편

### 해결 2: 세션 외부 저장소 (권장)
```
[서버 1] ┐
[서버 2] ├──> [Redis (세션 저장소)]
[서버 3] ┘
```
- Spring Session + Redis → 어느 서버로 가도 세션 조회 가능

### 해결 3: 무상태 인증 (JWT)
서버가 세션을 저장하지 않음 → 로드밸런싱이 자유로움

> **서버를 무상태(Stateless)로 만드는 것**이 수평 확장의 핵심입니다. 세션, 업로드 파일(→ S3), 캐시(→ Redis)를 서버 밖으로 빼세요.

## 6. AWS ELB (Elastic Load Balancing)

| 종류 | 계층 | 특징 | 사용처 |
|---|---|---|---|
| **ALB** (Application) | L7 | 경로·호스트 기반 라우팅, HTTPS 종료(ACM 인증서), WAF 연동, 대상: EC2·IP·Lambda·ECS/EKS | **웹 서비스, API, MSA** |
| **NLB** (Network) | L4 | 초저지연, 수백만 RPS, **고정 IP(Elastic IP)**, TCP/UDP | 게임, IoT, 고정 IP가 필요한 경우 |
| GWLB (Gateway) | L3 | 방화벽 등 보안 장비로 트래픽 전달 | 네트워크 보안 장비 |
| CLB (Classic) | L4/L7 | 구세대 | 사용 지양 |

### ALB 구성 요소
```
[ALB]
 └── 리스너 (HTTPS:443)         ← 포트·프로토콜, 인증서
      └── 규칙 (Rule)           ← 경로 /api/* → 대상 그룹 A, 호스트 admin.* → B
           └── 대상 그룹 (Target Group)
                ├── EC2 / Pod IP 1  (헬스 체크)
                └── EC2 / Pod IP 2
```

- ALB는 **여러 가용 영역(AZ)** 에 걸쳐 배치되어 그 자체가 고가용성
- ALB의 IP는 바뀔 수 있으므로 **DNS 이름**(Route 53 Alias)으로 연결
- **연결 드레이닝 (Deregistration Delay)**: 대상 그룹에서 서버를 뺄 때, 처리 중인 요청이 끝날 때까지 기다림 (기본 300초) → 무중단 배포에 중요

## 7. 로드밸런서 자체의 장애는?

로드밸런서가 하나면 그게 **단일 장애점(SPOF)** 이 됩니다.
- 온프레미스: LB를 2대(Active-Standby) + **VRRP/Keepalived**로 가상 IP 공유
- 클라우드: ALB/NLB는 AWS가 **여러 AZ에 분산된 관리형 서비스**로 제공
- DNS 레벨 분산: Route 53 헬스 체크 + 장애 조치(Failover) 라우팅

## 8. 면접 질문

1. **L4와 L7 로드밸런서의 차이는?**
   → L4는 IP와 포트만 보고 빠르게 분산하고, L7은 URL·헤더·쿠키 같은 HTTP 내용을 보고 경로 기반 라우팅 등 세밀한 분산을 합니다.
2. **로드밸런싱 알고리즘에는 어떤 것이 있나요?**
   → 라운드 로빈, 가중 라운드 로빈, 최소 연결, IP 해시 등이 있으며, 요청 처리 시간이 들쭉날쭉하면 최소 연결이 유리합니다.
3. **Sticky Session의 문제점과 대안은?**
   → 부하가 쏠리고 해당 서버 장애 시 세션이 유실됩니다. Redis 같은 외부 세션 저장소나 JWT로 서버를 무상태로 만드는 것이 대안입니다.
4. **ALB와 NLB의 차이는?**
   → ALB는 L7으로 경로·호스트 기반 라우팅과 HTTPS 종료를 지원해 웹 서비스에, NLB는 L4로 초저지연·고정 IP를 제공해 TCP/UDP 트래픽에 적합합니다.

---

## 핵심 정리
- LB = 부하 분산 + 헬스 체크로 고가용성 + 수평 확장
- L4(IP·포트, NLB) vs L7(URL·헤더, ALB·Nginx)
- 알고리즘: 라운드 로빈 / 가중치 / 최소 연결 / IP 해시
- 서버는 무상태로 → 세션은 Redis 또는 JWT
- ALB = 리스너 → 규칙 → 대상 그룹(헬스 체크), 연결 드레이닝
