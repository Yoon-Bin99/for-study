# 01. 가상화와 컨테이너

> **학습 목표**
> - 가상 머신(VM)과 컨테이너의 구조적 차이를 그림으로 설명할 수 있다.
> - 컨테이너를 가능하게 하는 리눅스 기술(namespace, cgroup)을 설명할 수 있다.
> - 도커의 구성 요소(이미지, 컨테이너, 레지스트리)와 기본 명령어를 사용할 수 있다.

---

## 1. 왜 컨테이너인가?

> "제 컴퓨터에서는 되는데요?"

개발 PC, 테스트 서버, 운영 서버의 **OS, 라이브러리 버전, 설정이 달라서** 생기는 문제를 해결합니다.

| 기존 방식의 문제 | 컨테이너의 해결 |
|---|---|
| 서버마다 JDK·라이브러리 버전 차이 | 애플리케이션 + 실행 환경을 **이미지 하나로 묶음** |
| 서버 세팅 문서·수작업 | Dockerfile로 **코드화**, 언제든 같은 환경 재현 |
| 한 서버에 여러 앱 → 의존성 충돌 | 컨테이너마다 **격리** |
| 서버 하나 준비에 수십 분~수일 | 컨테이너는 **수 초** 만에 실행 |

---

## 2. 가상 머신 vs 컨테이너

```
        가상 머신 (VM)                        컨테이너
+-------+-------+-------+           +-------+-------+-------+
| App A | App B | App C |           | App A | App B | App C |
| Libs  | Libs  | Libs  |           | Libs  | Libs  | Libs  |
|게스트OS|게스트OS|게스트OS|           +-------+-------+-------+
+-------+-------+-------+           |   컨테이너 엔진 (Docker)  |
|     하이퍼바이저          |           +-----------------------+
+-----------------------+           |   호스트 OS (리눅스 커널)  |
|       호스트 OS          |           +-----------------------+
+-----------------------+           |       하드웨어            |
|       하드웨어            |           +-----------------------+
+-----------------------+
```

| 비교 | 가상 머신 | 컨테이너 |
|---|---|---|
| 가상화 대상 | **하드웨어** (CPU, 메모리, 디스크를 가상화) | **OS 레벨** (프로세스 격리) |
| OS | VM마다 **게스트 OS 전체** | **호스트 커널 공유** |
| 크기 | 수 GB | 수십~수백 MB |
| 시작 시간 | 수십 초~분 | **수 초 이하** |
| 격리 수준 | **강함** (커널까지 분리) | 상대적으로 약함 (커널 공유) |
| 밀도 | 서버당 수~수십 개 | 서버당 수십~수백 개 |
| 예 | VMware, VirtualBox, KVM, **AWS EC2** | **Docker**, containerd, Podman |

### 하이퍼바이저 종류
| 타입 | 설명 | 예 |
|---|---|---|
| Type 1 (베어메탈) | 하드웨어 위에 바로 설치 | VMware ESXi, Xen, KVM, AWS Nitro |
| Type 2 (호스트형) | 호스트 OS 위에 프로그램으로 설치 | VirtualBox, VMware Workstation |

> 컨테이너가 VM을 대체하는 것이 아니라 **함께** 씁니다. AWS에서는 EC2(VM) 위에서 컨테이너를 실행합니다.

> **Windows·Mac에서 도커는?** 리눅스 커널이 필요하므로 Docker Desktop은 내부에 가벼운 리눅스 VM(WSL2, macOS 가상화)을 띄우고 그 안에서 컨테이너를 실행합니다.

## 3. 컨테이너를 만드는 리눅스 기술

컨테이너는 특별한 것이 아니라 **격리되고 자원이 제한된 리눅스 프로세스**입니다.

### namespace: "무엇을 볼 수 있는가" (격리)
| namespace | 격리하는 것 |
|---|---|
| **PID** | 프로세스 ID → 컨테이너 안의 앱은 자신이 PID 1이라고 봄 |
| **NET** | 네트워크 인터페이스, IP, 포트 |
| **MNT** | 파일시스템 마운트 → 자기만의 루트(/) |
| UTS | 호스트 이름 |
| IPC | 프로세스 간 통신 자원 |
| USER | 사용자·그룹 ID |

### cgroup (Control Group): "얼마나 쓸 수 있는가" (자원 제한)
- CPU, 메모리, 디스크 I/O, 네트워크 사용량을 **제한**
- 메모리 제한을 넘으면 → 커널이 컨테이너 프로세스를 **OOM Kill** (종료 코드 137)

```bash
docker run -m 512m --cpus 1.5 myapp     # 메모리 512MB, CPU 1.5개로 제한
```

### Union File System (OverlayFS)
- 이미지를 **읽기 전용 레이어**들의 겹으로 구성하고, 컨테이너는 그 위에 **얇은 쓰기 레이어**만 추가
- 같은 이미지로 컨테이너를 100개 띄워도 이미지 레이어는 **공유** → 빠르고 저장 공간 절약

## 4. 도커의 구성 요소

```
  [Dockerfile] ──docker build──> [이미지] ──docker run──> [컨테이너]
                                    │  ↑
                         docker push│  │docker pull
                                    ↓  │
                              [레지스트리 (Docker Hub, AWS ECR)]
```

| 개념 | 비유 | 설명 |
|---|---|---|
| **이미지 (Image)** | 클래스, 설계도 | 실행에 필요한 파일·설정을 담은 **읽기 전용 템플릿** |
| **컨테이너 (Container)** | 객체, 인스턴스 | 이미지를 실행한 **프로세스** (쓰기 레이어 추가) |
| **레지스트리 (Registry)** | GitHub | 이미지 저장소 (Docker Hub, **AWS ECR**, GHCR) |
| **Dockerfile** | 소스 코드 | 이미지를 만드는 명령서 |

### 도커 아키텍처
```
[docker CLI] ──REST API──> [dockerd (도커 데몬)] ──> [containerd] ──> [runc] → 컨테이너 프로세스
```
- 표준화: **OCI (Open Container Initiative)** 이미지·런타임 규격 → 도커로 만든 이미지를 쿠버네티스(containerd)에서도 그대로 실행

## 5. 기본 명령어

### 이미지
```bash
docker pull nginx:1.27             # 이미지 다운로드 (태그 생략 시 :latest)
docker images                      # 로컬 이미지 목록
docker rmi nginx:1.27              # 이미지 삭제
docker image prune -a              # 사용하지 않는 이미지 정리
```

### 컨테이너 실행
```bash
docker run -d --name web -p 8080:80 nginx:1.27
```
| 옵션 | 의미 |
|---|---|
| `-d` | 백그라운드(detached) 실행 |
| `--name web` | 컨테이너 이름 |
| `-p 8080:80` | **호스트 8080 → 컨테이너 80** 포트 연결 |
| `-e KEY=value` | 환경 변수 |
| `-v /host/path:/container/path` | 볼륨(디렉토리) 연결 |
| `--rm` | 종료 시 자동 삭제 |
| `-it` | 대화형 터미널 (`docker run -it ubuntu bash`) |
| `--restart unless-stopped` | 죽으면 자동 재시작 |

### 컨테이너 관리
```bash
docker ps                  # 실행 중인 컨테이너
docker ps -a               # 종료된 것까지
docker logs -f web         # ★ 로그 (실시간)
docker exec -it web sh     # ★ 실행 중인 컨테이너 안으로 들어가기
docker stop web            # SIGTERM → 10초 후 SIGKILL
docker start web / docker restart web
docker rm web              # 삭제 (-f: 실행 중이어도 강제)
docker inspect web         # 상세 정보 (IP, 마운트, 환경 변수)
docker stats               # CPU·메모리 실시간 사용량
docker system df           # 도커가 쓰는 디스크
docker system prune        # 중지된 컨테이너, 안 쓰는 네트워크·이미지 정리
```

### 컨테이너 생명주기
```
created ──start──> running ──stop──> exited ──rm──> (삭제)
                     │  ↑
                pause│  │unpause
                     ↓  │
                    paused
```

> **컨테이너는 메인 프로세스(PID 1)가 끝나면 종료됩니다.** `docker run ubuntu`가 바로 종료되는 이유는 기본 명령(bash)이 할 일 없이 끝나기 때문입니다.

### 종료 코드로 원인 파악
| 코드 | 의미 |
|---|---|
| 0 | 정상 종료 |
| 1 | 애플리케이션 에러 |
| **137** | SIGKILL (128+9) → 주로 **메모리 초과(OOM)** 또는 강제 종료 |
| 143 | SIGTERM (128+15) → 정상적인 중지 요청 |

## 6. 컨테이너의 특성: 일회용(Immutable)

- 컨테이너 안에서 파일을 수정해도 **컨테이너를 삭제하면 사라집니다.**
- 그래서 **설정은 환경 변수로, 데이터는 볼륨이나 외부 저장소(DB, S3)로** 분리합니다.
- 컨테이너 안에 SSH로 들어가 고치지 않고, **이미지를 새로 만들어 교체**합니다. (Immutable Infrastructure)

> 이것이 **12-Factor App** 원칙과 연결됩니다: 설정은 환경에, 프로세스는 무상태로, 로그는 표준 출력(stdout)으로.

## 7. 면접 질문

1. **VM과 컨테이너의 차이는?**
   → VM은 하이퍼바이저 위에 게스트 OS 전체를 올려 하드웨어를 가상화하고, 컨테이너는 호스트 커널을 공유하며 프로세스를 격리하므로 더 가볍고 빠르지만 격리 수준은 VM보다 약합니다.
2. **컨테이너는 어떻게 격리되나요?**
   → 리눅스 namespace로 프로세스·네트워크·파일시스템 등을 격리하고, cgroup으로 CPU·메모리 사용량을 제한합니다.
3. **이미지와 컨테이너의 차이는?**
   → 이미지는 읽기 전용 템플릿이고, 컨테이너는 이미지를 실행한 인스턴스로 그 위에 쓰기 레이어가 추가됩니다.
4. **컨테이너가 종료 코드 137로 죽었다면?**
   → SIGKILL로 종료된 것으로, 대부분 메모리 제한 초과로 OOM Kill 된 경우입니다.

## 핵심 정리
- 컨테이너 = 앱 + 실행 환경을 묶어 어디서나 동일하게
- VM(하드웨어 가상화, 게스트 OS) vs 컨테이너(커널 공유, 프로세스 격리)
- namespace(격리) + cgroup(자원 제한) + OverlayFS(레이어)
- 이미지(설계도) → 컨테이너(실행), 레지스트리(ECR)
- `run -d -p -e -v`, `logs -f`, `exec -it`, 137 = OOM
