# 02. 도커 이미지와 Dockerfile

> **학습 목표**
> - 이미지 레이어와 빌드 캐시의 원리를 설명할 수 있다.
> - Dockerfile 주요 명령어를 사용해 Spring Boot 이미지를 만들 수 있다.
> - 멀티 스테이지 빌드로 이미지 크기를 줄일 수 있다.
> - 이미지 최적화·보안 모범 사례를 적용할 수 있다.

---

## 1. 이미지 레이어

이미지는 **Dockerfile의 명령 하나하나가 만든 레이어의 겹**입니다.

```
+------------------------------+
| COPY app.jar                 |  ← 레이어 4 (자주 바뀜)
+------------------------------+
| RUN 설정                      |  ← 레이어 3
+------------------------------+
| JRE 설치                      |  ← 레이어 2
+------------------------------+
| 베이스 OS (ubuntu)             |  ← 레이어 1 (거의 안 바뀜)
+------------------------------+
```

- 각 레이어는 **변경 사항(diff)만** 저장하고 읽기 전용
- 같은 레이어는 이미지 간에 **공유** (pull·push 시 이미 있는 레이어는 건너뜀)

### 빌드 캐시
- 빌드 시 **이전과 같은 명령 + 같은 입력 파일**이면 캐시된 레이어를 재사용
- **한 레이어가 바뀌면 그 아래(이후) 레이어는 모두 다시 빌드**

→ **자주 바뀌는 것은 Dockerfile 아래쪽에, 잘 안 바뀌는 것은 위쪽에** 둡니다.

```dockerfile
# 나쁜 예: 소스 한 줄만 바꿔도 의존성 다운로드부터 다시
COPY . .
RUN ./gradlew dependencies

# 좋은 예: 빌드 설정이 그대로면 의존성 레이어는 캐시 사용
COPY build.gradle settings.gradle gradlew ./
COPY gradle ./gradle
RUN ./gradlew dependencies --no-daemon
COPY src ./src
RUN ./gradlew bootJar --no-daemon
```

## 2. Dockerfile 명령어

| 명령어 | 의미 |
|---|---|
| `FROM` | **베이스 이미지** (모든 Dockerfile의 시작) |
| `WORKDIR` | 작업 디렉토리 (없으면 생성, 이후 명령의 기준 경로) |
| `COPY` | 빌드 컨텍스트(호스트)의 파일을 이미지로 복사 |
| `ADD` | COPY + URL 다운로드·tar 자동 해제 (**특별한 이유 없으면 COPY 사용**) |
| `RUN` | **빌드 시점**에 명령 실행 (패키지 설치 등) → 레이어 생성 |
| `ENV` | 환경 변수 (빌드·실행 시 모두) |
| `ARG` | **빌드 시점에만** 쓰는 변수 (`--build-arg`) |
| `EXPOSE` | 컨테이너가 쓰는 포트 **문서화** (실제로 열지는 않음, `-p`가 필요) |
| `USER` | 이후 명령·실행 사용자 |
| `ENTRYPOINT` | 컨테이너 **시작 시 항상 실행**할 명령 |
| `CMD` | 기본 실행 명령 / ENTRYPOINT의 기본 인자 (`docker run` 뒤 인자로 덮어쓸 수 있음) |
| `HEALTHCHECK` | 컨테이너 상태 확인 명령 |
| `LABEL` | 메타데이터 |

### RUN vs CMD vs ENTRYPOINT
| | 실행 시점 | 덮어쓰기 |
|---|---|---|
| `RUN` | **빌드** 시 | - |
| `CMD` | 컨테이너 **실행** 시 | `docker run image 다른명령` 으로 쉽게 덮어씀 |
| `ENTRYPOINT` | 컨테이너 **실행** 시 | `--entrypoint`로만 덮어씀 |

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
CMD ["--spring.profiles.active=dev"]
# docker run myapp                                 → java -jar app.jar --spring.profiles.active=dev
# docker run myapp --spring.profiles.active=prod  → CMD 부분만 교체
```

### exec 형식 vs shell 형식
```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]   # exec 형식 (권장): java가 PID 1 → SIGTERM을 직접 받음
ENTRYPOINT java -jar app.jar             # shell 형식: /bin/sh -c 가 PID 1 → 시그널이 java에 전달 안 될 수 있음
```
> shell 형식을 쓰면 `docker stop` 시 SIGTERM이 앱에 전달되지 않아 Graceful Shutdown이 안 되고 10초 뒤 강제 종료됩니다. **exec 형식(JSON 배열)** 을 쓰세요.

## 3. Spring Boot Dockerfile

### 가장 단순한 방식 (jar를 미리 빌드한 경우)
```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY build/libs/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### 멀티 스테이지 빌드 (권장)
**빌드용 이미지(JDK, Gradle)와 실행용 이미지(JRE)를 분리**해, 최종 이미지에는 실행에 필요한 것만 남깁니다.

```dockerfile
# ---------- 1단계: 빌드 ----------
FROM eclipse-temurin:21-jdk AS builder
WORKDIR /workspace
COPY gradlew settings.gradle build.gradle ./
COPY gradle ./gradle
RUN chmod +x gradlew && ./gradlew dependencies --no-daemon
COPY src ./src
RUN ./gradlew bootJar --no-daemon -x test

# ---------- 2단계: 실행 ----------
FROM eclipse-temurin:21-jre
WORKDIR /app

# root가 아닌 사용자로 실행
RUN groupadd --system spring && useradd --system --gid spring spring
USER spring:spring

COPY --from=builder /workspace/build/libs/*.jar app.jar

EXPOSE 8080
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0"
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]
```

- `sh -c "exec java ..."`: 환경 변수 `$JAVA_OPTS`를 확장하면서도 `exec`로 java가 PID 1을 이어받아 시그널을 받음
- **`-XX:MaxRAMPercentage`**: JVM이 **컨테이너 메모리 제한**의 75%를 힙으로 사용 (최신 JVM은 컨테이너 제한을 인식). `-Xmx`를 컨테이너 제한과 같게 주면 힙 외 메모리(메타스페이스, 스레드 스택) 때문에 OOM Kill 됩니다.

| 이미지 | 대략적 크기 |
|---|---|
| JDK + Gradle + 소스 | 수백 MB ~ 1GB 이상 |
| **JRE + jar (멀티 스테이지)** | 약 200~300MB |
| distroless / Alpine JRE | 더 작음 |

### 빌드와 실행
```bash
docker build -t myapp:1.0.0 .
docker run -d -p 8080:8080 -e SPRING_PROFILES_ACTIVE=prod --name myapp myapp:1.0.0
```

> Spring Boot는 Dockerfile 없이 `./gradlew bootBuildImage`(Cloud Native Buildpacks)로도 이미지를 만들 수 있습니다.

## 4. .dockerignore

`docker build .`의 `.`(빌드 컨텍스트) 전체가 도커 데몬으로 전송됩니다. 불필요한 파일을 제외해 **빌드 속도를 높이고 비밀 정보 유출을 막습니다.**

```
.git
.gradle
build
!build/libs/*.jar
*.md
.env
.idea
node_modules
```

## 5. 이미지 태그 전략

```
myapp:latest        ← 무엇인지 알 수 없음, 운영 사용 금지
myapp:1.4.2         ← 시맨틱 버전
myapp:a1b2c3d       ← Git 커밋 해시 (CI/CD에서 추천)
myapp:1.4.2-a1b2c3d
```
> `latest`는 "가장 최신"이 아니라 **태그를 안 붙였을 때의 기본 이름**일 뿐입니다. 운영에서는 **변하지 않는 태그**를 써야 롤백과 추적이 가능합니다.

## 6. 모범 사례

| 항목 | 방법 |
|---|---|
| 작은 베이스 이미지 | `-jre`, `-slim`, `alpine`, distroless |
| 멀티 스테이지 | 빌드 도구를 최종 이미지에서 제거 |
| **root로 실행하지 않기** | `USER` 지정 |
| 레이어 캐시 순서 | 안 바뀌는 것 위, 자주 바뀌는 것 아래 |
| RUN 합치기 + 캐시 정리 | `RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*` |
| **비밀 정보 넣지 않기** | 비밀번호·키를 `ENV`, `COPY`로 넣으면 레이어에 영구히 남음 → 실행 시 환경 변수, Secrets Manager |
| 버전 고정 | `FROM eclipse-temurin:21-jre` (`latest` X) |
| 취약점 스캔 | `docker scout`, Trivy, ECR 이미지 스캔 |
| exec 형식 ENTRYPOINT | 시그널 전달 |

## 7. 면접 질문

1. **도커 이미지 레이어와 캐시를 활용해 빌드를 빠르게 하는 방법은?**
   → 잘 바뀌지 않는 의존성 설치를 앞에, 자주 바뀌는 소스 복사를 뒤에 두어, 소스만 바뀌었을 때 앞 레이어는 캐시를 재사용하게 합니다.
2. **멀티 스테이지 빌드란?**
   → 빌드용 이미지에서 결과물을 만든 뒤 실행용 이미지로 결과물만 복사해, 빌드 도구가 없는 작고 안전한 최종 이미지를 만드는 방법입니다.
3. **CMD와 ENTRYPOINT의 차이는?**
   → 둘 다 실행 시 명령이지만, CMD는 `docker run` 인자로 쉽게 덮어써지고 ENTRYPOINT는 고정 실행 명령이며 CMD가 그 기본 인자가 될 수 있습니다.
4. **컨테이너를 root로 실행하면 안 되는 이유는?**
   → 컨테이너 탈출 취약점이 있을 때 호스트 root 권한까지 얻을 수 있어 피해가 커지기 때문입니다.

## 핵심 정리
- 이미지 = 레이어의 겹, 바뀐 레이어부터 아래는 재빌드 → 의존성 먼저, 소스 나중
- RUN(빌드 시) / CMD(기본 명령, 덮어쓰기 쉬움) / ENTRYPOINT(고정)
- exec 형식으로 시그널 전달, 멀티 스테이지로 크기 감소
- 비 root, 비밀 정보 X, latest 대신 버전·커밋 태그, MaxRAMPercentage
