# 03. 도커 네트워크와 볼륨

> **학습 목표**
> - 도커 네트워크 드라이버(bridge, host, none)의 차이를 설명할 수 있다.
> - 사용자 정의 네트워크에서 컨테이너 이름으로 통신할 수 있다.
> - 볼륨, 바인드 마운트, tmpfs의 차이를 설명하고 데이터를 영속화할 수 있다.

---

# Part 1. 네트워크

## 1. 네트워크 드라이버

| 드라이버 | 설명 | 사용처 |
|---|---|---|
| **bridge** (기본) | 호스트 안에 가상 네트워크(docker0)를 만들고 컨테이너마다 사설 IP 부여 | 단일 호스트의 일반적인 경우 |
| **host** | 컨테이너가 **호스트 네트워크를 그대로** 사용 (포트 매핑 불필요, 격리 X) | 네트워크 성능이 중요할 때 (Linux에서만 의미 있음) |
| none | 네트워크 없음 | 완전 격리 |
| overlay | **여러 호스트**에 걸친 네트워크 | Docker Swarm |

```bash
docker network ls
docker network inspect bridge
```

## 2. bridge 네트워크와 포트 매핑

```
           호스트 (공인 IP 203.0.113.10)
+-----------------------------------------------+
|   eth0 ── iptables NAT ── docker0 (172.17.0.1) |
|                              ├── 컨테이너 A 172.17.0.2:8080
|                              └── 컨테이너 B 172.17.0.3:3306
+-----------------------------------------------+

docker run -p 80:8080 A   →   외부 203.0.113.10:80 → 컨테이너 A 8080
```

- 컨테이너 IP는 **호스트 내부에서만** 유효, 재시작하면 바뀔 수 있음
- 외부에서 접근하려면 `-p 호스트포트:컨테이너포트`
- `-p 127.0.0.1:3306:3306` 처럼 **호스트 IP를 지정**하면 외부 노출 없이 로컬에서만 접근

> 도커의 `-p`는 iptables 규칙을 직접 추가하므로 **ufw 방화벽 설정을 우회**할 수 있습니다. DB 포트를 `-p 3306:3306`으로 열면 ufw로 막아도 외부에 노출될 수 있으니 주의하세요.

## 3. 사용자 정의 네트워크 (권장)

기본 bridge에서는 컨테이너끼리 **이름으로 찾을 수 없습니다.** 사용자 정의 네트워크를 만들면 **도커 내장 DNS**가 컨테이너 이름을 IP로 풀어 줍니다.

```bash
docker network create backend

docker run -d --name mysql --network backend \
  -e MYSQL_ROOT_PASSWORD=secret -e MYSQL_DATABASE=app mysql:8.4

docker run -d --name app --network backend -p 8080:8080 \
  -e SPRING_DATASOURCE_URL=jdbc:mysql://mysql:3306/app \
  myapp:1.0.0
#                                     ↑ 컨테이너 이름이 호스트명
```

- 같은 네트워크의 컨테이너끼리는 **포트 매핑 없이** 컨테이너 포트로 통신 (`mysql:3306`)
- DB는 `-p`로 외부에 열지 않고 내부 네트워크에서만 접근 → 보안

> **흔한 실수**: 컨테이너 안에서 `localhost:3306`으로 DB에 접속하려는 것. 컨테이너 안의 localhost는 **그 컨테이너 자신**입니다. 다른 컨테이너는 이름으로, 호스트 머신은 `host.docker.internal`(Docker Desktop)로 접근합니다.

# Part 2. 데이터 저장

## 4. 왜 필요한가?

컨테이너의 쓰기 레이어는 **컨테이너를 삭제하면 사라집니다.** DB 데이터, 업로드 파일을 컨테이너 안에 두면 재배포할 때마다 날아갑니다.

## 5. 저장 방식 3가지

```
        호스트
+--------------------------------------+
|  /var/lib/docker/volumes/mydata ─┐    |  ← 볼륨 (도커가 관리)
|  /home/ubuntu/config ──────────┐ │   |  ← 바인드 마운트 (내가 지정한 경로)
|                                │ │   |
|  +---------- 컨테이너 ---------+ │ │   |
|  |  /app/config  <─────────────┘ │   |
|  |  /var/lib/mysql <─────────────┘   |
|  |  /tmp (tmpfs: 메모리) |             |
|  +---------------------------+       |
+--------------------------------------+
```

| 방식 | 위치 | 특징 | 사용처 |
|---|---|---|---|
| **볼륨 (Volume)** | 도커가 관리하는 영역 (`/var/lib/docker/volumes`) | **권장**, 백업·이전 쉬움, 도커 명령으로 관리 | **DB 데이터** |
| **바인드 마운트 (Bind Mount)** | 호스트의 **임의 경로** | 호스트 파일을 바로 수정·반영 | 설정 파일, **개발 중 소스 코드** 공유 |
| tmpfs | **메모리** | 컨테이너 종료 시 삭제, 디스크에 안 씀 | 민감한 임시 데이터 |

```bash
# 볼륨
docker volume create mysql-data
docker run -d --name mysql -v mysql-data:/var/lib/mysql mysql:8.4
docker volume ls
docker volume inspect mysql-data
docker volume rm mysql-data

# 바인드 마운트 (절대 경로)
docker run -d -v /home/ubuntu/nginx.conf:/etc/nginx/nginx.conf:ro nginx:1.27
#                                                             ↑ 읽기 전용

# --mount (더 명시적인 문법)
docker run --mount type=volume,source=mysql-data,target=/var/lib/mysql mysql:8.4
```

> `docker rm`은 볼륨을 지우지 않습니다. 데이터는 남아 있고, 같은 볼륨을 연결하면 그대로 이어서 씁니다. (`docker rm -v`나 `docker volume prune`은 삭제하니 주의)

### 운영 환경에서는?
- 컨테이너 볼륨에 DB를 두는 것은 개발·테스트용으로 적합
- 운영에서는 **관리형 DB(AWS RDS)** 를 쓰고, 파일은 **S3** 에 저장해 컨테이너를 완전히 무상태로 만드는 것이 일반적입니다.
- 쿠버네티스에서는 PersistentVolume(EBS 등)을 씁니다. (→ `04.쿠버네티스/04.설정과스토리지.md`)

## 6. 로그는 어디에?

- 컨테이너 앱은 로그를 **파일이 아니라 표준 출력(stdout/stderr)** 으로 내보내는 것이 원칙
- 도커가 이를 수집해 `docker logs`로 보여 줌 (기본 json-file 드라이버, `/var/lib/docker/containers/` 아래)
- **로그 파일이 무한히 커져 디스크가 가득 차는 사고**가 흔함 → 크기 제한 설정

`/etc/docker/daemon.json`
```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```
- 운영에서는 로그 드라이버(awslogs, fluentd)나 수집 에이전트로 중앙 저장소에 보냄 (→ `08.모니터링과로깅/03.로그수집.md`)

## 7. 면접 질문

1. **도커 컨테이너끼리 통신하려면?**
   → 사용자 정의 bridge 네트워크에 함께 연결하면 도커 내장 DNS로 컨테이너 이름을 호스트명으로 사용해 통신할 수 있습니다.
2. **볼륨과 바인드 마운트의 차이는?**
   → 볼륨은 도커가 관리하는 영역에 저장되어 이식성과 관리가 쉽고, 바인드 마운트는 호스트의 특정 경로를 그대로 연결해 호스트 파일을 직접 공유합니다.
3. **컨테이너 안에서 localhost로 DB에 접속이 안 되는 이유는?**
   → 컨테이너는 자신만의 네트워크 namespace를 가지므로 localhost는 그 컨테이너 자신을 가리키기 때문입니다.

## 핵심 정리
- bridge(기본, 포트 매핑) / host(호스트 네트워크 공유) / none
- **사용자 정의 네트워크** → 컨테이너 이름으로 통신, DB는 외부 포트 노출 X
- 컨테이너 안 localhost = 자기 자신
- 데이터: 볼륨(DB) / 바인드 마운트(설정·개발) / tmpfs(메모리)
- 로그는 stdout, 로그 크기 제한 필수
