# 04. Docker Compose

> **학습 목표**
> - Docker Compose가 필요한 이유를 설명할 수 있다.
> - `compose.yaml`로 Spring Boot + MySQL + Redis 환경을 구성할 수 있다.
> - depends_on과 healthcheck로 실행 순서를 제어할 수 있다.
> - 환경 변수와 `.env` 파일, 프로필을 활용할 수 있다.

---

## 1. 왜 필요한가?

애플리케이션은 보통 여러 컨테이너로 구성됩니다 (앱 + DB + Redis + Nginx). 매번 `docker network create`, `docker run ...` 을 길게 치는 대신, **YAML 파일 하나에 전체 구성을 선언**하고 한 명령으로 실행합니다.

```bash
docker compose up -d     # 전체 시작
docker compose down      # 전체 중지·삭제
```

> 현재는 `docker compose`(공백, Compose V2 플러그인)를 씁니다. 예전 `docker-compose`(하이픈) 명령은 지원이 종료되었습니다. 파일 이름은 `compose.yaml`(권장) 또는 `docker-compose.yml`, 맨 위의 `version:` 항목은 더 이상 필요 없습니다.

| 용도 | 설명 |
|---|---|
| **로컬 개발 환경** | 팀원 모두 같은 DB·Redis 버전을 한 줄로 실행 |
| 통합 테스트 | CI에서 의존 서비스 띄우기 |
| 소규모 운영 | 서버 1대 운영 (여러 대로 확장하려면 쿠버네티스, ECS) |

## 2. 예제: Spring Boot + MySQL + Redis + Nginx

```
project/
├── compose.yaml
├── .env
├── Dockerfile
├── nginx/
│   └── default.conf
└── src/...
```

### compose.yaml
```yaml
services:
  mysql:
    image: mysql:8.4
    container_name: mysql
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_ROOT_PASSWORD}
      MYSQL_DATABASE: app
      MYSQL_USER: app
      MYSQL_PASSWORD: ${DB_PASSWORD}
      TZ: Asia/Seoul
    volumes:
      - mysql-data:/var/lib/mysql
    ports:
      - "127.0.0.1:3306:3306"          # 로컬에서만 접속 (DB 툴 연결용)
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7.4
    container_name: redis
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 10

  app:
    build:
      context: .
      dockerfile: Dockerfile
    image: myapp:local
    container_name: app
    environment:
      SPRING_PROFILES_ACTIVE: local
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/app
      SPRING_DATASOURCE_USERNAME: app
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD}
      SPRING_DATA_REDIS_HOST: redis
    depends_on:
      mysql:
        condition: service_healthy     # MySQL이 실제로 준비된 뒤 시작
      redis:
        condition: service_healthy
    restart: unless-stopped

  nginx:
    image: nginx:1.27
    container_name: nginx
    ports:
      - "80:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app

volumes:
  mysql-data:
  redis-data:
```

### .env (Git에 올리지 않기)
```
DB_ROOT_PASSWORD=root-secret
DB_PASSWORD=app-secret
```
- Compose는 같은 디렉토리의 `.env`를 자동으로 읽어 `${변수}`에 치환
- `.gitignore`에 `.env` 추가, 대신 `.env.example`을 공유

### nginx/default.conf
```nginx
server {
    listen 80;
    location / {
        proxy_pass http://app:8080;          # 서비스 이름으로 접근
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

## 3. 핵심 개념

| 항목 | 설명 |
|---|---|
| `services` | 실행할 컨테이너 정의. **서비스 이름 = 네트워크상 호스트명** |
| 기본 네트워크 | Compose가 프로젝트별 네트워크를 자동 생성 → 서비스끼리 이름으로 통신 |
| `image` / `build` | 이미지를 받아 쓸지, Dockerfile로 빌드할지 |
| `ports` | 호스트에 노출할 포트 (내부 통신에는 불필요) |
| `volumes` | 이름 있는 볼륨 or 바인드 마운트 |
| `environment` / `env_file` | 환경 변수 |
| `depends_on` | 시작 순서 |
| `restart` | `no`, `always`, `on-failure`, `unless-stopped` |
| `healthcheck` | 컨테이너 정상 여부 확인 |

### depends_on의 함정
```yaml
depends_on:
  - mysql              # mysql "컨테이너가 시작"된 뒤 app 시작 → MySQL이 "준비"된 건 아님!
```
MySQL 컨테이너는 시작 후 초기화에 수 초~수십 초가 걸립니다. 그 사이 앱이 접속하면 실패합니다.
→ **`condition: service_healthy` + `healthcheck`** 로 준비될 때까지 기다리게 합니다.

> 더 근본적으로는 앱이 **DB 연결 실패 시 재시도**하도록 만들어야 합니다. 운영 환경(쿠버네티스)에서는 시작 순서가 보장되지 않기 때문입니다.

## 4. 명령어

```bash
docker compose up -d                 # 백그라운드로 전체 실행
docker compose up -d --build         # 이미지 다시 빌드 후 실행
docker compose ps                    # 상태
docker compose logs -f app           # 특정 서비스 로그
docker compose exec mysql mysql -u app -p    # 컨테이너 안에서 명령
docker compose restart app
docker compose stop                  # 중지 (컨테이너 유지)
docker compose down                  # 중지 + 컨테이너·네트워크 삭제 (볼륨 유지)
docker compose down -v               # ★ 볼륨까지 삭제 (DB 데이터 사라짐)
docker compose config                # 변수 치환된 최종 설정 확인
docker compose up -d --scale app=3   # 서비스 복제 (container_name, 고정 ports가 있으면 불가)
```

## 5. 환경별 설정 분리

### 여러 파일 합치기
```bash
# compose.yaml (공통) + compose.prod.yaml (운영 덮어쓰기)
docker compose -f compose.yaml -f compose.prod.yaml up -d
```

### 프로필
```yaml
services:
  app: ...
  mysql: ...
  adminer:                     # DB 관리 UI — 필요할 때만
    image: adminer
    profiles: ["tools"]
    ports: ["8081:8080"]
```
```bash
docker compose --profile tools up -d
```

## 6. Spring Boot의 Compose 지원

Spring Boot 3.1+ 의 `spring-boot-docker-compose` 의존성을 추가하면, **앱을 실행할 때 compose.yaml의 서비스를 자동으로 띄우고 접속 정보(URL, 계정)를 자동 설정**합니다.
```groovy
developmentOnly 'org.springframework.boot:spring-boot-docker-compose'
```
테스트에서는 **Testcontainers**로 테스트마다 실제 DB 컨테이너를 띄울 수 있습니다.

## 7. 면접 질문

1. **Docker Compose를 쓰는 이유는?**
   → 여러 컨테이너의 이미지·네트워크·볼륨·환경 변수를 YAML 하나로 선언해 한 번에 실행·중지할 수 있어, 개발 환경을 쉽게 재현하고 공유할 수 있기 때문입니다.
2. **depends_on만으로 DB가 준비된 뒤 앱이 시작되나요?**
   → 아닙니다. 컨테이너 시작 순서만 보장하므로, healthcheck와 `condition: service_healthy`를 함께 쓰거나 앱에서 재시도 로직을 둬야 합니다.
3. **Compose와 쿠버네티스의 차이는?**
   → Compose는 주로 단일 호스트에서 여러 컨테이너를 정의·실행하는 도구이고, 쿠버네티스는 여러 노드에 걸쳐 컨테이너를 배포·확장·자가 치유하는 오케스트레이션 플랫폼입니다.

---

## 핵심 정리
- Compose = 여러 컨테이너를 YAML로 선언, `docker compose up -d / down`
- 서비스 이름 = 호스트명 (자동 네트워크)
- depends_on + healthcheck(service_healthy), 그래도 앱 재시도 필요
- 비밀은 `.env`(Git 제외), `down -v`는 데이터 삭제 주의
