# 01. 쿠버네티스 아키텍처

> **학습 목표**
> - 컨테이너 오케스트레이션이 필요한 이유를 설명할 수 있다.
> - 컨트롤 플레인과 워커 노드의 구성 요소와 역할을 설명할 수 있다.
> - 선언적 관리와 조정 루프(Reconciliation Loop)의 개념을 설명할 수 있다.
> - `kubectl` 기본 명령과 YAML 매니페스트 구조를 이해한다.

---

## 1. 왜 쿠버네티스인가?

컨테이너가 수십~수백 개, 서버가 여러 대가 되면 이런 문제가 생깁니다.

| 문제 | 쿠버네티스(K8s)의 해결 |
|---|---|
| 어느 서버에 컨테이너를 띄울까? | **스케줄링**: 자원이 여유 있는 노드에 자동 배치 |
| 컨테이너가 죽으면? | **자가 치유**: 자동 재시작·재배치 |
| 트래픽이 늘면? | **오토스케일링**: Pod 수 자동 조절 |
| 새 버전 배포는? | **롤링 업데이트**, 롤백 |
| 컨테이너끼리 어떻게 찾지? | **서비스 디스커버리**: Service + 내장 DNS |
| 설정·비밀번호 관리는? | ConfigMap, Secret |

> 쿠버네티스는 구글의 내부 시스템(Borg) 경험을 바탕으로 만든 **컨테이너 오케스트레이션** 플랫폼입니다. 이름 가운데 8글자를 줄여 **K8s**라고 부릅니다.

## 2. 클러스터 구조

```
                         [kubectl / CI·CD]
                                │ (HTTPS)
+───────────────── 컨트롤 플레인 (Control Plane) ─────────────────+
|                                                                |
|   [kube-apiserver] ←──────→ [etcd]  클러스터 상태 저장 (Key-Value) |
|        ↑    ↑                                                  |
|        │    └── [kube-scheduler]  새 Pod를 어느 노드에 둘지 결정     |
|        └─────── [kube-controller-manager] 원하는 상태 유지         |
|                 [cloud-controller-manager] 클라우드 연동(LB 등)   |
+────────────────────────────────────────────────────────────────+
          │                    │                     │
+──── 워커 노드 1 ────+  +──── 워커 노드 2 ────+   +──── 워커 노드 3 ────+
| [kubelet]          |  | [kubelet]          |   | [kubelet]          |
| [kube-proxy]       |  | [kube-proxy]       |   | [kube-proxy]       |
| [컨테이너 런타임]     |  | [containerd]       |   |                    |
|  ┌─Pod─┐ ┌─Pod─┐   |  |  ┌─Pod─┐           |   |  ┌─Pod─┐ ┌─Pod─┐   |
+────────────────────+  +────────────────────+   +────────────────────+
```

### 컨트롤 플레인 (클러스터의 두뇌)
| 구성 요소 | 역할 |
|---|---|
| **kube-apiserver** | 모든 요청의 **유일한 입구** (kubectl, 내부 컴포넌트 모두 API 서버와만 통신). 인증·인가·검증 |
| **etcd** | 클러스터의 **모든 상태를 저장**하는 분산 Key-Value 저장소. 백업 필수 |
| **kube-scheduler** | 새 Pod를 **어느 노드에 배치할지** 결정 (자원 요청량, 조건, 분산) |
| **kube-controller-manager** | 여러 **컨트롤러**를 실행 (Deployment, ReplicaSet, Node 컨트롤러 등) → 현재 상태를 원하는 상태로 맞춤 |
| cloud-controller-manager | 클라우드 API와 연동 (LoadBalancer 생성, 노드 관리) |

### 워커 노드 (실제 컨테이너가 도는 곳)
| 구성 요소 | 역할 |
|---|---|
| **kubelet** | 노드의 에이전트. API 서버로부터 받은 Pod 명세대로 컨테이너를 실행·감시, 상태 보고 |
| **kube-proxy** | Service로 들어온 트래픽을 Pod로 전달하는 네트워크 규칙(iptables/IPVS) 관리 |
| **컨테이너 런타임** | 컨테이너를 실제로 실행 (**containerd**, CRI-O) |

> 쿠버네티스 1.24부터 Docker 엔진을 직접 쓰는 dockershim이 제거되어 containerd 등을 씁니다. 하지만 **도커로 빌드한 이미지는 OCI 표준이라 그대로 실행됩니다.**

> **관리형 쿠버네티스 (AWS EKS, GKE, AKS)**: 컨트롤 플레인을 클라우드가 운영해 주고, 사용자는 워커 노드와 애플리케이션만 관리합니다. (→ `06.AWS/06.ECR과ECS와EKS.md`)

## 3. 선언적 관리와 조정 루프

### 명령형 vs 선언형
| 방식 | 예 | 특징 |
|---|---|---|
| 명령형 (Imperative) | "컨테이너 3개 실행해", "1개 더 띄워" | 과정을 지시 |
| **선언형 (Declarative)** | "**항상 3개가 떠 있는 상태**여야 한다" | 원하는 **결과(상태)** 를 정의 |

쿠버네티스는 **선언형**입니다. YAML로 원하는 상태(Desired State)를 제출하면, 컨트롤러가 끊임없이 현재 상태(Current State)와 비교해 맞춥니다.

### 조정 루프 (Reconciliation Loop)
```
        ┌────────────────────────────────────┐
        ↓                                    │
  [원하는 상태 확인] → [현재 상태 관찰] → [차이가 있으면 조치] ─┘
   replicas: 3          Pod 2개 실행 중       Pod 1개 생성
```

### Pod 하나가 생성되는 과정
```
1. kubectl apply -f deploy.yaml → API 서버 (인증·검증) → etcd에 저장
2. Deployment 컨트롤러: "ReplicaSet이 필요하네" → ReplicaSet 생성
3. ReplicaSet 컨트롤러: "Pod 3개가 필요한데 0개" → Pod 3개 생성 (아직 노드 미정)
4. 스케줄러: 노드가 정해지지 않은 Pod 발견 → 적절한 노드 선택 → API 서버에 기록
5. 해당 노드의 kubelet: "내 노드에 배정된 Pod가 있네" → containerd로 컨테이너 실행
6. kubelet이 상태를 API 서버에 보고 → Running
```
> 모든 컴포넌트는 **API 서버를 감시(watch)** 하며 자기 일만 합니다. 서로 직접 통신하지 않습니다.

## 4. YAML 매니페스트 구조

모든 쿠버네티스 리소스는 같은 뼈대를 가집니다.
```yaml
apiVersion: apps/v1          # 리소스의 API 그룹/버전
kind: Deployment             # 리소스 종류
metadata:                    # 이름, 네임스페이스, 레이블
  name: myapp
  namespace: default
  labels:
    app: myapp
spec:                        # ★ 원하는 상태
  replicas: 3
  # ... (이하 생략)
# status:                    # 현재 상태 (쿠버네티스가 채움, 작성 X)
```

### 레이블과 셀렉터
- **레이블**: 리소스에 붙이는 Key-Value 태그 (`app: myapp`, `env: prod`)
- **셀렉터**: 레이블로 리소스를 **골라내는** 조건
- Service → Pod, Deployment → Pod 연결이 모두 **레이블 셀렉터**로 이루어짐

### 네임스페이스 (Namespace)
- 클러스터를 **논리적으로 나누는** 단위 (팀별, 환경별: dev, stg)
- 기본: `default`, `kube-system`(시스템 컴포넌트)
```bash
kubectl get pods -n kube-system
kubectl create namespace dev
```

## 5. kubectl 기본 명령

```bash
kubectl apply -f deploy.yaml          # ★ 선언형으로 생성·변경
kubectl delete -f deploy.yaml

kubectl get pods                      # 목록 (-o wide: 노드·IP, -w: 실시간)
kubectl get deploy,svc,ingress
kubectl get all -n dev
kubectl describe pod <이름>            # ★ 상세 + 이벤트 (문제 원인 파악)
kubectl logs -f <pod>                 # 로그 (-c 컨테이너, --previous: 직전에 죽은 컨테이너)
kubectl exec -it <pod> -- sh          # 컨테이너 접속
kubectl port-forward svc/myapp 8080:80   # 로컬에서 클러스터 내부 서비스 접근
kubectl get events --sort-by=.metadata.creationTimestamp

kubectl config get-contexts           # 연결된 클러스터 목록
kubectl config use-context prod       # 클러스터 전환 (실수 주의!)
kubectl explain deployment.spec       # 필드 설명
```

> `kubectl create`, `kubectl run`(명령형)보다 **YAML 파일 + `kubectl apply`(선언형)** 로 관리해야 Git으로 이력 관리(GitOps)가 가능합니다.

## 6. 면접 질문

1. **쿠버네티스를 쓰는 이유는?**
   → 여러 노드에 걸친 컨테이너의 배치, 자가 치유, 오토스케일링, 롤링 업데이트, 서비스 디스커버리를 자동화하기 위해서입니다.
2. **컨트롤 플레인의 구성 요소는?**
   → 모든 요청을 받는 kube-apiserver, 상태를 저장하는 etcd, Pod를 노드에 배치하는 scheduler, 원하는 상태를 유지하는 controller-manager입니다.
3. **kubelet의 역할은?**
   → 각 워커 노드에서 API 서버가 지정한 Pod를 컨테이너 런타임으로 실행·감시하고 상태를 보고하는 에이전트입니다.
4. **선언적 관리란?**
   → 원하는 최종 상태를 정의하면 컨트롤러가 현재 상태를 계속 관찰해 원하는 상태와 같아지도록 조정하는 방식입니다.

## 핵심 정리
- K8s = 컨테이너 오케스트레이션 (스케줄링, 자가 치유, 스케일링, 롤링 배포)
- 컨트롤 플레인: apiserver(입구), etcd(상태), scheduler(배치), controller-manager(조정)
- 워커 노드: kubelet(실행), kube-proxy(네트워크), containerd
- 선언형 + 조정 루프, 레이블 셀렉터로 연결
- `apply -f`, `get`, `describe`, `logs`, `exec`
