# 02. 파드와 워크로드 (Pod & Workloads)

> **학습 목표**
> - Pod의 개념과 Pod 안의 컨테이너가 공유하는 것을 설명할 수 있다.
> - Deployment, ReplicaSet, Pod의 관계를 설명할 수 있다.
> - StatefulSet, DaemonSet, Job/CronJob의 용도를 구분할 수 있다.
> - 자원 요청(requests)과 제한(limits)을 설정할 수 있다.
> - Pod 상태와 흔한 오류(CrashLoopBackOff, ImagePullBackOff, OOMKilled)를 진단할 수 있다.

---

## 1. Pod

**쿠버네티스에서 배포하는 가장 작은 단위**입니다. 하나 이상의 컨테이너를 묶은 것입니다.

```
+──────────── Pod (IP: 10.0.1.23) ────────────+
|  +─────────────+     +──────────────────+   |
|  | app 컨테이너  |     | 사이드카 (로그 수집) |   |
|  | :8080       |     |                  |   |
|  +─────────────+     +──────────────────+   |
|        공유: 네트워크(같은 IP, localhost), 볼륨  |
+─────────────────────────────────────────────+
```

- Pod 안의 컨테이너는 **같은 IP와 포트 공간을 공유** → `localhost`로 서로 통신
- 볼륨을 공유할 수 있음
- 보통 **Pod 1개 = 메인 컨테이너 1개** (+ 필요시 사이드카)
- **Pod는 일회용**: 죽으면 같은 Pod가 살아나는 게 아니라 **새 Pod(새 IP)** 가 만들어짐 → 그래서 Pod IP로 직접 통신하지 않고 **Service**를 씀

### 멀티 컨테이너 패턴
| 패턴 | 예 |
|---|---|
| **사이드카** | 로그 수집 에이전트, 서비스 메시 프록시(Envoy) |
| **Init 컨테이너** | 메인 컨테이너 시작 **전에** 실행되고 끝나는 컨테이너 (DB 마이그레이션, 설정 다운로드) |

### Pod YAML (직접 만들 일은 거의 없음)
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  containers:
    - name: app
      image: 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:a1b2c3d
      ports:
        - containerPort: 8080
```
> Pod를 직접 만들면 죽었을 때 아무도 다시 만들어 주지 않습니다. **항상 Deployment 같은 컨트롤러로 관리**합니다.

## 2. Deployment → ReplicaSet → Pod

```
[Deployment]  "myapp 이미지 v2로, 3개, 롤링 업데이트로"   ← 사용자가 관리
     │ 관리
[ReplicaSet]  "레이블 app=myapp인 Pod를 정확히 3개 유지"  ← 버전마다 하나
     │ 관리
[Pod] [Pod] [Pod]
```

| 리소스 | 역할 |
|---|---|
| **ReplicaSet** | 지정한 수의 Pod 복제본을 **항상 유지** (죽으면 새로 생성) |
| **Deployment** | ReplicaSet을 관리하며 **배포 전략(롤링 업데이트), 롤백, 이력** 제공 |

### Deployment YAML (Spring Boot)
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp              # 이 레이블을 가진 Pod를 관리
  template:                   # ★ 만들 Pod의 템플릿
    metadata:
      labels:
        app: myapp            # selector와 반드시 일치
    spec:
      containers:
        - name: app
          image: 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:a1b2c3d
          ports:
            - containerPort: 8080
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: prod
          resources:
            requests:
              cpu: 500m
              memory: 768Mi
            limits:
              memory: 768Mi
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
```

```bash
kubectl apply -f deployment.yaml
kubectl get deploy,rs,pods
kubectl set image deployment/myapp app=myapp:b2c3d4e   # 이미지 교체 → 롤링 업데이트
kubectl rollout status deployment/myapp
kubectl rollout history deployment/myapp
kubectl rollout undo deployment/myapp                  # ★ 직전 버전으로 롤백
kubectl scale deployment/myapp --replicas=5
kubectl rollout restart deployment/myapp               # 설정 변경 반영 등을 위한 재시작
```

## 3. 그 밖의 워크로드

| 리소스 | 용도 | 특징 | 예 |
|---|---|---|---|
| **Deployment** | **무상태(Stateless)** 앱 | Pod가 서로 같음, 순서·이름 무관 | **Spring Boot API**, 웹 서버 |
| **StatefulSet** | **상태가 있는(Stateful)** 앱 | Pod마다 **고정된 이름(app-0, app-1)**, **순서대로** 생성·삭제, Pod마다 **전용 볼륨** | DB, Kafka, Redis 클러스터, Elasticsearch |
| **DaemonSet** | **모든 노드에 하나씩** | 노드가 추가되면 자동 배치 | 로그 수집(Fluent Bit), 모니터링 에이전트(node-exporter) |
| **Job** | **한 번 실행하고 끝나는** 작업 | 성공할 때까지 재시도 | DB 마이그레이션, 배치 처리 |
| **CronJob** | **주기적으로** Job 실행 | cron 표현식 | 매일 새벽 정산, 리포트 생성 |

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-report
spec:
  schedule: "0 3 * * *"          # 매일 03:00 (기본 UTC — timeZone 필드로 지정 가능)
  timeZone: "Asia/Seoul"
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: report
              image: myapp-batch:1.0.0
```

> 운영 DB는 보통 쿠버네티스 안(StatefulSet)보다 **관리형 DB(RDS)** 를 씁니다. 상태가 있는 워크로드는 백업·복구·업그레이드 운영 부담이 크기 때문입니다.

## 4. 자원 요청과 제한 (requests / limits)

```yaml
resources:
  requests:          # "최소 이만큼은 보장해 줘" → 스케줄링 기준
    cpu: 500m        # 0.5 코어 (1000m = 1 코어)
    memory: 512Mi
  limits:            # "이 이상은 못 씀"
    cpu: "1"
    memory: 512Mi
```

| 항목 | requests | limits |
|---|---|---|
| 의미 | 보장받는 최소량 | 사용 가능한 최대량 |
| 용도 | **스케줄러가 노드 배치 시 사용** (노드 여유 자원 ≥ requests) | 초과 사용 방지 |
| CPU 초과 시 | - | **스로틀링** (느려짐, 죽지 않음) |
| 메모리 초과 시 | - | **OOMKilled** (컨테이너 종료 후 재시작) |

### QoS 클래스 (노드 메모리가 부족할 때 누구부터 쫓아낼까)
| 클래스 | 조건 | 퇴출 순서 |
|---|---|---|
| **Guaranteed** | 모든 컨테이너가 requests = limits (CPU·메모리 모두) | 마지막 |
| Burstable | requests < limits 등 일부만 설정 | 중간 |
| BestEffort | 아무것도 설정 안 함 | **가장 먼저** |

> **실무 팁**: 메모리는 requests = limits로 맞추고, JVM은 `-XX:MaxRAMPercentage=75`로 컨테이너 제한에 맞춥니다. CPU limits는 스로틀링으로 응답 지연을 일으킬 수 있어 requests만 두는 팀도 많습니다.

## 5. Pod 상태와 문제 해결

### Pod 단계 (Phase)
| 상태 | 의미 |
|---|---|
| Pending | 생성됐지만 아직 실행 전 (스케줄링 대기, 이미지 다운로드 중) |
| Running | 노드에 배치되어 컨테이너 실행 중 |
| Succeeded | 모든 컨테이너 정상 종료 (Job) |
| Failed | 컨테이너가 실패로 종료 |

### 흔한 오류
| 상태 | 원인 | 확인 |
|---|---|---|
| **Pending** (계속) | 노드 자원 부족(requests가 너무 큼), 노드 셀렉터 불일치, PVC 바인딩 실패 | `kubectl describe pod` → Events |
| **ImagePullBackOff** / ErrImagePull | 이미지 이름·태그 오타, **ECR 권한 없음**, 프라이빗 레지스트리 인증 | `describe` |
| **CrashLoopBackOff** | 컨테이너가 시작하자마자 계속 죽음 → 재시작 간격이 점점 늘어남. 앱 설정 오류, DB 연결 실패, **liveness probe가 너무 빨리 실패** | `kubectl logs <pod> --previous` |
| **OOMKilled** | 메모리 limits 초과 | `describe` → Last State: OOMKilled, Exit Code 137 |
| CreateContainerConfigError | 참조한 ConfigMap·Secret이 없음 | `describe` |

```bash
# 진단 3종 세트
kubectl get pods                       # 상태 확인
kubectl describe pod <pod>             # Events에서 원인
kubectl logs <pod> --previous          # 직전에 죽은 컨테이너의 로그
```

## 6. 면접 질문

1. **Pod란? 컨테이너와의 차이는?**
   → 쿠버네티스의 최소 배포 단위로, 네트워크(IP)와 볼륨을 공유하는 하나 이상의 컨테이너 묶음입니다.
2. **Deployment와 ReplicaSet의 관계는?**
   → ReplicaSet은 지정한 수의 Pod를 유지하고, Deployment는 ReplicaSet을 관리하며 롤링 업데이트와 롤백 같은 배포 기능을 제공합니다.
3. **StatefulSet은 언제 쓰나요?**
   → DB처럼 Pod마다 고유한 이름·순서·전용 저장소가 필요한 상태 유지 애플리케이션에 씁니다.
4. **requests와 limits의 차이는?**
   → requests는 스케줄링 시 보장받는 최소 자원이고, limits는 최대 사용량으로 CPU는 초과 시 스로틀링, 메모리는 초과 시 OOMKilled 됩니다.
5. **CrashLoopBackOff는 어떻게 해결하나요?**
   → `kubectl logs --previous`로 직전 실행 로그를 보고, `describe`로 이벤트와 종료 코드를 확인해 설정 오류·의존 서비스 연결·probe 설정 문제를 찾습니다.

## 핵심 정리
- Pod = 최소 단위, 컨테이너들이 IP·볼륨 공유, 일회용
- Deployment → ReplicaSet → Pod (롤링 업데이트, `rollout undo`)
- 무상태 Deployment / 상태 StatefulSet / 노드마다 DaemonSet / 일회성 Job·CronJob
- requests(스케줄링) vs limits(CPU 스로틀링, 메모리 OOMKilled)
- 진단: `get` → `describe`(Events) → `logs --previous`
