# 03. 서비스와 인그레스 (Service & Ingress)

> **학습 목표**
> - Service가 필요한 이유와 레이블 셀렉터로 Pod를 찾는 원리를 설명할 수 있다.
> - Service 타입(ClusterIP, NodePort, LoadBalancer)을 비교할 수 있다.
> - 클러스터 내부 DNS로 서비스를 호출할 수 있다.
> - Ingress와 Ingress Controller로 외부 HTTP 트래픽을 라우팅할 수 있다.

---

## 1. 왜 Service가 필요한가?

Pod는 언제든 죽고 새로 만들어지며, 그때마다 **IP가 바뀝니다.** 또 Pod가 여러 개면 어디로 보낼지 정해야 합니다.

**Service**는 레이블로 선택한 Pod 집합 앞에 **고정된 가상 IP와 DNS 이름**을 주고, 요청을 Pod들로 **분산**합니다.

```
                       Service "myapp" (ClusterIP 10.100.5.20, DNS myapp)
                       selector: app=myapp
[다른 Pod] ──요청──>         │  (kube-proxy가 만든 iptables/IPVS 규칙으로 분산)
                ┌──────────┼──────────┐
           [Pod 10.0.1.4] [Pod 10.0.2.7] [Pod 10.0.3.9]   ← 레이블 app=myapp
```

- Service는 **레이블 셀렉터**에 맞는 Pod 중 **Ready 상태인 것만** 엔드포인트로 관리 (readinessProbe 실패 시 제외)
```bash
kubectl get endpointslices -l kubernetes.io/service-name=myapp
```

## 2. Service 타입

| 타입 | 접근 범위 | 동작 | 사용처 |
|---|---|---|---|
| **ClusterIP** (기본) | **클러스터 내부만** | 내부 가상 IP | 서비스 간 내부 통신 (회원 서비스 → 주문 서비스) |
| **NodePort** | 외부 (노드 IP:포트) | **모든 노드의 30000~32767 포트**를 열어 전달 | 테스트, 온프레미스 |
| **LoadBalancer** | 외부 | 클라우드의 **로드밸런서를 자동 생성** (AWS NLB 등) + NodePort | 외부 공개 (서비스마다 LB 하나 → 비용) |
| ExternalName | - | 외부 도메인의 별칭(CNAME) | 외부 DB 주소를 내부 이름으로 |

```
LoadBalancer ⊃ NodePort ⊃ ClusterIP   (상위 타입은 하위 기능을 포함)
```

### ClusterIP 예시
```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  type: ClusterIP
  selector:
    app: myapp              # 이 레이블의 Pod로 전달
  ports:
    - port: 80              # Service 포트 (호출하는 쪽이 쓰는 포트)
      targetPort: 8080      # Pod(컨테이너) 포트
```

### 포트 정리
| 이름 | 의미 |
|---|---|
| `port` | Service가 받는 포트 |
| `targetPort` | Pod 컨테이너의 포트 |
| `nodePort` | (NodePort 타입) 노드에서 열리는 포트 |

## 3. 클러스터 내부 DNS

쿠버네티스는 **CoreDNS**로 Service 이름을 IP로 풀어 줍니다.

```
<서비스>.<네임스페이스>.svc.cluster.local

myapp                                   # 같은 네임스페이스
myapp.prod                              # 다른 네임스페이스
myapp.prod.svc.cluster.local            # 전체 이름 (FQDN)
```

```yaml
# 주문 서비스에서 회원 서비스 호출
env:
  - name: MEMBER_API_URL
    value: http://member-service.prod:80
```
> 서비스 디스커버리를 위해 Eureka 같은 별도 서버 없이 **DNS만으로 해결**됩니다.

## 4. Ingress

### 문제
서비스마다 `type: LoadBalancer`를 쓰면 **로드밸런서가 서비스 수만큼** 생겨 비용이 크고, 경로 기반 라우팅·TLS 관리가 흩어집니다.

### Ingress
**외부 HTTP(S) 트래픽을 URL 호스트·경로에 따라 내부 Service로 라우팅하는 규칙**입니다. L7 라우팅을 담당합니다.

```
                         [Ingress Controller + 외부 LB 1개]
 api.example.com/members ───────┬──> Service member  ──> Pods
 api.example.com/orders  ───────┼──> Service order   ──> Pods
 admin.example.com       ───────┴──> Service admin   ──> Pods
```

### Ingress vs Ingress Controller
| 구분 | 설명 |
|---|---|
| **Ingress** | 라우팅 **규칙**(YAML 리소스). 그 자체로는 아무것도 안 함 |
| **Ingress Controller** | 규칙을 읽어 **실제로 트래픽을 처리하는 프로그램** (별도 설치 필요) |

| Ingress Controller | 특징 |
|---|---|
| **AWS Load Balancer Controller** | Ingress를 보고 **ALB를 자동 생성·설정** (EKS 표준) |
| ingress-nginx | 클러스터 안에 Nginx를 띄워 처리. **커뮤니티 프로젝트는 2026년 3월 유지보수가 종료**되어 새 프로젝트에는 권장하지 않음 (Gateway API 구현체로 이전 추세) |
| Traefik, Kong, HAProxy | 다양한 기능 |

### Ingress 예시 (EKS + ALB)
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip               # ALB → Pod IP로 직접
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS": 443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-northeast-2:123456789012:certificate/xxxx
    alb.ingress.kubernetes.io/healthcheck-path: /actuator/health
spec:
  ingressClassName: alb
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /members
            pathType: Prefix
            backend:
              service:
                name: member-service
                port:
                  number: 80
          - path: /orders
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 80
```

| pathType | 의미 |
|---|---|
| `Prefix` | 경로 접두사 일치 (`/members`, `/members/1`) |
| `Exact` | 정확히 일치 |

> **Gateway API**: Ingress의 후속 표준으로, 역할 분리(인프라 담당 vs 앱 담당)와 더 풍부한 라우팅(헤더 기반, 가중치)을 지원합니다. 새 프로젝트에서 점점 많이 쓰입니다.

## 5. 전체 트래픽 흐름 (EKS 기준)

```
사용자
  │ https://api.example.com/orders/1
  ↓
Route 53 (DNS: api.example.com → ALB)
  ↓
ALB (HTTPS 종료, ACM 인증서) ← AWS Load Balancer Controller가 Ingress를 보고 생성
  │ 규칙: /orders → order-service 대상 그룹
  ↓
order-service Pod (Pod IP로 직접, target-type: ip)
  │ 회원 정보 필요
  ↓ http://member-service.prod (ClusterIP, CoreDNS)
member-service Pod
  ↓
RDS (VPC 내부)
```

## 6. 면접 질문

1. **Service가 필요한 이유는?**
   → Pod는 재생성될 때마다 IP가 바뀌므로, 레이블로 선택한 Pod 집합에 고정된 IP와 DNS 이름을 제공하고 트래픽을 분산하기 위해서입니다.
2. **ClusterIP, NodePort, LoadBalancer의 차이는?**
   → ClusterIP는 클러스터 내부 전용, NodePort는 모든 노드의 특정 포트로 외부 접근, LoadBalancer는 클라우드 로드밸런서를 생성해 외부에 공개합니다.
3. **Ingress란? Service LoadBalancer와 차이는?**
   → Ingress는 호스트·경로 기반으로 HTTP 트래픽을 여러 Service로 라우팅하는 L7 규칙으로, 로드밸런서 하나로 여러 서비스를 노출할 수 있습니다. 실제 처리는 Ingress Controller가 합니다.
4. **쿠버네티스에서 서비스 디스커버리는 어떻게 하나요?**
   → CoreDNS가 `서비스명.네임스페이스.svc.cluster.local` 이름을 Service IP로 풀어 줍니다.

---

## 핵심 정리
- Service = Pod 집합의 고정 IP + DNS + 분산 (Ready인 Pod만)
- ClusterIP(내부) / NodePort(노드 포트) / LoadBalancer(클라우드 LB)
- DNS: `서비스.네임스페이스.svc.cluster.local`
- Ingress(L7 규칙) + Ingress Controller(실제 처리, EKS는 ALB Controller)
