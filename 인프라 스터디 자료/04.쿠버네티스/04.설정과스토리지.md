# 04. 설정과 스토리지 (ConfigMap, Secret, Volume)

> **학습 목표**
> - ConfigMap과 Secret으로 설정을 이미지에서 분리할 수 있다.
> - Secret이 기본적으로 암호화가 아니라는 점과 보완 방법을 설명할 수 있다.
> - PV, PVC, StorageClass의 관계를 설명할 수 있다.

---

## 1. 왜 설정을 분리하는가?

같은 이미지를 **dev, stg, prod 환경에 그대로** 배포하고, 환경별 차이(DB 주소, 로그 레벨)는 **외부에서 주입**합니다. (12-Factor App: 설정은 환경에)

```
[myapp:a1b2c3d 이미지 하나]
     ├── dev  + ConfigMap(dev) + Secret(dev)
     ├── stg  + ConfigMap(stg) + Secret(stg)
     └── prod + ConfigMap(prod) + Secret(prod)
```

---

## 2. ConfigMap

**민감하지 않은 설정**을 Key-Value로 저장합니다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
data:
  SPRING_PROFILES_ACTIVE: prod
  LOGGING_LEVEL_ROOT: INFO
  application-prod.yml: |          # 파일 내용 통째로도 가능
    server:
      shutdown: graceful
    spring:
      jpa:
        open-in-view: false
```

### Pod에서 사용하는 방법
```yaml
spec:
  containers:
    - name: app
      image: myapp:a1b2c3d
      # 방법 1: 모든 키를 환경 변수로
      envFrom:
        - configMapRef:
            name: myapp-config
      # 방법 2: 특정 키만
      env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: myapp-config
              key: LOGGING_LEVEL_ROOT
      # 방법 3: 파일로 마운트
      volumeMounts:
        - name: config
          mountPath: /config            # Spring Boot는 ./config/ 의 설정 파일을 자동으로 읽음
  volumes:
    - name: config
      configMap:
        name: myapp-config
        items:
          - key: application-prod.yml
            path: application-prod.yml
```

| 방식 | ConfigMap 변경 시 |
|---|---|
| 환경 변수 | **Pod 재시작해야 반영** (`kubectl rollout restart`) |
| 볼륨 마운트 | 파일은 잠시 후 자동 갱신 (앱이 다시 읽어야 의미 있음) |

> Spring Boot는 `SPRING_DATASOURCE_URL` 같은 **환경 변수를 자동으로 `spring.datasource.url` 속성에 매핑**합니다(relaxed binding).

## 3. Secret

**비밀번호, API 키, 인증서** 같은 민감 정보를 저장합니다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: myapp-secret
type: Opaque
stringData:                     # 평문으로 작성하면 저장 시 base64로 인코딩됨
  SPRING_DATASOURCE_PASSWORD: super-secret
  JWT_SECRET: abcdef123456
```
```yaml
envFrom:
  - secretRef:
      name: myapp-secret
```
```bash
kubectl create secret generic myapp-secret --from-literal=SPRING_DATASOURCE_PASSWORD=super-secret
kubectl get secret myapp-secret -o jsonpath='{.data.SPRING_DATASOURCE_PASSWORD}' | base64 -d
```

### ⚠️ Secret은 기본적으로 "암호화"가 아니다
- `data` 필드는 **base64 인코딩**일 뿐, 누구나 디코딩 가능
- etcd에 기본 설정으로는 평문에 가깝게 저장될 수 있음
- **Secret YAML을 Git에 올리면 안 됩니다.**

### 보완 방법
| 방법 | 설명 |
|---|---|
| **RBAC** | Secret 조회 권한을 최소한으로 |
| etcd 암호화 (Encryption at Rest) | EKS는 KMS로 Secret 봉투 암호화 지원 |
| **External Secrets Operator** | **AWS Secrets Manager / Parameter Store**의 값을 Secret으로 동기화 → 비밀은 AWS에서 관리 |
| Sealed Secrets | 암호화된 형태로 Git에 저장, 클러스터 안에서만 복호화 |
| Secrets Store CSI Driver | 비밀을 파일로 직접 마운트 |

## 4. 볼륨과 영구 저장소

Pod 안의 파일은 Pod가 사라지면 함께 사라집니다.

| 볼륨 종류 | 수명 | 용도 |
|---|---|---|
| `emptyDir` | **Pod와 같이** 생성·삭제 | Pod 안 컨테이너끼리 임시 파일 공유 (사이드카) |
| `configMap`, `secret` | - | 설정 파일 마운트 |
| `hostPath` | 노드에 남음 | 노드 파일 접근 (보안상 지양) |
| **PersistentVolume** | **Pod와 독립적** | DB 데이터 등 영구 저장 |

### PV, PVC, StorageClass

```
[개발자]  PVC: "10Gi, ReadWriteOnce 저장소 필요해요"
            │  (바인딩)
            ↓
[관리자/자동]  PV: 실제 저장소 (AWS EBS 볼륨 vol-0abc...)
            ↑  동적 생성
       StorageClass: "gp3 EBS로 만들어 주는 템플릿"
```

| 리소스 | 의미 | 비유 |
|---|---|---|
| **PV** (PersistentVolume) | 클러스터에 등록된 **실제 저장 공간** | 주차장의 실제 주차 칸 |
| **PVC** (PersistentVolumeClaim) | Pod가 쓰기 위한 **저장소 요청서** | 주차권 신청 |
| **StorageClass** | PVC 요청 시 PV를 **자동으로(동적 프로비저닝)** 만드는 방법 | 주차 칸 자동 생성 규칙 |

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: gp3
  resources:
    requests:
      storage: 10Gi
---
# Pod에서 사용
spec:
  containers:
    - name: app
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: data-pvc
```

### 접근 모드
| 모드 | 의미 | AWS 예 |
|---|---|---|
| **ReadWriteOnce (RWO)** | **한 노드**에서 읽기·쓰기 | **EBS** (같은 AZ의 한 인스턴스에만 연결) |
| ReadOnlyMany (ROX) | 여러 노드에서 읽기 | |
| **ReadWriteMany (RWX)** | **여러 노드**에서 읽기·쓰기 | **EFS** (NFS) |

> EBS는 **하나의 가용 영역(AZ)** 에 속하므로, 그 PV를 쓰는 Pod는 같은 AZ 노드에만 스케줄됩니다. StatefulSet은 `volumeClaimTemplates`로 Pod마다 PVC를 자동 생성합니다.

### Reclaim Policy (PVC 삭제 시 PV는?)
| 정책 | 동작 |
|---|---|
| Delete (동적 생성 기본값) | 실제 디스크(EBS)도 **삭제** |
| Retain | PV와 데이터 **보존** (수동 정리) → 중요한 데이터는 Retain |

## 5. 면접 질문

1. **ConfigMap과 Secret의 차이는?**
   → 둘 다 설정을 이미지에서 분리해 주입하지만, ConfigMap은 일반 설정, Secret은 민감 정보용입니다. Secret은 base64 인코딩일 뿐이라 RBAC, etcd 암호화, 외부 비밀 저장소 연동으로 보완해야 합니다.
2. **설정을 이미지에 넣지 않고 분리하는 이유는?**
   → 같은 이미지를 여러 환경에 그대로 배포하고, 설정 변경 시 이미지를 다시 빌드하지 않으며, 비밀 정보가 이미지에 남지 않게 하기 위해서입니다.
3. **PV와 PVC의 차이는?**
   → PV는 실제 저장 공간 리소스이고, PVC는 Pod가 필요한 용량과 접근 모드를 요청하는 리소스로 조건에 맞는 PV와 바인딩됩니다. StorageClass가 있으면 PV가 동적으로 생성됩니다.

---

## 핵심 정리
- 이미지 하나 + 환경별 ConfigMap·Secret 주입
- 환경 변수 주입은 변경 시 재시작 필요
- Secret = base64(암호화 X) → Git 금지, External Secrets + AWS Secrets Manager
- 영구 저장: PVC(요청) → StorageClass(동적 생성) → PV(EBS/EFS)
- EBS = RWO + 단일 AZ, EFS = RWX
