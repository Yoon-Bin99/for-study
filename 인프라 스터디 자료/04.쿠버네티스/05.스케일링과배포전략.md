## 1. Probe (헬스 체크)

kubelet이 컨테이너 상태를 주기적으로 검사합니다.

| Probe | 질문 | 실패하면 |
|---|---|---|
| **startupProbe** | "**시작이 끝났니?**" | 성공할 때까지 다른 probe를 보류. 제한 횟수 넘게 실패하면 재시작 |
| **readinessProbe** | "**트래픽을 받을 준비가 됐니?**" | **Service 엔드포인트에서 제외** (재시작 X) |
| **livenessProbe** | "**살아 있니?** (멈추거나 데드락 아니니?)" | **컨테이너 재시작** |

```yaml
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30          # 최대 5초 × 30 = 150초까지 기동 대기
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
```

> Spring Boot는 쿠버네티스 환경을 감지하면 `/actuator/health/liveness`, `/actuator/health/readiness`를 자동으로 제공합니다. (`management.endpoint.health.probes.enabled=true`로 어디서든 활성화)

### 흔한 실수
| 실수 | 결과 |
|---|---|
| JVM 기동(30~60초)보다 liveness가 먼저 실패 | 뜨기도 전에 계속 재시작 → **CrashLoopBackOff** → startupProbe 사용 |
| **liveness에 DB 연결 확인을 넣음** | DB가 잠깐 느려지면 **모든 Pod가 동시에 재시작** → 장애 확대 |
| readiness 없음 | 기동 중인 Pod에 트래픽이 가서 에러 |

> 원칙: **liveness는 "프로세스 자체가 회복 불가능한가"만**, 외부 의존성 상태는 readiness에서(또는 앱 레벨에서) 다룹니다.

## 2. 오토스케일링

```
              Pod 수 조절                      노드 수 조절
[HPA] ─── Pod 2개 → 6개 ───>  노드 자원 부족 → Pending Pod 발생 ─── [Cluster Autoscaler / Karpenter] → 노드 추가
```

### HPA (Horizontal Pod Autoscaler) — Pod 수평 확장
지표(CPU, 메모리, 사용자 정의 지표)를 보고 **Pod 개수**를 늘리고 줄입니다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70     # 평균 CPU가 requests의 70% 넘으면 확장
```

```
원하는 Pod 수 = ceil(현재 Pod 수 × 현재 지표값 / 목표 지표값)
예: 현재 3개, 평균 CPU 105%, 목표 70% → ceil(3 × 105 / 70) = ceil(4.5) = 5개
```

- **전제 조건**: `metrics-server` 설치, 컨테이너에 **requests 설정** (사용률 = 사용량 / requests)
- 축소는 급격한 변동을 막기 위해 기본 5분 안정화 기간 후 진행
- 요청 수·큐 길이 같은 지표로 확장하려면 **KEDA** 또는 Prometheus Adapter 사용

### VPA (Vertical Pod Autoscaler)
Pod의 **requests/limits 값 자체**를 조정 (수직 확장). 적정 자원 추천용으로 많이 씀.

### 노드 오토스케일링
| 도구 | 동작 |
|---|---|
| **Cluster Autoscaler** | 스케줄되지 못한 Pending Pod가 있으면 **노드 그룹(ASG)** 의 노드 수 증가, 놀고 있는 노드는 감소 |
| **Karpenter** (AWS 주도) | 노드 그룹 없이 Pending Pod에 **딱 맞는 인스턴스 타입을 직접 골라** 빠르게 생성, 스팟 활용·통합(consolidation)에 강함 |

## 3. 배포 전략: 롤링 업데이트

Deployment의 기본 전략입니다. **새 버전 Pod를 조금씩 늘리고 구버전을 조금씩 줄입니다.**

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1           # 원하는 수보다 최대 몇 개 더 만들 수 있나 (25% 기본)
      maxUnavailable: 0     # 동시에 몇 개까지 사용 불가여도 되나 (25% 기본)
  minReadySeconds: 10       # Ready 후 이 시간 동안 안정적이어야 다음 단계 진행
```

```
replicas 4, maxSurge 1, maxUnavailable 0
v1 v1 v1 v1
v1 v1 v1 v1 v2      ← v2 하나 추가 (최대 5개)
v1 v1 v1 v2         ← v2가 Ready → v1 하나 종료
v1 v1 v2 v2 ...
v2 v2 v2 v2         ← 완료
```
- `maxUnavailable: 0` → 처리 용량이 줄지 않음 (안전, 느림)
- **새 Pod가 readiness를 통과하지 못하면 롤아웃이 멈춤** → 구버전이 계속 서비스 → `rollout undo`

| 전략 | 동작 |
|---|---|
| **RollingUpdate** (기본) | 점진적 교체 |
| Recreate | 모두 종료 후 새로 생성 → **다운타임 발생** (두 버전 공존이 불가능할 때) |

> 블루/그린, 카나리 배포는 → `05.CICD/04.배포전략.md` (Argo Rollouts 등으로 구현)

## 4. 무중단 종료: Pod가 죽는 과정

롤링 업데이트나 축소로 Pod가 종료될 때 요청 유실을 막아야 합니다.

```
1. Pod 삭제 요청 → 상태 Terminating
2. 동시에 진행:
   (a) Service 엔드포인트·ALB 대상에서 제거 시작 (전파에 시간이 걸림)
   (b) preStop 훅 실행 → 그다음 컨테이너에 SIGTERM
3. 앱은 SIGTERM을 받으면 새 요청을 거절하고 처리 중인 요청 마무리 (Graceful Shutdown)
4. terminationGracePeriodSeconds(기본 30초)가 지나면 SIGKILL
```

**문제**: (a)가 끝나기 전에 앱이 먼저 종료되면, 아직 이 Pod로 오던 요청이 실패합니다.
**해결**: preStop에서 잠깐 대기해 라우팅에서 빠질 시간을 줍니다.

```yaml
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]
```
```yaml
# application.yml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```
> preStop 대기 시간 + 앱 종료 시간 < terminationGracePeriodSeconds 가 되도록 설정합니다.

### PodDisruptionBudget (PDB)
노드 점검·축소처럼 **자발적인 중단** 시에도 최소한의 Pod를 유지합니다.
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp
```

### 가용 영역 분산
```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone     # AZ별로 고르게
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: myapp
```
→ AZ 하나가 장애 나도 서비스 유지

## 5. 매니페스트 관리: Helm과 Kustomize

환경(dev/stg/prod)마다 거의 같은 YAML을 복붙하면 관리가 어려워집니다.

| 도구 | 방식 | 특징 |
|---|---|---|
| **Helm** | **템플릿 + values 파일** → 패키지(Chart) | 쿠버네티스의 패키지 매니저. 오픈소스 설치(Prometheus, Ingress Controller)에 표준. 릴리스 버전 관리·롤백 |
| **Kustomize** | **기본 YAML + 환경별 패치(overlay)** | 템플릿 문법 없음, `kubectl apply -k`에 내장 |

```bash
# Helm
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack -n monitoring --create-namespace
helm upgrade myapp ./chart -f values-prod.yaml
helm rollback myapp 3
helm list -A
```

```
# Kustomize 구조
k8s/
├── base/               deployment.yaml, service.yaml, kustomization.yaml
└── overlays/
    ├── dev/            kustomization.yaml (replicas 1, 이미지 태그 dev)
    └── prod/           kustomization.yaml (replicas 4, 자원 증가)
```
```bash
kubectl apply -k k8s/overlays/prod
```

### GitOps (Argo CD)
매니페스트를 **Git 저장소에 두고**, Argo CD가 클러스터 상태를 **Git과 자동으로 동기화**합니다. Git이 단일 진실 공급원(Single Source of Truth)이 되어 변경 이력·리뷰·롤백이 Git으로 해결됩니다. (→ `05.CICD/01.CICD개념과브랜치전략.md`)

## 6. 면접 질문

1. **liveness와 readiness probe의 차이는?**
   → liveness가 실패하면 컨테이너를 재시작하고, readiness가 실패하면 재시작하지 않고 Service 엔드포인트에서 제외해 트래픽만 막습니다.
2. **HPA는 어떻게 동작하나요?**
   → metrics-server 등에서 지표를 읽어 목표 사용률 대비 현재 사용률로 필요한 Pod 수를 계산해 Deployment의 replicas를 조정합니다. CPU 사용률 기준이면 requests 설정이 필요합니다.
3. **롤링 업데이트 중 요청 유실을 막으려면?**
   → readinessProbe로 준비된 Pod에만 트래픽을 보내고, preStop 대기와 Graceful Shutdown으로 라우팅에서 빠질 시간을 주며, maxUnavailable을 0으로 둡니다.
4. **Helm과 Kustomize의 차이는?**
   → Helm은 템플릿과 values로 패키지를 만들고 릴리스를 관리하며, Kustomize는 템플릿 없이 기본 YAML에 환경별 패치를 덧씌웁니다.

## 핵심 정리
- startup(기동 대기) / readiness(트래픽 제외) / liveness(재시작), liveness에 외부 의존성 X
- HPA(Pod 수, requests 필요) + Cluster Autoscaler·Karpenter(노드 수)
- 롤링 업데이트 maxSurge·maxUnavailable, `rollout undo`
- 무중단 종료: preStop sleep + SIGTERM Graceful Shutdown + PDB + AZ 분산
- Helm(템플릿·패키지) / Kustomize(패치) / Argo CD(GitOps)
