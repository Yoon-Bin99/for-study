# 01. CI/CD 개념과 Git 브랜치 전략

> **학습 목표**
> - CI, 지속적 전달, 지속적 배포의 차이를 설명할 수 있다.
> - CI/CD 파이프라인의 단계와 각 단계의 목적을 설명할 수 있다.
> - Git Flow, GitHub Flow, 트렁크 기반 개발을 비교할 수 있다.
> - Push 방식 배포와 GitOps(Pull 방식) 배포의 차이를 설명할 수 있다.

---

## 1. CI/CD란?

### CI (Continuous Integration, 지속적 통합)
개발자들이 코드를 **자주(하루 여러 번) 메인 브랜치에 통합**하고, 통합할 때마다 **자동으로 빌드·테스트**하는 것입니다.

- 목적: 통합 문제(충돌, 버그)를 **일찍, 작게** 발견
- 없으면? 몇 주 동안 각자 개발 → 마지막에 합치다 충돌 지옥 ("Integration Hell")

### CD: 두 가지 의미
| 용어 | 의미 | 운영 배포 |
|---|---|---|
| **지속적 전달 (Continuous Delivery)** | 언제든 운영에 배포할 수 있는 상태로 자동 준비 (스테이징까지 자동) | **사람이 승인** 버튼 |
| **지속적 배포 (Continuous Deployment)** | 테스트를 통과하면 **운영까지 자동 배포** | 자동 |

```
코드 Push ─[CI: 빌드 → 테스트 → 분석]─> 아티팩트 ─[CD: 스테이징 배포 → (승인) → 운영 배포]─> 모니터링
```

## 2. 파이프라인 단계

| 단계 | 하는 일 | 도구 예 |
|---|---|---|
| **Source** | 코드 변경 감지 (Push, PR) | GitHub, CodeCommit |
| **Build** | 컴파일, 의존성 설치, jar 생성 | Gradle, Maven |
| **Test** | 단위·통합 테스트, 커버리지 | JUnit, Testcontainers, JaCoCo |
| **정적 분석·보안** | 코드 품질, 취약점, 비밀 유출 검사 | SonarQube, Checkstyle, Trivy, Dependabot |
| **Package** | 도커 이미지 빌드·태그 | Docker, Jib, Buildpacks |
| **Publish** | 레지스트리에 업로드 | **ECR**, Docker Hub, GHCR |
| **Deploy** | 환경별 배포 | kubectl, Helm, Argo CD, CodeDeploy, ECS |
| **Verify** | 헬스 체크, 스모크 테스트, 지표 확인, 실패 시 롤백 | Actuator, CloudWatch, Prometheus |

### CI/CD 도구
| 도구 | 특징 |
|---|---|
| **GitHub Actions** | GitHub 내장, YAML, 마켓플레이스 액션 풍부 |
| **AWS CodePipeline + CodeBuild + CodeDeploy** | AWS 서비스와 통합, IAM 권한 관리 |
| Jenkins | 오래된 표준, 설치형, 플러그인 많음, 운영 부담 |
| GitLab CI | GitLab 내장 |
| **Argo CD** | 쿠버네티스 전용 **GitOps CD** |

## 3. 좋은 파이프라인의 원칙

| 원칙 | 설명 |
|---|---|
| **빠르게** | 10분 이내 목표. 캐시(Gradle, Docker 레이어), 병렬 실행 |
| **한 번 빌드, 여러 번 배포** | 이미지를 **한 번만 빌드**하고 같은 이미지를 dev → stg → prod로 승격 (환경마다 다시 빌드 X) |
| **불변 아티팩트** | 이미지 태그는 커밋 해시, 같은 태그를 덮어쓰지 않음 |
| **실패하면 멈춤** | 테스트 실패 시 다음 단계 진행 X |
| **비밀 정보 분리** | 코드에 키 X, CI의 Secret 저장소·OIDC 사용 |
| **롤백 가능** | 이전 이미지로 즉시 되돌릴 수 있게 |
| **재현 가능** | 누가 언제 돌려도 같은 결과 |

## 4. Git 브랜치 전략

### Git Flow
```
main      ●──────────────────●────────────●     (운영 배포 버전, 태그 v1.0, v1.1)
           \                / \          /
hotfix      \              /   ●────────●       (운영 긴급 수정)
             \            /
release       \     ●────●                      (배포 준비: QA, 버그 수정)
               \   /      \
develop   ●─────●─●────────●──────●──           (다음 버전 통합)
           \   /            \    /
feature     ●─●              ●──●               (기능 개발)
```
| 브랜치 | 역할 |
|---|---|
| main | 운영에 배포된 코드 |
| develop | 다음 배포를 위한 통합 |
| feature/* | 기능 개발 (develop에서 분기) |
| release/* | 배포 준비 |
| hotfix/* | 운영 긴급 수정 (main에서 분기) |

- 장점: 체계적, **정기 릴리스**(모바일 앱, 패키지 소프트웨어)에 적합
- 단점: 복잡, 브랜치가 오래 살아 충돌 증가, 잦은 배포에 부적합

### GitHub Flow
```
main      ●────────●─────────●────────●    (항상 배포 가능)
           \      /  \      /
feature     ●──●─●    ●────●               (PR → 리뷰 → CI 통과 → merge → 배포)
```
- **main + 기능 브랜치**만 사용
- PR로 리뷰, CI 통과 후 main에 머지하면 배포
- 장점: 단순, **잦은 배포(웹 서비스)** 에 적합
- 단점: 여러 버전을 동시에 유지하기 어려움

### 트렁크 기반 개발 (Trunk-Based Development)
- 모두가 **main(trunk)에 작은 단위로 매일 여러 번** 통합 (브랜치는 수명이 1~2일 이내)
- 미완성 기능은 **피처 플래그(Feature Flag)** 로 숨긴 채 배포
- 대규모 테크 기업의 방식, 강력한 자동 테스트가 전제

| 비교 | Git Flow | GitHub Flow | 트렁크 기반 |
|---|---|---|---|
| 복잡도 | 높음 | 낮음 | 낮음 |
| 배포 주기 | 정기 릴리스 | 수시 | 매우 잦음 |
| 브랜치 수명 | 김 | 짧음 | 매우 짧음 |
| 적합 | 앱, 패키지, 버전 관리 필요 | 웹 서비스, 소규모 팀 | 성숙한 CI·테스트 문화 |

### 커밋·PR 관례
- **Conventional Commits**: `feat: 회원 가입 API`, `fix: 주문 금액 계산 오류`, `refactor:`, `test:`, `docs:`, `chore:`
- PR은 작게, CI 통과 + 리뷰 승인 후 머지 (Branch Protection Rule)
- 머지 방식: Merge commit / **Squash merge**(PR을 커밋 하나로) / Rebase

## 5. 배포 방식: Push vs Pull (GitOps)

### Push 방식 (전통적)
```
[CI 서버] ──kubectl apply / helm upgrade──> [클러스터]
```
- CI가 클러스터 접근 권한(자격 증명)을 가짐
- 단순하지만, 누군가 클러스터를 직접 바꾸면 Git과 실제 상태가 어긋남(Drift)

### Pull 방식 (GitOps)
```
[CI] 이미지 빌드·push → 매니페스트 저장소의 이미지 태그 수정(커밋)
                              ↓ (감시)
[Argo CD (클러스터 안)] ── Git 상태와 클러스터 상태를 비교해 동기화 ──> 배포
```
| GitOps 원칙 | 의미 |
|---|---|
| 선언적 | 원하는 상태를 YAML로 |
| **Git이 단일 진실 공급원** | 모든 변경은 Git 커밋(PR)으로 |
| 자동 동기화 | 에이전트가 Git → 클러스터 반영 |
| 지속적 조정 | 수동 변경(Drift)을 감지해 되돌림 |

- 장점: 배포 이력 = Git 로그, **롤백 = git revert**, CI가 클러스터 권한을 가질 필요 없음(보안)
- 보통 **애플리케이션 코드 저장소**와 **매니페스트(배포 설정) 저장소**를 분리

## 6. 면접 질문

1. **CI/CD란?**
   → CI는 코드를 자주 통합하며 자동으로 빌드·테스트하는 것이고, CD는 검증된 결과물을 자동으로 배포 가능한 상태로 만들거나(지속적 전달) 운영까지 자동 배포(지속적 배포)하는 것입니다.
2. **지속적 전달과 지속적 배포의 차이는?**
   → 지속적 전달은 운영 배포 직전까지 자동화하고 마지막에 사람이 승인하며, 지속적 배포는 운영 배포까지 자동입니다.
3. **Git Flow와 GitHub Flow의 차이는?**
   → Git Flow는 develop·release·hotfix 등 여러 브랜치로 정기 릴리스를 관리하고, GitHub Flow는 main과 기능 브랜치만으로 PR 머지 시 바로 배포하는 단순한 방식입니다.
4. **GitOps란?**
   → Git 저장소를 배포 상태의 단일 진실 공급원으로 두고, 클러스터 안의 에이전트가 Git의 선언된 상태와 실제 상태를 자동으로 동기화하는 방식입니다.

## 핵심 정리
- CI(자주 통합 + 자동 빌드·테스트) / CD(전달: 승인 후 배포, 배포: 완전 자동)
- 파이프라인: Source → Build → Test → 분석 → 이미지 → Push → Deploy → Verify
- 한 번 빌드해 여러 환경으로 승격, 커밋 해시 태그
- Git Flow(정기 릴리스) / GitHub Flow(수시 배포) / 트렁크 기반(피처 플래그)
- Push 배포 vs GitOps(Argo CD, Git = 진실)
