# 02. GitHub Actions

> **학습 목표**
> - 워크플로, 이벤트, 잡, 스텝, 러너의 관계를 설명할 수 있다.
> - Spring Boot 프로젝트의 CI(빌드·테스트) 워크플로를 작성할 수 있다.
> - OIDC로 AWS에 키 없이 인증하고 ECR에 이미지를 푸시할 수 있다.
> - Secrets, 캐시, 환경(Environment) 승인을 활용할 수 있다.

---

## 1. 구성 요소

```
.github/workflows/ci.yml   ← 워크플로 (YAML 파일 하나)
   on: push, pull_request   ← 이벤트 (트리거)
   jobs:
     build:                 ← 잡 (러너 하나에서 실행, 잡끼리는 기본 병렬)
       runs-on: ubuntu-latest  ← 러너 (실행 머신)
       steps:               ← 스텝 (순서대로)
         - uses: actions/checkout@v4     ← 액션 (재사용 가능한 단위)
         - run: ./gradlew build          ← 쉘 명령
```

| 개념 | 설명 |
|---|---|
| **Workflow** | 자동화 프로세스 전체 (`.github/workflows/*.yml`) |
| **Event** | 실행 조건: `push`, `pull_request`, `schedule`(cron), `workflow_dispatch`(수동) |
| **Job** | 같은 러너에서 실행되는 스텝 묶음. `needs`로 순서 지정 |
| **Step** | `uses`(액션) 또는 `run`(명령) |
| **Runner** | 실행 서버. GitHub 호스팅(ubuntu-latest 등) 또는 **Self-hosted** |
| **Action** | 재사용 컴포넌트 (마켓플레이스) |

> 액션은 `@v4`처럼 **버전을 고정**해서 씁니다. (보안을 더 엄격히 하려면 커밋 SHA로 고정) 아래 예시의 액션 버전은 작성 시점 기준이며, 각 액션 저장소에서 최신 메이저 버전을 확인하세요.

## 2. CI 워크플로: 빌드와 테스트

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest

    services:                      # 테스트용 DB 컨테이너
      mysql:
        image: mysql:8.4
        env:
          MYSQL_ROOT_PASSWORD: test
          MYSQL_DATABASE: app_test
        ports: ["3306:3306"]
        options: >-
          --health-cmd="mysqladmin ping -h localhost"
          --health-interval=5s --health-retries=10

    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: JDK 21 설정
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"

      - name: Gradle 설정 (캐시 포함)
        uses: gradle/actions/setup-gradle@v4

      - name: 빌드 및 테스트
        run: ./gradlew build
        env:
          SPRING_DATASOURCE_URL: jdbc:mysql://localhost:3306/app_test
          SPRING_DATASOURCE_USERNAME: root
          SPRING_DATASOURCE_PASSWORD: test

      - name: 테스트 리포트 업로드 (실패해도)
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-report
          path: build/reports/tests/test
```

- PR을 올리면 자동으로 빌드·테스트 → 결과가 PR에 표시
- **Branch Protection Rule**에서 "이 체크가 통과해야 머지 가능"으로 설정

## 3. Secrets와 변수

```yaml
steps:
  - run: echo "Slack 알림"
    env:
      SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK_URL }}   # 로그에 자동 마스킹 (***)
      APP_ENV: ${{ vars.APP_ENV }}                       # 민감하지 않은 변수
```
- 저장소 Settings → Secrets and variables → Actions
- **Environment**(dev, prod)별로 Secret을 나누고, prod에는 **승인자(Required reviewers)** 지정 가능

### 자주 쓰는 컨텍스트
| 표현식 | 값 |
|---|---|
| `${{ github.sha }}` | 커밋 해시 → **이미지 태그** |
| `${{ github.ref_name }}` | 브랜치·태그 이름 |
| `${{ github.event_name }}` | push, pull_request ... |
| `${{ secrets.X }}` / `${{ vars.X }}` | 비밀 / 변수 |

## 4. OIDC로 AWS 인증 (Access Key 없이)

### 옛날 방식의 문제
IAM 사용자 Access Key를 GitHub Secret에 저장 → **유출되면 영구적인 키**가 노출됨, 주기적 교체 필요

### OIDC (OpenID Connect)
```
1. 워크플로 실행 시 GitHub가 "이 저장소, 이 브랜치의 워크플로다"라는 단기 토큰(JWT) 발급
2. AWS STS가 토큰을 검증 → 신뢰 정책에 맞으면 IAM 역할의 임시 자격 증명(1시간) 발급
3. 키를 저장할 필요 없음
```

AWS 쪽 준비:
1. IAM → 자격 증명 공급자(Identity Provider)에 `token.actions.githubusercontent.com` 추가
2. IAM 역할 생성, 신뢰 정책에서 **특정 저장소·브랜치만** 허용
```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
    "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:my-org/my-repo:ref:refs/heads/main" }
  }
}
```
3. 역할에 ECR 푸시 등 **필요한 권한만** 부여

## 5. CD 워크플로: 이미지 빌드 → ECR 푸시 → 배포

```yaml
# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]

permissions:
  id-token: write          # ★ OIDC 토큰 발급에 필요
  contents: read

env:
  AWS_REGION: ap-northeast-2
  ECR_REPOSITORY: myapp

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.meta.outputs.image }}
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"

      - uses: gradle/actions/setup-gradle@v4

      - name: 테스트 및 jar 빌드
        run: ./gradlew build

      - name: AWS 인증 (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: ${{ env.AWS_REGION }}

      - name: ECR 로그인
        id: ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: 이미지 빌드 및 푸시
        id: meta
        run: |
          IMAGE=${{ steps.ecr.outputs.registry }}/${ECR_REPOSITORY}:${{ github.sha }}
          docker build -t "$IMAGE" .
          docker push "$IMAGE"
          echo "image=$IMAGE" >> "$GITHUB_OUTPUT"

  deploy:
    needs: build-and-push          # 앞 잡이 성공해야 실행
    runs-on: ubuntu-latest
    environment: production        # ★ 승인자가 승인해야 진행 (설정 시)
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: ap-northeast-2

      - name: EKS 배포 (Push 방식 예시)
        run: |
          aws eks update-kubeconfig --name my-cluster --region ap-northeast-2
          kubectl set image deployment/myapp app=${{ needs.build-and-push.outputs.image }}
          kubectl rollout status deployment/myapp --timeout=300s
```

> kubectl이 동작하려면 이 IAM 역할이 EKS 클러스터의 **액세스 항목(Access Entry)** 에 등록되어 쿠버네티스 권한을 받아야 합니다. (→ `06.AWS/06.ECR과ECS와EKS.md`)

> GitOps를 쓴다면 `deploy` 잡에서 kubectl 대신 **매니페스트 저장소의 이미지 태그를 수정해 커밋**하고, Argo CD가 반영하게 합니다.

## 6. 유용한 기능

```yaml
# 경로 필터: 백엔드 코드가 바뀔 때만
on:
  push:
    paths: ["backend/**", ".github/workflows/backend.yml"]

# 동시 실행 제어: 같은 브랜치의 이전 배포 취소
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true

# 매트릭스: 여러 버전으로 테스트
strategy:
  matrix:
    java: ["17", "21"]

# 조건부 실행 (잡의 steps 안에서)
steps:
  - run: ./notify.sh
    if: failure()       # 앞 스텝이 실패했을 때만 (success(), always(), cancelled())
```

| 기능 | 용도 |
|---|---|
| `actions/cache` / setup-* 내장 캐시 | 의존성 캐시로 빌드 시간 단축 |
| Reusable workflow (`workflow_call`) | 여러 저장소에서 같은 파이프라인 재사용 |
| Self-hosted runner | 사내망 접근, 비용 절감, 특수 장비 |
| Dependabot | 의존성 업데이트 PR 자동 생성 |

## 7. 면접 질문

1. **GitHub Actions의 구성 요소는?**
   → 이벤트로 실행되는 워크플로 안에 여러 잡이 있고, 잡은 러너에서 실행되며, 잡 안의 스텝은 액션이나 쉘 명령을 순서대로 실행합니다.
2. **CI에서 AWS 자격 증명을 안전하게 쓰는 방법은?**
   → 장기 Access Key를 저장하지 않고 OIDC로 GitHub 토큰을 IAM 역할의 임시 자격 증명으로 교환하며, 신뢰 정책으로 특정 저장소·브랜치만 허용하고 최소 권한을 부여합니다.
3. **이미지 태그로 커밋 해시를 쓰는 이유는?**
   → 이미지와 소스 코드 버전이 1:1로 대응되어 추적과 롤백이 쉽고, 태그가 덮어써지지 않기 때문입니다.

## 핵심 정리
- Workflow(on 이벤트) → Job(runner, needs) → Step(uses / run)
- CI: checkout → setup-java → gradle build(테스트) → 리포트
- CD: OIDC(`id-token: write`) → ECR 로그인 → `docker build/push :${{ github.sha }}` → 배포
- Secrets·Environment 승인, concurrency, 캐시
