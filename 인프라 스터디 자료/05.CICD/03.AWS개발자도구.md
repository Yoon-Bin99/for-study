# 03. AWS 개발자 도구: CodePipeline, CodeBuild, CodeDeploy

> **학습 목표**
> - CodePipeline, CodeBuild, CodeDeploy의 역할과 관계를 설명할 수 있다.
> - `buildspec.yml`로 빌드·이미지 푸시 단계를 작성할 수 있다.
> - `appspec.yml`과 라이프사이클 훅으로 EC2 배포를 구성할 수 있다.
> - ECS·EKS 배포와 GitHub Actions 대비 장단점을 설명할 수 있다.

---

## 1. 전체 구조

```
[GitHub / CodeCommit / S3]
          │ (변경 감지: CodeConnections로 GitHub 연결)
          ↓
+──────────────── CodePipeline (파이프라인 오케스트레이션) ────────────────+
|  Source Stage  →  Build Stage     →  Approval   →  Deploy Stage        |
|  소스 다운로드      CodeBuild          (수동 승인)      CodeDeploy / ECS /   |
|                  buildspec.yml                      CodeBuild(kubectl)  |
+────────────────────────────────────────────────────────────────────────+
   각 단계의 결과물(아티팩트)은 S3 아티팩트 버킷을 통해 다음 단계로 전달
```

| 서비스 | 역할 | 비유 |
|---|---|---|
| **CodePipeline** | 단계(Source → Build → Deploy)를 **연결·순서 제어** | 공장의 컨베이어 벨트 |
| **CodeBuild** | 컨테이너에서 **빌드·테스트·이미지 생성** 실행 (서버 관리 불필요, 분 단위 과금) | 조립 작업자 |
| **CodeDeploy** | EC2·온프레미스·**ECS**·Lambda에 **배포** (인플레이스, 블루/그린) | 배송 담당 |
| CodeConnections (구 CodeStar Connections) | GitHub·GitLab 등 외부 저장소 연결 | |
| ECR | 도커 이미지 저장소 | 창고 |

> CodeCommit은 신규 고객 대상 판매가 중단되었다가 2025년 말 다시 일반 제공(GA)으로 전환되었습니다. 대부분의 팀은 소스를 **GitHub에 두고 CodeConnections로 연결**합니다.

## 2. CodeBuild: buildspec.yml

프로젝트 루트에 `buildspec.yml`을 둡니다. CodeBuild는 이 파일대로 **빌드 컨테이너 안에서** 명령을 실행합니다.

```yaml
version: 0.2

env:
  variables:
    AWS_REGION: ap-northeast-2
    ECR_REPO: 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/myapp
  secrets-manager:
    SONAR_TOKEN: prod/ci:sonarToken          # Secrets Manager 값 주입

phases:
  install:
    runtime-versions:
      java: corretto21
  pre_build:
    commands:
      - echo "ECR 로그인"
      - aws ecr get-login-password --region $AWS_REGION | docker login --username AWS --password-stdin ${ECR_REPO%%/*}
      - IMAGE_TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c 1-7)   # 커밋 해시 7자리
  build:
    commands:
      - echo "테스트 및 빌드"
      - ./gradlew clean build
      - docker build -t $ECR_REPO:$IMAGE_TAG .
  post_build:
    commands:
      - docker push $ECR_REPO:$IMAGE_TAG
      # ECS 배포 액션이 읽을 파일 생성
      - printf '[{"name":"app","imageUri":"%s"}]' $ECR_REPO:$IMAGE_TAG > imagedefinitions.json

artifacts:
  files:
    - imagedefinitions.json
    - appspec.yml
    - scripts/**/*
    - build/libs/*.jar

reports:
  junit-tests:
    files: ["build/test-results/test/*.xml"]
    file-format: JUNITXML

cache:
  paths:
    - /root/.gradle/caches/**/*
    - /root/.gradle/wrapper/**/*
```

| phase | 용도 |
|---|---|
| `install` | 런타임 설치 |
| `pre_build` | 로그인, 변수 준비 |
| `build` | 빌드·테스트 |
| `post_build` | 푸시, 결과 파일 생성 (build 실패해도 실행되므로 주의) |

- 도커 이미지를 빌드하려면 CodeBuild 프로젝트 설정에서 **권한 있는 모드(Privileged)** 를 켜야 합니다.
- CodeBuild **서비스 역할(IAM Role)** 에 ECR 푸시, S3 아티팩트, 로그 권한을 부여합니다.
- 테스트에 DB가 필요하면 **VPC 설정**으로 프라이빗 서브넷의 리소스에 접근할 수 있습니다.

## 3. CodeDeploy: EC2 배포

### 구성 요소
| 요소 | 설명 |
|---|---|
| 애플리케이션 | 배포 대상의 이름 |
| **배포 그룹** | 배포할 인스턴스 묶음 (**태그** 또는 **Auto Scaling 그룹**으로 지정) + 배포 설정 |
| **CodeDeploy 에이전트** | EC2에 설치되어 배포 명령을 수행 |
| **appspec.yml** | 무엇을 어디에 복사하고 어떤 스크립트를 실행할지 |
| 배포 설정 | `AllAtOnce`, `HalfAtATime`, `OneAtATime` (동시에 몇 대씩) |

### appspec.yml (EC2)
```yaml
version: 0.0
os: linux
files:
  - source: build/libs/
    destination: /opt/myapp/
hooks:
  ApplicationStop:
    - location: scripts/stop.sh
      timeout: 60
  AfterInstall:
    - location: scripts/after_install.sh
  ApplicationStart:
    - location: scripts/start.sh
      timeout: 120
      runas: app
  ValidateService:
    - location: scripts/health_check.sh
      timeout: 120
```

### 라이프사이클 훅 순서 (인플레이스)
```
ApplicationStop → DownloadBundle → BeforeInstall → Install → AfterInstall
   → ApplicationStart → ValidateService
(로드밸런서가 있으면 앞뒤로 BlockTraffic / AllowTraffic: 배포 중인 인스턴스를 대상 그룹에서 빼고 다시 넣음)
```
- `ValidateService`에서 헬스 체크 실패(종료 코드 ≠ 0) → 배포 실패 → **자동 롤백** 설정 가능

### 배포 유형
| 유형 | 동작 |
|---|---|
| **인플레이스 (In-place)** | 기존 인스턴스에서 앱을 멈추고 새 버전 설치 (배포 설정으로 몇 대씩 진행) |
| **블루/그린** | 새 인스턴스(Auto Scaling 그룹 복제)에 배포 → 트래픽 전환 → 구 인스턴스 종료 |

## 4. ECS와 EKS로 배포

### ECS
| 방식 | 설명 |
|---|---|
| **ECS 표준 배포** | CodePipeline의 ECS 액션이 `imagedefinitions.json`을 읽어 **태스크 정의 새 리비전 → 서비스 롤링 업데이트** |
| **ECS 블루/그린 (CodeDeploy)** | `appspec.yaml` + `imageDetail.json`, ALB 리스너를 새 태스크 세트로 전환, 카나리·선형 트래픽 이동 (`ECSCanary10Percent5Minutes`) |

> ECS는 2025년부터 **CodeDeploy 없이도 ECS 자체 블루/그린 배포**를 지원합니다.

### EKS
CodePipeline에는 EKS 배포 액션이 추가되었지만(Helm·kubectl 매니페스트), 실무에서는
- **CodeBuild에서 `kubectl`/`helm` 실행** (CodeBuild 역할을 EKS Access Entry에 등록) 또는
- **이미지만 푸시하고 Argo CD(GitOps)** 로 배포하는 방식이 많이 쓰입니다.

## 5. GitHub Actions vs AWS CodePipeline

| 비교 | GitHub Actions | AWS CodePipeline + CodeBuild |
|---|---|---|
| 위치 | 코드 저장소와 같은 곳 | AWS 계정 안 |
| 설정 | 워크플로 YAML 하나 | 파이프라인 + buildspec + appspec (콘솔·IaC) |
| AWS 연동 | OIDC로 역할 위임 | **IAM 역할로 네이티브**, VPC 내부 리소스 접근 쉬움 |
| 생태계 | 마켓플레이스 액션 풍부 | AWS 서비스 위주 |
| 비용 | 무료 분량 + 분 단위 | 파이프라인·빌드 시간 과금 |
| 적합 | GitHub 중심 팀, 범용 | AWS 중심, 규정상 빌드가 계정 안에서 돌아야 할 때 |

> 혼합도 흔합니다: **CI는 GitHub Actions**(PR 테스트), **CD는 CodePipeline/Argo CD**.

## 6. 면접 질문

1. **CodePipeline, CodeBuild, CodeDeploy의 차이는?**
   → CodePipeline은 소스·빌드·배포 단계를 연결하는 오케스트레이터, CodeBuild는 빌드·테스트를 실행하는 관리형 빌드 서비스, CodeDeploy는 EC2·ECS·Lambda에 배포하는 서비스입니다.
2. **buildspec.yml의 phase는?**
   → install(런타임), pre_build(로그인·준비), build(빌드·테스트), post_build(푸시·결과 생성)이며, artifacts로 다음 단계에 넘길 파일을 지정합니다.
3. **CodeDeploy에서 배포 실패를 어떻게 감지하나요?**
   → appspec의 ValidateService 훅에서 헬스 체크 스크립트를 실행해 실패하면 배포를 실패 처리하고, 자동 롤백을 설정해 이전 버전으로 되돌립니다.

---

## 핵심 정리
- CodePipeline(연결) → CodeBuild(buildspec: 빌드·이미지) → CodeDeploy(appspec: 배포)
- 단계 간 결과물은 S3 아티팩트, 권한은 서비스 역할(IAM)
- EC2: 에이전트 + appspec 훅(ApplicationStop → ... → ValidateService)
- ECS: imagedefinitions.json, EKS: CodeBuild kubectl 또는 Argo CD
