# 04. 배포 전략 (무중단 배포)

> **학습 목표**
> - 다운타임이 생기는 이유와 무중단 배포의 조건을 설명할 수 있다.
> - 롤링, 블루/그린, 카나리 배포의 동작과 장단점을 비교할 수 있다.
> - DB 스키마 변경을 무중단으로 진행하는 방법(Expand-Contract)을 설명할 수 있다.
> - 롤백 전략과 피처 플래그를 설명할 수 있다.

---

## 1. 다운타임은 왜 생기는가?

서버 1대에서 `기존 앱 종료 → 새 앱 시작`을 하면, JVM이 뜨는 수십 초 동안 요청을 받을 수 없습니다.

무중단 배포의 조건:
1. **서버가 2대 이상** (하나를 바꾸는 동안 다른 쪽이 처리)
2. 앞단에 **로드밸런서**
3. **헬스 체크**: 준비된 서버에만 트래픽
4. **Graceful Shutdown**: 처리 중인 요청 마무리 후 종료
5. 새 버전과 구버전이 **잠시 공존해도 문제없을 것** (API·DB 호환성)

---

## 2. 재생성 (Recreate)

```
v1 v1 v1  →  (모두 종료)  →  v2 v2 v2
              ↑ 다운타임
```
- 가장 단순, 두 버전이 공존하지 않음
- **다운타임 발생** → 내부 도구, 개발 환경, 두 버전 공존이 불가능할 때

---

## 3. 롤링 배포 (Rolling)

**서버를 하나씩(또는 일부씩) 새 버전으로 교체**합니다.

```
[LB]→ v1 v1 v1 v1
      v2 v1 v1 v1      ← 하나 빼서 교체, 헬스 체크 통과 후 다시 투입
      v2 v2 v1 v1
      v2 v2 v2 v1
      v2 v2 v2 v2
```

| 장점 | 단점 |
|---|---|
| 추가 인프라가 거의 필요 없음 | 배포 중 **v1과 v2가 섞여서** 응답 (호환성 필요) |
| 쿠버네티스·ECS 기본 방식 | 롤백도 다시 롤링 → **느림** |
| | 배포 중 처리 용량이 일시적으로 감소할 수 있음 (maxSurge로 보완) |

---

## 4. 블루/그린 배포 (Blue/Green)

**현재 버전(Blue)과 같은 규모의 새 환경(Green)을 따로 만들고, 검증 후 트래픽을 한 번에 전환**합니다.

```
            ┌──> [Blue  v1 v1 v1]  ← 현재 운영
[LB] ───────┤
            └ ┄> [Green v2 v2 v2]  ← 새 버전 배포·테스트 (내부 테스트 포트로 검증)

전환:  LB 대상을 Green으로 변경 (한 번에)
            ┌ ┄> [Blue  v1 v1 v1]  ← 대기 (문제 시 즉시 되돌림)
[LB] ───────┤
            └──> [Green v2 v2 v2]  ← 운영
```

| 장점 | 단점 |
|---|---|
| **즉시 전환, 즉시 롤백** (LB만 다시 Blue로) | 일시적으로 **인프라 2배** 비용 |
| 버전 혼재 없음 | DB는 공유하므로 스키마 호환성 여전히 필요 |
| 운영과 같은 환경에서 사전 검증 | 전환 순간 모든 사용자가 새 버전 → 문제 시 영향 큼 |

구현:
- AWS: **CodeDeploy 블루/그린**(EC2 ASG, ECS), ECS 네이티브 블루/그린, ALB 대상 그룹 전환
- Route 53 가중치·DNS 전환 (DNS 캐시 때문에 느림)
- 쿠버네티스: Service의 셀렉터를 `version: blue` → `version: green`으로 변경, Argo Rollouts

---

## 5. 카나리 배포 (Canary)

**새 버전에 트래픽 일부(예: 5%)만 보내 지표를 확인하고, 문제가 없으면 점진적으로 늘립니다.**
(탄광의 카나리아: 유독 가스를 먼저 감지)

```
단계 1:  v1 ████████████████████ 95%   v2 █ 5%     → 에러율·응답 시간 확인
단계 2:  v1 ████████████████ 75%       v2 █████ 25%
단계 3:  v1 ██████████ 50%             v2 ██████████ 50%
단계 4:                                v2 ████████████████████ 100%
         ↑ 어느 단계에서든 지표가 나빠지면 v2 → 0% (자동 롤백)
```

| 장점 | 단점 |
|---|---|
| **실제 운영 트래픽으로 검증**, 문제 시 영향 범위 최소 | 트래픽 분할 기능 필요 (LB 가중치, 서비스 메시) |
| 지표 기반 **자동 승격·롤백** 가능 | 모니터링 체계가 전제 |
| | 배포 시간이 김, 버전 혼재 |

구현:
- **ALB 가중치 대상 그룹** (95:5), CodeDeploy `ECSCanary10Percent5Minutes`, `Linear10PercentEvery1Minute`
- 쿠버네티스: **Argo Rollouts**, Flagger + 서비스 메시(Istio)·Gateway API
- 특정 사용자(사내 직원, 베타 사용자)에게만 먼저 노출하는 방식도 가능 (헤더·쿠키 기반 라우팅)

---

## 6. 비교 정리

| 전략 | 다운타임 | 롤백 속도 | 추가 비용 | 버전 혼재 | 위험 범위 |
|---|---|---|---|---|---|
| Recreate | **있음** | 느림 | 없음 | 없음 | 전체 |
| **Rolling** | 없음 | 느림 | 적음 | 있음 | 점진적 |
| **Blue/Green** | 없음 | **즉시** | **2배 (일시)** | 없음 | 전환 시 전체 |
| **Canary** | 없음 | 빠름 | 적음 | 있음 | **최소** |

> A/B 테스트는 배포 전략이 아니라 **기능·UI의 효과를 비교하는 실험**입니다. 카나리는 "안정성 검증", A/B는 "어느 쪽이 더 나은가(전환율)" 측정이 목적입니다.

## 7. DB 스키마 변경: Expand-Contract 패턴

롤링·카나리에서는 v1과 v2가 **같은 DB를 동시에** 씁니다. 컬럼 이름을 바로 바꾸면 v1이 깨집니다.

예: `users.name` → `users.full_name` 으로 변경
```
1단계 (Expand, 확장)    full_name 컬럼 추가 (NULL 허용) ← v1은 영향 없음
2단계 배포             v2: name과 full_name 둘 다에 쓰기, 읽기는 full_name 우선
3단계 데이터 이전       기존 name 데이터를 full_name으로 복사 (배치)
4단계 배포             v3: full_name만 사용
5단계 (Contract, 축소)  name 컬럼 삭제 ← 이제 아무도 안 씀
```
원칙:
- **하위 호환되는 변경**(컬럼 추가, NULL 허용)을 먼저, **파괴적 변경**(삭제, 이름 변경, NOT NULL)은 나중에
- 마이그레이션 도구: **Flyway**, Liquibase (버전 관리되는 SQL 파일)
- 대용량 테이블 `ALTER`는 락을 오래 잡을 수 있음 → MySQL Online DDL, gh-ost, pt-online-schema-change

> API도 마찬가지입니다. 응답 필드를 삭제·이름 변경하지 말고, 새 필드 추가 → 클라이언트 전환 → 구 필드 제거 순서로 진행합니다.

## 8. 롤백과 피처 플래그

### 롤백 전략
| 방법 | 설명 |
|---|---|
| 이전 이미지로 재배포 | `kubectl rollout undo`, 이전 태그로 배포 (**불변 태그 필수**) |
| 블루/그린 역전환 | LB를 Blue로 |
| GitOps | `git revert` → Argo CD 동기화 |
| **롤포워드 (Roll-forward)** | 되돌리지 않고 빠르게 수정 버전 배포 (DB 변경이 섞여 되돌리기 어려울 때) |

### 피처 플래그 (Feature Flag / Toggle)
**배포(Deploy)와 출시(Release)를 분리**합니다. 코드는 배포하되, 기능은 설정으로 켜고 끕니다.
```java
if (featureFlags.isEnabled("new-checkout", user)) {
    return newCheckout(order);
}
return legacyCheckout(order);
```
- 문제가 생기면 **재배포 없이 플래그만 끔** → 가장 빠른 롤백
- 특정 사용자 비율에만 켜는 점진적 출시
- 도구: LaunchDarkly, Unleash, AWS AppConfig, 직접 구현(DB·설정)
- 주의: 다 쓴 플래그는 **반드시 제거** (기술 부채)

## 9. 면접 질문

1. **무중단 배포 방법에는 어떤 것이 있나요?**
   → 서버를 하나씩 교체하는 롤링, 새 환경을 만들어 한 번에 전환하는 블루/그린, 일부 트래픽으로 먼저 검증하는 카나리가 있습니다.
2. **블루/그린과 카나리의 차이는?**
   → 블루/그린은 별도 환경을 준비해 트래픽을 한 번에 전환하고 즉시 롤백할 수 있으며, 카나리는 트래픽을 점진적으로 늘리며 지표로 검증해 문제 영향 범위를 최소화합니다.
3. **롤링 배포 중 DB 스키마는 어떻게 변경하나요?**
   → 구버전과 신버전이 동시에 동작하므로, 하위 호환되는 변경(컬럼 추가)을 먼저 하고 코드 전환 후 파괴적 변경(삭제)을 나중에 하는 Expand-Contract 방식으로 진행합니다.
4. **피처 플래그의 장점은?**
   → 배포와 기능 출시를 분리해 재배포 없이 기능을 켜고 끌 수 있어 빠른 롤백과 점진적 출시가 가능합니다.

---

## 핵심 정리
- 무중단 조건: 2대 이상 + LB + 헬스 체크 + Graceful Shutdown + 버전 호환
- Recreate(다운타임) / Rolling(기본, 혼재) / Blue-Green(즉시 전환·롤백, 2배 비용) / Canary(일부 트래픽, 지표 기반)
- DB는 Expand → 코드 전환 → Contract (Flyway)
- 롤백: 불변 태그 재배포, 피처 플래그로 배포와 출시 분리
