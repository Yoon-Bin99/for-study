# 03. EC2와 오토스케일링

> **학습 목표**
> - EC2 인스턴스 유형 이름을 읽고 용도에 맞게 고를 수 있다.
> - AMI, 키 페어, 사용자 데이터, 인스턴스 프로파일의 역할을 설명할 수 있다.
> - 구매 옵션(온디맨드, Savings Plans, 스팟)을 비교할 수 있다.
> - Auto Scaling 그룹과 스케일링 정책을 설계할 수 있다.

## 1. EC2 (Elastic Compute Cloud)

AWS의 **가상 서버**입니다. (IaaS)

### 인스턴스 유형 읽기
```
  m   7   g   .   large
  │   │   │       └── 크기: nano < micro < small < medium < large < xlarge < 2xlarge ...
  │   │   └── 추가 속성: g = Graviton(ARM), i = Intel, a = AMD, d = 로컬 NVMe, n = 네트워크 강화
  │   └── 세대 (숫자가 클수록 최신, 보통 가성비 좋음)
  └── 패밀리
```

| 패밀리 | 용도 | 예 |
|---|---|---|
| **t** (버스터블) | 평소 낮고 가끔 튀는 부하. **CPU 크레딧** 방식 | t3.micro, t4g.small (개발·테스트, 소규모) |
| **m** (범용) | CPU·메모리 균형 | m7g.large (일반 웹·API) |
| **c** (컴퓨팅) | CPU 많음 | c7g (배치, 인코딩, 고부하 API) |
| **r** (메모리) | 메모리 많음 | r7g (캐시, 인메모리 DB, JVM 큰 힙) |
| **g, p** (가속) | GPU | g5, p5 (머신러닝) |
| i (스토리지) | 고성능 로컬 SSD | 데이터베이스 |

> **t 계열 주의**: 기준 성능 이상으로 CPU를 계속 쓰면 크레딧이 소진되어 **성능이 급락**합니다(standard 모드). 지속 부하가 있는 운영 서버는 m/c 계열을 고려하세요.

## 2. EC2 구성 요소

| 요소 | 설명 |
|---|---|
| **AMI** (Amazon Machine Image) | OS + 설치 소프트웨어가 담긴 **템플릿** (Amazon Linux 2023, Ubuntu). 내 서버를 AMI로 만들어 복제 가능 |
| **인스턴스 유형** | CPU·메모리 사양 |
| **키 페어** | SSH 접속용 공개키·개인키 (.pem) |
| **보안 그룹** | 방화벽 |
| **EBS 볼륨** | 루트 디스크 (네트워크 연결 블록 스토리지) |
| **사용자 데이터 (User Data)** | **최초 부팅 시 실행할 스크립트** |
| **IAM 인스턴스 프로파일** | EC2가 AWS 서비스(S3 등)에 접근할 때 쓰는 **IAM 역할** |
| 탄력적 IP | 고정 공인 IP (중지·시작해도 유지) |

### 사용자 데이터 예
```bash
#!/bin/bash
dnf install -y java-21-amazon-corretto docker
systemctl enable --now docker
usermod -aG docker ec2-user
```

### 인스턴스 프로파일 (IAM 역할)
```
❌ EC2 안에 Access Key를 파일로 저장 → 유출 위험
✅ EC2에 IAM 역할 연결 → SDK가 인스턴스 메타데이터에서 임시 자격 증명을 자동으로 받아 사용 (자동 갱신)
```
> 메타데이터 서비스는 **IMDSv2(토큰 필수)** 로 설정하는 것이 보안 권장 사항입니다. (SSRF 공격으로 자격 증명이 탈취되는 것 방지)

### 인스턴스 상태
```
pending → running ⇄ stopping → stopped ──→ terminated (삭제, 복구 불가)
            │ reboot
```
| 동작 | 과금 | 데이터 |
|---|---|---|
| 중지 (stop) | 컴퓨팅 과금 X, **EBS는 과금** | EBS 유지, 퍼블릭 IP 바뀜 (탄력적 IP 제외) |
| 종료 (terminate) | 없음 | 루트 EBS 기본 삭제 |
| 재부팅 | 계속 | 유지 |

## 3. 구매 옵션

| 옵션 | 할인 | 특징 | 적합 |
|---|---|---|---|
| **온디맨드** | 없음 | 약정 없이 초 단위 과금 | 짧은 실험, 예측 불가 |
| **Savings Plans** | 큼 (최대 70%대) | 1·3년 **시간당 사용 금액** 약정, 인스턴스 유형·리전 유연 (Compute SP는 Fargate·Lambda도 적용) | 꾸준한 기본 부하 |
| 예약 인스턴스 (RI) | 큼 | 특정 유형 약정 | 고정된 워크로드 (RDS 등) |
| **스팟** | **최대 90%** | 남는 용량, **2분 전 통보 후 회수 가능** | 배치, CI 러너, 무상태 워커, 쿠버네티스 노드 일부 |

> 일반적인 조합: **기본 부하는 Savings Plans, 피크는 온디맨드, 중단돼도 되는 작업은 스팟**

## 4. Auto Scaling 그룹 (ASG)

**EC2 인스턴스 수를 자동으로 조절**하고, 비정상 인스턴스를 **자동 교체**합니다.

```
         [ALB] ── 대상 그룹 (헬스 체크)
           │
+──── Auto Scaling 그룹 (최소 2 / 원하는 3 / 최대 10) ────+
|  AZ-a: [EC2] [EC2]        AZ-c: [EC2]                 |
|            ↑ 시작 템플릿(AMI, 유형, 보안 그룹, 사용자 데이터)으로 생성 |
+───────────────────────────────────────────────────────+
       ↑ CloudWatch 지표 (평균 CPU 60% 초과 → 추가)
```

| 설정 | 의미 |
|---|---|
| **시작 템플릿 (Launch Template)** | 어떤 인스턴스를 만들지 (AMI, 유형, 키, SG, 사용자 데이터, IAM 역할) |
| 최소 / 원하는 / 최대 용량 | 범위와 현재 목표 |
| 서브넷 (여러 AZ) | AZ에 고르게 분산 |
| **헬스 체크 유형** | EC2 상태 검사 또는 **ELB 헬스 체크**(앱이 응답하지 않으면 교체) |

### 스케일링 정책
| 정책 | 동작 | 예 |
|---|---|---|
| **대상 추적 (Target Tracking)** | 지표를 **목표값에 맞추도록** 자동 조절 (가장 쉬움, 권장) | 평균 CPU 50% 유지, 대상당 요청 수 1000 |
| 단계 (Step) | 지표 구간별로 다르게 | CPU 70% 이상 +2, 90% 이상 +4 |
| **예약 (Scheduled)** | 정해진 시간에 | 매일 09시 최소 6대, 22시 2대 |
| 예측 (Predictive) | 과거 패턴으로 미리 확장 | 주기적 트래픽 |

### 고려 사항
| 항목 | 설명 |
|---|---|
| **워밍업 시간** | JVM 기동 + JIT 예열에 시간이 걸림 → 새 인스턴스가 지표에 반영되기 전 과도한 추가 방지 |
| 쿨다운 | 연속 조정 사이 대기 |
| **수명 주기 훅** | 종료 전 로그 업로드·연결 드레이닝 등 작업 시간 확보 |
| **무상태 서버** | 언제든 만들어지고 사라지므로 **세션·파일을 서버에 저장하지 않기** |
| 인스턴스 새로 고침 | 새 AMI·시작 템플릿으로 롤링 교체 |

## 5. 배포 방식: 골든 AMI vs 부트스트랩

| 방식 | 설명 | 장단점 |
|---|---|---|
| 부트스트랩 | 기본 AMI + 사용자 데이터로 부팅 시 설치·다운로드 | 유연, **기동이 느림**, 외부 저장소 장애에 취약 |
| **골든 AMI** | 앱까지 설치된 AMI를 미리 만듦 (Packer, EC2 Image Builder) | **빠른 기동**, 불변 인프라, AMI 관리 필요 |
| 컨테이너 | EC2(또는 Fargate)에서 이미지 pull | 현재 가장 흔함 (ECS, EKS) |

## 7. 면접 질문

1. **EC2에서 AWS 서비스에 접근할 때 Access Key를 쓰면 안 되는 이유는?**
   → 키가 서버에 저장되어 유출 위험이 있고 교체가 어렵기 때문입니다. IAM 역할(인스턴스 프로파일)을 연결하면 자동 갱신되는 임시 자격 증명을 씁니다.
2. **Auto Scaling 그룹의 역할은?**
   → 지표나 일정에 따라 인스턴스 수를 자동으로 조절하고, 헬스 체크에 실패한 인스턴스를 교체하며, 여러 AZ에 분산해 고가용성을 유지합니다.
3. **스팟 인스턴스는 언제 쓰나요?**
   → 대폭 할인되지만 언제든 회수될 수 있으므로, 중단되어도 다시 실행하면 되는 배치·CI·무상태 워커에 씁니다.
4. **오토스케일링 환경에서 서버를 무상태로 만들어야 하는 이유는?**
   → 인스턴스가 수시로 생성·종료되므로 세션이나 파일을 로컬에 저장하면 유실되기 때문입니다.

## 핵심 정리
- 유형: 패밀리(t/m/c/r/g) + 세대 + 속성(g=Graviton) + 크기
- AMI(템플릿), 사용자 데이터(부팅 스크립트), **IAM 역할(키 대신)**, IMDSv2
- 구매: 온디맨드 / Savings Plans(약정) / 스팟(최대 90%, 회수 가능)
- ASG: 시작 템플릿 + 최소·원하는·최대 + 대상 추적 정책 + ELB 헬스 체크
