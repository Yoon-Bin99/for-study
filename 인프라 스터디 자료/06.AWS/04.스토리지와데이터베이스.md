# 04. 스토리지와 데이터베이스 (S3, EBS, EFS, RDS, ElastiCache)

> **학습 목표**
> - 블록, 파일, 객체 스토리지의 차이와 EBS, EFS, S3를 구분할 수 있다.
> - S3의 스토리지 클래스, 보안 설정, Presigned URL을 활용할 수 있다.
> - RDS Multi-AZ와 읽기 전용 복제본의 차이를 설명할 수 있다.
> - 상황에 맞는 AWS 데이터베이스를 선택할 수 있다.

---

## 1. 스토리지 유형

| 유형 | 설명 | 비유 | AWS |
|---|---|---|---|
| **블록** | 디스크를 블록 단위로 제공, OS가 파일시스템을 만듦 | 컴퓨터에 꽂은 SSD | **EBS** |
| **파일** | 여러 서버가 **동시에 마운트**하는 공유 파일시스템 (NFS) | 회사 공유 드라이브 | **EFS** |
| **객체** | 파일을 **키(경로) + 데이터 + 메타데이터**로 저장, HTTP API로 접근 | 무한 용량 창고 | **S3** |

| 비교 | EBS | EFS | S3 |
|---|---|---|---|
| 연결 | **EC2 한 대** (같은 AZ) | 여러 EC2·Pod 동시 (여러 AZ) | API(HTTP)로 어디서든 |
| 용량 | 지정 (GB~TB) | 자동 확장 | **사실상 무제한** |
| 성능 | 매우 빠름 (저지연) | 중간 | 처리량 높음, 지연은 큼 |
| 가격 | 중간 | 비쌈 | **저렴** |
| 용도 | OS 디스크, DB | 공유 파일 | **업로드 파일, 정적 웹, 백업, 로그, 데이터 레이크** |

## 2. EBS (Elastic Block Store)

- EC2에 네트워크로 연결되는 블록 스토리지, **하나의 AZ**에 속함
- 볼륨 유형: **gp3**(범용 SSD, 기본 권장, IOPS·처리량을 따로 지정), io2(고성능 DB), st1/sc1(HDD)
- **스냅샷**: S3에 증분 백업, 다른 AZ·리전으로 복사해 복원
- 인스턴스 스토어: EC2에 물리적으로 붙은 로컬 디스크 → 매우 빠르지만 **중지하면 데이터 삭제**

## 3. S3 (Simple Storage Service)

### 기본 개념
```
s3://my-bucket/uploads/2026/11/profile-42.png
     └─버킷─┘ └──────────── 키(Key) ───────────┘
```
- **버킷**: 최상위 컨테이너, 이름은 **전 세계에서 유일**
- **객체**: 파일 + 메타데이터, 최대 5TB
- 폴더처럼 보이지만 실제로는 **키 이름에 `/`가 들어간 것**(평면 구조)
- 내구성 99.999999999% (11 nines) — 여러 AZ에 복제 저장

### 스토리지 클래스
| 클래스 | 용도 |
|---|---|
| **Standard** | 자주 접근 |
| **Intelligent-Tiering** | 접근 패턴을 모를 때 자동으로 계층 이동 |
| Standard-IA / One Zone-IA | 가끔 접근 (조회 시 비용) |
| **Glacier** (Instant / Flexible / Deep Archive) | 보관용, 매우 저렴, 복원에 시간 (Deep Archive는 수 시간) |

- **수명 주기 정책**: "30일 지나면 IA로, 1년 지나면 Glacier로, 3년 지나면 삭제" 자동화

### 보안
| 기능 | 설명 |
|---|---|
| **퍼블릭 액세스 차단** (Block Public Access) | 기본 활성화 — **끄지 마세요** (유출 사고 1순위) |
| 버킷 정책 / IAM 정책 | 누가 무엇을 할 수 있는지 |
| 기본 암호화 | 모든 새 객체 자동 암호화 (SSE-S3 기본, SSE-KMS 선택) |
| **버전 관리** | 덮어쓰기·삭제해도 이전 버전 복구 가능 |
| Object Lock | 삭제 금지(WORM), 랜섬웨어 대비 |

### Presigned URL: 파일 업로드·다운로드 패턴
**서버를 거치지 않고 클라이언트가 S3에 직접 업로드**하게 하는 임시 URL입니다.

```
1. 클라이언트 → 서버: "프로필 사진 올릴게요"
2. 서버: 권한 확인 후 5분짜리 Presigned PUT URL 발급 (서버의 IAM 권한으로 서명)
3. 클라이언트 → S3: 그 URL로 직접 PUT 업로드
4. 클라이언트 → 서버: "업로드 완료, 키는 uploads/42.png"
```
- 장점: 대용량 파일이 **서버 대역폭·메모리를 쓰지 않음**, 버킷은 비공개 유지

```java
// AWS SDK for Java v2
S3Presigner presigner = S3Presigner.create();
PutObjectRequest put = PutObjectRequest.builder()
        .bucket("my-bucket").key("uploads/42.png").contentType("image/png").build();
PresignedPutObjectRequest req = presigner.presignPutObject(b -> b
        .signatureDuration(Duration.ofMinutes(5))
        .putObjectRequest(put));
String url = req.url().toString();
```

### 그 밖의 활용
- **정적 웹 호스팅** (React 빌드) + CloudFront
- 이벤트 알림 → Lambda (업로드되면 썸네일 생성)
- 로그·백업 저장소, Athena로 S3 데이터를 SQL 조회

## 4. RDS (Relational Database Service)

**관리형 관계형 DB**: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, **Aurora**

### AWS가 해 주는 것
- 설치, 패치, **자동 백업**(특정 시점 복구, PITR), 모니터링, 장애 조치
- 사용자는 스키마, 쿼리, 인덱스, 파라미터 튜닝, 접근 제어 담당
- OS 접속(SSH)은 불가

### Multi-AZ vs 읽기 전용 복제본
```
Multi-AZ (고가용성)                        Read Replica (읽기 확장)
[앱] → [Primary (AZ-a)]                  [앱 쓰기] → [Primary]
          │ 동기 복제                                     │ 비동기 복제
          ↓                                ┌─────────────┼─────────────┐
       [Standby (AZ-c)]                [Replica 1]  [Replica 2]  [다른 리전 Replica]
       (평소 접근 불가)                    ↑ 앱 읽기 요청
장애 시 Standby가 자동 승격
(DNS 엔드포인트는 그대로, 보통 1~2분)
```

| 비교 | **Multi-AZ** | **Read Replica** |
|---|---|---|
| 목적 | **고가용성 (장애 조치)** | **읽기 성능 확장** |
| 복제 | **동기** | **비동기** (복제 지연 있음) |
| 대기 DB 사용 | 불가 (Standby, Multi-AZ DB 클러스터는 읽기 가능) | 읽기 가능 |
| 장애 시 | **자동 장애 조치** | 수동 승격 |

> 운영 DB는 **Multi-AZ 필수**. 읽기가 많으면 Read Replica 추가 + 애플리케이션에서 읽기/쓰기 라우팅 (CS 자료 `04.데이터베이스/08.레플리케이션과샤딩.md` 참고)

### Aurora
- AWS가 클라우드용으로 만든 MySQL·PostgreSQL 호환 DB
- 스토리지가 **3개 AZ에 6벌 복제**되고 자동 확장, 빠른 장애 조치, 최대 15개 복제본
- **Aurora Serverless v2**: 부하에 따라 용량 자동 조절

### 연결 관리
- 비밀번호는 **Secrets Manager**에 저장하고 자동 교체
- Lambda처럼 연결이 폭증하는 환경은 **RDS Proxy**로 커넥션 풀링

## 5. 그 밖의 데이터 서비스

| 서비스 | 유형 | 용도 |
|---|---|---|
| **ElastiCache** (Redis / Valkey / Memcached) | 인메모리 캐시 | 캐시, 세션, 랭킹, 분산 락 |
| **DynamoDB** | 서버리스 키-값 NoSQL | 대규모·일정한 저지연(한 자릿수 ms), 장바구니, 세션, IoT |
| DocumentDB | MongoDB 호환 문서 DB | |
| OpenSearch | 검색·로그 분석 | 전문 검색, 로그 |
| Neptune | 그래프 DB | 추천, 관계 분석 |
| Redshift | 데이터 웨어하우스 | 대규모 분석(OLAP) |

### 선택 가이드
| 상황 | 선택 |
|---|---|
| 일반적인 서비스, 트랜잭션·JOIN 필요 | **RDS (MySQL/PostgreSQL) / Aurora** |
| 자주 읽는 데이터, 세션 | **ElastiCache** |
| 접근 패턴이 단순하고 규모가 매우 큼 | DynamoDB |
| 파일 | **S3** |
| 검색 | OpenSearch |

## 6. 면접 질문

1. **EBS, EFS, S3의 차이는?**
   → EBS는 한 EC2에 붙는 블록 스토리지, EFS는 여러 서버가 동시에 마운트하는 공유 파일 스토리지, S3는 HTTP API로 접근하는 무제한 객체 스토리지입니다.
2. **파일 업로드를 Presigned URL로 처리하는 이유는?**
   → 클라이언트가 S3에 직접 업로드해 서버의 대역폭과 메모리 부담을 없애고, 버킷을 비공개로 유지하면서 제한된 시간 동안만 권한을 주기 위해서입니다.
3. **RDS Multi-AZ와 Read Replica의 차이는?**
   → Multi-AZ는 다른 AZ에 동기 복제한 대기 DB로 장애 시 자동 전환하는 고가용성 기능이고, Read Replica는 비동기 복제로 읽기 요청을 분산하는 확장 기능입니다.

## 핵심 정리
- 블록(EBS, 단일 AZ) / 파일(EFS, 공유) / 객체(S3, 무제한·저렴)
- S3: 퍼블릭 차단 유지, 버전 관리, 수명 주기, **Presigned URL로 직접 업로드**
- RDS: 관리형, Multi-AZ(동기·자동 장애 조치) vs Read Replica(비동기·읽기 확장), Aurora
- 캐시 ElastiCache, 대규모 키-값 DynamoDB
