# 05. IAM과 보안

> **학습 목표**
> - IAM 사용자, 그룹, 역할, 정책의 관계를 설명할 수 있다.
> - IAM 정책 JSON을 읽고 최소 권한 정책을 작성할 수 있다.
> - 역할(Role)과 임시 자격 증명이 Access Key보다 안전한 이유를 설명할 수 있다.
> - KMS, Secrets Manager, WAF, CloudTrail 등 보안 서비스의 용도를 설명할 수 있다.

---

## 1. IAM (Identity and Access Management)

**"누가(인증) 무엇을 할 수 있는가(인가)"** 를 관리합니다. 글로벌 서비스이며 무료입니다.

| 개념 | 설명 | 예 |
|---|---|---|
| **루트 사용자** | 계정 생성 시 이메일 계정, **모든 권한** | 일상 사용 금지, **MFA 필수** |
| **IAM 사용자** | 사람(또는 앱)용 장기 자격 증명 (비밀번호, Access Key) | 개발자 계정 |
| **그룹** | 사용자 묶음, 그룹에 정책 부여 | Developers, Admins |
| **역할 (Role)** | 누군가가 **잠시 맡아서(Assume) 쓰는** 권한. **임시 자격 증명** 발급 | EC2 역할, Lambda 역할, CI 배포 역할, 다른 계정 접근 |
| **정책 (Policy)** | 권한을 정의한 **JSON 문서** | S3 읽기 허용 |

```
[사용자] ─ 소속 ─> [그룹] ─ 연결 ─> [정책]
[EC2 / Lambda / GitHub Actions] ─ Assume ─> [역할] ─ 연결 ─> [정책]
```

> 사람도 IAM 사용자 대신 **IAM Identity Center(SSO)** 로 로그인해 역할을 맡는 방식이 권장됩니다.

## 2. 정책 (Policy)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadUploads",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::my-app-bucket/uploads/*"
    },
    {
      "Sid": "DenyDeleteBucket",
      "Effect": "Deny",
      "Action": "s3:DeleteBucket",
      "Resource": "*"
    }
  ]
}
```

| 요소 | 의미 |
|---|---|
| `Effect` | `Allow` 또는 `Deny` |
| `Action` | 허용·거부할 API (`서비스:동작`, `s3:GetObject`, `ec2:*`) |
| `Resource` | 대상 리소스 **ARN** |
| `Condition` | 조건 (IP, MFA 여부, 태그, 시간) |
| `Principal` | (리소스 기반 정책에서) **누구에게** |

### ARN (Amazon Resource Name)
```
arn:aws:s3:::my-bucket/uploads/*
arn:aws:iam::123456789012:role/github-actions-deploy
arn:aws:rds:ap-northeast-2:123456789012:db:prod-db
    │   │    │              │            └── 리소스
    │   │    │              └── 계정 ID
    │   │    └── 리전
    │   └── 서비스
    └── 파티션
```

### 권한 평가 규칙
```
1. 기본은 모두 거부 (Implicit Deny)
2. Allow가 있으면 허용
3. 명시적 Deny가 하나라도 있으면 무조건 거부 (Deny > Allow)
```

### 정책 종류
| 종류 | 붙는 곳 | 예 |
|---|---|---|
| **자격 증명 기반 정책** | 사용자·그룹·역할 | "이 역할은 S3를 읽을 수 있다" |
| **리소스 기반 정책** | 리소스 자체 | S3 버킷 정책, SQS 정책 ("이 버킷은 저 역할만 접근 가능") |
| **신뢰 정책** | 역할 | "**누가 이 역할을 맡을 수 있는가**" (EC2 서비스, 특정 GitHub 저장소) |
| 권한 경계, SCP | 사용자·역할 / 조직 | 최대 권한 제한 |
| AWS 관리형 / 고객 관리형 | | `AmazonS3ReadOnlyAccess` / 직접 작성 |

## 3. 역할과 임시 자격 증명

| Access Key (장기) | 역할 (임시) |
|---|---|
| 만료 없음 → **유출 시 계속 악용** | 보통 1시간 내 만료, 자동 갱신 |
| 코드·설정 파일·Git에 실수로 노출 | 저장할 키가 없음 |
| 주기적 교체 필요 | 교체 불필요 |

### 역할을 쓰는 곳
| 주체 | 방법 |
|---|---|
| EC2 | **인스턴스 프로파일** |
| ECS 태스크 | **태스크 역할** (앱용) / 태스크 실행 역할 (이미지 pull·로그용) |
| **EKS Pod** | **Pod Identity** 또는 IRSA (Pod별로 다른 역할) |
| Lambda | 실행 역할 |
| GitHub Actions | **OIDC** → `AssumeRoleWithWebIdentity` |
| 다른 AWS 계정 | 교차 계정 역할 |

> AWS SDK는 **자격 증명 공급자 체인**으로 환경 변수 → 설정 파일 → 컨테이너·인스턴스 역할 순으로 자동 탐색합니다. 코드에 키를 넣을 필요가 없습니다.

## 4. 최소 권한 원칙 (Least Privilege)

**필요한 작업에 필요한 리소스만 허용**합니다.

```
❌ "Action": "*", "Resource": "*"                         // 관리자 권한
❌ "Action": "s3:*", "Resource": "*"                      // 모든 버킷의 모든 작업
✅ "Action": ["s3:GetObject", "s3:PutObject"],
   "Resource": "arn:aws:s3:::my-app-bucket/uploads/*"    // 이 버킷의 이 경로, 읽기·쓰기만
```

도구:
- **IAM Access Analyzer**: 실제 사용 기록을 바탕으로 최소 권한 정책 생성, 외부 공개 리소스 탐지
- 마지막 사용 시각(Last accessed) 확인 → 안 쓰는 권한 제거

### 계정 보안 기본 체크리스트
- [ ] 루트 계정 **MFA**, 루트 Access Key 생성 금지
- [ ] 사람은 SSO/IAM 사용자 + MFA, 애플리케이션은 **역할**
- [ ] Access Key가 꼭 필요하면 최소 권한 + 주기적 교체
- [ ] **CloudTrail** 활성화 (모든 API 호출 기록)
- [ ] **Budgets 알람**
- [ ] S3 퍼블릭 액세스 차단 계정 수준 설정
- [ ] 여러 계정은 **AWS Organizations**로 관리 (dev / prod 계정 분리)

> **Access Key를 GitHub에 올리면** 봇이 수 분 안에 찾아 채굴용 인스턴스를 대량으로 띄웁니다. 실수로 올렸다면 커밋 삭제가 아니라 **즉시 키 비활성화·삭제**가 먼저입니다.

## 5. 데이터 보호 서비스

| 서비스 | 용도 |
|---|---|
| **KMS** (Key Management Service) | 암호화 키 생성·관리. S3, EBS, RDS 암호화에 사용 (봉투 암호화) |
| **Secrets Manager** | DB 비밀번호, API 키 저장 + **자동 교체**(RDS 연동) |
| **Systems Manager Parameter Store** | 설정값·비밀 저장 (일반 파라미터는 무료) |
| **ACM** (Certificate Manager) | SSL/TLS 인증서 무료 발급·자동 갱신 (ALB, CloudFront용) |

```java
// Spring Boot: Spring Cloud AWS로 Secrets Manager·Parameter Store 값을 설정으로 가져오기
// application.yml
// spring.config.import: aws-secretsmanager:prod/myapp/db
```

### 암호화 두 가지
| 구분 | 의미 | 방법 |
|---|---|---|
| **저장 시 암호화** (at rest) | 디스크·스토리지에 저장된 데이터 | KMS (S3, EBS, RDS 암호화 옵션) |
| **전송 중 암호화** (in transit) | 네트워크로 이동하는 데이터 | TLS (HTTPS, DB SSL 연결) |

## 6. 위협 방어와 감사

| 서비스 | 용도 |
|---|---|
| **WAF** | 웹 방화벽: SQL Injection, XSS, 봇, **IP별 요청 수 제한** (ALB, CloudFront, API Gateway에 연결) |
| **Shield** | DDoS 방어 (Standard는 기본 무료, Advanced는 유료) |
| **CloudTrail** | **누가 언제 어떤 API를 호출했는지** 감사 로그 ("누가 보안 그룹을 열었지?") |
| **GuardDuty** | 로그를 분석해 위협 탐지 (비정상 API 호출, 악성 IP 통신, 채굴) |
| AWS Config | 리소스 설정 변경 이력과 규칙 준수 평가 ("암호화 안 된 EBS가 있는가") |
| Security Hub | 보안 상태 통합 대시보드 |
| Inspector | EC2·ECR 이미지·Lambda 취약점 스캔 |

## 7. 면접 질문

1. **IAM 사용자와 역할의 차이는?**
   → 사용자는 장기 자격 증명을 가진 고정된 주체이고, 역할은 신뢰 정책에 허용된 주체가 잠시 맡아 임시 자격 증명을 받는 권한 묶음입니다.
2. **EC2나 컨테이너에서 Access Key 대신 역할을 쓰는 이유는?**
   → 키를 저장할 필요가 없고, 자동 갱신되는 짧은 수명의 자격 증명을 써서 유출 위험과 관리 부담을 줄일 수 있기 때문입니다.
3. **IAM 정책 평가에서 Allow와 Deny가 충돌하면?**
   → 기본은 거부이고, Allow가 있으면 허용되지만, 명시적 Deny가 하나라도 있으면 항상 거부됩니다.
4. **최소 권한 원칙이란?**
   → 주체에게 작업 수행에 필요한 최소한의 동작과 리소스만 허용해, 자격 증명이 유출되거나 실수가 있어도 피해 범위를 줄이는 원칙입니다.

---

## 핵심 정리
- IAM: 사용자 / 그룹 / **역할(임시)** / 정책(JSON: Effect, Action, Resource, Condition)
- 평가: 기본 거부 → Allow → **명시적 Deny 우선**
- 앱은 역할: EC2 인스턴스 프로파일, ECS 태스크 역할, EKS Pod Identity, GitHub OIDC
- 최소 권한, 루트 MFA, CloudTrail, Access Key 유출 시 즉시 비활성화
- KMS(키), Secrets Manager(비밀·자동 교체), ACM(인증서), WAF·GuardDuty(방어)
