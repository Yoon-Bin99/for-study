# 06. AWS 컨테이너 서비스: ECR, ECS, Fargate, EKS

> **학습 목표**
> - ECR에 이미지를 푸시하고 수명 주기 정책을 설정할 수 있다.
> - ECS의 클러스터, 태스크 정의, 서비스 개념을 설명할 수 있다.
> - EC2 시작 유형과 Fargate의 차이를 설명할 수 있다.
> - EKS의 구성(노드 그룹, Fargate, Karpenter, 애드온, 접근 제어)을 설명할 수 있다.
> - ECS와 EKS 중 상황에 맞는 선택을 할 수 있다.

---

## 1. 전체 그림

```
[개발자 / CI]
    │ docker push
    ↓
[ECR: 이미지 저장소]
    │ pull
    ├──────────────> [ECS: AWS 고유 오케스트레이터]  ─┐
    │                                              ├─ 실행 위치: [EC2 인스턴스] or [Fargate(서버리스)]
    └──────────────> [EKS: 관리형 쿠버네티스]      ─┘
```

---

## 2. ECR (Elastic Container Registry)

AWS의 **프라이빗 도커 이미지 저장소**입니다.

```bash
# 저장소 생성
aws ecr create-repository --repository-name myapp --image-scanning-configuration scanOnPush=true

# 로그인 → 태그 → 푸시
aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com
docker tag myapp:a1b2c3d 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:a1b2c3d
docker push 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:a1b2c3d
```

| 기능 | 설명 |
|---|---|
| IAM 기반 권한 | 푸시는 CI 역할, pull은 ECS 실행 역할·EKS 노드 역할에만 |
| **이미지 스캔** | 푸시 시 취약점(CVE) 검사 |
| **태그 불변성 (Immutable tags)** | 같은 태그 덮어쓰기 금지 → 추적·롤백 신뢰성 |
| **수명 주기 정책** | "태그 없는 이미지 7일 후 삭제", "최근 30개만 유지" → 저장 비용 절감 |
| 교차 리전·계정 복제 | DR, 멀티 계정 |

## 3. ECS (Elastic Container Service)

**AWS가 만든 컨테이너 오케스트레이터**입니다. 쿠버네티스보다 개념이 적고 AWS 서비스와 통합이 깊습니다.

### 구성 요소
```
[클러스터]  ← 논리적 묶음
   └── [서비스: myapp-service]  "태스크 3개를 항상 유지, ALB에 연결, 롤링 배포"
          ├── [태스크] ← 태스크 정의(설계도) v5로 실행된 컨테이너 묶음
          ├── [태스크]
          └── [태스크]
```

| ECS 개념 | 쿠버네티스 대응 | 설명 |
|---|---|---|
| **태스크 정의 (Task Definition)** | Pod 템플릿 | 이미지, CPU·메모리, 포트, 환경 변수, 비밀, 로그, IAM 역할 (리비전으로 버전 관리) |
| **태스크 (Task)** | Pod | 태스크 정의로 실행된 컨테이너 묶음 |
| **서비스 (Service)** | Deployment + Service | 원하는 태스크 수 유지, LB 연결, 배포, 오토스케일링 |
| 클러스터 | 클러스터 | |

### 태스크 정의 예 (일부)
```json
{
  "family": "myapp",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "512",
  "memory": "1024",
  "executionRoleArn": "arn:aws:iam::123456789012:role/ecsTaskExecutionRole",
  "taskRoleArn": "arn:aws:iam::123456789012:role/myapp-task-role",
  "containerDefinitions": [
    {
      "name": "app",
      "image": "123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:a1b2c3d",
      "portMappings": [{ "containerPort": 8080 }],
      "environment": [{ "name": "SPRING_PROFILES_ACTIVE", "value": "prod" }],
      "secrets": [
        { "name": "SPRING_DATASOURCE_PASSWORD",
          "valueFrom": "arn:aws:secretsmanager:ap-northeast-2:123456789012:secret:prod/db-AbCdEf" }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/myapp",
          "awslogs-region": "ap-northeast-2",
          "awslogs-stream-prefix": "app"
        }
      }
    }
  ]
}
```

| 역할 | 누가 쓰나 | 권한 |
|---|---|---|
| **태스크 실행 역할** | ECS 에이전트 | ECR 이미지 pull, CloudWatch 로그 쓰기, Secrets 읽기 |
| **태스크 역할** | **애플리케이션 코드** | S3, SQS 등 앱이 쓰는 AWS 서비스 |

### 시작 유형 (실행 위치)
| 비교 | EC2 시작 유형 | **Fargate** |
|---|---|---|
| 서버 관리 | EC2 인스턴스(ASG)를 **직접 관리** (패치, 용량) | **서버 없음** — 태스크 단위로 CPU·메모리만 지정 |
| 과금 | EC2 인스턴스 시간 | 태스크의 vCPU·메모리 × 실행 시간 |
| 비용 | 꽉 채워 쓰면 저렴 | 단가는 비싸지만 관리·유휴 비용 없음 |
| 제약 | 자유도 높음 (GPU, 특수 설정) | GPU 등 일부 제한 |
| 적합 | 대규모·고밀도, 특수 요구 | **대부분의 웹·API, 소규모 팀** |

> 용량 공급자(Capacity Provider)로 **Fargate Spot**을 섞으면 비용을 크게 줄일 수 있습니다.

### ECS 서비스 배포
- 롤링 업데이트(최소 정상 % / 최대 %), **배포 서킷 브레이커**(실패 시 자동 롤백)
- 블루/그린(네이티브 또는 CodeDeploy) (→ `05.CICD/03.AWS개발자도구.md`)
- 서비스 오토스케일링: CPU·메모리·ALB 요청 수 대상 추적
- 서비스 간 통신: **Service Connect**(서비스 이름으로 호출) 또는 Cloud Map

## 4. EKS (Elastic Kubernetes Service)

**AWS 관리형 쿠버네티스**입니다. 컨트롤 플레인(API 서버, etcd)을 AWS가 여러 AZ에 운영합니다.

```
+─── EKS 컨트롤 플레인 (AWS 관리, 클러스터당 시간 요금) ───+
|   kube-apiserver, etcd, scheduler, controller          |
+────────────────────────────────────────────────────────+
               │
+──── 고객 VPC ────────────────────────────────────────────+
|  데이터 플레인 (워커):                                       |
|   - 관리형 노드 그룹 (EC2 ASG, AWS가 생성·업데이트 지원)       |
|   - Karpenter (Pending Pod에 맞는 EC2를 직접 프로비저닝)     |
|   - Fargate 프로파일 (Pod 단위 서버리스)                     |
|   - EKS Auto Mode (노드·주요 애드온까지 AWS가 관리)          |
+─────────────────────────────────────────────────────────+
```

### 데이터 플레인 선택
| 옵션 | 설명 |
|---|---|
| 관리형 노드 그룹 | EC2 노드를 ASG로, 버전 업그레이드·교체를 AWS가 도움 |
| **Karpenter** | 노드 그룹 없이 Pod 요구에 맞는 인스턴스 자동 선택, 스팟·통합에 강함 |
| Fargate | 노드 관리 없음, DaemonSet 불가 등 제약 |
| **EKS Auto Mode** | 노드 프로비저닝·스케일링·주요 애드온(로드밸런서 컨트롤러, 스토리지 드라이버 등)까지 AWS가 운영 |

### 꼭 알아야 할 애드온·컨트롤러
| 구성 요소 | 역할 |
|---|---|
| **VPC CNI** | Pod에 **VPC의 실제 IP**를 할당 → Pod가 VPC 리소스와 직접 통신 (대신 서브넷 IP 소모 주의) |
| CoreDNS | 클러스터 DNS |
| kube-proxy | Service 네트워킹 |
| **AWS Load Balancer Controller** | Ingress → **ALB**, Service(LoadBalancer) → **NLB** 생성 |
| **EBS CSI Driver** | PVC → EBS 볼륨 생성 |
| Metrics Server | HPA용 지표 |
| External Secrets / Secrets Store CSI | Secrets Manager 연동 |

### 접근 제어: 두 가지 방향
| 방향 | 방법 |
|---|---|
| **사람·CI → 클러스터** (kubectl 권한) | IAM 주체를 **EKS 액세스 항목(Access Entry)** 에 등록하고 액세스 정책 연결 (예전 방식: `aws-auth` ConfigMap) |
| **Pod → AWS 서비스** (S3, SQS 등) | **EKS Pod Identity** 또는 **IRSA**(서비스 어카운트에 IAM 역할 연결) — 노드 역할을 모든 Pod가 공유하지 않게 |

```bash
aws eks update-kubeconfig --name my-cluster --region ap-northeast-2
kubectl get nodes
```

### 운영 시 고려 사항
- 쿠버네티스 **버전 지원 기간**이 정해져 있어 정기적인 클러스터 업그레이드 필요 (표준 지원 이후 연장 지원은 추가 요금)
- 서브넷 IP 부족(VPC CNI) → 서브넷을 넉넉하게 설계
- 관측성: CloudWatch Container Insights, Prometheus(AMP) + Grafana

## 5. ECS vs EKS

| 비교 | ECS | EKS |
|---|---|---|
| 학습 곡선 | **낮음** | 높음 (쿠버네티스 생태계 전체) |
| 컨트롤 플레인 비용 | 무료 | 클러스터당 시간 요금 |
| 이식성 | AWS 전용 | **표준 쿠버네티스** → 멀티 클라우드·온프레미스 |
| 생태계 | AWS 서비스 통합 | **Helm, Argo CD, Istio, KEDA 등 오픈소스** |
| 운영 부담 | 적음 | 큼 (업그레이드, 애드온) |
| 적합 | 소규모 팀, AWS 올인, 빠른 시작 | 대규모 MSA, 쿠버네티스 역량 보유, 이식성 필요 |

> 그 밖에 **App Runner**(소스나 이미지만 주면 HTTPS 엔드포인트까지 자동)처럼 더 단순한 선택지도 있습니다. 팀 규모와 운영 역량에 맞춰 고르세요.

## 6. 면접 질문

1. **ECS의 태스크 정의, 태스크, 서비스의 차이는?**
   → 태스크 정의는 컨테이너 실행 설계도, 태스크는 그것으로 실행된 인스턴스, 서비스는 원하는 태스크 수를 유지하고 로드밸런서 연결·배포·스케일링을 관리하는 단위입니다.
2. **Fargate의 장단점은?**
   → 서버를 관리하지 않고 태스크 단위 자원만 지정해 운영 부담이 적지만, 단가가 높고 GPU 등 일부 기능에 제약이 있습니다.
3. **EKS에서 Pod가 S3에 접근하려면?**
   → EKS Pod Identity나 IRSA로 서비스 어카운트에 IAM 역할을 연결해 Pod별로 최소 권한의 임시 자격 증명을 쓰게 합니다.
4. **ECS와 EKS 중 무엇을 선택하겠습니까?**
   → AWS 중심의 소규모 팀이 빠르게 운영하려면 ECS(Fargate), 쿠버네티스 생태계와 이식성이 필요하고 운영 역량이 있다면 EKS를 선택합니다.

## 핵심 정리
- ECR: 프라이빗 레지스트리, 스캔, 태그 불변성, 수명 주기 정책
- ECS: 태스크 정의(설계도) → 태스크(실행) → 서비스(유지·LB·배포), 실행 역할 vs 태스크 역할
- 실행 위치: EC2(직접 관리) vs **Fargate(서버리스)**
- EKS: 관리형 컨트롤 플레인 + 노드 그룹/Karpenter/Fargate/Auto Mode, LB Controller, Access Entry, Pod Identity
- ECS(단순·AWS 통합) vs EKS(표준·생태계·운영 부담)
