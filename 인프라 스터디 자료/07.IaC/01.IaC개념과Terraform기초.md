# 01. IaC 개념과 Terraform 기초

> **학습 목표**
> - IaC가 필요한 이유와 선언형·명령형, 가변·불변 인프라를 설명할 수 있다.
> - IaC 도구(Terraform, CloudFormation, CDK, Ansible)를 비교할 수 있다.
> - Terraform의 기본 문법(provider, resource, variable, output, data)을 사용할 수 있다.
> - `init → plan → apply` 워크플로와 상태 파일의 역할을 설명할 수 있다.

---

## 1. IaC (Infrastructure as Code)란?

**인프라(서버, 네트워크, DB)를 콘솔 클릭이 아니라 코드로 정의하고 관리**하는 것입니다.

### 콘솔 클릭의 문제
| 문제 | 예 |
|---|---|
| 재현 불가 | "운영 환경이랑 똑같이 스테이징 만들어 주세요" → 기억에 의존 |
| 이력 없음 | 누가 언제 보안 그룹을 바꿨는지 모름 |
| 실수 | 수십 번 클릭 중 하나 빠뜨림 |
| 리뷰 불가 | 변경 전에 검토할 방법 없음 |
| 설정 표류 (Drift) | 환경마다 조금씩 달라짐 |

### IaC의 장점
- **버전 관리**(Git): 변경 이력, 롤백, PR 리뷰
- **재현성**: 같은 코드로 dev / stg / prod를 똑같이
- **자동화**: CI/CD로 인프라 변경 배포
- **문서화**: 코드 자체가 인프라 명세서

## 2. 핵심 개념

### 선언형 vs 명령형
| 방식 | 설명 | 예 |
|---|---|---|
| **선언형** | **원하는 최종 상태**를 기술, 도구가 차이를 계산해 적용 | Terraform, CloudFormation, 쿠버네티스 YAML |
| 명령형 | **실행할 절차**를 순서대로 기술 | 쉘 스크립트, AWS CLI, (Ansible은 절차형에 가까움) |

```
선언형: "EC2가 3대 있어야 한다"   → 지금 2대면 1대 추가, 4대면 1대 삭제
명령형: "EC2를 1대 만들어라"      → 실행할 때마다 1대씩 늘어남
```

### 멱등성 (Idempotency)
같은 코드를 **여러 번 적용해도 결과가 같아야** 합니다. 선언형 도구의 핵심 성질입니다.

### 가변 인프라 vs 불변 인프라
| 방식 | 설명 |
|---|---|
| 가변 (Mutable) | 서버에 접속해 패키지 업데이트·설정 변경 → 서버마다 상태가 달라짐("눈송이 서버") |
| **불변 (Immutable)** | 변경이 필요하면 **새로 만들고 교체** (새 AMI, 새 컨테이너 이미지) → 항상 같은 상태 |

> "애완동물(Pets) vs 가축(Cattle)": 서버에 이름을 붙이고 아프면 치료하는 대신, 번호를 붙이고 문제가 있으면 교체합니다.

## 3. IaC 도구 비교

| 도구 | 방식 | 대상 | 특징 |
|---|---|---|---|
| **Terraform** (HashiCorp) | 선언형, **HCL** 언어 | **멀티 클라우드** (AWS, GCP, Azure, GitHub, Datadog...) | 사실상 표준, 상태 파일로 관리, BSL 라이선스 |
| OpenTofu | Terraform과 호환 | 멀티 클라우드 | Terraform 라이선스 변경 후 등장한 오픈소스 포크 (Linux Foundation) |
| **CloudFormation** | 선언형, YAML/JSON | AWS 전용 | AWS가 상태 관리, 추가 비용 없음 |
| **AWS CDK** | TypeScript, Java, Python 등 **프로그래밍 언어** → CloudFormation 생성 | AWS 전용 | 반복문·클래스 등 언어 기능 활용 |
| Pulumi | 프로그래밍 언어 | 멀티 클라우드 | |
| **Ansible** | 절차형(YAML 플레이북), 에이전트 없음(SSH) | **서버 설정 관리** | 프로비저닝보다 **구성 관리**(패키지 설치, 설정 파일 배포)에 강함 |

| 역할 구분 | 도구 |
|---|---|
| **프로비저닝** (인프라 생성: VPC, EC2, RDS) | Terraform, CloudFormation, CDK |
| **구성 관리** (서버 안 설정: 패키지, 파일) | Ansible, Chef, Puppet |
| 이미지 빌드 | Packer, Dockerfile |

> 컨테이너와 관리형 서비스를 쓰면 서버 안을 설정할 일이 줄어들어, 요즘은 **Terraform(인프라) + Dockerfile(앱 환경) + 쿠버네티스 YAML/Helm(배포)** 조합이 흔합니다.

## 4. Terraform 동작 원리

```
[.tf 코드 (원하는 상태)]
         │
         ├── terraform plan ──> 비교 ──> [상태 파일 terraform.tfstate (Terraform이 아는 현재 상태)]
         │                        │
         │                        └──> [실제 클라우드 (API로 조회)]
         ↓
   실행 계획: + 생성 / ~ 변경 / - 삭제 / -/+ 교체
         │
   terraform apply ──> Provider(AWS 플러그인)가 AWS API 호출 ──> 상태 파일 갱신
```

## 5. 기본 문법 (HCL)

### 프로젝트 구조
```
infra/
├── versions.tf     # Terraform·provider 버전
├── provider.tf     # provider 설정
├── variables.tf    # 입력 변수
├── main.tf         # 리소스
├── outputs.tf      # 출력값
└── terraform.tfvars  # 변수 값 (비밀은 넣지 않기)
```

### versions.tf / provider.tf
```hcl
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"     # 6.x 범위 (작성 시점 예시, 최신 메이저 버전 확인)
    }
  }
}

provider "aws" {
  region = var.region

  default_tags {                 # 모든 리소스에 공통 태그
    tags = {
      Project   = "myapp"
      ManagedBy = "terraform"
    }
  }
}
```

### variables.tf
```hcl
variable "region" {
  description = "AWS 리전"
  type        = string
  default     = "ap-northeast-2"
}

variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "stg", "prod"], var.env)
    error_message = "env는 dev, stg, prod 중 하나여야 합니다."
  }
}

variable "db_password" {
  type      = string
  sensitive = true          # plan/apply 출력에서 가림
}
```

### main.tf: 리소스와 참조
```hcl
# 형식: resource "<타입>" "<이름>" { ... }
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "${var.env}-vpc" }
}

resource "aws_subnet" "public_a" {
  vpc_id                  = aws_vpc.main.id        # ★ 다른 리소스 참조 → 의존성 자동 파악
  cidr_block              = "10.0.1.0/24"
  availability_zone       = "${var.region}a"
  map_public_ip_on_launch = true
  tags = { Name = "${var.env}-public-a" }
}

resource "aws_security_group" "app" {
  name   = "${var.env}-app-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]   # ALB 보안 그룹에서만
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

# data: 이미 존재하는 것을 조회 (만들지 않음)
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}
```

### outputs.tf
```hcl
output "vpc_id" {
  value = aws_vpc.main.id
}
```

### 자주 쓰는 표현
| 문법 | 예 | 의미 |
|---|---|---|
| 참조 | `aws_vpc.main.id` | 리소스 속성 |
| 문자열 보간 | `"${var.env}-vpc"` | |
| `count` | `count = 3` → `aws_instance.web[0]` | 같은 리소스 여러 개 |
| `for_each` | `for_each = toset(["a", "c"])` → `each.key` | 키 기반 여러 개 (권장) |
| 조건식 | `var.env == "prod" ? 3 : 1` | |
| `locals` | `locals { name = "${var.env}-app" }` → `local.name` | 내부 계산값 |
| `depends_on` | 명시적 의존성 | 참조로 알 수 없을 때만 |
| `lifecycle` | `prevent_destroy = true` | **실수로 삭제 방지** (운영 DB) |

## 6. 워크플로

```bash
terraform init        # provider 다운로드, 백엔드(상태 저장소) 초기화
terraform fmt         # 코드 포맷팅
terraform validate    # 문법 검사
terraform plan        # ★ 무엇이 바뀌는지 미리 보기 (반드시 확인!)
terraform apply       # 적용 (확인 후 yes)
terraform destroy     # 전부 삭제 (실습 후 과금 방지)

terraform state list  # 관리 중인 리소스 목록
terraform output      # 출력값
terraform import aws_s3_bucket.logs my-existing-bucket   # 기존 리소스를 관리 대상으로 (또는 import 블록)
```

### plan 결과 읽기
```
  # aws_instance.web must be replaced
-/+ resource "aws_instance" "web" {
      ~ ami = "ami-old" -> "ami-new" # forces replacement
    }
Plan: 1 to add, 0 to change, 1 to destroy.
```
| 기호 | 의미 |
|---|---|
| `+` | 생성 |
| `~` | 변경 (그 자리에서 수정) |
| `-` | **삭제** |
| `-/+` | **삭제 후 재생성 (교체)** — DB라면 데이터 유실! |

> **`plan`에서 `destroy`나 `-/+`가 보이면 반드시 이유를 확인**하세요. 이름 하나 바꿨는데 운영 DB가 교체되는 사고가 흔합니다.

## 7. 상태 파일 (State)

`terraform.tfstate`는 **코드의 리소스와 실제 클라우드 리소스 ID의 매핑**을 저장합니다.

| 주의 | 이유 |
|---|---|
| **Git에 올리지 않기** | DB 비밀번호 등 **민감 정보가 평문**으로 들어 있음 |
| **원격 백엔드에 저장** | 팀원 모두 같은 상태를 봐야 함 (로컬 파일이면 각자 다름) |
| **잠금 (Locking)** | 두 사람이 동시에 apply하면 상태 손상 |
| 직접 수정 금지 | `terraform state mv/rm` 명령 사용 |

→ 원격 백엔드와 팀 운영은 → `02.Terraform실전.md`

## 8. 면접 질문

1. **IaC를 쓰는 이유는?**
   → 인프라를 코드로 버전 관리해 변경 이력·리뷰·롤백이 가능하고, 같은 환경을 반복해서 정확히 재현하며, 수작업 실수와 설정 표류를 줄이기 위해서입니다.
2. **선언형 IaC란?**
   → 실행 절차가 아니라 원하는 최종 상태를 정의하면 도구가 현재 상태와의 차이를 계산해 적용하는 방식으로, 여러 번 적용해도 결과가 같습니다(멱등성).
3. **Terraform 상태 파일의 역할과 주의점은?**
   → 코드의 리소스와 실제 리소스를 매핑해 변경 사항을 계산하는 데 쓰이며, 민감 정보가 들어 있어 Git에 올리지 않고 원격 백엔드에 잠금과 함께 저장해야 합니다.
4. **Terraform과 Ansible의 차이는?**
   → Terraform은 클라우드 리소스를 생성·관리하는 선언형 프로비저닝 도구이고, Ansible은 서버 안의 패키지·설정을 관리하는 구성 관리 도구입니다.

## 핵심 정리
- IaC = 인프라를 코드로 → 버전 관리, 재현성, 리뷰, 자동화
- 선언형 + 멱등성, 불변 인프라
- Terraform: provider / resource / data / variable / output / locals
- `init → plan(반드시 확인, -/+ 주의) → apply`, 실습 후 `destroy`
- 상태 파일: Git 금지, 원격 백엔드 + 잠금
