# 02. Terraform 실전: 원격 상태, 모듈, 환경 분리, CI

> **학습 목표**
> - S3 원격 백엔드와 상태 잠금을 설정할 수 있다.
> - 모듈로 코드를 재사용하고 공개 모듈을 활용할 수 있다.
> - 환경(dev/stg/prod)을 분리하는 방법을 비교할 수 있다.
> - Terraform을 PR 기반으로 운영하는 흐름을 설명할 수 있다.

---

## 1. 원격 백엔드 (S3)

```hcl
terraform {
  backend "s3" {
    bucket       = "mycompany-terraform-state"
    key          = "prod/network/terraform.tfstate"
    region       = "ap-northeast-2"
    encrypt      = true
    use_lockfile = true      # S3 자체 잠금 (Terraform 1.10+)
  }
}
```

- 상태 버킷은 **버전 관리 활성화**(실수 복구), 퍼블릭 차단, 암호화
- 잠금: Terraform 1.10부터 **S3 네이티브 잠금(`use_lockfile`)** 을 지원합니다. 이전에는 **DynamoDB 테이블**(`dynamodb_table`)로 잠금을 구현했고, DynamoDB 방식은 지원 중단 예정(deprecated)입니다.
- 상태 버킷 자체는 보통 별도로(콘솔·부트스트랩 코드로) 한 번 만들어 둡니다. (닭과 달걀 문제)

### 상태 분리 (Blast Radius 줄이기)
하나의 상태 파일에 모든 인프라를 넣으면:
- plan이 느려지고, 실수 하나가 **전체에 영향**
- 권한 분리가 어려움

```
state 분리 예
prod/network/   VPC, 서브넷, NAT        (거의 안 바뀜)
prod/data/      RDS, ElastiCache        (신중하게)
prod/app/       ECS/EKS, ALB, IAM       (자주 바뀜)
```
다른 상태의 값은 `terraform_remote_state` 데이터 소스나 SSM Parameter Store로 참조합니다.

## 2. 모듈 (Module)

**재사용 가능한 Terraform 코드 묶음**입니다. 함수처럼 입력(variables)을 받아 리소스를 만들고 출력(outputs)을 돌려줍니다.

```
modules/
└── web-service/
    ├── main.tf        # ALB 대상 그룹, ECS 서비스, 보안 그룹, 오토스케일링
    ├── variables.tf   # name, image, cpu, memory, desired_count ...
    └── outputs.tf
envs/
├── dev/main.tf
└── prod/main.tf
```

```hcl
# envs/prod/main.tf
module "member_api" {
  source        = "../../modules/web-service"
  name          = "member-api"
  image         = "123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/member:a1b2c3d"
  cpu           = 512
  memory        = 1024
  desired_count = 3
}

module "order_api" {
  source        = "../../modules/web-service"
  name          = "order-api"
  image         = "123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/order:b2c3d4e"
  desired_count = 2
}

output "member_api_url" {
  value = module.member_api.url
}
```

### 공개 모듈 활용
[Terraform Registry](https://registry.terraform.io)의 검증된 모듈을 쓰면 수백 줄을 몇 줄로 줄일 수 있습니다.
```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"            # 예시 버전, 레지스트리에서 최신 확인

  name = "prod-vpc"
  cidr = "10.0.0.0/16"
  azs             = ["ap-northeast-2a", "ap-northeast-2c"]
  public_subnets  = ["10.0.1.0/24", "10.0.2.0/24"]
  private_subnets = ["10.0.11.0/24", "10.0.12.0/24"]

  enable_nat_gateway = true
  single_nat_gateway = true     # 비용 절감 (운영은 AZ마다 하나가 고가용성)
}
```
> 모듈 `version`은 **반드시 고정**하세요. 버전이 바뀌면 의도치 않은 변경이 생길 수 있습니다.

## 3. 환경 분리 방법

| 방법 | 구조 | 장점 | 단점 |
|---|---|---|---|
| **디렉토리 분리** (권장) | `envs/dev`, `envs/prod` 각각 백엔드·변수 | 명확, 환경별 상태·권한 분리, prod 실수 위험 낮음 | 코드 중복 → 모듈로 해결 |
| Workspace | 같은 코드, `terraform workspace select prod` | 간단 | 현재 workspace를 착각하기 쉬움, 환경 차이 표현 어려움 |
| tfvars 파일 | `-var-file=prod.tfvars` | 간단 | 백엔드 분리 별도 처리 |
| Terragrunt | 래퍼 도구로 DRY 구성 | 대규모에 적합 | 도구 추가 학습 |

> AWS **계정 자체를 환경별로 분리**(dev 계정, prod 계정)하는 것이 가장 안전합니다. prod 계정에는 CI 역할만 apply 권한을 갖게 합니다.

## 4. 팀 운영: PR 기반 워크플로

```
1. 브랜치에서 .tf 수정 → PR 생성
2. CI: terraform fmt -check, validate, tflint, 보안 스캔(Checkov, Trivy)
3. CI: terraform plan → 결과를 PR 코멘트로 게시
4. 리뷰어가 plan 결과 확인 (특히 destroy / replace)
5. 승인 후 main 머지 → CI가 terraform apply (prod는 수동 승인 단계)
```
- 도구: GitHub Actions + `hashicorp/setup-terraform`, **Atlantis**, HCP Terraform(Terraform Cloud), Spacelift
- CI의 AWS 인증은 **OIDC 역할** (→ `05.CICD/02.GitHubActions.md`)
- **콘솔에서 직접 수정하지 않기** → 하면 Drift 발생, 다음 plan에서 되돌리려 함

### Drift 확인
```bash
terraform plan -refresh-only     # 실제 리소스가 코드와 달라진 부분 확인
```

## 5. 비밀 정보 다루기

| 방법 | 설명 |
|---|---|
| ❌ tfvars에 비밀번호 작성 후 Git 커밋 | 금지 |
| `sensitive = true` | 출력에서만 가림 (**상태 파일에는 평문 저장**) |
| 환경 변수 `TF_VAR_db_password` | CI Secret에서 주입 |
| **AWS에서 생성·관리** | RDS `manage_master_user_password = true` → 비밀번호를 Secrets Manager가 생성·교체, Terraform은 모름 |
| 임시 값(ephemeral) | Terraform 1.10+의 ephemeral 리소스·write-only 인자로 상태에 저장하지 않기 |

## 6. 자주 하는 실수

| 실수 | 결과 | 예방 |
|---|---|---|
| 리소스 이름(`resource "aws_db_instance" "main"`)을 바꿈 | 삭제 후 재생성 | `moved` 블록으로 이름 변경 알리기 |
| 교체를 유발하는 속성 변경 | DB·볼륨 교체 | plan 확인, `prevent_destroy` |
| 상태 파일 로컬 보관 | 팀원 간 상태 불일치, 유실 | 원격 백엔드 |
| provider·모듈 버전 미고정 | 어느 날 갑자기 다른 결과 | `~>` 버전 제약 + `.terraform.lock.hcl` 커밋 |
| 콘솔 수동 변경 | Drift | 모든 변경은 코드로 |

```hcl
moved {
  from = aws_db_instance.main
  to   = aws_db_instance.primary
}
```

> `.terraform/` 디렉토리와 `*.tfstate`는 `.gitignore`에, **`.terraform.lock.hcl`(provider 버전 잠금)은 커밋**합니다.

## 7. 면접 질문

1. **Terraform 상태를 원격으로 관리하는 이유는?**
   → 팀원이 같은 상태를 공유하고, 잠금으로 동시 적용에 의한 손상을 막으며, 민감 정보가 담긴 상태 파일을 암호화된 저장소에 안전하게 보관하기 위해서입니다.
2. **Terraform 모듈을 쓰는 이유는?**
   → 반복되는 리소스 구성을 재사용 가능한 단위로 묶어 중복을 줄이고, 환경 간 일관성을 높이기 위해서입니다.
3. **인프라 변경을 안전하게 배포하는 방법은?**
   → PR에서 plan 결과를 리뷰하고, 삭제·교체 여부를 확인한 뒤 승인 후 CI에서 apply하며, 콘솔 직접 수정을 금지해 Drift를 막습니다.

---

## 핵심 정리
- 원격 백엔드: S3 + 버전 관리 + 암호화 + 잠금(`use_lockfile`)
- 상태는 영역별로 분리해 영향 범위 축소
- 모듈 = 재사용 단위, 공개 모듈 활용 시 버전 고정
- 환경은 디렉토리(+ 계정) 분리, PR에서 plan 리뷰 → 머지 후 apply
- 비밀은 상태에 남지 않게, 이름 변경은 `moved`, 중요 리소스는 `prevent_destroy`
