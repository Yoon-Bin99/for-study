# 01. 관측 가능성 (Observability)

> **학습 목표**
> - 모니터링과 관측 가능성의 차이를 설명할 수 있다.
> - 관측 가능성의 세 축(메트릭, 로그, 트레이스)의 역할을 구분할 수 있다.
> - 골든 시그널, RED, USE 방법으로 무엇을 측정할지 정할 수 있다.
> - SLI, SLO, SLA와 에러 버짓을 설명할 수 있다.
> - 좋은 알람의 조건을 설명할 수 있다.

---

## 1. 모니터링 vs 관측 가능성

| 구분 | 모니터링 | 관측 가능성 |
|---|---|---|
| 질문 | "**무엇이** 잘못됐나?" (미리 정한 지표) | "**왜** 잘못됐나?" (예상 못 한 문제도 파고들 수 있는가) |
| 예 | CPU 90% 초과 알람 | 특정 사용자의 결제 요청이 어느 서비스의 어느 쿼리에서 느려졌는지 추적 |

시스템이 MSA·컨테이너로 복잡해지면 미리 정한 대시보드만으로는 원인을 찾기 어렵습니다. **외부 출력(데이터)만 보고 내부 상태를 추론할 수 있는 능력**이 관측 가능성입니다.

## 2. 세 가지 축 (Three Pillars)

| 축 | 형태 | 답하는 질문 | 예 | 도구 |
|---|---|---|---|---|
| **메트릭 (Metrics)** | **시간에 따른 숫자** (집계) | "**지금 상태가 어떤가?** 추세는?" | 초당 요청 수, 에러율, p99 응답 시간, CPU | **Prometheus**, CloudWatch Metrics |
| **로그 (Logs)** | **이벤트의 상세 기록** (텍스트·JSON) | "**무슨 일이** 있었나?" | `ERROR 주문 42 결제 실패: 카드 한도 초과` | **ELK/EFK**, Loki, CloudWatch Logs |
| **트레이스 (Traces)** | 요청 하나가 **여러 서비스를 거친 경로와 시간** | "**어디서** 느려졌나?" | API Gateway 5ms → 주문 20ms → 결제 **800ms** → DB | **Jaeger**, Tempo, Zipkin, X-Ray |

### 조합해서 쓰는 흐름
```
1. [메트릭] 알람: "결제 API p99 응답 시간 3초 초과"
2. [트레이스] 느린 요청 하나를 열어 보니 → 결제 서비스의 외부 PG 호출 구간이 2.8초
3. [로그] 해당 trace_id로 로그 검색 → "PG 타임아웃, 재시도 3회"
```
→ 이렇게 이어지려면 **로그에 trace_id를 함께 기록**해야 합니다.

### 메트릭 vs 로그
| | 메트릭 | 로그 |
|---|---|---|
| 데이터 양 | 작음 (숫자 집계) | 큼 |
| 비용 | 저렴 | 비쌈 (저장·검색) |
| 용도 | **알람, 대시보드, 추세** | **상세 원인 분석** |
| 주의 | 카디널리티(레이블 종류 수) 폭발 | 민감 정보 노출, 저장 비용 |

## 3. 무엇을 측정할까?

### 4대 골든 시그널 (Google SRE)
| 시그널 | 의미 | 예 |
|---|---|---|
| **Latency** (지연) | 요청 처리 시간 (성공·실패 따로) | p50, p95, **p99** 응답 시간 |
| **Traffic** (트래픽) | 수요의 양 | 초당 요청 수(RPS) |
| **Errors** (에러) | 실패한 요청 비율 | 5xx 비율 |
| **Saturation** (포화도) | 자원이 얼마나 찼나 | CPU, 메모리, 스레드 풀, DB 커넥션 풀 사용률 |

### RED 방법 (서비스·API용)
- **R**ate: 초당 요청 수
- **E**rrors: 실패 수
- **D**uration: 응답 시간 분포

### USE 방법 (자원·인프라용)
- **U**tilization: 사용률 (CPU 70%)
- **S**aturation: 대기열 (Load Average, 스레드 풀 대기)
- **E**rrors: 에러 (디스크 I/O 에러)

### 평균이 아니라 백분위수 (Percentile)
```
요청 100개: 99개는 50ms, 1개는 5000ms
평균 = 99.5ms        ← "괜찮아 보임"
p99 = 5000ms         ← "100명 중 1명은 5초를 기다림"
```
> 평균은 느린 요청을 숨깁니다. **p95, p99**를 함께 보세요. 사용자는 한 페이지에서 여러 요청을 하므로, p99가 나쁘면 꽤 많은 사용자가 느림을 경험합니다.

### 백엔드에서 꼭 볼 지표
| 계층 | 지표 |
|---|---|
| API | RPS, 에러율(4xx/5xx), p99 응답 시간 (엔드포인트별) |
| JVM | 힙 사용량, **GC 시간·횟수**, 스레드 수 |
| Tomcat | 활성 스레드 / 최대 스레드 |
| **DB 커넥션 풀** | **활성·대기 중 커넥션 수** (HikariCP pending) |
| DB | 느린 쿼리, 커넥션 수, CPU, 복제 지연 |
| 인프라 | CPU, 메모리, 디스크, 네트워크, Pod 재시작 수 |
| 비즈니스 | 주문 수, 결제 성공률, 가입 수 |

## 4. SLI, SLO, SLA

| 용어 | 의미 | 예 |
|---|---|---|
| **SLI** (Indicator, 지표) | 서비스 수준을 **측정하는 값** | 성공한 요청 비율, 300ms 이내 응답 비율 |
| **SLO** (Objective, 목표) | SLI의 **내부 목표치** | "30일간 요청의 99.9%가 성공한다" |
| **SLA** (Agreement, 계약) | 고객과의 **계약**, 어기면 보상(크레딧) | "월 가용성 99.9% 미만이면 요금 10% 환불" |

```
SLA (외부 약속)  ≤  SLO (내부 목표, 더 엄격)   ← SLI로 측정
```

### 가용성 숫자의 의미
| 가용성 | 연간 허용 장애 시간 | 월간 |
|---|---|---|
| 99% | 약 3.65일 | 약 7.3시간 |
| 99.9% ("쓰리 나인") | 약 8.76시간 | 약 43.8분 |
| 99.99% | 약 52.6분 | 약 4.4분 |
| 99.999% | 약 5.26분 | 약 26초 |

> 9가 하나 늘 때마다 비용과 복잡도는 크게 늘어납니다. 서비스 특성에 맞는 목표를 정하는 것이 중요합니다.

### 에러 버짓 (Error Budget)
**100% - SLO = 허용된 실패량**
- SLO 99.9% → 한 달에 약 43분의 장애·에러는 "써도 되는 예산"
- 예산이 남으면 → 적극적으로 새 기능 배포
- 예산을 다 쓰면 → 배포를 멈추고 안정성 개선에 집중
→ 개발 속도와 안정성 사이의 균형을 **데이터로** 결정합니다.

## 5. 알람 (Alerting)

### 좋은 알람의 조건
| 원칙 | 설명 |
|---|---|
| **증상 기반** | "CPU 80%"(원인)보다 "**에러율 5% 초과, p99 2초 초과**"(사용자가 겪는 증상) |
| **조치 가능** | 받으면 무엇을 해야 할지 알 수 있어야 함 (**런북** 링크) |
| 지속 시간 조건 | 순간 튀는 값 무시: "5분 동안 계속 초과" |
| 심각도 구분 | Critical(즉시 호출) / Warning(업무 시간 확인) |
| **알람 피로 방지** | 너무 많으면 모두 무시하게 됨 → 의미 없는 알람은 삭제 |

```
❌ "CPU 사용률 80% 초과"    ← 배치 작업 중엔 정상일 수도
✅ "결제 API 5xx 비율이 5분간 1% 초과 — 런북: wiki/payment-errors"
```

### 도구
- Prometheus **Alertmanager** → Slack, PagerDuty, 이메일
- **CloudWatch Alarm** → SNS → 이메일·Slack·Lambda
- Grafana Alerting

## 6. OpenTelemetry

**메트릭·로그·트레이스를 수집하는 벤더 중립 표준**(CNCF)입니다. 한 번 계측하면 백엔드(Prometheus, Jaeger, Datadog, X-Ray)를 바꿔도 코드를 다시 고칠 필요가 없습니다.

```
[앱 + OTel SDK / Java Agent] ──OTLP──> [OTel Collector] ──> Prometheus / Tempo / Loki / X-Ray / Datadog
```

```bash
# Java 에이전트로 코드 수정 없이 자동 계측
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=order-service \
     -Dotel.exporter.otlp.endpoint=http://otel-collector:4317 \
     -jar app.jar
```
> Spring Boot 3에서는 **Micrometer**(메트릭) + **Micrometer Tracing**(트레이스, OTel 브리지)을 많이 씁니다.

## 7. 면접 질문

1. **관측 가능성의 세 가지 요소는?**
   → 시간에 따른 수치인 메트릭, 이벤트 상세 기록인 로그, 요청이 여러 서비스를 거친 경로와 시간인 트레이스입니다.
2. **응답 시간을 평균 대신 p99로 보는 이유는?**
   → 평균은 소수의 매우 느린 요청을 숨기기 때문에, 실제로 일부 사용자가 겪는 나쁜 경험을 파악하려면 백분위수를 봐야 합니다.
3. **SLO와 SLA의 차이는?**
   → SLO는 내부적으로 정한 서비스 수준 목표이고, SLA는 고객과 맺은 계약으로 어기면 보상이 따르며, 보통 SLO를 SLA보다 엄격하게 둡니다.
4. **좋은 알람이란?**
   → 사용자가 겪는 증상에 기반하고, 받았을 때 조치할 수 있으며, 일시적 변동에 울리지 않고, 너무 많지 않아 무시되지 않는 알람입니다.

## 핵심 정리
- 모니터링(무엇) vs 관측 가능성(왜)
- 메트릭(상태·알람) / 로그(상세) / 트레이스(어디서) — trace_id로 연결
- 골든 시그널: 지연·트래픽·에러·포화도, 평균 대신 p99
- SLI(측정) → SLO(목표) → SLA(계약), 에러 버짓
- 알람은 증상 기반 + 조치 가능, OpenTelemetry로 표준 계측
