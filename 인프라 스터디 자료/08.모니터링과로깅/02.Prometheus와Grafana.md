# 02. Prometheus와 Grafana

> **학습 목표**
> - Prometheus의 Pull 방식 수집 구조를 설명할 수 있다.
> - 메트릭 타입(Counter, Gauge, Histogram, Summary)을 구분할 수 있다.
> - Spring Boot Actuator + Micrometer로 메트릭을 노출할 수 있다.
> - 기본 PromQL(rate, sum by, histogram_quantile)을 작성할 수 있다.
> - Grafana 대시보드와 알람 규칙을 구성할 수 있다.

---

## 1. 구조

```
                         ┌───────── Pull (주기적으로 GET /metrics) ─────────┐
                         ↓                                                │
[Spring Boot /actuator/prometheus]  [node-exporter :9100]  [mysqld-exporter]  ...
                         │
                    [Prometheus 서버] ── 시계열 DB(TSDB)에 저장, 규칙 평가
                     │          │
          PromQL 조회 │          │ 알람 규칙 충족
                     ↓          ↓
               [Grafana]   [Alertmanager] ── Slack / PagerDuty / 이메일
               대시보드      그룹화·중복 제거·라우팅
```

| 구성 요소 | 역할 |
|---|---|
| **Prometheus 서버** | 대상에서 메트릭을 **Pull(스크레이프)**, 시계열 저장, PromQL 질의 |
| **Exporter** | 메트릭을 Prometheus 형식으로 노출 (node-exporter: 서버, mysqld-exporter: DB) |
| 애플리케이션 계측 | 앱이 직접 `/metrics` 노출 (Spring Boot는 Actuator) |
| **Alertmanager** | 알람 그룹화·억제·라우팅 |
| **Grafana** | 시각화 대시보드 (Prometheus, Loki, CloudWatch 등 다양한 데이터 소스) |
| Pushgateway | 짧게 끝나는 배치 작업은 Push로 |

### Pull 방식의 장점
- 대상이 살아 있는지 자동으로 알 수 있음 (`up` 지표가 0이면 스크레이프 실패)
- 앱은 Prometheus 주소를 몰라도 됨
- 쿠버네티스에서는 **서비스 디스커버리**로 Pod를 자동으로 찾아 수집

> 쿠버네티스에서는 **kube-prometheus-stack**(Helm 차트)으로 Prometheus + Grafana + Alertmanager + 기본 대시보드를 한 번에 설치하는 것이 일반적입니다. AWS에는 관리형인 **Amazon Managed Service for Prometheus(AMP)** 와 **Amazon Managed Grafana**가 있습니다.

## 2. 메트릭 형식과 타입

```
# 메트릭 이름{레이블} 값
http_server_requests_seconds_count{method="GET",uri="/api/orders",status="200"} 1523
jvm_memory_used_bytes{area="heap"} 2.5E8
```

| 타입 | 의미 | 예 | 주로 쓰는 함수 |
|---|---|---|---|
| **Counter** | **계속 증가만** 하는 값 (재시작 시 0) | 총 요청 수, 총 에러 수 | `rate()`, `increase()` |
| **Gauge** | **오르내리는** 현재 값 | 메모리 사용량, 활성 스레드, 큐 길이 | 그대로, `avg_over_time()` |
| **Histogram** | 값을 **구간(bucket)별로 세어** 분포 저장 | 응답 시간 분포 | `histogram_quantile()` |
| Summary | 클라이언트에서 백분위수를 계산 | | (여러 인스턴스 합산 불가) |

> Counter의 **값 자체는 의미가 거의 없습니다.** "지금까지 1523번"보다 "**초당 몇 번**"이 중요하므로 `rate()`를 씁니다.

## 3. Spring Boot 연동

```groovy
// build.gradle
implementation 'org.springframework.boot:spring-boot-starter-actuator'
runtimeOnly 'io.micrometer:micrometer-registry-prometheus'
```

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health, prometheus
  metrics:
    tags:
      application: order-service           # 모든 메트릭에 공통 레이블
    distribution:
      percentiles-histogram:
        http.server.requests: true         # 응답 시간 히스토그램 → p99 계산 가능
```

→ `GET /actuator/prometheus` 에서 JVM, Tomcat, HikariCP, HTTP 요청 메트릭이 자동 노출

> `/actuator`는 내부 정보가 많으므로 **외부에 공개하지 않습니다.** 관리 포트를 분리(`management.server.port: 8081`)하거나 Ingress·보안 그룹에서 막으세요.

### 비즈니스 메트릭 직접 추가
```java
@Service
public class OrderService {
    private final Counter orderCounter;
    private final Timer paymentTimer;

    public OrderService(MeterRegistry registry) {
        this.orderCounter = Counter.builder("orders.created")
                .description("생성된 주문 수")
                .register(registry);
        this.paymentTimer = Timer.builder("payment.duration")
                .publishPercentileHistogram()
                .register(registry);
    }

    public void createOrder(OrderRequest req) {
        paymentTimer.record(() -> paymentClient.pay(req));
        orderCounter.increment();
    }
}
```

### 카디널리티 주의
```java
❌ Counter.builder("orders").tag("userId", userId)     // 사용자 수만큼 시계열 생성 → 메모리 폭발
✅ Counter.builder("orders").tag("payMethod", "CARD")  // 값의 종류가 적은 레이블만
```
> 레이블에 **사용자 ID, 주문 ID, 전체 URL(쿼리 포함)** 같은 값을 넣으면 시계열이 폭증해 Prometheus가 느려지거나 죽습니다.

### 스크레이프 설정 (쿠버네티스 밖의 단순 예)
```yaml
# prometheus.yml
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: order-service
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["app1:8080", "app2:8080"]
```
쿠버네티스에서는 `ServiceMonitor`(Prometheus Operator) 리소스로 레이블 기반 자동 수집을 설정합니다.

## 4. PromQL 기본

```promql
# 1. 초당 요청 수 (최근 5분 기준), 서비스 전체
sum(rate(http_server_requests_seconds_count[5m]))

# 2. URI별 초당 요청 수
sum by (uri) (rate(http_server_requests_seconds_count[5m]))

# 3. 5xx 에러 비율 (%)
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m])) * 100

# 4. p99 응답 시간 (히스토그램)
histogram_quantile(0.99,
  sum by (le) (rate(http_server_requests_seconds_bucket[5m])))

# 5. JVM 힙 사용률
sum(jvm_memory_used_bytes{area="heap"}) / sum(jvm_memory_max_bytes{area="heap"})

# 6. HikariCP 커넥션 대기 중인 스레드
hikaricp_connections_pending

# 7. 수집 대상이 죽었는지
up == 0
```

| 문법 | 의미 |
|---|---|
| `{status=~"5.."}` | 레이블 정규식 일치 (`=`, `!=`, `=~`, `!~`) |
| `[5m]` | 최근 5분 범위 |
| `rate()` | Counter의 **초당 평균 증가율** (재시작으로 0이 돼도 보정) |
| `increase()` | 범위 동안 증가량 |
| `sum by (label)` | 레이블별 합계 |
| `histogram_quantile(0.99, ...)` | 버킷으로 백분위수 계산 |

## 5. 알람 규칙

```yaml
groups:
  - name: order-service
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{application="order-service",status=~"5.."}[5m]))
          / sum(rate(http_server_requests_seconds_count{application="order-service"}[5m])) > 0.01
        for: 5m                          # 5분 동안 지속될 때만
        labels:
          severity: critical
        annotations:
          summary: "order-service 5xx 비율 1% 초과"
          runbook: "https://wiki.example.com/runbook/order-errors"

      - alert: HighLatencyP99
        expr: |
          histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket{application="order-service"}[5m]))) > 2
        for: 10m
        labels:
          severity: warning
```

## 6. Grafana

- 데이터 소스: Prometheus, Loki, Tempo, CloudWatch, MySQL ...
- **커뮤니티 대시보드 가져오기**: grafana.com의 대시보드 ID로 import (JVM Micrometer, Node Exporter Full, Spring Boot 등)
- 변수(`$application`, `$instance`)로 하나의 대시보드에서 서비스 전환
- 패널 구성 예: RPS / 에러율 / p50·p95·p99 / JVM 힙·GC / Tomcat 스레드 / HikariCP / Pod 재시작
- 메트릭 → 로그(Loki) → 트레이스(Tempo)로 클릭해 이동하는 연결 기능

### CloudWatch와 비교
| | Prometheus + Grafana | CloudWatch |
|---|---|---|
| 관리 | 직접 운영 (또는 AMP/AMG) | 완전 관리형 |
| AWS 리소스 지표 | exporter 필요 | **자동 수집** (EC2, RDS, ALB) |
| 쿼리 | PromQL (강력) | Metrics Insights |
| 생태계 | 쿠버네티스 표준, 오픈소스 | AWS 통합 |
| 비용 | 인프라 비용 | 지표·API·로그 양 과금 |

> 흔한 조합: **AWS 리소스(RDS, ALB)는 CloudWatch**, **애플리케이션·쿠버네티스는 Prometheus**, 대시보드는 Grafana에서 둘 다 연결

## 7. 면접 질문

1. **Prometheus는 어떻게 메트릭을 수집하나요?**
   → 대상의 HTTP 엔드포인트를 주기적으로 스크레이프하는 Pull 방식이며, 쿠버네티스에서는 서비스 디스커버리로 대상을 자동으로 찾습니다.
2. **Counter와 Gauge의 차이는?**
   → Counter는 증가만 하는 누적 값으로 rate로 증가율을 보고, Gauge는 메모리 사용량처럼 오르내리는 현재 값입니다.
3. **p99 응답 시간은 어떻게 구하나요?**
   → 응답 시간을 Histogram으로 기록하고 PromQL의 `histogram_quantile(0.99, rate(..._bucket[5m]))`로 계산합니다.
4. **메트릭 레이블에 사용자 ID를 넣으면 안 되는 이유는?**
   → 레이블 조합마다 시계열이 만들어져 카디널리티가 폭증하고, 저장소의 메모리와 성능에 큰 문제를 일으키기 때문입니다.

---

## 핵심 정리
- Prometheus: Pull 수집 → TSDB → PromQL / Alertmanager / Grafana
- 타입: Counter(rate) / Gauge / Histogram(histogram_quantile)
- Spring Boot: Actuator + micrometer-registry-prometheus → `/actuator/prometheus` (외부 비공개)
- PromQL: `sum by (uri) (rate(x[5m]))`, 에러율, p99
- 카디널리티 주의, 알람은 `for` 지속 조건 + 런북
