# 03. 로그 수집과 분산 추적

> **학습 목표**
> - 좋은 로그의 조건(레벨, 구조화, 상관관계 ID)을 설명하고 적용할 수 있다.
> - 중앙 집중식 로그 수집이 필요한 이유와 파이프라인 구조를 설명할 수 있다.
> - ELK/EFK, Loki, CloudWatch Logs를 비교할 수 있다.
> - 분산 추적(trace, span)의 원리를 설명할 수 있다.

---

## 1. 좋은 로그란?

### 로그 레벨
| 레벨 | 용도 | 예 |
|---|---|---|
| **ERROR** | 즉시 확인이 필요한 실패 | 결제 실패, DB 연결 끊김 |
| **WARN** | 당장 문제는 아니지만 주의 | 재시도 후 성공, 지원 종료 예정 API 호출 |
| **INFO** | 주요 비즈니스 흐름 | 주문 생성, 서버 기동 |
| DEBUG | 개발·디버깅용 상세 정보 | 메서드 입력값 |
| TRACE | 매우 상세 | |

> 운영 기본은 **INFO**. DEBUG를 운영에서 켜 두면 로그 양과 비용이 폭증합니다. Spring Boot Actuator의 `/actuator/loggers`로 **재시작 없이 특정 패키지의 레벨만** 잠시 바꿀 수 있습니다.

### 로그에 넣을 것 / 넣지 말 것
| ✅ 넣을 것 | ❌ 넣지 말 것 |
|---|---|
| 시각(타임존 포함), 레벨, 서비스 이름 | **비밀번호, 토큰, 카드 번호, 주민번호** |
| **trace_id / request_id** | 개인정보 원문 (마스킹: `kim***@gmail.com`) |
| 사용자 ID(내부 식별자), 주문 ID | 요청·응답 바디 전체(대용량) |
| 에러 메시지 + **스택 트레이스** | 의미 없는 "여기 들어옴" 로그 |
| 처리 시간, 외부 호출 결과 | |

```java
// ❌ 문자열 이어 붙이기: 레벨이 꺼져 있어도 문자열 연산 발생, 검색 어려움
log.info("주문 생성 " + orderId + " 사용자 " + userId);

// ✅ 플레이스홀더
log.info("주문 생성 orderId={}, userId={}, amount={}", orderId, userId, amount);

// ✅ 예외는 마지막 인자로 → 스택 트레이스 출력
log.error("결제 실패 orderId={}", orderId, e);
```

## 2. 구조화된 로그 (Structured Logging)

사람이 읽는 텍스트 대신 **JSON**으로 남기면, 로그 시스템이 필드별로 **검색·집계**할 수 있습니다.

```
텍스트:  2026-11-09 10:00:00 ERROR [order-service] 결제 실패 orderId=42
JSON:   {"@timestamp":"2026-11-09T10:00:00.123+09:00","level":"ERROR","service":"order-service",
         "traceId":"4bf92f3577b34da6","orderId":42,"message":"결제 실패","exception":"..."}
```
→ `level:ERROR AND service:order-service AND orderId:42` 처럼 정확히 검색

```yaml
# Spring Boot 3.4+ : 구조화 로그 내장 지원
logging:
  structured:
    format:
      console: ecs        # ecs(Elastic), logstash, gelf 형식
```
> 이전 버전은 `logstash-logback-encoder` 라이브러리를 씁니다.

### MDC로 요청마다 ID 붙이기
```java
@Component
public class RequestIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String requestId = Optional.ofNullable(req.getHeader("X-Request-Id"))
                                   .orElse(UUID.randomUUID().toString());
        MDC.put("requestId", requestId);           // 이 스레드의 모든 로그에 자동 포함
        res.setHeader("X-Request-Id", requestId);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                           // 스레드 풀 재사용 → 반드시 정리
        }
    }
}
```
> Micrometer Tracing을 쓰면 `traceId`, `spanId`가 MDC에 자동으로 들어갑니다.

## 3. 왜 중앙 집중식 로그인가?

서버 10대, Pod 50개에 로그가 흩어져 있으면:
- 어느 서버에서 에러가 났는지 모름 → 하나씩 SSH 접속
- **Pod·컨테이너가 죽으면 로그도 사라짐**
- 여러 서비스에 걸친 요청을 따라갈 수 없음

→ 모든 로그를 **한곳에 모아 저장·검색**합니다.

### 수집 파이프라인
```
[앱: stdout으로 JSON 로그 출력]
        ↓ (컨테이너 런타임이 노드의 /var/log/containers/*.log 로 기록)
[수집 에이전트: Fluent Bit / Vector / CloudWatch Agent]  ← DaemonSet으로 노드마다
        ↓ 파싱, 필드 추가(Pod 이름, 네임스페이스), 필터링, 마스킹
[(선택) 버퍼: Kafka / Kinesis]  ← 급증 대비
        ↓
[저장·검색: Elasticsearch / OpenSearch / Loki / CloudWatch Logs / S3]
        ↓
[시각화: Kibana / OpenSearch Dashboards / Grafana]
```

> 컨테이너 환경 원칙: **앱은 파일이 아니라 stdout으로 로그를 쓰고**, 수집은 인프라(에이전트)가 담당합니다. (12-Factor App: 로그는 이벤트 스트림)

## 4. 로그 스택 비교

### ELK / EFK
| 구성 | 역할 |
|---|---|
| **E**lasticsearch (또는 OpenSearch) | 저장 + **전문 검색 엔진** (역색인) |
| **L**ogstash / **F**luentd·Fluent Bit | 수집·변환 |
| **K**ibana | 검색 UI, 대시보드 |

- 장점: **강력한 전문 검색**, 복잡한 집계
- 단점: 모든 필드를 색인 → **저장·메모리 비용 큼**, 클러스터 운영 부담

### Grafana Loki
- **레이블만 색인**하고 로그 본문은 압축 저장 (S3 등) → **저렴**
- LogQL: `{app="order-service"} |= "ERROR" | json | orderId="42"`
- Prometheus와 같은 레이블 체계 → Grafana에서 메트릭과 함께
- 단점: 본문 전문 검색은 Elasticsearch보다 느림

### CloudWatch Logs
- AWS 관리형, ECS(awslogs 드라이버)·Lambda는 기본 연동
- **Logs Insights** 쿼리
```
fields @timestamp, level, message, orderId
| filter level = "ERROR" and service = "order-service"
| sort @timestamp desc
| limit 50
```
- 메트릭 필터로 "ERROR 로그 수" → 알람
- 주의: 수집(GB당)·저장 비용, **보존 기간 설정 필수** (기본은 무기한)

| 비교 | ELK/OpenSearch | Loki | CloudWatch Logs |
|---|---|---|---|
| 색인 | 전체 필드 | 레이블만 | 자동 |
| 검색 | **가장 강력** | 레이블 + grep | 중간 (Insights) |
| 비용 | 높음 | **낮음** | 사용량 과금 |
| 운영 | 부담 큼 (관리형 OpenSearch Service 있음) | 비교적 가벼움 | **없음** |
| 적합 | 로그 분석이 핵심, 대규모 검색 | 쿠버네티스 + Grafana | AWS 관리형 위주, 소규모 |

### 비용 관리
- 수집 단계에서 **불필요한 로그 필터링** (헬스 체크 요청 로그 제외)
- 보존 기간: 핫(7~30일, 빠른 검색) → 오래된 로그는 **S3로 아카이브**
- 로그 레벨 관리, 샘플링

## 5. 분산 추적 (Distributed Tracing)

MSA에서는 요청 하나가 여러 서비스를 거칩니다. 어디서 느려졌는지 찾으려면 **요청 전체 경로**가 필요합니다.

```
Trace ID: 4bf92f3577b34da6 (요청 전체에 하나)
├── Span: API Gateway         [0ms ──────────────────────────────── 950ms]
│   └── Span: order-service   [5ms ─────────────────────────────── 940ms]
│       ├── Span: DB 주문 조회  [10ms ── 30ms]
│       ├── Span: member-service 호출 [35ms ── 60ms]
│       └── Span: payment-service 호출 [65ms ─────────────────── 930ms]  ← 병목!
│           └── Span: 외부 PG API  [70ms ──────────────────── 920ms]
```

| 개념 | 의미 |
|---|---|
| **Trace** | 요청 하나의 전체 여정 (고유 trace_id) |
| **Span** | 그 안의 작업 하나 (서비스 호출, DB 쿼리), 시작·종료 시각, 부모 span |
| **컨텍스트 전파** | 서비스를 호출할 때 **HTTP 헤더로 trace_id를 넘김** (W3C 표준 `traceparent` 헤더) |
| 샘플링 | 모든 요청을 저장하면 비용이 크므로 일부만 (예: 10%, 에러는 전부) |

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             버전   trace-id(32자리)                  parent-span-id     flags(샘플링)
```

### Spring Boot 설정
```groovy
implementation 'io.micrometer:micrometer-tracing-bridge-otel'
implementation 'io.opentelemetry:opentelemetry-exporter-otlp'
```
```yaml
management:
  tracing:
    sampling:
      probability: 0.1          # 10% 샘플링
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
```
- RestClient, WebClient, Kafka 등 Spring이 관리하는 클라이언트는 **자동으로 헤더 전파**
- 로그 패턴에 traceId가 포함되어 **로그 ↔ 트레이스 연결**

| 도구 | 특징 |
|---|---|
| **Jaeger** | CNCF, 오픈소스 표준 UI |
| **Grafana Tempo** | 저렴한 저장(S3), Grafana 연동 |
| Zipkin | 오래된 오픈소스 |
| **AWS X-Ray** | AWS 관리형 (ADOT·OTel 연동) |
| Datadog, New Relic | 상용 APM (메트릭·로그·트레이스 통합) |

## 6. 면접 질문

1. **로그를 중앙에서 수집해야 하는 이유는?**
   → 여러 서버·컨테이너에 흩어진 로그를 한곳에서 검색하고, 컨테이너가 종료돼도 로그를 보존하며, 여러 서비스를 거친 요청을 연관 지어 분석하기 위해서입니다.
2. **구조화된 로그의 장점은?**
   → JSON 같은 형식으로 필드가 나뉘어 있어 로그 시스템에서 필드별 검색·필터·집계가 정확하고 쉽습니다.
3. **분산 추적은 어떻게 동작하나요?**
   → 요청마다 trace ID를 만들고 서비스를 호출할 때 HTTP 헤더로 전파하며, 각 작업을 span으로 기록해 요청 전체 경로와 구간별 소요 시간을 재구성합니다.
4. **ELK와 Loki의 차이는?**
   → ELK는 로그 전체를 색인해 강력한 검색을 제공하지만 비용과 운영 부담이 크고, Loki는 레이블만 색인해 저렴하지만 본문 검색은 상대적으로 느립니다.

## 핵심 정리
- 로그: 운영은 INFO, 플레이스홀더, 예외는 마지막 인자, **민감 정보 금지**
- **구조화(JSON) + requestId/traceId(MDC)**
- 컨테이너는 stdout → 에이전트(Fluent Bit, DaemonSet) → 저장소
- ELK(강력·비쌈) / Loki(레이블·저렴) / CloudWatch Logs(관리형, 보존 기간 설정)
- 분산 추적: trace(요청 전체) + span(구간), traceparent 헤더 전파
