# 01. 마이크로서비스 아키텍처 (MSA)

> **학습 목표**
> - 모놀리식과 MSA의 장단점을 비교하고 언제 MSA를 선택할지 판단할 수 있다.
> - 서비스를 나누는 기준(도메인, Bounded Context)을 설명할 수 있다.
> - API 게이트웨이, 서비스 디스커버리, 서비스 간 통신 방식을 설명할 수 있다.
> - 서비스별 DB와 분산 트랜잭션(Saga, Outbox) 문제를 설명할 수 있다.

---

## 1. 모놀리식 vs MSA

```
모놀리식 (Monolithic)                       MSA (Microservices)
+───────────────────────────+          [API Gateway]
|  회원 | 상품 | 주문 | 결제   |           /    |     |    \
|      하나의 애플리케이션       |       [회원]  [상품]  [주문]  [결제]
+───────────────────────────+         │      │      │      │
              │                      [DB]   [DB]   [DB]   [DB]
           [하나의 DB]
```

| 비교 | 모놀리식 | MSA |
|---|---|---|
| 배포 | 전체를 한 번에 | **서비스별 독립 배포** |
| 확장 | 전체를 복제 | **필요한 서비스만** 확장 (주문만 10대) |
| 장애 | 한 기능의 메모리 누수가 전체를 죽임 | **장애 격리** (잘 설계했을 때) |
| 기술 | 하나의 스택 | 서비스별 선택 가능 |
| 팀 | 하나의 코드베이스에 모두 | **팀별 서비스 소유** |
| 개발 초기 | **빠르고 단순** | 느림 (인프라·통신 설계) |
| 트랜잭션 | DB 트랜잭션 하나로 | **분산 트랜잭션** 문제 |
| 디버깅 | 스택 트레이스 하나 | **분산 추적** 필요 |
| 운영 | 단순 | CI/CD, 모니터링, 서비스 디스커버리 등 **운영 역량 필수** |
| 네트워크 | 함수 호출 | **네트워크 호출** (지연, 실패 가능) |

### 언제 MSA를 선택할까?
- 조직이 커서 **여러 팀이 독립적으로** 배포해야 할 때
- 기능별 트래픽·확장 요구가 크게 다를 때
- 도메인 경계가 명확할 때
- **CI/CD, 컨테이너, 관측 가능성 기반이 갖춰졌을 때**

> 작은 팀·초기 서비스는 **모놀리식(또는 모듈러 모놀리스)로 시작**하는 것이 일반적인 권장입니다. 모듈 경계를 잘 나눠 두면 나중에 필요한 부분만 분리할 수 있습니다. 경계를 잘못 나눈 MSA는 "분산된 모놀리스"가 되어 둘의 단점만 갖게 됩니다.

## 2. 서비스를 어떻게 나눌까?

### 도메인 주도 설계 (DDD)의 Bounded Context
같은 단어도 맥락마다 의미가 다릅니다.
```
"상품"
 ├ 카탈로그 맥락: 이름, 설명, 이미지, 카테고리
 ├ 재고 맥락:    수량, 창고 위치
 └ 주문 맥락:    주문 당시 가격, 수량 (스냅샷)
```
→ 맥락(Bounded Context)마다 서비스를 나누고, 각자 자기 모델을 가집니다.

### 좋은 서비스 경계의 조건
- **높은 응집도, 낮은 결합도**: 함께 바뀌는 것은 한 서비스에
- 서비스 하나의 변경이 다른 서비스 배포를 요구하지 않음
- 한 팀이 소유·운영할 수 있는 크기
- 서비스끼리 **동기 호출이 줄줄이 이어지지 않음** (A → B → C → D)

## 3. 핵심 구성 요소

### API 게이트웨이
클라이언트의 **단일 진입점**으로, 공통 기능을 처리합니다.
```
[모바일/웹] → [API Gateway] → /members/** → 회원 서비스
                          → /orders/**  → 주문 서비스
```
| 기능 | 설명 |
|---|---|
| 라우팅 | 경로·호스트 기반으로 서비스에 전달 |
| **인증** | JWT 검증을 한 곳에서 → 내부 서비스에는 사용자 정보만 전달 |
| Rate Limiting | 요청 수 제한 |
| 로깅, 트레이싱 시작 | trace_id 발급 |
| 응답 집계 (BFF) | 여러 서비스 결과를 합쳐 화면에 맞게 |

도구: **Spring Cloud Gateway**, AWS API Gateway, Kong, ALB(단순 라우팅), 쿠버네티스 Ingress·Gateway API

### 서비스 디스커버리
서비스 인스턴스는 수시로 생기고 사라지므로 **주소를 동적으로 찾아야** 합니다.
| 방식 | 예 |
|---|---|
| 클라이언트 측 | Netflix **Eureka** + Spring Cloud LoadBalancer (클라이언트가 레지스트리 조회) |
| **플랫폼 제공** | **쿠버네티스 Service + DNS**, ECS Service Connect, AWS Cloud Map |

> 쿠버네티스를 쓰면 Eureka 없이 `http://member-service`로 호출하면 됩니다.

### 설정 관리
- Spring Cloud Config, 쿠버네티스 ConfigMap·Secret, AWS Parameter Store·AppConfig

### 서비스 메시 (Service Mesh)
- 각 Pod에 **사이드카 프록시(Envoy)** 를 붙여 서비스 간 통신을 인프라가 처리
- mTLS 암호화, 재시도·타임아웃, 트래픽 분할(카나리), 관측성을 **코드 수정 없이**
- Istio, Linkerd, (사이드카 없는 Istio Ambient 모드)
- 강력하지만 **복잡도와 운영 부담이 큼** → 필요가 명확할 때 도입

## 4. 서비스 간 통신

| 방식 | 프로토콜 | 특징 | 사용처 |
|---|---|---|---|
| **동기 REST** | HTTP/JSON | 단순, 범용, 디버깅 쉬움 | 즉시 응답이 필요한 조회 |
| **gRPC** | HTTP/2 + Protobuf | 바이너리 → **빠름**, 스키마 강제, 스트리밍 | 내부 서비스 간 고성능 통신 |
| **비동기 메시징** | Kafka, SQS, RabbitMQ | **느슨한 결합**, 장애 격리, 버퍼링 | 이벤트 전파, 후속 처리 (→ `02.메시지큐와Kafka.md`) |

### 동기 호출의 위험
```
주문 → 회원 → 쿠폰 → 포인트
가용성: 99.9% × 99.9% × 99.9% × 99.9% ≈ 99.6%   ← 연결될수록 전체 가용성이 떨어짐
지연:  각 서비스 응답 시간이 모두 더해짐
쿠폰 서비스가 느려지면 → 회원 → 주문까지 스레드가 묶여 연쇄 장애
```
→ **타임아웃, 재시도, 서킷 브레이커** 필수 (→ `03.고가용성과장애대응.md`), 가능하면 비동기 이벤트로 전환

```java
// Spring 6.1+ RestClient 예 (타임아웃 설정은 RequestFactory에서)
RestClient client = RestClient.builder()
        .baseUrl("http://member-service")
        .requestFactory(new JdkClientHttpRequestFactory(
                HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(1)).build()))
        .build();

MemberDto member = client.get().uri("/members/{id}", id).retrieve().body(MemberDto.class);
```

## 5. 데이터 관리

### Database per Service
**각 서비스가 자기 DB를 소유**하고, 다른 서비스의 DB에 직접 접근하지 않습니다. (API·이벤트로만)
- 이유: DB를 공유하면 스키마 변경 하나가 여러 서비스를 깨뜨림 → 독립 배포 불가

**문제**: 서비스 간 JOIN 불가, 트랜잭션 불가

### 조회 문제 해결
| 방법 | 설명 |
|---|---|
| API 조합 | 게이트웨이·BFF에서 여러 서비스를 호출해 합침 |
| **데이터 복제** | 필요한 데이터를 이벤트로 받아 **자기 DB에 사본** 저장 (주문 서비스가 회원 이름을 보관) |
| **CQRS** | 쓰기 모델과 **조회 전용 모델**(여러 서비스 데이터를 합친 읽기용 DB, Elasticsearch) 분리 |

### 분산 트랜잭션 문제
"주문 생성 + 재고 차감 + 결제"가 각각 다른 서비스·DB에 있으면 하나의 DB 트랜잭션으로 묶을 수 없습니다.

| 방법 | 설명 | 평가 |
|---|---|---|
| 2PC (Two-Phase Commit) | 코디네이터가 모든 참여자에게 준비 → 커밋 | 느리고, 코디네이터 장애에 취약, **MSA에서 거의 안 씀** |
| **Saga 패턴** | 각 서비스가 **로컬 트랜잭션**을 순서대로 실행, 실패하면 **보상 트랜잭션**으로 되돌림 | **MSA 표준** |

```
Saga: 주문 생성 → 재고 차감 → 결제
                              ✗ 결제 실패
      주문 취소 ← 재고 복구 ←──┘   (보상 트랜잭션)
```
| Saga 방식 | 설명 |
|---|---|
| **코레오그래피** (Choreography) | 각 서비스가 **이벤트를 듣고 다음 행동** (중앙 관리자 없음) → 단순하지만 흐름 파악 어려움 |
| **오케스트레이션** (Orchestration) | **오케스트레이터**가 각 서비스에 명령 → 흐름이 명확, 오케스트레이터 복잡 |

> Saga는 **최종적 일관성(Eventual Consistency)** 을 받아들이는 것입니다. 잠시 "주문은 생성됐지만 결제 대기" 같은 중간 상태가 보일 수 있으므로 상태 설계가 중요합니다.

### Transactional Outbox 패턴
"DB 저장"과 "이벤트 발행"을 **원자적으로** 처리하는 방법입니다.
```
문제: DB 커밋 성공 → Kafka 발행 실패  → 이벤트 유실
      Kafka 발행 성공 → DB 커밋 실패  → 없는 주문의 이벤트

해결:
1. 같은 DB 트랜잭션으로 [orders 테이블] + [outbox 테이블(이벤트)]에 저장
2. 별도 프로세스(폴링 또는 CDC: Debezium)가 outbox를 읽어 Kafka로 발행
3. 발행 후 처리 완료 표시
→ 최소 한 번(at-least-once) 발행 보장 → 소비자는 멱등하게 처리
```

## 6. 면접 질문

1. **모놀리식과 MSA의 장단점은?**
   → 모놀리식은 개발·배포·트랜잭션이 단순하지만 일부 변경에도 전체를 배포하고 부분 확장이 어렵습니다. MSA는 독립 배포·확장·장애 격리가 가능하지만, 네트워크 통신, 분산 트랜잭션, 운영 복잡도가 커집니다.
2. **API 게이트웨이의 역할은?**
   → 클라이언트의 단일 진입점으로 라우팅, 인증, 요청 제한, 로깅 같은 공통 관심사를 처리합니다.
3. **MSA에서 분산 트랜잭션은 어떻게 처리하나요?**
   → 각 서비스의 로컬 트랜잭션을 이벤트나 오케스트레이터로 연결하고, 실패 시 보상 트랜잭션으로 되돌리는 Saga 패턴을 쓰며, 이벤트 발행의 원자성은 Outbox 패턴으로 보장합니다.
4. **서비스마다 DB를 분리하는 이유는?**
   → DB를 공유하면 스키마 변경이 여러 서비스에 영향을 줘 독립 배포가 불가능해지기 때문입니다.

## 핵심 정리
- 모놀리식(단순, 초기 권장) vs MSA(독립 배포·확장, 운영 복잡) — 조직·도메인·운영 역량으로 판단
- 경계: Bounded Context, 높은 응집도·낮은 결합도
- API 게이트웨이(진입점·인증), 서비스 디스커버리(K8s DNS), 서비스 메시(선택)
- 통신: REST / gRPC / 비동기 메시징, 동기 체인은 위험
- Database per Service → Saga(보상 트랜잭션) + Outbox, CQRS
