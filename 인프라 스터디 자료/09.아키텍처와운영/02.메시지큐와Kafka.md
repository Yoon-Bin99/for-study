# 02. 메시지 큐와 Kafka

> **학습 목표**
> - 메시지 큐를 쓰는 이유(비동기, 결합도 감소, 부하 평탄화)를 설명할 수 있다.
> - 점대점(큐)과 발행-구독(토픽) 모델을 구분할 수 있다.
> - Kafka의 구조(브로커, 토픽, 파티션, 오프셋, 컨슈머 그룹)를 설명할 수 있다.
> - 메시지 전달 보장 수준과 멱등 소비자를 설명할 수 있다.
> - Kafka, RabbitMQ, SQS를 비교할 수 있다.

---

## 1. 왜 메시지 큐인가?

### 동기 방식의 문제
```
[주문 API] ──동기──> 결제 → 재고 → 이메일 발송 → 포인트 적립 → 알림톡
            응답 시간 = 모두 합친 시간, 이메일 서버가 느리면 주문도 느려지고, 죽으면 주문 실패
```

### 메시지 큐 사용
```
[주문 API] → 주문 저장 → "주문 완료" 이벤트 발행 → 즉시 응답
                              ↓
                       [메시지 브로커]
                     ↙       ↓        ↘
             [이메일 서비스] [포인트 서비스] [알림 서비스]   ← 각자 자기 속도로 처리
```

| 장점 | 설명 |
|---|---|
| **비동기 처리** | 오래 걸리는 작업을 뒤로 → 응답 시간 단축 |
| **결합도 감소** | 생산자는 누가 소비하는지 모름 → 새 소비자 추가 시 생산자 수정 X |
| **장애 격리** | 이메일 서비스가 죽어도 주문은 성공, 메시지는 쌓였다가 복구 후 처리 |
| **부하 평탄화** (Load Leveling) | 트래픽 급증 시 큐가 버퍼 역할, 소비자는 처리 가능한 속도로 |
| 확장 | 소비자를 늘려 병렬 처리 |

| 단점 | 설명 |
|---|---|
| 복잡도 | 브로커 운영, 메시지 형식 관리 |
| **최종적 일관성** | 즉시 반영되지 않음 |
| 디버깅 | 흐름 추적이 어려움 (trace_id를 메시지 헤더로 전파) |
| 중복·순서 | 중복 수신, 순서 뒤바뀜 가능성 처리 필요 |

## 2. 메시징 모델

### 점대점 (Point-to-Point, 큐)
```
[생산자] → [큐: 작업1 작업2 작업3] → [소비자 A] (작업1)
                                 → [소비자 B] (작업2)
```
- 메시지 하나는 **소비자 하나만** 처리
- 작업 분배 (이미지 리사이징 작업 큐)
- 예: **SQS**, RabbitMQ 큐

### 발행-구독 (Pub/Sub, 토픽)
```
[발행자] → [토픽: 주문완료] → [구독자: 이메일]   (모두 같은 메시지를 받음)
                          → [구독자: 포인트]
                          → [구독자: 통계]
```
- 메시지 하나를 **여러 구독자가 각각** 받음
- 이벤트 전파
- 예: **Kafka**(컨슈머 그룹별), **SNS**, Redis Pub/Sub

> AWS에서 흔한 패턴: **SNS(팬아웃) → SQS 큐 여러 개 → 각 서비스**

## 3. Kafka 구조

**대용량 이벤트 스트리밍 플랫폼**입니다. 메시지를 **디스크에 로그로 저장**하고, 소비 후에도 보존 기간 동안 남겨 둡니다.

```
                        Kafka 클러스터
          +──────────────────────────────────────────+
          |  토픽: order-events (파티션 3, 복제 3)       |
[생산자] →  |  파티션 0: [0][1][2][3][4][5] →          |  → [컨슈머 그룹: email-service]
 key로     |  파티션 1: [0][1][2][3] →                 |       컨슈머 A ← 파티션 0
 파티션    |  파티션 2: [0][1][2][3][4] →              |       컨슈머 B ← 파티션 1, 2
 결정      |       ↑ 오프셋 (각 메시지의 위치 번호)        |
          |  브로커 1      브로커 2      브로커 3        |  → [컨슈머 그룹: point-service]
          +──────────────────────────────────────────+       컨슈머 C ← 파티션 0, 1, 2
```

| 개념 | 설명 |
|---|---|
| **브로커** | Kafka 서버 하나. 여러 대가 클러스터 구성 |
| **토픽** | 메시지의 카테고리 (`order-events`) |
| **파티션** | 토픽을 나눈 단위. **병렬 처리의 단위**이자 **순서 보장의 단위** |
| **오프셋** | 파티션 안에서 메시지의 순번. 컨슈머는 "어디까지 읽었는지" 오프셋을 커밋 |
| **프로듀서** | 메시지를 보냄. **key**가 같으면 같은 파티션으로 → 순서 보장 |
| **컨슈머 그룹** | 같은 그룹의 컨슈머들은 **파티션을 나눠** 처리. 다른 그룹은 **독립적으로 전부** 받음 |
| 복제 (Replication) | 파티션을 여러 브로커에 복제 (리더 1 + 팔로워). 리더가 죽으면 팔로워가 승격 |
| 메타데이터 관리 | 예전 ZooKeeper → 현재 **KRaft**(Kafka 자체 합의, Kafka 4.0부터 ZooKeeper 제거) |

### 핵심 규칙
- **순서는 파티션 안에서만 보장** → 같은 주문의 이벤트는 `key = orderId`로 같은 파티션에
- 한 컨슈머 그룹에서 **파티션 하나는 컨슈머 하나만** 읽음
  → **컨슈머 수 > 파티션 수**면 남는 컨슈머는 놀게 됨 → 병렬도 = 파티션 수
- 컨슈머가 추가·제거되면 **리밸런싱**(파티션 재할당) 발생

### Kafka가 빠른 이유
- 디스크에 **순차 쓰기**(append-only 로그) → 랜덤 쓰기보다 훨씬 빠름
- OS 페이지 캐시 활용, **Zero-copy**(sendfile)로 커널에서 바로 네트워크 전송
- 배치 전송·압축
- 파티션으로 수평 확장

## 4. 메시지 전달 보장

| 수준 | 의미 | 위험 |
|---|---|---|
| **At-most-once** (최대 한 번) | 보내고 확인 안 함 | **유실** 가능 |
| **At-least-once** (최소 한 번) | 확인될 때까지 재전송 | **중복** 가능 → **실무 기본값** |
| Exactly-once (정확히 한 번) | 중복도 유실도 없음 | 구현 비용 큼 (Kafka 트랜잭션은 Kafka 내부 처리에 한정) |

### 프로듀서 설정
| 설정 | 의미 |
|---|---|
| `acks=all` | 모든 동기화된 복제본(ISR)에 기록돼야 성공 → 유실 최소화 (Kafka 3.0+ 기본값) |
| `enable.idempotence=true` | 재시도해도 같은 메시지가 중복 저장되지 않음 (3.0+ 기본값) |
| `min.insync.replicas=2` (브로커/토픽) | 최소 2개 복제본이 살아 있어야 쓰기 허용 |

### 컨슈머: 오프셋 커밋 시점
```
처리 전에 커밋 → 처리 중 죽으면 그 메시지는 건너뜀 (유실)
처리 후에 커밋 → 커밋 전에 죽으면 다시 처리 (중복)  ← 권장
```

### 멱등 소비자 (Idempotent Consumer)
at-least-once에서는 중복이 생기므로, **같은 메시지를 두 번 처리해도 결과가 같게** 만듭니다.
```java
@KafkaListener(topics = "order-events", groupId = "point-service")
@Transactional
public void handle(OrderCompletedEvent event) {
    if (processedEventRepository.existsById(event.eventId())) {
        return;                                   // 이미 처리한 이벤트 → 무시
    }
    pointService.addPoint(event.memberId(), event.amount());
    processedEventRepository.save(new ProcessedEvent(event.eventId()));
}
```
- 이벤트에 **고유 ID** 포함, 처리 기록 테이블(UNIQUE 제약)
- 또는 업서트, "상태가 이미 PAID면 무시" 같은 자연스러운 멱등 로직

### 실패 처리
- 재시도(지수 백오프) 후에도 실패하면 **DLQ (Dead Letter Queue/Topic)** 로 보내 따로 분석·재처리
- 포이즌 메시지(형식 오류)가 컨슈머를 계속 막지 않게

## 5. Kafka vs RabbitMQ vs SQS

| 비교 | **Kafka** | **RabbitMQ** | **AWS SQS** |
|---|---|---|---|
| 모델 | 분산 **로그** (Pull) | 메시지 **브로커** (Push) | 관리형 **큐** (Pull) |
| 소비 후 메시지 | **보존** (기간 동안), 재처리(오프셋 되돌리기) 가능 | 확인(ack)하면 삭제 | 삭제 |
| 처리량 | **매우 높음** (초당 수백만) | 높음 | 높음 (거의 무제한 확장) |
| 순서 | 파티션 내 보장 | 큐 내 보장 | Standard: 보장 X / **FIFO 큐**: 보장 |
| 라우팅 | 토픽·파티션 | **유연** (Exchange: direct, topic, fanout) | 단순 |
| 운영 | 부담 큼 (**MSK**, Confluent Cloud로 완화) | 중간 (Amazon MQ) | **없음** (서버리스) |
| 적합 | 이벤트 스트리밍, 로그 수집, CDC, 여러 소비자, 이벤트 재처리 | 작업 큐, 복잡한 라우팅, RPC | AWS 환경의 작업 큐, 서비스 간 비동기 처리 |

### SQS 핵심 개념
| 개념 | 설명 |
|---|---|
| **가시성 타임아웃** | 소비자가 메시지를 가져가면 일정 시간 다른 소비자에게 안 보임 → 그 안에 삭제하지 않으면 다시 보임(재처리) |
| DLQ | `maxReceiveCount`번 실패하면 DLQ로 이동 |
| Long Polling | 메시지가 올 때까지 최대 20초 대기 → 빈 응답·비용 감소 |
| Standard vs FIFO | 최소 한 번·순서 보장 X / 순서 보장·중복 제거 (처리량 제한) |

> Redis도 Pub/Sub(저장 X, 구독자가 없으면 유실)과 **Streams**(저장, 컨슈머 그룹)를 제공해 가벼운 메시징에 쓸 수 있습니다.

## 6. 면접 질문

1. **메시지 큐를 쓰는 이유는?**
   → 오래 걸리는 작업을 비동기로 처리해 응답 시간을 줄이고, 생산자와 소비자의 결합도를 낮추며, 장애를 격리하고, 트래픽 급증 시 버퍼 역할을 하기 때문입니다.
2. **Kafka에서 순서를 보장하려면?**
   → Kafka는 파티션 안에서만 순서를 보장하므로, 순서가 중요한 메시지는 같은 key를 써서 같은 파티션으로 보냅니다.
3. **컨슈머 그룹이란?**
   → 같은 그룹의 컨슈머들이 토픽의 파티션을 나눠 처리하는 단위로, 그룹이 다르면 같은 메시지를 독립적으로 받습니다. 병렬도는 파티션 수로 제한됩니다.
4. **메시지가 중복으로 처리되는 것은 어떻게 막나요?**
   → 실무에서는 최소 한 번 전달을 기본으로 하므로, 이벤트 고유 ID로 처리 여부를 기록하는 등 소비자를 멱등하게 만듭니다.
5. **Kafka와 RabbitMQ의 차이는?**
   → Kafka는 메시지를 로그로 보존하는 고처리량 스트리밍 플랫폼으로 재처리와 다수 소비자에 강하고, RabbitMQ는 유연한 라우팅을 가진 메시지 브로커로 처리된 메시지는 삭제되며 작업 큐에 적합합니다.

## 핵심 정리
- 메시지 큐 = 비동기 + 느슨한 결합 + 장애 격리 + 부하 평탄화 (대신 최종적 일관성)
- 큐(하나가 처리) vs 토픽(모두 받음)
- Kafka: 토픽 → 파티션(순서·병렬 단위) → 오프셋, 컨슈머 그룹, key로 순서 보장, KRaft
- At-least-once + **멱등 소비자** + DLQ, 처리 후 오프셋 커밋
- Kafka(스트리밍·보존) / RabbitMQ(라우팅·작업 큐) / SQS(관리형, 가시성 타임아웃)
