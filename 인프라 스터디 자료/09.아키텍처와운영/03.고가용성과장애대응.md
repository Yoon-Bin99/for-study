# 03. 고가용성과 장애 대응

> **학습 목표**
> - 가용성, 단일 장애점(SPOF), 이중화(Active-Active, Active-Standby)를 설명할 수 있다.
> - 타임아웃, 재시도, 서킷 브레이커, 벌크헤드, 레이트 리미팅을 적용할 수 있다.
> - 백업과 재해 복구(RPO, RTO, DR 전략)를 설명할 수 있다.
> - 장애 대응 절차와 포스트모템을 설명할 수 있다.
> - 부하 테스트와 용량 계획을 수행할 수 있다.

## 1. 고가용성 (High Availability)

**가용성 = 서비스가 정상 동작한 시간의 비율**입니다. (99.9% = 한 달 약 43분 장애 허용, → `08.모니터링과로깅/01.관측가능성.md`)

### 단일 장애점 (SPOF, Single Point of Failure)
**그것 하나가 죽으면 전체가 멈추는 구성 요소**입니다.
```
[사용자] → [로드밸런서 1대] → [서버 1대] → [DB 1대]
              SPOF            SPOF         SPOF
```

### 계층별 이중화
| 계층 | SPOF 제거 방법 |
|---|---|
| DNS | Route 53 (분산 관리형), 헬스 체크 + 장애 조치 라우팅 |
| 로드밸런서 | ALB/NLB (여러 AZ에 걸친 관리형) |
| 애플리케이션 | **여러 AZ**에 2대 이상 + Auto Scaling / 쿠버네티스 replicas + AZ 분산 |
| 세션·파일 | 서버 밖으로: Redis, S3 → **서버 무상태** |
| 캐시 | ElastiCache 복제본 + 자동 장애 조치 |
| **DB** | **RDS Multi-AZ** / Aurora, 백업 |
| 메시지 브로커 | Kafka 복제 계수 3, MSK 여러 AZ |
| 리전 | 멀티 리전 (DR) |

### 이중화 방식
| 방식 | 설명 | 장단점 |
|---|---|---|
| **Active-Active** | 모든 노드가 동시에 트래픽 처리 | 자원 효율 좋음, 장애 시 즉시 분산 / 데이터 동기화 복잡 |
| **Active-Standby** (Passive) | 대기 노드는 평소 쉬다가 장애 시 승격 | 단순 / 대기 자원 낭비, 전환 시간 필요 (RDS Multi-AZ) |

> **N+1 원칙**: 필요한 용량이 N대라면 N+1대(이상)로 운영해 한 대가 죽어도 감당할 수 있게 합니다. AZ가 2개라면 한 AZ가 통째로 장애 나도 나머지가 전체 트래픽을 받을 수 있는지 확인하세요.

## 2. 장애 전파를 막는 패턴 (Resilience Patterns)

분산 시스템에서는 **"외부 호출은 언제든 실패하거나 느려진다"** 를 전제로 설계합니다.

### 2-1. 타임아웃 (Timeout)
**가장 기본이자 가장 중요**합니다. 타임아웃이 없으면 느린 외부 서비스 하나가 스레드를 무한정 붙잡아 **서버 전체가 응답 불가**가 됩니다.

```
Tomcat 스레드 200개 → 결제 API가 30초씩 걸림 → 초당 10개 요청만 와도 20초 후 스레드 고갈
                   → 결제와 무관한 조회 API까지 모두 응답 불가 (연쇄 장애)
```
| 종류 | 의미 | 예시 값 |
|---|---|---|
| 연결 타임아웃 (Connect) | TCP 연결 수립까지 | 1~3초 |
| 읽기 타임아웃 (Read) | 응답을 기다리는 시간 | 호출 대상의 p99 × 여유 |
| DB 쿼리 타임아웃, 커넥션 풀 대기 타임아웃 | | HikariCP `connectionTimeout` |

> HTTP 클라이언트의 기본 타임아웃이 **무한대**인 경우가 많습니다. 모든 외부 호출에 명시적으로 설정하세요.

### 2-2. 재시도 (Retry)
일시적 오류(네트워크 순간 끊김, 503)는 다시 시도하면 성공할 수 있습니다.
- **지수 백오프 + 지터(Jitter)**: 100ms → 200ms → 400ms + 랜덤 → 모든 클라이언트가 동시에 재시도하는 **재시도 폭풍** 방지
- **멱등한 요청만 재시도** (GET, 멱등 키가 있는 결제 요청). POST 결제를 무작정 재시도하면 이중 결제
- 4xx(잘못된 요청)는 재시도해도 소용없음
- 재시도 횟수 제한 (보통 2~3회)

### 2-3. 서킷 브레이커 (Circuit Breaker)
**실패가 계속되는 서비스 호출을 일시적으로 차단**해 빠르게 실패하고(Fail Fast), 상대 서비스가 회복할 시간을 줍니다. 전기 차단기와 같습니다.

```
          실패율 50% 초과
 [CLOSED] ─────────────────> [OPEN]
 정상 호출                    호출 즉시 차단 → 폴백 응답
    ↑                           │ 일정 시간(예: 30초) 경과
    │ 시험 호출 성공              ↓
    └──────────────────── [HALF-OPEN]
                           일부 요청만 시험 통과
                           실패하면 다시 OPEN
```

```java
// Resilience4j + Spring Boot
@CircuitBreaker(name = "payment", fallbackMethod = "paymentFallback")
@Retry(name = "payment")
@TimeLimiter(name = "payment")   // (비동기 반환 타입에서 사용)
public CompletableFuture<PaymentResult> pay(PaymentRequest req) {
    return CompletableFuture.supplyAsync(() -> paymentClient.pay(req));
}

private CompletableFuture<PaymentResult> paymentFallback(PaymentRequest req, Throwable t) {
    // 대체 동작: "결제 대기" 상태로 저장 후 나중에 재처리, 사용자에게 안내
    return CompletableFuture.completedFuture(PaymentResult.pending(req.orderId()));
}
```
```yaml
resilience4j:
  circuitbreaker:
    instances:
      payment:
        sliding-window-size: 20
        failure-rate-threshold: 50
        slow-call-duration-threshold: 2s
        slow-call-rate-threshold: 50
        wait-duration-in-open-state: 30s
  retry:
    instances:
      payment:
        max-attempts: 3
        wait-duration: 200ms
        enable-exponential-backoff: true
```

### 2-4. 폴백 (Fallback)과 우아한 기능 저하 (Graceful Degradation)
핵심 기능은 지키고 부가 기능은 포기합니다.
| 상황 | 폴백 |
|---|---|
| 추천 서비스 장애 | 인기 상품 목록(캐시)으로 대체 |
| 리뷰 서비스 장애 | 상품 페이지는 보여 주고 리뷰 영역만 "잠시 후 다시 시도" |
| 결제 PG 장애 | "결제 대기" 처리 후 재시도 큐 |

### 2-5. 벌크헤드 (Bulkhead, 격벽)
배의 격벽처럼 **자원을 나눠** 한 곳의 문제가 전체로 번지지 않게 합니다.
- 외부 서비스별로 **스레드 풀·커넥션 풀 분리** (결제용 20개, 추천용 10개)
- 추천 서비스가 느려져도 결제 호출용 자원은 남아 있음

### 2-6. 레이트 리미팅 (Rate Limiting)과 백프레셔
- 클라이언트(IP, API 키)별 요청 수 제한 → 과도한 요청·공격으로부터 보호 (429 응답)
- 알고리즘: **토큰 버킷**, 슬라이딩 윈도우
- 위치: API 게이트웨이, Nginx `limit_req`, WAF, 애플리케이션(Bucket4j + Redis)

| 패턴 | 막는 것 |
|---|---|
| 타임아웃 | 무한 대기 |
| 재시도 | 일시적 오류 |
| 서킷 브레이커 | 계속 실패하는 대상으로의 호출, 연쇄 장애 |
| 폴백 | 전체 기능 실패 |
| 벌크헤드 | 자원 고갈의 전파 |
| 레이트 리미팅 | 과부하 |

## 3. 백업과 재해 복구 (DR, Disaster Recovery)

### RPO와 RTO
```
    마지막 백업          장애 발생            복구 완료
────────●───────────────────💥──────────────────●────────> 시간
        │←──── RPO ────────→│←────── RTO ───────→│
        (얼마나 데이터를 잃어도 되나)  (얼마나 빨리 복구해야 하나)
```
| 지표 | 의미 | 예 |
|---|---|---|
| **RPO** (Recovery Point Objective) | 허용 가능한 **데이터 손실 시간** | RPO 1시간 → 최소 1시간마다 백업 |
| **RTO** (Recovery Time Objective) | 허용 가능한 **복구 소요 시간** | RTO 30분 → 30분 안에 서비스 재개 |

### DR 전략 (비용·복구 속도 순)
| 전략 | 설명 | RTO / RPO | 비용 |
|---|---|---|---|
| **백업 & 복원** | 다른 리전에 백업만, 장애 시 인프라부터 새로 구축 (IaC 필수) | 시간~일 | **최저** |
| 파일럿 라이트 | 핵심(DB 복제)만 다른 리전에 켜 두고, 장애 시 나머지 생성 | 수십 분~시간 | 낮음 |
| 웜 스탠바이 | 축소된 전체 환경이 다른 리전에서 상시 실행 → 장애 시 확장 | 분 | 중간 |
| **멀티 사이트 Active-Active** | 여러 리전이 동시에 운영 | **거의 0** | **최고** |

### 백업 원칙
- **3-2-1 규칙**: 사본 3개, 서로 다른 매체 2종, 1개는 오프사이트(다른 리전·계정)
- RDS 자동 백업(PITR) + 스냅샷을 **다른 리전·계정으로 복사**
- S3 버전 관리 + 교차 리전 복제, Object Lock(랜섬웨어 대비)
- **복원 테스트를 정기적으로** — 복원해 본 적 없는 백업은 백업이 아닙니다.

## 4. 장애 대응 (Incident Response)

### 장애 발생 시 절차
```
1. 감지     알람, 사용자 문의 → 장애 선언, 담당자(Incident Commander) 지정
2. 전파     장애 채널 개설, 상태 페이지·관련 부서 공지
3. 완화     ★ 원인 분석보다 "서비스 복구"가 먼저
            - 최근 배포가 있었다면 → 즉시 롤백
            - 서버 증설, 트래픽 차단(레이트 리밋), 피처 플래그 OFF, 장애 서비스 격리(서킷 브레이커)
4. 복구 확인 지표(에러율, 응답 시간) 정상화 확인
5. 원인 분석 로그·트레이스·변경 이력 (CloudTrail, 배포 기록)
6. 포스트모템 재발 방지
```

> 장애의 상당수는 **변경(배포, 설정 변경)** 직후에 발생합니다. "최근에 무엇이 바뀌었나?"를 가장 먼저 확인하고, 롤백을 주저하지 마세요.

### 포스트모템 (Postmortem)
| 항목 | 내용 |
|---|---|
| 요약 | 무슨 일이, 언제, 얼마나 영향(사용자 수, 시간) |
| 타임라인 | 발생 → 감지 → 대응 → 복구 (분 단위) |
| 근본 원인 | **5 Whys**로 표면 원인 너머까지 |
| 잘된 점 / 아쉬운 점 | 감지가 빨랐나? 런북이 있었나? |
| **재발 방지 액션 아이템** | 담당자와 기한이 있는 구체적 작업 (알람 추가, 타임아웃 설정, 자동화) |

> **비난 없는 문화 (Blameless)**: "누가 실수했나"가 아니라 "**왜 시스템이 그 실수를 허용했나**"를 묻습니다. 사람을 탓하면 다음에는 장애를 숨기게 됩니다.

### 카오스 엔지니어링
운영과 비슷한 환경에서 **일부러 장애를 주입**(인스턴스 종료, 지연 추가, AZ 차단)해 시스템이 견디는지 검증합니다. (Netflix Chaos Monkey, AWS Fault Injection Service)

## 5. 부하 테스트와 용량 계획

### 테스트 종류
| 종류 | 목적 |
|---|---|
| **부하 테스트** (Load) | 예상 트래픽에서 목표 성능(p99, 에러율)을 만족하는가 |
| **스트레스 테스트** (Stress) | 한계점은 어디인가, 한계를 넘으면 어떻게 망가지는가 |
| 스파이크 테스트 | 갑작스러운 급증 (이벤트 오픈) |
| 내구성 테스트 (Soak) | 장시간(수 시간) 실행 시 메모리 누수·커넥션 누수 |

### 도구
**k6**(JavaScript 시나리오), **nGrinder**(국내 많이 사용), JMeter, Gatling, Locust

```javascript
// k6 예시: 1분 동안 가상 사용자 100명까지 증가, p95 500ms 미만 목표
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 100 },
    { duration: '3m', target: 100 },
    { duration: '1m', target: 0 },
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const res = http.get('https://stg-api.example.com/api/products?page=1');
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}
```

### 병목 찾기 순서
```
응답 시간 증가 / 처리량 정체
 → 앱 서버 CPU? (높으면 증설·코드 최적화)
 → Tomcat 스레드 / HikariCP 대기 (pending > 0이면 커넥션 부족 또는 느린 쿼리)
 → DB CPU, 느린 쿼리 로그, 락 대기 (인덱스, 쿼리 튜닝, 캐시, 읽기 복제본)
 → 외부 API 지연 (타임아웃, 캐시, 비동기화)
 → GC 시간 (힙 크기, 객체 생성 줄이기)
```

### 용량 계획
```
예상 피크 RPS 2,000, 서버 1대가 p99 목표 안에서 처리 가능한 RPS 300 (부하 테스트로 측정)
필요 대수 = 2000 / 300 ≈ 7대 → AZ 2개 중 하나가 장애여도 견디려면 AZ당 7대 = 14대 (또는 오토스케일링 최대치로 확보)
```
> 오토스케일링은 새 인스턴스가 뜨는 데 시간이 걸리므로, **급증이 예상되는 이벤트 전에는 미리 확장**(예약 스케일링)해 둡니다.

## 6. 면접 질문

1. **단일 장애점(SPOF)을 없애려면?**
   → 로드밸런서·애플리케이션·DB 등 모든 계층을 여러 가용 영역에 이중화하고, 서버를 무상태로 만들어 세션·파일을 외부 저장소로 분리합니다.
2. **서킷 브레이커란?**
   → 특정 외부 호출의 실패율이 임계치를 넘으면 일정 시간 호출을 차단해 즉시 실패·폴백 처리하고, 이후 일부 요청으로 회복 여부를 확인해 연쇄 장애를 막는 패턴입니다.
3. **타임아웃이 중요한 이유는?**
   → 타임아웃이 없으면 느린 외부 서비스가 스레드와 커넥션을 계속 점유해 자원이 고갈되고, 관련 없는 기능까지 응답하지 못하는 연쇄 장애가 발생하기 때문입니다.
4. **RPO와 RTO의 차이는?**
   → RPO는 장애 시 허용 가능한 데이터 손실 시간으로 백업 주기를 결정하고, RTO는 허용 가능한 복구 시간으로 DR 전략을 결정합니다.
5. **장애가 발생하면 어떻게 대응하나요?**
   → 먼저 영향을 파악하고 공유한 뒤, 원인 분석보다 롤백·증설·트래픽 차단 같은 완화 조치로 서비스를 복구하고, 이후 원인을 분석해 비난 없는 포스트모템으로 재발 방지 작업을 정합니다.

## 핵심 정리
- 고가용성 = SPOF 제거, 모든 계층 다중 AZ 이중화, 서버 무상태, N+1
- 회복 패턴: **타임아웃**(필수) / 재시도(백오프+지터, 멱등만) / 서킷 브레이커 / 폴백 / 벌크헤드 / 레이트 리밋
- DR: RPO(데이터 손실) · RTO(복구 시간), 백업&복원 → 파일럿 라이트 → 웜 스탠바이 → 멀티 사이트
- 백업은 복원 테스트까지, 3-2-1
- 장애 대응: 복구 먼저(롤백), 비난 없는 포스트모템
- 부하 테스트(k6, nGrinder)로 한계 측정 → 병목 분석 → 용량 계획
