# 01. 테스트의 종류와 원칙

> **학습 목표**
> - 테스트 코드를 작성하는 이유를 설명할 수 있다.
> - 단위·통합·E2E 테스트의 차이와 테스트 피라미드를 이해한다.
> - 좋은 테스트의 원칙(FIRST)과 Given-When-Then 구조를 적용할 수 있다.
> - 무엇을 테스트하고 무엇을 테스트하지 않을지 판단할 수 있다.

---

## 1. 왜 테스트 코드를 작성하는가?

| 이유 | 설명 |
|---|---|
| **회귀 방지** | 새 기능을 추가해도 기존 기능이 깨지지 않았는지 자동 확인 |
| **리팩터링 안전망** | 동작은 그대로 두고 구조를 바꿀 때 자신감 |
| 빠른 피드백 | 서버를 띄우고 Postman으로 클릭하는 대신 몇 초 안에 확인 |
| **살아 있는 문서** | 테스트 이름과 내용이 "이 코드는 이렇게 동작해야 한다"는 명세 |
| 설계 개선 | 테스트하기 어려운 코드 = 결합도가 높은 코드라는 신호 |

> "테스트를 작성할 시간이 없다"는 말은, 대개 **나중에 수동 테스트와 버그 수정에 더 많은 시간을 쓰게 된다**는 뜻입니다.

---

## 2. 테스트의 종류

| 종류 | 범위 | 속도 | 예 |
|---|---|---|---|
| **단위 테스트 (Unit)** | 클래스·메서드 하나, 외부 의존성은 가짜로 | **매우 빠름** (ms) | `Order.cancel()`, 할인 계산 로직 |
| **통합 테스트 (Integration)** | 여러 컴포넌트 + 실제 DB·스프링 컨텍스트 | 느림 (초) | Repository + MySQL, 서비스 + 트랜잭션 |
| **E2E 테스트 (End-to-End)** | 사용자 관점 전체 흐름 | **매우 느림** | 회원가입 → 로그인 → 주문 (브라우저·API) |
| 인수 테스트 (Acceptance) | 요구사항(시나리오) 단위 | 느림 | "회원은 장바구니 상품을 주문할 수 있다" |
| 계약 테스트 (Contract) | 서비스 간 API 약속 | 빠름 | Spring Cloud Contract, Pact |

### 테스트 피라미드
```
            ▲  E2E          적게 (느리고 깨지기 쉬움, 비쌈)
           ╱ ╲
          ╱통합╲         적당히 (DB, 스프링, 외부 연동 확인)
         ╱───────╲
        ╱  단위    ╲      많이 (빠르고 안정적, 원인 파악 쉬움)
       ╱───────────╲
```
> 백엔드 실무에서는 "단위 테스트만" 또는 "통합 테스트만"이 아니라, **도메인 로직은 단위 테스트로 촘촘히, Repository·API는 통합 테스트로** 확인하는 조합이 일반적입니다. 피라미드 대신 통합 테스트 비중을 높인 "테스트 트로피" 모델을 따르는 팀도 있습니다.

## 3. 좋은 테스트의 원칙: FIRST

| 원칙 | 의미 | 위반 예 |
|---|---|---|
| **F**ast | 빠르게 | 테스트마다 스프링 컨텍스트 새로 띄우기 |
| **I**ndependent | 서로 독립적 (순서 무관) | 앞 테스트가 저장한 데이터에 의존 |
| **R**epeatable | 언제 어디서나 같은 결과 | `LocalDateTime.now()`, 랜덤, 외부 API에 의존 |
| **S**elf-validating | 성공/실패를 스스로 판단 | `System.out.println` 으로 눈으로 확인 |
| **T**imely | 적시에 (프로덕션 코드와 함께) | 배포 후 몰아서 작성 |

## 4. 테스트 구조: Given-When-Then (AAA)

```java
@Test
@DisplayName("배송 전 주문은 취소할 수 있다")
void cancel_beforeShipping() {
    // given (Arrange): 준비
    Order order = Order.create("ORD-1", address, 10_000);

    // when (Act): 실행 — 보통 한 줄
    order.cancel();

    // then (Assert): 검증
    assertThat(order.getStatus()).isEqualTo(OrderStatus.CANCELED);
}
```
- **when은 한 가지 행동**만 → 테스트가 실패했을 때 원인이 명확
- 테스트 이름은 **구현이 아니라 행동(요구사항)** 으로: `cancel_beforeShipping` 보다 "배송 전 주문은 취소할 수 있다"
- 한 테스트는 **하나의 개념**을 검증 (assert가 여러 개여도 같은 개념이면 OK)

## 5. 무엇을 테스트할까?

| 우선순위 높음 | 우선순위 낮음 / 테스트 안 함 |
|---|---|
| **비즈니스 규칙** (할인, 상태 전이, 재고) | 단순 getter/setter |
| **경계값** (0, 최대값, 빈 목록, 날짜 경계) | 프레임워크 자체 기능 (JPA save가 저장되는지) |
| **예외 상황** (재고 부족, 권한 없음) | private 메서드 (public 메서드로 간접 검증) |
| 직접 작성한 쿼리 (`@Query`, QueryDSL) | 외부 라이브러리 내부 |
| 버그가 났던 곳 (**재발 방지 테스트**) | |

### 경계값 테스트 예
```
"수량은 1 이상 100 이하"
→ 0 (실패), 1 (성공), 100 (성공), 101 (실패)
```

## 6. 테스트하기 어려운 코드

```java
public class OrderService {
    public void order() {
        if (LocalDateTime.now().getHour() < 9) throw ...;    // ❌ 현재 시간 직접 사용
        new TossPaymentClient().pay(...);                     // ❌ 직접 생성한 외부 의존성
    }
}
```
| 문제 | 해결 |
|---|---|
| 현재 시간·랜덤 | `Clock`, 값을 파라미터로 주입 (`→ 03.테스트설계/04.동시성과시간테스트.md`) |
| 외부 의존성 직접 생성 | **DI** + 인터페이스 → 테스트에서 가짜로 교체 (`→ 04.테스트더블과Mockito.md`) |
| static 메서드·싱글톤 | 인스턴스 메서드 + 빈으로 |
| 너무 많은 책임 | 클래스 분리 |

## 7. 면접 질문

1. **테스트 코드를 작성하는 이유는?**
   → 변경 시 기존 기능이 깨지지 않았는지 자동으로 확인해 회귀를 막고, 리팩터링의 안전망이 되며, 코드의 동작을 설명하는 문서 역할을 하고, 테스트하기 쉬운 구조로 설계를 개선하기 때문입니다.
2. **단위 테스트와 통합 테스트의 차이는?**
   → 단위 테스트는 하나의 클래스나 메서드를 외부 의존성 없이 빠르게 검증하고, 통합 테스트는 DB·스프링 컨텍스트 등 여러 구성 요소를 함께 실행해 연동이 올바른지 검증합니다.
3. **좋은 테스트의 조건은?**
   → FIRST 원칙처럼 빠르고, 서로 독립적이며, 환경과 시간에 상관없이 같은 결과를 내고, 스스로 성공·실패를 판단하며, 행동 단위의 명확한 이름과 Given-When-Then 구조를 가져야 합니다.

---

## 핵심 정리
- 테스트 = **회귀 방지 + 리팩터링 안전망 + 문서**
- 피라미드: **단위 많이, 통합 적당히, E2E 적게**
- **FIRST** + **Given-When-Then**, 이름은 행동으로
- 비즈니스 규칙·경계값·예외·직접 작성한 쿼리를 우선 테스트
