# 04. 테스트 더블과 Mockito

> **학습 목표**
> - 테스트 더블의 종류(Dummy, Stub, Fake, Spy, Mock)를 구분할 수 있다.
> - Mockito로 스텁(`given/when`)과 행위 검증(`verify`)을 할 수 있다.
> - 상태 검증과 행위 검증의 차이를 이해하고, Mock 남용의 문제를 설명할 수 있다.
> - `ArgumentCaptor`, BDDMockito, 스프링의 `@MockitoBean`을 사용할 수 있다.

---

## 1. 테스트 더블이란?

테스트에서 **실제 객체를 대신하는 가짜 객체** (영화의 스턴트 더블에서 유래)
```
OrderService ──▶ PaymentClient (실제: 외부 결제 API — 느리고, 돈이 나가고, 결과가 매번 다름)
             ──▶ 테스트에서는 가짜로 교체
```

| 종류 | 설명 | 예 |
|---|---|---|
| **Dummy** | 전달만 하고 사용하지 않음 | 생성자 파라미터 채우기용 null 객체 |
| **Stub** | 미리 정한 값을 **반환** | `paymentClient.pay()` → 항상 성공 응답 |
| **Fake** | 실제처럼 동작하는 **간단한 구현** | 메모리 Map 기반 Repository, 인메모리 큐 |
| **Spy** | 실제 객체 + 호출 기록 | 실제 메서드를 실행하면서 몇 번 호출됐는지 기록 |
| **Mock** | 기대한 **호출이 일어났는지 검증** | `emailSender.send()`가 1번 호출됐는가? |

### Fake 예
```java
public class FakeOrderRepository implements OrderRepository {   // 인터페이스가 있다면
    private final Map<Long, Order> store = new HashMap<>();
    private long sequence = 0;

    @Override
    public Order save(Order order) {
        ReflectionTestUtils.setField(order, "id", ++sequence);
        store.put(order.getId(), order);
        return order;
    }

    @Override
    public Optional<Order> findById(Long id) { return Optional.ofNullable(store.get(id)); }
}
```
> Fake는 여러 테스트에서 재사용할 수 있고 구현에 덜 묶입니다. 외부 시스템(결제·메일·시계)의 Fake를 만들어 두면 테스트가 단단해집니다.

## 2. 상태 검증 vs 행위 검증

| | 상태 검증 (State) | 행위 검증 (Behavior) |
|---|---|---|
| 확인 대상 | **결과 값·상태** | **어떤 메서드가 어떻게 호출되었나** |
| 도구 | assertThat | Mockito `verify` |
| 예 | 주문 상태가 PAID인가 | `paymentClient.pay(10000)`이 호출되었나 |
| 리팩터링 내성 | **강함** | 약함 (내부 구현을 바꾸면 깨짐) |

> 가능하면 **상태 검증을 우선**하고, 반환값이 없는 외부 부수 효과(메일 발송, 메시지 발행, 결제 요청)에만 행위 검증을 씁니다.

## 3. Mockito 기본

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    OrderRepository orderRepository;

    @Mock
    PaymentClient paymentClient;

    @InjectMocks                              // 위 Mock들을 생성자로 주입해 실제 객체 생성
    OrderService orderService;

    @Test
    void 결제에_성공하면_주문이_PAID_상태가_된다() {
        // given
        Order order = Order.create("ORD-1", address, 10_000);
        when(orderRepository.findById(1L)).thenReturn(Optional.of(order));
        when(paymentClient.pay(any(PaymentRequest.class)))
                .thenReturn(new PaymentResult(true, "TX-1"));

        // when
        orderService.pay(1L);

        // then
        assertThat(order.getStatus()).isEqualTo(OrderStatus.PAID);          // 상태 검증
        verify(paymentClient, times(1)).pay(any(PaymentRequest.class));     // 행위 검증
    }
}
```

### 스텁 (Stubbing)
```java
when(repo.findById(1L)).thenReturn(Optional.of(order));
when(repo.findById(anyLong())).thenReturn(Optional.empty());
when(client.pay(any())).thenThrow(new PaymentException("한도 초과"));
when(client.pay(any())).thenReturn(fail, success);         // 첫 호출 fail, 두 번째 success (재시도 테스트)
when(repo.save(any(Order.class))).thenAnswer(inv -> inv.getArgument(0));   // 받은 인자 그대로 반환

doThrow(new RuntimeException()).when(emailSender).send(any());   // void 메서드
doNothing().when(emailSender).send(any());
```

### 인자 매처
| 매처 | 의미 |
|---|---|
| `any()`, `any(Order.class)` | 아무거나 |
| `anyLong()`, `anyString()` | 타입별 |
| `eq(1L)` | 정확히 이 값 |
| `argThat(r -> r.amount() > 0)` | 조건 |
> ⚠️ 매처와 실제 값을 섞을 수 없습니다: `when(client.pay(1L, any()))` ❌ → `pay(eq(1L), any())` ✅

### 행위 검증
```java
verify(emailSender).send(any());                    // 1번 호출
verify(emailSender, times(2)).send(any());
verify(emailSender, never()).send(any());           // 호출되지 않음
verify(emailSender, atLeastOnce()).send(any());
verifyNoMoreInteractions(emailSender);              // 남용 주의 (구현에 강하게 묶임)

InOrder inOrder = inOrder(stockService, paymentClient);
inOrder.verify(stockService).decrease(any(), anyInt());   // 재고 차감 후
inOrder.verify(paymentClient).pay(any());                 // 결제
```

## 4. ArgumentCaptor: 전달된 인자 검사

```java
@Captor
ArgumentCaptor<PaymentRequest> requestCaptor;

@Test
void 결제_요청에_할인된_금액이_전달된다() {
    orderService.pay(1L);

    verify(paymentClient).pay(requestCaptor.capture());
    PaymentRequest sent = requestCaptor.getValue();
    assertThat(sent.amount()).isEqualTo(9_000L);
    assertThat(sent.orderNo()).isEqualTo("ORD-1");
}
```

## 5. BDDMockito (Given-When-Then 스타일)

```java
import static org.mockito.BDDMockito.*;

given(orderRepository.findById(1L)).willReturn(Optional.of(order));     // when → given
given(paymentClient.pay(any())).willThrow(new PaymentException("실패"));

orderService.pay(1L);

then(emailSender).should(never()).send(any());                          // verify → then
```
> 기능은 같고 이름만 다릅니다. given 절에 `when(...)`이 등장하는 어색함이 없어 국내에서 많이 씁니다.

## 6. Spy

```java
@Spy
DiscountPolicy policy = new RateDiscountPolicy();

doReturn(500L).when(policy).discount(anyLong());   // spy는 when().thenReturn() 대신 doReturn (실제 메서드 호출 방지)
```
> Spy가 필요하다는 것은 클래스가 너무 많은 일을 한다는 신호일 수 있습니다. 가능하면 의존성을 분리하세요.

## 7. 스프링에서 Mock 빈: `@MockitoBean`

```java
@WebMvcTest(OrderController.class)
class OrderControllerTest {

    @MockitoBean                         // 스프링 컨텍스트의 빈을 Mock으로 교체
    OrderService orderService;
}
```
| 버전 | 애노테이션 |
|---|---|
| Boot 3.3 이하 | `@MockBean`, `@SpyBean` (`org.springframework.boot.test.mock.mockito`) |
| Spring 6.2 / Boot 3.4+ | **`@MockitoBean`, `@MockitoSpyBean`** (`org.springframework.test.context.bean.override.mockito`), `@MockBean`은 deprecated |
| Boot 4 | `@MockBean` **제거** → `@MockitoBean` 사용 |

> `@MockitoBean`의 조합이 테스트 클래스마다 다르면 **스프링 컨텍스트 캐시가 깨져** 테스트가 느려집니다. (`→ 02.스프링테스트/05.통합테스트와격리.md`)

## 8. Mock을 언제 쓰고 언제 쓰지 말까?

| ✅ Mock/Fake가 적합 | ❌ Mock이 부적합 |
|---|---|
| 외부 API (결제, 문자, 메일) | **도메인 객체** (Order, Money) → 실제 객체 사용 |
| 느리거나 비결정적인 것 (시간, 랜덤) | 값 객체, DTO |
| 아직 구현되지 않은 협력 객체 | **Repository를 모킹해 쿼리 검증** → 실제 DB 통합 테스트로 |
| 실패 상황 재현 (타임아웃, 5xx) | 내가 소유하지 않은 타입을 과하게 모킹 (JDBC Connection 등) |

### Mock 남용의 문제
```java
// 구현을 그대로 복사한 테스트 — 리팩터링하면 깨지지만 버그는 못 잡음
verify(repo).findById(1L);
verify(order).validate();
verify(order).changeStatus(PAID);
verify(repo).save(order);
```
- 테스트가 **"무엇을"이 아니라 "어떻게"** 를 검증 → 리팩터링 내성 ↓
- Mock이 실제와 다르게 동작해도 테스트는 통과 → **거짓 안심**
> "Don't mock what you don't own" — 외부 라이브러리는 직접 감싼 어댑터(`PaymentClient`)를 만들고, 그 어댑터를 모킹합니다.

### 참고: Mockito 5
- 기본 mock maker가 **inline** → `final` 클래스·메서드도 모킹 가능
- JDK 21+에서 동적 에이전트 로딩 경고가 나오면 Gradle 테스트 JVM에 Mockito를 `-javaagent`로 지정하는 것이 권장됩니다

## 9. 면접 질문

1. **Mock과 Stub의 차이는?**
   → Stub은 미리 정한 값을 반환해 테스트 대상이 동작할 수 있게 하는 데 목적이 있고(상태 검증), Mock은 기대한 메서드 호출이 실제로 일어났는지 검증하는 데 목적이 있습니다(행위 검증).
2. **Mock을 남용하면 어떤 문제가 있나요?**
   → 테스트가 내부 구현 방식에 묶여 리팩터링하면 쉽게 깨지고, Mock이 실제와 다르게 동작해도 통과해 실제 버그를 놓칠 수 있습니다. 도메인 객체는 실제 객체를, 외부 시스템만 Mock이나 Fake로 대체합니다.
3. **`@Mock`과 `@MockitoBean`의 차이는?**
   → @Mock은 스프링 없이 Mockito가 만드는 순수 Mock이고, @MockitoBean은 스프링 컨텍스트의 빈을 Mock으로 교체합니다. 단위 테스트는 @Mock이 훨씬 빠릅니다.

## 핵심 정리
- 테스트 더블: Dummy · **Stub(반환)** · **Fake(간단 구현)** · Spy · **Mock(호출 검증)**
- **상태 검증 우선**, 외부 부수 효과만 행위 검증
- Mockito: `when/given` 스텁, `verify/then` 검증, `ArgumentCaptor`
- 스프링: **`@MockitoBean`** (Boot 4에서 `@MockBean` 제거)
- 도메인은 실제 객체, **외부 시스템만** 가짜로
