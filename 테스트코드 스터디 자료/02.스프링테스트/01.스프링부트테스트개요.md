# 01. 스프링 부트 테스트 개요

> **학습 목표**
> - `@SpringBootTest`와 슬라이스 테스트(`@WebMvcTest`, `@DataJpaTest`)의 차이를 설명할 수 있다.
> - 테스트 종류별로 어떤 도구를 선택할지 판단할 수 있다.
> - 스프링 테스트 컨텍스트 캐싱의 원리를 이해한다.
> - Spring Boot 4의 테스트 모듈 변화를 안다.

---

## 1. 스프링 테스트 지원

```
spring-boot-starter-test
 ├─ JUnit Jupiter         테스트 실행
 ├─ AssertJ, Hamcrest     검증
 ├─ Mockito               Mock
 ├─ JsonPath, JSONassert  JSON 검증
 ├─ spring-test           스프링 TestContext, MockMvc
 └─ spring-boot-test      @SpringBootTest, 슬라이스 테스트
```
### Spring Boot 4: 테스트도 모듈화
```groovy
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    // Boot 4: 기능별 테스트 스타터 (슬라이스 애노테이션이 여기로 이동)
    testImplementation 'org.springframework.boot:spring-boot-starter-webmvc-test'     // @WebMvcTest
    testImplementation 'org.springframework.boot:spring-boot-starter-data-jpa-test'   // @DataJpaTest
}
```
| 애노테이션 | Boot 3 패키지 | Boot 4 패키지 |
|---|---|---|
| `@WebMvcTest`, `@AutoConfigureMockMvc` | `org.springframework.boot.test.autoconfigure.web.servlet` | `org.springframework.boot.webmvc.test.autoconfigure` |
| `@DataJpaTest` | `org.springframework.boot.test.autoconfigure.orm.jpa` | `org.springframework.boot.data.jpa.test.autoconfigure` |
| `@SpringBootTest` | `org.springframework.boot.test.context` | 동일 |
> 업그레이드 시 import만 바꾸면 대부분 그대로 동작합니다. 이 자료의 코드는 import를 생략하고 애노테이션 이름으로 설명합니다.

## 2. 테스트 도구 선택표

| 테스트 대상 | 도구 | 스프링 컨텍스트 | 속도 |
|---|---|---|---|
| 도메인 로직 (Order, Money) | **JUnit + AssertJ** | ❌ | ⚡ 가장 빠름 |
| 서비스 로직 (협력 객체 Mock) | **JUnit + Mockito** (`@ExtendWith(MockitoExtension.class)`) | ❌ | ⚡ |
| 컨트롤러 (요청·응답·검증·예외) | **`@WebMvcTest`** + MockMvc | 웹 계층만 | 빠름 |
| Repository (쿼리) | **`@DataJpaTest`** + Testcontainers | JPA만 | 보통 |
| 전체 흐름 (서비스 + 트랜잭션 + DB) | **`@SpringBootTest`** | 전체 | 느림 |
| 외부 API 클라이언트 | `@RestClientTest` + MockRestServiceServer, WireMock | 클라이언트만 | 빠름 |

> 원칙: **필요한 만큼만 띄운다.** 서비스 로직 하나 확인하려고 `@SpringBootTest`를 쓰면 테스트가 수십 배 느려집니다.

## 3. `@SpringBootTest`

```java
@SpringBootTest
class OrderServiceIntegrationTest {

    @Autowired OrderService orderService;
    @Autowired OrderRepository orderRepository;

    @Test
    void 주문을_생성하면_DB에_저장된다() {
        Long id = orderService.create(new OrderCreateRequest(...));
        assertThat(orderRepository.findById(id)).isPresent();
    }
}
```
| 옵션 | 의미 |
|---|---|
| `webEnvironment = MOCK` (기본) | 서블릿 컨테이너 없이 Mock 환경 → MockMvc로 요청 (`@AutoConfigureMockMvc`) |
| `webEnvironment = RANDOM_PORT` | **실제 톰캣을 랜덤 포트로** 띄움 → `RestTestClient`, `TestRestTemplate`으로 진짜 HTTP 요청 |
| `properties = "payment.timeout=1s"` | 테스트용 설정 덮어쓰기 |
| `classes = ...` | 특정 설정만 로드 |

## 4. 슬라이스 테스트

필요한 계층의 빈만 등록해 빠르게 테스트합니다.

| 애노테이션 | 등록되는 빈 | 등록되지 않는 빈 |
|---|---|---|
| `@WebMvcTest(XController.class)` | Controller, ControllerAdvice, Filter, WebMvcConfigurer, Converter, Validator, **Spring Security 설정** | Service, Repository → `@MockitoBean`으로 |
| `@DataJpaTest` | Repository, EntityManager, DataSource, Flyway | Service, Controller |
| `@JsonTest` | Jackson 설정 | |
| `@RestClientTest` | RestClient.Builder, MockRestServiceServer | |
| `@DataRedisTest` | Redis Repository, RedisTemplate | |

## 5. 테스트 컨텍스트 캐싱 ★

스프링은 **같은 설정의 테스트 클래스끼리 ApplicationContext를 재사용**합니다.
```
OrderServiceTest   @SpringBootTest                    → 컨텍스트 A 생성 (10초)
MemberServiceTest  @SpringBootTest                    → 컨텍스트 A 재사용 (0초)
PaymentServiceTest @SpringBootTest + @MockitoBean(PaymentClient) → 설정이 다름 → 컨텍스트 B 새로 생성 (10초)
CouponServiceTest  @SpringBootTest + @ActiveProfiles("x")       → 컨텍스트 C 새로 생성 (10초)
```
**캐시 키**가 달라지는 원인: `@MockitoBean` 조합, `@ActiveProfiles`, `properties`, `@TestPropertySource`, `@Import`, `@DirtiesContext`
### 대응
```java
@SpringBootTest
@ActiveProfiles("test")
public abstract class IntegrationTestSupport {          // 공통 부모 클래스
    @MockitoBean protected PaymentClient paymentClient;  // 외부 의존 Mock을 한곳에 모음
    @MockitoBean protected SmsSender smsSender;
}

class OrderServiceTest extends IntegrationTestSupport { ... }
class MemberServiceTest extends IntegrationTestSupport { ... }   // 같은 컨텍스트 재사용
```
- `@DirtiesContext`는 컨텍스트를 버리게 하므로 **최대한 피하기**
- 로그 `org.springframework.test.context.cache: debug`로 캐시 적중 확인

## 6. 테스트용 설정

```
src/test/resources/
 ├── application-test.yml     # 테스트 프로필 설정
 └── sql/                     # 테스트 데이터 스크립트
```
```yaml
# application-test.yml
spring:
  jpa:
    hibernate:
      ddl-auto: validate      # Flyway로 스키마 생성 후 검증 (운영과 동일 스키마)
    properties:
      hibernate:
        format_sql: true
logging:
  level:
    org.hibernate.SQL: debug
```
```java
@TestConfiguration                       // 테스트에서만 쓰는 빈
public class FixedClockConfig {
    @Bean @Primary
    Clock testClock() {
        return Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneId.of("Asia/Seoul"));
    }
}
```

## 7. 면접 질문

1. **`@SpringBootTest`와 `@WebMvcTest`의 차이는?**
   → SpringBootTest는 애플리케이션 전체 빈을 등록하는 통합 테스트이고, WebMvcTest는 컨트롤러·필터 등 웹 계층 빈만 등록하는 슬라이스 테스트로, 서비스는 Mock으로 대체해 빠르게 컨트롤러만 검증합니다.
2. **테스트가 느린 이유와 개선 방법은?**
   → 테스트마다 MockitoBean이나 프로필 설정이 달라 스프링 컨텍스트가 매번 새로 만들어지는 경우가 많습니다. 공통 부모 클래스로 설정을 통일해 컨텍스트 캐시를 재사용하고, 단위 테스트로 충분한 것은 스프링 없이 작성합니다.
3. **어떤 테스트를 어떤 도구로 작성하나요?**
   → 도메인 로직은 순수 단위 테스트, 서비스 로직은 Mockito 단위 테스트나 통합 테스트, 컨트롤러는 WebMvcTest, 쿼리는 DataJpaTest와 Testcontainers, 전체 흐름은 SpringBootTest로 작성합니다.

---

## 핵심 정리
- **필요한 만큼만 띄우기**: 단위 → 슬라이스(`@WebMvcTest`, `@DataJpaTest`) → `@SpringBootTest`
- `RANDOM_PORT` = 실제 서버, `MOCK` = MockMvc
- **컨텍스트 캐싱**: MockitoBean·프로필 조합을 통일 (공통 부모 클래스), `@DirtiesContext` 지양
- Boot 4: `spring-boot-starter-webmvc-test` 등 **기능별 테스트 스타터 + 패키지 변경**
