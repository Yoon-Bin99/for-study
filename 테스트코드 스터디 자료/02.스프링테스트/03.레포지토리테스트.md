# 03. 레포지토리 테스트 (@DataJpaTest)

> **학습 목표**
> - `@DataJpaTest`의 동작(트랜잭션 롤백, 내장 DB 교체)을 이해한다.
> - 무엇을 테스트해야 하는지(직접 작성한 쿼리) 구분할 수 있다.
> - 영속성 컨텍스트 때문에 테스트가 거짓으로 통과하는 문제를 `flush/clear`로 막을 수 있다.
> - 테스트 데이터를 준비하는 방법(직접 저장, `@Sql`, 픽스처)을 비교할 수 있다.

---

## 1. `@DataJpaTest`

```java
@DataJpaTest
class OrderRepositoryTest {

    @Autowired OrderRepository orderRepository;
    @Autowired MemberRepository memberRepository;
    @Autowired EntityManager em;
}
```
| 특징 | 설명 |
|---|---|
| 로드되는 빈 | JPA 관련만 (Repository, EntityManager, DataSource, Flyway/Liquibase) |
| **트랜잭션** | 각 테스트가 `@Transactional` → 끝나면 **자동 롤백** |
| **DB 교체** | 기본적으로 **내장 DB(H2)로 교체**하려고 시도 |
| SQL 로그 | `spring.jpa.show-sql=true` 기본 |
| QueryDSL | `JPAQueryFactory` 빈은 등록되지 않음 → `@Import(QuerydslConfig.class)` |

### H2 vs 실제 DB
```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)   // 내장 DB로 바꾸지 마라
class OrderRepositoryTest { ... }
```
| H2 (MySQL 모드) | 실제 DB (Testcontainers) |
|---|---|
| 빠르고 설치 불필요 | Docker 필요, 처음 몇 초 소요 |
| **방언 차이**: 네이티브 쿼리, JSON 컬럼, 함수, 락 동작, 대소문자, 인덱스 힌트가 다를 수 있음 | **운영과 동일** |
| "H2에선 통과, 운영 MySQL에서 실패" 위험 | 신뢰도 높음 |
> 권장: **Testcontainers로 운영과 같은 DB**를 사용 (`→ 04.Testcontainers.md`). Boot 3.1+에서 `@ServiceConnection`을 쓰면 `@AutoConfigureTestDatabase` 설정 없이도 컨테이너 DB를 사용합니다.

## 2. 무엇을 테스트할까?

| 테스트 O | 테스트 X |
|---|---|
| **직접 작성한 쿼리**: `@Query`, QueryDSL, 네이티브 쿼리 | `save`, `findById` 같은 기본 메서드 (Spring Data가 이미 검증) |
| 복잡한 쿼리 메서드 (`findTop10ByStatusAndCreatedAtAfter...`) | 단순 `findByEmail` (원하면 가볍게) |
| fetch join, 페이징, 정렬, 동적 조건 | |
| **N+1이 해결되었는지** (쿼리 수) | |
| 매핑 (값 타입, enum, 연관관계, 제약 조건) | |

## 3. 예제

```java
@DataJpaTest
@Import(QuerydslConfig.class)
class OrderQueryRepositoryTest {

    @Autowired OrderRepository orderRepository;
    @Autowired MemberRepository memberRepository;
    @Autowired EntityManager em;
    @Autowired JPAQueryFactory queryFactory;

    OrderQueryRepository orderQueryRepository;

    @BeforeEach
    void setUp() {
        orderQueryRepository = new OrderQueryRepository(queryFactory);
    }

    @Test
    void 상태와_회원이름으로_주문을_검색한다() {
        // given
        Member kim = memberRepository.save(Member.create("kim", "kim@shop.com"));
        Member lee = memberRepository.save(Member.create("lee", "lee@shop.com"));
        orderRepository.save(Order.create(kim, OrderStatus.PAID, 10_000));
        orderRepository.save(Order.create(kim, OrderStatus.CANCELED, 20_000));
        orderRepository.save(Order.create(lee, OrderStatus.PAID, 30_000));
        em.flush();
        em.clear();                                        // ★ 1차 캐시 비우기

        // when
        List<Order> result = orderQueryRepository.search(
                new OrderSearchCondition(OrderStatus.PAID, "ki", null, null));

        // then
        assertThat(result)
                .extracting(Order::getTotalPrice)
                .containsExactly(10_000L);
    }

    @Test
    void 조건이_모두_없으면_전체를_조회한다() { ... }

    @Test
    void 기간_경계값_종료일_당일_주문도_포함한다() { ... }   // 날짜 경계는 꼭 테스트
}
```

## 4. ★ 영속성 컨텍스트 함정: flush와 clear

```java
@Test
void 주문_상태_변경() {
    Order order = orderRepository.save(Order.create(kim, OrderStatus.PAID, 10_000));

    order.cancel();

    Order found = orderRepository.findById(order.getId()).orElseThrow();
    assertThat(found.getStatus()).isEqualTo(OrderStatus.CANCELED);   // 통과... 하지만 DB에 UPDATE가 나갔을까?
}
```
- `findById`는 **1차 캐시**에서 같은 객체를 꺼내므로, DB에 반영되지 않았어도(매핑 오류가 있어도) 통과합니다
- 롤백되는 테스트에서는 **flush조차 일어나지 않아** INSERT·UPDATE SQL이 아예 실행되지 않을 수도 있습니다

```java
order.cancel();
em.flush();     // SQL을 DB로 보냄 (제약 조건·매핑 오류가 여기서 드러남)
em.clear();     // 1차 캐시 비움 → 다음 조회는 진짜 DB에서

Order found = orderRepository.findById(order.getId()).orElseThrow();   // SELECT 실행
```
> 지연 로딩·fetch join 테스트도 `clear()` 없이 하면 이미 캐시에 있는 엔티티 때문에 **N+1이 재현되지 않습니다.**

### 쿼리 수 검증 (N+1 방지 테스트)
```java
@Test
void 주문_목록과_회원을_한_번의_쿼리로_조회한다() {
    // given: 주문 3건 (회원 3명) 저장 후 flush, clear
    Statistics stats = em.getEntityManagerFactory().unwrap(SessionFactory.class).getStatistics();
    stats.setStatisticsEnabled(true);
    stats.clear();

    List<Order> orders = orderRepository.findAllWithMember(OrderStatus.PAID);
    orders.forEach(o -> o.getMember().getName());       // 지연 로딩 유발

    assertThat(stats.getPrepareStatementCount()).isEqualTo(1);
}
```

## 5. 테스트 데이터 준비

| 방법 | 장점 | 단점 |
|---|---|---|
| **테스트 안에서 직접 저장** | 테스트만 보고 이해 가능 (given이 명확) | 코드가 길어짐 |
| `@Sql("/sql/orders.sql")` | 대량·복잡한 데이터 | 데이터가 테스트 밖에 있어 **파악이 어려움**, 스키마 변경 시 깨짐 |
| **픽스처(Fixture) 클래스** | 재사용, 기본값 + 필요한 값만 변경 | 공용 픽스처에 의존이 커지면 위험 |
| `data.sql` (전역) | | 모든 테스트가 공유 → 독립성 ↓ (비권장) |

```java
public class OrderFixture {
    public static Order paidOrder(Member member) {
        return Order.create(member, OrderStatus.PAID, 10_000);
    }
    public static Order order(Member member, OrderStatus status, long price) {
        return Order.create(member, status, price);
    }
}
```
> 테스트에 **필요한 값은 테스트 안에서 드러나게** 하세요. `paidOrder()`만 보고 금액이 10,000원인지 알 수 없다면, 금액을 검증하는 테스트에서는 금액을 명시적으로 넘깁니다.

## 6. 면접 질문

1. **`@DataJpaTest`의 특징은?**
   → JPA 관련 빈만 로드하는 슬라이스 테스트로 각 테스트가 트랜잭션 안에서 실행되고 끝나면 롤백되며, 기본적으로 내장 DB로 교체를 시도합니다.
2. **H2 대신 실제 DB로 테스트하는 이유는?**
   → 네이티브 쿼리, 함수, 락 동작, JSON 타입 등 DB마다 문법과 동작이 달라 H2에서 통과해도 운영 DB에서 실패할 수 있기 때문에, Testcontainers로 운영과 같은 DB에서 테스트합니다.
3. **레포지토리 테스트에서 `flush`와 `clear`를 하는 이유는?**
   → 저장 후 같은 영속성 컨텍스트에서 조회하면 1차 캐시의 객체가 반환되어 실제 SQL과 매핑을 검증하지 못하므로, flush로 SQL을 실행하고 clear로 캐시를 비운 뒤 DB에서 다시 조회합니다.

---

## 핵심 정리
- `@DataJpaTest` = JPA 빈만 + **테스트마다 롤백**
- 테스트 대상은 **직접 작성한 쿼리** (`@Query`, QueryDSL), N+1 해결 여부
- H2보다 **Testcontainers 실제 DB**
- 저장 후 검증 전 **`em.flush(); em.clear();`**
- 테스트 데이터는 **테스트 안에서 드러나게** (픽스처는 보조)
