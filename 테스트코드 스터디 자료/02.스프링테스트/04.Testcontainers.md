# 04. Testcontainers

> **학습 목표**
> - Testcontainers가 해결하는 문제와 동작 방식을 이해한다.
> - `@ServiceConnection`으로 MySQL·Redis·Kafka 컨테이너를 스프링 테스트에 연결할 수 있다.
> - 컨테이너를 여러 테스트에서 공유해 속도를 높일 수 있다.
> - Testcontainers 2.0의 변경 사항을 안다.

---

## 1. Testcontainers란?

테스트 코드에서 **Docker 컨테이너를 띄워** 실제 DB·Redis·Kafka 등을 사용하고, 테스트가 끝나면 자동으로 정리하는 라이브러리입니다.
```
테스트 시작
  → Docker로 mysql:8.4 컨테이너 실행 (랜덤 포트)
  → 준비될 때까지 대기 (Wait Strategy)
  → 스프링에 접속 정보 주입
  → 테스트 실행
테스트 끝 → 컨테이너 자동 삭제 (Ryuk 컨테이너가 정리)
```
| 대안 | 문제 |
|---|---|
| H2·임베디드 Redis | 운영과 다른 동작 |
| 공용 개발 DB | 데이터 충돌, 동시 실행 불가, 테스트 독립성 ✗ |
| 로컬에 직접 설치 | 사람·CI마다 버전이 다름 |
| **Testcontainers** | **운영과 같은 이미지, 매번 깨끗한 환경, CI에서도 동일** (Docker만 있으면 됨) |

## 2. 의존성 (Testcontainers 2.x)

```groovy
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-testcontainers'
    testImplementation 'org.testcontainers:testcontainers-junit-jupiter'
    testImplementation 'org.testcontainers:testcontainers-mysql'
    testImplementation 'org.testcontainers:testcontainers-kafka'
}
```
### 1.x → 2.0 주요 변경 (2025)
| 항목 | 1.x | 2.x |
|---|---|---|
| 모듈 이름 | `org.testcontainers:mysql`, `junit-jupiter` | **`testcontainers-` 접두사**: `testcontainers-mysql`, `testcontainers-junit-jupiter` |
| 패키지 | `org.testcontainers.containers.MySQLContainer` | **`org.testcontainers.mysql.MySQLContainer`** (모듈별 패키지, 옛 클래스는 deprecated) |
| 제네릭 | `MySQLContainer<?>` | `MySQLContainer` (제네릭 제거) |
| JUnit 4 | 지원 | **제거** (JUnit 5+ 필요) |
> 블로그 예제의 `new MySQLContainer<>("mysql:8.0")`와 `org.testcontainers.containers` import는 1.x 문법입니다. 버전은 Spring Boot가 관리하므로 따로 적지 않아도 됩니다.

## 3. 기본 사용: `@ServiceConnection` (Boot 3.1+)

```java
@DataJpaTest
@Testcontainers
class OrderRepositoryTest {

    @Container
    @ServiceConnection                 // 컨테이너의 접속 정보를 spring.datasource.*에 자동 연결
    static MySQLContainer mysql = new MySQLContainer("mysql:8.4");

    @Autowired OrderRepository orderRepository;

    @Test
    void 저장과_조회() { ... }
}
```
- `static` 필드 → 클래스의 모든 테스트가 **하나의 컨테이너 공유** (인스턴스 필드면 테스트마다 새로 띄움)
- `@ServiceConnection` 이전 방식: `@DynamicPropertySource`로 `spring.datasource.url` 등을 직접 등록
```java
@DynamicPropertySource
static void props(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", mysql::getJdbcUrl);
    registry.add("spring.datasource.username", mysql::getUsername);
    registry.add("spring.datasource.password", mysql::getPassword);
}
```

### 지원되는 서비스 (일부)
| 컨테이너 | 연결되는 설정 |
|---|---|
| `MySQLContainer`, `PostgreSQLContainer` | DataSource (JDBC), R2DBC |
| `KafkaContainer` (`org.testcontainers.kafka`) | `spring.kafka.bootstrap-servers` |
| `RedisContainer` (com.redis.testcontainers) 또는 `GenericContainer("redis:7")` + `@ServiceConnection(name = "redis")` | Redis |
| `RabbitMQContainer`, `ElasticsearchContainer`, `MongoDBContainer` | 각 클라이언트 |

## 4. 컨테이너 공유: 모든 테스트 클래스에서 한 번만

클래스마다 컨테이너를 띄우면 테스트 클래스 수 × 수 초가 걸립니다.

### 방법 ① `@TestConfiguration` + `@Bean` (권장)
```java
@TestConfiguration(proxyBeanMethods = false)
public class TestcontainersConfig {

    @Bean
    @ServiceConnection
    MySQLContainer mysqlContainer() {
        return new MySQLContainer("mysql:8.4");
    }

    @Bean
    @ServiceConnection
    KafkaContainer kafkaContainer() {
        return new KafkaContainer("apache/kafka-native:4.0.0");
    }

    @Bean
    @ServiceConnection(name = "redis")
    GenericContainer<?> redisContainer() {
        return new GenericContainer<>("redis:7.4").withExposedPorts(6379);
    }
}
```
```java
@SpringBootTest
@Import(TestcontainersConfig.class)
public abstract class IntegrationTestSupport { }
```
→ 컨테이너가 **스프링 빈**이 되어 컨텍스트 캐시와 함께 재사용되고, 컨텍스트가 종료될 때 정리됩니다.

### 방법 ② static 싱글톤 컨테이너
```java
public abstract class IntegrationTestSupport {
    static final MySQLContainer MYSQL = new MySQLContainer("mysql:8.4");
    static { MYSQL.start(); }           // JVM 종료 시 Ryuk가 정리

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url", MYSQL::getJdbcUrl);
        r.add("spring.datasource.username", MYSQL::getUsername);
        r.add("spring.datasource.password", MYSQL::getPassword);
    }
}
```

### 로컬 개발에도 활용: `bootTestRun`
```java
// src/test/java
public class TestApplication {
    public static void main(String[] args) {
        SpringApplication.from(Application::main)
                .with(TestcontainersConfig.class)
                .run(args);
    }
}
```
→ `./gradlew bootTestRun` 하면 **DB·Redis·Kafka가 자동으로 뜬 상태**로 애플리케이션 실행 (docker-compose 없이). Boot는 `spring-boot-docker-compose`로 `compose.yaml`을 자동 실행하는 방법도 제공합니다.

## 5. 속도와 안정성 팁

| 팁 | 설명 |
|---|---|
| 컨테이너 **공유** | 위의 `@TestConfiguration` / 싱글톤 |
| **이미지 버전 고정** | `mysql:8.4` (latest ✗) — 재현성 |
| 가벼운 이미지 | `apache/kafka-native`, `postgres:16-alpine` |
| 재사용 (로컬 전용) | `~/.testcontainers.properties`에 `testcontainers.reuse.enable=true` + `.withReuse(true)` → 테스트 실행 간 컨테이너 유지 (CI에선 끔) |
| 스키마 | Flyway 마이그레이션이 컨테이너에 자동 적용 → **운영과 같은 스키마** |
| 데이터 격리 | 컨테이너를 공유하므로 테스트 간 데이터 정리 필요 (`→ 05.통합테스트와격리.md`) |
| CI | GitHub Actions `ubuntu-latest`에는 Docker가 있어 바로 동작 |

## 6. 면접 질문

1. **Testcontainers를 쓰는 이유는?**
   → 테스트에서 운영과 같은 DB·Redis·Kafka 이미지를 Docker로 띄워 방언 차이 없이 검증할 수 있고, 매번 깨끗한 환경을 만들어 독립적이며 로컬과 CI에서 같은 결과를 얻을 수 있기 때문입니다.
2. **`@ServiceConnection`의 역할은?**
   → 컨테이너의 호스트, 포트, 계정 같은 접속 정보를 스프링 부트의 연결 설정으로 자동 등록해 DynamicPropertySource를 직접 작성하지 않아도 되게 합니다.
3. **Testcontainers 테스트가 느릴 때 개선 방법은?**
   → 컨테이너를 static이나 스프링 빈으로 만들어 여러 테스트 클래스가 공유하게 하고, 스프링 컨텍스트 설정을 통일해 캐시를 재사용하며, 가벼운 이미지를 사용합니다.

---

## 핵심 정리
- Testcontainers = 테스트용 **실제 인프라를 Docker로**, 끝나면 자동 정리
- **`@ServiceConnection`** 으로 접속 정보 자동 연결 (Boot 3.1+)
- **컨테이너 공유**: `@TestConfiguration` + `@Bean` 또는 static 싱글톤
- 2.x: `testcontainers-*` 모듈 이름, `org.testcontainers.<모듈>` 패키지, 제네릭 제거, JUnit 4 제거
