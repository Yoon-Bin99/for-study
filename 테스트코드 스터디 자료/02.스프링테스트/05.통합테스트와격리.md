# 05. 통합 테스트와 데이터 격리

> **학습 목표**
> - 서비스 통합 테스트를 작성하고, 외부 시스템을 적절히 대체할 수 있다.
> - 테스트 `@Transactional` 롤백의 장점과 **함정**을 설명할 수 있다.
> - 테스트 간 데이터 격리 방법(롤백, truncate, 테스트별 데이터)을 비교할 수 있다.
> - 외부 HTTP API를 WireMock·MockRestServiceServer로 테스트할 수 있다.

---

## 1. 서비스 통합 테스트

```java
class OrderServiceTest extends IntegrationTestSupport {   // @SpringBootTest + Testcontainers + 공통 MockitoBean

    @Autowired OrderService orderService;
    @Autowired ProductRepository productRepository;
    @Autowired OrderRepository orderRepository;

    @Test
    void 주문하면_재고가_차감되고_주문이_저장된다() {
        // given
        Product product = productRepository.save(Product.create("키보드", 50_000, 10));
        given(paymentClient.pay(any())).willReturn(PaymentResult.success("TX-1"));   // 외부만 Mock

        // when
        Long orderId = orderService.order(new OrderCreateRequest(product.getId(), 3, "서울"));

        // then
        assertThat(productRepository.findById(product.getId()).orElseThrow().getStock()).isEqualTo(7);
        assertThat(orderRepository.findById(orderId).orElseThrow().getStatus()).isEqualTo(OrderStatus.PAID);
    }

    @Test
    void 결제에_실패하면_재고가_원복된다() {
        Product product = productRepository.save(Product.create("키보드", 50_000, 10));
        given(paymentClient.pay(any())).willThrow(new PaymentException("한도 초과"));

        assertThatThrownBy(() -> orderService.order(new OrderCreateRequest(product.getId(), 3, "서울")))
                .isInstanceOf(PaymentException.class);

        assertThat(productRepository.findById(product.getId()).orElseThrow().getStock()).isEqualTo(10);   // 롤백 확인
    }
}
```
> 위 두 번째 테스트는 **테스트 클래스에 `@Transactional`이 없어야** 의미가 있습니다. 서비스의 트랜잭션이 실제로 커밋·롤백되는지 확인하는 테스트이기 때문입니다.

## 2. 테스트의 `@Transactional`: 편리하지만 위험하다 ★

```java
@SpringBootTest
@Transactional        // 각 테스트 끝나면 롤백 → 데이터 정리가 자동
class OrderServiceTest { ... }
```
### 장점
- 테스트마다 데이터가 자동으로 지워짐 → 격리 쉬움

### 함정
| 함정 | 설명 |
|---|---|
| **운영과 다른 트랜잭션 범위** | 테스트 트랜잭션이 서비스 트랜잭션을 감싸서, 서비스에 `@Transactional`이 **빠져 있어도** 테스트는 통과 |
| **지연 로딩 예외를 못 잡음** | 테스트 트랜잭션 안이라 영속성 컨텍스트가 열려 있어 `LazyInitializationException`이 재현되지 않음 |
| **커밋 시점 동작 누락** | flush가 안 일어나 제약 조건 위반을 놓침, `@TransactionalEventListener(AFTER_COMMIT)`가 실행되지 않음 |
| REQUIRES_NEW, 다른 스레드 | 별도 트랜잭션·스레드(`@Async`, 동시성 테스트, RANDOM_PORT 요청)는 롤백되지 않음 → 데이터가 남음 |
| 변경 감지 검증이 거짓 통과 | 1차 캐시 때문에 (`→ 03.레포지토리테스트.md`) |

```java
// 서비스에 @Transactional을 깜빡한 경우
public void changeName(Long id, String name) {
    Member m = memberRepository.findById(id).orElseThrow();
    m.changeName(name);           // 운영: 트랜잭션 없음 → 변경 감지 X → DB 반영 안 됨 (버그)
}
// 테스트 @Transactional 안에서는 같은 영속성 컨텍스트라 이름이 바뀐 것처럼 보여 통과
```
> 결론: `@DataJpaTest`의 롤백은 괜찮지만, **서비스 통합 테스트는 `@Transactional` 없이 실제처럼 커밋**하고, 데이터는 별도로 정리하는 방식이 더 안전합니다.

## 3. 데이터 격리 방법

| 방법 | 설명 | 장단점 |
|---|---|---|
| 테스트 `@Transactional` 롤백 | 자동 롤백 | 편리, 위의 함정 |
| **`@AfterEach` 에서 truncate** | 모든 테이블 비우기 | 실제 커밋 동작 검증, 구현 필요 |
| `deleteAllInBatch()` | Repository별 삭제 | FK 순서 신경 써야 함 |
| `@Sql(executionPhase = AFTER_TEST_METHOD)` | 정리 SQL 실행 | 테이블 추가 시 스크립트 수정 |
| 테스트별 고유 데이터 | 이메일·주문번호에 UUID | 정리 없이도 충돌 없음 (보조 수단) |

### 공통 DB 정리기
```java
@Component
public class DatabaseCleaner {

    @PersistenceContext
    private EntityManager em;

    private List<String> tableNames;

    @PostConstruct
    void init() {
        tableNames = em.getMetamodel().getEntities().stream()
                .map(e -> e.getJavaType().getAnnotation(Table.class))
                .filter(Objects::nonNull)
                .map(Table::name)
                .toList();
    }

    @Transactional
    public void clear() {
        em.flush();
        em.createNativeQuery("SET FOREIGN_KEY_CHECKS = 0").executeUpdate();     // MySQL
        for (String table : tableNames) {
            em.createNativeQuery("TRUNCATE TABLE " + table).executeUpdate();
        }
        em.createNativeQuery("SET FOREIGN_KEY_CHECKS = 1").executeUpdate();
    }
}
```
```java
@SpringBootTest
@Import({TestcontainersConfig.class, DatabaseCleaner.class})
public abstract class IntegrationTestSupport {
    @Autowired DatabaseCleaner databaseCleaner;

    @AfterEach
    void cleanUp() { databaseCleaner.clear(); }
}
```
> `@Table`이 없는 엔티티는 기본 테이블 이름 규칙(카멜 → 스네이크)을 적용하거나, `information_schema`에서 테이블 목록을 읽도록 확장하세요. PostgreSQL은 `TRUNCATE ... RESTART IDENTITY CASCADE`를 사용합니다.

## 4. 외부 API 테스트

### 대체 방법 비교
| 방법 | 검증 범위 | 용도 |
|---|---|---|
| `@MockitoBean PaymentClient` | 클라이언트 **사용하는 쪽** 로직 | 서비스 테스트 |
| **MockRestServiceServer** (`@RestClientTest`) | `RestClient`/`RestTemplate` 요청·응답 매핑 | 클라이언트 단위 테스트 |
| **WireMock** | 실제 HTTP 서버 흉내 (지연, 타임아웃, 5xx) | 클라이언트 통합 테스트, 장애 시나리오 |

### `@RestClientTest`
```java
@RestClientTest(PaymentClient.class)
class PaymentClientTest {

    @Autowired PaymentClient paymentClient;
    @Autowired MockRestServiceServer server;

    @Test
    void 결제_승인_응답을_변환한다() {
        server.expect(requestTo("https://api.payment.com/v1/payments"))
                .andExpect(method(HttpMethod.POST))
                .andExpect(jsonPath("$.amount").value(10_000))
                .andRespond(withSuccess("""
                        {"transactionId": "TX-1", "status": "APPROVED"}
                        """, MediaType.APPLICATION_JSON));

        PaymentResult result = paymentClient.pay(new PaymentRequest("ORD-1", 10_000));

        assertThat(result.transactionId()).isEqualTo("TX-1");
        server.verify();
    }

    @Test
    void 서버_오류면_예외로_변환한다() {
        server.expect(requestTo("https://api.payment.com/v1/payments"))
                .andRespond(withServerError());

        assertThatThrownBy(() -> paymentClient.pay(new PaymentRequest("ORD-1", 10_000)))
                .isInstanceOf(PaymentException.class);
    }
}
```
> `@RestClientTest`는 `RestClient.Builder`로 클라이언트를 만든 경우에 동작합니다. 생성자에서 `RestClient.create()`로 직접 만들면 Mock 서버가 연결되지 않습니다.

### WireMock (타임아웃·지연 재현)
```java
stubFor(post("/v1/payments")
        .willReturn(aResponse().withStatus(200).withFixedDelay(5_000)));   // 5초 지연
// 클라이언트 read timeout 3초 → 타임아웃 예외가 나는지, 재시도·서킷 브레이커가 동작하는지 검증
```

## 5. 비동기·이벤트 테스트

```java
@Test
void 주문_완료_후_알림이_발송된다() {
    orderService.order(request);       // AFTER_COMMIT 이벤트 → @Async 알림

    await().atMost(Duration.ofSeconds(3))          // Awaitility: 조건이 맞을 때까지 대기
           .untilAsserted(() -> verify(notificationSender).send(any()));
}
```
- `Thread.sleep(3000)` ❌ → 느리고 불안정. **Awaitility** 사용 (`→ 03.테스트설계/04.동시성과시간테스트.md`)
- `@RecordApplicationEvents` + `ApplicationEvents`로 발행된 스프링 이벤트를 검증할 수 있음

## 6. 면접 질문

1. **테스트에 `@Transactional`을 붙이면 생기는 문제는?**
   → 테스트 트랜잭션이 서비스 트랜잭션을 감싸서 운영과 범위가 달라지므로, 서비스에 트랜잭션이 누락되거나 지연 로딩 예외, 커밋 시점 동작(제약 조건, AFTER_COMMIT 이벤트)을 놓칠 수 있습니다.
2. **테스트 간 데이터 격리는 어떻게 하나요?**
   → 레포지토리 테스트는 롤백을 활용하고, 서비스 통합 테스트는 실제로 커밋한 뒤 AfterEach에서 테이블을 truncate하는 정리기를 사용합니다.
3. **외부 API를 호출하는 코드는 어떻게 테스트하나요?**
   → 사용하는 쪽은 클라이언트를 Mock으로 대체하고, 클라이언트 자체는 MockRestServiceServer나 WireMock으로 요청 형식, 응답 변환, 오류·타임아웃 처리를 검증합니다.

---

## 핵심 정리
- 통합 테스트는 **외부 시스템만** Mock, 나머지는 실제
- 테스트 `@Transactional` = 편리하지만 **트랜잭션 누락·지연 로딩·커밋 동작을 숨김**
- 서비스 통합 테스트: **실제 커밋 + `@AfterEach` truncate**
- 외부 API: `@RestClientTest` + MockRestServiceServer, 장애는 **WireMock**
- 비동기는 `sleep` 대신 **Awaitility**
