# 01. 좋은 테스트 작성법

> **학습 목표**
> - 구현이 아니라 **행동**을 테스트해야 하는 이유를 설명할 수 있다.
> - 테스트 이름, 구조, 픽스처를 읽기 좋게 작성할 수 있다.
> - 불안정한(flaky) 테스트의 원인을 알고 제거할 수 있다.
> - 테스트하기 좋은 코드로 설계를 개선할 수 있다.

---

## 1. 좋은 테스트의 네 가지 속성

| 속성 | 의미 | 깨지는 경우 |
|---|---|---|
| **회귀 방지** | 버그를 잡아낸다 | 핵심 로직을 테스트하지 않음 |
| **리팩터링 내성** | 동작이 같으면 구조를 바꿔도 통과 | 내부 구현(private 호출 순서, Mock 호출)을 검증 |
| **빠른 피드백** | 빨리 실행된다 | 매번 스프링 전체를 띄움, sleep |
| **유지 보수성** | 읽고 고치기 쉽다 | 긴 given, 의미 없는 이름, 중복 |
> 블라디미르 코리코프의 「단위 테스트(Unit Testing)」가 정리한 기준입니다. 특히 **리팩터링 내성**이 낮은 테스트는 "거짓 경보"를 울려 팀이 테스트를 신뢰하지 않게 만듭니다.

---

## 2. 구현이 아니라 행동을 테스트하라

```java
// ❌ 구현 검증: 내부에서 어떤 메서드를 어떤 순서로 부르는지
@Test
void 주문() {
    orderService.order(request);
    verify(productRepository).findById(1L);
    verify(product).decreaseStock(2);
    verify(orderRepository).save(any());
}

// ✅ 행동 검증: 결과적으로 무엇이 달라졌는지
@Test
void 주문하면_재고가_줄고_주문이_생성된다() {
    Long orderId = orderService.order(request);

    assertThat(stockOf(productId)).isEqualTo(8);
    assertThat(orderRepository.findById(orderId)).isPresent();
}
```
- **public API를 통해** 검증 (private 메서드를 테스트하고 싶다면 → 별도 클래스로 분리할 신호)
- Mock 검증은 **외부로 나가는 부수 효과**(메일, 결제, 메시지)에만

---

## 3. 테스트 이름

| 나쁜 이름 | 좋은 이름 |
|---|---|
| `test1`, `orderTest` | `재고가_부족하면_주문할_수_없다` |
| `cancel_success` | `배송_전_주문은_취소할_수_있다` |
| `testCalculateDiscountWithGoldGradeReturns9000` | `골드_등급은_10퍼센트_할인된다` |
- 비개발자도 이해할 수 있는 **도메인 언어**로
- "~하면 ~한다" (조건 → 결과)
- 메서드 이름에 구현 용어(`returnsTrue`, `callsRepository`)를 넣지 않기

## 4. 읽기 좋은 테스트 구조

### ① given은 짧고, 테스트에 중요한 값만 드러나게
```java
// ❌ 무엇이 중요한지 알 수 없음
Member member = new Member(null, "kim", "kim@shop.com", "010-1234-5678", Grade.GOLD,
        LocalDate.of(1990, 1, 1), "서울", true, false, LocalDateTime.now());

// ✅ 테스트 데이터 빌더 / 픽스처: 이 테스트에 중요한 값(등급)만 명시
Member member = aMember().grade(Grade.GOLD).build();
```
```java
public class MemberFixture {
    private String name = "kim";
    private String email = "kim@shop.com";
    private Grade grade = Grade.BRONZE;

    public static MemberFixture aMember() { return new MemberFixture(); }
    public MemberFixture grade(Grade grade) { this.grade = grade; return this; }
    public MemberFixture email(String email) { this.email = email; return this; }
    public Member build() { return Member.create(name, email, grade); }
}
```

### ② 테스트에 로직을 넣지 않기
```java
// ❌ 테스트 안에서 기대값을 계산 — 프로덕션 코드와 같은 버그를 복사할 수 있음
long expected = price * (100 - rate) / 100;
assertThat(policy.apply(price)).isEqualTo(expected);

// ✅ 기대값은 리터럴로
assertThat(policy.apply(10_000)).isEqualTo(9_000);
```
- 테스트 안의 `if`, `for`, `try-catch`는 대부분 **테스트를 나누라는 신호**

### ③ `@BeforeEach`에 너무 많이 넣지 않기
- 모든 테스트가 공유하는 준비만 (`@BeforeEach`에 데이터를 잔뜩 넣으면 각 테스트의 given이 보이지 않음)

### ④ 하나의 테스트 = 하나의 행동
```java
// ❌ 한 테스트에서 생성·수정·삭제를 모두
// ✅ 테스트 3개로 나누기 (실패 시 원인이 바로 보임)
```

## 5. 불안정한 테스트 (Flaky Test)

같은 코드인데 **가끔 실패**하는 테스트. 팀이 "또 그거네" 하며 무시하기 시작하면 테스트 전체의 신뢰가 무너집니다.
| 원인 | 해결 |
|---|---|
| **현재 시간** (`LocalDateTime.now()`) | `Clock` 주입 (`→ 04.동시성과시간테스트.md`) |
| 랜덤 값 | 시드 고정, 값 주입 |
| **테스트 간 데이터 공유** | 데이터 격리 (`→ 02.스프링테스트/05.통합테스트와격리.md`) |
| 실행 순서 의존 | 각 테스트가 자기 데이터를 준비 |
| `Thread.sleep`으로 비동기 대기 | **Awaitility** |
| 컬렉션 순서 가정 (`HashSet`, ORDER BY 없는 쿼리) | `containsExactlyInAnyOrder`, 쿼리에 정렬 |
| 외부 API·네트워크 | Mock/WireMock |
| 타임존·로케일 | `ZoneId` 명시, CI 타임존 고정 |
| 부동소수점 | `isCloseTo` |

## 6. 테스트하기 좋은 코드 = 좋은 설계

```java
// ❌ 테스트하기 어려움: 시간·외부 의존을 내부에서 직접 생성
public class CouponService {
    public void issue(Long memberId) {
        if (LocalDate.now().isAfter(LocalDate.of(2026, 12, 31))) throw ...;
        new KakaoNotifier().send(memberId, "쿠폰 발급");
    }
}

// ✅ 의존성 주입 → 테스트에서 교체 가능
@Service
@RequiredArgsConstructor
public class CouponService {
    private final Clock clock;
    private final Notifier notifier;      // 인터페이스

    public void issue(Long memberId) {
        if (LocalDate.now(clock).isAfter(END_DATE)) throw ...;
        notifier.send(memberId, "쿠폰 발급");
    }
}
```
### 도메인 로직을 엔티티·값 객체로 → 순수 단위 테스트
```java
// 서비스가 계산을 다 하면 서비스 테스트(Mock 많음)로만 검증 가능
// 도메인 객체가 계산하면 new 만으로 빠르게 테스트
class OrderTest {
    @Test
    void 주문_총액은_상품가격_곱하기_수량의_합이다() {
        Order order = Order.create(List.of(line(1000, 2), line(500, 3)));
        assertThat(order.totalPrice()).isEqualTo(3_500);
    }
}
```
> 테스트가 쓰기 어렵다면 테스트 기술이 아니라 **설계를 의심**하세요: 책임이 너무 많은 클래스, 숨겨진 의존성, static·싱글톤 남용.

## 7. 면접 질문

1. **좋은 테스트란 무엇인가요?**
   → 버그를 잡아내고, 내부 구현을 바꿔도 동작이 같으면 깨지지 않으며, 빠르고 읽기 쉬운 테스트입니다. 이를 위해 구현이 아닌 행동을 public API로 검증하고, 이름은 도메인 언어로 작성합니다.
2. **Flaky 테스트의 원인과 해결은?**
   → 현재 시간, 랜덤, 테스트 간 데이터 공유, sleep 기반 비동기 대기, 순서 가정 등이 원인이며, Clock 주입, 데이터 격리, Awaitility, 순서 무관 검증으로 해결합니다.
3. **private 메서드는 어떻게 테스트하나요?**
   → 직접 테스트하지 않고 public 메서드를 통해 간접적으로 검증합니다. 별도로 테스트하고 싶을 만큼 복잡하다면 별도 클래스로 분리하는 것이 좋습니다.

---

## 핵심 정리
- 좋은 테스트 = **회귀 방지 + 리팩터링 내성 + 빠름 + 유지 보수성**
- **행동(결과)을 검증**, Mock 검증은 외부 부수 효과만
- 이름은 도메인 언어, given은 **중요한 값만** (픽스처·빌더), 기대값은 리터럴
- Flaky 원인 제거: 시간·랜덤·공유 데이터·sleep·순서
- 테스트가 어려우면 **설계 개선 신호**
