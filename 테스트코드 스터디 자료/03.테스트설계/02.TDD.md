# 02. TDD (Test-Driven Development)

> **학습 목표**
> - TDD의 Red-Green-Refactor 사이클을 설명하고 실습할 수 있다.
> - TDD의 장점과 한계를 균형 있게 설명할 수 있다.
> - 인사이드아웃·아웃사이드인 방식의 차이를 이해한다.
> - BDD와의 관계를 안다.

---

## 1. TDD란?

**테스트를 먼저 작성하고, 그 테스트를 통과하는 최소한의 코드를 작성한 뒤, 리팩터링**하는 개발 방법 (켄트 벡)

```
     ┌──────────┐
     │  🔴 Red   │  실패하는 테스트 작성 (아직 구현 없음 → 컴파일 에러도 실패)
     └────┬─────┘
          ▼
     ┌──────────┐
     │ 🟢 Green  │  테스트를 통과하는 "최소한"의 코드 (하드코딩도 OK)
     └────┬─────┘
          ▼
     ┌──────────┐
     │🔵Refactor │  중복 제거, 이름 개선, 구조 정리 (테스트는 계속 통과)
     └────┬─────┘
          └──────▶ 다시 Red (다음 요구사항)
```

## 2. 실습: 비밀번호 검증기

요구사항: 비밀번호는 **8자 이상**, **숫자 포함**, **대문자 포함**이어야 한다.

### 🔴 Red: 첫 테스트
```java
class PasswordValidatorTest {
    PasswordValidator validator = new PasswordValidator();

    @Test
    void 조건을_모두_만족하면_유효하다() {
        assertThat(validator.isValid("Abcdefg1")).isTrue();
    }
}
// PasswordValidator가 없음 → 컴파일 실패 = Red
```

### 🟢 Green: 최소 구현
```java
public class PasswordValidator {
    public boolean isValid(String password) {
        return true;              // 일단 통과만
    }
}
```

### 🔴 Red: 다음 테스트로 구현을 강제
```java
@Test
void 여덟_자_미만이면_유효하지_않다() {
    assertThat(validator.isValid("Abcde1")).isFalse();
}
```

### 🟢 Green
```java
public boolean isValid(String password) {
    return password.length() >= 8;
}
```

### 🔴 → 🟢 숫자, 대문자 조건 추가
```java
@ParameterizedTest
@ValueSource(strings = {"Abcdefgh", "abcdefg1", "Abc1"})   // 숫자 없음, 대문자 없음, 짧음
void 조건을_하나라도_만족하지_않으면_유효하지_않다(String password) {
    assertThat(validator.isValid(password)).isFalse();
}

@ParameterizedTest
@NullAndEmptySource
void null이나_빈_문자열은_유효하지_않다(String password) {
    assertThat(validator.isValid(password)).isFalse();
}
```
```java
public boolean isValid(String password) {
    if (password == null) return false;
    return password.length() >= 8
            && password.chars().anyMatch(Character::isDigit)
            && password.chars().anyMatch(Character::isUpperCase);
}
```

### 🔵 Refactor: 규칙을 객체로 분리 (확장 대비)
```java
public class PasswordValidator {
    private static final int MIN_LENGTH = 8;
    private final List<Predicate<String>> rules = List.of(
            p -> p.length() >= MIN_LENGTH,
            p -> p.chars().anyMatch(Character::isDigit),
            p -> p.chars().anyMatch(Character::isUpperCase)
    );

    public boolean isValid(String password) {
        return password != null && rules.stream().allMatch(rule -> rule.test(password));
    }
}
// 테스트가 모두 통과하므로 리팩터링이 안전함을 확인
```

## 3. TDD의 장점과 한계

| 장점 | 한계·비판 |
|---|---|
| **요구사항을 먼저 명확히** 생각하게 됨 | 익숙해지기까지 초기 속도가 느림 |
| 테스트하기 쉬운 구조(작은 단위, DI)가 자연스럽게 | 요구사항이 불명확한 탐색·프로토타입 단계엔 부적합 |
| 높은 테스트 커버리지가 부산물로 | UI, 외부 연동, 인프라 코드는 적용 어려움 |
| **리팩터링 안전망** | 잘못된 테스트를 먼저 만들면 잘못된 설계가 굳어짐 |
| 작은 단계 → 디버깅 시간 감소 | "100% TDD"를 강요하면 형식주의 |
> 실무에서는 **도메인 로직, 계산, 규칙이 복잡한 부분**에 TDD를 적용하고, 나머지는 구현 후 테스트를 작성하는 경우가 많습니다. 면접에서는 "모든 곳에 쓴다"보다 **적용한 경험과 기준**을 말하는 것이 좋습니다.

## 4. 인사이드아웃 vs 아웃사이드인

| | 인사이드아웃 (Classic, Detroit) | 아웃사이드인 (London, Mockist) |
|---|---|---|
| 시작점 | **도메인 객체**부터 (Order, Money) | **바깥(컨트롤러·인수 테스트)** 부터 |
| 협력 객체 | 실제 객체 사용 | Mock으로 대체하며 안쪽으로 |
| 장점 | 리팩터링 내성 ↑, 도메인 설계에 집중 | 필요한 인터페이스가 먼저 드러남 (YAGNI) |
| 단점 | 사용되지 않는 코드가 생길 수 있음 | Mock이 많아 구현에 묶이기 쉬움 |

## 5. BDD (Behavior-Driven Development)

TDD를 **비즈니스 행동** 중심으로 확장한 방법. 개발자·기획자·QA가 같은 언어(시나리오)로 요구사항을 정의합니다.
```gherkin
Feature: 주문 취소
  Scenario: 배송 전 주문은 취소할 수 있다
    Given 결제가 완료된 주문이 있다
    When 회원이 주문을 취소한다
    Then 주문 상태는 "취소"가 된다
    And 결제가 환불된다
```
- 도구: Cucumber, (Kotlin) Kotest BehaviorSpec
- JUnit의 Given-When-Then 주석, BDDMockito, `@DisplayName`도 같은 철학

## 6. 면접 질문

1. **TDD란? 사이클을 설명해 주세요.**
   → 테스트를 먼저 작성하는 개발 방법으로, 실패하는 테스트를 작성하는 Red, 통과하는 최소 코드를 작성하는 Green, 테스트를 유지하며 구조를 개선하는 Refactor를 반복합니다.
2. **TDD의 장단점은?**
   → 요구사항을 먼저 구체화하고 테스트하기 쉬운 설계와 리팩터링 안전망을 얻지만, 초기 속도가 느리고 요구사항이 불명확하거나 외부 연동이 많은 코드에는 적용이 어렵습니다.
3. **TDD를 실제로 적용해 본 경험이 있나요?**
   → (예시) 할인 정책처럼 규칙이 많은 도메인 로직에 TDD를 적용해 경계값 테스트를 먼저 정의했고, 이후 정책이 추가될 때 테스트 덕분에 안전하게 리팩터링할 수 있었습니다.

---

## 핵심 정리
- **Red → Green(최소 구현) → Refactor** 반복, 작은 단계
- 장점: 요구사항 명확화, 테스트 가능한 설계, 안전한 리팩터링
- 한계: 초기 비용, 탐색·UI·외부 연동엔 부적합 → **복잡한 도메인 로직에 선택 적용**
- 인사이드아웃(실제 객체) vs 아웃사이드인(Mock), BDD = 행동·시나리오 중심
