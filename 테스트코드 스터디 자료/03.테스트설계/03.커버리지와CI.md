# 03. 테스트 커버리지와 CI

> **학습 목표**
> - 라인·브랜치 커버리지의 의미와 한계를 설명할 수 있다.
> - JaCoCo로 커버리지를 측정하고 기준 미달 시 빌드를 실패시킬 수 있다.
> - GitHub Actions에서 테스트를 자동 실행하고 결과를 PR에 반영할 수 있다.
> - 테스트가 느려졌을 때 개선하는 방법을 안다.

---

## 1. 커버리지란?

**테스트가 실행한 코드의 비율**입니다.
| 종류 | 측정 대상 | 예 |
|---|---|---|
| 라인(Line) | 실행된 줄 | 100줄 중 80줄 → 80% |
| **브랜치(Branch)** | `if`/`switch`의 **각 분기** | `if (a && b)`의 참/거짓 경우 |
| 메서드·클래스 | 한 번이라도 호출된 메서드·클래스 | |

```java
public long discount(long price, Grade grade) {
    if (grade == Grade.GOLD) return price * 90 / 100;
    return price;
}
// GOLD 테스트만 있으면: 라인 2/2 = 100%, 브랜치 1/2 = 50%
```
> 라인 커버리지보다 **브랜치 커버리지**가 실제로 검증한 경우의 수를 더 잘 보여 줍니다.

## 2. 커버리지의 한계

```java
@Test
void 할인() {
    discountPolicy.discount(10_000, Grade.GOLD);   // 실행만 하고 검증(assert) 없음
}
// 커버리지는 올라가지만 아무것도 검증하지 않음
```
| 커버리지가 알려 주는 것 | 알려 주지 않는 것 |
|---|---|
| **테스트되지 않은 코드** (빨간 줄) | 테스트가 **올바르게 검증하는지** |
| | 경계값·예외 상황을 충분히 다뤘는지 |
| | 요구사항이 맞게 구현됐는지 |

- 커버리지는 **목표가 아니라 지표**입니다. 100%를 강요하면 검증 없는 테스트, getter 테스트가 늘어납니다.
- 보통 **도메인·서비스 계층 70~80%** 정도를 기준으로 삼고, DTO·설정·생성 코드는 제외합니다.
- 테스트의 질을 보려면 **뮤테이션 테스트**(PIT): 코드를 일부러 바꿨을 때(`>` → `>=`) 테스트가 실패하는지 확인

## 3. JaCoCo 설정 (Gradle)

```groovy
plugins {
    id 'jacoco'
}

jacoco {
    toolVersion = '0.8.13'
}

test {
    useJUnitPlatform()
    finalizedBy jacocoTestReport               // 테스트 후 리포트 생성
}

def excludes = ['**/dto/**', '**/config/**', '**/*Application*', '**/Q*.class', '**/exception/**']

jacocoTestReport {
    dependsOn test
    reports {
        html.required = true                   // build/reports/jacoco/test/html/index.html
        xml.required = true                    // CI·SonarQube 연동용
    }
    afterEvaluate {
        classDirectories.setFrom(files(classDirectories.files.collect {
            fileTree(dir: it, exclude: excludes)
        }))
    }
}

jacocoTestCoverageVerification {
    violationRules {
        rule {
            element = 'CLASS'
            limit {
                counter = 'BRANCH'
                value = 'COVEREDRATIO'
                minimum = 0.70                 // 브랜치 70% 미만이면 빌드 실패
            }
            excludes = ['*.dto.*', '*.config.*', '*Application']
        }
    }
}

check.dependsOn jacocoTestCoverageVerification
```
```bash
./gradlew test jacocoTestReport          # 리포트 생성
./gradlew check                          # 기준 검증 포함
```
> QueryDSL Q클래스(`Q*.class`), Lombok 생성 코드는 제외합니다. Lombok은 `lombok.config`에 `lombok.addLombokGeneratedAnnotation = true`를 두면 JaCoCo가 자동으로 제외합니다.

## 4. CI에서 테스트 자동 실행 (GitHub Actions)

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      checks: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'

      - uses: gradle/actions/setup-gradle@v4      # Gradle 캐시

      - name: Test
        run: ./gradlew check                      # Testcontainers는 러너의 Docker 사용

      - name: Test Report
        if: always()
        uses: mikepenz/action-junit-report@v5
        with:
          report_paths: '**/build/test-results/test/TEST-*.xml'

      - name: Upload coverage report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: jacoco-report
          path: build/reports/jacoco/test/html
```
### 팀 규칙으로 만들기
| 규칙 | 설정 |
|---|---|
| 테스트 실패 시 머지 금지 | GitHub **Branch protection** → Required status checks에 `test` 지정 |
| 커버리지 하락 표시 | PR 코멘트 액션(jacoco-report 등), Codecov, SonarQube Quality Gate |
| 느린 테스트 분리 | `@Tag("slow")` → PR에서는 제외, 야간 빌드에서 실행 |
> 배포 파이프라인 전체(빌드 → 이미지 → 배포)는 `인프라 스터디 자료`의 CI/CD 문서를 참고하세요.

## 5. 테스트가 느릴 때

| 원인 | 개선 |
|---|---|
| **스프링 컨텍스트 재생성** | `@MockitoBean`·프로필 조합 통일 (공통 부모), `@DirtiesContext` 제거 |
| 단위로 충분한데 `@SpringBootTest` | 순수 단위 테스트·슬라이스 테스트로 |
| 클래스마다 컨테이너 시작 | 컨테이너 공유 (`→ 02.스프링테스트/04.Testcontainers.md`) |
| `Thread.sleep` | Awaitility |
| 순차 실행 | Gradle `maxParallelForks`, JUnit 병렬 실행 (공유 자원·DB 데이터 충돌 주의) |
| Gradle 빌드 | 빌드 캐시, 설정 캐시, 변경된 모듈만 테스트 |

```groovy
test {
    maxParallelForks = Runtime.runtime.availableProcessors().intdiv(2) ?: 1   // JVM 여러 개로 병렬
}
```
> Gradle 테스트 리포트(`build/reports/tests/test/index.html`)에서 **오래 걸리는 테스트 클래스**를 먼저 찾으세요.

## 6. 면접 질문

1. **커버리지가 높으면 좋은 테스트인가요?**
   → 아닙니다. 커버리지는 실행된 코드의 비율일 뿐 올바르게 검증했는지는 알려 주지 않습니다. 테스트되지 않은 영역을 찾는 지표로 쓰고, 핵심 로직의 브랜치 커버리지와 경계값·예외 테스트를 중시합니다.
2. **라인 커버리지와 브랜치 커버리지의 차이는?**
   → 라인은 실행된 코드 줄의 비율이고, 브랜치는 조건문의 각 분기(참·거짓)가 실행된 비율로, 조건 분기 검증 여부를 더 정확히 보여 줍니다.
3. **CI에서 테스트를 어떻게 운영했나요?**
   → (예시) PR마다 GitHub Actions에서 테스트와 JaCoCo 커버리지 검증을 실행하고, 브랜치 보호 규칙으로 실패 시 머지를 막았습니다.

---

## 핵심 정리
- 커버리지 = 실행된 코드 비율, **브랜치 커버리지**가 더 의미 있음
- **지표이지 목표가 아님** — 검증 없는 테스트로 올릴 수 있음, 질은 뮤테이션 테스트로
- JaCoCo: 리포트 + `jacocoTestCoverageVerification`으로 기준 미달 시 실패
- CI: PR마다 테스트 + **브랜치 보호로 머지 차단**
- 느리면 **컨텍스트 캐시·컨테이너 공유·sleep 제거**부터
