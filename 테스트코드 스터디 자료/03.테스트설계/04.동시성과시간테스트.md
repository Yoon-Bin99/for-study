# 04. 동시성 테스트와 시간 테스트

> **학습 목표**
> - `ExecutorService` + `CountDownLatch`로 동시 요청 상황을 재현하는 테스트를 작성할 수 있다.
> - 동시성 테스트에서 트랜잭션·데이터 정리 주의점을 안다.
> - `Clock` 주입으로 현재 시간에 의존하는 코드를 테스트할 수 있다.
> - 비동기 코드를 Awaitility로 안정적으로 테스트할 수 있다.

---

## 1. 동시성 테스트가 필요한 이유

재고 차감, 쿠폰 발급, 좋아요 수 같은 기능은 **한 명씩 요청할 때는 항상 정상**입니다. 문제는 동시에 요청이 몰릴 때만 드러납니다.
> 갱신 분실과 해결책(락)은 `Spring JPA 스터디 자료의 03.JPA실전/05.동시성과락.md`, 자바 동시성 도구는 `JAVA·JVM 스터디 자료의 05.동시성/04.동시성유틸과ThreadLocal.md`를 참고하세요.

## 2. 동시 요청 재현하기

```java
class StockConcurrencyTest extends IntegrationTestSupport {    // @SpringBootTest, @Transactional 없음!

    @Autowired StockService stockService;
    @Autowired ProductRepository productRepository;

    @Test
    void 동시에_100명이_1개씩_주문하면_재고가_0이_된다() throws InterruptedException {
        // given
        Product product = productRepository.save(Product.create("한정판", 10_000, 100));
        int threadCount = 100;
        ExecutorService executor = Executors.newFixedThreadPool(32);
        CountDownLatch ready = new CountDownLatch(threadCount);   // 모두 준비될 때까지
        CountDownLatch start = new CountDownLatch(1);             // 동시에 출발
        CountDownLatch done = new CountDownLatch(threadCount);    // 모두 끝날 때까지
        AtomicInteger success = new AtomicInteger();
        AtomicInteger fail = new AtomicInteger();

        // when
        for (int i = 0; i < threadCount; i++) {
            executor.submit(() -> {
                ready.countDown();
                try {
                    start.await();
                    stockService.decrease(product.getId(), 1);
                    success.incrementAndGet();
                } catch (Exception e) {
                    fail.incrementAndGet();
                } finally {
                    done.countDown();
                }
            });
        }
        ready.await();
        start.countDown();                                   // 출발 신호
        boolean finished = done.await(10, TimeUnit.SECONDS); // 무한 대기 방지
        executor.shutdown();

        // then
        assertThat(finished).isTrue();
        assertThat(success.get()).isEqualTo(100);
        assertThat(productRepository.findById(product.getId()).orElseThrow().getStock()).isZero();
    }

    @Test
    void 재고보다_많은_요청이_오면_재고만큼만_성공한다() throws InterruptedException {
        // 재고 10, 요청 50 → 성공 10, 실패 40, 재고 0 (음수가 되면 안 됨)
    }
}
```
| 도구 | 역할 |
|---|---|
| `ExecutorService` | 여러 스레드로 요청 실행 |
| `CountDownLatch` | 출발을 맞추고(start), 모두 끝날 때까지 대기(done) |
| `AtomicInteger` | 스레드 안전하게 성공·실패 횟수 집계 |
| `done.await(timeout)` | 데드락 시 테스트가 영원히 멈추지 않게 |

### 락이 없는 코드로 먼저 실패를 확인하라
```
1. 락 없이 테스트 실행 → 재고가 0이 아닌 값(예: 37)으로 실패하는 것을 확인 (문제 재현)
2. 원자적 UPDATE / 비관적 락 / 낙관적 락 + 재시도 적용
3. 같은 테스트가 통과하는지 확인
```
> 처음부터 통과하는 동시성 테스트는 **문제를 재현하지 못하고 있을 가능성**이 있습니다. 스레드 수, 풀 크기, HikariCP 풀 크기를 조절해 실제로 경합이 일어나는지 확인하세요.

## 3. 동시성 테스트 주의점

| 주의점 | 이유 |
|---|---|
| **테스트에 `@Transactional` 금지** | 각 스레드는 별도 트랜잭션 → 테스트 트랜잭션이 커밋되지 않아 다른 스레드가 데이터를 못 봄, 롤백도 안 됨 |
| 데이터 정리 | `@AfterEach`에서 truncate (`→ 02.스프링테스트/05.통합테스트와격리.md`) |
| 실제 DB 사용 | H2와 MySQL의 락·격리 동작이 다름 → **Testcontainers** |
| 커넥션 풀 | 스레드 수 > 풀 크기면 커넥션 대기 → 타임아웃 설정 확인 |
| 결과의 비결정성 | 통과해도 "운이 좋았을" 수 있음 → `@RepeatedTest`로 여러 번 |
| 테스트 시간 | 무거우므로 `@Tag("concurrency")`로 분리 가능 |

## 4. 시간에 의존하는 코드 테스트: Clock

```java
// ❌ 테스트할 수 없는 코드: 실행하는 시각에 따라 결과가 다름
public boolean isEventPeriod() {
    LocalDateTime now = LocalDateTime.now();
    return now.isAfter(START) && now.isBefore(END);
}
```
### Clock 주입
```java
@Configuration
public class ClockConfig {
    @Bean
    public Clock clock() {
        return Clock.system(ZoneId.of("Asia/Seoul"));
    }
}

@Service
@RequiredArgsConstructor
public class CouponService {
    private final Clock clock;

    public void issue(Long memberId) {
        LocalDateTime now = LocalDateTime.now(clock);
        if (now.isBefore(EVENT_START) || !now.isBefore(EVENT_END)) {
            throw new BusinessException(ErrorCode.NOT_EVENT_PERIOD);
        }
        // ...
    }
}
```
```java
class CouponServiceTest {

    static final ZoneId SEOUL = ZoneId.of("Asia/Seoul");

    @Test
    void 이벤트_시작_시각_정각에는_발급된다() {
        Clock fixed = Clock.fixed(
                LocalDateTime.of(2026, 12, 1, 0, 0).atZone(SEOUL).toInstant(), SEOUL);
        CouponService service = new CouponService(fixed /*, 그 밖의 의존성 */);

        assertThatNoException().isThrownBy(() -> service.issue(1L));
    }

    @Test
    void 이벤트_종료_시각이_되면_발급되지_않는다() {
        Clock fixed = Clock.fixed(
                LocalDateTime.of(2026, 12, 8, 0, 0).atZone(SEOUL).toInstant(), SEOUL);
        CouponService service = new CouponService(fixed);

        assertThatThrownBy(() -> service.issue(1L))
                .isInstanceOf(BusinessException.class);
    }
}
```
### 또 다른 방법: 시간을 파라미터로
```java
// 도메인 메서드는 시간을 인자로 받으면 Clock조차 필요 없음
public boolean isExpired(LocalDateTime now) {
    return !now.isBefore(expiredAt);
}
// 호출하는 쪽(서비스)에서만 LocalDateTime.now(clock)
```
| 테스트할 시간 경계 | 예 |
|---|---|
| 시작·종료 **정각** | 00:00:00, 23:59:59 |
| 날짜 변경 | 자정, 월말, **윤년 2월 29일** |
| 타임존 | UTC 서버 vs KST 기준 마감 |
| 만료 | 토큰·쿠폰 만료 직전·직후 |

> 스프링 통합 테스트에서는 `@TestConfiguration`에 고정 Clock 빈을 `@Primary`로 등록하거나 `@MockitoBean Clock`을 사용합니다.

## 5. 비동기 테스트: Awaitility

```java
// ❌ 언제 끝날지 모르니 넉넉히 sleep → 느리고, 그래도 가끔 실패
Thread.sleep(3000);
assertThat(notificationRepository.count()).isEqualTo(1);

// ✅ 조건이 만족될 때까지 폴링, 최대 시간만 지정
await().atMost(Duration.ofSeconds(5))
       .pollInterval(Duration.ofMillis(100))
       .untilAsserted(() ->
               assertThat(notificationRepository.count()).isEqualTo(1));
```
```groovy
testImplementation 'org.awaitility:awaitility'   // Spring Boot가 버전 관리
```
- `@Async`, `@TransactionalEventListener`, Kafka 컨슈머, 스케줄러 결과 검증에 사용
- "일어나지 않아야 하는 것"은 `during(Duration.ofSeconds(1))`로 일정 시간 동안 조건 유지 확인

### 스케줄러 테스트
```java
// @Scheduled 메서드는 스케줄을 기다리지 말고 메서드를 직접 호출해 로직을 검증
```

## 6. 면접 질문

1. **동시성 문제를 어떻게 테스트하나요?**
   → ExecutorService로 여러 스레드에서 동시에 요청하고 CountDownLatch로 출발을 맞춘 뒤 모두 끝날 때까지 기다려 최종 상태를 검증합니다. 먼저 락 없이 실패를 재현하고, 해결책을 적용해 통과하는지 확인합니다.
2. **동시성 테스트에 `@Transactional`을 붙이면?**
   → 각 스레드는 별도 트랜잭션으로 실행되므로 테스트 트랜잭션에서 저장한 데이터가 커밋되지 않아 보이지 않고, 스레드들의 변경은 롤백되지 않아 데이터가 남습니다. 트랜잭션 없이 실행하고 직접 정리합니다.
3. **현재 시간에 의존하는 코드는 어떻게 테스트하나요?**
   → Clock을 빈으로 주입받아 LocalDateTime.now(clock)을 사용하고, 테스트에서는 Clock.fixed로 원하는 시각을 고정해 경계값을 검증합니다.

---

## 핵심 정리
- 동시성: **ExecutorService + CountDownLatch(ready/start/done) + AtomicInteger**
- **락 없이 실패 재현 → 해결 → 통과** 순서, `@Transactional` 금지, 실제 DB
- 시간: **`Clock` 주입 + `Clock.fixed`**, 도메인은 시간을 파라미터로
- 비동기: `Thread.sleep` 대신 **Awaitility `await().untilAsserted()`**
